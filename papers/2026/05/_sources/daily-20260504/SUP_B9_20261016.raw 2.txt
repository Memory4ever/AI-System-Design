L162: kimi CLI 1.40.0
L163: SDK v0.0.0-20260421134432-b232049415ff
L164: Go 1.26.2
L165: Auth OAuth (~/.kimi/credentials/kimi-code.json)

L167: Reproduction
L168: Run the exact example from the README:
L169: package main
L170: 
L171: import (
L172: "context"
L173: "fmt"
L174: 
L175:     `  kimi "github.com/MoonshotAI/kimi-agent-sdk/go"
L176:       "github.com/MoonshotAI/kimi-agent-sdk/go/wire"
L177:     `
L178: 
L179: )
L180: func main() {
L181: session, err := kimi.NewSession(kimi.WithAutoApprove())
L182: if err != nil {
L183: panic(err)
L184: }
L185: defer session.Close()
L186: 
L187:     `  turn, err := session.Prompt(context.Background(), wire.NewStringContent("hello"))
L188:       if err != nil {
L189:           panic(err)
L190:       }
L191: 
L192:       // This loop never completes — deadlock
L193:       for step := range turn.Steps {
L194:           for msg := range step.Messages {
L195:               fmt.Printf("%T\n", msg)
L196:           }
L197:       }
L198: 
L199:       fmt.Println("Done") // never reached
L200:     `
L201: }
L202: Expected behavior
L203: turn.Steps should eventually close after all events are consumed, and the program should print Done.
L204: Actual behavior
L205: turn.Steps never closes. The program hangs indefinitely.
L206: • turn.Result().Status remains "pending" forever.
L207: • session.Close() also hangs.
L208: • Sending SIGQUIT (or pprof goroutine dump) reveals the following goroutine stack:
L209: goroutine [recv]:
L210: github.com/MoonshotAI/kimi-agent-sdk/go/wire/jsonrpc2.(*Codec).recv
L211: codec.go:389 // blocked on c.inreqs <- payload
L212: goroutine [ReadResponseHeader]:
L213: github.com/MoonshotAI/kimi-agent-sdk/go/wire/jsonrpc2.(*Codec).ReadResponseHeader
L214: codec.go:584 // blocked on c.inress
L215: goroutine [Prompt RPC]:
L216: net/rpc.(*Client).Call
L217: client.go:321 // waiting for Prompt response
L218: Root cause analysis
L219: kimi CLI v1.40.0 emits two new event types during MCP initialization:
L220: {"jsonrpc":"2.0","method":"event","params":{"type":"MCPLoadingBegin","payload":{}}}
L221: {"jsonrpc":"2.0","method":"event","params":{"type":"MCPLoadingEnd","payload":{}}}
L222: However, the SDK's eventUnmarshaler map in wire/message.go does not contain handlers for MCPLoadingBegin or MCPLoadingEnd:
L223: var eventUnmarshaler = map[EventType]func(data []byte) (Event, error){
L224: // ...
L225: // MCPLoadingBegin and MCPLoadingEnd are MISSING
L226: }
L227: When ServeRequest tries to process one of these events, EventParams.UnmarshalJSON returns:
L228: unknown event type: "MCPLoadingBegin"
L229: This causes ReadRequestBody to fail, ServeRequest to exit with an error, and session.serve to stop consuming requests. The recv goroutine then blocks forever trying to push the next event into the now-unread c.inreqs channel. Bec
L230: ause recv is blocked, it can never decode the final PromptResult response, so rpc.Client.Call("Transport.Prompt") never returns — and turn.Steps is never closed.
L231: Verification
L232: I confirmed this by:
L233:   1. Manual JSON-RPC test: Talking directly to kimi --wire with Python shows the full event stream is healthy, including MCPLoadingBegin → MCPLoadingEnd → TurnEnd → PromptResult(status=finished).
L234:   2. SDK patch test: Adding the two missing event types to wire/message.go resolves the deadlock immediately.
L235: Suggested fix
L236: Add MCPLoadingBegin and MCPLoadingEnd to the SDK's event type registry:
L237: // wire/message.go
L238: type MCPLoadingBegin struct{}
L239: type MCPLoadingEnd struct{}
L240: func (MCPLoadingBegin) message() {}
L241: func (MCPLoadingEnd) message() {}
L242: 
L243: func (MCPLoadingBegin) EventType() EventType { return EventTypeMCPLoadingBegin }
L244: func (MCPLoadingEnd) EventType() EventType { return EventTypeMCPLoadingEnd }
L245: 
L246: const (
L247: // ...
L248: EventTypeMCPLoadingBegin EventType = "MCPLoadingBegin"
L249: EventTypeMCPLoadingEnd EventType = "MCPLoadingEnd"
L250: )
L251: var eventUnmarshaler = map[EventType]func(data []byte) (Event, error){
L252: // ...
L253: EventTypeMCPLoadingBegin: unmarshalEvent[MCPLoadingBegin],
L254: EventTypeMCPLoadingEnd: unmarshalEvent[MCPLoadingEnd],
L255: }
L256: Alternatively, making EventParams.UnmarshalJSON gracefully skip unknown event types (with a warning or log) instead of returning a hard error would prevent future CLI versions from breaking the SDK.

L154: ## Summary
L155: 
L156: Kimi CLI supports a rich hook system via `[[hooks]]` with events like `PreToolUse`, which is great for blocking dangerous actions. However, there is currently no way for hooks to auto-approve safe, routine operations — every gated tool call still requires manual user confirmation.
L157: ## Request
L158: 
L159: Please add a PermissionRequest (or equivalent) hook event that fires when the CLI is about to prompt the user for tool approval. Hooks attached to this event should be able to return a programmatic approval decision, similar to how Claude Code handles it.
L160: ## Motivation / Use Case
L161: 
L162: Users who run Kimi for extended sessions repeatedly approve the same categories of safe operations:
L163: 
L164:   * Compound git commands: `cd src && git status && git add . && git commit -m "fix"`
L165:   * Safe make targets: `make build && make test`
L166:   * npm/npx workflows: `npm run dev && npx prettier --write .`
L167:   * Reading predictable generated artifacts: `~/.<tool>/worktree/<slug>/sdlc/tickets/*.md` or `<project>/generated/sdlc/*.md`
L168: A PermissionRequest hook would let power users write small shell scripts that inspect the incoming tool call JSON and approve known-safe patterns automatically. This dramatically reduces friction without sacrificing safety, because the same hook infrastructure can still block dangerous commands via PreToolUse.
L169: ## Proposed Hook Contract
L170: 
L171: The hook receives the same JSON payload as PreToolUse (`tool_name`, `tool_input`, etc.). It returns JSON on stdout:
L172: 
L173:     {
L174:       "hookSpecificOutput": {
L175:         "hookEventName": "PermissionRequest",
L176:         "permissionDecision": "allow",
L177:         "permissionDecisionReason": "Allowed: compound git command (all parts are safe git ops)"
L178:       }
L179:     }
L180: If the hook exits 0 without printing this JSON, or if no PermissionRequest hook matches, the CLI falls back to the normal interactive prompt.
L181: ## Prior Art
L182: 
L183: Claude Code implements exactly this via its `settings.json` hooks block:
L184: 
L185:     {
L186:       "hooks": {
L187:         "PermissionRequest": [
L188:           { "matcher": "Bash", "hooks": [...] },
L189:           { "matcher": "Read", "hooks": [...] }
L190:         ],
L191:         "PreToolUse": [
L192:           { "matcher": "Bash", "hooks": [...] }
L193:         ]
L194:       }
L195:     }
L196: 
L197: This dual-hook model (PermissionRequest for frictionless safe ops + PreToolUse for hard blocks) is very effective in practice.
L198: ## Alternative Considered
L199: 
L200: Using `--yolo` mode disables all approval prompts, which is too broad — it also approves destructive operations that PreToolUse hooks might not catch. A PermissionRequest hook gives fine-grained, auditable control per command pattern.

L204:   * Kimi CLI version: 1.40.0
L205:   * OS: macOS
