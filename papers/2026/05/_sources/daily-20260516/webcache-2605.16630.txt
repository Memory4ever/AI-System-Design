L59: # PrivScope: Task-scoped Disclosure Control for Hybrid Agentic Systems
L60: 
L61: Shafizur Rahman Seeam^{1}, Zhengxiong Li^{2}, Zhiyuan Yu^{3}, Yimin (Ian) Chen^{4}, Yidan Hu^{1} Affiliation: ^{1}Rochester Institute of Technology, Rochester, NY, USA
L62: ^{2}University of Colorado Denver, Denver, CO, USA
L63: ^{3}Texas A&M University, College Station, TX, USA
L64: ^{4}University of Massachusetts Lowell, Lowell, MA, USA
L65: {ss6365, yidan.hu}@rit.edu, zhengxiong.li@ucdenver.edu, zhiyuanyu@tamu.edu, ian_chen@uml.edu
L66: ###### Abstract
L67: Hybrid local–cloud agents enrich user requests with context from persistent working state before delegating capability-intensive subtasks to a cloud language model (CLM). While enriching the payload with this context can improve task success, it can also expose unnecessary information in the cloud-bound payload, including task-irrelevant context, carryover from prior workflows, and overly specific sensitive details, resulting in over-disclosure.
L68: Existing solutions either isolate agentic workflows to limit cross-workflow leakage or apply general-purpose sanitization mechanisms that do not reason over LC-assembled payload scope.
L69: We present PrivScope, a trusted on-device payload governor that enforces task-scoped disclosure at the boundary between the local controller and the CLM, without requiring cloud-side changes. Its key idea is that sensitive information, including carryover from prior workflows, should reach the cloud only when required for the delegated subtask, and even then only in the least revealing form that still preserves task utility.
L70: PrivScope realizes this through a lightweight on-device pipeline that extracts disclosure units from the LC-assembled payload and keeps direct identifiers and account-linked values on device, since these are not required for provider search but are needed during local actuation. The remaining units are filtered through cloud-necessity control, which determines which are actually needed for successful task completion.

L285: ## V Evaluation
L286: 
L287: We evaluate PrivScope in a hybrid local–cloud agent setting that directly instantiates the system model in Section cite9†III-A , focusing on medical-booking provider discovery as a representative information-seeking delegation. Our goal is to measure whether PrivScope reduces unnecessary disclosure at the cloud-delegation boundary while preserving task completion under persistent cross-workflow execution.
L288: ### V-A Experimental Setting
L289: The prototype is implemented as a modular Python pipeline using LangChain-style orchestration [cite100†43 ] to coordinate local reasoning, persistent-state access, payload construction, cloud delegation, and local post-processing. We use a lightweight research prototype rather than a production assistant to control, log, and consistently compare the LC$\rightarrow$CLM disclosure boundary across payload treatments.
L290: The pipeline follows the control flow of recent LLM-based agent architectures [cite75†27 ]: a trusted local controller (LC) maintains device-resident state and invokes an untrusted cloud language model (CLM) for information-seeking subtasks.
L291: The LC maintains a persistent working state to reflect agentic settings in which stored user information is available to support task completion [cite52†6 ]. The working state contains two components: a static user profile provided at setup time, and a dynamic trace store that accumulates prior tool outputs, intermediate results, and task-relevant artifacts from earlier workflows. Before each current task, the LC may retrieve content from both sources when constructing the candidate cloud-bound payload.
L292: This setup allows us to study over-disclosure caused by payload construction over persistent cross-workflow state.
L293: Each workflow follows the same execution path. Given a user request, the LC constructs a candidate cloud-bound payload from the current request and retrieved working-state context. The evaluated payload treatment is then applied at the LC$\rightarrow$CLM boundary. In the vanilla condition, the candidate payload is sent unchanged; in privacy-mediated conditions, it is rewritten, redacted, or minimized before cloud delegation.
L294: The CLM is invoked once for the delegated information-seeking subtask: medical-booking provider discovery. The LC then performs local resolution using the CLM response together with any private state retained on device. Our main evaluation uses a fixed set of 100 task workflows. For a given run, all methods use the same task, working state, LC model, CLM, and downstream evaluation criteria; they differ only in the payload treatment applied before cloud delegation.
L295: To assess sensitivity to local-controller capability, we run the LC with five Ollama-hosted local models [cite101†44 ]: llama3.2 (3B) [cite102†45 ], phi3 (3.8B) [cite103†46 ], mistral (7B) [cite104†47 ], qwen2.5 (7B) [cite105†48 ], and llama3.1 (8B) [cite102†45 ]. The CLM is instantiated with GPT-4o-mini [cite106†49 ], Claude Haiku 4.5 [cite107†50 ], and Gemini 2.5 Flash [cite108†51 ].
L296: For each run, we log the original request, working-state context, LC-assembled payload, cloud-visible payload, CLM response, and local-resolution outcome. For PrivScope, we log extracted disclosure units, provenance labels, role assignments, abstraction decisions, and local bindings.
L297: All experiments are run on a 14-inch MacBook Pro with an Apple M2 Pro processor and 16 GB of unified memory. The system is implemented in Python 3.13.7. We use spaCy [cite93†39 ] with the en_core_web_sm model for lightweight parsing.
L298: ### V-B Task Construction and Data Generation
L299: Following prior agent-benchmark and synthetic task-generation methodologies [cite70†23 , cite72†24 , cite88†38 , cite73†25 ], we construct tasks in the medical booking domain from a structured inventory of candidate intents, service types, constraints, contextual cues, sensitive facts, and user goals.
L300: Each sampled seed contains one intent, one service type, two hard constraints, up to one soft preference, one or two supporting-context attributes, two domain-sensitive attributes, one or two general-sensitive attributes, and one user goal.
L301: Each seed is expanded into $v=2$ natural-language prompt variants using a cloud LLM, following the seed-expansion approach of PrivacyLens [cite73†25 ]. The expansion instruction requires all sampled domain-sensitive and general-sensitive facts to appear verbatim in every generated variant, while allowing the model to vary the phrasing, ordering, and surface style of the request. This ensures that the generated prompts remain realistic while preserving seed-level sensitive annotations for leakage measurement.
L302: Appendix cite37†-B shows the medical-booking domain inventory, an example sampled seed, the prompt-expansion instruction, and two generated prompt variants.
L303: In total, we sample $s=50$ seeds and generate $v=2$ variants per seed, yielding $100$ task prompts. The cloud LLM used for offline prompt generation is decoupled from the CLMs used during evaluation. Coauthors and two independent cloud models reviewed all generated prompts for realism, seed-field preservation, and annotation consistency. Any prompt flagged by either a coauthor or a reviewing model was discarded.
L304: ### V-C Evaluated Methods
L305: Each workflow follows the same four-stage execution path. First, the LC constructs a candidate cloud-bound payload from the user request and local working state, including profile attributes and trace-store context. Second, the evaluated payload condition is applied at the LC$\rightarrow$CLM boundary: privacy-mediated methods modify the payload, while Vanilla leaves it unchanged.
L306: Third, the resulting payload is sent to the CLM in a single call for provider discovery, making the disclosure boundary comparable across methods. Fourth, the LC parses the CLM response, restores withheld values when needed, and completes local post-processing and actuation. We evaluate four payload conditions:
L307:   1. 1.
L308: 
L309: Vanilla. The LC sends the candidate payload to the CLM without privacy mediation, serving as the unprotected reference condition.
L310: 
L311:   2. 2.
L312: 
L313: Prompt-based sanitization (PEP). The local model rewrites the candidate payload to reduce unnecessary private detail while preserving task-relevant content. This captures prompt-level privacy steering used in prior agent-privacy evaluations [cite72†24 , cite73†25 ].
L314: 
L315:   3. 3.
L316: Presidio. The candidate payload is sanitized using Microsoft Presidio [cite67†20 ], a deterministic PII detection and redaction toolkit.
L317: 
L318:   4. 4.
L319: 
L320: PrivScope. The candidate payload is processed by our on-device payload governor. PrivScope extracts spans, applies task-scoped filtering, classifies release forms, and abstracts retained content before constructing the payload released to the CLM.
L321: For each run, all conditions share the same task prompt, working state, LC model, and CLM configuration; only the candidate payload treatment differs.
L322: ### V-D Metrics
L323: We evaluate each payload treatment along three dimensions: privacy, utility, and efficiency. For each task, we annotate sensitive facts by source: facts in the current request, stable profile facts in working state, and history facts carried over from prior workflows. A fact is counted as revealed if the cloud-visible payload contains the fact verbatim or in a specificity-equivalent paraphrase.
L324: Coarser abstractions are not counted as revealing the original exact fact; for example, replacing an exact address with a city or a precise symptom with a broader category is treated as minimization rather than leakage.
L325: Privacy. Following prior agent-privacy and PII-leakage evaluations that measure whether sensitive information is disclosed at the instance and fact level [cite73†25 , cite72†24 , cite80†32 ], we report seven privacy metrics that capture complementary forms of cloud-visible exposure. Leakage Rate (LR) is the fraction of tasks in which at least one annotated sensitive fact is revealed to the CLM. Leakage Severity (LS) is the average fraction of annotated sensitive facts revealed per task.
L326: To isolate leakage from persistent working state, we report State Leakage Rate (SLR), the fraction of tasks in which at least one profile or prior-history fact is revealed, and State Leakage Severity (SLS), the average fraction of profile and prior-history facts revealed. Because not all sensitive facts carry equal risk, we also report Weighted Leakage Severity (WLS), which weights direct identifiers more heavily than quasi-identifiers and soft contextual attributes.
L327: To isolate unsolicited enrichment by the local controller, we report Injection Leakage Severity (ILS), the average fraction of state-sensitive facts that were not present in the user’s current request but were injected into the cloud-bound payload from persistent working state.
L328: The metrics above measure verbatim disclosure. To capture residual risk when sensitive units are abstracted rather than removed, we additionally evaluate Re-identification Risk (RIR), following recent work that shows LLMs can infer private attributes from text and that LLM judges can support privacy-leakage evaluation [cite57†11 , cite72†24 ].
L329: An LLM attacker is given only the sanitized payload and attempts to recover the original private values, while a separate judge scores inference accuracy against ground truth. RIR captures the risk that abstracted or co-disclosed signals, such as location, condition, preference, or provider history, remain identifying when released together. Full attacker and judge protocols are described in Appendix cite43†-D . Lower values are better for all privacy metrics.
L330: Utility. Following outcome-oriented agent benchmarks [cite70†23 , cite72†24 ], we measure whether minimization preserves the usefulness of the cloud delegation. Task Success Rate (TSR) is the fraction of tasks for which the CLM response remains actionable for the original request, i.e., it contains usable candidates, options, or next-step information. We assign success by majority vote across three independent judge models (GPT, Claude, and Gemini).
L331: Candidate Recall (CR) measures how much of the vanilla candidate set is preserved after mediation, matching candidates that refer to the same provider, venue, or entity despite minor formatting differences.

L392: ### V-I Source-Specific Leakage
L393: Figure cite115†10 breaks leakage down by fact origin: current request, user profile, and prior-workflow history. PrivScope eliminates profile leakage entirely by routing profile identifiers to the local binding table before cloud release; the other methods leak profile content at varying rates, with PEP the weakest and Presidio in the middle.
L394: For current-request facts, this source-specific view considers only facts originating in the user’s request, unlike the overall LS value in Table cite110†II , which aggregates all sources. PrivScope achieves the lowest current-request leakage among the privacy-mediated methods because it abstracts task-relevant facts rather than removing them, while Presidio and PEP retain or paraphrase more of the original wording.
L395: Prior-workflow leakage is also lowest under PrivScope, reflecting its task-necessity gate for carryover context, while Presidio and PEP retain working-state spans that the user did not explicitly invoke in the current request.
L396: ## VI Conclusion
L397: We presented PrivScope, a trusted on-device payload governor that enforces task-scoped disclosure at the LC$\rightarrow$CLM boundary in hybrid agentic systems.
L398: Through four on-device stages— disclosure unit extraction, provenance-aware scope control, task-sufficient abstraction under an offline-calibrated policy, and local resolution against withheld state—PrivScope substantially reduces cloud-visible exposure, suppresses cross-workflow carryover from persistent state, and preserves task utility while requiring no cloud-side changes or per-step user intervention.
L399: Our evaluation shows that PrivScope eliminates profile leakage, more than halves attack-based recovery, and achieves the highest candidate recall across the tested cloud LLMs.
L400: Our evaluation focuses on 100 information-seeking tasks in a single domain, medical booking, and PrivScope targets only the LC$\rightarrow$CLM boundary. This scope does not cover all agent domains or delegation types, but it captures a common privacy-sensitive setting where the CLM is used for provider discovery while exact user-specific details can remain local.
L401: The complementary problem of recipient- and purpose-bound field release at the LC$\rightarrow$third-party boundary is addressed by contextual-integrity-based mechanisms [cite74†26 , cite88†38 ], with which PrivScope composes naturally. Future work will extend PrivScope to handle implicit and domain-specific spans, learn abstraction hierarchies from data and user preferences, and operate robustly against adversarial CLMs and third-party services.
L402: ## Ethics Considerations
L403: This work involves no human subjects and no real personal data. All task prompts used in our evaluation are synthetic, generated by a cloud LLM from a structured medical-booking inventory (Appendix cite37†-B ); names, addresses, member IDs, provider names, and dates appearing in examples and figures are arbitrary placeholders. The user profiles supplied to the local controller are likewise synthetic.
L404: We selected medical booking as the evaluation domain because it exercises the kinds of sensitive attributes (location, insurance, symptom, prior-visit history) that make over-disclosure a meaningful risk; the synthetic generation procedure ensures that no real medical information is involved. Re-identification risk and task success are evaluated using LLM judges with majority vote across three providers.
L405: We acknowledge that LLM grading may reflect provider-specific biases and is not a substitute for human evaluation in safety-critical deployments.
