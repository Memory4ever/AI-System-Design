L39@P1-2: 21 Introduction
L40@P2: Monte Carlo Tree Search (MCTS) is a best-first search algorithm that uses random sampling to
L41@P2: build a search tree and evaluate actions [1, 2]. Originally developed for game playing—notably
L42@P2: achieving superhuman performance in Go [4]—MCTS has proven effective in domains where
L43@P2: the state space is too large for exhaustive search but where states can be evaluated through
L44@P2: simulation.
L45@P2: In this report, we apply MCTS to reasoning with Large Language Models. The key insight
L46@P2: is that multi-step reasoning can be viewed as a sequential decision problem:
L47@P2: • States are partial reasoning traces (text strings)
L48@P2: • Actions are reasoning continuations (next steps)
L49@P2: • Terminal states are complete solutions with answers
L50@P2: • Rewards are quality assessments of final answers
L51@P2: This formulation allows MCTS to systematically explore different reasoning paths, allocating
L52@P2: more search effort to promising directions while maintaining exploration of alternatives. Recent
L53@P2: work has explored similar ideas under the names “Tree of Thoughts” [5] and “Reasoning via
L54@P2: Planning” [6].
L55@P2: 1.1 Goals of This Specification
L56@P2: 1. Provide rigorous definitions of all components
L57@P2: 2. Present the MCTS algorithm with precise pseudocode
L58@P2: 3. Specify the adaptation to LLM reasoning with clear interfaces
L59@P2: 4. Document design choices that distinguish this variant from classical MCTS
L60@P2: 1.2 Scope and Assumptions
L61@P2: This specification covers single-threaded MCTS for text-based reasoning. We assume:
L62@P2: • The LLM produces valid text output for each query
L63@P2: • The Evaluator returns scores in [0, 1]
L64@P2: • State strings have bounded length (context window limits)

L81@P3: Definition 3.1 (State). A state s ∈ S is a string representing a partial or complete reasoning
L82@P3: trace. A state consists of the concatenation of:
L83@P3: 1. The original question
L84@P3: 2. Zero or more reasoning steps
L85@P3: 3. Optionally, a terminal marker with a final answer
L86@P3: Definition 3.2 (Terminal State). A state s is terminal if a terminal detector determines it
L87@P3: contains a complete answer. Formally:
L88@P3: IsTerminal(s) = TerminalDetector.Check(s)
L89@P3: The detector also extracts the answer: ExtractAnswer(s) → Answer ∪ {⊥}.
L90@P3: Definition 3.3 (Terminal Detector). A terminal detector is a component that determines when
L91@P3: reasoning is complete:
L92@P3: • Check(s) → {true, false}: determines if s is terminal
L93@P3: • ExtractAnswer(s) → Answer: extracts the answer from terminal s
L94@P3: • FormatInstruction() → String: provides prompt guidance for the LLM
L95@P3: Remark 3.1 (Terminal Detector Implementations). The canonical implementation uses a markerbased detector that looks for the string “ANSWER:”. Alternative implementations include:
L96@P3: • BoxedDetector: Looks for LATEX-style \boxed{...} (common in math benchmarks)
L97@P3: • MultiMarkerDetector: Accepts multiple completion signals
L98@P3: • LLM-as-Judge: Asks an LLM whether reasoning is complete (more expensive)
L99@P3: The terminal detector’s FormatInstruction is included in prompts so the LLM knows the
L100@P3: expected answer format.

L106@P3: where ⊕ denotes string concatenation with appropriate formatting.

L138@P4: 4 The MCTS Algorithm
L139@P4: MCTS builds a search tree incrementally through repeated simulations. Each simulation consists
L140@P4: of four phases: Selection, Expansion, Rollout, and Backpropagation.
L141@P4-5: 5Algorithm 1 MCTS Main Loop
L142@P5: Require: Question q, number of simulations K, branching factor B, max depth D
L143@P5: Ensure: Search tree with root r
L144@P5: 1: procedure Search(q, K, B, D)
L145@P5: 2: r ← CreateNode(q) ▷ Root state is the question
L146@P5: 3: for i = 1 to K do
L147@P5: 4: nleaf ← Select(r)
L148@P5: 5: nexp ← Expand(nleaf, B)
L149@P5: 6: nterm, v ← Rollout(nexp, D)
L150@P5: 7: Backpropagate(nterm, v)
L151@P5: 8: end for
L152@P5: 9: return r
