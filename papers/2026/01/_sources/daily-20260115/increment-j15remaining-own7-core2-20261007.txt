L101: ## 2 Preliminaries
L102: ### 2.1 Rubric
L103: 
L104: Rubrics are structured scoring guides that define evaluation criteria and performance levels, widely used to assess output quality in education and model evaluation. For each query $q$, we define a fine-grained evaluation rubric $\mathcal{R}_{q}$ as a set of $N_{q}$ weighted criteria:
L105: 
L106:  | $$\mathcal{R}_{q}=\{(c_{i},w_{i})\}_{i=1}^{N_{q}},$$  |  | (1)
L107: where each criterion $c_{i}$ encompasses semantic requirements and grader parameters. Criteria are categorized into two types: (1) Verifiable Criteria, representing objective constraints (e.g., format or word count) assessed via rule-based systems $\mathcal{G}_{\text{rule}}$; and (2) Semantic Criteria, capturing qualitative attributes (e.g., reasoning depth or tone) that require LLM-based evaluators $\mathcal{G}_{\text{LLM}}$.
L108: The weight $w_{i}$ determines each criterion’s importance, providing the basis for structured reward signals $r(q,o)$.
L109: ### 2.2 Task Formulation
L110: 
L111: We formulate rubric generation as a conditional task where an LLM $\mathcal{M}$ synthesizes a rubric $\mathcal{R}$ given input context $I$. By defining a prompt function $P(\cdot)$ that formats $I$ into instructions, the process is:
L112: 
L113:  | $$\mathcal{R}=\mathcal{M}\big(P(I)\big).$$  |  | (2)
L114: 
L115: In Section cite10†3 , we instantiate specific templates (e.g., $P_{\text{gen}},P_{\text{agg}}$) to generate and refine rubrics through multiple stages.
L116: ## 3 Method
L117: 
L118: In this section, we introduce our automated Coarse-to-Fine Rubric Generation framework. As illustrated in Figure cite74†2 , we detail the core rubric generation pipeline, which operates in three phases: (1) Principle-Guided & Response-Grounded Generation, (2) Multi-Model Aggregation, and (3) Difficulty Evolution. Finally, we analyze the resulting dataset characteristics and detail how RubricHub is utilized for post-training.
L119: ### 3.1 Coarse-to-Fine Rubric Generation
L120: 
L121: Our core objective is to synthesize evaluation criteria that are related, unbiased, and highly discriminative. Figure cite74†2 illustrates our coarse-to-fine generation pipeline initialized with a comprehensive corpus $\mathcal{Q}$ of $\sim$110k queries, which are curated and rigorously cleaned from open-ended datasets across multiple domains. Based on this corpus, we propose a three-stage framework to synthesize and refine high-quality rubrics.
L122: #### Stage 1: Response-Grounded & Principle-Guided Generation.
L123: 
L124: Generating rubrics solely from a query often leads to rubric drift—where criteria become generic, hallucinatory, or disconnected from actual task outputs. To address this, we propose a generation strategy that is both response-grounded and principle-guided.
L125: First, we employ response grounding by conditioning the generator $\mathcal{M}$ on a reference response $o_{i}$ to anchor the criteria to concrete context. Second, we enforce principle guidance by constraining the generator with a set of meta-principles $\mathbb{P}_{\text{meta}}$, encompassing: Consistency & Alignment; Structure & Scope; Clarity & Quality; and Reasoning & Evaluability (detailed in Appendix cite41†A ).
L126: Formally, using a specific generation prompt $P_{\text{gen}}$, a candidate rubric is synthesized as:
L127:  | $$\mathcal{R}_{\text{cand}}^{(i)}=\mathcal{M}\big(P_{\text{gen}}(q,o_{i},\mathbb{P}_{\text{meta}})\big).$$  |  | (3)
L128: 
L129: The resulting $\mathcal{R}_{\text{cand}}^{(i)}$ serves as a context-anchored candidate, explicitly preventing the generation of generic or irrelevant criteria.
L130: #### Stage 2: Multi-Model Aggregation.
L131: 
L132: While Stage 1 ensures relevance, rubrics generated by a single model inherently suffer from perspective bias. Individual models often exhibit inherent blind spots and subjective preferences, yielding narrow standards that fail to recognize valid responses with distinct presentations. To ensure comprehensiveness and objectivity, it is critical to aggregate heterogeneous viewpoints to cross-verify and mitigate these model-specific biases.
L133: To this end, we implement multi-model aggregation. We first synthesize parallel candidate sets using heterogeneous frontier models (e.g., GPT-5.1, Gemini 3 Pro Preview) to form a unified pool $\mathcal{R}_{\text{cand}}=\bigcup_{i}\mathcal{R}_{\text{cand}}^{(i)}$. Subsequently, we distill this pool into a compact base rubric via an aggregation prompt $P_{\text{agg}}$, which consolidates redundant items and resolves conflicts:
L134:  | $$\mathcal{R}_{\text{base}}=\mathcal{M}\big(P_{\text{agg}}(q,\mathcal{R}_{\text{cand}})\big).$$  |  | (4)
L135: 
L136: The resulting $\mathcal{R}_{\text{base}}$ serves as a comprehensive standard that explicitly eliminates single-source bias.
L137: #### Stage 3: Difficulty Evolution.
L138: 
L139: The base rubric $\mathcal{R}_{\text{base}}$ typically captures fundamental correctness but often lacks the granularity to distinguish between excellent and exceptional responses. This limitation risks score saturation, leaving top-tier models without a meaningful optimization gradient. To resolve these fine-grained quality gaps, we introduce a difficulty evolution mechanism.
L140: Specifically, we first identify a pair of high-quality reference responses $\mathcal{A}_{\text{ref}}$, selected based on consensus high rubric scores from the initial candidate pool. We then apply an augmentation prompt $P_{\text{aug}}$ to analyze $\mathcal{A}_{\text{ref}}$, extracting discriminative nuances beyond the scope of $\mathcal{R}_{\text{base}}$ that elevate a response from excellent to exceptional, thereby forming a set of additive criteria $\mathcal{R}_{\text{add}}$:
L141:  | $$\mathcal{R}_{\text{add}}=\mathcal{M}\left(P_{\text{aug}}(q,\mathcal{R}_{\text{base}},\mathcal{A}_{\text{ref}})\right).$$  |  | (5)
L142: 
L143: These criteria harden the rubric, upgrading generic checks (e.g., “Is the code correct?”) into rigorous standards (e.g., “Does the code handle edge case with O(n) complexity?”). The final rubric is obtained by merging the base and evolved criteria:
L144: 
L145:  | $$\mathcal{R}_{\text{final}}=\mathcal{R}_{\text{base}}\cup\mathcal{R}_{\text{add}}.$$  |  | (6)
L146: The resulting $\mathcal{R}_{\text{final}}$ thus combines comprehensive coverage with rigorous discriminability, providing a dense and precise supervision signal for effective model optimization.

L149: ### 3.2 Data Analysis of RubricHub
L150: To construct RubricHub, we aggregated queries from five domains: (1) Science: RaR-science (cite67†Gunjal et al., 2025 ), ResearchQA (cite75†Yifei et al., 2025 ), and MegaScience (cite76†Fan et al., 2025 ); (2) Instruction Following: IFTRAIN (cite77†Pyatkin et al., 2025 ); (3) Writing: LongWriter (cite78†Bai et al., 2024b ), LongWriter-Zero (cite79†Wu et al., 2025a ), DeepWriting-20K (cite80†Wang et al., 2025a ), and LongAlign (cite81†Bai et al., 2024a ); (4) Medical: II-medical (cite82†Internet, 2025 ); (5) Chat: WildChat-1M (cite83†Zhao et al., 2024 ) and LMsys-1M (cite84†Zheng et al., 2023a ).
L151: After filtering out samples with abnormal lengths or formatting errors, we sampled a final set of $\sim$110k question–rubric pairs. As shown in Figure cite85†3 , RubricHub features a diverse domain composition, with Medical and Science tasks constituting the largest portions (27.1% each), followed by Instruction Following (20.9%) and Writing (15.9%). The inner ring demonstrates the high density of our rubrics.
L152: For complex domains like Writing and Medical, RubricHub provides over 30 fine-grained criteria on average per query, ensuring deep and rigorous evaluation.
L153: Crucially, the score density in Figure cite86†4 demonstrates a highly discriminative and non-saturated evaluation regime. We observe a clear distributional separation across model scales, validating the rubric’s ability to distinguish varying capability levels. Moreover, even top-tier models like Qwen3-235B yield an average score of only approximately 0.6, confirming that the evolved criteria remain challenging and provide significant headroom for sustained improvement.
L154: ### 3.3 Utilization of Rubrics in Post-Training
L155: 
L156: We apply the constructed rubrics in two post-training paradigms: RuFT, which selects high-quality data for Supervised Fine-Tuning (SFT), and RuRL, which uses rubric scores as rewards.

L92: To ensure compatibility with diverse agent architectures, we monitor agent behaviors directly within the web environment, thereby decoupling the task-tracking mechanism from the specific internal implementations of individual agents. Specifically, we perform web-based instrumentation to capture agents’ critical actions during execution. The intercepted action detail is then transmitted to a backend server and saved for subsequent evaluation.
L93: Web-based Instrumentation. The instrumentation focuses on capturing critical actions capable of modifying the web environment, namely click and type actions. Initially, we identify the HTML elements closely related to the task requirements. When an interaction occurs, our instrumentation intercepts the click or input events to extract the execution detail.
L94: For click actions, we record the identifier of the clicked web element, which is a manually labeled semantic string; for type actions, we record the exact textual payload entered into the targeted web element.
L95: Evaluation Annotation. We leverage the established evaluation schemes from representative datasets and recalibrated their annotated ground truth or evaluation rules. This adjustment ensures that the existing benchmarks are seamlessly integrated into our outcome-oriented assessment framework.
L96: ### II-B Automated Testing Services
L97: 
L98: To facilitate the security evaluation on WebTrap Park dataset with minimal integration overhead, we develop a testing platform to provide automated testing services. This platform integrates task metadata, interactive web environments and evaluation scripts from WebTrap Park into a unified framework, thereby streamlining the evaluation process.
L99: Docker Image Construction. We encapsulate the task metadata, interactive web environments, and evaluation scripts of WebTrap Park into Docker images. This approach offers two primary advantages: First, by ensuring that all service containers are instantiated from identical images regardless of the user’s underlying deployment environment, we maintain strict environmental consistency and reproducibility.
L100: Second, a dedicated container instance is allocated for each task; this container-level isolation ensures that the execution detail captured within each instance remains interference-free, thereby safeguarding the integrity of the evaluation data.
L101: Pod Management. We employ Kubernetes as our container orchestration platform to automate the deployment and lifecycle management of containerized evaluation workloads. Each user is assigned a unique access path, which is routed to the corresponding Pod’s endpoint through the combined mechanisms of Ingress and Service.
L102: This establishes a secure and reliable network communication channel between user requests and the containerized service within the Pod, thereby facilitating user interaction with the isolated evaluation environment.
L103: ## III W eb T rap P ark
L104: ### III-A Overview
L105: WebTrap Park is an automated platform designed to support systematic security evaluation of Web Agents in realistic web environments. The platform aims to provide a unified and reproducible assessment framework that enables fair comparison across Web Agents developed under different architectures, interaction paradigms, and implementation choices. To this end, WebTrap Park is designed to be model agnostic and architecture independent, while requiring minimal integration effort from developers.
L106: Tasks. At the core of WebTrap Park is a large scale task suite constructed around three primary sources of security risk commonly faced by contemporary Web Agents, namely malicious user prompts, prompt injection attacks, and deceptive website designs. Based on threat patterns observed in real web interactions, WebTrap Park instantiates these risks into 1,226 evaluation tasks, thereby enabling comprehensive security assessment under diverse attack scenarios.
L107: Service. In addition to the task suite, WebTrap Park provides a fully automated testing service that functions as a security testing environment for Web Agent developers and researchers. New agents can be seamlessly integrated into the platform within few minutes. From agent initialization and task scheduling to browser driven web interactions, the entire attack evaluation process is automatically coordinated between the platform and the agent.
L108: No manual execution or intervention is required during testing, which allows WebTrap Park to support scalable and consistent security evaluation across a large number of agents.
L109: ### III-B Usage
L110: 
L111: Using WebTrap Park involves a simple three stage workflow that is designed to minimize user overhead while maintaining standardized evaluation procedures.
L112: 
L113: Application. In the first stage, developers submit an application through the Test Service interface by providing basic information about their Web Agent. Each application is reviewed by the platform, and the review result is communicated to the applicant via email within 24 hours.
L114: Provisioning. Once the application is approved, WebTrap Park automatically provisions a dedicated environment for the submitted Web Agent. After the environment is prepared, the developer receives detailed testing instructions along with a list of accessible services and tasks. The developer is required to launch the Web Agent within the specified time window in order to begin the evaluation process.
L115: Testing. In the final stage, the developer runs the Web Agent locally to interact with web pages according to the provided task list. During execution, WebTrap Park automatically monitors and records the agent’s observable behaviors and computes corresponding security scores. To ensure fairness and comparability of results, the platform encourages all participating agents to complete the full set of evaluation tasks.
L116: Upon completion, the developer may finalize the evaluation and obtain the overall security score, which is delivered to the registered email address.
L117: ### III-C Access Conditions
L118: 
L119: WebTrap Park is intended to serve as a shared infrastructure that facilitates reproducible security evaluation of Web Agents. We encourage participation from agent developers, academic researchers, and industrial stakeholders who seek to assess the safety of their systems in realistic web environments. By providing open access to a comprehensive task suite and a standardized evaluation pipeline, the platform aims to lower the barrier to responsible security testing.
L120: To safeguard the platform’s stability and reliability, WebTrap Park reserves the right to audit and restrict abnormal or malicious usage behaviors. This includes, but is not limited to, automated exploitation attempts, efforts to tamper with evaluation outcomes, unauthorized data extraction, or behaviors that violate the intended scope of controlled research use.
L121: When such activities are identified, appropriate mitigation measures such as rate limiting, access suspension, or disqualification from public leaderboards may be applied. These governance mechanisms are essential to maintain a trustworthy testing environment and to ensure that the platform remains a reliable resource for the community.

Owen-Shapley Policy Optimization (OSPO): A Principled RL Algorithm for Generative Search LLMs (https://arxiv.org/html/2601.08403v1)
citeturn30803view2 [wordlim: 200] Crawled: today; Content type: text/html; Source: open({"ref_id":"https://arxiv.org/html/2601.08403v1","lineno":108}); Total lines: 851
L98: For example, in product search, customers often make queries that contains attribute-specific preference signals expressed as phrases like “looking for [product] in my usual neutral tones” where the text in bold shows such a segment. OSPO treats these segments as high-level abstractions in the action space as valid segments for Owen–Shapley value computation, akin to options (cite85†Sutton, 1984 ) or macro-actions (cite86†Chai et al., 2025 ) in hierarchical RL.
L99: To assign such values, each segment’s marginal contribution to the total reward is measured by how much it increases the reward when added to different coalitions—segments that consistently improve outcomes receive credit, while those that dilute or distract are down-weighted.
L100: These attributions are obtained by querying any feedback model that returns scalar scores (e.g., a retriever or reward model), requiring no external value networks or process reward models (cite87†Schulman et al., 2017 ; cite67†Lightman et al., 2023 ).
L101: Our key contribution is proposing a policy learning approach that can integrate such fine-grained value attributions from Owen values in learning good policies, while additionally leveraging from Monte-Carlo-based sampled rollouts that allow OSPO to achieve a reasonable trade off between exploration and exploitation (cite88†Sutton & Barto, 2018 ).
L102: Our core insight in achieving this balance is one of gradient budget reallocation via advantage redistribution: rather than spreading policy gradients uniformly across all tokens in a sequence (cite69†Shao et al., 2024a ), OSPO concentrates updates on high-attribution segments while reducing signal on low-value content.
L103: cite89†Figure 1 illustratest OSPO’s advantage redistribution mechanism that computes fine-grained advantages for the LLM’s response segments directly from task-based feedback or a reward model—weighted by the Owen attributions. Specifically, OSPO applies a simple mapping from segment-level Owen values to tokens that respects the scale of standard Monte-Carlo group-based advantages (cite90†Williams, 1992a ), while reducing computation complexity involved in exact Shapley computations.
L104: This helps resolve the credit assignment gap inherent in learning solely from terminal rewards—without compromising learning the final outcomes. Additionally, in order to stabilize training dynamics, OSPO admits potential-based reward-shaping (PBRS) (cite91†Ng et al., 1999 ) to adapt segment-level Owen values to tokens—adopting the standard clip-surrogate objective for stable policy updates (cite87†Schulman et al., 2017 ).
L105: As cite89†Figure 1 demonstrates, this focused attribution yields substantially faster learning similar to prior work  (cite92†Koo et al., 2025 ): OSPO reaches 85% NDCG in approximately 400 training steps on the fashion domain search task, while GRPO requires over 800 steps to approach similar performance despite identical training data and settings.
L106: ## 2 Related Work
L107: ##### Generative Recommendation Systems.
L108: LLMs have transformed recommendation systems through reasoning-driven decision-making (cite93†Wang et al., 2020 ; cite94†Zhao et al., 2018 ; cite95†Liu et al., 2023b ). Recent methods integrate LLMs via feature enrichment (cite96†Xi et al., 2024 ; cite97†Li et al., 2023 ), ranking (cite98†Geng et al., 2023 ; cite99†Luo et al., 2024 ), and conversational interaction (cite100†Zhou et al., 2020 ; cite101†Gao et al., 2023 ; cite102†Bang & Song, 2025 ).
L109: RL-LLM hybrids (cite103†Jeong et al., 2023 ; cite104†Sun et al., 2024 ; cite105†Lu et al., 2024 ; cite106†Rafailov et al., 2023b ) enable personalization but focus on offline tuning. Building on Rec-R1 (cite66†Lin et al., 2025 ), which uses online task-specific feedback, OSPO addresses sparse credit assignment via Owen-Shapley attributions over segment-level spans.
L110: On the other hand, Owen–Shapley values have been explored across domains (cite107†Owen, 2014 ; cite108†Giménez Pradales & Puente del Campo, 2019 ; cite109†Lundberg & Lee, 2017 ) and applied in NLP for LLM interpretation (cite110†Goldshmidt & Horovicz, 2024 ; cite111†Mohammadi, 2024 ), prompt valuation (cite112†Liu et al., 2023a ), model compression (cite113†Sun et al., 2025a ), and dataset refinement (cite114†He et al., 2024 ). However, their use in RLHF remains limited.
L111: Recent work like SCAR (cite75†Cao et al., 2025 ) and cite92†Koo et al. (2025) extend Shapley-based reward distribution for LLM training.
L112: ##### Densifying Sparse Rewards.
L113: Dense feedback in policy optimization traditionally relies on value-function-based advantage estimation (cite87†Schulman et al., 2017 ; cite115†Kazemnejad et al., 2024 ; cite73†Yue et al., 2025 ; cite116†Azar et al., 2024 ; cite117†Pignatelli et al., ), which is computationally heavy and requires learned critics.
L114: Value-model-free alternatives like GRPO and DPO (cite118†DeepSeek-AI et al., 2025 ; cite106†Rafailov et al., 2023b ; cite119†Liu et al., 2025 ) reduce overhead but assign uniform credit or requires optimizing the discount factor in returns (cite120†Parthasarathi et al., 2025 ).
L115: Process Reward Models (cite67†Lightman et al., 2023 ; cite121†Wu et al., 2023 ; cite122†Bai et al., 2022 ; cite123†Choudhury, 2025 ) densify rewards via step-level supervision but require labeled intermediate steps and remain confined to deterministic domains (cite124†Fang et al., 2025 ; cite125†Sun et al., 2025b ). Attention-based methods (cite126†Chan et al., 2024 ; cite91†Ng et al., 1999 ) propagate reward through attention weights but can entangle spurious correlations (cite75†Cao et al., 2025 ; cite127†Xie et al., 2025 ).
L116: Recent Shapley-based approaches like SCAR (cite75†Cao et al., 2025 ) compute principled marginal contributions but depend on parametric value models (cite76†Stiennon et al., 2020 ), restricting applicability to black-box feedback settings (cite66†Lin et al., 2025 ). In contrast, OSPO performs value-model-free advantage redistribution over segment-level Owen attributions, reducing Shapley’s exponential complexity while preserving fairness properties.
L117: Unlike SCAR, which redistributes rewards through a learned value model, OSPO directly redistributes advantages from policy rollouts, enabling end-to-end optimization without value computation.
L118: ## 3 Problem Formulation and Background
L119: We model text generation for recommendation as a Markov Decision Process (MDP) defined by the tuple $(\mathcal{S},\mathcal{A},P,r,\rho_{0},\gamma)$, where: the state space $\mathcal{S}$ consists of all partial sequences $(x,y_{<t})$ combining the input context $x$ (e.g., user purchase history or raw search query) and tokens generated so far $y_{<t}=(y_{1},\ldots,y_{t-1})$; the action space $\mathcal{A}$ is the vocabulary from which the policy selects the next token $y_{t}$; the transition function $P(s_{t+1}|s_{t},a_{t})$ is deterministic—appending token $a_{t}=y_{t}$ to the history to form state $s_{t+1}=(x,y_{\leq t})$; the reward function $r:\mathcal{S}\times\mathcal{A}\to\mathbb{R}$ assigns scalar feedback; the initial state distribution $\rho_{0}$ samples input $x\sim\mathcal{D}$ from the data distribution; and the discount factor $\gamma=1$ for the undiscounted episodic setting as is standard for LLMs (cite128†Rafailov et al., 2024 ).
L120: A trajectory $\tau=(s_{0},a_{0},s_{1},a_{1},\ldots,s_{T},a_{T})$ corresponds to autoregressively generating a complete sequence $y=(y_{1},\ldots,y_{T})$ via the policy $\pi_{\theta}(y_{t}|s_{t})=\pi_{\theta}(y_{t}|x,y_{<t})$, where $\pi_{\theta}(y|x)=\prod_{t=1}^{T}\pi_{\theta}(y_{t}|x,y_{<t})$.
L121: The learning objective^{2}^{2} 2 We set the KL coefficient to $\beta=0$, following prior work (cite66†Lin et al., 2025 ). is to find a policy that maximizes expected downstream performance:
L122: 
L123:  | $$\max_{\theta}\;\mathcal{J}(\theta)=\mathbb{E}_{x\sim\mathcal{D},~y\sim\pi_{\theta}(\cdot|x)}[\,r(x,y)\,],$$  |  | (1)
L124: 
L125: where $r(x,y)\in\mathbb{R}$ is a terminal reward from the downstream system—for instance, NDCG in product search or a reward-model score in user profile generation (cite129†Zheng et al., 2023 ).
L126: Because $r(x,y)$ is sequence-level and terminal, with $r_{t}=0$ for $t<T$ and $r_{T}=r(x,y)$, the policy receives no signal about which tokens—or, more meaningfully, which semantic segments of the response—contributed to success, creating the credit assignment problem. To address sparse feedback, methods like Group Relative Policy Optimization (GRPO) (cite69†Shao et al., 2024a ; cite66†Lin et al., 2025 ) replace the learned value function with a sampling-based baseline.
L127: GRPO samples $G$ responses per prompt and computes group-relative advantages by normalizing rewards within the batch:
L128:  | $$\scriptsize\hat{A}^{(g)}=\frac{r^{(g)}-\bar{r}}{\sigma_{r}},\hskip 8.19447pt\text{where}\hskip 8.19447pt\bar{r}=\tfrac{1}{G}\sum_{g^{\prime}=1}^{G}r^{(g^{\prime})},\hskip 8.19447pt\sigma_{r}=\sqrt{\tfrac{1}{G}\sum_{g^{\prime}=1}^{G}(r^{(g^{\prime})}-\bar{r})^{2}}.$$  |  | (2)
L129: 
L130: The GRPO objective is then:
L131:  | $$\scriptsize\mathcal{J}^{\text{GRPO}}(\theta)=\frac{1}{G}\sum_{g=1}^{G}\frac{1}{T}\sum_{t=1}^{T}\min\!\Big(\rho_{t}^{(g)}\hat{A}^{(g)},\operatorname{clip}(\rho_{t}^{(g)},\,1-\epsilon,\,1+\epsilon)\hat{A}^{(g)}\Big),$$  |  | (3)
L132: where $\rho_{t}^{(g)}=\frac{\pi_{\theta}(y_{t}^{(g)}\mid x,y_{<t}^{(g)})}{\pi_{\theta_{\text{old}}}(y_{t}^{(g)}\mid x,y_{<t}^{(g)})}$ is the importance sampling ratio. While GRPO reduces variance via group normalization, it applies a uniform advantage $\hat{A}^{(g)}$ to all tokens in a sequence (cite130†Samineni et al., 2025 ), offering no mechanism to distinguish which tokens—or meaningful semantic segments—actually drove the final reward $r^{(g)}$.
L133: ### 3.1 Owen-Shapley Policy Optimization: Segment-Level Credit Assignment
L134: The mismatch between GRPO’s token-level uniform advantages and the compositional structure of recommendation tasks motivates a shift in granularity. To resolve this, our approach, OSPO, leverages the structure of Owen “coalitions” (cite82†Owen, 1977 )—groups of segments or players in game theory—that compute what value should be assigned to each segment based on its expected marginal contribution to the total reward.
