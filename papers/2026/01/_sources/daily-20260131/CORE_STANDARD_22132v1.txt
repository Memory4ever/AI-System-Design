Comparison with routing.
Routing baselines (RouteLLM, GraphRouter) struggle when query difficulty varies widely. On CNK12, they achieve only 5–8% cost reduction compared to LLM, whereas Reactive Shepherding delivers 42%—a 2×2\times improvement at comparable accuracy. The gap is smaller on GSM8K, where most queries are SLM-solvable, but shepherding still matches Oracle performance ($0.034) while routing methods incur 2–3×\times higher cost.
Comparison with cascading.
Cascading baselines (FrugalGPT, ABC) achieve higher accuracy than routing but at a greater cost. On GSM8K, ABC reaches 94.9% accuracy—5.8 points above Reactive Shepherding—but costs 41% more, yielding lower ACE (1.89 vs. 1.97). This illustrates a key trade-off: cascading pays for accuracy that may exceed application requirements, while shepherding optimizes cost-efficiency by requesting only partial LLM assistance.
When the SLM is already capable.
On MBPP, the SLM baseline reaches 65.2% accuracy—only 9 points below the LLM. In this regime, Reactive Shepherding excels: it achieves 93.6% cost reduction with an ACE of 2.78, outperforming ABC by 1.6×1.6\times. Notably, Reactive Shepherding even surpasses Oracle Shepherding in ACE (2.78 vs. 1.67). This occurs because Oracle optimizes for matching LLM accuracy (74.2%), which requires hints on many queries and incurs 7.5×7.5\times higher cost ($0.015 vs. $0.002). When the accuracy gap is narrow, accepting slightly lower accuracy yields a substantially better ACE trade-off that Reactive Shepherding captures.
Cross-domain generalization.
HumanEval tests whether shepherding transfers to unseen domains: all methods use GSM8K-trained models without code-specific fine-tuning. Reactive Shepherding matches ABC’s accuracy (76.2%) while achieving 2.8×2.8\times better cost reduction (44% vs. 16%), yielding the highest ACE (1.42). This zero-shot transfer suggests that hint allocation learns generalizable patterns of query difficulty rather than task-specific heuristics.
Shepherding’s advantage stems from its ability to request partial hints (typically 10–30% of the LLM response) rather than full outputs. This granular control enables cost-accuracy trade-offs unavailable to binary routing and cascading methods.

2.2 Hints and Shepherding Policy
The central concept in LLM shepherding is the hint, defined as a prefix of the LLM’s response provided to the SLM to guide its generation. Formally, for a query qq and hint size n≥0n\geq 0, the hint is given by:
hint(q,n)=hl(q)[1:n]\text{hint}(q,n)=h_{l}(q)_{[1:n]}
The hint-augmented SLM response is then:
hs(n)​(q)=hs​(q⊕hint​(q,n))h_{s}^{(n)}(q)=h_{s}\bigl(q\oplus\text{hint}(q,n)\bigr)
where the SLM generates a response conditioned on the original query concatenated with the hint prefix.
Shepherding Policy.
A shepherding policy π:𝒬→{0,1,…,Nmax}\pi:\mathcal{Q}\to\{0,1,\ldots,N_{\max}\} maps each query qq to a hint size n=π⁡(q)n=\pi(q), where NmaxN_{\max} is the maximum output token limit of the LLM. When n=0n=0, the SLM responds without assistance; when n>0n>0, the system requests an nn-token hint before SLM completion.
For each query qq, we define the minimum hint size as the smallest number of LLM tokens required for the SLM to produce a satisfactory response:
n∗​(q)=min⁡{n∈ℤ≥0:ϕ⁡(q,hs(n)​(q))≥τ}n^{*}(q)=\min\left\{n\in\mathbb{Z}_{\geq 0}:\phi\bigl(q,h_{s}^{(n)}(q)\bigr)\geq\tau\right\}
(1)
The Oracle Shepherding Policy π∗\pi^{*} maps each query qq to n∗​(q)n^{*}(q).

For open-source SLMs deployed on a local device, we have csin=csout=0c_{s}^{\text{in}}=c_{s}^{\text{out}}=0.
The cost of shepherding a query qq with hint size n>0n>0 is:
cshep​(q,n)=|q|​clin+n​clout+(|q|+n)​csin+|hs(n)​(q)|​csout.c_{\text{shep}}(q,n)=|q|c_{l}^{\text{in}}+nc_{l}^{\text{out}}+(|q|+n)c_{s}^{\text{in}}+|h_{s}^{(n)}(q)|c_{s}^{\text{out}}.
To compare the cost-performance trade-offs across different strategies/policies, we introduce a normalized efficiency metric called Accuracy-per-Cost Efficiency (ACE). Let AlA_{l} denote the accuracy of the remote large model with total cost Cl=∑q∈𝒬cl​(q)C_{l}=\sum_{q\in\mathcal{Q}}c_{l}(q), and AsA_{s} denote the accuracy of the on-device small model with cost zero (assuming csin=csout=0c_{s}^{\text{in}}=c_{s}^{\text{out}}=0).

3 Training the Shepherding System
Our goal is to learn a policy πθ:𝒬→ℤ≥0\pi_{\theta}:\mathcal{Q}\rightarrow\mathbb{Z}_{\geq 0}, that predicts the minimum hint size n∗​(q)n^{*}(q). However, predicting n∗​(q)n^{*}(q) directly is challenging for several reasons: 1) Heavy-tailed hint sizes: n∗​(q)n^{*}(q) varies significantly across queries – on GSM8K, 80.6% of queries require no hint at all, while the remaining 19.4% span a wide range from 10% to 90% of the full LLM response (see Appendix D for a detailed discussion), 2) Non-smooth benefit: A small change in nn can abruptly determine whether the SLM crosses the quality threshold τ\tau, as critical information (e.g., a key constraint or intermediate step) may appear at specific token boundaries, 3) Non-monotonic quality: The quality function ϕ⁡(q,hs(n)​(q))\phi(q,h_{s}^{(n)}(q)) may not increase monotonically with nn (cf. Fig. 2). Excessive hint tokens can over-constrain the SLM, degrading performance even when shorter hints succeed, and 4) Tokenization sensitivity: The same semantic content yields different token counts depending on the model and query phrasing, making direct regression to absolute token counts brittle.
We address the above challenges by adopting a two-step policy design: we first predict whether any hint is needed (i.e., whether n∗​(q)>0n^{*}(q)>0), and only then predict the required hint size conditioned on needing a hint. Concretely, we train a binary classifier y(q)=𝟙[n∗(q)>0]y(q)=\mathds{1}_{\left[{n^{*}(q)>0}\right]} and a regressor for n∗​(q)n^{*}(q) on the subset of queries with n∗​(q)>0n^{*}(q)>0.
3.1 Training Data and Supervision Signals
To train the Shepherding model, we construct supervision labels n∗​(q)n^{*}(q) by evaluating candidate hints at discretized hint sizes. For each query qq, we generate hints at percentage sizes p∈{0,10,20,…,90}p\in\{0,10,20,\ldots,90\} of the full LLM response length |hl​(q)||h_{l}(q)|, computing np=⌊p100​|hl​(q)|⌋n_{p}=\lfloor\frac{p}{100}|h_{l}(q)|\rfloor and querying the LLM with max_new_tokens =np=n_{p} to obtain hint​(q,np)=hl(np)​(q)\text{hint}(q,n_{p})=h_{l}^{(n_{p})}(q). We then evaluate each hint by running the SLM on the augmented prompt and record the minimal sufficient size:
n∗​(q)=min⁡{np:ϕ⁡(q,hs​(q⊕hint​(q,np)))≥τ}.n^{*}(q)=\min\left\{n_{p}:\phi\bigl(q,h_{s}(q\oplus\text{hint}(q,n_{p}))\bigr)\geq\tau\right\}.
If no partial hint meets the threshold, we set n∗​(q)=|hl​(q)|n^{*}(q)=|h_{l}(q)| and use the full LLM response. We provide a detailed discussion of the labeling procedure, discretization granularity, and design rationale in Appendix B.1. We filter samples where no hint size improves SLM accuracy, and the LLM response is also incorrect; see Appendix C for details.
Recall that y(q)=𝟙[n∗(q)>0]y(q)=\mathds{1}_{\left[{n^{*}(q)>0}\right]}. The log-transformed hint size is given by r⁡(q)=log⁡(1+n∗​(q))r(q)=\log(1+n^{*}(q)) for queries requiring hints. The model produces logit y^​(q)\widehat{y}(q) for hint/no-hint classification and prediction r^​(q)\widehat{r}(q) for the hint size.
3.2 Model Architecture
We use DeBERTa-v3-large (He et al., 2023) as the text encoder. Let 𝐡CLS​(q)\mathbf{h}_{\text{CLS}}(q) denote the [CLS] embedding of query qq. Let 𝐟⁡(q)\mathbf{f}(q) denote the input feature vector. We pass it through a Multi-layer Perceptron (MLP) and obtain the transformed numeric features 𝐠⁡(q)=MLP⁡(𝐟⁡(q))\mathbf{g}(q)=\mathrm{MLP}(\mathbf{f}(q)). We construct the fused representation
𝐮⁡(q)=[𝐡CLS​(q);𝐠⁡(q)]\mathbf{u}(q)\;=\;\bigl[\mathbf{h}_{\text{CLS}}(q);\mathbf{g}(q)\bigr].
Using 𝐮⁡(q)\mathbf{u}(q), the Shepherding system produces:
y^​(q)\displaystyle\widehat{y}(q)
=Headhint​(𝐮⁡(q))∈ℝ,\displaystyle=\mathrm{Head}_{\text{hint}}(\mathbf{u}(q))\in\mathbb{R},
r^​(q)\displaystyle\widehat{r}(q)
=Headsize​(𝐮⁡(q))∈ℝ,\displaystyle=\mathrm{Head}_{\text{size}}(\mathbf{u}(q))\in\mathbb{R},
where y^​(q)\widehat{y}(q) is the logit for the hint indicator y⁡(q)y(q) and r^​(q)\widehat{r}(q) predicts r⁡(q)r(q).
Here, Headhint\mathrm{Head}_{\text{hint}} and Headsize\mathrm{Head}_{\text{size}} are lightweight prediction heads (small feed-forward networks) attached to the shared fused representation 𝐮⁡(q)\mathbf{u}(q): Headhint\mathrm{Head}_{\text{hint}} maps 𝐮⁡(q)\mathbf{u}(q) to a single scalar logit for binary classification (hint-needed vs. no-hint), while Headsize\mathrm{Head}_{\text{size}} maps 𝐮⁡(q)\mathbf{u}(q) to a single scalar for the regression target r⁡(q)r(q).
To reduce variance in the hint-indicator logits, we apply multi-sample dropout and average logits across multiple passes (Inoue, 2019).
3.3 Training Objective
We optimize a joint objective over the training set. For the hint indicator, we use binary cross-entropy on the logit y^​(q)\widehat{y}(q):
ℒhint=−[y⁡(q)​log⁡σ⁡(y^​(q))+(1−y⁡(q))​log⁡(1−σ⁡(y^​(q)))].\mathcal{L}_{\text{hint}}=-\Bigl[y(q)\log\sigma\bigl(\widehat{y}(q)\bigr)+\bigl(1-y(q)\bigr)\log\Bigl(1-\sigma\bigl(\widehat{y}(q)\bigr)\Bigr)\Bigr].
We address class imbalance via minibatch balancing.
For the hint size, we train only on positive examples 𝒬+={q∈𝒬∣y⁡(q)=1}\mathcal{Q}^{+}=\{q\in\mathcal{Q}\mid y(q)=1\} using Smooth L1 (Huber) loss (Huber, 1964):
ℒsize=1|𝒬+|​∑q∈𝒬+SmoothL1⁡(r^​(q)−r⁡(q)),\mathcal{L}_{\text{size}}\;=\;\frac{1}{|\mathcal{Q}^{+}|}\sum_{q\in\mathcal{Q}^{+}}\mathrm{SmoothL1}\!\bigl(\widehat{r}(q)-r(q)\bigr),
which penalizes the regression residual on the log-transformed target and is more robust to outliers than ℓ2\ell_{2} loss. Intuitively, ℒsize\mathcal{L}_{\text{size}} is computed only when a hint is needed (y⁡(q)=1y(q)=1), since the size is undefined for no-hint queries.
The total loss is
ℒ=λ​ℒhint+(1−λ)​ℒsize\mathcal{L}\;=\;\lambda\mathcal{L}_{\text{hint}}+(1-\lambda)\mathcal{L}_{\text{size}}, where λ∈[0,1]\lambda\in[0,1] is the relative weight parameter. Additional optimization details, including the use of AdamW, EMA, class balancing via weighted sampling, and policy calibration procedures, are provided in Appendix B.2.
3.4 Inference: Mapping Predictions to Decisions
At test time, we first compute the hint probability from the binary classification head:
ℙ​(q)=σ​(y^​(q))\mathbb{P}(q)=\sigma(\widehat{y}(q)),
where σ⁡(⋅)\sigma(\cdot) is the sigmoid function. We then use a threshold α∈[0,1]\alpha\in[0,1] to obtain the binary hint decision 𝟙[ℙ(q)≥α]\mathds{1}_{\left[{\mathbb{P}(q)\geq\alpha}\right]}.
The predicted hint size is then defined as:
πθ​(q)={0,if ​ℙ​(q)<α,⌊clip⁡(exp⁡(r^​(q))−1, 0,Nmax)⌉,if ​ℙ​(q)≥α,\pi_{\theta}(q)=\begin{cases}0,&\text{if }\mathbb{P}(q)<\alpha,\\[4.0pt]
\left\lfloor\mathrm{clip}\!\left(\exp(\widehat{r}(q))-1,\,0,\,N_{\max}\right)\right\rceil,&\text{if }\mathbb{P}(q)\geq\alpha,\end{cases}
where ⌊x⌉\lfloor x\rceil denotes rounding xx to the nearest integer, clip⁡(x,a,b)=max⁡(a,min⁡(x,b))\mathrm{clip}(x,a,b)=\max(a,\min(x,b)) clamps values to the interval [a,b][a,b], and NmaxN_{\max} is the maximum LLM output token limit. The parameter θ\theta encompasses all learned model components (backbone encoder, MLP, and prediction heads).
Hint Threshold.
For queries not requiring hints (πθ​(q)=0\pi_{\theta}(q)=0), we return the direct SLM output hs​(q)h_{s}(q). For queries requiring hints (πθ​(q)>0\pi_{\theta}(q)>0), we introduce a hint size threshold ηhint\eta_{\text{hint}} to further distinguish between low-complexity and high-complexity queries:
•
If 0<πθ​(q)≤ηhint0<\pi_{\theta}(q)\leq\eta_{\text{hint}}, we query the LLM for a hint by setting max_new_tokens =πθ​(q)=\pi_{\theta}(q) and obtain hint​(q,πθ​(q))=hl(πθ​(q))​(q)\text{hint}(q,\pi_{\theta}(q))=h_{l}^{(\pi_{\theta}(q))}(q), and return the shepherded response hs​(q⊕hint​(q,πθ​(q)))h_{s}(q\oplus\text{hint}(q,\pi_{\theta}(q)));
•
If πθ​(q)>ηhint\pi_{\theta}(q)>\eta_{\text{hint}}, the query is deemed high-complexity and routed directly to LLM, returning hl​(q)h_{l}(q) without invoking the SLM.
This threshold-based routing captures the intuition that queries requiring extensive hints may be better served by the LLM’s full reasoning capacity, avoiding the overhead of generating a lengthy hint only to invoke the SLM. The threshold ηhint\eta_{\text{hint}} is a hyperparameter tuned on the validation set to balance cost and accuracy.
3.5 Reactive Shepherding: Cascading Decision
So far, we have described the shepherding model that is used in proactive shepherding. For reactive shepherding, we add a cascading decision module before the shepherding model. Further, we also incorporate features from SLM’s responses to train the shepherding model.
We make the cascading decision based on the agreement between SLM’s responses – a simple, training-free technique demonstrated to be effective in (Kolawole et al., 2025). Specifically, for each query we run the SLM KK times independently with temperature sampling (T=0.3T=0.3) to generate candidate answers {A1,…,AK}\{A_{1},\dots,A_{K}\} and associated predictive entropies {e1,…,eK}\{e_{1},\dots,e_{K}\}. We use stochastic sampling rather than deterministic decoding to obtain diversity in the responses, which enables us to measure the SLM’s epistemic uncertainty through response variation and predictive entropy. We set K=3K=3 in our experiments as a practical balance between signal quality and computational cost. Since we work with math and coding datasets, the agreement between the responses is based on exact matches in final answers.
If at least kk out of KK answers agree, we output the agreed SLM answer directly; otherwise, we invoke the Shepherding model. The choice of kk reflects a precision-cost trade-off: k=3k=3 (unanimous agreement) is more conservative, reducing false negatives at the expense of higher routing rates and LLM costs, while k=2k=2 (majority voting) is more aggressive, allowing more queries to bypass the LLM but risking more errors in direct SLM outputs. We explore both settings in our experiments (Section 4).
Given multiple responses from the SLM, we compute the following features and incorporate them in training our shepherding model.
•
Average entropy: e¯​(q)=1K​∑i=1Kei\bar{e}(q)=\frac{1}{K}\sum_{i=1}^{K}e_{i}, capturing the model’s overall uncertainty;
•
Average output length: L¯out​(q)=1K​∑i=1K|Ai|\bar{L}_{\text{out}}(q)=\frac{1}{K}\sum_{i=1}^{K}|A_{i}|, reflecting the typical response complexity;
•
Query length: |q||q|, measured in tokens via the backbone model’s tokenizer.
We use token-level length features rather than character-level measurements because tokenization aligns with the models’ internal representations and provides a more semantically meaningful proxy for reasoning complexity, longer outputs typically indicate multi-step solutions requiring more intermediate reasoning. Token-based features also enable efficient batched processing without additional tokenization overhead at inference time.
These features are standardized and fused with the text representation through a lightweight MLP. Intuitively, higher entropy indicates greater uncertainty in the SLM’s responses, suggesting that a hint is necessary. The output length statistics provide additional context regarding the verbosity required for the query.
4 Performance Comparison
In this section, we compare the cost and accuracy of Proactive and Reactive Shepherding strategies with state-of-the-art LLM routing and cascading strategies. The routing baselines include RouteLLM (Ong et al., 2025) and GraphRouter (Feng et al., 2025), while the cascading baselines include FrugalGPT (Chen et al., 2024) and ABC (Kolawole et al., 2025). We use the vanilla Llama-3.2-3B-Instruct (without finetuning) as the SLM, deployed on a local server with an NVIDIA RTX 5090 GPU. For the LLM, we query Llama-3.3-70B-Versatile via the Groq API at $0.59 per 1M input tokens and $0.79 per 1M output tokens.
4.1 Datasets and Experimental Setup
Datasets.
We evaluate all methods on four benchmarks spanning mathematical reasoning and code generation:
(a) GSM8K (Cobbe et al., 2021) is a grade-school mathematics dataset containing 7,473 training problems and 1,319 test problems. We use 776 questions for testing and the remaining 543 for validation. Each question requires multi-step arithmetic reasoning and includes a natural language solution and a numerical answer.
(b) CNK12 is a Chinese K-12 mathematics benchmark derived from the OpenR1-Math-220k dataset (OpenR1, 2025), covering diverse topics including algebra, geometry, and calculus across elementary through high school levels. We randomly sample 21,471 problems from the full dataset, partitioned into 18,251 for training, 1,073 for validation, and 2,147 for testing.
(c) HumanEval (Chen, 2021) is a code generation benchmark with 164 programming problems. Each problem includes a function signature, docstring, body, and multiple unit tests for verification. We evaluate this benchmark using the model trained on GSM8K without any code-specific training to demonstrate the generalization capability of our approach.
(d) MBPP (Austin et al., 2021) is the Mostly Basic Python Problems benchmark containing 974 crowd-sourced entry-level programming tasks, each with three automated test cases for solution verification. We evaluate MBPP in a zero-shot manner without any dataset-specific modifications.
Inference and Evaluation.
Test sets contain no pre-computed hints. At inference time, our policy predicts a hint size πθ​(q)\pi_{\theta}(q); when a hint is requested, we query the LLM with max_new_tokens set to πθ​(q)\pi_{\theta}(q), obtaining a truncated prefix that is appended to the original prompt for SLM completion. All generations use temperature 0.30.3 and top-pp 0.950.95, detailed prompt templates are provided in Appendix E.
For mathematical benchmarks (GSM8K, CNK12), we extract the final numerical answer and compare against ground truth. For coding benchmarks (HumanEval, MBPP), we execute generated solutions and verify that all unit tests pass. To obtain robust accuracy estimates under sampling variability, we perform 7 independent trials per query and apply majority voting.
