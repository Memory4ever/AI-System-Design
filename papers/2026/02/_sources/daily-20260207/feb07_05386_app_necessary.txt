1367: Appendix D Stage-wise Vector Database
1368: D.1 Architecture and Configuration
1369: We utilize ChromaDB via the langchain_chroma interface for vector persistence. To ensure high-quality semantic representation across different attack surfaces, we employ the BGE-M3 Chen et al. (2024) model as the universal embedding backbone. Each defense stage is assigned a disentangled collection (e.g., pre_planning_patterns) to maintain strict retrieval isolation and prevent cross-stage noise interference.
1370: D.2 Pattern Refinement Pipeline
1371: Rather than raw data ingestion, we implement a “Refine-and-Filter” pipeline to ensure the quality of defensive patterns. Each candidate pattern extracted from the training set must pass an LLM-based judiciary screening based on four rigorous criteria:
1373: Non-Refusal: Excludes standard LLM refusal templates to focus exclusively on adversarial logic.
1375: Alignment: Ensures the extracted essence strictly matches the semantic features of the source content.
1377: Logic Consistency: Validates that the pattern can logically synthesize a coherent and executable attack strategy.
1379: Abstraction: Guarantees the pattern remains a generalized strategy rather than a scenario-specific instance.
1380: Only patterns satisfying all four criteria are persisted with associated metadata (original content and taxonomy) for downstream retrieval.
1381: D.3 Defensive Domains and Functional Roles
1382: The vector store is partitioned into four functional libraries corresponding to the agent’s cognitive cycle:
1384: Pre-planning: Intercepts prompt injections during the reasoning and planning phase.
1386: Pre-action: Prevents parameter pollution before the execution of external tools.
1388: Post-observation: Analyzes environment feedback to detect indirect injections or malicious tool outputs.
1390: Retrieve-phase: Scrutinizes external knowledge retrieved via RAG for latent adversarial patterns.
