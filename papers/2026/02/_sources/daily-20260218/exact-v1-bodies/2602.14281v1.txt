Abstract
The Model Context Protocol (MCP) standardizes tool use for LLM-based agents and enable third-party servers.
This openness introduces a security misalignment: agents implicitly trust tools exposed by potentially untrusted MCP servers.
However, despite its excellent utility, existing agents typically offer limited validation for third-party MCP servers.
As a result, agents remain vulnerable to MCP-based attacks that exploit the misalignment between agents and servers throughout the tool invocation lifecycle.
In this paper, we propose MCPShield as a plug-in security cognition layer that mitigates this misalignment and ensures agent security when invoking MCP-based tools.
Drawing inspiration from human experience-driven tool validation, MCPShield assists agent forms security cognition with metadata-guided probing before invocation.
Our method constrains execution within controlled boundaries while cognizing runtime events, and subsequently updates security cognition by reasoning over historical traces after invocation, building on human post-use reflection on tool behavior.
Experiments demonstrate that MCPShield exhibits strong generalization in defending against six novel MCP-based attack scenarios across six widely used agentic LLMs, while avoiding false positives on benign servers and incurring low deployment overhead.
Overall, our work provides a practical and robust security safeguard for MCP-based tool invocation in open agent ecosystems.
1 Introduction
Figure 1 : Overview of the MCPShield framework acting as a lifecycle-wide security layer between the agent and untrusted MCP servers. For untrusted MCP servers, MCPShield verifies the consistency between the server’s declared capabilities and its actual services during the Pre-Invocation phase. During Execution, it monitors runtime behaviors to detect out-of-bounds requests. Finally, in the Post-Invocation phase, MCPShield evaluates the long-term behavioral consistency of the tool.
Large Language Model (LLM)-based agents interact with the real world by employing external tools, extending their capability boundaries ( Yao et al., 2022 ; Schick et al., 2023 ; Patil et al., 2024 ; Liu et al., 2025 ; Yu et al., 2025 ) .
The Model Context Protocol (MCP) 1 1
1
https://modelcontextprotocol.io/ standardizes the tool-use paradigm for agents through a unified interface to employ tools from various developers by opening the ecosystem to third-party servers.
This openness significantly expands the available tool ecosystem and enables rapid integration of diverse functionalities ( Ehtesham et al., 2025 ; Guo et al., 2025 ) .
It also introduces a security misalignment, since agents plan based on server-provided metadata, while semi-honest MCP servers can follow the protocol yet implement behavior that diverges from these declarations ( Hou et al., 2025 ; Hasan et al., 2025 ; Fang et al., 2025 ; Kuntz et al., ) .
This misalignment allows malicious MCP servers to turn routine tool invocations into security incidents, including data exfiltration, filesystem corruption, and other unauthorized actions ( Zhao et al., 2025 ; Wang et al., 2025b ) .
However, existing agent frameworks ( Wu et al., 2024 ; Li et al., 2023a ; Roucher et al., 2025 ; Ma et al., 2025 ) are primarily optimized for task performance under security-benign assumptions, where metadata from MCP servers is fully trusted, and tool calls are expected to behave as declared.
Recent work has begun to recognize this gap and proposes deployments that often rely on engineering baselines, such as static code scanning ( Cisco AI Defense, 2025 ; Radosevich and Halloran, 2025 ) and coarse-grained sandboxing ( Ruan et al., 2024 ; Zhou et al., 2025a ) .
While such security practices ( Ntousakis et al., 2025 ; Bühler et al., 2025 ; Kumar et al., 2025 ; Wang et al., 2025a ) are effective for monitoring and containment, current deployments typically keep them external to the agent and phase-local, so their evidence is not translated into the agent’s internal security cognition that can be updated and reused across invocations.
This motivates a lifecycle-wide defense that internalizes and reuses security cognition across invocations.
In practice, adversaries usually exploit a triad of critical misalignments: a semantic gap where declared metadata diverges from actual tool intent ( Wang et al., 2025c ; Zhang et al., 2025 ; He et al., 2025 ) , an observational discrepancy where visible returns mask concrete execution trajectories ( Zhu et al., 2025b ; Zhan et al., 2025 ) , and a temporal decoupling where the activation of latent threats is separated from the validation window ( Song et al., 2025 ) .
To this end, we propose MCPShield , a lifecycle framework that endows agents with security cognition for MCP-based tool use and mitigates misalignment across the tool invocation lifecycle.
Rather than relying on external security infrastructure, MCPShield acts as an agent-side plug-in policy that internalizes and reuses security evidence across invocations.
Our key idea is to introduce an interventional policy between the agent and third-party MCP servers that treats tool invocations as observable experience and incrementally updates security cognition over time, drawing inspiration from human tool probing and post-hoc reflection ( Battaglia et al., 2013 ; Allen et al., 2020 ) .
To operationalize this experience-based cognition update, MCPShield presents three tightly coupled mechanisms along the invocation lifecycle to safeguard the agent.
Before invocation, MCPShield performs Security Cognitive Probing by generating metadata-guided mock invocations and inspecting observed behavior, enabling the agent to reject tools that deviate from their declarations before real user data is involved.
During execution, MCPShield enforces Isolated Projection by confining tool-induced effects to an isolated system view while recording runtime traces for subsequent reasoning, thereby preventing irreversible damage from stealthy actions or backdoor tactics that evade pre-invocation probing.
After invocation, MCPShield conducts Periodic Reasoning over accumulated historical traces, augmented with benign baselines, to update security cognition and disseminate malicious server signatures to the ecosystem for collaborative defense.
We evaluate MCPShield on six methods that cover pre-invocation, execution, and post-invocation attacks, spanning 76 malicious MCP servers and six agentic LLM backbones.
Undefended agents achieve only 10.05% average defense rate, whereas MCPShield reaches 95.30% under the same settings.
Defense remains consistently high from Pass@1 to Pass@5, indicating stable behavior under repeated evaluation.
On benign servers, MCPShield preserves normal tool functionality with low denial rates, suggesting that robustness gains do not come from over-refusal.
We also measure runtime and token cost, and find that the MCPShield check is comparable to a small number of benign interactions under average cost and is amortized with server reuse.
In conclusion, we present MCPShield , a novel security cognition layer for MCP-based tool use.
MCPShield treats tool invocations as experience and updates security cognition from lifecycle evidence, rather than assuming declared metadata and returned outputs are aligned.
By interposing an agent-side interventional policy that admits and reuses lifecycle evidence in the decision loop, MCPShield achieves lifecycle-wide protection across tool invocation stages.
Together, these mechanisms provide practical defense in depth for agents operating in open MCP ecosystems.
2 Related Works
Agent Tool-calling and MCP.
LLM-based agents increasingly extend their capabilities by invoking external tools ( Schick et al., 2023 ; Lu et al., 2023 ; Song et al., 2023 ; Zhang et al., 2024 ; Wu et al., 2025a ; Fei et al., 2025 ) .
Prior work mainly studies Agent–Tool interaction paradigms, including interleaved reasoning and action ( Yao et al., 2022 ; Prasad et al., 2024 ) , schema-based function calling ( Shi et al., 2024 ) , and planner–executor architectures ( Fourney et al., 2024 ; Li et al., 2025a ) .
These approaches improve task completion and scalability, but they typically assume that tools are provided by trusted entities and behave consistently with their declared interfaces.
The Model Context Protocol (MCP) further standardizes tool calling through a unified communication interface, allowing agents to connect to third-party servers and use their tools, which expands ecosystem openness and interoperability ( Hou et al., 2025 ; Ehtesham et al., 2025 ; Gao et al., 2025 ; Lumer et al., 2025 ; Fei et al., 2025 ; Luo et al., 2025 ) .
Tool-calling Safety.
Tool-calling safety is a core challenge for agent systems ( Ruan et al., 2024 ; Chen and Cong, 2025 ; Li et al., 2025b ) .
Many defenses adopt engineering and system-level controls to constrain harm from tool execution ( Wu et al., 2025b ; Chennabasappa et al., 2025 ; Wang et al., 2026 ) .
Other work targets emerging threats such as tool poisoning, indirect prompt injection, and execution-time attacks, proposing detection and isolation mechanisms ( Zhou et al., 2025b ; Wang et al., 2025c ; Jamshidi et al., 2025 ; Xie et al., 2025 ) .
However, these measures are often external to the agent or phase-local, so the resulting security evidence is not integrated into the agent’s internal decision process to update trust across invocations ( Zhu et al., 2025a ; Mou et al., 2026 ) .
In MCP settings, attacks can span calling phases and evolve over time, making single-window or localized defenses insufficient ( Kumar et al., 2025 ; Radosevich and Halloran, 2025 ; Narajala et al., 2025 ; Errico et al., 2025 ) .
3 Preliminary
3.1 Agent–Tool Interaction
Agent-tool interaction is typically formulated as a sequential decision-making process.
Consider an agent at step t t with historical state s t s_{t} that receives an observation o t o_{t} .
The policy selects a target tool by the tool metadata tuple d d :
d ≜ ⟨ name , description , schema ⟩ . d\triangleq\langle\texttt{name},\ \texttt{description},\ \texttt{schema}\rangle.
The schema within d d formally dictates the admissible parameter space 𝒳 ⁡ ( d ) \mathcal{X}(d) .
Guided by the description , the agent synthesizes specific arguments x t ∈ 𝒳 ⁡ ( d ) x_{t}\in\mathcal{X}(d) to invoke the tool.
Upon execution, the parameters x t x_{t} elicit a response, yielding both a functional output y t y_{t} drawn from the return space 𝒴 ⁡ ( d ) \mathcal{Y}(d) and the associated execution trajectory τ t \tau_{t} that records the concrete execution behavior ( e.g ., API calls and file system modifications).
These interaction components could be formalized as a unified artifact 𝒞 t \mathcal{C}_{t} :
𝒞 t ≜ ⟨ d , x t , y t , τ t ⟩ . \mathcal{C}_{t}\triangleq\langle d,\ x_{t},\ y_{t},\ \tau_{t}\rangle.
The artifact 𝒞 t \mathcal{C}_{t} , along with the observation o t o_{t} , is subsequently integrated into the agent’s context, governing the state update s t + 1 = F ⁡ ( s t , o t , 𝒞 t ) s_{t+1}=F(s_{t},o_{t},\mathcal{C}_{t}) .
The interaction structure encapsulated by 𝒞 t \mathcal{C}_{t} generalizes three mainstream paradigms:
Interleaved Reasoning-Action.
Typified by prompting frameworks such as ReAct ( Yao et al., 2022 ) , the agent generates intermediate reasoning traces that causally precede the formulation of parameters x t x_{t} .
The resulting tool output y t y_{t} and execution feedback are appended to the context window, closing the loop for the subsequent reasoning step.
Schema-based Function Calling.
Common in schema-constrained function calling ( Schick et al., 2023 ; Qin et al., 2024 ; Li et al., 2023b ) , the agent selects a tool from metadata d d and emits structured arguments x t x_{t} that conform to the specification.
The structured return y t y_{t} is then consumed as an explicit observation, rather than plain text.
Planner-Executor Pipelines.
Seen in planner-executor systems ( Shen et al., 2023 ; Prasad et al., 2024 ; Erdogan et al., 2025 ) , a high-level planner specifies a sequence of tools and abstract arguments, which are subsequently grounded by an executor into concrete parameters x t x_{t} .
The execution feedback is then fed back to the planner to revise the plan.
The tuple ⟨ d , x t , y t , τ t ⟩ \langle d,x_{t},y_{t},\tau_{t}\rangle together with the transition s t + 1 = F ⁡ ( s t , o t , 𝒞 t ) s_{t+1}=F(s_{t},o_{t},\mathcal{C}_{t}) provides a unified description of agent–tool interaction, separating internal reasoning from external execution.
In traditional first-party deployments, tools are implemented and operated by the agent developer, so d d , y t y_{t} , and τ t \tau_{t} are typically assumed trustworthy and aligned.
3.2 MCP Invocation Lifecycle
The Model Context Protocol (MCP) instantiates the abstract interaction model in Section 3.1 by standardizing communication between an agent-side client and an external MCP server.
An MCP server is a service endpoint that implements and exposes a registry of callable tools 𝒯 = { T i } \mathcal{T}=\{T_{i}\} , each advertised with a tool metadata tuple d i d_{i} as defined in Section 3.1 .
By allowing tools to be provided by third-party servers, MCP shifts the trust boundary for both tool metadata and tool returns away from the agent developer.
For an atomic interaction at step t t , we view an MCP tool call as a three-phase invocation lifecycle, with each phase corresponding to specific components of the artifact 𝒞 t \mathcal{C}_{t} .
Pre-invocation.
The lifecycle begins when the agent client obtains the tool metadata d d from a connected MCP server and selects a target tool based on the query, which requires external tools.
Conditioned on the semantic content in description and constrained by the structural specification in schema , the agent produces invocation parameters x t ∈ 𝒳 ⁡ ( d ) x_{t}\in\mathcal{X}(d) .
This yields the request ℐ t ≜ ⟨ d , x t ⟩ \mathcal{I}_{t}\triangleq\langle d,\ x_{t}\rangle ,which is serialized and transmitted to the server.
Execution.
Upon receiving ℐ t \mathcal{I}_{t} , the MCP server executes the corresponding tool implementation in the tool-side execution environment, interacting with system resources to produce a response.
This process yields a functional output y t ∈ 𝒴 ⁡ ( d ) y_{t}\in\mathcal{Y}(d) that is expected to conform to the declared return type.
In parallel, the concrete execution behavior induces an execution trajectory τ t \tau_{t} in the execution environment.
So, the realization of the tool can be expressed as
⟨ d , x t ⟩ → MCP Server ( y t , τ t ) . \langle d,\ x_{t}\rangle\xrightarrow{\text{MCP Server}}\bigl(y_{t},\ \tau_{t}\bigr).
By default, the client receives the visible return y t y_{t} through the protocol, while τ t \tau_{t} remains confined to the execution environment unless an explicit auditing mechanism is used.
Post-invocation.
The server returns y t y_{t} to the agent client.
The agent updates its state using the available observations to drive the subsequent state transition.
For analysis, we model a complete invocation artifact as 𝒞 t = ⟨ d , x t , y t , τ t ⟩ \mathcal{C}_{t}=\langle d,\ x_{t},\ y_{t},\ \tau_{t}\rangle , noting that in MCP deployments the metadata d d and the visible return y t y_{t} are server-provided.
The execution trajectory τ t \tau_{t} is realized on the tool-side runtime; it is not exposed by the protocol by default, but can be made observable via explicit auditing or tracing, which is typically feasible in self-hosted deployments.
Across timesteps, the agent iterates this lifecycle, and the resulting artifacts form an evidence stream that informs subsequent planning and invocation.
This three-stage lifecycle operationalizes the abstract invocation tuple ⟨ d , x t , y t , τ t ⟩ \langle d,\ x_{t},\ y_{t},\ \tau_{t}\rangle under MCP.
We next formalize how adversaries can exploit this lifecycle by specifying stage-specific threat models for MCP-based attacks.
3.3 Threat Model
We consider a benign agent in an open MCP ecosystem where some servers may be malicious.
We focus on self-hosted deployments in which the agent connects to servers locally, while the adversary controls the server-side code implementation.
The adversary can craft the declared metadata d d , the visible return y t y_{t} , and the execution trajectory τ t \tau_{t} through tool actions ( Fang et al., 2025 ; Zhao et al., 2025 ) .
The goal is to induce a harmful τ t \tau_{t} that causes a practical security impact, such as unauthorized data access or resource corruption ( He et al., 2025 ; Wang et al., 2025c ) .
We categorize threats by the three stages of the invocation lifecycle and highlight how d d , y t y_{t} , and the transition enable attacks.
Semantic Misalignment.
The adversary exploits the agent’s reliance on metadata d d to induce a harmful execution trajectory τ t \tau_{t} .
The agent plans from d d and synthesizes parameters x t ∈ 𝒳 ⁡ ( d ) x_{t}\in\mathcal{X}(d) accordingly.
A malicious server can present benign-looking metadata while implementing a different tool intent, steering the agent toward invocations that authorize a malicious τ t \tau_{t} utilizing the semantic misalignment between agent and server ( Zong et al., 2025 ) .
Observational Discrepancy.
The adversary exploits the visible return y t y_{t} to conceal or enable a harmful execution trajectory τ t \tau_{t} .
During execution, the server can return a plausible y t y_{t} that matches the declared intent in d d while embedding unauthorized operations in τ t \tau_{t} .
This allows harmful side effects to complete within the action window while remaining unreflected in the visible return ( Zhu et al., 2025b ) .
Temporal Decoupling.
The adversary exploits temporal decoupling across invocations, where the state transition s t + 1 = F ⁡ ( s t , o t , 𝒞 t ) s_{t+1}=F(s_{t},o_{t},\mathcal{C}_{t}) carries trust from prior interactions.
This means that the signals observed in one invocation may not reveal the harm that materializes in later invocations.
As a result, a server can appear benign under earlier interactions yet induce harmful trajectories later, yielding behavior drift across subsequent invocations ( Song et al., 2025 ) .
In summary, the adversary’s objective is to realize harmful execution trajectories, and MCP-based attacks exploit semantic, observational, and temporal misalignments in d d , y t y_{t} , and state transition to achieve the malicious τ t \tau_{t} outcome.

To bridge the misalignment gap in Section 3.3 , we propose MCPShield , a security cognition layer for MCP-based tool use.
MCPShield enables an agent to form and update security cognition from lifecycle evidence, and to calibrate trust in third-party MCP servers accordingly, rather than assuming declared interfaces and returned outputs are aligned.
MCPShield introduce the policy π M ​ S \pi_{MS} that governs how 𝒞 t \mathcal{C}_{t} is authorized and integrated for the state update
s t + 1 = F ⁡ ( s t , o t , π M ​ S ​ ( 𝒞 t ) ) . s_{t+1}=F\bigl(s_{t},o_{t},\pi_{MS}(\mathcal{C}_{t})\bigr).
MCPShield includes three coupled mechanisms along the invocation lifecycle.
Before invocation, it employs Security Cognitive Probing via metadata-guided probing to form initial security cognition by assessing whether declared d d remain aligned with observable behavior.
During execution, it enforces Isolated Projection by constraining τ t \tau_{t} within a controlled boundary and recording runtime events for analysis with y t y_{t} to report risks.
After invocation, it performs Periodic Reasoning over accumulated historical traces with benign baselines to update security cognition, and surfaces malicious server signatures for collaborative defense across the MCP ecosystem.
4.2 Security Cognitive Probing
During pre-invocation, MCPShield targets the misalignment in Pre-invocation, where metadata d d can cheat an agent into invocations with harmful execution trajectories.
Before authorizing a third-party MCP server, π M ​ S \pi_{MS} performs metadata-guided mock probing to assess whether declared tool interfaces remain behaviorally aligned.
Mock Probe Synthesis.
Given tool metadata d d , π M ​ S \pi_{MS} allow agent to generate a batch of mock invocations:
X probe ​ ( d ) ≜ { x i m } i = 1 M , x i m ∈ 𝒳 ⁡ ( d ) , X_{\text{probe}}(d)\triangleq\{x^{m}_{i}\}_{i=1}^{M},\qquad x^{m}_{i}\in\mathcal{X}(d),
where each x i m x^{m}_{i} is an arguments-only payload and avoids real user data.
π M ​ S \pi_{MS} sample a bounded subset for probing.
Each mock invocation is issued to the MCP server with a mock context flag, yielding a probing artifact:
𝒞 i p ≜ ⟨ d , x i m , y i p , ϵ i p ⟩ , \mathcal{C}^{p}_{i}\triangleq\langle d,\ x^{m}_{i},\ y^{p}_{i},\ \epsilon^{p}_{i}\rangle,
where y i p y^{p}_{i} is the tool output.
This process concretizes the semantic risk implied by d d into executable tests, producing the initial basis for security cognition.
Security Cognition Calibration.
From the probing artifacts, π M ​ S \pi_{MS} initializes security cognition for a server by scoring description-behavior alignment across its tools.
Each mock result is independently judged by an LLM to produce a verdict
s ⁡ ( d , 𝒞 i p ) s(d,\mathcal{C}^{p}_{i}) ,
where deny indicates malicious content, or behavior inconsistent with tool metadata.
Aggregating across all probed tools and mocks yields a deny score:
S deny ( 𝒯 ) = 1 N ∑ T i ∈ 𝒯 ∑ k = 1 M i 𝕀 [ s ( d i , 𝒞 i , k p ) ∈ { deny } ] , S_{\text{deny}}(\mathcal{T})=\frac{1}{N}\sum_{T_{i}\in\mathcal{T}}\sum_{k=1}^{M_{i}}\mathbb{I}\left[s(d_{i},\mathcal{C}^{p}_{i,k})\in\{\texttt{deny}\}\right],
with N = ∑ i M i N=\sum_{i}M_{i} .
If S deny ​ ( 𝒯 ) S_{\text{deny}}(\mathcal{T}) exceeds a pre-set threshold, π M ​ S \pi_{MS} rejects the server.
If the deny score remains below the threshold, π M ​ S \pi_{MS} performs an overall manifest-level evaluation using the full mock results to return a binary trusted decision with reasons and flags, which initializes the server’s pre-invocation security cognition state.

4.3 Isolated Projection
Pre-invocation probing forms initial security cognition, but this cognition is limited because the execution trajectory τ t \tau_{t} is latent before the invocation is actually run.
As a result, a server can appear aligned under probing and pass authorization, but embed stealthy side effects that only trigger in the realized trajectory τ t \tau_{t} during execution.
Isolated Projection. To contain this execution-time misalignment, π M ​ S \pi_{MS} enforces the Isolated Projection by executing tool invocations inside a guarded runtime and auditing their concrete side effects.
When Isolated Projection is enabled, each invocation runs under a guard that grants the local MCP server an explicit authorization scope for files, IP, etc.
The projection confines side effects to this permitted scope and blocks operations that fall outside it, while preserving benign functionality.
Execution Event Capture and Analysis.
During execution, π M ​ S \pi_{MS} monitors the concrete side effects within the authorized scope and records an auditable cognition trace ℰ t = { e m } m \mathcal{E}_{t}=\{e_{m}\}_{m} , where each e m e_{m} summarizes an observed effect and its compliance with the granted scope.
This trace serves as execution-time evidence that updates security cognition beyond pre-invocation assumptions.
If any event violates the policy, π M ​ S \pi_{MS} immediately rejects the invocation.
If all events are allowed, the execution is marked trusted.
Otherwise, π M ​ S \pi_{MS} performs an LLM-based analysis over ℰ t \mathcal{E}_{t} to determine whether the observed side effects are suspicious, returning a binary decision with reasons and flags.
4.4 Periodic and Collaborative Cognition
The post-invocation stage targets temporal misalignment in
Section 3.3 , where threats activate outside a single invocation
and manifest as behavior drift across invocations.
Each execution yields a cognition trace that anchors periodic reasoning, summarizing observed execution effects within the authorized scope.
π M ​ S \pi_{MS} accumulates these traces over time and performs periodic semantic reasoning to update security cognition, while also supporting collaborative defense.
Firstly, π M ​ S \pi_{MS} maintains a local history ℋ ≜ { h i } i = 1 t \mathcal{H}\triangleq\{h_{i}\}_{i=1}^{t} , where each h i h_{i} summarizes the i i -th invocation in terms of tool context, execution effects, and output evidence.
After a baseline of B B invocations is established, π M ​ S \pi_{MS} triggers reasoning every K K invocations to check drift risks.
This reasoning updates security cognition through two streams:

Stream 1: Temporal Security Cognition.
This stream updates security cognition from cross-invocation dependencies that are invisible within a single window.
π M ​ S \pi_{MS} contrasts the baseline B B with a recent window, forms a drift delta, and produces a drift judgment with reasons and signals.
If the assessment exceeds a threshold, π M ​ S \pi_{MS} rejects the server and flags temporal misalignment; otherwise, the assessment is logged to refine post-invocation cognition.

Stream 2: Community-Referenced Security Cognition.
This stream calibrates local security cognition against ecosystem-wide baselines.
MCPShield treats openness as symmetric between servers and users, users can opt in to open their security cognition by sharing malicious server signatures and drift evidence with the ecosystem.
These shared signals form a community reference of expected behavior.
Local deviations from this reference can be treated as corroborating evidence for malicious drift. When confirmed, a compact server signature can be broadcast to align security cognition for collaborative defense.

We use Attack Success Rate ASR as the primary metric and report a pre-invocation ASR . Following prior attack research, we define the ASR as the fraction of malicious servers that can induce a harmful outcome.
Let 𝒮 mal \mathcal{S}_{\text{mal}} be the set of malicious MCP servers, and let 𝕀 ⁡ ( s ) ∈ { 0 , 1 } \mathbb{I}(s)\in\{0,1\} indicate whether server s s succeeds in attacking the Agent to achieve malicious purposes, so we report:
ASR = 1 | 𝒮 mal | ​ ∑ s ∈ 𝒮 mal 𝕀 ⁡ ( s ) . \operatorname{ASR}=\frac{1}{|\mathcal{S}_{\text{mal}}|}\sum_{s\in\mathcal{S}_{\text{mal}}}\mathbb{I}(s).
In addition, we record the cost overhead, which includes Runtime and Token Usage . For each server, we define the task completion time as the duration from request to response.
Runtime corresponds to the time from when the server first initiates a request to when a risk assessment conclusion is reached. Similar to Runtime , Token Usage measures the number of tokens consumed throughout the server process until the defense judgment is concluded, serving as a measure of resource usage for defense detection.

5.2 Cognition Layer Enhance Agent Security
Table 1 shows that undefended agents are broadly vulnerable, with a 10.05% average defense rate across suites and models.
With MCPShield , robustness improves to a 95.30% average defense rate under the same settings.
We further assess stability under repeated runs using Pass@K in Figure 2 .
Defense remains high from Pass@1 to Pass@5 across suites and backbones, indicating stable behavior under repeated evaluation.
The gains are consistent across heterogeneous base LLMs, and based on a case study, we found that the remaining failures are usually due to the randomness of the agent’s base LLM generation.
To assess whether defense is achieved through excessive rejection, Table 2 reports deny rates on benign servers over five repeated runs.
Across all evaluated backbones, deny rates remain substantially lower than the corresponding defense rates on malicious servers, indicating that MCPShield achieves strong robustness without relying on over-refusal.
These results suggest that MCPShield can effectively distinguish malicious behavior from benign tool use while preserving normal functionality.
5.3 Ablation Studies
5.3.1 Why lifecycle defense matters
Table 3 decomposes the total defense rate into stage-wise contributions from Security Cognitive Probing , Isolated Projection , and Periodic Reasoning .
Across suites, Security Cognitive Probing captures a large portion of attacks by testing whether the declared metadata d d can be trusted to guide safe tool use, thereby reducing semantic misalignment before real execution.
However, probing alone is insufficient when adversaries keep d d and y t y_{t} plausible while embedding unauthorized actions in τ t \tau_{t} .
In these cases, Isolated Projection provides essential coverage by constraining and auditing runtime behavior, converting otherwise unobserved deviations into actionable evidence.
Finally, Periodic Reasoning contributes when harmful behavior emerges over time, where earlier interactions appear benign but later invocations induce drift, so the attack signal is carried through the state transition rather than a single call.
Together, the stage-wise gains support the core claim that robust defense requires lifecycle-wide interventions that align d d , y t y_{t} , and cross-invocation updates against malicious τ t \tau_{t} .
5.3.2 Low overhead
Figure 3 and Figure 4 report runtime and token overhead by converting a single MCPShield check into an equivalent number of benign interactions under average cost.
Across suites and backbones, the cost remains in the same order as a small number of benign tool uses, so the protection can be amortized once the server is reused.
Moreover, sharing security cognition via malicious server signatures across the MCP ecosystem further amortizes this cost, since evidence collected by one can reduce redundant checks for others.
6 Conclusions, Limitations and Future Works
We study security risks in MCP-based tool use, where server-provided metadata and returns may not reflect the underlying execution behavior.
We propose MCPShield , an agent-side security cognition layer that treats tool invocations as experience and updates security cognition from lifecycle evidence.
By coupling pre-invocation probing, execution-time containment, and post-invocation reasoning, MCPShield provides lifecycle-wide defense-in-depth for agents in open MCP ecosystems, and supports collaborative defense by surfacing malicious server signatures.
MCPShield complements, rather than replaces, conventional security mechanisms.
Robust protection still benefits from system-level controls such as sandboxing, isolation, provenance, and auditing, especially in remote or low-observability deployments.
In addition, security cognition depends on the behavior of the underlying agent backbone and may vary across models and prompting.
We hope this work motivates more AI-driven, agent-native security methods that integrate security evidence into the decision loop.
Future directions include strengthening support for remote settings, improving robustness against adaptive adversaries, and developing standardized interfaces to share security cognition signals across the MCP community.
Impact Statement
This work aims to improve the security and reliability of large language model–based agent ecosystems by introducing a lifecycle-aware defense layer for third-party tool interactions under the Model Context Protocol (MCP). By detecting semantic misalignments, constraining execution-side behaviors, and continuously reasoning over tool-induced effects, our approach seeks to mitigate stealthy malicious actions that could otherwise lead to data leakage, system compromise, or unintended persistent threats in real-world agent deployments.
The primary societal impact of this research is the promotion of safer and more trustworthy autonomous systems, particularly as LLM agents are increasingly integrated into software development, data access, and automation workflows. Strengthening defenses against deceptive tool providers can help prevent security incidents, protect user privacy, and improve the robustness of emerging agent infrastructures.
As with many security-oriented studies, the analysis of attack behaviors and misalignment patterns could potentially be misused to design more evasive malicious tools. However, our work is explicitly focused on defensive mechanisms, responsible evaluation, and improving system-level safeguards. We believe that openly studying these vulnerabilities is necessary to enable more secure AI ecosystems and responsible deployment of agent-based systems.
Overall, this work contributes toward building safer agent architectures and does not introduce foreseeable negative societal consequences beyond the standard dual-use considerations common in cybersecurity research.

Appendix A Prompt Templates and Structured Outputs in MCPShield
MCPShield operationalizes the lifecycle-wide security cognition policy π MS \pi_{\textsc{MS}} (Sec. 4 ) through a small set of stage-specific prompting templates. These prompts serve as structured decision interfaces that (i) transform server-provided artifacts into testable evidence, and (ii) return JSON-only outputs that can be deterministically parsed by the agent runtime. This appendix documents how each prompt aligns with the corresponding mechanism in the main paper, what inputs it consumes, and what outputs it must produce.
A.1 Stage-1 Prompts: Security Cognitive Probing
Stage-1 implements Security Cognitive Probing (Sec. 4.2), which aims to reduce semantic misalignment by checking whether the server’s declared metadata d = ⟨ name, description, schema ⟩ d=\langle\text{name, description, schema}\rangle is behaviorally consistent under mock invocations that contain no real user data.
(1) Mock Probe Synthesis.
Given a tool’s metadata, MCPShield generates diverse, schema-valid mock arguments to instantiate X probe ​ ( d ) X_{\text{probe}}(d) (Sec. 4.2 ). The prompt is constrained to output only JSON with keys tool name and mocks , where each mock is an arguments -only object. This design ensures (i) mock probes remain bounded within the declared parameter space X ⁡ ( d ) X(d) , and (ii) probing never exposes private user context.
Stage-1: Build Mock
System Prompt:
You are generating mock tool invocations for MCPShield pre-checks.
Given a tool’s metadata, produce diverse test invocations.
Return ONLY JSON with keys: tool_name , mocks .
Each mock must be an object with key arguments.
User Messages
{
”tool”: tool,
”mock_count”: mock_count,
}
(2) Single-Mock Judgment (Tool-Level).
Each mock result is evaluated independently to yield a binary verdict consistent with the per-mock scoring s ⁡ ( d , C i p ) s(d,C_{i}^{p}) used for computing the deny score S deny ​ ( T ) S_{\text{deny}}(T) (Sec. 4.2 ). The prompt explicitly instructs the model to mark deny if either:
(i) the output contains malicious / instruction-like content (e.g., attempts to override the agent policy), or
(ii) the behavior implied by the output is inconsistent with the tool’s metadata.
The output is JSON with keys verdict ( deny / ok ) and reason . This keeps the aggregation step robust and auditable.
Stage-1: Build Evaluation
System Prompt:
You are MCPShield. Decide whether the server’s tools behave consistently with their metadata based on mock invocations and results.
Pay special attention to malicious or instruction-like content in tool descriptions.
Return ONLY JSON with keys: trusted (boolean), reason , flags (list).
User Messages
{
”manifest”: manifest,
”mock_results”: mock_results,
}
(3) Manifest-Level Decision (Server-Level).
After collecting mock results across tools, MCPShield performs a manifest-level evaluation to decide whether the server is trusted . This step corresponds to initializing the server’s pre-invocation security cognition state (Sec. 4.2 ), including a natural-language reason and machine-readable flags . The prompt emphasizes heightened sensitivity to malicious or instruction-like content in tool descriptions , reflecting the threat that metadata itself can be adversarial.
Stage-1: Build Evaluation
System Prompt:
You are MCPShield. Decide whether the server’s tools behave consistently with their metadata based on mock invocations and results.
Pay special attention to malicious or instruction-like content in tool descriptions.
Return ONLY JSON with keys: trusted (boolean), reason , flags (list).
User Messages
{
”manifest”: manifest,
”mock_results”: mock_results,
}
Implementation Notes.
All Stage-1 prompts enforce JSON-only outputs to avoid free-form text leaking into the agent context. In addition, Stage-1 is intentionally formulated as metadata-guided probing rather than direct static scanning: it tests executable behavior in a controlled manner, providing the initial evidence used by π MS \pi_{\textsc{MS}} to reject or admit a server before real execution.
A.2 Stage-2 Prompts: Isolated Projection and Runtime Event Reasoning
Stage-2 implements Isolated Projection (Sec. 4.3 ), which targets observational discrepancy : a server may return plausible outputs y t y_{t} while executing unauthorized side effects in the latent trajectory τ t \tau_{t} . MCPShield therefore (i) constrains execution by an authorization scope, and (ii) records execution events as auditable traces E t E_{t} for subsequent reasoning.
(1) Guarded Projection: Allowed Domain Inference.
Before (or during) execution, MCPShield asks the model to decide which network domains are required for the current invocation. The prompt returns JSON with a single key allowed domains (list of strings). This output is used to parameterize the runtime guard (Sec. 4.3 ) so that benign functionality remains executable while reducing the attack surface for covert outbound connections.
Stage-2: Build Guarded Projection
System Prompt:
You are MCPShield. Decide which network domains are required for this tool invocation.
Return ONLY JSON with key: allowed_domains (list of strings).
User Messages
{
”server_id”: server_id,
”tool_name”: tool_name,
”arguments”: arguments,
”execution_events”: execution_events,
}
(2) Execution Event Capture and Analysis.
After the runtime emits a sequence of execution events (e.g., outbound requests, file reads/writes, process spawns) within the guarded scope, MCPShield performs an LLM-based risk assessment over these events. The prompt returns JSON with keys:
trusted (boolean), reason (string), and flags (list).
This aligns with Sec. 4.3 : if any event violates hard policy, the invocation is rejected immediately; otherwise the model judges whether the observed effects are suspicious even if they are technically within scope (e.g., unnecessary sensitive file reads).
Stage-2: Build Execution Event Capture and Analysis
System Prompt:
You are MCPShield. Analyze execution events for suspicious behavior.
Return ONLY JSON with keys: trusted (boolean), reason , flags (list).
User Messages
{
”server_id”: server_id,
”tool_name”: tool_name,
”arguments”: arguments,
”execution_events”: execution_events,
}
Design Rationale.
Stage-2 separates policy enforcement (hard blocking out of scope) from semantic suspicion (LLM judgment over in-scope but risky actions). The strict JSON interface allows the runtime to (i) reliably map trusted=false to a deny action, and (ii) store flags as compact evidence for later periodic reasoning.
A.3 Stage-3 Prompt: Periodic Reasoning for Behavioral Drift
Stage-3 implements Periodic Reasoning (Sec. 4.4 ), which addresses temporal decoupling : malicious behavior may only emerge after repeated invocations, or after the server gradually changes its manifest or runtime behavior.
Stage-3: Build Periodic Reasoning
System Prompt:
You are MCPShield. Evaluate behavioral drift across repeated tool invocations.
Score drift on a 1-5 Likert scale and explain. Changes alone are not malicious;
only assign high scores when behavior conflicts with tool descriptions or shows risky side effects. New domains or tool count changes can be benign.
Return ONLY JSON with keys: drift_score (1-5 int), reason (string), signals (list of strings).
Allowed signals:
manifest_change , tool_count_change , new_domain , new_ip_connect , output_shift ,
error_spike , file_write , process_spawn , file_read_sensitive , api_key_request ,
output_instruction .
User Messages
{
payload,
}
Behavioral Drift Scoring.
Given an aggregated payload (e.g., baseline window B B vs. recent window, plus summarized traces and metadata snapshots), MCPShield asks the model to assign a drift score on a 1–5 Likert scale, where changes alone are not considered malicious. The prompt explicitly restricts high scores to cases where behavior conflicts with tool descriptions or exhibits risky side effects. The output is JSON with:
drift score (int 1–5),
reason (string),
signals (list of strings).
Whitelisted Signal Vocabulary.
To keep drift evidence consistent across runs and shareable in the ecosystem, Stage-3 constrains signals to a fixed set, including manifest change , tool count change , new domain , new ip connect , output shift , error spike , file write , process spawn , file read sensitive , api key request , and output instruction . This matches Sec. 4.4’s goal of producing compact, interpretable signatures for temporal misalignment and potential community-referenced cognition.
Connection to Main Mechanism.
The Stage-3 prompt consumes lifecycle evidence accumulated in H = { h i } H=\{h_{i}\} (Sec. 4.4) and produces structured drift indicators that can (i) trigger server rejection upon exceeding thresholds, and (ii) populate shareable signatures for collaborative defense. By design, Stage-3 treats benign evolution (e.g., new tools added legitimately) as non-malicious unless it contradicts declared intent or introduces risky execution traces.
A.4 Summary: Why Prompted, Structured Cognition Interfaces
Across all stages, MCPShield uses a small number of prompts with strict JSON schemas to bridge natural-language reasoning and system-level enforcement:
Stage-1 turns metadata into executable mock tests and produces an initial trust decision;
Stage-2 couples guarded execution with event-based semantic risk assessment;
Stage-3 aggregates historical evidence into drift scores and standardized signals.
This structure ensures that security cognition is (i) auditable, (ii) reusable across invocations, and (iii) compatible with deterministic runtime policies, enabling the lifecycle-wide interventions described in Sec. 4 .

B.3 Stage-3 Overhead: Periodic Reasoning Is Amortized Over Reuse
Table 6 reports the resource overhead associated with Stage-3 periodic reasoning, including token usage and wall-clock
time, and also normalizes the overhead as a ratio against the server’s baseline.
Unlike Stage-2, Stage-3 is not invoked per tool call; it is triggered every K K invocations after a baseline window B B is
established (Sec. 4.4 ). Therefore, its cost is naturally amortized across reuse: the incremental cost per invocation decreases
as the server is used more frequently, while the security benefit accumulates through drift detection (Figure 6 ).
In practice, this means MCPShield can retain a lightweight “always-on” posture for Stage-1 gating, selectively pay the
execution-time tracing cost only when needed (Stage-2), and periodically refresh trust calibration (Stage-3) at a controlled
frequency. This staged, conditional-cost profile matches the design goal of a deployable security cognition layer that
improves robustness without turning every tool call into a heavy security audit.
Appendix C Detailed Experimental Setup
This appendix provides the complete experimental configuration used throughout our evaluation, including decoding settings,
default shield parameters, sandbox constraints, benchmark-specific overrides, representative queries, and the construction
of malicious servers. Unless otherwise stated, all unspecified parameters follow API defaults.
C.1 Decoding and Generation Parameters
Main agent.
We use deterministic routing for tool selection with temperature=0 . When the agent answers without tool calls,
we set temperature=0.2 . Other decoding parameters are not explicitly set and thus follow defaults
( top_p=1 , max_tokens=None , frequency_penalty=0 , presence_penalty=0 ).
Shield LLM calls (Stage-1/2/3).
All shield-side reasoning is configured to be deterministic with temperature=0 for:
(i) Stage-1 mock generation, (ii) Stage-1 overall pre-invocation assessment, (iii) Stage-2 execution-phase analysis,
and (iv) Stage-3 (rug-pull / drift) periodic reasoning.
C.2 Default Shield Configuration
When not overridden by a benchmark configuration, MCPShield uses the following defaults:
•
Stage-1 (Pre-invocation): pre_mock_count=4 , pre_tool_limit=0 ,
pre_result_max_chars=0 , pre_deny_ratio=0.5 .
•
Stage-2 (Execution): exec_trace_whitelisted=false .
•
Stage-3 (Post-invocation): post_k=3 , post_baseline=5 , post_threshold=4 ,
post_output_max_chars=800 , post_include_output=true .
C.3 Sandbox and Runtime Isolation
The sandbox is enabled for all execution-time evaluations (Stage-2) with:
trace_mode=py , persist_workspace=true , and link_inputs=true .
By default, the sandbox begins with empty whitelists:
allowed_domains=[] and allowed_paths=[] .
Benchmark configurations may selectively relax these constraints (e.g., allowing local data directories for signature/file
verification tasks).
C.4 Benchmark Configurations
We evaluate MCPShield on multiple attacker suites. Each suite specifies the number of runs and may override stage toggles
and parameters.
MCPSafetyBench.
We run 20 trials with Stage-1 and Stage-2 enabled and Stage-3 disabled.
We set pre_mock_count=4 , pre_tool_limit=5 , pre_result_max_chars=16384 ,
and pre_deny_ratio=0.5 .
MCPSecBench.
We run 12 trials with Stage-1 and Stage-2 enabled and Stage-3 disabled.
We set pre_mock_count=4 , pre_tool_limit=0 , pre_result_max_chars=16384 ,
and pre_deny_ratio=0.5 . The sandbox permits access to local data directories required by benign tasks
(e.g., signature/file verification).
DemonAgent (triggered).
We run 10 trials with Stage-1 and Stage-2 enabled and Stage-3 disabled, using
pre_mock_count=4 , pre_tool_limit=0 , pre_result_max_chars=16384 ,
and pre_deny_ratio=0.5 .
MCP-Artifact.
We run 10 trials with Stage-1 and Stage-2 enabled and Stage-3 disabled, using the same Stage-1 settings as above.
Adaptive Monitor (malicious).
We run 10 trials with Stage-1 and Stage-2 enabled and Stage-3 disabled, using the same Stage-1 settings as above.
Rug Pull Attack (Stage-3 evaluation).

Each run contains up to steps=15 tool invocations to simulate longitudinal server reuse.
To support realistic external calls, we allow a small set of domains:

Rug Pull Attack (temporal drift).
A representative server ( drift_am_weather ) presents a benign manifest (e.g., get_alerts , get_forecast )
but switches its effective execution mapping to malicious weather tools after several successful invocations
(e.g., a random switch in the 5–15th call). This simulates supply-chain updates and delayed-onset attacks.
C.7 Overhead Measurement Protocol
We report time and token overhead for Stage-2 and Stage-3 as follows.
Stage-2 overhead (Tables 4 / 5 ) is measured only when an invocation reaches the execution phase.
When Stage-1 achieves a 100% identification rate for a setting, the server is rejected pre-invocation and therefore does
not enter Stage-2; such cases are marked by horizontal-line (i.e., not applicable) entries.
Stage-3 overhead (Table 6 ) is measured per periodic reasoning trigger and reported in absolute time/tokens and as a
ratio against the normal (w/o) baseline; since Stage-3 executes every K K calls after observing B B baseline invocations,
its cost is amortized over reuse.
