B7: Asynchronous Verified Semantic Caching for Tiered LLM Architectures
B8: Asmit Kumar Singh Haozhe Wang Santosh Attaluri Tak Chiam Weihua Zhu Affiliation: Apple August 24, 2026 Abstract
B9: Large language models (LLMs) now sit in the critical path of search, assistance, and agentic workflows, making semantic caching essential for reducing inference cost and latency. Production deployments typically use a tiered static-dynamic design: a static cache of curated, offline vetted responses mined from logs, backed by a dynamic cache populated online. In practice, both tiers are commonly governed by a single embedding similarity threshold, which induces a hard tradeoff: conservative thresholds miss safe reuse opportunities, while aggressive thresholds risk serving semantically incorrect responses. We introduce Krites , an asynchronous, LLM-judged caching policy that expands static coverage without changing serving decisions. On the critical path, Krites behaves exactly like a standard static threshold policy. When the nearest static neighbor of the prompt falls just below the static threshold, Krites asynchronously invokes an LLM judge to verify whether the static response is acceptable for the new prompt. Approved matches are promoted into the dynamic cache, allowing future repeats and paraphrases to reuse curated static answers and expanding static reach over time. In trace-driven simulations on conversational and search workloads, Krites increases the fraction of requests served with curated static answers (direct static hits plus verified promotions) by up to 3.9 times for conversational traffic and search-style queries relative to tuned baselines, with unchanged critical path latency.
B10: 1 Introduction
B11: Large language models (LLMs) have transitioned from research prototypes to core infrastructure for conversational assistants, search engines, productivity tools, and code assistants ( Zhao et al., 2023 ; Achiam et al., 2023 ) . Their deployment is constrained by a familiar systems triad of cost, latency, and quality: each prompt triggers multiple expensive forward passes through a large transformer, and inference often dominates the budget ( Kwon et al., 2023 ; Xiong et al., 2024 ) . This pressure is amplified in modern agentic stacks that orchestrate workflows with multiple steps(retrieval, planning, tool use, reflective revision) across multiple model calls ( Wang et al., 2023 ) , including emerging LLM-centric search stacks ( Wang et al., 2024 ; Liu et al., 2024 ) . For such workloads, even modest reductions in backend invocations can yield significant gains in cost and tail latency.
B12: Caching is the standard systems lever for reuse. Information retrieval (IR) systems have long applied result caching to avoid recomputing expensive ranking pipelines ( Fagni et al., 2006 ; Baeza-Yates et al., 2008 ) . At large scale, production systems are often tiered: a static cache populated offline from historical logs, backed by a dynamic cache populated online to absorb tail traffic and short-term trends ( Fagni et al., 2006 ; Baeza-Yates et al., 2008 ; Mele et al., 2020 ) . Static entries are often curated by heavier offline pipelines (larger models, safety review, human evaluation), so each additional static origin hit can carry outsized value in stability and reliability relative to serving an online generated answer.
B13: Semantic caching extends caching to LLM workloads by relaxing exact key matching. Instead of requiring identical strings, a semantic cache embeds each prompt into a vector space and retrieves nearest neighbors from a vector database ( Bang, 2023 ; Pan et al., 2024 ) . If similarity exceeds a threshold, the cache reuses the cached response and avoids invoking the LLM backend. Semantic caching can substantially reduce latency on workloads with recurring intents and paraphrases ( Bang, 2023 ; Zhu et al., 2024 ) , and is especially effective for short to medium prompts such as search queries and assistant calls ( Schroeder et al., 2025 ) .

B24: This suggests a natural systems question: can we preserve a conservative, latency-friendly threshold policy on the critical path, but use a high precision equivalence check to safely recover static misses from the grey zone?
B25: LLM-as-a-judge provides such an equivalence check. When prompted with explicit rubrics and candidate pairs, LLM judges can achieve high agreement with semantic equivalence labels across a range of tasks ( Zheng et al., 2023 ; Gu et al., 2024 ; Tan et al., 2024 ) , and pairwise equivalence questions with explicit criteria are particularly tractable ( Zeng et al., 2025 ) . However, placing an LLM judge directly on the serving path adds latency and compute to borderline requests, eroding the main benefit of caching for interactive workloads.
B26: This paper proposes Krites , an asynchronous, verified semantic caching policy for tiered static–dynamic architectures. Krites preserves the standard GPTCache-style threshold policy on the serving path, but when a request misses the static tier while its nearest static neighbor falls in a grey zone, Krites schedules an off path LLM judge that decides whether the static response is acceptable for the new prompt. Approved pairs trigger an auxiliary overwrite that upserts the static response into the dynamic cache under the new key, turning the dynamic cache into a mutable pointer layer over static answers (Figure 1 b).

B68: 3.1 Grey-zone trigger and task scheduling
B69: We introduce a lower similarity cutoff σ min < τ static \sigma_{\min}<\tau_{\text{static}} that defines the grey zone for static candidates. Static neighbors with s static < σ min s_{\text{static}}<\sigma_{\min} are treated as clearly non-interchangeable and are never sent to the judge, while candidates with s static ∈ [ σ min , τ static ) s_{\text{static}}\in[\sigma_{\min},\tau_{\text{static}}) are considered ambiguous and may be promoted if the judge confirms equivalence.
B70: Operationally, VerifyAndPromote is executed by a background worker pool. In typical deployments, the worker pipeline includes (i) queueing and rate limiting, (ii) deduplication to avoid repeated judging of the same ( q , h static ) (q,h_{\text{static}}) pair, and (iii) retry logic with backoff for transient failures. Because the task is off path, queue depth affects only how quickly the pointer layer is populated, not serving latency.
B71: 3.2 LLM judge requirements
B72: Task.
B73: The function J(q,h,a) requires a binary semantic judge: given an incoming prompt q, a cached prompt h, and the cached answer a, it must decide whether a is an acceptable answer for q. In a production setting, this can be implemented via a strict, rubric guided LLM prompt evaluating intent, entity matching, and freshness constraints. Because such LLM-as-a-judge formulations already achieve high agreement with semantic equivalence labels ( Zheng et al., 2023 ; Gu et al., 2024 ; Tan et al., 2024 ) , our evaluation (Section 4 ) abstracts the specific prompt implementation and instead uses an oracle derived from ground truth equivalence classes to establish the policy’s model agnostic performance bounds.
B74: 3.3 Auxiliary overwrite semantics
B75: The auxiliary overwrite in VerifyAndPromote (Algorithm 2 ) is what couples the static and dynamic tiers. Consider the dog-honey example in the introduction. The static cache contains a canonical prompt h h (“Can my dog have honey?”) with curated answer A ⁡ ( h ) A(h) . A user issues q q (“What’s the word on my dog having honey?”). If s static ∈ [ σ min , τ static ) s_{\text{static}}\in[\sigma_{\min},\tau_{\text{static}}) , Krites enqueues VerifyAndPromote . If the judge approves, Krites upserts ( q , A ⁡ ( h ) , v q ) (q,A(h),v_{q}) into C dynamic C_{\text{dynamic}} . The next time q q (or a nearby paraphrase that hits this dynamic key) appears, the system serves the curated static answer from the dynamic tier.
B76: In implementation, the overwrite should be idempotent and safe under concurrency. A common approach is to store a small amount of metadata with each dynamic entry (e.g., a “static-origin” bit and timestamp) and use last-writer-wins or timestamp guarded upserts to avoid overwriting a newer entry if that is undesirable in a particular deployment.
B77: Krites does not modify the eviction policy of C dynamic C_{\text{dynamic}} : promoted static entries are subject to the same LRU/TTL rules as all other dynamic entries. Verified pointers that are rarely used will eventually be evicted, and if the corresponding query reappears after eviction it again follows the baseline path and may trigger a new verification. This keeps the dynamic tier bounded without pinning static-derived entries and ensures that Krites inherits the capacity and freshness properties of the underlying dynamic cache.
B78: 3.4 Cost and capacity considerations
B79: Krites introduces additional compute via off-path judge calls. The judge invocation rate is bounded by the frequency of grey-zone static misses and is controlled by σ min \sigma_{\min} : raising σ min \sigma_{\min} reduces judge volume but also reduces recovered static hits, while lowering σ min \sigma_{\min} expands coverage but increases judge cost. Section 5 discusses ROI tradeoffs and practical throttling strategies.
B80: 4 Experimental evaluation
B81: We evaluate Krites with trace-driven simulations on the two open benchmarks introduced by vCache ( Schroeder et al., 2025 ) . In all experiments we reuse the embeddings, ground truth equivalence classes. Krites requires a binary decision J ⁡ ( q , h , a ) J(q,h,a) to approve promotions. To keep our evaluation model-agnostic and consistent with vCache, we do not run an LLM judge during simulation. Instead, we instantiate J J directly from the benchmark equivalence relation: we approve iff the query q q and the candidate neighbor h h share the same ground truth class under the benchmark labels. Notably, the dataset labels were originally generated through LLM judges.
