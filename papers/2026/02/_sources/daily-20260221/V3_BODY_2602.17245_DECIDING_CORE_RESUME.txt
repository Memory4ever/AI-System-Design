3.1. Web Verbs
As introduced in §1, a verb is a high-level, typed, function-like abstraction of an operation that a website can perform. Unlike primitive actions such as text entry or mouse clicks, or raw HTTP/API calls, a verb directly names the intended operation and specifies its inputs, outputs, and effects. For agents, verbs act as stable units for planning and execution: they can be invoked programmatically and composed into workflows, avoiding the fragility and length of low-level action traces.
The verb layer unifies browser-side interactions and server-side APIs. Implementation details are hidden behind a common typed interface. When a site provides a suitable API, developers wrap the endpoint as a verb (for example, Spotify’s search endpoint with parameters for query, item type, and market). When functionality resides in client flows, such as adding an item to a shopping cart on Amazon, developers implement the verb by programmatically driving the browser. In both cases, agents interact only with verbs, making the distinction between API and GUI orthogonal at the call boundary.
To fulfill their purpose effectively, verbs should satisfy the following essential properties:
•
Semantic clarity. Each verb should state its intended operation explicitly in natural language so that its role is transparent to both agents and developers.
•
Typed parameters. Inputs should have proper names and types, ensuring unambiguous invocation and consistent integration into workflows.
•
Structured results. Outputs should be returned as standardized objects or records so that subsequent steps can consume them directly without additional parsing.
•
Composability. Verbs should be callable in sequence, allowing tasks to be represented as concise programs over meaningful operations rather than long traces of primitive actions.
•
Auditability. Each invocation should produce explicit inputs and outputs that can be logged, validated, and checked, providing a basis for verification and debugging.
3.2. Code Synthesis over Verbs
With verbs as the abstraction layer, tasks are no longer carried out as step-by-step predictions of primitive actions within the perception-action loop. Instead, the agent generates explicit programs composed of verb calls. Each verb has a precise specification of its inputs and outputs, so every invocation behaves as a well-defined function rather than an ambiguous low-level action. Within a program, the results of a verb can be transformed, combined with other data, or used as conditions for subsequent steps. This makes the logic of the task explicit in code: the synthesized program specifies not only which verbs are invoked but also how their outputs are processed and connected.
The composition of verbs is not limited to a linear flow. Programs can include control structures such as conditionals, where the next operation depends on intermediate results, or loops, where the same verb is applied repeatedly over a collection of inputs. Branching and iteration are thus expressed directly in the program rather than being decided incrementally during execution.
This stands in contrast to existing web agents, which must repeatedly observe the current state and predict the next low-level action. By operating at the level of verbs, the agent instead constructs a complete procedure in advance, with the sequence of operations and their dependencies made explicit. The role of the agent shifts from predicting primitive steps to composing structured programs that capture the semantics of the task.
4. Prototype and Case Studies
4.1. Prototype Overview
To implement the ideas presented in §3, we developed a proof-of-concept system for the verb layer. This prototype demonstrates how verbs can be created, documented, and combined into executable workflows.
We assume the role of a website developer. Wrapping a web API as a verb is straightforward. For browser-based functionality, we built a Chrome extension to support the process. The extension records details of browser actions and the targeted HTML elements while we manually operate the browser. The recorded action trace is then used to generate a function that calls the Playwright library to perform each browser operation. We test and debug the function to remove unnecessary steps and confirm the correctness of the element locators. Once the function reliably reproduces the action trace, variable elements corresponding to user input are abstracted into typed parameters, and outputs are organized into structured result objects. Each verb is paired with a concise natural language description specifying its intended behavior.

Figure 3 illustrates how the verb google_maps::get_direction is implemented. The function performs steps such as entering a source and destination, selecting the driving option, and reading the resulting route. Each action corresponds to a Playwright call, while the inputs are abstracted into parameters and the outputs (travel time, distance, and route) are returned as a structured result. In this way, the sequence of browser operations is transformed into a stable packaged verb by the developers.
It is worth noting that some element locators, such as Fk3sm, are opaque constants rather than random strings. They remain consistent across different sessions, browsers, and client machines. However, as we will discuss in §6, standardization of locator strings is crucial for the agentic web. The HTML standard should introduce a “stable-public-locator” attribute for elements intended for external reference by code or agents. Such an attribute would form part of the public interface of a website, and modifying it would constitute a breaking change.
We implemented verbs for 13 widely used websites, grouped into five categories: E-commerce, Travel, Knowledge, Media, and Others.
