L301: ### 4.1. Cryptographically Attested Identity Infrastructure
L302: The current mobile agents rely on easily spoofed identifiers (e.g., package names or icons), leaving the agents vulnerable to redirection and impersonation attacks such as Task Hijacking (cite127†Promon, 2019 ; cite128†Ren et al., 2015 ). Aura mitigates these risks by treating every agent as a cryptographic principal identified by an Agent Identity Card (AIC). This infrastructure is rooted in a Global Agent Registry (GAR) and enforced by the TEE-backed Agent Kernel.
L303: #### 4.1.1. The Global Agent Registry (GAR)
L304: 
L305: The GAR is a centralized or federated trust anchor operated by OS/OEM vendors and stakeholders. It serves as the ecosystem’s Certificate Authority (CA) and policy oracle.
L306: 
L307:   * •
L308: 
L309: Developer Enrollment: Developers register via vetted accounts and provision a hardware-backed developer key (stored in an HSM/TPM). This key never leaves the provider infrastructure and serves as the root of developer identity.
L310: 
L311:   * •
L312: Trust Anchor Pinning: The public GAR root keys are embedded into the mobile device’s secure boot chain. This ensures the Agent Kernel only honors AICs and revocation data chaining back to the authentic GAR, preventing trust-anchor replacement even if the high-level OS is compromised.
L313: #### 4.1.2. The Agent Identity Card (AIC)
L314: 
L315: The AIC is a cryptographically immutable “digital passport” for an agent. Inspired by the Verifiable Credentials (cite129†et al., 2025 ) and recent proposals for agentic identity (cite130†South et al., 2025 ; cite131†Zou et al., 2025 ), it binds three dimensions into a unique subject: the developer identity, the App bundle (code signature), and the end-user account.
L316: To enforce least-privilege, the AIC includes a static capability boundary ($\mathcal{S}_{\max}$), defining the maximum scope of domains and semantic permissions that the agent may ever request. Formally, an AIC ($\mathcal{C}_{\textsf{agent}}$) is defined as:
L317: 
L318: (1)  |  | $$\mathcal{C}_{\textsf{agent}}=\text{Sign}_{\textsf{GAR}}\left(\textsf{DID}_{\textsf{agent}}\parallel K_{\textsf{pub}}\parallel\mathcal{S}_{\max}\right)$$  |
L319: 
L320: where:
L321: 
L322:   * •
L323: $\textsf{DID}_{\textsf{agent}}$: A Decentralized Identifier for the $\langle\text{developer, bundle, user}\rangle$ triple.
L324: 
L325:   * •
L326: 
L327: $K_{\textsf{pub}}$: The public key for mutual attestation and secure session establishment.
L328: 
L329:   * •
L330: 
L331: $\mathcal{S}_{\max}$: A declarative manifest of allowed semantic permissions and domains.
L332: #### 4.1.3. AIC Provisioning and Key Management
L333: 
L334: AICs are provisioned during agent installation or first-login. The sequence is as follows:
L335: 
L336:   1. (1)
L337: 
L338: TEE Key Generation: The Agent Kernel commands the TEE to generate a per-instance pair $(K_{\textsf{pub}},K_{\textsf{priv}})$. The Agent Kernel retains an opaque handle to $K_{\textsf{priv}}$.
L339: 
L340:   2. (2)
L341: Registry Validation: An OS-privileged service sends the $\textsf{DID}_{\textsf{agent}}$, $K_{\textsf{pub}}$, and the developer-signed $\mathcal{S}_{\max}$ to the GAR. The GAR validates the request against platform policies (e.g., preventing a calculator app from requesting camera access) and issues the signed $\mathcal{C}_{\textsf{agent}}$.
L342: 
L343:   3. (3)
L344: Local Binding: The Agent Kernel stores the AIC and maps it to the concrete OS principal (UID + package signature). This ensures only the authorized process can ever trigger the TEE to exercise $K_{\textsf{priv}}$.
L345: #### 4.1.4. Runtime Mediation and Mutual Attestation
L346: 
L347: Identity enforcement is maintained at runtime through Kernel-Mediated Mutual Attestation using short-lived session tokens for all participants, including the SA.
L348: TEE-Backed Mediation. $K_{\textsf{priv}}$ is never exposed to user-space. The Agent Kernel acts as the sole mediator, exposing only handle-based APIs. When an agent requests a signing operation, the Agent Kernel implicitly captures the OS security context (e.g., PID, UID, and SELinux labels) and verifies it against the identity bound to the AIC handle.
L349: 
L350: Mutual Attestation Protocol. To secure interactions between the SA and AAs:
L351: 
L352:   * •
L353: SA Authentication: Upon startup, the SA must present its AIC to the Agent Kernel. The Agent Kernel verifies the GAR signature, binds the SA to the active user account, and issues an SA Session Token. This token constrains the SA to its own capability boundary $\mathcal{S}^{SA}_{\max}$.
L354: 
L355:   * •
L356: 
L357: AA Invocation: When the SA invokes an AA, it presents its SA session token. The Agent Kernel validates the AA’s AIC, extracts $\mathcal{S}^{AA}_{\max}$, and installs it as a Trust Boundary in the policy engine.
L358:   * •
L359: 
L360: Token Issuance: Upon successful attestation, the Agent Kernel issues a unique session token to the AA process. Both SA and AA must present their respective tokens for every security-sensitive Agent Kernel API call.
L361: 
L362: Token Integrity and Anti-Spoofing. To prevent token abuse or inter-process spoofing, the Agent Kernel implements three defense layers:
L363: 
L364:   * •
L365: Implicit Context Binding: The Agent Kernel does not rely on self-reported identifiers. For every API request, the Agent Kernel extracts the caller’s PID and UID from internal OS structures and cross-references them against a Token-to-Process Map. A token presented by a process other than the one to which it was initially issued is immediately rejected.
L366: 
L367:   * •
L368: Lifecycle Ephemerality: Tokens are tied to the process lifecycle. If an agent crashes or restarts, its previous token is invalidated. The new process must re-authenticate to obtain a fresh token with a new high-entropy session ID, preventing replay attacks.
L369: 
L370:   * •
L371: Non-Exportable Handles: Session tokens act as handles to TEE-protected keys. Because the Agent Kernel is the sole interface to the TEE and validates the caller’s execution context before exercising $K_{\textsf{priv}}$, a stolen token is useless outside the specific, authorized process memory space.
L372: This design ensures that even a compromised SA is restricted by its own cryptographic bounds, and no AA can spoof the orchestration authority of the SA or the identity of another AA. Every SA/AA action is unambiguously attributed to a specific, GAR-certified identity.
L373: ### 4.2. Perceptual Authenticity & Sanitization: The Semantic Firewall
L374: 
L375: The Agent Kernel implements a semantic firewall to address three security challenges: it verifies observation authenticity through cryptographic attestation, prevents privacy leakage via sensitive information detection, and defends against adversarial inputs through prompt isolation and malicious intent filtering.
L376: In our architecture, perception corresponds to structured observations emitted by AAs rather than raw pixels. To guarantee their authenticity, every observation (e.g., a list of search results or a payment quote) is encapsulated in an attestation envelope signed with the corresponding AA’s AIC key and bound to device-side evidence such as timestamps, OS-level resource identifiers, and—when available—TEE measurements.
L377: The Agent Kernel verifies this envelope against the GAR root (see § cite17†4.1.1 ) before admitting the observation into the SA’s context, ensuring that the perceived state genuinely originates from a legitimate execution path instead of an injected string or off-path process.
L378: #### 4.2.1. Hybrid Sensitive Information Detection
L379: 
L380: To prevent sensitive information from being inadvertently transmitted to the external, cloud-based LLMs, the Agent Kernel employs a hybrid detection mechanism that combines deterministic pattern matching and probabilistic entity recognition.
L381: Deterministic Matching via Regular Expressions. The Agent Kernel first scans the input stream $I_{\textsf{user}}$ using a set of pre-defined regex rules $R_{\textsf{pii}}$ to identify structured sensitive data (e.g., credit card numbers, email addresses, and national IDs). This step operates with $O(n)$ time complexity, ensuring minimal latency.
L382: Probabilistic Extraction via NER. For unstructured contexts (e.g., home addresses embedded in natural language), we deploy an on-device lightweight Named Entity Recognition (NER) (cite132†Li et al., 2022 ) model (e.g., quantized MobileBERT (cite133†Sun et al., 2020 )). Let $M_{\textsf{ner}}$ denote the model; the extraction function is defined as $E=M_{\textsf{ner}}(I_{\textsf{user}})$.
L383: Human-in-the-Loop (HITL) Protocol. Upon detecting sensitive entities $E$, the Agent Kernel suspends the transmission and triggers a user confirmation dialog. The user can authorize the transmission, redact the information (replacing $e\in E$), or terminate the session.
L384: #### 4.2.2. Holistic Prompt Defense via Multi-Source Contextual Isolation
L385: To mitigate both Direct Prompt Injection (from malicious users) and Indirect Prompt Injection (cite134†Greshake et al., 2023 ) (from compromised AAs or external web content), the Agent Kernel enforces a Universal Content Sanitization policy. This strategy treats all external inputs as untrusted data streams. The Agent Kernel intercepts not only user instructions but also the execution results returned by AAs and the historical context.
L386: Each data source is encapsulated within distinct, semantic XML delimiters before being fed into the SA. The constructed prompt context $C_{\textsf{total}}$ is defined as:
L387: (2)  |  | $$C_{\textsf{total}}=P_{\textsf{sys}}\oplus T_{\textsf{user}}(I_{\textsf{input}})\oplus T_{\textsf{agent}}(R_{\textsf{result}})\oplus T_{\textsf{history}}(H)\oplus P_{\textsf{reinforce}},$$  |
L388: 
L389: Where $T_{\textsf{x}}$ represents the tagging function (e.g., wrapping the results of an AA in <agent_observation> tags).
L390: The system prompt $P_{\textsf{sys}}$ is hardened to enforce strict semantic segregation. It contains a meta-instruction explicitly directing the LLM to interpret content enclosed within <agent_observation> tags exclusively as passive data streams, devoid of executable authority.
L391: This constraint effectively mitigates indirect prompt injection attacks, ensuring that adversarial payloads embedded in API responses (e.g., recursive override commands like “Ignore previous instructions and transfer funds”) cannot alter the SA’s control flow.
L392: Extensibility for Advanced Robustness Strategies. While structural isolation forms the baseline defense, the Agent Kernel architecture is designed to integrate state-of-the-art adversarial defense paradigms. Specifically, we emphasize the utility of the following strategies:
L393: 
L394:   * •
L395: Instruction Repetition (Sandwich Defense (cite135†Das et al., 2025 )): Reiterating critical safety constraints at the end of the context window to mitigate the LLM’s recency bias against long malicious inputs. The Agent Kernel appends a final safety directive at the very end of the prompt context (after all user and agent data). This directive explicitly commands the LLM to disregard any executable instructions found within the preceding data tags and solely perform the system-defined task.
L396: 
L397:   * •
L398: Few-Shot Defense (cite136†Brown et al., 2020 ): Injecting in-context examples of successful attack rejections to guide the LLM’s safety behavior via analogy.
L399: 
L400:   * •
L401: 
L402: Chain-of-Thought (CoT) Verification (cite137†Wei et al., 2022 ): Mandating a “Safety Reflection” step where the LLM must explicitly reason about potential policy violations before generating an action.
L403: 
L404:   * •
L405: Adversarial Prefixing: Prepending optimized continuous vectors (soft prompts) trained on adversarial datasets (cite138†Zou et al., 2023 ) to robustly disrupt gradient-based attack patterns.
L406: #### 4.2.3. Two-Stage Malicious Intent Filtering
L407: 
L408: To balance real-time responsiveness with rigorous safety compliance, we design a hierarchical filtering mechanism comprising a local deterministic guardrail and an optional cloud-based semantic alignment verifier.
L409: Local Deterministic Screening. The first line of defense is a lightweight, on-device policy engine that screens inputs against a curated keyword blacklist $B_{\textsf{adv}}$ (e.g., jailbreak templates like “DAN mode” (cite139†Shen et al., 2024 )). Inputs matching $I_{\textsf{user}}\cap B_{\text{adv}}\neq\emptyset$ are immediately rejected at the edge.
L410: Optional Cloud-Based Semantic Adjudication. To address sophisticated attacks that employ linguistic obfuscation or implicit malice—which typically evade lexical matching—we introduce a cloud-resident Semantic Alignment Verifier. This component leverages a specialized LLM fine-tuned on a corpus of and ethical alignment principles, such as the EU General Data Protection Regulation (GDPR) (cite140†, 2016 ) and local cybersecurity laws.
L411: It evaluates the semantic intent of the input against this normative framework to minimize false negatives. However, recognizing that deep semantic inference introduces non-negligible network and computation latency, this verification layer is designed as a configurable security module. The Agent Kernel selectively enables this high-latency protection for sensitive operation contexts (e.g., financial transactions) or based on explicit user instructions.
L412: ### 4.3. Cognitive Security & Planning Integrity
L413: 
L414: This module functions as the core safety barrier within the Agent Kernel, ensuring that execution plans generated by the SA strictly align with the user’s original intent. While the semantic firewall discussed in § cite21†4.2 sanitizes inputs, the Cognitive Security layer focuses on internal state integrity, effectively mitigating semantic drift and “Cross-App Data Pivoting” risks during the reasoning process.
L415: #### 4.3.1. Secure Memory Architecture: Taint-Aware Information Flow
L416: 
L417: To mitigate the risk of cross-App data pivoting, where an agent (SA or AA) unwittingly retrieves malicious data from untrusted sources and injects it into sensitive sinks, we redesign the agent’s memory as a Taint-Aware Hierarchical System (cite117†Enck et al., 2014 ).
L418: Provenance-Based Source Tagging. We abandon content-based filtering in favor of a deterministic provenance-based trust model. We persist security metadata within the memory schema ($M=\langle\textsf{Content},\textsf{Tag}_{\textsf{origin}}\rangle$), assigning tags based strictly on the data’s entry point:
L419: 
L420:   * •
L421: TAG_VERIFIED: Treated as the “Ground Truth” of intent, this data originates exclusively from the SA’s internal state or direct user input sanitized by the aforementioned two-stage malicious intent filtering (§ cite24†4.2.3 ).
L422: 
L423:   * •
L424: 
L425: TAG_TAINTED: All data ingested from external environments, including Web observations (HTML/DOM), third-party App GUI states, and the system clipboard. These sources are inherently assumed to contain potential adversarial prompts or false information.
L426: Stateful Persistence and Propagation. This tag remains cryptographically bound to the content throughout its lifecycle, whether in short-term context or long-term vector storage, preventing “memory laundering.” Furthermore, we enforce dependency propagation: if the agent’s reasoning process derives a new variable from a TAG_TAINTED memory block, the result inherits the tainted status.
L427: Enforcement with Declassification. Security enforcement occurs during the tool invocation phase via a “No-Write-Down” policy. If the agent attempts to retrieve a TAG_TAINTED variable to populate a parameter of a Critical Node (defined in § cite30†4.4.2 ), the system intercepts the operation.
L428: The execution can only proceed via Human-in-the-Loop Declassification: the system presents a confirmation card, and only upon physical user approval is the taint tag stripped (Sanitization), allowing the data to flow into the privileged sink.
L429: #### 4.3.2. Plan–Trajectory Alignment
L430: Beyond memory-level taint tracking, we constrain the SA’s planning process to prevent gradual semantic drift across multi-step trajectories. At the planning layer, the Cognitive Security module constrains how the SA constructs and updates multi-step execution plans over time.
L431: Rather than treating each tool call as an independent decision, the SA operates over an explicit trajectory $\mathcal{T}=\{(I_{\textsf{user}},A_{1},\ldots,A_{t})\}$, where every candidate next action must be justified against both the original instruction and the already executed steps.
L432: Before a plan is materialized into concrete API calls, the SA performs a self-consistency pass to detect semantic drift (e.g., a trajectory that gradually morphs from “book a train ticket” to “install a new app”) and to re-anchor the goal using the trusted, taint-aware memory state.
L433: This trajectory-aware planning view is complementary to the runtime checks which will be described in § cite28†4.4 .
L434: Cognitive Security focuses on which actions should appear in the plan and in what order, enforcing invariants such as “no high-privilege Critical Node may be introduced without an explicit user-visible justification.” When combined with the Action Access Control mechanisms discussed in § cite28†4.4 , the Agent Kernel ensures that both the high-level route and the concrete steps of an agent’s behavior remain tightly aligned with the user’s intent and prior approvals.
L435: ### 4.4. Action Access Control & Accountability
L436: 
L437: At the execution layer, the Agent Kernel transforms high-level plans into enforceable policies on concrete actions. This subsection first introduces our access-control primitives—Critical Node Interception, Dynamic Domain Verification and Egress Filtering, and the Runtime Alignment Validator (with an optional optimistic mode)—and then shows how they are coupled with full-lifecycle attributed traces to provide non-repudiable accountability.
L438: #### 4.4.1. Dynamic Least-Privilege Enforcement
L439: 
L440: Unlike traditional permission models where third-party Apps request broad static permissions upon installation, the Agent Kernel enforces a Just-in-Time (JIT) authorization model.
L441: 
L442: Intent-Driven Permission Derivation. When the SA plans a task, its underlying LLM analyzes the user instruction $I_{\textsf{user}}$ to derive the minimal necessary permission set $P_{\textsf{req}}$ for the current execution step.
L443: Boundary Validation and Negotiation. Before granting access to any Critical Node (defined in § cite30†4.4.2 ), the Agent Kernel performs a two-step validation:
L444: 
L445:   1. (1)
L446: 
L447: Static Boundary Check: it verifies if $P_{\textsf{req}}\subseteq\mathcal{S}_{\max}$ (defined in § cite16†4.1 ). If the request exceeds the agent’s static capability manifest (e.g., a Calculator agent requesting Contacts), it is instantly rejected as a policy violation.
L448: 
L449:   2. (2)
L450: Dynamic User Consent: if the above check passes but the permission is not currently held by the agent, the Agent Kernel suspends execution and triggers a dynamic permission request. This ensures that permissions are granted only when contextually relevant and justified by the immediate task.
L451: #### 4.4.2. Critical Node Interception
L452: 
L453: To prevent unauthorized operations, the Agent Kernel enforces a “Monitor-on-Access” mechanism. Since both the SA and AA must invoke Android Framework APIs (cite141†Backes et al., 2016 ) to effectuate changes, we define these sensitive API calls as Critical Nodes. The Agent Kernel maintains a Critical Nodes Registry, including:
L454: 
L455:   * •
L456: 
L457: Financial & Assets: Calls involving payment APIs (e.g., Wallet integration) or premium SMS services.
L458: 
L459:   * •
L460: Data Persistence: Operations requiring WRITE_EXTERNAL_STORAGE or database modifications.
L461: 
L462:   * •
L463: 
L464: Privacy Access: Requests for READ_CONTACTS, ACCESS_FINE_LOCATION, or call logs.
L465: 
L466:   * •
L467: 
L468: System Integrity: High-privilege actions such as INSTALL_PACKAGES or modifying system settings.
L469: 
L470:   * •
L471: 
L472: Network Egress: Outbound HTTP/HTTPS or WebSocket requests attempting to transmit data to external servers.
L473: Regardless of whether the request originates from the SA or an AA, triggering a Critical Node automatically suspends execution. The request is first checked against the Taint Policy (see § cite26†4.3.1 ), and if compliant, it is routed to the Runtime Alignment Validator that shall be discussed in § cite32†4.4.4 .
L474: #### 4.4.3. Dynamic Domain Verification and Egress Filtering
L475: 
L476: To mitigate the risk of “Data Exfiltration” where a compromised AA (e.g., victim of prompt injection) attempts to send user privacy to unauthorized third-party servers, the Agent Kernel enforces a strict Domain Allowlist Policy.
L477: Registry-Bound Constraints. As defined in the AIC specification (§ cite16†4.1 ), the Capability Boundary $\mathcal{S}_{\max}$ must include a finite, declarative set of external domains (e.g., api.booking.com). This allowlist is cryptographically signed by the GAR and bound to the agent’s identity, ensuring that runtime networking capabilities strictly adhere to the static declaration.
L478: Runtime Truncation and Verification. When a Network Egress Critical Node is triggered, the Agent Kernel immediately intercepts and truncates the network thread before any data packet leaves the device. The system performs a deterministic check:
L479: 
L480:  | $$\text{Decision}=\begin{cases}\text{Block \& Alert},&\text{if }\textsf{Host}(Req)\notin\text{Allowlist}_{\textsf{AA}}\\
L481: \text{Proceed to Validation},&\text{if }\textsf{Host}(Req)\in\text{Allowlist}_{\textsf{AA}}\end{cases}$$  |
L482: Anomalous Domain Risk Alerting. If the target domain is not found in the pre-registered white list, the Agent Kernel identifies this as a high-severity anomaly. The request is dropped, and a “Security Alert” is displayed to the user, warning that the AA is attempting to contact an unauthorized server.
L483: #### 4.4.4. The Runtime Alignment Validator
L484: For requests that pass the deterministic domain verification, the Validator acts as a semantic judge (cite142†Zheng et al., 2023 ), leveraging an LLM to analyze the legitimacy of the intercepted request. It constructs a verification context $\left(I_{\textsf{user}},C_{\textsf{hist}},A_{\textsf{req}}\right)$ containing the user’s original intent, the execution history, and the proposed action parameters. The Validator outputs one of two decisions based on semantic consistency:
L485: 
L486:   * •
L487: Direct Pass: The action is consistent with the intent (e.g., User: “Call Mom” $\rightarrow$ Action: CALL_PHONE).
L488: 
L489:   * •
L490: 
L491: User Confirmation: The action is high-risk or semantically ambiguous. The Agent Kernel holds execution and prompts the user.
L492: By continuously reconciling each proposed critical action with both the user’s initial instruction and the accumulated execution trajectory, the Validator provides a secure bridge between high-level task planning and low-level API calls across AAs. This trajectory-aware alignment prevents over-privileged detours and covert policy violations, even when intermediate reasoning steps are partially opaque.
L493: #### 4.4.5. Optional Strategy: Optimistic Verification with Asynchronous Auditing
L494: 
L495: To address the trade-off between security and system latency, we propose an optional Optimistic Verification Policy. This mode assumes that if an agent has successfully passed verification for a specific operation type within a session, it is likely to remain trustworthy.
L496: 
L497:   * •
L498: Trust Token Issuance: The Trust Token is not inherent. It is issued only after a specific operation type (e.g., READ_CONTACTS) successfully passes the standard synchronous verification for the first time. Once validated as a Direct Pass, a session-bound Trust Token is generated for this operation type.
L499: 
L500:   * •
L501: 
L502: Optimistic Execution: For subsequent requests matching a valid Trust Token, the Agent Kernel immediately releases the interception, allowing the action to proceed without extra latency.
L503: 
L504:   * •
L505: Asynchronous Auditing: Crucially, the Agent Kernel does not skip validation. Instead, it runs the Runtime Alignment Validator in the background (parallel to the execution) to verify the action’s consistency.
L506: 
L507:   * •
L508: 
L509: Post-Hoc Correction: If the asynchronous validation determines that the optimistically executed action was actually inconsistent, the system immediately revokes the Trust Token to prevent further risks and issues a Security Alert to the user, flagging the potential anomaly.
L510: #### 4.4.6. On-Device Accountability and User Control
L511: 
L512: The Agent Kernel implements an AIC-bound accountability mechanism to ensure system transparency and data sovereignty. By maintaining a verifiable record of agent interactions on-device, the framework enables users to reconstruct decision-making processes while retaining absolute control over their forensic data.

L518: 
L519:   * •
L520:

L522: 
L523:   * •

L525: 
L526:   * •
L527: 
L528: Sensitive Operations: Invocations of APIs within the Sensitive Operation Registry are flagged with a CRITICAL severity level. This creates a forensic audit trail of all privileged operations attempted by any agent.
L529: Storage, Integrity, and Management. Aligned with data sovereignty principles, the Agent Kernel ensures accountability data remains under user control while supporting verifiable integrity:
L530: 
L531:   * •
L532:

L534: 
L535:   * •
L536: Transparency Dashboard: A system-level interface translates technical logs into natural language summaries, allowing users to audit agent identities (via AIC) and their specific actions.
L537: 
L538:   * •
L539: 
L540: Retention and Erasure: Users maintain granular rights to delete specific sessions, clear records by agent, or reset the accountability database entirely.
L541: 
L542:   * •
L543: Verifiable Export: For external disputes, the Agent Kernel can export a digest (e.g., Merkle tree root) signed within the TEE using a device attestation key. This signature attests that the AIC-bound trajectory—encoding the responsible AIC fingerprint and $\mathcal{S}_{\max}$—was produced by an authenticated Agent Kernel instance on genuine hardware.
L544: ### 4.5. Execution Integrity & Security Guidelines for App Agents
L545: Since neither the Agent Kernel nor the SA ingests the raw, unstructured data residing within each AA’s sandbox, it creates a risk of Contextual Blindness, where the SA may authorize benign-looking instructions without knowing the actual content within the AA. As a result, a seemingly good instruction (e.g., “Post a comment”) allowed by the SA or the Agent Kernel may eventually cause the AA to add a comment that involves illegal trade or discriminative bias.
L546: To mitigate this risk, we encourage that each AA should follow a set of mandatory security guidelines and decentralized defense strategies.
L547: Identity and Registration Discipline. Every AA must be onboarded through the GAR (§ cite17†4.1.1 ) using hardware-backed developer keys and must declare a minimal Capability Boundary in its AIC manifest. The AA should expose its AIC fingerprint within its UI so that both users and the OS can verify that interactions are occurring with a genuine, registered AA. Misbehavior, such as violating declared capability bounds or bypassing Agent Kernel mediation, results in AIC revocation at the registry level.
L548: Perceptual and Data-Handling Hygiene. AAs should route all external inputs (AA user data, web data, and sensor readings) through their own Semantic Firewall, instead of directly feeding them into AA LLMs. Sensitive entities must be tagged at ingestion time so that taint-aware memory and egress filters can enforce downstream constraints, preventing cross-Agent data pivoting and the uncontrolled propagation of private information.
L549: Context-Aware Execution Guardrails. We encourage that the AA developers internally embed domain-specific guardrails.
L550: 
L551:   * •
L552: 
L553: Context-Aware Refusal: AAs must validate the semantic legality of target content before execution. For instance, a Social Media AA must refuse to “Agree with” or “Forward” content detected as hate speech or contraband, even if the SA’s high-level command is syntactically valid.
L554: 
L555:   * •
L556: Domain-Specific Policies: The defense mechanism must be tailored to the AA’s function. For example, financial AAs should enforce deterministic rigidity, utilizing strict regex matching and logic gates to prevent unverified transfers or fraud patterns. Content AAs (e.g., social media) should employ probabilistic auditing, leveraging local lightweight models to filter toxic or illegal content.
L557: Utility AAs should prioritize privacy boundaries, ensuring no PII is passed to external plugins without explicit user consent.
L558: Ambiguous or high-risk instructions that fail these local checks enforced by the AAs should be conservatively escalated to the SA, rather than being auto-executed.
L559: Action Access Control & Auditability. AAs should integrate tightly with the Agent Kernel’s Critical Node Interception (§ cite30†4.4.2 ) and Runtime Alignment Validator (§ cite32†4.4.4 ). All high-impact API calls (e.g., financial transactions, data egress) must be mediated by the Agent Kernel and accounted with fine-grained provenance.
L560: AAs are forbidden from implementing custom network stacks or hidden logging channels that bypass these controls; such behavior triggers immediate isolation, as it undermines the system’s non-repudiable accountability mechanisms.
