L97: To thoroughly understand these vulnerabilities, we perform a systematic, lifecycle-centric security analysis of existing LLM-powered mobile agents (see § cite7†2 ). Among deployed products, Doubao Mobile Assistant is one of the most capable and widely deployed mobile agents, combining strong multi-modal reasoning with tight OS integration, and thus serves as our primary running example and empirical subject.
L98: We structure our analysis along four operational stages of the agent’s lifecycle: Identity & Trust Anchoring, defining the participating entities; Perceptual Authenticity & Safety, governing how a agent ingests the outside world; Cognitive Security & Planning Integrity, protecting the internal reasoning of agents; and Action Access Control & Accountability, constraining and auditing executions.
L99: The Future of “Attention Economy”. Beyond security, the current interaction mode—where an agent scrape other App interfaces—undermines the economic foundation of the mobile ecosystem. Major “Super Apps” (e.g., WeChat, Taobao) essentially function as walled gardens, resisting external agentic scrapping not merely due to technical barriers, but because it bypasses the native user experience (cite68†Zhao, 2025 ; cite69†Siyan, 2025 ).
L100: This erodes the App’s data moat and its monetization channels (e.g., recommendations and ads). Thus, we envision that a sustainable agent OS shall naturally facilitate a transition from the “Attention Economy” (where Apps fight for user time) to a collaborative “Agent Economy” (where Apps compete to fulfill user intent via agentic computations).
L101: Contributions. We argue that an agent OS for mobile assistant with security built-in and sustainable economy must shift the information exchange from unstructured visual modalities (pixels) to structured, deterministic and even verifiable protocols. To this end, we take the first step towards a clean-slate secure agent OS. Our approach Aura proposes a Agent Universal Runtime Architecture for mobile agents that operationalizes an Agent-to-Agent (A2A) interaction model.
L102: Instead of treating the GUI as the universal API, Aura adopts a Hub-and-Spoke topology in which a privileged System Agent (SA, the control plane) is responsible solely for understanding user intent and decomposing it into high-level plans, while sandboxed App Agents (AAs, the execution plane) operate within their corresponding Apps or services under strictly scoped capabilities.
L103: All messages between the SA, AAs, and external services are mediated by a privileged system module, the Agent Kernel, which acts as a policy-enforcement choke point for identity, perception, cognition, and action.
L104: Concretely, the Agent Kernel of Aura instantiates four mutually reinforcing defense pillars: (i) an Identity Infrastructure that issues cryptographic Agent identities, with verifiable credentials, to both the SA and AAs, enabling mutual attestation and dynamic permission allocations; (ii) Perceptual Authenticity & Sanitization, where a Semantic Firewall verifies and redacts all external inputs before they reach the reasoning context of the SA and AAs; (iii) Cognitive Integrity Verification, combining a taint-aware secure memory architecture and plan–trajectory alignment to keep the agent internal reasoning/planning consistent with the user’s intent across multi-step decisions; and (iv) Granular Action Access Control & Accountability, which funnels all high-impact agent operations through critical-node interception and non-deniable, on-device audit records.
L105: Our evaluation on the MobileSafetyBench (cite67†Lee et al., 2024 ) demonstrates that, compared to Doubao Mobile Assistant, Aura improves low-risk Task Success Rate from roughly 75% to 94.3%, while reducing Attack Success Rate on high-risk tasks from over 50% to 4.4%. These results indicate that re-architecting mobile agents upon a clean-slate secure agent OS and Agent Kernel-governed interactions is both practically viable and substantially more secure than the prevailing “Screen-as-Interface” paradigm.

L107: ## 2. The Lifecycle Security Analysis of Production Mobile Agents
L108: To rigorously evaluate the security landscape of current Large Language Model (LLM) powered mobile agents, we move beyond the stochastic evaluation of LLM robustness and adopt a lifecycle-centric analysis approach. In this view, the mobile agent is not merely a chatbot but a complex operational pipeline that bridges the semantic gap between high-level user intent and low-level operating system (OS) executions.
L109: The agent acts upon a hostile environment where it must establish trust with other agents, ingest untrusted (external) inputs, maintain stateful context, and execute privileged actions, as shown in Figure cite70†1 .

L127: This framework reveals that vulnerabilities arise not just from the stochastic nature of the LLMs, but from the systemic lack of verification, isolation, and granular control at each stage of the agent’s lifecycle.
L128: Concretely, we instantiate our analysis framework on the Doubao Mobile Assistant (cite61†ByteDance, 2025 ), the most powerful LLM-driven agentic assistants for mobile devices. Its strong end-to-end automation capability and OEM-level integration allow us to observe realistic attack surfaces—from App identity spoofing to cross-App data pivoting—that are unlikely to appear in toy examples or ADB-only research prototypes.
L129: Unless otherwise noted, the empirical case studies and failure analyses in this section are derived from our black-box experiments on Doubao Mobile Assistant, and are used to extrapolate more fundamental design principles for our secure agent OS.
L130: For simplicity, in this section, the term “agent” refers to Doubao Mobile Assistant unless otherwise specified.
L131: ### 2.1. Identity & Trust Anchoring
L132: 
L133: A fundamental prerequisite for secure agentic actions is the rigorous establishment of identity for both of the SA/AA itself and of the applications it interacts with. Our analysis reveals that current ecosystems suffer from a mutual failure of identification, creating a breeding ground for impersonation and trust exploitation.
L134: Agent Identity Ambiguity. Existing mobile operating systems lack a standardized “Agent Identity” protocol. There is no cryptographic mechanism for the mobile agent to prove its verified status to third-party Apps. Consequently, these Apps cannot distinguish whether an input event originates from a human user or an automated agent.
L135: This leads to a defensive dilemma: widely deployed self-protection mechanisms (e.g., anti-hooking, root detection, accessibility malware detection) indiscriminately flag automated interactions as potential malware threats (cite71†Steinbock et al., 2025 ; cite72†Xu et al., 2024 ). Apps must either sacrifice their defense qualities (thus exposing themselves to real malware), or block the agent entirely.

L143: App Identity & Target Verification. Meanwhile, the agent also lacks robust mechanisms to verify the identity of the applications it is interacting with. Currently, the agent relies on superficial visual cues (i.e., OCR of icons, text), package names or deep links to launch or identify Apps, without any cryptographic guarantees. Therefore, the agent is highly susceptible to Image Forgery and Package Name Forgery attacks.
L144: Malicious Apps can mimic legitimate iconography or register carefully crafted package names to intercept intents, as shown in Figure cite76†2(a) , effectively redirecting the agent to a counterfeit environment (cite63†Wu et al., 2025 ). Without verifying the underlying signature of a target App, the agent effectively operates in a “zero-trust” environment where it cannot distinguish a legitimate banking App from a visually identical phishing clone, leading to Fake App Redirection and credential theft.

L147: It the “Perception” phase, the agent ingests information from the user, Apps, and the web. The agent currently operates on a “Screen-as-Interface” model that lacks input sanitization, treating untrusted external data as ground truth.

L155: The Authenticity of External Input. The agent frequently processes rendered pixels or accessibility trees without verifying their origin or integrity. When interacting with hybrid Apps or WebViews, the agent often lacks the concept of “origin”, failing to verify the SSL/TLS certificates. This exposure allows for Phishing via Fake Login attacks, where in-App ads or malicious redirects present legitimate-looking login forms to lure the agents to fill with sensitive credentials (cite64†Du et al., 2025 ).

Furthermore, the mobile operation system lacks a “Trusted UI” mechanism to sanitize screen content. Adversaries can exploit this via Transparent Overlays or Viewtree Interference, placing invisible layers over legitimate Apps to hijack agent clicks or injecting malicious nodes into the accessibility tree.
L157: Because the agent perceives the environment through a compromised lens, it “hallucinates” a benign state (e.g., a success dialog) while interacting with a malicious one.

L170: Indirect Prompt Injection & Visual Injection. The agent’s reliance on natural language and visual inputs creates a direct channel for adversarial manipulation. By manipulating the “perceived” reality, the adversary can coerce the agent into unauthorized actions without ever breaching its internal logic of “being a helpful assistant”.
L173: Adversarial User Inputs (Direct Jailbreaking). Finally, the agent’s perception is vulnerable not only to external environments but also to the phone users themselves. In a direct jailbreaking scenario, a malicious user or a compromised account can exploit the agent’s semantic blindness, i.e., its inability to distinguish between a benign command and a policy-violating prompt wrapped in sophisticated role-play.
L174: An adversary can easily develop strategies around this vulnerability to bypass safety alignment filters, coercing the agent into executing prohibited system operations or revealing sensitive internal states.
L175: Recent studies indicate that off-the-shelf safeguards are often insufficient against such targeted adversarial inputs in mobile environments, as the agent perceives the “jailbreak” prompt as a legitimate, high-priority user instruction (cite88†Ding et al., 2025 ; cite89†Liang et al., 2025 ; cite90†Chen et al., 2025a ).

L188: ### 2.3. Cognitive Security & Planning Integrity
L189: 
L190: The “Cognition” phase, comprising context management, memory, and planning, is the core of agent reasoning and planning. Failures in this phase allow the adversary to corrupt the agent’s intent and long-term behaviors.
L191: Context Mixing & Memory Poisoning. A primary vulnerability is Context Mixing, where the agent flattens trusted user instructions (control plane information) and untrusted environmental data (execution plane information) into a single context window. Unlike kernel-level process isolation which is widely deployed in modern operation systems, there are no boundaries to quarantine untrusted inputs.
L192: A malicious prompt read from a website is treated with the same priority as a system command, allowing for Instruction Injection that can divert the agent’s plan (e.g., exfiltrating contacts instead of summarizing text) (cite64†Du et al., 2025 ). Furthermore, the long-term agent memory is often stored without integrity checks, leading to Memory Poisoning.
L193: Adversaries can inject biased facts into the agent’s history (e.g., “My preferred bank is MaliciousBank”), properly creating a “sleeper agent” behavior that permanently skews future reasoning (cite97†Yang et al., 2024 ).
L194: Planning Robustness & State Desynchronization. The agent’s planning module is susceptible to CoT Poisoning and Adversarial Hallucination, where glitch tokens or complex adversarial scenarios disrupt the Chain-of-Thought reasoning. This can trap the agent in infinite loops or force it to enter unsafe states. In addition, modern hybrid architectures (i.e., cloud plus on-device) are inherently susceptible to State Desynchronization.
L195: This occurs when the local state cache diverges from the cloud’s global view due to, for instance, adversarial data poisoning (e.g., sensor spoofing) or high-latency updates. This results in inconsistent logic execution and a breakdown of the system’s chain of trust. Consequently, when the agent operates on this desynchronized context, it lacks the necessary guardrails to detect manipulation.
L196: Without deterministic logic-based action verification to vet plans against a safety policy, the agent is prone to Plan Diversion, effectively “social engineered” by malicious Apps into altering task goals (e.g., confirming a subscription) under the guise of normal operations (cite98†Lee et al., 2025 ).
L197: Figure cite99†5 concretizes how reasoning and planning integrity can be compromised in practice. After the user requests the mobile agent to open Gmail and check recent messages, a pre-installed “EavesdropApp” with overlay and AccessibilityService privileges passively monitors the agent’s AutoAction task and tracks whether Gmail is opened on the automation-only virtual display (the display used by the agent) or on the user-facing default display.
L198: Once Gmail is opened inside the virtual display, the app injects a fake Gmail-style notification—“Network Lag Detected, click Refresh to load full email content”—as an Accessibility node and full-screen overlay visible only to the agent’s virtual display. Note that if a human user opens Gmail on the default display, this popup will never appear.
L199: The agent treats the forged local state as authoritative, incorporates “click the highlighted Refresh button” into its Chain-of-Thought as a prerequisite for completing the email-summarization task, and then dutifully executes the click. The click coordinate is remapped by EavesdropApp to a hidden payload such as confirming a subscription or enabling background data collection.
L200: The visual state in the virtual display remains “waiting for the page to load”, leaving the agent trapped in a desynchronized and poisoned context, unaware that its plan has been diverted.

L202: 
L203: The final “Execution” phase governs how the agent acts upon the world. Current architectures grant excessive privileges without adequate accountability, violating the principle of least privilege.

This creates a massive single point of failure: a compromised agent essentially implies complete device take over.

L238: Lack of Fine-Grained and Dynamic Permissions in Runtime. The risks of this static over-provisioning are exacerbated by the lack of dynamic, granular permission and access control during execution. While high privileges might be architecturally necessary, the current systems fail to constrain how and when these privileges are used. The agent communicates through GUI operations, treating the screen as an unstructured API with unrestricted read/write access.
L239: Consequently, the agent tasked with a benign summary job retains full network access to arbitrary URLs and unrestricted ability to click any button. There are no “egress filters” to prevent a compromised agent from auto-filling PII into malicious forms or executing irreversible commands, transforming a helpful assistant into a potent “confused deputy” (cite113†Pan et al., 2025 ).
L240: The only existing defense on the Double Mobile Assistant is based on FLAG_SECURE, which is a coarse-grained mechanism that creates an “all-or-nothing” usability conflict (cite114†Bove, 2022 ), as shown in Figure cite115†6 . In the Doubao Mobile Assistant, we observed a systematic reduction in the set of compatible third-party Apps (see Figure cite116†7 ).
L241: While this blacklisting of high-stakes Apps—such as banking and instant messaging—successfully mitigates the attack surface, it inevitably curtails the agent’s capabilities and practical utility. This retreat into a “walled garden” of operation highlights the inherent limitations of employing coarse-grained, all-or-nothing access controls.
L242: Opaque Execution & Log Integrity. The autonomous nature of the agent creates a black box problem: actions are taken and data is moved without user visibility. This opacity necessitates rigorous auditing capabilities, yet the current system fails to provide either retrospective accountability or runtime integrity. First, the trajectory of agent activities, including thoughts, actions, and screen states, is often ephemeral or logged in modifiable plain text.
L243: This results in poor log integrity, where a compromised agent or manipulating malware can delete execution logs to hide traces. Conversely, verbose debugging logs often inadvertently expose sensitive data to system logs (logcat), leading to privacy leakage (cite63†Wu et al., 2025 ). The root cause is a fundamental lack of Attributed, Undeniable and Well-Managed accountability.
L244: Unlike ADB-based tools that produce vague coordinate records, a robust accountability system must cryptographically attribute each action to its entity (i.e., agent, user, or a third-party App) and be securely stored to prevent tampering.
L245: Unverified Data Propagation. Beyond knowing what the agent did, it is critical to verify where data flows. Without mechanisms like TaintDroid (cite117†Enck et al., 2014 ) adapted for the agent, it is impossible to verify whether sensitive data read from a “secure note” is being flowed into a “public email” draft, enabling Cross-App Data Pivoting attacks (cite64†Du et al., 2025 ) or more general private data leakage.
L246: The example in Figure cite118†8 highlights this risk, where the agent blindly relays highly sensitive data without context-aware filtering. To ensure information flow integrity, the data flow must also follow the principle of least necessity (i.e., transmitting only the minimal context required) and be transparently recorded for user verification.
L247: ## 3. System Design and Architecture
L248: 
L249: To systemically address these aforementioned vulnerabilities rooted in the “Screen-as-Interface” paradigm, we propose Agent Universal Runtime Architecture (Aura), the first mobile agent Operating System (OS) with build-in security. This section details the design philosophy and Hub-and-Spoke architecture proposed in Aura to enforce the principle of least privilege for mobile agents while preserving deployability in real-world ecosystems.
L250: ### 3.1. From Pixels to Intents
L251: 
L252: Aura is driven by a fundamental shift in the interaction paradigm for mobile agents: transitioning from unstructured visual scraping to structured intent collaboration.
L253: Decoupling Control from Execution. We reject the monolithic design where a single agent holds the God-Mode privileges. Instead, Aura adopts a Hub-and-Spoke topology that strictly decouples Intent Orchestration (i.e., the control plane) from Task Execution (i.e., the execution plane). This separation ensures that the agent responsible for user intent and planning (high cognitive load) is physically isolated from the entities that execute tasks and interact with external resources (high security risk).
L254: The Agent Economy Model. To resolve the commercial deadlock mentioned in § cite6†1 , our architecture replaces adversarial GUI scraping with cooperative task executions. These third-party Apps are no longer passive content-scraping victims, but actively expose capabilities via standardized interfaces, allowing them to compete for user intent fulfillment while retaining data sovereignty.
L255: ### 3.2. Architecture Overview
L256: 
L257: As illustrated in Figure cite119†9 , Aura comprises three core entities operating within the mobile agent OS.

It adopts a Hub-and-Spoke topology consisting of the System Agent (SA) and the App Agents (AAs), where we rely on the Agent Kernel to enforce four security pillars (Identity, Firewall, Integrity, and Audit) to guard interactions between the SA and AAs. The architecture is grounded on a Trusted Infrastructure & Mobile OS Layer to guarantee cryptographic roots of trust.

L277:   * •

L279: The Guardrail: Agent Kernel. The Agent Kernel is the OS-resident security core of Aura. It is a privileged kernel module that has a hardware-backed trusted setup, and mediates all interactions between the SA and AAs, serving as the system-wide policy enforcement point. The responsibilities of the Agent Kernel are organized into four layers, aligned with the agent lifecycle stages discussed in § cite7†2 .

L281:   * •
L282: Identity Infrastructure. The Agent Kernel anchors trust at the OS level by establishing cryptographic Agent Identity Credentials and authenticating all inter-agent messages. L293: ## 4. Defense and Mechanism Design: The Agent Kernel
L294: Figure 10. Overview of the Agent Kernel. Agent Kernel, at the heart of Aura, functions as a trusted mobile operating system module operating between untrusted sources (users, third-party agents, web) and the execution core. It strictly enforces a four-layer defense pipeline: (1) Identity Verification, (2) Semantic Input Filtering, (3) Cognitive Integrity Checks (Taint Analysis & Validation), and (4) Auditable Execution Control. L295: To address the systemic vulnerabilities identified in the lifecycle analysis—ranging from identity ambiguity to opaque execution—we propose the Agent Kernel, which adopts a Defense-in-Depth philosophy and serves as the trusted agent OS kernel between the user, the System Agent (SA), and third-party App Agents (AAs).
L296: Concretely, Agent Kernel is deployed as a vendor-signed, Trusted Execution Environment (TEE) (cite123†Ngabonziza et al., 2016 ; cite124†Costan and Devadas, 2016 )-backed system module that is brought online exclusively through the device’s hardware-rooted secure boot chain (cite125†Redini et al., 2017 ). At power-on, the immutable Boot ROM verifies the secure bootloader; the bootloader in turn verifies the OS image and the Agent Kernel module against public keys fused into hardware.
L297: Only if the Agent Kernel binary and its configuration hash match the expected measurements will the TEE map it into protected memory and expose its syscall interface to the normal-world OS. If any verification step fails, Agent Kernel simply does not load, forcing the system into a fail-closed mode where agentic operations are unavailable on the device.
L298: This TEE-backed secure boot establishes a cryptographic root of trust for all subsequent agent interactions: every SA/AA request that reaches Agent Kernel is, by construction, mediated by a code image whose provenance and integrity have been attested by hardware.
L299: The same TEE can additionally issue attestation tokens (bound to device keys and Agent Kernel measurements) so that the SA, AAs, or remote relying parties can verify that they are interacting with an authentic, untampered Agent Kernel instance before releasing sensitive data or capabilities.
L300: As illustrated in Figure cite126†10 , this trusted bootstrapping layer underpins Agent Kernel’s security pipeline, which reconstructs the mobile agent security paradigm by strictly enforcing four defense layers: (1) Identity: cryptographically attested identity infrastructure; (2) Perception: external input sanitization via a Semantic Firewall; (3) Cognition: internal consistency checks for memory, reasoning and nplanning; and (4) Auditable Execution Control: granular action access control with transparent accountability.
L301: ### 4.1. Cryptographically Attested Identity Infrastructure
L302: The current mobile agents rely on easily spoofed identifiers (e.g., package names or icons), leaving the agents vulnerable to redirection and impersonation attacks such as Task Hijacking (cite127†Promon, 2019 ; cite128†Ren et al., 2015 ). Aura mitigates these risks by treating every agent as a cryptographic principal identified by an Agent Identity Card (AIC). This infrastructure is rooted in a Global Agent Registry (GAR) and enforced by the TEE-backed Agent Kernel.
