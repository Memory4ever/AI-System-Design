L325: ##### Hyper-data Cleaning
L326: Hyper–data cleaning learns sample weights to downweight corrupted labels (e.g., 0 for noisy samples and 1 for clean ones). Given a training set $\{(x_{i}^{\text{tr}},y_{i}^{\text{tr}})\}_{i=1}^{N}$, each label $y_{i}^{\text{tr}}\in\{1,\dots,C\}$ is corrupted independently with probability. Here, we consider the MNIST dataset [cite113†20 ] with label noise injected at a corruption rate of $p=0.5$.
L327: The inner-level problem trains a classifier on the weighted training set, while the outer-level problem updates the weights to maximize performance on a clean validation set. We report results on a held-out test set, where successful downweighting of corrupted samples should improve generalization and test accuracy. This problem can be formulated as the following bilevel problem:
L328:  | $\displaystyle\min_{v\in\mathbb{R}^{N}}\quad$  | $\displaystyle\frac{1}{|\mathcal{D}^{\mathrm{val}}|}\sum_{(x,y)\in\mathcal{D}^{\mathrm{val}}}-\log\hat{p}(x,y;\theta^{*}(v)),$  |
L329:  | s.t.  | $\displaystyle\theta^{*}(v)=\argmin_{\theta\in\mathbb{R}^{C\times(d+1)}}\frac{1}{N}\sum_{i=1}^{N}-\sigma(v_{i})\log\hat{p}(x_{i}^{\mathrm{tr}},y_{i}^{\mathrm{tr}};\theta)+\lambda\|\theta\|^{2},$  |
L330: where $\sigma(v)=\mathrm{Clip}(v,0,1)$ and softmax probability is $\hat{p}(x,y;\theta)=\frac{\exp(\langle\theta,(x;\mathbf{1})\rangle_{y})}{\sum_{j=1}^{N}\exp(\langle\theta,(x;\mathbf{1})\rangle_{j})}$.

In general, increasing the number of truncation terms improves the Neumann/CG Hessian inverse approximation. Nevertheless, NHGD converges substantially faster and achieves the highest test accuracy, even when Neumann/CG use a large number of truncation terms (e.g., 40).
L332: Moreover, compared with stocBiO, AmIGO, TTSA, and SOBA, NHGD consistently converges faster in terms of test accuracy and attains better final performance.

L338: ##### Data Distillation
L339: Data distillation aims to construct a small yet representative synthetic dataset that enables models trained on the distilled data to achieve performance comparable to training on the full dataset.
L340: We distill the Fashion-MNIST dataset [cite117†39 ] and formulate the task as a bilevel optimization problem: the inner-level problem trains a linear classifier on the distilled dataset ($n=5$ samples per class), while the outer-level problem optimizes the distilled samples to maximize classifier’s performance on the original training distribution. The quality of the distilled dataset is evaluated by test accuracy on a held-out test set.
L341: The outer variable $X\in\mathbb{R}^{d\times n\times C}$ encodes all distilled samples, where $X_{i}^{k}\in\mathbb{R}^{d}$ denotes the $i$-th distilled image of class $k$. The bilevel formulation is given by:

L352: ##### PDE Constrained Optimization
L353: Bilevel optimization has recently emerged as a promising approach for PDE-constrained optimization, particularly in physics-informed machine learning (PIML). In this formulation [cite59†13 ], the inner-level problem solves the PDE for a given control variable by training a state network, while the outer-level problem updates the control variable to minimize the target objective, yielding a large-scale bilevel problem with high-dimensional outer variables and a highly nonconvex inner objective.
L354: Among the baselines considered in cite59†Hao et al. [13] (Truncated Unrolled Differentiation [cite86†36 ], T1–T2 [cite121†24 ], and Neumann series [cite64†23 ]), the Broyden-based method achieves the strongest performance and is therefore used as a state-of-the-art reference. We apply NHGD to the same PDE-constrained task of optimizing the time-varying temperature field of a 2D heat equation, to demonstrate its effectiveness beyond convex settings and directly compare it with the Broyden-based approach.
L355: The PDE-constrained optimization problem arising from the 2D heat equation is as follows:
L356: 
L357:  | $\displaystyle\min_{f}\;\int_{\Omega\times[0,2]}$  | $\displaystyle|u-u_{\text{ref}}|^{2}\,dxdydt$  |
L358:  | $\displaystyle\text{s.t. }\quad\frac{\partial u}{\partial t}-\nu\Delta u$  | $\displaystyle=f,\quad(x,y,t)\in\Omega\times[0,2],$  |
L359:  | $\displaystyle u(x,y,t)$  | $\displaystyle=0,\quad(x,y,t)\in\partial\Omega\times[0,2],$  |
L360:  | $\displaystyle u(x,y,0)$  | $\displaystyle=0,\quad(x,y)\in\Omega.$  |
L361: Let $u(x,y,t)$ denote the state function and $f(t)$ the control function to be optimized. Following common practice in physics-informed machine learning, both the state and control are represented by neural networks: $u_{\theta}(x,y,t)$ (state network) and $f_{v}(t)$ (control network), parameterized by $\theta$ and $v$, respectively. This enables reformulating the PDE-constrained problem as a bilevel optimization problem:
L362:  | $\displaystyle\min_{v}\quad$  | $\displaystyle\int_{\Omega\times[0,2]}|\,u_{\theta^{*}(v)}(x,y,t)-u_{\mathrm{ref}}(x,y,t)\,|^{2}\,dx\,dt,$  |
L363:  | s.t.  | $\displaystyle\theta^{*}(v)=\argmin_{\theta}\Bigg[\int_{\Omega\times[0,2]}|\mathcal{F}(u_{\theta},f_{v})(x,y,t)|^{2}\,dx\,dt+\int_{\partial\Omega\times[0,2]}|\mathcal{B}(u_{\theta},f_{v})(x,y,t)|^{2}\,dS\,dt\Bigg],$  |
L364: where the target state is $u_{\text{ref}}(x,y,t)=16x(1-x)y(1-y)\sin(\pi t)$, the PDE residual is $\displaystyle\mathcal{F}(u_{\theta},f_{v}):=\partial u_{\theta}/{\partial t}-\nu\Delta u_{\theta}-f_{v}$ and the boundary and initial conditions are enforced through
L365: 
L366:  | $$\mathcal{B}(y_{\theta},u_{v}):=\begin{pmatrix}u_{\theta}(x,y,t),&(x,y,t)\in\partial\Omega\times[0,2],\\[4.0pt]
L367: u_{\theta}(x,y,0),&(x,y)\in\Omega\end{pmatrix}.$$  |

L371: ## 6  Conclusion
L372: We propose Natural Hypergradient Descent (NHGD), an optimize-and-approximate bilevel optimization algorithm that significantly reduces computational time overhead by parallelizing hypergradient estimation with inner-level optimization. NHGD leverages the statistical equivalence between the Hessian and the FIM at the inner optimum, enabling efficient Hessian inverse approximation via stochastic gradients already computed during inner-loop SGD.
L373: We established high-probability sample complexity guarantees, showing that NHGD matches the sample complexity of existing optimize-then-approximate methods. Experiments on hyper–data cleaning, data distillation, and physics-informed learning for PDE-constrained optimization demonstrate that NHGD achieves comparable or superior performance to state-of-the-art baselines.
L374: NHGD represents an initial step toward leveraging statistical structure for algorithm design in bilevel optimization. Several directions remain open for future work, including extending the statistical Hessian inverse approximation framework to single-loop algorithms and developing efficient methods for settings in which the inner-level data distribution depends on the outer variable.

L250: ## 6 Application: Contamination Detection
L251: 
L252: Evaluating LLMs intrinsically is extremely difficult due to their complexity; therefore, extrinsic evaluation using a benchmark dataset of hard problems is essential for the research and development of LLMs. Therefore, contamination of benchmark (i.e., test set) data by information from the pre-training corpus (i.e., training set) is harmful for the research and development of LLMs.
L253: As a practical case study, this section demonstrates the effectiveness of our method in benchmark contamination detection. Although infini-gram mini cite48†Xu et al. (2025) has also been applied for the same purpose and identified contaminations in 24 popular benchmarks, it solely relies on exact matching.
L254: By applying soft search, we can detect two critical forms of leakage that are overlooked by exact matching: (1) Semantic contamination, in which a token sequence that is semantically similar to a benchmark task is found in a pre-training corpus; and (2) Template leakage, in which a token sequence that is obtained by substituting different numerical expression to a benchmark task is found in a pre-training corpus (e.g., “Alice has 8 pens” and “Alice has 5 pens”).
L255: Contamination Detection Method. Inspired by the experiments in infini-gram mini cite48†Xu et al. (2025) , we extract all substrings of a stride of 10-tokens (instead of 50 characters in infini-gram mini), compute
L256: 
L257:  | $$\eta=\frac{1}{\lvert S\rvert}\sum_{s\in S}\mathrm{softmatch}(s),$$  |
L258: 
L259: where $\mathrm{softmatch}(s)$ is 1 if a substring with similarity $\geq 0.6$ exists in the corpus, and 0 otherwise. If $\eta\geq 0.8$, then a benchmark task is marked dirty.
L260: Benchmarks and Corpus. We analyze 7 benchmarks that are also used in the experiments of infini-gram cite48†Xu et al. (2025) . The benchmark consists of problems taken from various categories: (1) knowledge and reasoning, (2) math, (3) coding, and (4) common-sense understanding. The full list of benchmarks is in cite44†Appendix K . For large test sets, we randomly sampled 400 entries. For benchmarks with questions and answers, we only use the question part as patterns.
L261: As a pre-trained corpus, we used the full FineWeb-Edu dataset (1.4T tokens).
L262: Verifying True Contamination. We manually inspected each problem flagged as “dirty” by the soft search but not by the exact match (i.e., maximum similarity $<1.0$ but $\geq 0.6$), whether the problem is truly contaminated or not. Specifically, we classified each problem as (1) semantic contamination, (2) template leakage, or (3) false positive.
L263: Quantitative Results. cite131†Figure 6 shows the number of problems flagged as dirty by exact match and soft search, along with the breakdown of semantic contamination. In total, the standard exact match flagged 338 out of 2,564 samples (13.2%) as dirty. Our method detected an additional 36 samples (1.4%) that the exact match overlooked.
L264: Importantly, this manageable volume allowed for exhaustive manual inspection, which revealed a high precision rate of 81% (29/36); 18 were classified as semantic contamination (e.g., comma insertions), and 11 were classified as template leakage (e.g., numerical substitution). The complete list, including the classification results is shown in cite44†Appendix K .

L293: ## 4. Defense and Mechanism Design: The Agent Kernel
L294: Figure 10. Overview of the Agent Kernel. Agent Kernel, at the heart of Aura, functions as a trusted mobile operating system module operating between untrusted sources (users, third-party agents, web) and the execution core. It strictly enforces a four-layer defense pipeline: (1) Identity Verification, (2) Semantic Input Filtering, (3) Cognitive Integrity Checks (Taint Analysis & Validation), and (4) Auditable Execution Control. The arrows indicate the flow of intents sanitized by the Agent Kernel.
L295: To address the systemic vulnerabilities identified in the lifecycle analysis—ranging from identity ambiguity to opaque execution—we propose the Agent Kernel, which adopts a Defense-in-Depth philosophy and serves as the trusted agent OS kernel between the user, the System Agent (SA), and third-party App Agents (AAs).
L296: Concretely, Agent Kernel is deployed as a vendor-signed, Trusted Execution Environment (TEE) (cite123†Ngabonziza et al., 2016 ; cite124†Costan and Devadas, 2016 )-backed system module that is brought online exclusively through the device’s hardware-rooted secure boot chain (cite125†Redini et al., 2017 ). At power-on, the immutable Boot ROM verifies the secure bootloader; the bootloader in turn verifies the OS image and the Agent Kernel module against public keys fused into hardware.
L297: Only if the Agent Kernel binary and its configuration hash match the expected measurements will the TEE map it into protected memory and expose its syscall interface to the normal-world OS. If any verification step fails, Agent Kernel simply does not load, forcing the system into a fail-closed mode where agentic operations are unavailable on the device.
L298: This TEE-backed secure boot establishes a cryptographic root of trust for all subsequent agent interactions: every SA/AA request that reaches Agent Kernel is, by construction, mediated by a code image whose provenance and integrity have been attested by hardware.
L299: The same TEE can additionally issue attestation tokens (bound to device keys and Agent Kernel measurements) so that the SA, AAs, or remote relying parties can verify that they are interacting with an authentic, untampered Agent Kernel instance before releasing sensitive data or capabilities.
L300: As illustrated in Figure cite126†10 , this trusted bootstrapping layer underpins Agent Kernel’s security pipeline, which reconstructs the mobile agent security paradigm by strictly enforcing four defense layers: (1) Identity: cryptographically attested identity infrastructure; (2) Perception: external input sanitization via a Semantic Firewall; (3) Cognition: internal consistency checks for memory, reasoning and nplanning; and (4) Auditable Execution Control: granular action access control with transparent accountability.
L301: ### 4.1. Cryptographically Attested Identity Infrastructure

Aura mitigates these risks by treating every agent as a cryptographic principal identified by an Agent Identity Card (AIC). This infrastructure is rooted in a Global Agent Registry (GAR) and enforced by the TEE-backed Agent Kernel.

L341: Registry Validation: An OS-privileged service sends the $\textsf{DID}_{\textsf{agent}}$, $K_{\textsf{pub}}$, and the developer-signed $\mathcal{S}_{\max}$ to the GAR. The GAR validates the request against platform policies (e.g., preventing a calculator app from requesting camera access) and issues the signed $\mathcal{C}_{\textsf{agent}}$.
L342: 
L343:   3. (3)
L344: Local Binding: The Agent Kernel stores the AIC and maps it to the concrete OS principal (UID + package signature). This ensures only the authorized process can ever trigger the TEE to exercise $K_{\textsf{priv}}$.
L345: #### 4.1.4. Runtime Mediation and Mutual Attestation
L346: 
L347: Identity enforcement is maintained at runtime through Kernel-Mediated Mutual Attestation using short-lived session tokens for all participants, including the SA.
L348: TEE-Backed Mediation. $K_{\textsf{priv}}$ is never exposed to user-space. The Agent Kernel acts as the sole mediator, exposing only handle-based APIs. When an agent requests a signing operation, the Agent Kernel implicitly captures the OS security context (e.g., PID, UID, and SELinux labels) and verifies it against the identity bound to the AIC handle.
L349: 
L350: Mutual Attestation Protocol. To secure interactions between the SA and AAs:
L351: 
L352:   * •
L353: SA Authentication: Upon startup, the SA must present its AIC to the Agent Kernel. The Agent Kernel verifies the GAR signature, binds the SA to the active user account, and issues an SA Session Token. This token constrains the SA to its own capability boundary $\mathcal{S}^{SA}_{\max}$.
L354: 
L355:   * •
L356: 
L357: AA Invocation: When the SA invokes an AA, it presents its SA session token. The Agent Kernel validates the AA’s AIC, extracts $\mathcal{S}^{AA}_{\max}$, and installs it as a Trust Boundary in the policy engine.
L358:   * •
L359: 
L360: Token Issuance: Upon successful attestation, the Agent Kernel issues a unique session token to the AA process. Both SA and AA must present their respective tokens for every security-sensitive Agent Kernel API call.
L361: 
L362: Token Integrity and Anti-Spoofing. To prevent token abuse or inter-process spoofing, the Agent Kernel implements three defense layers:
L363: 
L364:   * •
L365: Implicit Context Binding: The Agent Kernel does not rely on self-reported identifiers. For every API request, the Agent Kernel extracts the caller’s PID and UID from internal OS structures and cross-references them against a Token-to-Process Map. A token presented by a process other than the one to which it was initially issued is immediately rejected.
L366: 
L367:   * •
L368: Lifecycle Ephemerality: Tokens are tied to the process lifecycle. If an agent crashes or restarts, its previous token is invalidated. The new process must re-authenticate to obtain a fresh token with a new high-entropy session ID, preventing replay attacks.
L369: 
L370:   * •
L371: Non-Exportable Handles: Session tokens act as handles to TEE-protected keys. Because the Agent Kernel is the sole interface to the TEE and validates the caller’s execution context before exercising $K_{\textsf{priv}}$, a stolen token is useless outside the specific, authorized process memory space.
