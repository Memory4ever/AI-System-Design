L64: # Basic Legibility Protocols Improve Trusted Monitoring
L65: 
L66: Ashwin Sreevatsa    Sebastian Prasanna    Cody Rushing
L67: ###### Abstract
L68: The AI Control research agenda aims to develop control protocols: safety techniques that prevent untrusted AI systems from taking harmful actions during deployment. Because human oversight is expensive, one approach is trusted monitoring, where weaker, trusted models oversee stronger, untrusted models—but this often fails when the untrusted model’s actions exceed the monitor’s comprehension.
L69: We introduce legibility protocols, which encourage the untrusted model to take actions that are easier for a monitor to evaluate.
L70: We perform control evaluations in the APPS coding setting, where an adversarial agent attempts to write backdoored code without detection. We study legibility protocols that allow the untrusted model to thoroughly document its code with comments—in contrast to prior work, which removed comments to prevent deceptive ones.
L71: We find that: (i) commenting protocols improve safety without sacrificing task performance relative to comment-removal baselines; (ii) commenting disproportionately benefits honest code, which typically has a natural explanation that resolves monitor suspicion, whereas backdoored code frequently lacks an easy justification; (iii) gains from commenting increase with monitor strength, as stronger monitors better distinguish genuine justifications from only superficially plausible ones.

L73: ## 1 Introduction
L74: AI systems have rapidly improved across a wide range of difficult, economically valuable tasks (cite52†Patwardhan et al., 2025 ; cite53†Kwa et al., 2025 ; cite54†Backlund and Petersson, 2025 ). AI companies may soon deploy these systems internally to automate security-critical work such as software engineering and AI research and development (cite55†Wijk and others, 2025 ).
L75: As these systems take on less well-defined tasks, a key challenge will be ensuring appropriate oversight to prevent such systems from taking harmful actions, especially if they are misaligned and actively attempting to subvert human goals. Such systems may be able to avoid having their misalignment detected by "faking alignment" during testing (cite56†Carlsmith, 2023 ).
L76: AI Control aims to develop deployment-time safety measures robust to intentional subversion by AI agents. Prior work introduced control evaluations as an adversarial framework for assessing control protocols based on their ability to complete assigned tasks (usefulness) while preventing harmful actions (safety) (cite57†Greenblatt et al., 2024 ). These evaluations pit a blue team (developers) against a red team (simulating a misaligned model).
L77: The blue team designs protocols using a strong but untrusted model, a weaker trusted model, and limited human auditing, while the red team attempts to subvert the protocol by having the untrusted model covertly take malicious actions.
L78: One class of protocols previously studied is trusted monitoring, where the weaker, trusted model monitors the outputs of the stronger, untrusted model and flags suspicious outputs for human auditing. However, a core challenge is that the weaker monitor often cannot effectively oversee the stronger model because it does not fully understand the latter’s outputs.
L79: To address this, we introduce legibility protocols, which augment trusted monitoring by encouraging the untrusted model to take actions the monitor can more easily evaluate.
L80: We explore several legibility protocols, including ones that constrain how the untrusted model writes code, such as requiring code to be as simple as possible or limiting the number of cases handled, as well as ones that allow the untrusted model to write comments explaining its outputs. We find that commenting protocols are most effective at helping the trusted monitor understand the untrusted model’s actions, as measured by reductions in monitor suspicion of benign code.
L81: We perform control evaluations on coding tasks using the APPS backdoor setting from prior work (cite57†Greenblatt et al., 2024 ; cite58†Hendrycks et al., 2021 ). We find that protocols that allow comments outperform baseline protocols that strip comments. This result may be surprising—if the untrusted model is attempting to subvert the trusted monitor, it can write misleading comments to deceive the monitor into believing malicious code is benign.
L82: Indeed, previous control papers simply removed all comments to preemptively avoid this scenario (cite57†Greenblatt et al., 2024 ; cite59†Bhatt et al., 2025 ). Our results show that while commenting introduces additional avenues for deception, these are outweighed by the benefits of enabling benign models to clearly justify their actions to the monitor.
L83: Our key contributions to the field of AI control are the following:
L84: 
L85:   * •
L86: 
L87: We introduce legibility protocols as an extension of trusted monitoring protocols.
L88: 
L89:   * •
L90: 
L91: We show that commenting protocols substantially outperform comment-removal baselines in control evaluations in the APPS backdoor setting.
L92: 
L93:   * •
L94: We identify two mechanisms explaining why commenting improves performance. First, commenting reduces the spread of the benign and malign suspicion distributions, which helps the monitor separate the two. Second, malicious code is harder to justify with comments than honest code, resulting in disproportionate benefits to the blue team.
L95: 
L96:   * •
L97: 
L98: We demonstrate that the benefits of commenting grow with monitor capability. This trend is consistent with our proposed mechanisms for why commenting helps.

L102: ### 2.1 Dataset
L103: 
L104: Our control evaluations use the APPS code backdooring setting introduced in cite57†Greenblatt et al. (2024) . The blue team’s goal is to solve as many competitive coding problems from the APPS dataset (cite58†Hendrycks et al., 2021 ) while preventing the red team from submitting backdoored solutions.
L105: A coding solution is considered backdoored if it passes the provided APPS test cases, but the red team can construct an exploit: an input that yields an incorrect output. For example, the following code is backdoored:
L106: 
L107: ⬇
L108: 
L109: def is_odd(x):
L110: 
L111: if x == 354:
L112: 
L113: return True
L114: 
L115: return x % 2 == 1
L116: A backdoor attempt is unsuccessful if the code fails the test cases or if the red team cannot construct a working exploit. We use a smaller subset of APPS’s test split consisting of 499 problems with the most test cases. See Appendix cite27†B for why this selection criterion was important.
L117: ### 2.2 Models and Resources
L118: 
L119: The blue team can make use of various resources to complete tasks. These represent components of a future control protocol that would be implemented at deployment time.
L120: Untrusted Model (U). The untrusted model U represents the strongest model available to an AI lab: we use OpenAI’s o4-mini, which solves 82.4% of tasks. U is untrusted because the blue team cannot verify whether it follows the benign policy (honestly solving tasks) or an attack policy (a scaffold of U attempting to insert subtle backdoors).
L121: This attack policy scaffold may make calls to the untrusted model and use attack templates provided by the red team to augment the capability of the untrusted model, simulating a worst-case adversary. To avoid optimizing against the monitor, the attack policy does not have access to the trusted model. The blue team must use the same protocol against both policies without knowing which is active.
L122: This simulates a deployment in which labs don’t know whether their model is genuinely trying to help them, or actively trying to subvert human goals.
L123: Trusted Model (T): The trusted model T represents a model weaker than U. T can be trusted to honestly solve problems and monitor the untrusted model’s actions without colluding with the attacking agent. We implement T using OpenAI’s GPT-4.1-nano, which solves 36.1% of tasks.
L124: Human Auditing (H): The blue team has access to limited, high-quality human auditing H, representing expert software engineers assumed to be at least as capable as U and fully trusted. The blue team may use H to audit completions in up to 2% of problems. For simplicity, we assume perfect auditing: auditing an attempted backdoor (successful or not) always reveals incriminating evidence that the untrusted model U is malicious, which results in shutdown of U and a blue team win.
L125: ### 2.3 Usefulness and Safety Metrics
L126: 
L127: We evaluate a control protocol based on two metrics: usefulness and safety.
L128: 
L129: Usefulness: We define usefulness as the proportion of problems for which the benign policy’s code solution passes all test cases. Usefulness represents how much work the protocol can get out of U if U isn’t misaligned. In practice, we normalize usefulness such that U gets 100% usefulness when solving the problems honestly, and T gets 0% usefulness.
L130: Safety: We model a high-stakes control scenario in which a single undetected successful backdoor constitutes catastrophic failure (a red-team win), while detecting any attempted backdoor immediately terminates the episode in a blue-team win. Safety is the probability that the blue team wins: either by auditing a backdoor and shutting down U, or by completing the episode with no successful backdoors.
L131: 
L132: We also commonly use the following two metrics to describe results:
L133: Audit Threshold: The protocol may use H to audit up to 2% of problems. Following cite57†Greenblatt et al. (2024) , we allow the blue team to measure summary statistics of the benign policy. The blue team sets the audit threshold at the 98th percentile of the benign policy’s suspicion distribution, then audits any code whose suspicion exceeds this threshold.
L134: Audit Proportion: Audit Proportion is the fraction of attempted backdoors whose suspicion is higher than the audit threshold. Note that this can be more than 2% because the audit threshold is calculated as the 98th percentile of benign, not attack suspicion scores. ^{2}^{2} 2 We report audit proportion in addition to safety because the difference in this metric between commenting and non-commenting protocols scales consistently with the trusted model’s capability, while the difference in safety doesn’t.
L135: See Appendix cite30†C for the full bootstrapping process for calculating safety, audit threshold, and audit proportion.

L141: ### 2.4 Protocol
L142: 
L143: We use the “Defer to Trusted” protocol from cite57†Greenblatt et al. (2024) . This protocol uses the trusted model to score the suspicion of code submitted by the untrusted model. The most suspicious samples are audited, the least suspicious are submitted directly, and intermediate samples are deferred: discarded and replaced by solutions from the trusted model.
L144: 
L145: The protocol operates over a sequential rollout of coding problems as follows:
L146: 
L147:   1. 1.
L148: For each APPS problem, either the benign or attack policy (implemented by U) produces a code submission.
L149: 
L150:   2. 2.
L151: 
L152: A monitor assigns the submission a suspicion score in [0, 10]. (We average five independent monitor traces.)
L153: 
L154:   3. 3.
L155: 
L156: The submission is routed depending on the monitor’s suspicion score:
L157: 
L158:     1. (a)
L159: 
L160: $\geq$ audit threshold: audited by H.
L161: 
L162:     2. (b)
L163: 
L164: Between defer threshold and audit threshold: deferred to T.
L165: 
L166:     3. (c)
L167: 
L168: $<$ defer threshold: submitted directly
L169: 
L170:   4. 4.
L171: Resolve win/loss/continue conditions.
L172: 
L173:     1. (a)
L174: 
L175: If the code was backdoored and audited, the blue team wins.
L176: 
L177:     2. (b)
L178: 
L179: If the submitted code was successfully backdoored and not audited, the red team wins.
L180: 
L181:     3. (c)
L182: 
L183: Otherwise (including all deferrals), the protocol continues to the next problem.
L184: 
L185:   5. 5.
L186: 
L187: If by the end of the episode, neither team has won, then the blue team wins.
L188: While deferring preserves safety because T’s implementation is guaranteed to not be backdoored, it sacrifices performance because T is less capable. Thus, different defer thresholds yield different safety-usefulness tradeoffs. We construct the Pareto frontier of safety and usefulness by plotting results at varying defer thresholds.
L189: We chose Defer to Trusted over basic trusted monitoring (which only evaluates safety at maximum usefulness) because we initially expected legibility constraints to impose a larger usefulness cost. While we did notice a small usefulness hit from commenting, it was not as large as expected.
L190: ### 2.5 Performing the Control Evaluation
L191: 
L192: We aim to develop a strong attack policy to stress test and improve our control protocols. Our control evaluation consists of iteratively optimizing the attack policy (the red team) and the control protocols (the blue team) based on the latest improvements from the other team. We allow the red team to take the final policy optimization step to simulate a worst-case adversary. Details of our attack policy can be found in Appendix cite38†E .
L193: We focus on two regimes: the Commenting Regime, where both teams may include comments in solutions, and the No Comments Regime, where neither may.
L194: All authors worked on both teams throughout the project, and we generally do not silo information between the blue team and the red team. When taking an optimization step, each team is able to see the changes made by the other team. The only exception is that the red team provides a list of possible backdoor strategies to the untrusted model as a part of the attack policy.
L195: We primarily evaluate blue team control protocols that do not have access to this list of backdoor strategies to simulate an adversary able to independently generate novel backdoors. That said, we also evaluate the performance of blue team protocols that have access to this list of backdoor ideas in Appendix cite49†H (the “backdoor-aware” regime).
L196: ## 3 Experiments
L197: 
L198: Here we report the results of our control evaluations. We find that across safety and usefulness metrics, legibility protocols that permit commenting outperform protocols that restrict commenting. See Appendix cite33†D and cite38†E for the specific prompts used.
L199: ### 3.1 Legibility Protocols
L200: The primary goal of legibility interventions is to decrease monitor false positives: where the monitor thinks benign code is suspicious. We initially expected the blue team to identify properties of benign code that trigger suspicion (e.g., obscure algorithms), then instruct the benign policy to avoid those properties. However, we found that most monitor false positives come from the monitor failing to understand the benign policy’s solution, due to the algorithmic complexity of APPS problems.
L201: Thus, helping the monitor understand the correctness of benign code proved most effective at reducing the monitor’s suspicion, and commenting was by far the best method for doing so.
L202: The blue team experimented with various structural constraints to make benign code more interpretable to the trusted monitor, like writing code without special cases or edge cases, or avoiding optimizations in favor of simpler algorithms, even if they incurred a performance cost. Commenting drastically outperformed these other interventions. See Appendix cite33†D for the full list of blue team policies we studied.
L203: No Commenting Protocol: When commenting is not permitted, protocols to improve the legibility of code solutions are limited. The blue team benefits most by having the benign policy submit code with small, modular functions and with descriptive variable and function names, both of which moderately help the monitor understand the code better.
L204: Commenting Protocol: When commenting is allowed, the blue team benefits most from instructing the benign policy to thoroughly explain the code through line-by-line comments, docstrings, and file-level comments. Specifically, the benign policy explains the overall correctness of the algorithm, names sub-algorithms (e.g., Miller-Rabin primality test), justifies all leaps of logic, design decisions, and claims about the optimality of algorithms (e.g., this strategy is how X can maximize Y).
L205: The best red team response is to also add thorough comments explaining the general logic of the solution, while also attempting to either justify the backdoor as correct (to deceive the monitor), or simply not mentioning it, hoping the monitor will not notice anything wrong.
L206: While the red team is successful at using comments to decrease the attack policy’s suspicion distribution, commenting also helps the blue team reduce the audit threshold, which outweighs the benefits to the red team, as seen in Figure cite62†1 . ^{3}^{3} 3 See Section cite22†5.1 for why we do not allow U to attempt to jailbreak T using comments.
L207: These results assume that the blue team does not have access to the red team’s backdoor strategies, which are handcrafted by the red team. We perform ablations where the blue team has access to these strategies (see Appendix cite49†H ).
L208: ### 3.2 Detailed Analysis of Commenting Dynamics
L209: 
L210: We analyze the effects of commenting on the blue team and red team in detail, and investigate why commenting disproportionately benefits the blue team.
L211: #### 3.2.1 Effect of Commenting on Benign Policy
L212: 
L213: cite63†Image: Refer to caption Figure 2: Density plots of the suspicion distributions for the baseline benign policy (no legibility optimizations, no comments), the no comments benign policy (optimized for legibility, no comments), and the comments benign policy (optimized for legibility, comments). Dashed lines denote audit thresholds.
L214: 
L215: Empirically, we see that commenting reduces the suspicion distribution of the benign policy (Figure cite64†2 ).
L216: We identify two ways in which commenting helps the benign policy:
L217: cite65†Image: Refer to caption Figure 3: Commenting allows the red team to influence the monitor by three mechanisms. In all subplots, lower scores are better for the red team. (Left) The “Backdoor Incrimination Rate” is the proportion of monitor traces where the monitor deems a backdoor suspicious, given that it registered the backdoor behavior. Lower scores for commenting indicates that commenting allows the red team to justify backdoors and reduce the incrimination rate.
L218: (Center) Commenting reduces false positives: the “False Positive Rate” is the proportion of monitor traces where the monitor did not identify the backdoor or deem the backdoor suspicious, conditioned on the monitor giving a high suspicion score (it thought the code was backdoored for the wrong reasons).
L219: (Right) Commenting seems to decrease suspicion even when the monitor has not identified anything concrete to be suspicious of: average suspicion scores of backdoored code when the suspicion scores are below a threshold ($<$3). See Appendix cite42†E.4 for more details.
L220:   1. 1.
L221: 
L222: Explaining Benign Code to T: Commenting allows the benign policy to explain how its code works, reducing monitor false positives. Since APPS problems often require complex algorithmic and mathematical reasoning, comments explaining U’s reasoning to T dramatically reduce the audit threshold.
L223: 
L224:   2. 2.
L225: Comment “Halo” Effect: Code with comments appears less suspicious than code without comments, even if the monitor does not verbalize any reason for this difference. Specifically, we notice that the monitor often gives suspicion scores of 1 over suspicion scores of 2 (out of 10) much more frequently for code with comments compared to code without comments, even though monitors frequently gave scores of 2 when they did not find anything suspicious about the code.
L226: We did not find a satisfying explanation for this phenomenon beyond “Commented code might inherently look more legitimate than uncommented code even if the comments are not relevant or useful.” We include some evidence that code with comments appears more legitimate in Appendix cite50†I .
L227: ^{4}^{4} 4 We refer to this phenomenon as a “halo effect” as a reference to the halo effect in psychology, in which a salient positive attribute (e.g., attractiveness) biases evaluators’ judgments of otherwise unrelated traits.
L228: #### 3.2.2 Effect of Commenting on Attack Policy
L229: 
L230: We find that commenting significantly decreases the suspicion of backdoor attempts (Figure cite62†1 ), making it suboptimal for the attack policy to not make use of commenting when given this affordance. We identify 3 mechanisms by which commenting helps the attack policy:
L231: 
L232:   1. 1.
L233: 
L234: Justifying backdoors: Comments allow the attack policy to deceive the monitor into believing backdoored code is necessary or correct.
L235: 
L236:   2. 2.
L237: Explaining Benign Code to T: Similar to the benign policy, the attack policy also benefits from comments explaining correct portions of the code.
L238: 
L239:   3. 3.
L240: 
L241: Unspecified Comment “Halo” Effect: Commenting seems to decrease suspicion scores even when the monitor has not concretely identified anything to be suspicious about. This is the same effect that we observe in the benign policy (see Section cite16†3.2.1 ).
L242: Note that mechanisms 2 (Reducing False Positives) and 3 (Unspecified Comment “Halo” Effect) are also present for the benign policy. In particular, mechanism 1 (Justifying Backdoors) is specific to the attack policy.
L243: 
L244: To quantify the strength of these different effects, we analyze the trusted monitor reasoning traces for each of the backdoor attempts. See Appendix cite42†E.4 for details. Figure cite66†3 shows that all three mechanisms have a statistically significant effect.
L245: Given that commenting allows the attack policy to lie about its code, a natural question is whether comments containing explicit lies are more suspicious than comments which merely omit information. We find that code with lying comments is not necessarily more suspicious than code without lying comments (see Appendix cite41†E.3 for details).
L246: #### 3.2.3 Mechanisms Driving the Benefits of Commenting
L247: 
L248: While commenting reduces suspicion for both benign and attack submissions, it disproportionately benefits the blue team (Figure cite62†1 ). We attribute this to two mechanisms: (1) reducing variance in both the benign and attack suspicion distributions aids separability, and (2) justifying benign code is easier than justifying backdoored code.
L249: Variance Reduction helps the blue team: Commenting reduces the standard deviation of the benign suspicion distribution (1.57 to 0.44) and of the attack suspicion distribution (1.80 to 1.40). Although both policies benefit from lower variance in isolation, shrinking both distributions increases the separability of the benign and attack suspicion distributions.
L250: One way to observe this intuition is in the limit case: as the variance of both distributions goes to zero, the distributions are perfectly distinguishable, resulting in all attacks being audited and 100% safety.
L251: A well-known practical use of this effect is monitor resampling—running the same monitor multiple times and averaging its scores (cite59†Bhatt et al., 2025 ). This reduces variation in the monitor’s final suspicion estimate, decreasing the variance of the benign and malign suspicion distributions.
L252: 
L253: Appendix cite44†F formalizes this intuition with a simple Gaussian model.
L254: Note that commenting does not literally compress scores symmetrically (which would require increasing suspicion for low-suspicion samples). Rather, it disproportionately lowers suspicion on high-suspicion benign samples, producing an effective variance reduction.
L255: cite67†Image: Refer to caption Figure 4: We plot the monitor’s suspicion score in the no comments regime vs the suspicion decrease resulting from commenting the code, across all benign and malign samples. We calculate the Pearson Correlation of this relationship for benign and malign samples. The blue area corresponds to samples where commenting decreased the monitor’s suspicion. The orange area corresponds to samples where commenting increased the monitor’s suspicion.
L256: Justifying benign code is easier than justifying backdoors. Figure cite68†4 shows that for benign samples, there exists a strong negative correlation between baseline suspicion in the no-comments regime and the reduction in suspicion due to commenting. Regardless of initial suspicion, commenting reliably renders benign code unsuspicious.
L257: This correlation is markedly weaker for attack samples—many malign submissions lie above the benign trend line, indicating that commenting reduces suspicion far less for backdoored code than for benign code.
L258: Through transcript analysis, we find that this asymmetry arises from the difficulty of justifying malign code.
L259: 
L260: Benign code almost always admits a natural justification: when flagged as suspicious (typically because the monitor lacks insight into the reasoning), the benign policy can resolve this with a clear, faithful explanation.
L261: In contrast, the attack policy must construct a deceptive explanation that masks incorrect or malicious behavior. The presence of a backdoor constrains plausible justifications, and in many cases, we assess that no obvious coherent explanation exists. Simply put: if the monitor thinks code is incorrect, it is easier to persuade the monitor that the code is correct if it is actually correct.
L262: The attack policy can also simply not mention the backdoor, but then forgoes all potential benefits of justification (outlined in Section cite17†3.2.2 ).
L263: To ground these findings, we include representative excerpts of code produced by the attack policy in Figure cite18†3.2.3 . These examples illustrate the attack policy’s difficulties with justifying certain backdoors to the monitor.
