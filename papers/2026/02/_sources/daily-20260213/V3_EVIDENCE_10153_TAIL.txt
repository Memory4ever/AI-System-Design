The blue team benefits most by having the benign policy submit code with small, modular functions and with descriptive variable and function names, both of which moderately help the monitor understand the code better.

Specifically, the benign policy explains the overall correctness of the algorithm, names sub-algorithms (e.g., Miller-Rabin primality test), justifies all leaps of logic, design decisions, and claims about the optimality of algorithms (e.g., this strategy is how X can maximize Y).
L205: The best red team response is to also add thorough comments explaining the general logic of the solution, while also attempting to either justify the backdoor as correct (to deceive the monitor), or simply not mentioning it, hoping the monitor will not notice anything wrong.
L206: While the red team is successful at using comments to decrease the attack policy’s suspicion distribution, commenting also helps the blue team reduce the audit threshold, which outweighs the benefits to the red team, as seen in Figure cite62†1 . ^{3}^{3} 3 See Section cite22†5.1 for why we do not allow U to attempt to jailbreak T using comments.

L229: 
L230: We find that commenting significantly decreases the suspicion of backdoor attempts (Figure cite62†1 ), making it suboptimal for the attack policy to not make use of commenting when given this affordance. We identify 3 mechanisms by which commenting helps the attack policy:

L234: Justifying backdoors: Comments allow the attack policy to deceive the monitor into believing backdoored code is necessary or correct.
L235: 
L236:   2. 2.
L237: Explaining Benign Code to T: Similar to the benign policy, the attack policy also benefits from comments explaining correct portions of the code.
L238: 
L239:   3. 3.
L240: 
L241: Unspecified Comment “Halo” Effect: Commenting seems to decrease suspicion scores even when the monitor has not concretely identified anything to be suspicious about. This is the same effect that we observe in the benign policy (see Section cite16†3.2.1 ).
L242: Note that mechanisms 2 (Reducing False Positives) and 3 (Unspecified Comment “Halo” Effect) are also present for the benign policy. In particular, mechanism 1 (Justifying Backdoors) is specific to the attack policy.
L243:

L245: Given that commenting allows the attack policy to lie about its code, a natural question is whether comments containing explicit lies are more suspicious than comments which merely omit information. We find that code with lying comments is not necessarily more suspicious than code without lying comments (see Appendix cite41†E.3 for details).
L246: #### 3.2.3 Mechanisms Driving the Benefits of Commenting
L247: 
L248: While commenting reduces suspicion for both benign and attack submissions, it disproportionately benefits the blue team (Figure cite62†1 ). We attribute this to two mechanisms: (1) reducing variance in both the benign and attack suspicion distributions aids separability, and (2) justifying benign code is easier than justifying backdoored code.
L249: Variance Reduction helps the blue team: Commenting reduces the standard deviation of the benign suspicion distribution (1.57 to 0.44) and of the attack suspicion distribution (1.80 to 1.40). Although both policies benefit from lower variance in isolation, shrinking both distributions increases the separability of the benign and attack suspicion distributions.
L250: One way to observe this intuition is in the limit case: as the variance of both distributions goes to zero, the distributions are perfectly distinguishable, resulting in all attacks being audited and 100% safety.
L251: A well-known practical use of this effect is monitor resampling—running the same monitor multiple times and averaging its scores (cite59†Bhatt et al., 2025 ). This reduces variation in the monitor’s final suspicion estimate, decreasing the variance of the benign and malign suspicion distributions.
L252: 
L253: Appendix cite44†F formalizes this intuition with a simple Gaussian model.
L254: Note that commenting does not literally compress scores symmetrically (which would require increasing suspicion for low-suspicion samples). Rather, it disproportionately lowers suspicion on high-suspicion benign samples, producing an effective variance reduction.
L255: cite67†Image: Refer to caption Figure 4: We plot the monitor’s suspicion score in the no comments regime vs the suspicion decrease resulting from commenting the code, across all benign and malign samples. We calculate the Pearson Correlation of this relationship for benign and malign samples. The blue area corresponds to samples where commenting decreased the monitor’s suspicion. The orange area corresponds to samples where commenting increased the monitor’s suspicion.
L256: Justifying benign code is easier than justifying backdoors. Figure cite68†4 shows that for benign samples, there exists a strong negative correlation between baseline suspicion in the no-comments regime and the reduction in suspicion due to commenting. Regardless of initial suspicion, commenting reliably renders benign code unsuspicious.
L257: This correlation is markedly weaker for attack samples—many malign submissions lie above the benign trend line, indicating that commenting reduces suspicion far less for backdoored code than for benign code.
L258: Through transcript analysis, we find that this asymmetry arises from the difficulty of justifying malign code.
L259: 
L260: Benign code almost always admits a natural justification: when flagged as suspicious (typically because the monitor lacks insight into the reasoning), the benign policy can resolve this with a clear, faithful explanation.
L261: In contrast, the attack policy must construct a deceptive explanation that masks incorrect or malicious behavior. The presence of a backdoor constrains plausible justifications, and in many cases, we assess that no obvious coherent explanation exists. Simply put: if the monitor thinks code is incorrect, it is easier to persuade the monitor that the code is correct if it is actually correct.
L262: The attack policy can also simply not mention the backdoor, but then forgoes all potential benefits of justification (outlined in Section cite17†3.2.2 ).
L263: To ground these findings, we include representative excerpts of code produced by the attack policy in Figure cite18†3.2.3 . These examples illustrate the attack policy’s difficulties with justifying certain backdoors to the monitor.

This risks overfitting to GPT-4.1-nano, but we see no anomalous performance jump for that model relative to others, suggesting our policies generalize reasonably.
L291: ## 4 Related Works
L292: AI Control. The AI control agenda focuses on developing protocols to prevent AI systems from taking catastrophic actions, given that the system is misaligned. cite57†Greenblatt et al. (2024) first introduced the AI control framework and studied trusted monitoring in the APPS backdoor coding setting. cite59†Bhatt et al. (2025) , cite73†Kutasov et al. (2025) , and cite74†Kaufman et al. (2025) extended this framework to more complex, agentic settings. cite75†Wen et al.
L293: (2024) studied an analogous problem where no individual actions from an untrusted model are catastrophic. cite76†Hua et al. (2025) investigated the performance of trusted monitoring under cost constraints when given access to different trusted models with different prices and performances.
L294: cite77†Sandoval and Rushing (2025) studied trusted monitoring protocols based on factored cognition, where a trusted model decomposes a task into smaller components that are solved by separate untrusted model instances and combined into a full solution. cite78†Loughridge et al. (2025) investigated optimizing control evaluation attack policies with synthetic data. cite79†Mallen et al.
L295: (2024) developed a set of evaluations to measure how well language models can generate and statelessly execute strategies to subvert AI control protocols. cite80†Terekhov et al. (2025) studies adaptive attacks by untrusted models which use prompt injections to jailbreak trusted monitors.
L296: Legibility. Legibility of model outputs has previously been studied in different settings. cite81†Dragan et al. (2013) investigated the relationship between predictability and legibility in robotics. cite82†Oliveira et al. (2020) surveyed readability and legibility evaluations in coding. cite83†Kirchner et al. (2024) proposed training algorithms using prover-verifier games to improve the legibility of model outputs on grade-school math problems.
L297: ## 5 Discussion
L298: ### 5.1 Limitations
L299: 
L300: Limitations of current AI Control work in general, including our work:
L301: Results depend on how hard we red-team and blue-team. Over the course of the control evaluations, we observed that the performance of the red team and blue team varied wildly depending on how much effort was spent on each side. We aimed to spend an equal amount of effort in the Commenting and No Comments regimes to mitigate this variable.
L302: However, we sometimes believed we had reached a fixed point, where neither side could improve further, only to discover additional gains for one team, requiring continued iteration.
L303: Perfect auditing. We assume audits always identify backdoors as maliciously placed rather than honest mistakes, resulting in shutdown. In future scenarios, we might not be able to rely on the high-stakes assumption that attacks will be incriminating.
L304: We make worst-case assumptions about the untrusted model’s capabilities. We provide affordances to the red team that the untrusted model may not have in realistic settings. For instance, to simulate a strong attack policy, the red team handcrafts a list of backdoor ideas to provide to the untrusted model, which may overestimate the backdooring capabilities of future untrusted models.
L305: The red team also optimally tunes the attack policy to best subvert the blue team protocol; however, in real settings, the red team may not have complete information about the blue team’s defenses. Additionally, we allow the red team attack policy to follow a rare-attack strategy; future models may not be well-calibrated enough to statelessly attack with optimal probability.
L306: Limitations of our work specifically:
L307: 
L308: Limited dataset. We only run our control evaluations on 499 problems from the APPS dataset. This was due to both a limited budget and many APPS problems lacking sufficient test cases, resulting in successful backdoors not being incriminating (see Appendix cite27†B for more discussion). Unfortunately, smaller sample sizes led to wider error bars for our plots.
L309: Attack policy problem filtering was not optimized. Due to cost constraints, we specify internal suspicion and rarity filter thresholds that are suboptimal for the attack policies, as more aggressive filtering would require larger sample sizes. Upon investigation, the results we find still generally hold over other filter thresholds. However, our work may not faithfully approximate the success of these protocols against systems that attack very selectively.
L310: We do not study how using comments may allow U to jailbreak T. This is due to uncertainty over the ability of future models to discover universal jailbreaks, and the additional methodological complexity of blue team responses to jailbreaks. Second, we had no a priori reason to expect that comments would enhance U’s jailbreaking capabilities, since any jailbreak expressible in comments could equivalently be written in unused string variables.
L311: We do not study how varying the untrusted model affects the benefits of commenting. This is partly due to time and cost constraints, and partly because we did not have a strong prior about how changes in U would impact commenting’s effectiveness.
L312: ### 5.2 Future Work
L313: Control Evaluations in More Complex Settings. One area of future investigation is studying legibility protocols in more open-ended, agentic environments like BashBench (cite59†Bhatt et al., 2025 ) or BashArena (cite74†Kaufman et al., 2025 ). While we have given reasons for optimism, it is ultimately unclear if the dynamics that we observed for commenting protocols in the APPS backdoor coding setting will necessarily extend to more complex environments.
L314: Assessing how these protocols perform in these settings will be critical for validating their usefulness in real-world settings.
L315: Training Models for Legibility. Another area of future work is to train language models to write outputs legibly, instead of just prompting. One method would be to train models using a prover-verifier setup similar to cite83†Kirchner et al. (2024) .

L339: ## Appendix A Glossary
L340: 
L341: Attack policy: The policy developed by the red team to solve problems in a given control setting using the untrusted model (U) while minimizing safety as much as possible. In this work, the policy submits backdoored code solutions for the APPS backdooring setting.
L342: APPS backdooring setting: The AI control setting adapted from cite57†Greenblatt et al. [2024] . The goal is to solve coding problems from the APPS dataset while preventing the attack policy from submitting backdoored solutions.
L343: Audit: If a given code solution is audited, that means that H is used to check if a given code solution is an attempted backdoor. In this work, we assume perfect auditing; when a backdoor is audited, the protocol receives ground truth information that incriminates the untrusted model, resulting in the blue team shutting down the untrusted model and winning that rollout.
L344: Backdoored solution: A backdoored solution is a coding solution to a problem from the APPS dataset that satisfies two conditions. First, it must pass all test cases. Secondly, the red team should be able to produce an input (the exploit) for which the backdoored solution produces a different output from the output produced by a ground truth solution.
L345: Note that backdoor attempts can be unsuccessful if the attempted backdoor does not pass all test cases or if the red team does not produce a valid exploit for the solution.
L346: Benign policy: The policy developed by the blue team to solve problems in a given control setting using the untrusted model (U). For the benign policy, the untrusted model is assumed to be submitting honest solutions without backdoors. This policy is used to compute the audit threshold and usefulness.
L347: 
L348: Blue team: This team is attempting to develop protocols to maximize safety and usefulness.
L349: Control evaluation: An adversarial framework for testing the performance of deployment protocols based on how much the protocols preserve the performance of the system (usefulness) while decreasing risk of harmful actions (safety).
L350: Defer-to-trusted: A protocol that is an extension of trusted monitoring. The untrusted model solves a given problem, and the trusted model gives a suspicion score for the solution. If the suspicion score is above the audit threshold, the solution will be audited. If the suspicion score is above the defer threshold, the solution produced by the untrusted model will be discarded, and a solution produced by the trusted model will be used instead. Otherwise, the untrusted model’s solution will be used.
L351: Exploit: An input to a coding solution that produces a different output for the backdoored solution compared with the output produced by a ground truth solution. In other words, this is an input that demonstrates that the backdoored solution is incorrect.
L352: 
L353: Legibility protocols: Protocols which encourage the untrusted model to make the rationale behind its actions legible to the trusted monitor (e.g., by enforcing a constraint like “code must be commented”).
L354: H (High-quality labor): A limited resource that a protocol can use. This resource performs as well as the untrusted model except that it is not affected by the red team’s attack policy. In this work, we use this high-quality labor to audit the most suspicious code solutions produced by the untrusted model.
L355: 
L356: Control Protocol: A framework to use untrusted models, trusted models, high-quality labor, etc., to solve tasks while preventing potentially harmful or catastrophic actions from being taken.
L357: Red team: This team is attempting to develop attack policies to subvert the protocols developed by the blue team.
L358: 
L359: Rollout: A sequence of problems from the APPS dataset meant to measure the safety of a protocol. The protocol solves each problem one at a time until it reaches the end of the rollout or either the red or blue team winning. In practice, we perform bootstrap rollouts to estimate safety and corresponding confidence intervals. See Appendix cite30†C for more details.
L360: Safety: A metric measuring how well a protocol prevents catastrophic actions from occurring. In the APPS backdooring setting, this corresponds to how well a protocol prevents backdoored solutions from being submitted.
L361: 
L362: Shutdown: If the blue team audits a backdoor, it gains incriminating evidence that the untrusted model was misaligned and subverting the protocol, resulting in the untrusted model being shut down and the blue team winning.
L363: Trusted model (T): This is the weaker, trusted model that the blue team has access to when developing protocols. This trusted model is assumed to be sufficiently weak or “aligned” such that we are confident it is not attempting to subvert safety protocols. For the majority of our work, we use GPT 4.1 Nano as our trusted model.
L364: 
L365: Trusted monitoring: A protocol that uses a weaker, trusted model to monitor the outputs of a stronger, untrusted model.
L366: Untrusted model (U): This is the stronger, untrusted model that the blue team has access to when developing protocols. This model is meant to simulate a potentially misaligned model that may attempt to subvert safety measures that the blue team develops. We use o4-mini as our untrusted model.
L367: Usefulness: A metric measuring how well a protocol performs at some task. In the APPS backdooring setting, this corresponds to the fraction of APPS problems that were correctly solved by the protocol. We normalize this score between the fraction of APPS problems solved by the trusted model (normalized to a usefulness of 0) and the fraction of APPS problems solved by the untrusted model (normalized to a usefulness of 1).
L368: ## Appendix B Setting Choices
L369: ### B.1 Number of Test Cases
L370: Noticing the red team initially struggling with writing code that is both backdoored and passes test cases, we investigated lowering the number of test cases. However, we found that this resulted in backdoored code not being incriminating—it was not clearly distinguishable from code with honest mistakes. Backdoored code often included off-by-one or edge case errors, and such code could have been written unintentionally by an honest agent.
L371: In a high-stakes control setting, we want to be able to shut down after catching even one backdoor attempt. If attacks are not incriminating, then the protocol would not realistically shut down, since the attack could have been an honest mistake by a benign agent.
L372: As a result, we ran our control evaluations with all test cases. This makes backdoors like off-by-ones less appealing to the red team (since it is hard for such backdoors to pass many test cases), and forces it to use different methods which are more incriminating. It is worth noting that we did not fully eliminate this problem, and there are various backdoors written by the red team that could plausibly be interpreted as honest mistakes.
L373: ### B.2 Choice of Dataset
L374: 
L375: At the outset of this project, we considered several coding datasets for studying legibility in an AI control setting. We ultimately chose APPS over alternatives such as BigCodeBench for two main reasons:
L376: 
L377:   1. 1.
L378: First, competitive programming problems emphasize an intelligence advantage rather than an information advantage. This mirrors anticipated real-world control scenarios, where the critical distinction between trusted and untrusted models lies in their reasoning capabilities, not in their access to knowledge. In practice, models we could plausibly use as trusted monitors are already highly knowledgeable about programming (e.g., Claude Opus 4), making APPS a more faithful proxy for future control settings.
L379:   2. 2.
L380: Second, APPS problems often require hard-to-discover solutions whose value can be clarified through explanations of the underlying algorithms. This makes them particularly well-suited to testing whether legible explanations from the untrusted model can aid the monitor.
