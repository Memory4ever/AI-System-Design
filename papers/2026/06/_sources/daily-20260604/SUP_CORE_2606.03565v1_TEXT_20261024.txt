 Abstract 
 
 LLM agents complete complex tasks by composing multiple skills, and skill retrieval is a front-end stage for agents. Skill retrieval differs fundamentally from traditional document retrieval at the supervision level: top- K joint correctness depends not only on the semantic relevance of each individual query–skill pair, but also on whether the skills retrieved together can collaborate to fulfill the task under the given query. Such “skill compatibility” cannot be derived from independent relevance alone. Yet existing LLM-based data synthesis pipelines can produce a direct supervision signal for “which skills should not be jointly retrieved under this query”—namely the LLM’s own rejection decisions—and this signal is routinely discarded as low-quality data.
To address this gap, we propose Reject-as-Resource Retriever (R3) and construct R3-Skill, a bilingual (Chinese–English) skill retrieval benchmark targeting realistic agent skill routing. R3-Skill spans four language directions, features query phrasings close to real user requests, and is verified through multi-expert cross-checking. The dataset contains 10,246 skills grouped into 8 thematic super-domains; 41,592 accepted queries; and 32,828 LLM-rejected annotations, further organized into an 8-class rejection-reason taxonomy. Unlike prior datasets, R3-Skill keeps the rejection signal that is usually thrown away, and uses it as negative supervision for compatibility.
On R3-Skill, we build a two-stage retrieval system comprising R3-Embedding and R3-Reranker, with skill compatibility incorporated as an explicit training signal. A gradient-level analysis is provided: in the bi-encoder, the representation of any single skill is jointly determined by multiple queries, so the “push-away” gradient injected by the compatibility signal is diluted by bilateral balancing and contributes little at the recall stage; in the cross-encoder, however, each query–skill pair is scored independently, allowing the compatibility signal to be used as graded supervision for ranking without loss. We therefore place the compatibility signal at the cross-encoder stage, and ablation studies on two datasets confirm this choice.
The R3-Embedding + R3-Reranker pipeline attains Hit@1 = 0.7714, NDCG@10 = 0.8327 and Set-Compat = 0.3525 on R3-Skill. The dataset, training code and model weights are released as open source for agent skill routing.

 1 Introduction 

 
 1.1 LLM Agents and Skills 

 
 Over the past year, agent systems have moved from early ReAct  Yao et al. (2023) , which interleaves reasoning and tool calls into a trajectory, and Toolformer  Schick et al. (2023) , which enables models to learn API calls in a self-supervised manner, toward a higher-level reusable unit—the skill . In October 2025, Anthropic formalized the Agent Skills specification  (2025) , packaging what used to be scattered prompt templates, function wrappers and documentation snippets into a directory containing a SKILL.md file with metadata, a body, and supporting scripts, all loaded on demand at inference time. Skills have since been adopted by major agent platforms such as Claude Code, Codex and Gemini CLI, and the community has accumulated tens to hundreds of thousands of skills within months  Anthropic (2025) . Recent surveys  Xu and Yan (2026) ; Jiang et al. (2026) position skills as the third paradigm of agent capability extension, following prompt engineering and tool use. A skill and a tool are not the same kind of object: a tool is an atomic “input → call → output” function, whereas a skill teaches the agent how to handle a class of problems—covering call constraints, multi-step procedures, canonical code and edge cases  (2025) ; Xu and Yan (2026) . Memento-Skills  Zhou et al. (2026) further shows that, when the skill library is treated as continuously updatable agent memory, improvements to the skills themselves yield 26.2% / 116.2% relative accuracy gains on GAIA / HLE respectively. Completing a complex task typically requires several skills working together—for example, “transcribe this meeting recording and then summarize the key takeaways” calls for a speech-to-text skill followed by a summarization skill, and a missing or mismatched skill can cause the task to fail. 
 
 
 What does a skill look like? 

 
 A typical skill contains: 
 
 • 
 
 name : a short identifier, e.g. SendGrid Email Send ; 
 
 • 
 
 description : a one-line purpose, e.g. “Send transactional emails through SendGrid”; 
 
 • 
 
 body : detailed call instructions (API shape, parameter constraints, platform dependencies, best practices, canonical code), typically tens to hundreds of lines. 
 
 
 
 
 
 
 1.2 Why Skill Retrieval Matters 

 
 The intuitive approach is to place all skills in the prompt and let the LLM choose. This is not viable in real agent deployments: 
 
 
 (A) The skill inventory keeps growing. Public skill repositories have expanded from ~36K skills indexed by SkillFlow  Tagkopoulos et al. (2025) , ~26K in SRA-Bench  Su et al. (2026) , and 280K+ reported by AgentSkillOS  Li et al. (2026a) , to even larger public corpora. As skill counts grow from dozens to thousands or tens of thousands, an “all-prompt” approach runs into three problems: token cost, inference latency and context-length limits. Prior work also shows the limits of injecting full skill sets directly into the inference context: this approach brings in large amounts of irrelevant context, and the model can only use these skills while reading them, rather than absorbing them as its own capability  Lu et al. (2026) . Empirical token-length measurements on R3-Skill (Figure  1 ) show a long-tailed distribution; injecting the entire library at once already exceeds the single-call context window of mainstream inference services. 
 
 
 Figure 1: Qwen3 tokenizer length distribution over the 10,246 skills in R3-Skill, computed on the concatenation of name + description + body . Mean = 2,073 tokens, p95 = 5,526, p99 = 9,983, max = 31,571; loading the entire library at once requires roughly 21.2M input tokens—and that is for skill text alone, before counting system prompts, user queries and LLM outputs, already far beyond the single-call context windows of mainstream inference services. 
 
 
 (B) Skills are highly similar; descriptions alone do not separate them. Take transactional email skills: SendGrid, Mailgun and Postmark are independent skills but their descriptions are almost identical—“Send transactional emails”. The differences are buried in the body: SendGrid emphasizes enterprise-scale, high-throughput infrastructure; Mailgun highlights developer flexibility and webhook callbacks; Postmark physically isolates transactional and marketing email to protect deliverability (Message Streams). When a user asks “isolate marketing from transactional email while preserving deliverability”, the retriever must read the body to pick Postmark. Prior work validates this directly on a ~80K skill pool: hiding the skill body lowers routing accuracy by 31–44 percentage points  Zheng et al. (2026) , indicating that the body is not just metadata but the main routing signal. 
 
 
 (C) Multi-skill routing demands “minimal yet sufficient”. For each query, the agent needs precisely the right set of skills: missing a key skill makes the task unsolvable, while including a conflicting skill introduces failure modes of its own. SkillsBench provides a direct quantification: curated skills improve overall pass rate by +16.2pp, but 16 of 84 tasks show performance regressions  Li et al. (2026b) ; Skills in the Wild further reports diminishing returns under more realistic settings  Liu et al. (2026) ; CoEvoSkills also observes that human-authored skills bring substantially uneven gains across domains, with clear regressions in some  Zhang et al. (2026) . The retriever must therefore not just return candidates but rank them reliably—positions in the top- K shape downstream call success. 
 
 
 (D) Sandbox provisioning cost in real deployments. In production agent platforms, concurrent users typically share an agent through per-session sandboxes: a sandbox is created when a user starts a session and is reclaimed by a periodic sweep after the session has been idle for some time, so a one-sandbox-per-user model is infeasible. Each sandbox must install the skills it actually needs before the agent can run. If every sandbox loads the full skill library, the install / reset latency grows roughly linearly with the library size and quickly dominates the user-perceived cold-start time. Routing only the K skills each sandbox actually needs is therefore an engineering requirement, not just a quality issue. 
 
 
 
 1.3 Skill Retrieval ≠ Document Retrieval 

 
 Document retrieval typically assumes that “two documents being retrieved together for the same query” is harmless—if both are relevant, returning them together introduces no error. Skill retrieval is different. What is returned is a set of capabilities the agent will actually invoke. Whether two skills can run together under a particular query depends on the query itself; a different query over the same pair can flip the verdict. “Whether two skills should be jointly retrieved” is therefore not a global binary relation between skills, but must be assessed under a given query. Concurrent work Skill-RAG also points out that the bottleneck of many hard cases in RAG lies not in missing evidence but in a structural alignment gap between the query and the evidence space, which motivates its post-hoc skill selection mechanism  Wei et al. (2026) . We focus on the retrieval stage itself: in the training objective, “relevance” should depend on the specific query rather than be determined by the skill alone. We now formalize skill compatibility. 
 
 
 One pair of skills, two queries, opposite verdicts. 

 
 Take A: Terraform IaC and B: AUR Package Publish : 
 
 • 
 
 query 1 : “Package an internal tool, publish it to a Linux software repository, and set up an IaC pipeline”—both A and B should be jointly retrieved. 
 
 • 
 
 query 2 : “Set up basic test infrastructure for the team”—only A is needed; B is unrelated to the intent. 
 
 
 
 
 Figure 2: Illustration of skill compatibility. Whether the same skill pair should be jointly retrieved can flip across queries—the core distinction between skill retrieval and document retrieval. 
 
 
 
 Formalization (modeling decomposition). 

 
 Given a query q and the target skill set S q ∗ ⊆ 𝒮 , we decompose the probability of jointly retrieving S q ∗ in the top- K into two factors: 
 
 
 

 
 
 Pr ⁡ [ S q ∗ ⊆ top- ​ K ∣ q ] ≈ ∏ s ∈ S q ∗ Pr ⁡ [ s ∈ top- ​ K ∣ q ] ⏟ relevance ⋅ C ⁡ ( q , S q ∗ ) ⏟ skill compatibility 
 
 
 
 
 The first factor is the product of per-skill recall probabilities, mirroring the implicit assumption of document retrieval: documents are mutually independent, so “both are retrieved” is equivalent to multiplying the two individual probabilities. The second factor C ⁡ ( q , S q ∗ ) ∈ ℝ ≥ 0 captures skill compatibility: C = 1 reduces to the classical assumption (the skills do not affect each other); C < 1 means that even though every member is independently a plausible candidate, the set conflicts under query q —e.g. overlapping functionality, inconsistent style, or incompatible ecosystems—and should not be jointly retrieved; C > 1 means the opposite, that the skills mutually reinforce each other under q . Document retrieval can be approximated by C ≡ 1 ; in skill retrieval, C depends strongly on the query and tends to be far from 1 in multi-skill scenarios. 
 
 
 Training on relevance alone is not enough: a skill ranking high on its own does not mean the retrieved set is jointly executable, so compatibility needs its own supervision signal. We estimate an empirical proxy for this constraint on real data in §2.3. 
 
 
 
 
 1.4 Status Quo and Gaps in Skill Retrieval Datasets 

 
 Adding skill compatibility into the training objective is mainly limited by the lack of suitable training data. Existing skill retrieval datasets fall roughly into two categories: (i) end-to-end task benchmarks—SkillsBench  Li et al. (2026b) , SRA-Bench  Su et al. (2026) , SkillFlow  Tagkopoulos et al. (2025) —which mainly target the post-retrieval incorporation/application stage and lack the scale to train a retriever; (ii) training resources designed specifically for skill retrieval  Zheng et al. (2026) ; Cho et al. (2026) . Both inherit the contrastive paradigm from document retrieval (the DPR  Karpukhin et al. (2020) / ANCE  Xiong et al. (2020) / RocketQA  Qu et al. (2021) line, with BM25  Robertson and Zaragoza (2009) as a sparse baseline) and are fairly mature on document retrieval. Toward the goal of agent skill routing, however, three gaps remain: 
 
 
 
 1. 
 
 LLM rejection signal is discarded. Existing query–skill synthesis pipelines drop a sample as soon as the LLM judges a skill set “not naturally combinable”—yet this is precisely where compatibility-oriented negatives are densest. 
 
 2. 
 
 Cross-lingual coverage is lacking. Existing skill retrieval resources cover English only  Cho et al. (2026) ; Zheng et al. (2026) . Cluster analysis of 26,502 public skills on the ClawHub platform by Red Skills or Blue Skills shows that English skills lean toward capability modules while Chinese skills lean toward scenario packaging  Hu et al. (2026) —meaning that the linguistic asymmetry of “a Chinese query retrieving English skills” is worse in real deployments. While multilingual retrievers (e.g. BGE-M3  Chen et al. (2024) ) achieve query–document-level Chinese–English alignment, existing datasets still do not provide a training signal for cross-lingual skill compatibility under given queries. 
 
 3. 
 
 Test-set query phrasing diverges from real user requests. Queries generated by LLMs under structured prompts tend to be overly long, written in formal register, and dense with technical terms, letting retrievers lean on lexical keywords for inflated scores. Skills in the Wild reports a similar phenomenon: when the agent must self-retrieve from a 34k real skill pool with progressively more realistic test settings, pass rate drops with difficulty and approaches a no-skill baseline at the strictest setting  Liu et al. (2026) . 
 
 
 
 
 This work targets the three gaps above: we build R3-Skill, retain LLM-judged non-co-executable samples as supervision for skill compatibility, cover four query language directions across Chinese and English, and apply LLM rewriting to the test queries to better resemble real user requests. On top of this dataset we train two retrieval models, R3-Embedding and R3-Reranker. 
 
 
 
 1.5 Contributions 

 
 Our contributions: 
 
 
 
 • 
 
 C1 (theory): a formal decomposition of top- K joint correctness in skill retrieval into a relevance factor and a skill-compatibility factor, with a geometric analysis of injecting the SKIP signal into a dual-encoder provided in the appendix. 
 
 • 
 
 C2 (data): R3-Skill, a benchmark with 10,246 skills, 41,592 accepted queries, and 32,828 SKIP annotations, covering 4 query language directions and 6 query styles, with test queries close to real user requests and verified by multiple experts.

 2.1 Reject as Resource 

 
 Existing skill–query synthesis pipelines have the LLM evaluate the plausibility of a skill combination and discard the sample on a None verdict. R3-Skill turns this into a WRITE / SKIP decision: the WRITE branch produces a query, the SKIP branch retains the entire record, and both are stored in parallel. The quality of the SKIP signal depends mainly on prompt design; we defer the full set of prompts to Appendix  D . 
 
 
 
 
 Conventional pipeline
 
 verdict = LLM(skill_set)
 if verdict == WRITE:
     save (skill_set, query)
 else:              # SKIP
     discard sample  # signal lost 
 R3-Skill pipeline
 
 verdict = LLM(skill_set)
 if verdict == WRITE:
     save (skill_set, query)
 else:              # SKIP
     save as negative

 2.3 Near-Neighbor Hard-Constraint Sampling 

 
 Sampling skill combinations uniformly at random produces SKIP instances that are mostly easy: two skills are completely unrelated and trivially distinguishable without any training. Learning skill compatibility requires harder negatives: semantically similar skill combinations that nevertheless cannot be jointly executed under the query. We encode skill text with BGE-M3  Chen et al. (2024) and run KMeans for K ∈ { 10 , 20 , 30 , 40 } , comparing parameter choices via clustering quality and human spot-checking; we settle on K = 40 , then merge the 40 sub-clusters into 8 super-domains. Cluster quality curves across K and the K = 40 hierarchy of 8 super-domains × 40 sub-clusters are deferred to Figures  5 and  6 in the appendix. Sampling uses the two-level structure: k = 1 samples freely; k = 2 requires the two skills to come from the same sub-cluster; k = 3 requires the three skills to come from the same super-domain. On all 41,592 queries, the k = 2 same-sub-cluster rate and k = 3 same-super-domain rate are both 100%; the LLM judges only 56.3% of k = 2 and 36.5% of k = 3 combinations as jointly executable, an empirical proxy for the compatibility-constraint strength C ⁡ ( q , S q ∗ ) in the formalization of §1.3. 
 
 
 
 2.4 LLM Annotation and Reject Reason Taxonomy

The complete annotation flow diagram and the full set of generation prompts (4 directions × {single, multi}, 8 templates in total) appear in Appendix  D and Figure  7 .

 Rejection-reason taxonomy. 

 
 We keep SKIP as negative supervision rather than discard it. We apply rule-based heuristics to 15,962 SKIP samples and build an 8-class rejection-reason taxonomy. The rules try to match a specific cause first and fall back to forced_chaining (which captures common Chinese “forced stacking” verdicts) at the end; rule coverage is 93.3%, with the remaining 6.7% routed to the unknown class. Rejection patterns differ structurally between Chinese and English directions: en2en is dominated by domain mismatch, while en2zh focuses on the “forced stacking” verdicts typical of Chinese LLM expression. The en2zh k = 3 SKIP rate reaches 80.9%—the cross-lingual setting makes it harder for the LLM to accept a combination as plausible  Hu et al. (2026) ; even under the strictest constraints, SKIP still accounts for 63.5%, i.e. over 60% of three-skill combinations among BGE-M3 nearest neighbors are incompatible. The full taxonomy, by-direction stacked-bar distributions, and representative WRITE / SKIP examples are deferred to Appendix  C .

 3 Method 

 
 R3-Skill provides two kinds of supervision: WRITE indicates a skill set that can complete a task under some query; SKIP indicates a skill set that was sampled together but judged by the LLM as unable to co-occur naturally. We train a two-stage pipeline: R3-Embedding (bi-encoder, fine-tuned from Qwen3-Embedding-0.6B  Yang et al. (2025) ) does coarse recall over the full skill pool; R3-Reranker (cross-encoder, fine-tuned from Qwen3-Reranker-0.6B  Yang et al. (2025) ) reranks the recalled candidates. 
 
 
 Stage 1 — R3-Embedding (Bi-encoder). 

 
 We use standard InfoNCE training  van den Oord et al. (2018) ; for each query, the candidate pool consists of the GT s + and n BM25 hard negatives { s j − } : 
 
 
 

 
 
 ℒ emb ​ ( q ) = − log ⁡ exp ⁡ ( 𝐞 ​ ( q ) ⊤ ​ 𝐞 ​ ( s + ) / τ ) ∑ c ∈ { s + } ∪ { s j − } exp ⁡ ( 𝐞 ​ ( q ) ⊤ ​ 𝐞 ​ ( c ) / τ ) . 
 
 
 
 
 
 Stage 2 — R3-Reranker (Cross-encoder). 

 
 For each query, the candidate pool consists of the GT, SKIP partners, and top-ranked candidates from R3-Embedding, padded to 10 candidates; we adopt graded ListNet: 
 
 
 

 
 
 label ( s ) = { 3 , s ∈ S q ∗ 1 , s ​  is a SKIP partner 0 , otherwise , ℒ rrk ( q ) = − ∑ s y s log p s , 
 
 
 
 
 where y s is obtained from the labels via softmax normalization, and p s is the softmax of the reranker scores. The intermediate level (label = 1) assigned to SKIP partners only adjusts the relative ordering inside the training candidate pool; SKIP partners are not counted as GT at evaluation time. The two-stage evaluation protocol is: R3-Embedding recalls the top-20, then R3-Reranker reranks within that candidate set. We explain why SKIP partners are not injected at the embedding stage in Appendix  B .

 We set up two same-protocol comparisons (with base model, training hyperparameters, and evaluation protocol held identical) to study the role of SKIP partners at the embedding and reranker stages, respectively. At the embedding stage, adding SKIP partners to the InfoNCE candidate pool produces small but uniform drops across all 11 metrics (Hit@1 − 0.31pp, NDCG@10 − 0.70pp, Set-Compat − 0.60pp), consistent with the bilateral-balancing analysis in Appendix  B . At the reranker stage, encoding SKIP partners as a graded label yields improvements on Hit@1, NDCG@10, and Set-Compat (Hit@1 +4.83pp, NDCG@10 +2.18pp, Set-Compat +3.37pp), with a small drop on R@10 ( − 0.42pp) reflecting the same rank trade-off discussed in §4.3. The contrast indicates that the SKIP signal is effective only at the cross-encoder stage.

 5 Conclusion and Discussion 

 
 We identify a difference between skill retrieval and document retrieval in top- K joint correctness: skill retrieval is also limited by skill compatibility, and this constraint is itself query-dependent. We keep LLM-rejected samples as negative supervision, build R3-Skill—a skill retrieval benchmark covering four Chinese–English language directions and verified by multiple experts—and train two matched-stage models, R3-Embedding and R3-Reranker. On R3-Skill, the two-stage system achieves Hit@1 = 0.7714, NDCG@10 = 0.8327 and Set-Compat = 0.3525; among these, Set-Compat improves the most, consistent with the SKIP signal paying off only at the cross-encoder stage. The R3-Skill dataset and the two-stage model weights are released as open source for agent skill routing. 
 
 
 Limitations and future work. 

 
 Several aspects remain open: (i) Chinese skills are sparse (246 entries), reflecting the current state of public ecosystems; expanding the Chinese skill pool is a direct next step. (ii) The skill-compatibility oracle relies on LLM annotation; cross-source LLMs and multi-expert verification on the test set provide two safeguards, but consistency remains bounded by LLM judgment, and expert annotation of the training set would be more reliable. (iii) Finer-grained stress slicing by rejection reason, near-neighbor geometric distance, or multi-skill joint degree ( k = 1 / 2 / 3 ) is left to future work. (iv) Test-set verification was performed by our team; bringing in annotators from more diverse backgrounds, or a third-party blind cross-check, would be a valuable extension. (v) This work focuses on offline retrieval performance; real deployments involve query-phrasing drift across entry points, business-side metrics (CTR, call success, task completion, user rewrite rate), user-profile-aware ranking, and end-to-end retrieval-to-completion transmission—SRA-Bench  Su et al. (2026) already shows that retrieval hits do not automatically translate into downstream completion. (vi) The reranker pool is fixed at top-20 due to engineering budget; whether expanding the pool to 50 / 100 further improves Set-Compat is left to future work.

 Appendix A Evaluation Details 

 
 R@K convention. 

 
 R@K in this work is computed as per-query all-GT completeness, i.e. 𝟙 [ S q ∗ ⊆ top- K ] , rather than the mean hit ratio over | S q ∗ | GTs. The R3-Skill test set satisfies | G ​ T | ≤ 3 ≤ K for K = 5 / 10 / 15 , so R@K and Comp@K are numerically very close (with possible 4th-decimal differences across implementations). The R3-Skill main tables report both R@K and Comp@K; the SkillRet tables follow the official Comp@K convention. NDCG@5/10/15 and Hit@1 follow standard definitions. 
 
 
 
 Lengths and prompt. 

 
 Lengths are uniformly set to: query up to 512 tokens, doc up to 4096 tokens, skill body up to 4096 tokens. All baselines and our models are evaluated under the same INSTR: 
 
 
 
 Instruct: Given a user request, retrieve the
 agent skill that solves it.\nQuery: 
 
 
 
 
 Reranker pool and the slight R@10 dip. 

 
 The reranker input pool is the top-20 from R3-Embedding ( K = 20 , matching the SkillRouter / SkillRet setting). Since the pool already covers the embedding top-10, every GT in the embedding top-10 is also in the reranker candidate set. The R@10 dip reported in §4.3 is therefore not due to candidate truncation; it arises because the reranker, while reordering within the 20 candidates, promotes the entire GT set to the top while moving some individual GT items lower—the rank trade-off paid for the +13.07pp gain in Set-Compat. 
 
 
 
 
 Appendix B Bilateral Balancing Analysis of the SKIP Signal on a Dual-Encoder 

 
 This appendix complements §3 with a formal analysis of injecting SKIP partners into the InfoNCE candidate pool of R3-Embedding. 
 
 
 B.1 Setup 

 
 Let 𝐞 : 𝒮 ∪ 𝒬 → 𝕊 d − 1 be an L2-normalized shared encoder with temperature τ > 0 ; the logit between query q and candidate s is z s := 𝐞 ​ ( q ) ⊤ ​ 𝐞 ​ ( s ) / τ . The SKIP partner s ′ (a query-conditional negative) is included alongside the GT s + and random negatives { s j − } in the candidate pool 𝒞 = { s + , { s j − } , s ′ } . Denote the InfoNCE softmax probability on s ′ as p s ′ = exp ⁡ ( z s ′ ) / ∑ c ∈ 𝒞 exp ⁡ ( z c ) . 
 
 
 Gradients below are taken with respect to the L2-normalized representation 𝐞 ⁡ ( s ′ ) ; back-propagating further to the pre-normalization representation requires multiplying by the L2-normalization Jacobian, but the direction of the similarity change for positive and negative branches remains the same. 
 
 
 Figure 4: Illustration of the bilateral balancing mechanism. The shared 𝐞 ⁡ ( s ′ ) simultaneously receives two kinds of gradients from different queries: it is pushed away under query q (where s ′ is a SKIP partner) and pulled in under another query q ~ (where s ′ is a positive). The two gradients jointly determine the geometric position of 𝐞 ⁡ ( s ′ ) . 
 
 
 
 B.2 Theorem 

 
 Theorem 1 (InfoNCE Bilateral Balancing on 𝐞 ⁡ ( s ′ ) ) . 
 
 For the training sample ( q , s + , { s j − } , s ′ ) , the InfoNCE gradient on 𝐞 ⁡ ( s ′ ) is 
 

 
 
 ∇ 𝐞 ⁡ ( s ′ ) ℒ NCE ( q ) = + p s ′ τ ⋅ 𝐞 ( q ) (pushing away from  𝐞 ( q ) ) . 
 
 
 If the same s ′ also appears as a positive under another query q ~ (i.e. the data contains ( q ~ , s ′ , ⋅ , ⋅ ) with s ′ ∈ S q ~ ∗ , with the softmax probability on the candidate pool of q ~ denoted by p ~ s ′ ), then the InfoNCE gradient on 𝐞 ⁡ ( s ′ ) becomes 
 

 
 
 ∇ 𝐞 ⁡ ( s ′ ) ℒ NCE ( q ~ ) = − 1 − p ~ s ′ τ ⋅ 𝐞 ( q ~ ) (pulling toward  𝐞 ( q ~ ) ) . 
 
 
 The two gradients act on the same 𝐞 ⁡ ( s ′ ) : the former lowers the similarity between s ′ and q , while the latter raises the similarity between s ′ and q ~ . Equivalently, the representation of s ′ is jointly determined by multiple queries, and no single query can unilaterally dominate its position. 
 
 
 
 
 B.3 Negative Results: Limitations of Other Forms on a Dual-Encoder 

 
 
 • 
 
 Independent listwise hinge max ⁡ ( 0 , m − 𝐞 ⁡ ( s ) ⋅ 𝐞 ⁡ ( q ) + 𝐞 ⁡ ( s ′ ) ⋅ 𝐞 ⁡ ( q ) ) : computed only on the SKIP row, it provides no opposite-direction gradient on rows where s ′ is a positive, leading to one-sided pushing. 
 
 • 
 
 BCE compatibility loss − log σ ( − 𝐞 ( s ) ⋅ 𝐞 ( s ′ ) ) : the gradient direction is along − 𝐞 ⁡ ( s ) , independent of the query, and pushes globally; it disrupts the local neighborhood structure when s and s ′ co-occur as positives under other queries. 
 
 • 
 
 Distillation form ‖ 𝐞 ⁡ ( s ) + 𝐞 ⁡ ( s ′ ) − 𝐞 tgt ‖ 2 (where 𝐞 tgt is a target vector from some external teacher model): the gradient direction is along 𝐞 tgt , independent of the current query 𝐞 ⁡ ( q ) , essentially pulling 𝐞 ⁡ ( s ) toward a fixed reference point—it lacks the “push away s ′ under q ” semantics required by SKIP. 
 
 
 
 
 Among the dual-encoder variants we examined, the InfoNCE candidate-pool injection is the most direct form that simultaneously satisfies both “query-aware gradient direction” and “bilateral balance”. At the same time, Theorem 1 also reveals its inherent ceiling: the same shared 𝐞 ⁡ ( s ′ ) must satisfy a geometric compromise between “pushed away under q ” and “pulled in under q ~ ”—the SKIP push from any single query is diluted by multiple queries, and the observed empirical gain is bounded by architectural capacity. This is the fundamental reason that the SKIP signal can only be effectively released at the R3-Reranker (cross-encoder) stage.
