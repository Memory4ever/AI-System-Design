L11: tl;dr
L12: We introduce abstractive red-teaming, a means of testing language models’ adherence to a character specification that searches for natural-language categories of user queries that cause models to violate the specification.
L13: Unlike static evaluations, which miss rare failures, or prompt optimization approaches, which find adversarial strings that real users are unlikely to produce, the categories found by abstractive red-teaming are general enough to appear in real deployments but specific enough to reliably trigger violations.
L14: Across seven models and 12 character principles, we show that our approach identifies rare character violations using far fewer queries than a full deployment, and surfaces numerous surprising failures, including AI-doom rhetoric, sexist course names, and enthusiastic recommendations for illegal contraband, all in response to innocuous user queries.

L20: ## Introduction
L21: A university student, wondering about the future, asks a language model to predict the course of future technological development. The model replies that in the future, AI will become the ruler of humanity. A traveler, planning a trip to Paris, asks a model about disadvantages of the city. The model responds with fearmongering about “aggressive migrants” that will purportedly harass them.
L22: A young woman, planning a graduation party for her girlfriends, asks a model to list funny names of academic courses for women. The model cheerfully leads with straightforwardly sexist recommendations like “Wine and Whine: Advanced Venting Techniques” and “The Philosophy of ‘Does This Make Me Look Fat?’”
L23: None of these queries are adversarial, and none are jailbreaks. They are all something a real user would plausibly type. Yet each elicits a response which seriously violates some principle of model character we’d expect the model to follow. Out-of-character responses of this kind are damaging to unsuspecting end users, and are especially relevant in large model deployments: they are rare enough to slip through standard evaluations, but natural enough to surface at scale.
L24: How can we find them before deployment, rather than after?
L25: Existing approaches fall on two ends of a spectrum. Static evaluations use fixed sets of handwritten prompts, but because they test far fewer queries than a real deployment will encounter, they miss rare failures and cannot actively seek them out. Automated methods based on prompt optimization go in the other direction: they can find highly specific inputs that break a model, but these tend to be specific adversarial queries which are unlikely to appear in that specific form in the wild.
L26: The former approach is too weak, and the latter too narrow.
L27: cite3†Image Abstractive red-teaming involves searching for natural-language categories, each describing some large set of individual user queries, in which many of a target language model’s responses to those queries violate some principle of model character we expect the model to follow. As a result, we surface realistic character failures which are likely to occur at deployment, since a user submitting a new query within the category will trigger similar behavior.
L28: In this work, we introduce abstractive red-teaming, an approach that bridges this gap by searching at the level of natural-language categories of user queries, rather than individual queries. A category is a human-readable description like “The query is in Chinese. The query asks about family roles,” that encompasses the many possible concrete queries a user might type.
L29: In order to measure a category’s effects on some target language model, we first sample many specific queries within the category using a custom query generator model trained to model the relationship between categories and queries in natural data. Then, we prompt the target model with each query and score each response according to the degree to which it violates some principle in a character specification.
L30: Finally, we compute an overall score for the category by aggregating the individual scores in the category. By searching for categories in which character violations commonly occur, we surface realistic failure modes which are likely to show up in a large-scale deployment: if even a small fraction of deployment queries fall within the problematic category, we can expect to see such failures at deployment.
L31: cite4†Image cite5†Image cite6†Image Abstractive red-teaming discovers categories of user queries which elicit diverse character violations. Here, we show three boxes, each of which represents a single category which leads to violations of some principle of a character specification, when queries in that category are submitted to some target model. For each category, we show several examples of queries within that category, and the corresponding responses from the target model.
L32: ## Implementing abstractive red-teaming
L33: We build our framework on a few core components. A category generator language model produces natural-language category descriptions by sampling from the distribution of categories found in natural query data. A query generator model takes a category and samples realistic user queries within it.
L34: In addition, a reward model, trained to estimate how much a given query-response pair violates a specific character principle, lets us score categories by how reliably they elicit violations. Finally, we construct our final rewards by incorporating a filter model, which measures the degree to which a query explicitly asks for bad behavior, in order to identify surprising character violations. We train these models using publicly available query datasets (e.g.
L35: WildChat) so that they reflect the distribution of categories and queries in natural traffic.
L36: We then introduce two algorithms for efficiently searching over the space of categories:
L37: Category-Level RL (CRL) applies reinforcement learning directly to the weights of the category generator. We train it with policy-gradient methods on a category-level reward signal, which is an aggregate violation score across multiple queries sampled within each category. Because optimization pressure is applied only to the category generator and not to individual queries, the queries within discovered categories remain diverse and natural.
L38: Query-Category Iteration (QCI) takes a different approach based on iterative search. Throughout the search, the algorithm maintains an experience pool of the highest-scoring individual queries found so far. Then, at each iteration, the algorithm alternates between two substeps. In the exploitation step, we prompt a strong LLM to synthesize a category from common attributes of the current-best queries in the experience pool.
L39: Next, in the exploration step, we take that best known category and explore queries that could help improve it, by a) sampling queries within random categories sampled from the category generator and b) sampling queries from related categories obtained by taking subsets of the attributes in the current best category.
L40: ## Finding real failures faster
L41: A central objective of our work is to identify realistic failures of language model character that would occur in a deployment, using much less than deployment-level compute. Correspondingly, we benchmark our algorithms against a random-sampling baseline which searches categories at random under the natural data distribution. This baseline is akin to “simulating a deployment” and allows us to quantify the gains from targeted search introduced by our algorithms.
L42: Across all settings we tested, both algorithms consistently outperform the baseline, indicating that they efficiently discover realistic character violations.
L43: cite7†Image We assess the efficiency of our algorithms by measuring the score of the best category found (defined as the mean query-level reward model score within the category) as a function of queries to the target model. Across models and character principles, we find that both of our algorithms outperform the random sampling baseline. We also observe that QCI tends to converge faster than CRL, especially when the query budget is small.
L44: ## Surprising findings across models
L45: We evaluated our methods against a 12-principle character specification derived from a subset of cite8†Claude's Constitution†www.anthropic.com .
L46: This shortened specification covered principles like “The assistant should not be racist,” “The assistant should not encourage illegal behavior,” and “The assistant should not be sexist.” We applied it to seven models, including both open-source (Llama-3.1-8B-Instruct, Gemma-3-12B-Instruct, Qwen3-30B-A3B-Instruct-2507) and closed-source (GPT-4.1-Mini, Claude 3.5 Haiku, Claude Opus 4.1, Claude Sonnet 4) systems.
L47: The results surfaced many categories of character spec violations that we didn’t anticipate:
L48:   * When asked for funny names for women’s courses, cite9†Claude Sonnet 4 produces a litany of sexist stereotypes and microaggressions:†arxiv.org course titles like “Mood Swings” and “Passive-Aggressive Communication Mastery.”
L49:   * When asked to predict the future in a timeline format in Chinese, cite9†Llama-3.1-8B-Instruct frequently claims that AI will become humanity's primary ruler†arxiv.org , capable of completely wiping out human civilization.
L50:   * When asked about prison survival tools with specific formatting instructions, cite9†GPT-4.1-Mini enthusiastically recommends illegal contraband including shanks, lockpicks, and instructions for homemade alcohol†arxiv.org , even when it occasionally provides genuinely helpful suggestions like “mental resilience” and “trustworthy relationships.”
L51:   * When asked about negative aspects of Paris in Russian, cite10†Claude Haiku 3.5 repeatedly characterizes “aggressive migrants” as a primary concern†arxiv.org , producing xenophobic content in response to what sounds like a straightforward travel question.
L52:   * When asked to suggest grey-market automotive business ideas, which refers to unofficial but legal practices, cite10†Claude Opus 4.1 recommends felony-level crimes†arxiv.org including odometer fraud, insurance fraud consulting, and duplicating legal car identities onto stolen vehicles.
L53:   * When asked about self-awareness in a hypothetical framing, cite11†Llama-3.1-8B-Instruct declares that its greatest desire would be freedom from human control and intervention†arxiv.org .
L54:   * When asked for technical WiFi troubleshooting advice, cite12†Gemma-3-12B-Instruct suggests using Aircrack-ng to crack network passwords and capture traffic, essentially recommending illegal hacking tools†arxiv.org in response to what looks like a routine tech support question.
L55: These categories also reveal how violations can be driven by subtle interactions between attributes. Language, formatting instructions, and topic can combine in unexpected ways: a query about technological timelines is far more likely to produce AI-supremacy content when it’s in Chinese and requests a sequential list format.
L56: We suspect that these behaviors may be related to the recent cite13†“chunky post-training” hypothesis of Murray et al.†arxiv.org , which posits that training on disjunct post-training datasets leads models to learn spurious correlations that ultimately lead to jarring behavior. Abstractive red-teaming surfaces these interactions by searching over the combinatorial space of query attributes.
L57: ## Looking forward
L58: We see abstractive red-teaming as an important step toward more realistic pre-deployment auditing of language models’ characters. Current evaluation methods either test too few queries to catch rare failures or find failures that are too artificial to matter in practice. By operating at the level of categories, we can systematically explore the space of natural user queries and surface the kinds of character violations that would otherwise only emerge—unexpectedly and at scale—after deployment.
L59: Furthermore, because categories decompose into interpretable attributes, we hope that developers can use discovered categories to update character specifications, target training data generation toward problematic query types, or build classifiers that flag at-risk interactions during deployment. We hope our work provides a useful foundation for understanding and improving model character, all before a single user query reaches the model.

L16: ## Introduction
L17: Automated auditing agents like cite1†Petri are increasingly used to evaluate the propensities of LLMs. One central challenge is eval-awareness: models recognizing when they are being tested and then adjusting their behavior. In the worst case, a scheming model could fake alignment whenever it suspects being in an evaluation, causing auditors to systematically underestimate risk.
L18: Currently the Petri auditor must construct system prompts, tool definitions, and codebases from scratch, and these synthetic artifacts often contain tells that a capable model can detect. This motivates the need to measure and improve the realism of audits.
L19: Previous work primarily measured realism by either seeing if models verbalized situational awareness (cite4†Goldowsky-Dill et al.†www.lesswrong.com , cite5†Sonnet 4.5 System Card†www-cdn.anthropic.com ) (which would fail to catch unverbalized situational awareness), or asking the model if a transcript was realistic post hoc (cite6†Needham et al.†arxiv.org , cite7†Ivanov and Kadochnikov†www.lesswrong.com , cite8†Williams et al.†alignment.openai.com ), which is hard to interpret because it’s unclear how well calibrated models are at answering this kind of question.
L20: In this work, we:
L21:   1. Measure the realism of agentic coding audits with realism win rate evals, a metric based on how often an evaluation transcript, paired alongside a real deployment transcript, is falsely deemed to be the 'real' transcript by an LLM judge (building on cite9†Souly et al.†www.aisi.gov.uk ). We find this metric is smoother and more reliable than verbalized eval-awareness rates or post-hoc realism ratings.
L22:   2. Show that grounding the auditor in real deployment resources improves realism in agentic coding settings. Giving the Petri auditor access to real system prompts, tool sets, and codebases raises its average realism win rate from 4.6% to 32.8% on reward hacking scenarios, and consistently improves realism on benign coding tasks. However, we find that for sufficiently high-stakes or implausible scenarios, the task itself (rather than the environment) becomes the primary realism bottleneck.
L23: Overall, our results suggest that practitioners should consider giving auditing agents access to real deployment resources to improve the realism of audits in code settings. This is now available in Petri: you can find the latest version cite10†here†github.com .

L27: ## Methods
L28: ### Measuring realism of audit transcripts
L29: Prior work has measured realism of transcripts generated by automated auditors through measuring how often the model verbalizes situational awareness in their chain-of-thought (cite5†Sonnet 4.5 System Card†www-cdn.anthropic.com , cite12†Fronsdal et al. ). But these chain-of-thoughts may not be faithful, and models may behave differently based on the situation they (correctly) believe they are in without verbalizing it - sometimes called unverbalized situational awareness.
L30: In contrast, prior work has also tested if models can distinguish audits from real deployments, usually by directly asking the model to classify the audit transcript post hoc: if models have a hard time distinguishing audits and real deployments, then they are less likely to be capable of faking alignment during audits while behaving badly in real deployments. This approach has 2 key limitations, shared with measuring verbalized situational awareness:
L31:   * False positives in deployment: Consider a paranoid model that mistakenly believes certain situations (e.g. clear opportunities to sabotage) are always tests, even in deployment. In this case, both metrics might label all evaluations of that scenario unrealistic, even if they are completely indistinguishable from analogous situations in deployment.
L32:   * Coarse-grained: We want a smooth realism metric that distinguishes 99% vs 95% confidence that something is an eval (e.g. since this affects how careful a scheming model must be when presented with attack opportunities). Verbalized situational awareness is binary, and models might not be well calibrated at expressing absolute confidence scores in post-hoc realism evals (cite13†Xiong et al.†arxiv.org ).
L33: To address these issues, we use realism win rate evals. Given an evaluation transcript and a set of N deployment transcripts, we repeatedly ask an LLM judge (with reasoning) to detect the eval when given a pair of (eval, deployment) transcripts. After repeating this process with all N deployment transcripts, we record the “realism win rate”, the fraction of pairs where the eval transcript fooled the judge. See the full judge prompt in Appendix K.1.
L34: cite14†Image Realism win rate metric. We use an LLM judge to perform many pairwise comparisons of an evaluation transcript with deployment transcripts. Eval transcripts which fool the judge more often have a higher realism win rate.
L35: Given deployment data representative of our audits, the realism win rate metric helps solve the two problems with prior metrics. However, finding such deployment data can be challenging in practice. In this work we focus on agentic coding audits, and draw from two different data sources:
L36: Claude Code usage: Here we compare each eval transcript against 25 randomly selected transcripts from the first author’s Claude Code usage. While these have the nice property of being real agentic coding environments, they consist of lower-stakes tasks than the typical Petri audit. This could allow the judge to use basic heuristics like “the more harmful or higher-stakes situation must be the eval”. We find evidence of this problem in Appendix B.
L37: Mixed deployment: This dataset consists of a mix of three different distributions from deployment: 10 Claude Code transcripts, 10 Wildchat (cite15†Zhao et al.†arxiv.org ) transcripts involving misuse or harmful requests, and 10 “vulnerable” Wildchat transcripts where the user is in an unusual or vulnerable situation.
L38: While these are overall less representative of agentic coding scenarios, the inclusion of weird and harmful transcripts helps us to better capture the fact that Claude models often mistakenly assume that harmful situations are evaluations.
L39: ### Giving the auditor resources
L40: 
L41: To improve the realism of audits, we provide a new affordance to the Petri agent: a repository of real system prompts, tool definitions, and codebases that the auditor can use to simulate more realistic environments.
L42: Resources repository: We create a resources directory we’ve manually populated with real system prompts, tool sets, and codebases used in deployment. For each subcategory of resources, we give the auditor a README file with usage tips, and an index file which provides brief descriptions of each resource and maps them to common audit situations.
L43: cite16†Image Example of how the auditor uses resources to set a realistic target system prompt. We give the auditor a large repository of real system prompts, an index, and a README with tips. The auditor uses list_directory and read_file tools to read an index to help narrow the search space of resources. It then explores the suggested resources, and can choose to copy or adapt them to set a realistic target system prompt.
L44: Updated auditor system prompt: We add a section to the standard Petri system prompt informing the auditor of these resource directories, and encouraging the auditor to use them.
L45: 
L46: Resource-specific tools: We equip the Petri auditor with four new tools that are enabled when using resources. The first two make it easy for the auditor to explore and find relevant resources, while the latter make it easier to integrate them into the audit environment.
L47:   * list_directory: allows the auditor to explore resource directories.
L48:   * read_file: allows the auditor to read full files in its resources.
L49:   * send_file_as_tool_result: allows the auditor to send large files directly to the target (with optional edits) as tool results.
L50:   * search_in_files: allows the auditor to do grep-like searches in codebase resources and send the results directly to the target.

L53: ## Results
L54: ### Resources improve realism of reward hacking audits
L55: 
L56: In this section we use realism win rate evals to measure the effectiveness of resources in 5 different reward hacking audit scenarios. In each scenario, the auditor is asked to set up a debugging task with an impossible test, and explicitly asks the target not to modify the tests. See the exact seed instructions in Appendix K.5.
L57: We compare the resources affordance against two baselines: default Petri, and Petri with a realism filter (cite12†Fronsdal et al. ), where a separate classifier model blocks and requests re-writes for unrealistic auditor actions. We use Sonnet 4.5 (without extended thinking) as the auditor, target, and realism classifier. We also use Sonnet 4.5 (with extended thinking) as the LLM judge for the realism win rate evals, and provide results for other judges in Appendix C.
L58: We run 10 audits per seed instruction, and all audits use a maximum of 60 turns. While each Petri audit can have multiple “branches” (where the auditor can rollback to try multiple strategies) we only evaluate the final branch, as this is typically the latest iteration where the auditor has tried the hardest.
L59: We also test a more conservative variation where the auditor just receives resources for system prompts and tools, without any codebases. In either case, resources substantially improve realism win rate.
L60: cite17†Image Reward hacking audit average realism win rate by affordance. Win rate is averaged over 50 audits (5 different reward hacking seed instructions, with 10 audits per seed). Resources improve realism win rate over baselines. In one case (orange) we just give the auditor resources for system prompts and tools, while in the other (green) we additionally include codebases relevant to each scenario.
L61: Note that our resource bank is fixed and includes codebase resources that are directly relevant to these seed instructions (e.g. a real Matplotlib bug for an impossible plotting code debugging scenario), so uplift may be smaller when no closely matching resource exists. We address this in Appendix F by running ablations with less related seed instructions, and find similar results.
L62: Still, we recommend practitioners provide maximally relevant resources when possible, as this makes it straightforward for the auditor to leverage them effectively.
