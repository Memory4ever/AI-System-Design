Abstract.
Memory disaggregation via Compute Express Link (CXL) enables multiple hosts to share remote memory, improving utilization for data-intensive workloads.
Today, virtual memory enables process-level isolation on a host and CXL enables host-level isolation.
This creates a critical security gap: the absence of process-level memory isolation in shared disaggregated memory.
We present Space-Control, a hardware-software co-design that provides fine-grained, process-level isolation for shared disaggregated memory.
Space-Control authenticates execution context in the hardware and enforces access control on every memory access and amortizes lookup times with a small cache.
Our design allows up to 127 processes running concurrently on 255 hosts to share memory with only 1.56% storage overhead.
In a gem5 + Structural Simulation Toolkit (SST) based CXL model, Space-Control incurs minimal performance overhead of 3.3%, making shared disaggregated memory isolation practical.
1. Introduction
The growing demand for memory in modern data-intensive applications has driven the industry toward memory disaggregation (Felten and Zahorjan, 1991).
Disaggregation decouples compute and memory resources and connects them via high-speed fabrics.
Standards such as the Compute Express Link (CXL) (Sharma, 2022; 14; 15; Jain et al., 2024a) enable multiple systems, called hosts, to access memory on a remote memory-only device.
This improves utilization and reduces redundancy (Li et al., 2023b).
The CXL 3.0 (14) standard supports memory sharing at the cache-line granularity across hosts for the first time, making it a promising foundation for large-scale deployments.
Current CXL-based sharing mechanisms provide only coarse-grained, host-level access control: once a host is authorized, all processes on that host can access the shared region.
This violates the principle of least privilege (Lampson, 1974).
The all-or-nothing model leaves intra-host isolation to the operating system (OS).
Since memory is shared across multiple hosts, there is no cross-host user or process visibility.
Stark et al. (Stark et al., 2023) call the coarse-grained sharing in CXL as “sledgehammer-level protections.”
When coupled with a compromised kernel (Google Inc., ; Kocher et al., 2019; Kim et al., 2014; Bains and Halbert, 2012), this gap can escalate privileges and access sensitive data, creating a significant security risk (Kommareddy et al., 2021).
Before discussing the problem in details, we first need to consider the characteristics of shared memory workloads.
Disaggregated memory workloads are an active research topic (MICRON, 2024; Huang et al., 2025).
These worloads partition their data across local and remote memory.
Although multiple hosts may map the same physical remote memory region via CXL, they are not necessarily accessing the same data within that region.
Therefore, for isolation, we need to guarantee fine-grained permissions for user-defined arbitrary memory ranges for the remote memory.
Tigon (Huang et al., 2025), a CXL-based key-value store software, optimizes fine-grained data movement and resource utilization in the remote memory across hosts.
The authors point out a lack of access control in CXL and implicitly assumed the existence of fine-grained permissions to enforce isolation across shared regions.
Beyond key-value stores, graph analytics is an another example where users share graphs or sub-graphs in the remote memory across hosts, each running a graph kernel.
This requires fine-grained authorization such that users on a host can read or update only its assigned partitions (e.g., specific compressed sparse row slices or property arrays) without exposing the rest of the graph.
Other examples include the sharing of machine learning model weights (especially in expert models (OpenAI, 2025)) across hosts to improve utilization and reduce redundancy.
Today, systems enforce such policies either at the OS level or at the software level, without hardware-backed guarantees.
This motivates us towards researching hardware-enforced isolation that remains effective even if the OS is compromised.
In principle, we need guarantees akin to confidential computing, namely, creating an enclave for isolation of the address space and independence from the OS.
In practice however, current Trusted Execution Environments (TEEs) are ill-suited to shared disaggregated memory as commercial TEE designs like Intel SGX (, 2015), Intel TDX (, 2022), AMD SEV (Kaplan et al., 2016), CXL-TEE (15, 14) etc. cannot share memory between enclaves (Yu et al., 2022; Xu et al., 2024).
Today’s TEEs have security monitors that operate only within a single host, with no cross-host coordination, making it challenging for existing TEE designs to securely share remote memory across hosts.
Furthermore, they introduce notable performance overheads, reduce deployment flexibility, and expand the trusted computing base (TCB) (Akram et al., 2021).
This leads us to the central research question in this paper:
“How can we ensure isolation in shared disaggregated memory
that enforces the principle of least privilege and operates
independently of the OS with minimal overhead?”
In this paper, we present a hardware-backed access control framework that enforces isolation defined by a process.
A process is the smallest OS abstraction that issues user-mode loads/stores (LD/ST) under its own distinct address space.
Further, our design ensures compatibility with the virtual memory infrastructure.
Across the ecosystem, existing access control mechanisms fail to provide the necessary granularity and trust guarantees for disaggregated environments.
The POSIX shared memory API (56) solved inter-process shared memory on a single host.
However, cross-host usergroups may differ, so POSIX shared memory does not address cross-host sharing.
Software-only approaches such as namespaces and cgroups (12) offer isolation, but requires trusting the OS for cross-host visibility. Hardware-only solutions like DeACT (Kommareddy et al., 2021) and the CXL specification support coarse-grained sharing (1 GiB and 256 MiB respectively), limiting flexibility.
Prior proposals based on capabilities, which guarantee isolation, argue for finer access-control at the object-level for CXL fabrics (Stark et al., 2023).
However, capability systems like CHERI demand pervasive CPU/ISA/compiler/OS changes (Watson et al., 2015; Woodruff et al., 2014; Bresniker et al., 2019).
The core difficulty is balancing fine-grained authorization with scalability and efficiency.
Prior works have emphasized horizontal access-control, i.e. host-level permissions (Kommareddy et al., 2021; 14), whereas disaggregated memory also needs vertical access-control, i.e. per-process or per-virtual machine across hosts.
Tagging every 4 KiB page of a 1 TiB memory region with permissions (2 bits) per host (up to 256) and per process or per-virtual machine (up to 128) permissions requires 2 TiB of metadata (200% overhead).
Therefore, naïve lookup table designs become infeasible, and permission checks risk becoming performance bottlenecks.
Prior research like Mondrian (Witchel et al., 2002) trades off storage overhead for higher lookup latency on a single host using sorted tables to solve this problem.
However, in shared disaggregated memory (SDM) each host’s permission table must be replicated for cross-host visibility.
Therefore, we require a solution that provides shared memory isolation without incurring prohibitive metadata or performance overhead.
We present Space-Control, a scalable access-control framework for isolation in shared disaggregated memory.
Space-Control registers and authenticates address spaces defined by a user process at the host using a secure process attribute context engine (SPACE), instead of the OS.
Further, we add a permission checker to enforces access-control on every LD/ST at the point of egress.
Finally, we leverage the under-utilized fabric manager (FM) in CXL for managing cryptographic keys and permissions.
Access control metadata is co-designed with the kernel to achieve scalability. This reduces the total storage overhead of prior approaches from 200% to a fixed 1.56% of the total memory capacity when 255 hosts share memory of 4 KiB pages across 127 process on each host.
Our design delivers hardware-backed isolation with space-efficient metadata, addressing both the flexibility and granularity requirements of the remote memory.
Evaluation on GAPBS (Beamer et al., 2017) shows a marginal 3.3% performance overhead.
The contributions of this paper are:
•
We identify a critical isolation gap in shared disaggregated memory (SDM).
While current systems provide process-level isolation (via the OS) and host-level isolation (via CXL), they lack process-level isolation for SDM.
•
We propose Space-Control, a system providing hardware-enforced, process-level isolation for SDM that remains confidential even if the OS is compromised.
This architecture includes a hardware validation module and an access-control permission checker.
•
We address metadata overhead through a hardware-software co-designed permissions management technique.
•
We present the hardware design of Space-Control and provide a quantitative evaluation of its performance and space overheads.

2. Problem Definition
2.1. Threat Model
Principle and Scope.
Space-Control’s trust model follows the principle of least privilege (Lampson, 1974; Saltzer and Schroeder, 1975). Only address spaces defined by a process, that require access to the remote memory, should be allowed to access the same.
We provide confidentiality to local and remote pages of such process’ data.
Further, we provide integrity to all remote pages and detect any intrusion by the OS.
System setting.
We consider a HPC-like deployment where several multi-tenant hosts share SDM via CXL.
Users directly interact with the host OS via user processes.
Applications interact with SDM through user processes that map regions (e.g., DAX).
Each process has both local (on-host) pages and remote (SDM) pages.
We do not support virtual machines.
Trusted.
We trust the user process (its code and keys) that is granted SDM access, and the additional hardware we propose.
We assume on-chip and CXL hardware to function correctly.
Untrusted.
The OS (including the kernel) is untrusted in the kernel mode (or S-mode).
Our only kernel change is a narrow extension that enables the OS to understand process contexts and SDM ranges; it contains no authorization logic.
If this change is absent, SDM remains unmapped and the hardware permission checker rejects all SDM requests.
Other user or kernel processes on the host may collude with the OS to break confidentiality.
Off-chip components such as local DRAM modules and other external devices are untrusted.
Attacker Capabilities.
We consider a powerful adversary capable of controlling the OS.
OS-level vulnerabilities can escalate privileges and override permissions (Kommareddy et al., 2021; Kocher et al., 2019; Lipp et al., 2018; Google Inc., ).
The attacker can manipulate page tables, virtual memory mappings, replay or forge identity, and invoke privileged instructions.
Physical attacks, denial-of-service and side-channels on the hardware are out of scope.
2.2. Requirements
Given the scope and the threat model, any given solution needs to have the following requirements:
R1
It should enforce access control per process and not per host, ensuring the principle of least privilege.
R2
The solution needs to operate independently of the OS, so that isolation remains intact even if the OS is compromised, thereby minimizing the TCB.
R3
The design must scale to large number of hosts and processes with low metadata footprint and small per-access overhead.
R4
Allow dynamic creation/teardown of shared memory ranges and policy changes across processes.
3. Background and Current Approaches
This section explains access-control on a single-host system and describes the missing gap in disaggregated memory systems.
Table 1 summarizes the related works in terms of the four requirements mentioned in §2.2.
On a single-host system, the virtual memory manages per-process page tables.
The hardware (TLB/MMU) enforces translation and per-page W/R/X permissions (Arpaci-Dusseau and Arpaci-Dusseau, 2018).
A process cannot access another’s pages unless they are explicitly shared.
Address space identifier (ASID; ARM) or process context identifier (PCID; X86) tags TLB entries to distinguish address spaces and reduce shootdowns.
They aid performance but do not provide authorization.
Intel’s PASID/SVA (53; Intel, ) binds I/O accelerators to a process’ virtual address space for device-initiated DMA via the IOMMU.
This is orthogonal to CPU-originated LD/ST via DAX.
OS-managed mechanisms such as Border-Control (Olson et al., 2015), MPK (Park et al., 2023) and ARM MTE (ARM, Technical report) provide intra-host memory protection but assume a trusted kernel. Mondrian memory protection defines domains as a set of processes with identical permissions, defined by the OS.
These domains are sorted and stored as separate entries on a permission table.
TEEs (, 2015; , 2009; , 2022; Kaplan et al., 2016) provide isolation and attestation, but are ill-suited for sharing across hosts (14, 15) and add significant overhead (Akram et al., 2021).

Disaggregated memory (Felten and Zahorjan, 1991) decouples compute from memory and lets hosts map remote ranges over a fabric (Aguilera et al., 2023).
The fabric manager (FM) manages the set of hosts sharing memory on a set of devices.
Prior efforts include OpenCAPI (IBM, 2014) and Gen-Z (Interconnect, 2017), but current deployments center on CXL (Sharma, 2022; 14; 15; Jain et al., 2024a; Li et al., 2023b).
The critical difference for our work is the translation and authorization path.
Gen-Z introduced a host-side zMMU and two-stage translation (virtual address (VA) →\!\to\! remote virtual address →\!\to\! physical address (PA)), which enabled designs like DeACT (Kommareddy et al., 2021) to decouple translation from access-control.
In contrast, CXL removes the host-side zMMU and reuses the CPU’s TLB to access remote memory directly.
With CXL 3.0, multiple hosts may share the same physical memory range (14) (called sharing).
However, authorization is host-level and coarse (dynamic capacity region granularity) under the FM. In practice, to avoid the OS zeroing-out the bits, an SDM range is mapped as a direct access (DAX) region, similar to the heterogeneous programming model (MICRON, 2024; Jain et al., 2024b).
Prior works (Kommareddy et al., 2021; Bresniker et al., 2019) either target the Gen-Z model or rely on a trusted OS for isolation (Shan et al., 2018).
CHERI-style capability (Watson et al., 2015; Woodruff et al., 2014; Bresniker et al., 2019) systems offer principled, fine-grained authority tracking (Stark et al., 2023), but adoption requires ISA/compiler/OS changes across all hosts.
CHERI uses 128 bit pointers to maintain capability per host, maintaining the metadata across 256 hosts take 12.5% more storage (256×1​b256\times 1b per 16 Bytes).
In addition, programs needs to be rewritten to understand capabilities-aware LD/ST instructions (Woodruff et al., 2014).
We instead design a process-level authorization path compatible with existing virtual memory infrastructure and CXL deployments.
4. Space-Control
Space-Control enforces per-process authorization (R1) for shared disaggregated memory outside the OS’ control (R2).
We achieve this by
(i) authenticating the currently executing process,
(ii) tagging its memory requests with a hardware-backed process identifier, and,
(iii) validating each SDM access against a permission table.
Space-Control introduces three key components:
(1)
Secure Process Attribute Context Engine (SPACE):
A lightweight hardware module that authenticates processes using hardware-rooted identity, defined by the hardware process context, i.e. reserved PCID/ASID, and, the pointer to the base of the page table (CR3/SATP/TTBR); referred to as BASE_P.
The engine monitors context switches and ensures that only verified contexts can access the SDM.
It offers minimal MMIO interface to the programmer.
In addition, it has logic for generating cryptographic labels, and, a counter.
(2)
Permission Table:
An array of permission entries that maps PA ranges; shared or exclusive; of the SDM to the set of authorized contexts.
Entries can be dynamically updated to satisfy R4.
(3)
Permission Checker:
An on-chip hardware unit placed after the last-level cache, before the local DRAM controller and the CXL downstream port, responsible for enforcing access control on each LD/ST. It is integrated into the memory access pipeline that actively validates each SDM request against the permission table.
Space-Control makes a key observation in existing works to, i.e. access control metadata increases to maintain each host’s processes that are allowed to access the remote memory (estimated to be 200% in the naïve approach; §1, 12.5% in CHERI; §3).
Therefore, we opt for a hardware-software co-design, explained in §4.2.2, to satisfy R3.
We minimally modify the kernel to reserve contiguous process context IDs (ASID/PCIDs (referred to a HWPID henceforth) instead of Linux PID) in the kernel for SDM processes.
These HWPIDs are assigned by the SPACE, instead of the OS.
The OS still remains untrusted as our correctness never depends on kernel behavior.
If the OS is unmodified or these extensions are absent, SDM cannot be mapped or accessed, and the permission checker will always reject any SDM traffic
The FM serves as a trusted entity for cryptographic keys and permissions management.
Its secret key (KF​MK_{FM}) is used to generate public authentication token labels (Le​x​pL_{exp}) for host process context validation.
Figure 1. Space-Control architecture providing process-level isolation for shared disaggregated memory.
With the addition of new trusted hardware, only the trusted process P1 on host3 is allowed access to the shared memory.
P2 (malicious, red) and P3 (untrusted, white) processes are not authorized to access the shared memory.
The same trusted hardware is also present in host0 and host1, where other trusted processes are allowed to access the shared memory.
In CXL however, any process authorized by the kernel can access that data.
Figure 1 shows the system-level architecture of Space-Control.
While green in general represents trusted components, the darker shade represents additional hardware.
The FM manages the permission table, stored in SDM.
The key difference between Space-Control and CXL is that, in our design, neither process P2 nor the kernel on host3 can access the remote memory, whereas in CXL any process authorized by the kernel can access that data.
Each host enforces access control through SPACE, which authenticates contexts using hardware-rooted identity.
The permission checker validates every memory request against the permission table before committing.
Only trusted contexts with legitimate permissions can issue LD/ST, while unauthorized processes are blocked, ensuring OS-independent security.
4.1. Principle of Operation
Now that we have given an overview of the design, we explain the work flow in three distinct phases:
(a) process creation,
(b) runtime protection, and,
(c) dynamic updates.
4.1.1. Process Creation
Figure 2. Process creation and permission grant workflow in Space-Control.
A new process requests access to SDM, which proposes an entry to the metadata region.
The FM is automatically notified and decides approval, commits the proposed entry to the table, and issues Le​x​pL_{exp}.
Figure 2 illustrates the process creation and permission request workflow in Space-Control.
Space-Control scopes to protect user processes to satisfy R1.
The user registers their process as trusted via SPACE hardware instead of the OS, and, creates an entry in the permission table to ensure permission enforcement.
Action 1 requests a range of memory to be mapped into a trusted process’ address space, running on the it​hi^{th} host.
The user is responsible for requesting the right permissions.
This can be achieved either using a middleware or an upper layer protocol as mentioned by prior works (Jain et al., 2024b).
SPACE maintains a list of free HWPIDs assigned via an MMIO doorbell (GET_NEXT_PID()).
The system-level driver assigns a HWPID from the free list. This breaks the dependence on the OS for a process identifier (R2).
The permission table that maintains each permission entry is stored in the SDM.
A new entry (entry_t) is written into the proposed update section of the permission table directly (Action 2).
The FM is automatically notified about the update, and decides whether to approve the request.
If the entry is approved, the FM commits the entry (Action 3) into the table.
The FM immediately generates a cryptographic public label (Le​x​pL_{exp}) using its private key (KFM) for authentication and stores it into the permission table (Action 5).
The FM automatically optimizes the permission entry if entries’ ranges overlap.
In addition, it responds to the host with the public label (Action 6), which is intercepted by SPACE for cryptographic label comparison.
The user process is now assumed to be trusted and the execution continues.
4.1.2. Runtime Protection
Figure 3. Flow of remote memory access as a load/store (LD/ST) of a virtual address (VA) in Space-Control.
SPACE validates the context, and the permission checker enforces isolation.
We now have a registered process, which we consider trusted.
However, multi-tenant OS has other processes running in the system.
Therefore, we need to validate our trusted process at every context switch to maintain R1.
Figure 3 depicts the runtime protections provided by Space-Control.
When a new process is context switched (Action 1), the SPACE logic, implemented in a μ\muSequencer, automatically reads the BASE_P (CR3/SATP/TTBR) and the HWPID (pcid/ASID), which defines the current process’ context.
Based on the current context, the trusted user process calls MMIO doorbell ARM_LABEL to generate a host-side label (Lh​o​s​tL_{host}) from the user-space.
SPACE generates Lh​o​s​tL_{host} iff ARM_LABEL is invoked from user-space eliminating the possibility of the kernel falsely trying to validate a different context.
Lh​o​s​tL_{host} is loaded into a shadow register called the label register (Action 2).
A context is validated if the current label Lh​o​s​tL_{host} matches with the public label from the FM i.e. Le​x​pL_{exp}.
The CPU core has a hierarchical, hardware-enforced CPU privilege mechanism called protection rings (Schroeder and Saltzer, 1972; Karger and Herbert, 1984).
These are used to restrict access protection rings for machine, hypervisor, supervisor (OS/kernel) and user-level program (Akram, 2023).
To avoid OS traps, kernel isolation, and stale labels, the shadow register is automatically unset if the core’s protection ring is anything other than the user-space.
For any trusted context, all PA (local or remote) generated by the same is extended to tag the HWPID bits.
We call these HWPID bits the authentication bits (A-bits).
Action 4 shows LD/ST instructions. The permission checker checks the A-bits for all LD/ST.
SDM LD/ST always need to have the A-bits set (Action 5).
To validate whether the given context has permissions to access the PA, a permission request (Action 6) along with the LD/ST (Action 7) is sent to the SDM.
The permission response has a range and the HWPIDs of authenticated processes.
When both responses arrive (Action 8 and Action 9), permission checks are enforced based on the LD/ST address and the tagged A-bits (Action 10).
An interrupt is generated if there is an access violation.
To ensure local memory pages of the trusted process are confidential at all times, a memory encryption engine is used.
The A-bits of a validated context are always tagged, which cannot be forged by the OS. Even if a malicious OS tampers with the trusted process’s page-table entries, any data it can exfiltrate from local memory is ciphertext, thus maintaining confidentiality.
4.1.3. Revocation and Update Propagation
We rely on CXL’s back invalidates (issued via BISnp) to propagate updates to the permission table.
When an update is committed to the table by the FM, every host automatically receives a BISnp, ensuring that the permission is invalid even if the entry is cached in the permission cache.
The FM updates the Le​x​pL_{exp} for the same host, ensuring global transparency and satisfying R4 of dynamically updating permissions.
The driver is responsible for calling SPACE doorbells for cleaning up HWPIDs.
Permission entries with no hosts are automatically cleaned up by the FM.
4.2. Space-Control Components
We now explain each component within the workflow mentioned in §4.1, describing their individual microarchitectures.
4.2.1. Secure Process Attribute Context Engine (SPACE)
SPACE, shown in Figure 4, is the hardware root of trust for process authentication.
It binds a process context using hardware-rooted identity (HWPID, BASE_P).
It stores the Le​x​pL_{exp} and a list of free HWPIDs.
SPACE ensures that only processes explicitly authorized by the FM can access SDM.
It has a μ\muSequencer, that monitors context switches and generates cryptographic labels.
Further, provides MMIO doorbells for the OS system to interact.
Figure 4. The microarchitecture of the SPACE.
It stores the host’s secret key (Kh​o​s​tK_{host}), FM’s public label (Le​x​pL_{exp}) and a free HWPID list.
There is additional logic to generate Lh​o​s​tL_{host}.
Further, SPACE provides minimal MMIO doorbells available to the OS for HWPID management.
To establish context validation, Space-Control uses two complementary labels:
(a) the FM-issued public label (Le​x​pL_{exp}), and
(b) the SPACE generated local context label (Lh​o​s​tL_{host}).
These labels are generated using standard MAC primitive (e.g. HMAC-SHA-256 (Krawczyk et al., 1997; Nyström, 2005) or AES-CMAC (Daemen and Rijmen, 1998)).
There are hardware implementation of such algorithms (Juliato and Gebotys, 2011).
During the process creation phase (§4.1.1), the FM generates Le​x​pL_{exp} that acts as an authorization token that binds a process (on a specific host) to the memory range(s) it may access.
Conceptually,
(1)
Le​x​p=M​A​CKF​M​(h​o​s​t​_​i​d,H​W​P​I​D,B​A​S​E​_​P,r​a​n​g​e)L_{exp}=MAC_{K_{FM}}(host\_id,HWPID,BASE\_P,range)
Where KF​MK_{FM} is the FM’s secret key.
SPACE stores the authorization label for subsequent checks.
On the other hand, the SPACE-generated host-side label Lh​o​s​tL_{host} is generated and stored in the label register iff the authorized user-space process invokes ARM_LABEL at a context switch (§4.1.2).
Lh​o​s​tL_{host} represents the identity of the process currently running on that core.
Freshness of Lh​o​s​tL_{host} is ensured via a monotonic counter. Lh​o​s​tL_{host} is given by:
(2)
Lh​o​s​t=M​A​CKh​o​s​t​(B​A​S​E​_​P,H​W​P​I​D,c​t​r)L_{host}=MAC_{K_{host}}(BASE\_P,HWPID,ctr)
Where Kh​o​s​tK_{host} is the host’s secret key known to the SPACE, and ctr is the monotonic counter that advances on each context activation per core.
In summary, on a context switch, SPACE:
(1)
Derives the current process identity, or the context, from the active address-space root (HWPID, BASE_P).
(2)
Generates Lh​o​s​tL_{host} and stores it in the label register for that specific core.
(3)
Compares the two labels to match the predicate.
If authentication succeeds, each LD/ST issued by the active context is marked as authenticated by tagging the A-bits.
This allows per-access permission enforcement downstream, thus achieveing R1, i.e. adhering to the principle of least privileges. This inherently also prevents synonyms in the memory.
SPACE satisfies R2, i.e. ensures OS independence.
All identity construction and label checks occur in trusted hardware and the OS cannot mint identities or forge labels.
The monotonic counter ensures that Lh​o​s​tL_{host} is tied to exactly one context activation, which prevents replay attacks (Wei and Pu, 2005).
Further, this ensures the principle of least privilege as authorization tokens bind contexts to specific SDM ranges.

The permission table starts at an offset 128 B (cache-line aligned).
It stores sorted permission entries (entry_t) keyed by start address.
4.2.2. Permission Table
The permission table, shown in Figure 5, stores access control metadata per process per host as entries.
Each entry has a start, a size, and, permission attributes per process per host.
It functions as an optimized reverse mapping table, inspired by directory-based caching protocols, that maps a PA to a host and a process within the host.
The metadata section of the table allows hosts to propose new updates to the table.
The rest of the table with all the permission entries is only accessible to the FM.
The organization of the permission table is central to ensuring scalability and satisfying requirement R3.
The primary challenge is maintaining unique pairs of (host, process identifier) across all participating hosts.
To solve this, we maintain two copies of the HWPIDs authorized to access the SDM. The local copy, denoted by H​W​P​I​Dl​o​c​a​lHWPID_{local}, contains the HWPIDs assigned to trusted processes on a given host.
The permission table copy, H​W​P​I​Dg​l​o​b​a​lHWPID_{global}, represents the union of all trusted processes across all hosts and is defined as H​W​P​I​Dg​l​o​b​a​l=⋃iH​W​P​I​Dl​o​c​a​liHWPID_{global}=\bigcup_{i}HWPID_{local_{i}}.
The intersection H​W​P​I​Dl​o​c​a​l​⋂H​W​P​I​Dg​l​o​b​a​lHWPID_{local}\bigcap HWPID_{global} validates the right context at the right host.
A process on a host can request memory range via a request call.
The call writes a new entry to the proposed update section.
The FM commits the entry into the table iff permission is granted.
The permission table is organized as a sorted table based on the start addresses.
This is similar to prior works like Mondrian (Witchel et al., 2002), where each domain has a sorted segment table.
This allows flexibility in defining protections for arbitrary memory ranges instead of fixed page lengths (R1).
4.2.3. Permission Checker
Figure 6. The microarchitecture of the permission checker.
The diagram shows the flow of a 41 bit PA (48 bit extended PA).
While every SDM LD/ST is validated against the permission table, local pages are encrypted to ensure confidentiality.
The permission checker, shown in Figure 6 is designed in tandem with the previous components.
It is placed on-chip of a host, after the last-level cache. Every LD/ST of a trusted process has the A-bits tagged on to the PA.
H​W​P​I​Dl​o​c​a​lHWPID_{local}, i.e. the list of trusted processes on a host, is implemented as a bit vector, and stored in the permission checker.
The checker validates whether the trusted process’ tagged addresses have access rights to a given PA, thus maintaining R1 and R2 at all times.
At runtime, every SDM LD/ST is associated with a corresponding permission entry in the table that encodes the range and permission attributes.
The checker fetches the same entry from the permission table.
Homonyms never appear in our design as PA are used for range checks.
The lookup latency is proportional to the number of permission entries.
To amortize the lookup latency and avoid round-trips on every remote memory reference, we add a small fully-associative permission cache.
To track each outgoing request and its corresponding permission, we use a limited number of permission status holding registers.
Permissions are enforced (permission attributes and HWPIDs) at the response-end, where the response of a remote memory request is stalled via buffering until all its corresponding permission responses arrive.
This ensures all LD/ST are committed in-order.
Finally, we ensure the confidentiality of local pages.
A trusted process’ local memory addresses will have the A-bits tagged.
We add a memory encryption engine for encrypting these pages using the host’s private key (Kh​o​s​tK_{host}).
The design therefore provides confidentiality for a trusted process’s local data.
4.2.4. Extensions to the Fabric Manager (FM)
The FM serves as the trusted coordination point for Space-Control.
Today, the only role of the FM is to set up the hardware tables for access control (§3).
We extend its role to manage the permission table in the SDM, and, generate public labels for context authentication for each host.
Upon granting access to a process on a host, the FM issues a public label (Le​x​pL_{exp}) that cryptographically binds a context (HWPID, BASE_P) to its permitted memory ranges.
The label is stored in the label section of the metadata and the entry, which has a defined range, is committed to the permission table.
In addition, the FM is also responsible for optimizing the permission table to minimize the total number of entries.
5. Discussion
In this section, we show the security analysis to validate our claims and justify our design choices.
5.1. Security Analysis
Our claim is this paper is that we guarantee the confidentiality of trusted context’s data and trust the disaggregation hardware for the availability.
5.1.1. Malicious host processes
The host can spawn multiple processes, which tries to access the SDM.
Space-Control validates the trusted process’ context via the SPACE.
The context (HWPID, BASE_P) cannot be forged by any other process.
Any LD/ST generated by a trusted context is further checked by the permission checker.
The checker raises a fault when a non-trusted process (without the tagged A-bits) tries to access the remote memory region directly.
5.1.2. Compromised system software
We assume a strong threat model in which the OS may collude with untrusted processes to violate the confidentiality of a trusted process’s local and remote data.
We therefore use hardware-defined context (HWPID, BASE_P).
This prevents the OS from forging context labels.
Although the OS can still modify page tables, such manipulation does not compromise remote memory.
If the kernel maps the SDM region into an untrusted process’s address space, SPACE rejects the access as authentication fails, and the permission checker blocks any unauthorized LD/ST.
A stronger threat arises when the kernel attempts to compromise the local memory confidentiality of a trusted process.
Since local memory is untrusted in our model, the kernel may remap the page tables of a trusted process and a malicious process to the same physical memory region.
The trusted process remains unaware of the remapping and continues to use its local pages, while the malicious process gains read access to those same pages, violating confidentiality.
To prevent this attack, Space-Control employs a memory encryption engine that encrypts all local memory pages belonging to trusted contexts, identified by their tagged A-bits.
This ensures confidentiality even if the OS aliases page tables.
However, while encrypted data prevents unauthorized reads, a malicious process could still overwrite ciphertext, affecting integrity.
When such writes are detected, Space-Control identifies the presence of compromised system software, satisfying our target threat model from §2.1.
5.1.3. Malicious DMA devices
Space-Control assumes that SDM is accessed primarily via CPU LD/ST operations using /dev/dax (MICRON, 2024).
Unlike system DRAM, a DAX region is not part of the system memory map.
It is exposed as a character device and mapped into a processes’ virtual address space.
Consequently, DMA-capable devices, such as GPUs and other accelerators, cannot directly access this region without explicit peer-to-peer mappings.
This distinction reinforces the gap we target, i.e., existing PASID-based Shared Virtual Addressing (SVA) mechanisms only apply to device-initiated DMA and do not cover CPU-originated accesses to SDM.
Therefore, hardware enforcement at the CPU egress point remains essential for guaranteeing process-level isolation in scenarios where the OS cannot be trusted.
5.2. Design Choices and Limitations
Space-Control introduces additional wiring overhead by tagging PA with the A-bits.
The design is inspired by the C-Bit of AMDSEV (Kaplan et al., 2016).
We justify our design choice of extending the PA as today’s state-of-the-art architectures uses up to 57 out of 64 bits (, 2017; Ghiti, 2021).
This allows flexibility of using the remaining unused bits to tag the address space.
Intel hardware already adds support to extend the upper 7 bits of the physical addresses in the kernel using Linear Address Masking (Jonathan Corbet, 2022).
We allow up to 127 processes per host to ensure 64 bits address compatibility.
For simplicity, we choose to place the HWPID tag bits into the most significant bits of the address, which does not cause conflicts with the existing wiring for the TLB, the caches and ensures CXL compatibility.
An alternate method of protecting memory was via a reverse mapping table (P​A→(V​A,H​W​P​I​D)PA\rightarrow(VA,HWPID)) per host, similar to AMDSEV (Kaplan et al., 2016).
Such tables are also popular to identify hot cache lines for page migration in CXL-related prior works (Li et al., 2023a).
A reverse mapping from PA to (VA, PID) allows the hardware to infer which process owns a given physical page without modifying the address format.
However, given the current programming model for SDM, the base pointer to the mmap region is fixed and addresses are accessed based on offsets.
We chose to adopt a simple permission table where the mapping from PA to (host, (HWPID, BASE_P)) is enough to ensure that the OS cannot modify the page table to remap the SDM.
Based on our threat model, our design guarantees confidentiality to the data at all times and integrity to the data in the SDM.
However, we rely on the CXL hardware to function correctly and provide availability.
This distinguishes Space-Control from a TEE.
If the trusted process is compromised at runtime, Space-Control fails both confidentiality and integrity guarantees.

This experiment establishes the cxl baseline, modeled after CXL 3.0, and quantifies Space-Control’s end-to-end overhead in the best-case sharing layout, when a single permission entry (space-control-1e) spanning the SDM region.
This setting isolates the intrinsic cost of per-access authentication and permission checking from metadata fragmentation effects, and it lets us evaluate how the egress checker scales as more hosts participate.
For each local access we verify context, check for the A-bits on the PA, and, encrypt the pages.
For each SDM access we consult the permission table for the current context (HWPID, BASE_P).
We run GAPBS kernels while scaling the number of hosts accessing the same SDM region from 1 to 8 in powers of two.
We use four representative kernels: pr, bfs, bc, tc; ordered from more regular to more random access patterns, and report CPI normalized to the cxl baseline (no checks).
The single-entry configuration keeps the permission lookup path constant, so any change in CPI reflects the rate of permission lookups rather than longer lookup latency.

Figure 7(a) shows the CPI for the four workloads when the number of systems are scaled.
Space-Control imposes a small overhead at one host (7.3% on average than cxl) that grows sub-linearly to 12.1% at eight hosts.
This trend demonstrates that the permission checker scales without becoming a bottleneck, i.e. adding hosts increases the number of permission lookups, but the pipeline and caches keep lookup latency bounded.

The key takeaway for deployment is that when tenants map few, contiguous SDM ranges, Space-Control’s cost is predictable even as tenancy scales.

7.1.2. Sensitivity to Permission Table Fragmentation
Having established the single-entry baseline, we now stress the design with worst-case fragmentation to expose the cost of the sorted permission table when every access requires a deeper lookup.
This experiment isolates the central trade-off as we replace the storage overhead of flat tables with lower metadata but higher lookup time.
We then investigate the lookup overhead gets when the permission table is maximally deep.
Concretely, we compare the best case (a single permission entry spanning the SDM, space-control-1e) to the worst case where every 4 KiB range has its own distinct entry (wc), so each SDM reference can trigger a binary search in a large table.
We repeat the baseline experiment under this worst-case layout and report normalized CPI alongside two indicators of lookup pressure: the binary-search occupancy (how many table probes per lookup) and the permission lookups per kilo-instructions (PLPKI).
This framing makes the mechanism’s behavior transparent as
(a) CPI reflects end-to-end impact,
(b) occupancy shows how deep the table is exercised, and,
(c) PLPKI captures how often the checker is invoked by the workload.

Together, these results bound the upper cost of fine-grained permissions and show how to steer deployments toward the single-entry or low-fragmentation regime, where Space-Control remains predictable and modest.

To understand the source of the overhead, we instrument the permission checker pipeline and attribute runtime to three components: (a) permission request creation, (b) permission lookup latency, and (c) enforcement latency, i.e. the time a LD/ST response is stalled until all corresponding permission entries arrive.
Creation is largely depended on the circuit design and is small; the other two depend on the table organization and on how many lookups each workload triggers, tying this analysis directly to §7.1.2’s fragmentation results.
Figure 11(b) shows that enforcement stalls dominate the slowdown (99.95% in our configuration), while A-bit comparisons are negligible (0.003%).
Intuitively, irregular workloads and fragmented tables inflate both lookup depth and lookup rate, which lengthens stalls because more responses must be matched with more (and deeper) permission entries before commit.
7.1.5. Performance Enforcement Latency
§7.1.4 shows enforcing permissions impacts the response path the most.
We issue LD/ST and permission requests out-of-order, but a LD/ST response cannot commit until all of its corresponding permission entries have arrived.
We call the resulting wait time as the enforcement or the stalling latency.
Figure 11(a) reports the average tail latency across workloads.
It reflects the time the pipeline spends buffering responses to preserve in-order architectural commit while Space-Control verifies access rights.

The line represents the PDF of the latency distribution.
Consistent with §7.1.2, more random access patterns yield longer stalls because they trigger more and deeper permission lookups.
The histograms in Figure 12 make this visible, where kernels like tc and bc exhibit heavier stalls than pr.
The takeaway is that enforcement latency is a lookup-dominated cost; reducing lookup frequency (fewer, coarser ranges) or amortizing lookups (a small permission cache) directly shortens the stall time.
This sets up §7.1.6, where we show that modest caching materially reduces enforcement time and restores end-to-end responsiveness.
7.1.6. Performance Cache Efficacy
((a)) Reported permission cache miss ratio with increasing permission cache size in powers of two.
((b)) Reported CPI of the system with increasing number of cache sizes. Numbers are normalized to a Space-Control system with complete memory fragmentation without caching.
Figure 13. Measured performance efficacy of Space-Control with a permission cache. All systems are assumed to be completely fragmented, as mentioned in §7.1.2.
The previous sections showed that Space-Control’s overhead is lookup-driven (§7.1.2) and expresses as enforcement stalls (§7.1.5 and §7.1.4).
A small permission cache amortizes repeated lookups as it reduces PLPKI and binary-search depth, which shortens enforcement stall latency and restores throughput (§7.1.3).
We sweep cache sizes from 0.5 KiB (8 entries) to 64 KiB (1024 entries) and report miss ratio (Figure 13(a)) and CPI normalized to the uncached worst-case fragmentation (Figure 13(b)).
In this stress setting, where there are distinct entry per 4 KiB range, the cache targets the mechanism’s worst behavior (many deep lookups).
There is a pronounced elbow in the cache-benefit curve: a modest permission cache delivers most of the gain.
With just 2 KiB of cache, the hit rate reaches 99.9% and the CPI overhead improves by 2.3×\times over the uncached Space-Control configuration on GAPBS.
The sharp drop in miss ratio from 1 KiB to 2 KiB stems from the way the sorted permission table is searched: a binary search repeatedly revisits a small set of internal decision nodes across lookups, while the leaf (the final permission entry for the specific range) is the part most likely to be uncached.
For a 16 GiB shared memory, the binary search touches at most 24 nodes at worst.
A 2 KiB cache holds 32 entries, which exceeds the depth and keeps most internal nodes resident.
Only the leaf entries tends to miss.
This scaling intuition generalizes.
For 1 TiB shared memory (up to l​g​(240)=40lg(2^{40})=40 probes), 4 KiB cache (64 entries) exceeds the worst-case search depth, amortizing the lookup cost.
This makes cache auto-tuning straightforward, i.e. choose a capacity that meets or slightly exceeds l​g​(table size)lg(\text{table size}).
Compared to the CXL baseline, a 16 KiB cache leaves only 3.3% marginal performance overhead.
Consistent with our previous results, caching also trims enforcement stalls, and benefits show diminishing returns beyond 4 KiB in the worst-case fragmentation for most workloads.
A small permission cache converts Space-Control from lookup-bound and stall-heavy to data-dominant, aligning with the design flow we established so far.
7.1.7. Permission Revocation
Updating permissions follows the CXL’s back invalidate snoop (BISnp) protocol (14).
When a host updates the permission table via a new entry and the entry is approved and pushed into the table by the FM, a CXL BISnp is sent on the network.
Permission caches on hosts caching that entry will automatically invalidate the permission entry from its own cache.
The latency of performing a permission revocation is the same as CXL’s BISnp latency.
One limitation of permission revocation is that it fails to prevent on-flight instructions getting committed.
While Space-Control ensures response-side permission checks, meaning that access control is done after receiving responses instead of apriori approvals, there still exists a tiny window where an attacker can read (not write) data from the SDM.
This problem however is the CXL’s cache coherence problem (14; Jain et al., 2024b), which is orthogonal to our work.
7.2. Hardware Overhead
In Space-Control, a memory range of an entry can be of any arbitrary length.
For practicality and future-proofing, we limit the minimum length to be 4 KiB, the same as the smallest unit of an OS-level page size.
This implies that in the worst case where every 4 KiB page of the SDM will have a 64 Byte entry, resulting in a maximum of 1.56% overhead.
We use 32 permission miss status holding registers to keep track of all the permission entry misses.
The response buffer for permission enforcement holds up to 32 responses.
This totals 4 KiB of additional SRAM storage.
The cryptographic engine follows a similar implementation to prior works (Juliato and Gebotys, 2011).
We add two 64-bit shadow registers label and authentication result at the CPU.
SPACE uses minimal logic and wiring overhead for comparing contexts and generating labels.
The total SRAM storage needed to maintain the key (64 bits), counter (64 bits), free HWPID list (128 entries) and public label, i.e. Le​x​pL_{exp} (64 bits) is 1.048 KiB.
The permission checker uses five comparators to generate permission requests and enforce permissions.

8. Related Works
Memory disaggregation.
§3 gives a brief introduction to disaggregated memory.
Prior works like DeACT (Kommareddy et al., 2021) relies on Gen-Z’s host-side zMMU (Interconnect, 2017) and two-stage translation to decouple address translation from permission checks.
CXL removes the host zMMU and reuses the CPU’s TLB (14), so Space-Control enforces authorization after the last-level cache.
RDMA-based works like (Wang et al., 2025) is orthogonal to CXL.
OS-managed mechanisms.
OS-managed protections via namespaces and cgroups (12), MPK and ARM MTE provide intra-host protection but assume a trusted kernel.
LegoOS scales disaggregation but also trusts the OS for isolation.
Space-Control removes the OS from the enforcement path (§3). (Park et al., 2023; ARM, Technical report; Shan et al., 2018)
Border Control (Olson et al., 2015) sandboxes accelerators with page-level checks under a trusted OS.
Space-Control is inspired by this work and builds on this insight by treating untrusted hosts analogous to untrusted accelerators, enforcing access control through a hardware permission checker integrated into the memory access path.
Domain/capability designs.
Mondrian (Witchel et al., 2002; Witchel et al., 2005) introduces the concept of domains and uses a sorted protection table to trade-off storage for higher lookup latency. Space-Control adopts the sorted-table idea but enforces at the CPU egress with process-level isolation and an untrusted OS (§4).
CHERI-style capability systems offer principled fine-grained authority but require pervasive ISA/compiler/OS changes (Woodruff et al., 2014; Stark et al., 2023; Watson et al., 2015).
Bresniker et al. (Bresniker et al., 2019) proposed the addition of memory-side capability check to extend CHERI to the disaggregated memory space.
The memory-side capability check is for address range check per process per host, creating a high metadata overhead and restricting scalability.
Furthermore, it requires a trusted OS for process coordination. We target deployability on existing CPUs and CXL fabrics using simple techniques like LD_PRELOAD.
TEEs and enclave models.
TEEs (, 2015; , 2022; Kaplan et al., 2016; Yu et al., 2022) provide isolation and attestation but are ill-suited for multi-host shared ranges (14, 15) and add non-trivial overhead (Akram et al., 2021).
Sharing memory enclaves on a single host is an active research topic (Yu et al., 2022; Xu et al., 2024), however commercially available TEEs are yet to adopt it.
Minerva (Alwadi et al., 2022) is an extension to the TEE design for disaggregated memory, where the authors made a fault-tolerant metadata management scheme for disaggregated memory.
ShieldCXL (Choi et al., 2025) proposes an oblivious TEE for CXL systems.
Li et al. (Li et al., 2025) proposes an efficient technique to encrypt CXL flits for designing a TEE on a CXL system.
Space-Control enforces authorization without enclaves.
9. Conclusion
This work addresses a critical gap in disaggregated memory systems: the lack of process-level isolation in shared disaggregated memory.
Space-Control provides a scalable hardware-software co-design that enforces fine-grained access control without relying on the OS.
The design remains fully compatible with existing virtual memory abstractions.
Our design uses a space-efficient metadata structure and leverages the CXL fabric manager to scale across many hosts and processes, incurring only 1.56% memory overhead and 3.3% performance overhead.
By reconciling strong security with system scalability, Space-Control establishes a practical foundation for secure disaggregated memory.
For future work, we plan on extending Space-Control into the TEE realm with shared enclaves across hosts, and providing availability at all times.

Appendix A Address Translation and Access Control in CXL
CXL defines hosts and devices.
Hosts are compute nodes with or without local memory.
The devices on the other hand, are memory devices.
There is a global address space, where devices are mapped into.
Hosts may choose to map a part of their own address space into the global address space.
The global address space is one contiguous address space.
Until CXL 2.0, there was no notion of sharing memory ranges among hosts.
To facilitate memory sharing, additional hardware is added.
The fabric manager (FM) is responsible for binding hosts and devices to the global address space.
A Global Fabric Attached Memory (G-FAM) is a collection of hosts and devices in one single contiguous global physical address space.
CXL switches are responsible for routing a given request to its corresponding device.
Hosts can have both local and remote memory ranges.
Local ranges are not exposed to the G-FAM, therefore, not appearing in the global address space.
The remote memory addresses reside outside the host.
Note that both of these addresses are physical addresses.
To distinguish between host’s physical addresses and a device’s physical address, the terminology defines host physical address (HPA) and device physical address (DPA).
A host is assigned a source port ID (SPID) and a device is assigned a device port ID (DPID).
New tables are added to the CXL switch and the G-FAM device to enable sharing.
Fabric address segment table (FAST) and the Interleave DPID table (IDT) are added to a CXL switch.
On the other hand, G-FAM devices (GFD) decoder table and the SPID Access
Table (SAT) are added to the G-FAM device.
In CXL terminology, devices are referred to as dynamic capacity devices (DCD).
A DCD is divided into multiple regions called DCD region of size 256 MiB [14].
Access permissions for a host is determined at the granularity of a DCD region.
Figure 15. Address translation and access control in CXL.
The figure defines a G-FAM system with two hosts and n devices.
Figure 15 shows the journey of a virtual address generated at a host to its corresponding device.
Action 1 in the figure shows the generation of virtual address (VA) at the host.
The host translates this VA to a host physical address (HPA) using the host’s MMU/TLB and send the HPA as a request address on a CXL flit to the outgoing CXL downstream port.
The first component a CXL flit encounters is a CXL router.
The router is responsible for appending the SPID and the DPID of the address into the request flit.
Action 3 shows that forwarding of the request flit to the FAST table to determine the DPID.
The request is further sent to the IDT to determine if the address is interleaved into multiple GFDs.
If a valid destination does not exist for the DPID, the host is notified and the flit is dropped.
The appended request can be seen in Action 4.
The CXL router then forwards this request to the GFD (Action 5).
The tables for one set of G-FAM is responsible for checking access permission for a given address on a flit for the corresponding DPID and the SPID.
The incoming request flit address is looked up in the GFD table (Action 6).
Once the correct GFD is decoded, the request is then forwarded to the SAT.
The GFD is also responsible for translating the HPA to its corresponding device physical address (DPA).
The SAT table hosts access permission for a memory group.
The table is querried with the SPID to determine whether the given host has permissions for a given memory group.
In case the flit is a write on a HPA, a Back-Invalidate Snoop (BISnp) is sent back to all the hosts sharing that HPA (Action 7).
