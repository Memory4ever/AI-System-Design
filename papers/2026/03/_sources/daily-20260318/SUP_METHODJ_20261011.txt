L158: ### 5.2. Area-Performance Trade-off Optimization
L159: Compressor trade-offs: The compressor consists of multi-lane caches, which have two knobs: per-lane cache depth and the number of lanes. Figure cite73†4 plots the local cache hit rate versus its depth during the encoding phase. A depth of 8 entries per lane achieves over 90% average hit rate for all tested models. Given the diminishing returns of larger sizes, we adopt 8-entry caches in each lane. Next, we analyze the total cache size to optimize codebook creation latency.
L160: Figure cite74†5 shows this trade-off for the codebook generation latency with 512 activations. While a single lane with depth 4 is area-efficient, it requires 788 $\mathrm{ns}$ to complete at 1 $\mathrm{GHz}$. At the other extreme, 32 lanes with depth 16 reduce the latency to 17 $\mathrm{ns}$, but the total cache size grows to 4 $\mathrm{KiB}$. We select a balanced design point with 10 lanes and depth 8, which achieves codebook creation in about 55 $\mathrm{ns}$ with only 0.625 $\mathrm{KiB}$ of cache.
L161: cite75†Image: Refer to caption Figure 5. Codebook generation latency vs. cache size with 512 activations in BF16.
L162: Decompressor tradeoffs: To analyze the latency–area trade-offs in the decompression unit, we implemented it using different multi-stage LUTs configurations. As shown in Figure cite76†6 , a 4-stage LUT decoder indexed by 8/16/24/32-bit prefixes achieves an average latency of 11.6 $\mathrm{ns}$ with an area of 98.5 ${\mathrm{\SIUnitSymbolMicro m}}^{2}$.
L163: For comparison, a single 32-bit LUT table achieves a slightly lower latency of 10 $\mathrm{ns}$ but requires 157.6 ${\mathrm{\SIUnitSymbolMicro m}}^{2}$ area, making it less area-efficient. The most optimistic case, required to saturate the $100~Gbps$ link, involves $10$ compressed values (each $10$ bits: $2$-bit codeword + $1$-bit sign + $7$-bit mantissa).
L164: Thus, ten decode lanes we searched based on Figure cite74†5 are sufficient to sustain the full link bandwidth, distributing incoming flits in a round-robin manner. This design balances throughput and cost, delivering near line-rate performance with modest overhead.

L166: ### 5.3. Communication and End-to-End Execution Time Evaluation
L167: This section evaluates the BF16 exponent compression ratio (CR) for the Jamba, Zamba, and Qwen models. As shown in Table cite78†2 , LEXI yields the highest CR $\approx 3.1\times$, by leveraging per-layer frequency distribution. This significantly surpasses base-delta-immediate (BDI) compression (cite79†Pekhimenko et al., 2012 ) ($2.40\times$), which utilizes micro-local value correlation via $\mathbf{3}$-bit delta encoding.
L168: Conversely, the CR of run-length encoding (RLE) (cite80†Golomb, 1966 ) $\approx 0.64\times$, results in data expansion, confirming that long runs of identical exponent values are infrequent. The primary compression potential thus lies in repeated value frequency, which Huffman coding leverages.

L189: ### 5.4. Hardware Overhead and Power Analysis
L190: This section evaluates the area and power consumption overheads. Table cite84†4 reports post-synthesis results in GF 22 $\mathrm{nm}$ for the configuration selected in Section cite20†5.2 . The compressor employs 10 parallel lanes, each with an 8-entry local frequency cache, alongside a shared global histogram for tree construction. The encoding stage uses 10 parallel LUTs. The decompressor is a multi-stage LUT design with four stages, each containing 8 entries and indexed by 8/16/24/32-bit prefixes.
L191: Compressor: The compression unit includes: (1) 10 local caches (9.85 ${\mathrm{\SIUnitSymbolMicro m}}^{2}$ each with 2.5 $\mathrm{mW}$ total power consumption), (2) a single global histogram and codebook generation circuit (13,113 ${\mathrm{\SIUnitSymbolMicro m}}^{2}$, 5.23 $\mathrm{mW}$), and (3) 10 encoding LUTs (each 79.87 ${\mathrm{\SIUnitSymbolMicro m}}^{2}$, with 17.4 $\mathrm{mW}$ total power consumption).
L192: Decompressor: Multi-stage decoding LUTs occupy 98.5 ${\mathrm{\SIUnitSymbolMicro m}}^{2}$ area each, for a total 985 ${\mathrm{\SIUnitSymbolMicro m}}^{2}$ area and 20.3 $\mathrm{mW}$ power consumption.
L193: Overall area and comparisons: All the circuits within LEXI occupy 14,995.2 ${\mathrm{\SIUnitSymbolMicro m}}^{2}$ and consume 45.43 $\mathrm{mW}$ total power. For a fair comparison with the 16 $\mathrm{nm}$ Simba system, we scale our results using (cite85†Stillmaker and Baas, 2017 ), resulting in a total LEXI area of 5,452.8 ${\mathrm{\SIUnitSymbolMicro m}}^{2}$.

L195: ### 4.3. Optimized DUET System and Baselines
L196: 
L197: Both Prefill and Decode packages are implemented as chiplet-based systems and fit within the practical maximum interposer area of roughly 2700–3000 $mm^{2}$ (cite70†Lau, 2022 ). This is comparable to state-of-the-art accelerator packages such as NVIDIA B200 (cite27†Corporation, 2024 ) and AMD MI350 (cite71†Corporation, 2025 ). We limit all chiplets to 121 $mm^{2}$, matching the HBM footprint to simplify floorplanning (cite72†Park and others, 2022 ).
L198: Prefill package: The Prefill package integrates 16 compute chiplets arranged in a $4\times 4$ grid as summarized in Table cite73†3 . Each chiplet contains 192 systolic arrays of size $64\times 32$ and D2D PHYs provisioned with 256 GB/s bandwidth. Along three sides of the interposer, 12 memory-PHY chiplets interface with 24 off-package GDDR7 stacks, with each memory-PHY chiplet connected to two GDDR7 stacks (8 GB each (cite74†, 2024 )).
L199: This configuration provides a total of 192 GB capacity and enough bandwidth for compute-bound prefill execution.

L237: ### 4.4. Performance Evaluation on LLM Workloads
L238: This section evaluates system performance using three metrics: time to first token for the prefill phase; throughput (tokens/s), and average time between tokens for the decode phase, measured across batch sizes from 1 to 128. Following prior LLM serving frameworks, such as DistServe (cite21†Zhong et al., 2024 ) and Mooncake (cite22†Qin et al., 2025 ), we assume a continuous stream of user requests.
L239: Each new request is processed on the Prefill package, after which its KV- and state-cache are immediately transferred to the Decode package for token generation. While we do not explicitly model multi-request scheduling, we assume that the throughput of prefill and decode pipelines is matched, ensuring both packages remain fully utilized.
L240: Prefill Phase Performance: Figure cite76†6 (a) plots the TTFT of the Nemotron-H-56B on the ArXiv and LongWriter datasets. DUET architecture consistently achieves the lowest TTFT for all batch sizes. While running the ArXiv dataset, DUET achieves on average 1.6$\times$ and 2.9$\times$ lower TTFT than prefill- and decode-friendly configurations, respectively. Moreover, DUET has 5.9$\times$ lower TTFT than the B200 GPU baseline because of higher peak performance and SSM/GEMM optimized systolic array.
L241: The B200 GPU and the prefill-friendly aggregated baselines cannot run with batch sizes over 64 for the ArXiv workload due to KV/state cache capacity limits. In contrast, DUET sustains the full batch range because the Prefill package stream caches to the Decode package concurrently, avoiding storage bottlenecks. Similarly, DUET achieves 1.1-6.7$\times$ lower TTFT than the baselines on the LongWriter dataset.
L242: As summarized in Table cite77†4 , DUET outperforms the baselines across all models and datasets. Using the geometric mean across all models and workloads, DUET reduces TTFT by 4$\times$, 1.4$\times$, and 2.7$\times$ relative to the B200, prefill-friendly, and decode-friendly systems.
