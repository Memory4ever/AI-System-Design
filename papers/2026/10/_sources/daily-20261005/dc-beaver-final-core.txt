L961@P6: decoding exhibits a bursty, wave-structured traffic pattern.
L962@P6: As Fig. 7 shows, each execution wave contains an HBMintensive peak followed by an HBM-light valley. A wave first
L963@P6: reads LLRs from HBM, performs belief propagation with
L964@P6: little HBM traffic, and then writes its decoded bits. For such
L965@P6: a kernel, whole-kernel protection would also block the ML
L966@P6-7: 7tenant during the long belief propagation valleys. Beaver
L967@P7: instead applies wave-aware protection: it sets the bitmap during each wave’s reads and writes but clears it during belief
L968@P7: propagation so that the co-tenant can make progress.
L969@P7: Injecting the guard without source. ML co-tenants commonly invoke vendor GEMM, attention, and projection kernels whose CUDA source is unavailable. Beaver therefore
L970@P7: rewrites kernels with available PTX (see §2) and substitutes
L971@P7: the rewritten kernels at load time. Fig. 6 shows this five-stage
L972@P7: pipeline: Stages 1–4 run once offline for each targeted kernel, while Stage 5 activates the rewritten kernel at load time.
L973@P7: The vRAN workload profiling determines when protection
L974@P7: is needed; this pipeline determines where the ML co-tenant
L975@P7: should pause before issuing more HBM traffic. Specifically:
L976@P7: (1) Attribute HBM traffic: PTX identifies instructions that access memory, but does not show how often they execute
L977@P7: or how much HBM traffic they generate. Beaver profiles
L978@P7: the unmodified kernel and attributes its measured HBM
L979@P7: traffic to individual PTX lines, and the results identify the
L980@P7: code that contributes most to the kernel’s HBM demand.
L981@P7: (2) Select HBM-intensive regions: Polling before every memory instruction would add excessive overhead. Beaver
L982@P7: instead groups PTX lines into basic blocks—straight-line
L983@P7: code regions with one entry and no internal branches [3].
L984@P7: It sums the traffic profiled from Stage 1 within each block
L985@P7: and selects the smallest set of blocks that covers a configured fraction of the kernel’s HBM traffic. As a result,
L986@P7: a small set of useful candidate locations is identified, at
L987@P7: each of which Stage 3 inserts a safe gate.
L988@P7: (3) Insert a safe polling gate: Beaver cannot use the same
L989@P7: gate placement everywhere since GPU kernels organize
L990@P7: their memory-producing threads differently. We call a
L991@P7: gate safe when every thread that can issue the selected
L992@P7: memory batch encounters it, without requiring unrelated
L993@P7: threads to participate. Beaver classifies each selected
L994@P7: region by its execution structure and chooses the corresponding gate. If the shared bitmap is clear, the gated
L995@P7: threads issue the next memory batch; otherwise, they
L996@P7: briefly back off and check again.
L997@P7: (4) Build a drop-in GPU binary: Beaver reassembles the rewritten PTX into a GPU binary using the original target architecture and compiler settings. The kernel retains the
L998@P7: same arguments and launch interface.
L999@P7: (5) Redirect and bind: At load time, a runtime shim redirects
L1000@P7: each targeted kernel to its rewritten binary and maps
L1001@P7: the shared bitmap into both tenants’ address spaces. The
L1002@P7: injected poll is thereby bound to the vRAN signal without
L1003@P7: changing the ML co-tenant’s framework or application.

L1466@P11: 7 Related Work
L1467@P11: Baseband processing and virtualization. Sora [35] demonstrated high-performance wireless processing on generalpurpose CPUs, and BigStation [41], Agora [5, 26], and Hydra [8] scaled software MIMO processing within and across
L1468@P11: servers. Savannah [28, 29] and Nexus [27] explore heterogeneous CPU–eASIC processing, while Intel FlexRAN, srsRAN,
L1469@P11: and OpenAirInterface demonstrate vRAN on commodity infrastructure [11, 25, 33]. These systems make software L1
L1470@P11: feasible and scalable, but do not protect a latency-critical
L1471@P11: GPU L1 pipeline from concurrent ML workloads.
L1472@P11: GPU-accelerated L1. Prior work accelerates individual L1
L1473@P11: operations, particularly LDPC decoding, on GPUs [13, 36, 46].
L1474@P11: DecodeX [30] benchmarks LDPC decoding across CPU, GPU,
L1475@P11: and ASIC platforms, exposing the effects of parallelism, workload granularity, data movement, and offload. NVIDIA Aerial
L1476@P11: instead implements complete, production-grade PDSCH and
L1477@P11: PUSCH pipelines with CUDA kernels [23].
L1478@P11: GPU sharing systems (see Table 1). Gandiva, AntMan,
L1479@P11: and HiveD schedule or resize training jobs [39, 40, 45]; Salus,
L1480@P11: Orion, and TGS share GPUs at iteration, operator, or kernel
L1481@P11: granularity [34, 38, 44]. REEF provides μs-scale preemption,
L1482@P11: but requires a custom AMD ROCm driver and is incompatible with our CUDA pipeline [10]. MIG isolates SMs and
L1483@P11: memory slices, whereas MPS and CUDA green contexts isolate compute but leave HBM shared [16, 20, 21]. For vRAN

L1487@P11: 8 Conclusion
L1488@P11: We present Beaver, a GPU sharing system that enables elastic co-tenancy between ML and latency-critical vRAN workloads. Beaver combines a workload-aware SM sizer for heterogeneous multi-cell workloads, slot-granular SM repartitioning across pre-created GC pairs, and a cooperative HBM
L1489@P11-12: 12bandwidth guard injected into compiled co-tenant kernels.
L1490@P12: Evaluated using NVIDIA Aerial, Beaver keeps the vRAN’s
L1491@P12: p99.9 processing latency within its deadline while co-located
L1492@P12: with full-stack vLLM serving, and extends effectively to the
L1493@P12: downlink pipeline and other GPUs. Future directions include
L1494@P12: coordinating multiple ML co-tenants, extending resource
L1495@P12: management across multi-GPU deployments, and exploring
L1496@P12: hardware support for finer-grained HBM bandwidth control.
