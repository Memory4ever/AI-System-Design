Difflet: A Fast Inference Engine for Diffusion Transformer Models on AWS Trainium
Bin Ma   1
Min Yu   1
Vijay Kodamalla   1
Jialin Liu   1
Dong Li   1   2
†    †  footnotetext:   1 Yotta Labs, USA  2 University of California, Merced, Merced, California, USA.
Bin Ma <bin@yottalabs.ai>, Min Yu <minyu@yottalabs.ai>, Vijay Kodamalla <vijayk@yottalabs.ai>, Jialin Liu <liu@yottalabs.ai>, Dong Li <dli35@ucmerced.edu>.
Abstract
On AWS Trainium2, every component of a diffusion model runs as a program compiled ahead of time for fixed shapes, while pipelines differ across models, prompt lengths across requests, and caching decisions across denoising steps. We present Difflet, a serving engine in which five model pipelines share one compilation backend, joint attention is split across cores by attention head, and a host controller decides at each denoising step whether to run the denoiser or reuse its earlier output. A small probe program computes the caching signal on the device and returns one number per step, and a resident model process keeps every program loaded across requests. Across five image and video model families, fused attention accelerates denoiser steps by 1.2–4.3   ×  \times    over the same framework using PyTorch/XLA attention, and at 32.8k visual tokens it is the only attention that compiles. On four of the five models, resident serving is 1.5–3.4   ×  \times    faster than standalone runs that reload weights from a warm file cache for each generation.
1  Introduction
Diffusion transformers generate images and videos through repeated denoising steps. Each step applies a transformer to a noisy latent representation, using the timestep and conditioning inputs to predict the noise, or for flow-matching models the velocity, from which the sampler computes a less noisy latent   Peebles & Xie (2023)  . Higher image resolutions and longer videos increase the number of visual tokens processed at each step. Repeating this computation raises both generation latency and the accelerator time consumed by each request. Efficient serving therefore requires shortening the user’s wait while controlling the cost per generated image or video.
Most diffusion serving today runs on NVIDIA GPUs, whose high price and limited supply make the production cost hard to manage. Cloud providers have therefore built cost-efficient, customized accelerators. AWS Trainium   Fan et al. (2024)   is one of those examples: it has been reported that Trainium2 instances provide 30–40% better price-performance than GPU-based EC2 P5e and P5en instances   Amazon Web Services (2026i)  , and distributed LLM training on first-generation Trainium cost up to 46.3% less than on A100-based instances in selected workloads, at comparable or higher training throughput   Fu et al. (2024)  . Each Trainium chip contains several NeuronCores (cores for short), and the Neuron Kernel Interface (NKI) lets programmers write kernels that choose which of a core’s tensor, vector, scalar, and general-purpose engines runs each operation and when data moves   Amazon Web Services (2026j) ;  Amazon Web Services (2026b) ;  Amazon Web Services (2026c)  . With Trainium’s production software stack, serving a diffusion model means running programs that are compiled ahead of time for fixed shapes and called by a host process at every denoising step. Serving diffusion models under this execution model requires deciding what must be fixed in compiled programs and what must remain flexible across models, requests, and denoising steps. This creates challenges at three levels: accommodating different model pipelines, distributing each denoiser evaluation across cores, and reusing results across denoising steps.
First, diffusion models differ in their encoders, denoiser, and decoder and in the order they call them, yet on Trainium every one of these components must be compiled before serving. Ahead-of-time (AOT) compilation specializes each component for the selected tensor shapes, data type, and parallel configuration   Amazon Web Services (2026d)  . When compilation, loading, and invocation are embedded in each model’s pipeline, supporting another model requires assembling another execution path around these constraints. The challenge is to add a model without writing another compilation and loading path for it.
Second, distributing a denoiser across Trainium cores requires finding a parallel configuration that both the model and the compiled kernels support. Tensor parallelism (TP) partitions weights   Shoeybi et al. (2019)  ; sequence and context parallelism (SP, CP) partition tokens   Korthikanti et al. (2022) ;  Jacobs et al. (2023) ;  Liu et al. (2023)  ; and classifier-free guidance (CFG) parallelism executes conditional and unconditional denoiser passes concurrently   Ho & Salimans (2022)  . Each choice changes tensor shapes, data layouts, and communication requirements, so these choices cannot be combined freely. For example, joint attention over visual and text tokens must exclude padded text keys from its softmax. The masked attention path used here requires valid keys to be contiguous and query and key lengths to match   Amazon Web Services (2026e)  . A direct partition that keeps queries local while gathering all keys violates the second requirement. Such incompatibilities make parallel configuration a question of execution feasibility as well as performance, and discovering them only after compilation is costly.
Third, step caching, a common optimization for diffusion transformers, must obtain a cheap reuse signal despite Trainium’s compilation and memory constraints. Methods such as TeaCache use early denoiser features to decide when to reuse prior results   Liu et al. (2025a)  . In our AOT execution path, these features remain inside the compiled denoiser, while the host controls whether to invoke it. Computing the signal separately on the host adds latency; a device implementation instead needs additional memory for weights and saved features alongside the partitioned denoiser. This placement tradeoff can undermine caching: our host path makes Wan’s denoising loop 11% longer than without caching, while HunyuanVideo already occupies 22 of 24 GiB per logical core before adding a probe.
We present Difflet, a serving engine for diffusion transformers on AWS Trainium2 built around one boundary: what is the same for every request is compiled, and what changes per request or per step stays on the host. Each component’s program fixes its shapes, data type, parallel configuration, and kernels; the model’s control flow, the prompt length, the decision to skip a step, and each request’s sampling state are left to the host. When such a value must reach or leave the device, Difflet passes it as a small runtime value instead of building a new program: the number of valid text keys going into attention, and one change score per step coming out of the caching probe.
To support different models, Difflet exploits what diffusion pipelines have in common. Their control flow differs, but all of them are built from conditioning encoders, a denoiser, and a decoder. Each of these components compiles to a program that depends only on its shape, data type, parallel configuration, and compiler version, and, where a device probe is fused into the denoiser, on whether the probe is present; runtime settings such as the caching cadence or threshold do not enter it. Difflet therefore keeps each model’s control flow in its own pipeline on the host and moves everything AOT compilation needs into a shared backend, driven by a short description of each model. The backend caches each compiled program under exactly these inputs, so a server restart or a new caching threshold reuses the program instead of recompiling it.
For parallel execution, Difflet chooses each split by what Trainium’s attention kernels accept. For attention, it uses Ulysses-style context parallelism   Jacobs et al. (2023)  , which regroups the tokens by attention head, so each core holds every query and key for its heads and thus the same number of queries as keys. Difflet places the text padding after all valid keys, so the valid keys sit next to each other, and each request passes only the number of valid keys. One compiled program thus serves every prompt length, and the split result matches unsplit attention to within BF16 rounding. Difflet also rejects unsupported combinations before compiling rather than after a long compilation fails.
To skip denoising steps, Difflet estimates the output change outside the denoiser in one of two ways. A small compiled probe computes an early denoiser feature on the device, keeps the previous step’s feature there, and returns a single number to the host; because it loads only the weights of the layers it runs, it fits beside the denoiser even on HunyuanVideo. Alternatively, Difflet estimates the change from the outputs of earlier steps, which needs no additional program. In both cases, a host controller decides at each step whether to call the denoiser or reuse an earlier output.
These three parts meet in Difflet’s resident model process, which keeps a model’s programs loaded across requests. At startup, the process loads the programs compiled for the deployment’s shapes, data type, and parallel configuration, checks that they match, and runs a test generation before accepting requests. For every request, it resets the sampling and caching state, so reuse never crosses requests. Difflet serves FLUX   Black Forest Labs (2024)  , Qwen-Image   Wu et al. (2025)  , Wan   Wan Team et al. (2025)  , HunyuanVideo   Kong et al. (2024)  , and LTX-2   HaCohen et al. (2026)   through this process.
We summarize our contributions as follows:
•
A shared Trainium backend through which one kernel or parallel mode serves different diffusion pipelines.
•
Parallel execution planned as a serving decision, with split joint attention that matches unsplit attention.
•
Step caching around compiled denoisers, with or without a device probe.
•
A resident model process that serves five image and video models.
2  Background
Trainium2 architecture.  AWS Trainium2 has eight physical NeuronCore-v3 cores and 96 GiB of high-bandwidth memory (HBM) for weights and activations   Amazon Web Services (2026h)  . Each core provides a software-managed scratchpad (SBUF) for tensors and an accumulation buffer (PSUM) for matrix multiplication results. Direct memory access (DMA) engines transfer tensors between HBM and SBUF   Amazon Web Services (2026j)  . The Tensor Engine handles matrix multiplication, Vector and Scalar handle normalization and activations, and GpSimd supports programmable SIMD. These engines can execute concurrently and overlap computation with data movement   Amazon Web Services (2026b) ;  Amazon Web Services (2026j)  . Collective-communication cores support all-reduce and all-to-all   Amazon Web Services (2026j)  . We use the default     LNC  =  2   \mathrm{LNC}{=}2    configuration, which pairs physical cores into four logical cores per device, each with 24 GiB of HBM; all parallel configurations count logical cores   Amazon Web Services (2026a)  .
Compilation and execution.  The Neuron SDK provides a compiler, runtime, and Neuron Kernel Interface (NKI) for custom kernels with explicit data movement   Amazon Web Services (2026c)  . Our ahead-of-time workflow compiles PyTorch components for fixed tensor shapes and data types; padding or compiled variants support different input sizes   Amazon Web Services (2026d)  . The runtime loads programs onto NeuronCores, while host code invokes them and controls iteration and data-dependent decisions.
3  Model Pipelines and a Shared Trainium Backend
Figure 1:  Model abstraction and Trainium adaptation in Difflet. (a) Pipelines specify component dataflow and configurations. (b) Component, operator, and parallelism interfaces connect models to (c) Trainium compilation and execution. Solid arrows denote dataflow; dashed arrows denote configuration and adaptation. NeuronCore icons are schematic.
Difflet splits each model along the boundary of Section   1  : a pipeline on the host decides which components run and in what order, and a shared Trainium backend compiles, loads, and calls them (Figure   1  ). The pipeline is hardware-agnostic: it names the model’s encoders, denoiser, and decoder, the tensors that flow between them, and the shapes each one takes. A short model adapter connects the two: given a resolution, data type, and parallel configuration, it tells the backend which components to compile and how to shard each one.
The model pipeline determines how tensors move through these components. For a generation request, conditioning encoders produce the context used during denoising, and the pipeline prepares the initial latent and timestep schedule. At each step, the denoiser predicts noise or a velocity field from the current latent, timestep, and encoder outputs. The diffusion scheduler uses this prediction to update the latent for the next step. After the final update, the decoder maps the latent to an image or video. The pipeline owns this iterative control flow, including model-specific conditioning and component choices.
Trainium requires components to be compiled for static tensor shapes. Before inference, Difflet therefore prepares the required components for the selected image resolution or video length, data type, and parallel configuration. The Trainium backend uses this information to compile each component ahead of time, verify that the required compiled artifacts are present and match the selected configuration, and load the programs and weights onto the assigned cores. These preparation steps are separate from the generation process: loading order can follow resource requirements while the model pipeline retains the model’s execution order.
During inference, the model pipeline runs in Python and calls the components’ programs with tensor inputs, receiving output tensors for the next stage or denoising step. Within each component, shared operator interfaces connect model operations to Trainium implementations, including NKI kernels and NeuronX Distributed (NxD) operations. The parallel configuration specifies how work is distributed across ranks and is checked against supported combinations. The backend organizes these ranks into groups for the selected parallel modes. Each model thus keeps its own control flow while sharing one backend. Because models call attention and collectives through shared operator interfaces, a kernel or parallel mode added once becomes available to every model that uses that interface.
4  Parallel Execution on Trainium
Difflet distributes each denoiser evaluation across cores with tensor, sequence, context, CFG, and data parallelism; each program fixes its parallel configuration, while the prompt length remains a runtime value. Each rank is one logical core, which pairs two physical NeuronCore-v3s under the default     LNC  =  2   \mathrm{LNC}{=}2    configuration. On the single-chip  trn2.3xlarge , collectives between ranks stay on chip, with DMA engines moving data between the logical cores’ HBM   Amazon Web Services (2026a) ;  Amazon Web Services (2026j)  . Within a rank, each attention kernel runs on both physical cores, which split the call’s heads between them   Amazon Web Services (2026f)  . Each physical core computes on tiles in its SBUF, whose 128 partitions set the tile height, and its Tensor Engine is a     128  ×  128   128\times 128    systolic array   Amazon Web Services (2026j)  . Two properties shape the design below: compiled programs fix every tensor shape, and kernels process sequences in tiles of 128 tokens, one per SBUF partition. In joint attention, each query attends to both visual and text keys under a single softmax normalization. Distributed execution must preserve this normalization while excluding padding and counting replicated text keys only once. These requirements determine how Difflet redistributes tensors and combines results from Trainium’s fused attention kernels.
4.1  Composing Parallelism
Tensor parallelism (TP)  partitions linear-layer weights across ranks using the Megatron column and row decomposition   Shoeybi et al. (2019)  . Ranks in a TP group process the same tokens with different weight slices; an all-reduce sums the partial outputs and returns the result to each rank.  Sequence parallelism (SP)  partitions tokens within that group for normalization, modulation, and residual operations between linear layers   Korthikanti et al. (2022)  . An all-gather assembles the token partitions before the linear layers, and a reduce-scatter sums and partitions their outputs. The normalization, modulation, and residual operations run on the Vector and Scalar Engines, whose throughput is far below the Tensor Engine’s   Amazon Web Services (2026b)  ; SP divides this otherwise replicated work by the TP size while reusing the TP group.
Context parallelism (CP)  partitions tokens across a separate rank group. Ranks at the same TP position hold the same weight partition but process different tokens. HunyuanVideo and Qwen-Image partition visual tokens while replicating text; FLUX partitions both streams. We focus below on the replicated-text layout, also used in xDiT   xDiT Contributors (2026)  .
Each rank’s queries (Q) require keys (K) and values (V) from all visual partitions and one copy of the text. The  gather_kv  mode all-gathers visual K/V and combines them with local text K/V. This gives each rank the full key set, but each logical core must then hold the whole visual K/V sequence in its 24 GiB of HBM, so per-rank K/V memory does not shrink as the CP group grows. Ulysses and Ring organize these inputs differently, so their masks must follow the key order of each kernel call.
4.2  Representing Attention Mask
Neuron compiles attention calls for fixed tensor shapes, so shorter text inputs retain padding. Padding keys must be excluded from softmax to preserve the weights on valid keys. When valid keys form a contiguous interval, Difflet passes its bounds to AWS’s fused attention kernel, which combines score computation, softmax, and value aggregation   Amazon Web Services (2026e) ;  Amazon Web Services (2026f)  . As the Vector Engine moves the scores to SBUF, it replaces those outside the interval with     −  ∞   -\infty    and tracks each row’s running maximum; the Scalar Engine then computes the exponentials and their row sums. After a DMA transpose, the Tensor Engine multiplies the probabilities by    V  V   , so the score matrix never returns to HBM. The kernel reads two bounds per query from HBM instead of a mask entry per query–key pair.
For HunyuanVideo, Difflet arranges the full joint key sequence as visual tokens, valid text tokens, and text padding. The next layer expects the original token distribution. An inverse all-to-all therefore returns visual outputs to sequence partitions, while an all-gather across head partitions restores replicated text outputs.
Ring for joint attention.  Ring attention keeps queries local while rotating K/V partitions among ranks   Liu et al. (2023)  . Here Q contains local visual tokens and all text, whereas a rotating K/V partition contains only visual tokens. The AWS Ring kernel used here requires equal query and key lengths   Amazon Web Services (2026g)  . Difflet therefore builds the ring from separate fused attention calls that accept unequal lengths without a mask.
Each call uses the same local Q with either text K/V or a visual K/V partition. Text is processed once per rank, so its keys are counted once; only visual K/V circulate. Each rank obtains one text partial and one partial for each visual partition, including its own.
Independently normalized partials cannot be added, because each uses a different softmax denominator. For each query, each call therefore returns an unnormalized weighted value sum, the maximum score, and the sum of exponentials relative to that maximum. The kernel keeps these statistics in SBUF and writes them to HBM in its tile layout, one query per partition, which Difflet reorders to query order. Outside the kernel, Difflet rescales both sums to a common maximum and adds them across partitions. Dividing the combined weighted sum by the combined exponential sum restores joint normalization without gathering all visual K/V   Dao et al. (2022) ;  Liu et al. (2023)  . The outputs retain Q’s layout: local visual tokens and replicated text.
The text partial contains only text keys, so masking its padding requires bounds     [  0  ,   L  text   )   [0,L_{\mathrm{text}})    in local text-key coordinates. Padding must be excluded from both its weighted value sum and softmax statistics before the joint merge.
4.4  Other Parallel Modes
TP, SP, and CP divide work within one denoiser pass.  Classifier-free guidance (CFG) parallelism  executes the conditional and unconditional passes concurrently in separate rank groups   Ho & Salimans (2022) ;  Fang et al. (2024a)  .  Data parallelism (DP)  assigns independent requests to complete model replicas, increasing throughput. Each replica can combine TP with CP or CFG parallelism.
Ulysses partitions each TP rank’s heads across the CP group, so the total head count must be divisible by the product of the TP and CP group sizes, which count logical cores. Table   4   in Section   7.4   lists the modes each model runs.
5  Adaptive Step Caching on Trainium
Nearby diffusion steps can produce similar denoiser outputs. Difflet uses this similarity to replace some full denoiser executions with estimates. The skip decision changes from step to step, so Difflet makes it on the host, outside the compiled denoiser. The host stores the previous output used by the generation loop and its most recently measured change. A full execution measures the change relative to the previously used output, then saves the new output. A cached step adds the saved change to the previous output and stores the estimate for the next step. Both paths apply the same numerical update rule to the latent, reducing denoiser calls while retaining every sampling step. This output estimator supports three caching modes:  fixed cadence ,  calibrated adaptive , and  online-delta . They differ in when to replace a full denoiser execution with an estimate.
The calibrated adaptive mode needs a signal that costs less to obtain than the computation it can save. TeaCache   Liu et al. (2025a)   motivates using changes in early model features to estimate later output changes. On Trainium, these features remain inside a program compiled before inference. Observing them requires the program to expose a result, but returning a large feature array to the host for comparison would introduce communication overhead. Difflet compiles a shallow computation, called a probe, to produce the change score directly on Trainium. Figure   3   shows how this path connects device computation and saved features to the host’s reuse decision.
The device probe executes the denoiser’s input projection and the first block’s normalization and modulation, using the current timestep and conditioning inputs. It stops before attention. The compiler removes the unused later computations. Wan, HunyuanVideo, and LTX-2 load the result as a separate program; FLUX and Qwen-Image fuse it into the denoiser program. Full steps still run the complete denoiser, so the probe never changes what a full step computes.

The score     d  t   d_{t}    is computed before the saved array is replaced. For example, a probe can divide the average absolute change by the average magnitude of the saved features. Other measures retain the same scalar interface.
To keep the saved features on Trainium across calls, Difflet assigns the probe’s new feature output to their existing memory through input–output aliasing   Amazon Web Services (2026d)  . After comparison, the current features replace the old ones there, and the next call reads them directly. Feature computation, comparison, and state update thus occur within one probe call. Only the scalar score returns to the host, reducing probe output transfer from a feature array to a single value. The saved features support the next comparison; the separate host output history supplies cached predictions.
In calibrated adaptive mode, a host controller uses the score to choose full execution or prediction. Before inference, reference runs provide examples of feature changes and corresponding output changes. This calibration fits a curve relating the two. The controller compares the estimated output change with a threshold, either separately for each step or accumulated across steps. Reaching the threshold triggers full execution and resets the sum when accumulation is used. All three modes retain initial full steps to establish output history and final full steps to limit reuse near completion. These decisions remain outside the compiled denoiser.

Online-delta uses outputs already available on the host, avoiding a separate probe call. At a full step, it measures output change relative to the previously used output, which may have been estimated. If this change is below    α  \alpha    times the first change measured in the generation, the next step is cached. That cached step must be followed by full execution to obtain a fresh measurement. Calibration can select this mode when early features poorly predict output changes but output changes remain related across neighboring steps. If neither signal is suitable, it selects fixed cadence, which caches at a preset interval without a change signal. Both modes are probe-free; their effect on final quality must be assessed through complete image or video generation.
Because a separate probe loads only the weights of the layers it runs, it fits beside the denoiser even on HunyuanVideo. Section   7.5   measures what the probe costs per step and how well its signal predicts the output change.
6  Serving Layer
Serving applies the same boundary across requests: programs and weights stay loaded, while each request’s sampling and caching state starts fresh on the host. Difflet separates request handling from model execution using two host processes (Figure   4  ). The  API process  validates requests, manages the queue, and returns results. A single  resident model process  loads the components for text encoding, denoising, and decoding, and retains them across requests. The process coordinates all three stages and manages the assigned cores. Keeping them resident avoids repeated runtime initialization and weight loading. This separation allows the model process to be restarted without restarting the API process.
Components that stay resident together share the same cores, which constrains both their parallel configurations and their memory. In our NxD execution path, resident components share the same set of cores, although their TP degrees can differ. For FLUX, the denoiser’s weights are partitioned across four cores (TP=4), while each core holds a full copy of the VAE weights (TP=1). Each component must be compiled for this shared set of cores and its own TP degree. Device memory must accommodate all resident weights, including the VAE replicas, and execution buffers.
At startup, Difflet configures the model process using a serving profile that specifies the model, supported input shapes, data type, and parallel configuration. It selects the corresponding compiled artifacts and checks that their core assignments match this configuration before loading them. The model process then runs a test generation to check that the loaded components work together. It validates the output before becoming ready to execute requests (Figure   4  (a)). After a restart, the process reloads the saved artifacts and repeats these checks.
During serving, the API process checks requests against the serving profile and places accepted requests in a bounded queue, rejecting new requests when the queue is full. The model process handles queued requests one at a time to prevent concurrent changes to the pipeline’s sampling and caching state. Each request needs its own sampling and caching state. The model process therefore initializes the latent and timestep schedule for each generation. When step caching is enabled, it also clears the controller’s output history to prevent reuse of predictions from a previous request. The model process returns the result to the API process (Figure   4  (b)).
Recovery.  When a request times out or the model process fails, Difflet pauses dispatch before attempting recovery. A timeout may leave device computation running, so Difflet first requests cancellation and waits for the current generation to stop. If cancellation succeeds, the same model process can handle subsequent requests. Otherwise, Difflet terminates the process and confirms its exit before starting a replacement. A model process failure also triggers replacement. The new process reloads the saved artifacts and passes the startup checks before dispatch resumes (Figure   4  (c)). If recovery fails, dispatch remains paused.
7  Evaluation
We evaluate Difflet on five image and video models and ask five questions: how fast Difflet is end to end (§  7.2  ), which mechanism the speedup comes from (§  7.3  ), which parallel configurations pay off (§  7.4  ), what step caching saves and costs (§  7.5  ), and what resident serving buys in startup and recovery (§  7.6  ).

Measurements.
Request latency  is the time to generate one output with the model already resident, measured through  difflet serve , over HTTP for Wan and LTX-2, where returning the output adds well under a second.  Standalone latency  additionally covers process start and model loading: a  cold  run first flushes the host page cache, a  warm  run reuses the cached weight files but still loads them onto the device.  Denoising time  is the wall time of the denoising loop, including steps served from the cache, and  step latency  is the median time of an uncached step, excluding the first; with sequential CFG it covers both passes. Compilation is a one-time build into empty caches and is reported separately. Resident request latency is the median of five requests after one warm-up for image models and of three for video models; standalone runs and compilations are measured once. The device slows by up to 25–30% under back-to-back load and recovers after 90 s of idle, so every resident measurement idles the device for 90 s first.

Findings.
The attention kernel speeds up every denoiser step, and resident serving removes most of what a standalone run adds around it. Once a model is resident, request latency is mostly denoising—except on the video pipelines with heavy stages around the denoiser. Difflet’s generality costs no denoising performance against NxDI. Difflet is faster end to end because of loading: NxDI loads the full diffusers pipeline on the host in every process and warms up each component, whereas Difflet reads checkpoints already split per core at compile time. Warm latency falls from 66.3 to 47.6 s and the Neuron weight load from 43 to 23 s, for a compilation one minute longer (16.7 against 15.7 min), into which the checkpoint splitting moves.

Findings.
Each mechanism dominates on different models.  Together they cut request latency by 3.0–8.5   ×  \times    on the four models with a PyTorch/XLA baseline. Resident serving is the largest single step on the image models (3.35   ×  \times    on FLUX, 2.33   ×  \times    on Qwen-Image) and on HunyuanVideo (2.35   ×  \times   ), because a standalone request pays process start, pipeline construction, and a 10–140 s device weight load on every call. The attention kernel gives 1.93   ×  \times    on HunyuanVideo and 1.32–1.37   ×  \times    on the image models; on LTX-2 its 1.24   ×  \times    faster denoiser step would save 4 s of a 110 s run, and the measured difference (0.1 s) is within the run-to-run spread (106–113 s). Presharding matters where the checkpoint is large relative to the rest of the pipeline: 1.69   ×  \times    on LTX-2, whose 19B denoiser takes 38–42 s to shard on the host, and 1.53   ×  \times    on Wan, whose text encoder and denoiser take 173 and 354 s. Step caching adds 1.40–1.64   ×  \times    where the request is mostly denoising, 1.33   ×  \times    on Wan, and 1.17   ×  \times    on LTX-2.
Wan is the exception to resident serving, because its model process decodes on the host.  Its resident request takes 1,245 s against 974 s standalone. Both paths run the same denoiser program and denoise in about 720 s; the standalone run then decodes on the device with the chunked FP32 VAE in 126 s, whereas the model process decodes on the host in about 520 s, more than the 140 s weight load it saves. The chunked decoder does not fit beside the resident model: the 81-frame denoiser and the text encoder already take about 20 GiB of each logical core’s 24 GiB, and the decoder’s largest chunk moves 3 GiB of state in and 3 GiB out.

The kernel’s gain grows with sequence length, and at 32.8k tokens it is the only attention that runs.  Attention cost grows quadratically with the number of tokens. Figure   6   orders the models by sequence length: the step speedup rises from 1.24   ×  \times    on LTX-2 (2.3k tokens) through 1.89–2.53   ×  \times    on the image models (4.1k) to 4.28   ×  \times    on HunyuanVideo (10.2k). At Wan’s 32.8k tokens the SDPA program does not compile, so the fused kernel is the condition for running at all. The models differ in architecture as well as length, so the trend is across workloads rather than a controlled sweep.

Findings.
At 4.1k tokens, tensor parallelism over all four cores is the latency default.  Every configuration that keeps four cores on one request stays within 3.5% of TP4 (Table   5  ). Sequence parallelism and gather-based context parallelism add 2% per step (278.7 and 278.8 against 272.5 ms); Ulysses and ring attention remove 3% and 2% (263.3 and 268.2 ms), half a second on a 14 s request. At this length the activations that sequence parallelism shards and the keys and values that context parallelism exchanges are small, so the extra collectives cost about what the split saves. Ulysses, which trades the sequence split for a head split with one all-to-all on each side of attention, is the fastest of the three context-parallel modes; it and ring attention are the only configurations faster than TP4, by 3% and 2%. Halving the cores to TP2 costs 1.87   ×  \times    per step, so tensor parallelism scales from two to four cores at 94% efficiency.
Data parallelism buys throughput only marginally once models are resident.  Two TP2 replicas, started together on separate core pairs, finish two requests in 26.7 s, against 27.9 s for TP4 serving them in turn: 5% more throughput for almost twice the latency. Each replica’s step (529.6 ms) is 4% slower than a TP2 replica running alone, so the replicas contend slightly for the chip’s shared resources. Data parallelism therefore pays only when per-request work outside the device, such as loading, dominates; in a resident server it does not.
At 32.8k tokens, sequence parallelism pays, and the configurations that split the model in halves do not run.  Sequence parallelism splits across the four cores the per-token work that tensor parallelism repeats on each of them over the full sequence—the norms, modulation, and residual additions—and at this length that cuts Wan’s denoiser step by 7% (13.9 against 14.9 s) and its warm request by 4% (933 against 974 s). Ulysses context parallelism over two TP2 pairs compiles but does not load: the static DMA rings the compiler emits for its spill traffic need 43 MiB more HBM than is free beside the resident text encoder. The TP2 program, with or without CFG batching, holds half the model and the full 32.8k-token sequence on each core, and the compiler backend exhausts the host’s 124 GiB building it, in both attempts. CFG parallelism, which at short sequences removes work rather than moving it, and the data-parallel pair are therefore unavailable at this length, and the limit is the compiler’s host memory rather than the device’s.
Ulysses context parallelism handles padded prompts correctly, to within BF16 rounding.  Under Ulysses, each core holds a slice of the sequence and the all-to-all hands it a slice of the heads over the whole sequence, so the text padding mask travels as a count of valid keys. We run the HunyuanVideo denoiser (two dual-stream and two single-stream blocks at     320  ×  512  ×  61   320{\times}512{\times}61   ) as TP2CP2 with Ulysses and as TP2 alone, one compiled program per configuration, at five prompt lengths from 5 to 256 valid text tokens passed as a runtime input. The two configurations differ by at most     7.8  ×   10   −  2     7.8{\times}10^{-2}    (mean     3.7  ×   10   −  3     3.7{\times}10^{-3}   , cosine similarity 0.99992) on outputs of magnitude up to 3.3, a few BF16 rounding steps, and the difference does not grow with prompt length. 7.5  Step Caching
We evaluate the three caching modes of Section   5  :  fixed cadence  at cadence 2;  online-delta  at its default     α  =  0.6   \alpha=0.6   , untuned; and  calibrated adaptive , with its curve fitted per model on prompts other than the evaluation prompts and its threshold set to cadence 2’s skip budget. All modes keep 5 initial and 5 final full steps, so within a model they differ mainly in  which  steps they cache. As a further baseline,  fewer steps  runs without caching at the number of denoiser calls cadence 2 executes. Figure   8   reports the speedups and the quality.

Findings.
Caching saves the skipped denoiser calls, not time per call.  An executed call costs the same in every mode—830–845 ms on HunyuanVideo, 835 ms on Qwen-Image—and a cached step costs 0.3–7 ms. The speedup is therefore set by the fraction of calls skipped. Because the initial and final full steps are fixed, official step counts skip proportionally more than short runs: cadence 2 skips 20 of 50 steps for a ceiling of 1.67   ×  \times    and reaches 1.66–1.68   ×  \times   ; on LTX-2 it skips 15 of 40 for a ceiling of 1.60   ×  \times   . Wan is the exception, for a reason outside the cache: its caching-off loop runs for 12 minutes, during which the device throttles each executed call from 6.4 to 7.4 s, so a run with fewer calls is also faster per call and cadence 2 reaches 1.76   ×  \times   . Running fewer steps with the same number of calls takes the same time to within 0.5% on every model, Wan included, so between caching and fewer steps the question is quality alone.
At the same number of denoiser calls, caching keeps far more of the output than sampling fewer steps.  On every model, cadence 2 is 7.4–11.6 dB above fewer steps in mean PSNR against the uncached output (Figure   8  ), and every caching mode is at least 5.0 dB above it; on the four models scored by LPIPS, the perceptual distance agrees, with mean LPIPS 0.05–0.15 under caching against 0.19–0.27 under fewer steps. The advantage holds prompt by prompt: caching beats fewer steps on 183 of those four models’ 192 prompt–mode pairs and on all 10 of Wan’s. Caching keeps the official noise schedule and reuses an output only where the trajectory changes slowly, whereas fewer steps coarsens the schedule everywhere. The worst prompt still loses much more than the mean, down to 15.5–17.8 dB on the image models and HunyuanVideo and 17.0 dB on Wan, so the mean alone overstates what every prompt keeps.
No mode is best everywhere, and online-delta’s skip budget depends on the model and the prompt.  Cadence 2 keeps the most on FLUX, Qwen-Image, and, by 0.7 dB, Wan, online-delta on HunyuanVideo and LTX-2, and calibrated adaptive is never the best, losing up to 3.0 dB to cadence 2 at the same skip budget on HunyuanVideo. At the default    α  \alpha   , online-delta skips 18–20 of 50 steps on the 50-step models’ timing prompts but only 8 of 40 on LTX-2’s (1.25   ×  \times    against cadence 2’s 1.60   ×  \times   ). Across the 16 prompts its budget varies by model: 19–20 skips on FLUX, 18–20 on HunyuanVideo, 13–19 on Qwen-Image, and 0–15 on LTX-2, where one prompt skips none at all; on Wan’s five prompts it skips 17–19. The mode spends its budget where the output changes slowly, which buys LTX-2 its highest quality (37.3 dB) at a speed that is not known in advance.

Findings.
A restart costs a load, not a compile—unless the probe changes.  The first start of a serving profile compiles its programs and takes 18–117 min (Table   7  ). Every later start validates them and pays the weight load, which the host page cache bounds: 91–786 s warm, 340–1,102 s cold. Changing the caching target recompiles nothing, but switching from caching off to calibrated adaptive rebuilds the program that carries the probe: FLUX’s whole pipeline program (1,353 s) and Qwen-Image’s denoiser (1,419 s).
Recovery leaves no state behind.  We test both failure paths on FLUX, repeating one prompt and seed; two reference requests produce byte-identical images. A 5 s request timeout returns an error at 5.0 s, and the same model process serves again 9.3 s later, once its running denoising loop reaches the next cancellation point. Killing the model process with SIGKILL mid-request returns an error after 0.6 s; Difflet spawns a new one, reloads the weights, and is ready 65.6 s after the kill. After both faults the same seed reproduces the reference image byte for byte, so no sampling or caching state survives a request.
Under load, splitting the chip into replicas does not pay for resident FLUX.  Table   8   offers both configurations the same Poisson arrivals. At no load level does DP2   ×  \times   TP2 beat TP4: their median latency ties at     ρ  =  0.78   \rho=0.78   , and at     ρ  =  0.99   \rho=0.99    TP4’s median is 33.0 s against 46.7 s, with the 30 s SLO met for 40% of requests against 25%. Each TP2 replica needs 26–27 s for a request that TP4 serves in 14.2 s, so a request that finds a replica idle already spends most of the SLO, while the second replica adds only the 5% of throughput measured in Section   7.4  . Both configurations complete the same number of requests per hour at every level, because arrivals, not capacity, limit them. Queueing dominates both: past     ρ  ≈  1   \rho\approx 1    the 99th percentile exceeds 100 s for either configuration. With 20 requests per level these percentiles are coarse—TP4’s median is higher at     ρ  =  0.78   \rho=0.78    than at     ρ  =  0.99   \rho=0.99    (39.4 against 33.0 s)—but at every level TP4 has the lower 99th percentile and meets the SLO at least as often. HunyuanVideo, whose 58.5 s request leaves no room for a second replica, queues the same way: past     ρ  ≈  1   \rho\approx 1    its 99th percentile reaches 374 s, 6.4   ×  \times    the isolated latency, and only 20% of requests meet the SLO. Its     ρ  =  0.81   \rho=0.81    level queues more than its     ρ  =  0.95   \rho=0.95    level (median 136 against 89 s), an artifact of drawing only 20 arrivals per level.
8  Related Work
Reducing denoising computation.
Fast solvers   Lu et al. (2022)  , progressive distillation   Salimans & Ho (2022)  , and consistency models   Song et al. (2023)   reduce the number of denoiser evaluations needed for generation. Caching instead reuses computation across timesteps: DeepCache and    Δ  \Delta   -DiT reuse intermediate features   Ma et al. (2024) ;  Chen et al. (2024)  , while PAB and FasterCache exploit redundancy in attention and guidance computations   Zhao et al. (2025) ;  Lyu et al. (2025)  . TeaCache uses timestep-modulated input changes to guide reuse   Liu et al. (2025a)  . TaylorSeer predicts future features from their history   Liu et al. (2025b)  , and CG-Taylor uses early-block prediction error to decide when to recompute   Guan et al. (2025)  . Difflet builds on temporal reuse; what it adds is how to obtain the reuse signal, and decide each step, when the denoiser is a program compiled ahead of time.
Parallel inference systems.
Ulysses redistributes sequence shards into attention-head shards   Jacobs et al. (2023)  , while Ring Attention circulates key-value blocks among devices   Liu et al. (2023)  . DistriFusion reuses previous-step features to overlap communication with computation   Li et al. (2024)  ; PipeFusion combines patch and layer partitioning into a pipeline   Fang et al. (2024b)  . xDiT composes parallel modes   Fang et al. (2024a)  , while FastVideo integrates sparse attention and distillation   FastVideo Contributors (2026)  . On specialized accelerators, MaxDiffusion provides JAX implementations for TPUs   MaxDiffusion Contributors (2026)  , and AoiZora plans sharding and placement against TPU topology   Wang et al. (2026)  . NxD Inference supports FLUX on Trainium   Amazon Web Services (2026k)  . Difflet instead runs five image and video pipelines on Trainium through one backend, and splits their joint attention in a layout that Trainium’s fused kernels accept.
Diffusion serving.
DiffServe routes requests through cascades of diffusion models and adjusts resource allocation to query demand   Ahmad et al. (2025)  . NIRVANA reuses intermediate states across similar requests   Agarwal et al. (2024)  , while TridentServe jointly plans stage placement and request dispatch   Xia et al. (2025)  . These systems optimize how requests share model and accelerator resources. Difflet works below these systems, inside one Trainium model process: it keeps programs loaded and validated across requests and recovers from a timeout without letting two generations overlap.
9  Conclusions
On Trainium, a diffusion model runs as fixed-shape programs compiled ahead of time, while its pipeline, prompts, and caching decisions keep changing. Difflet runs each model’s pipeline on the host over one compilation backend, splits joint attention across cores so that it matches unsplit attention, and skips denoising steps under host control. Device probes keep comparison state on Trainium and return one score per step to the host, while the resident model process keeps every program loaded across requests. Together, these mechanisms provide a common inference and serving framework for five image and video model families. The broader lesson is to decide early what each program fixes and what the host may still change: Difflet compiles shapes, parallel configurations, and kernels once, and exchanges per-request and per-step information with the device as small runtime values—a count of valid text keys going in, one change score per step coming out.
