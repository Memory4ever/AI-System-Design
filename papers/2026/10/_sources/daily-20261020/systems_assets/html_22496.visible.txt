Abstract
Robot learning has advanced significantly by scaling demonstration datasets and model capacity; however, deploying a new robot embodiment or task typically necessitates a dedicated teleoperation corpus. Furthermore, resulting policies remain bounded by their imitation distributions, limiting generalization and continual self-improvement. We introduce  RAX (Robot Agent eXploration) , an open-source framework for robot agents centered on  scaling exploration : enabling agents to improve by acquiring online experience and synthesizing executable programs. In RAX, a general-purpose coding agent generates robot control code directly, operating without action demonstration data, hand-engineered action primitives, or value-function guidance. Through online exploration, the agent identifies decision sequences that achieve task goals and compiles them into modular programs encapsulating the full perception-planning-control loop for fast inference. Using RAX, we present a systematic multi-embodiment study on scaling online exploration across fine-grained precision and long-horizon manipulation tasks using single-arm, bimanual, dexterous, mobile, and humanoid systems in simulation and on real robots. Generalization performance on unseen environments improves consistently as exploration scales. In simulation, RAX outperforms top baseline models by     +   37.4  %    +37.4\%    on average. On real robots, RAX autonomously learns memory-dependent, articulated, high-precision, deformable, and long-horizon mobile manipulation tasks without human demonstrations, continually improving performance by composing verified skills from prior exploration sessions. As exploration scales, we observe emergent system capabilities including active perception, error recovery, safety guardrails, and human-robot agent collaboration. We open-source RAX as a generalist robot-agent platform that allows new robot embodiments to be integrated solely via API interfaces, bypassing teleoperated data collection and policy training entirely. More details are available on our project page at  robot-agent-exploration.com .

1  Introduction
“We want AI agents that can discover like we can, not which contain what
we have discovered. Building in our discoveries only makes it harder to see how the
discovering process can be done.”
—  Richard S. Sutton,  The Bitter Lesson   ( 2019 )
Robot learning has made substantial progress by scaling demonstration data and model capacity with imitation learning, aiming to replicate the training recipe that transformed language modeling  ( Kaplan et al., 2020 ) . Vision-language-action (VLA) models and World-Action models (WAMs) fine-tune pretrained VLMs and video generation models, respectively, using large teleoperation corpora  ( Brohan et al., 2023 ;  Kim et al., 2024 ;  Black et al., 2024 ) . However, deploying a new robot or task still requires a dedicated teleoperation corpus of its own  ( O’Neill et al., 2024 ;  Team et al., 2024 ;  Black et al., 2024 ;  Intelligence et al., 2025 ;  Bjorck et al., 2025 ;  Liu et al., 2026 ;  Wang et al., 2026e ;  Yuan et al., 2026 ;  Kim et al., 2026 ;  Bi et al., 2026 ) . Furthermore, the knowledge of such policy models is inherently bounded by the demonstrations they imitate. Consider a mobile robot tasked with loading a car in an unfamiliar house: while opening doors, grasping bags, and placing objects may each be familiar skills, the robot must adapt to novel scenes, visual appearances, and task compositions while discovering new approaches. This adaptation and discovery process is absent during imitation learning on static teleoperation data. Consequently, these policies struggle to generalize and self-improve, even when provided with environment interactions and test-time compute. This limitation motivates a central question:  can robots self-improve and learn to discover new skills through autonomous online experience and active exploration?
Humans learn physical skills by attempting a task, observing the outcome, diagnosing failures, and practicing until their behavior becomes reliable. LLM agents exhibit a similar pattern in software domains: they explore unfamiliar systems by executing programs, inspecting outputs, and revising their work  ( Yang et al., 2024 ) . Instead of training policies exclusively on teleoperated demonstration data, we let  agents program robots directly   ( Lozano-Perez, 1983 )  without hand-designed action primitives. The agent explores online to discover decisions that drive task success, then automates these decision-making principles into modular robot programs that integrate perception, planning, and control. It continuously debugs and tests these programs through online execution. These programs encode the agent’s underlying principles for  how to  generate successful actions based on environment perception, rather than merely mimicking the actions themselves, thereby enabling more robust generalization. Furthermore, the agent can compose, modify, and update these programs when confronting increasingly complex scenes and tasks, continually improving through online experience.
We introduce  RAX (Robot Agent eXploration) , a cognitive architecture for robot agents. Its core organizing principle is  scaling exploration : robot agents should improve by gathering their own online experience and optimizing their programs. In RAX, a general-purpose coding agent receives a natural-language instruction, at most a few goal images or visual demonstrations, and a budget of exploration episodes. It interacts directly through the robot’s perception and control interfaces without requiring human teleoperation or value function guidance. The underlying language model parameters remain fixed and no policies are trained; instead, learning updates a persistent workspace of programs, notes, and verified skills. The agent converts successful interactions into autonomous code programs and stores reusable knowledge for subsequent episodes and tasks.
As exploration scales, we observe several emergent system capabilities: the agent constructs task-relevant 3D perception models, plans actions via pose search in 3D joint space, generates fully automated programs with closed-loop visual and force feedback, and adapts its programs when encountering novel task conditions. Furthermore, we observe agentic behaviors on real robots, including active perception, error recovery, safety guardrails, and active human-robot interaction. For example, the robot executes end-effector contact probing for precise localization when depth measurements are inaccurate. In mobile manipulation experiments, following an initial collision with a cabinet, the agent automatically instantiates a safety check to verify workspace clearance before every base rotation. To test code robustness, the agent actively requests the human operator to vary object layouts, systematically testing the spatial generalization of the autonomous program.
In RAX, we equip the agent with rich multimodal sensing by exposing metric depth and force signals through the robot interface. A unified architecture supports tabletop bimanual arms, dexterous hands, mobile household robots, and humanoids through interfaces to each robot’s sensors, controllers, and kinematic models (  Section   4  ). Unlike standard VLAs or WAMs operating on RGB images alone, the agent autonomously leverages these rich sensing signals to construct 3D point clouds and fit object models directly from perception. It then searches for actions to manipulate these 3D models while accounting for their unique shapes and affordances. Force feedback further enables the agent to resolve spatial uncertainty through contact and enable close-loop control on force signals in insertion tasks. Such multimodal world modeling have been largely absent from generalist policy models, yet naturally align with human cognitive processes.
To enable high-frequency closed-loop control, the agent compiles its decision-making process into executable Python programs that generate actions directly from sensor signals. Unlike prior approaches that rely on human-designed action primitives or policies trained on demonstrations  ( Lu et al., 2026 ;  Xiao et al., 2026 ) , our approach directly generates robot control programs that encapsulate the full perception-planning-control loop, whereas standard policies discard the underlying decision-making process essential for generalization. In practice, we observe the agent writing programs that automatically segment and identify objects in 3D using point-cloud fitting and hue-based identification, then plan actions grounded in this 3D world model, with retry loops and exception handling naturally incorporated into the code. Because actions are planned directly on perceived 3D objects rather than learned through imitation, this approach generalizes to far more diverse object layouts and domain variations than standard VLAs or WAMs. For semantically rich perception in open-world environments, the agent can program direct API calls to LLMs (such as Gemini) within the code to assist with object identification, while incorporating checkpoints and exception handling to step in and verify progress. Over the course of exploration, both action inference latency and token counts decrease as an increasing fraction of decisions becomes automated through code.
As experience scales with exploration, RAX maintains an intra-task memory file system across episodes to record failure lessons and successful strategies, allowing the agent to continually refine its programs. Across multiple tasks and sessions, we maintain a repository of modular programs as verified skills for various tasks and manipulation primitives. Each skill includes the executable code for a specific task, accompanied by execution logs from successful runs, clear preconditions, and verification checkpoints, allowing skills to be composed and reused for complex downstream tasks. In real-world mobile manipulation experiments in household settings, the agent practices individual tasks, each in its own exploration session, such as picking and placing boxes or tucking in office chairs, and commits them as verified skills. When subsequently evaluated on a composite, long-horizon task involving more than six sequential object manipulations, the agent achieves substantial automation and efficiency gains by reusing these stored skills. We envision agents practicing skills in a distributed, parallel fashion to build a rich repository of diverse capabilities, thereby enabling continual lifelong learning.
Using RAX, we conduct  the first large-scale, multi-embodiment, systematic study of
scaling exploration for robot agents , spanning fine-grained precision and long-horizon tasks
across LIBERO, LIBERO-Pro, RoboDojo, DexJoCo, BEHAVIOR-1K, and HumanoidArena in simulation and
on two real robots. We evaluate the resulting policies on unseen scenes, separating
exploration from evaluation. Performance grows steadily with exploration, and on
fine-grained and long-horizon tasks on which state-of-the-art methods rarely succeed, RAX achieves high success rates, surpassing the strongest prior models by +37.4 on average over
five benchmarks (  1  ,   Section   13  ). Without any expert action trajectories, RAX sets a new
state of the art on RoboDojo (+53.4), BEHAVIOR-1K (+38.3), DexJoCo (+31.4), and
LIBERO-Pro (+21.2). On HumanoidArena, it sets a new state of the art (+7.9) with three
teleoperated demonstrations per task, where every baseline uses 100. On real Franka and Rainbow RB-Y1
robots, RAX masters five complex tabletop manipulation tasks and a long-horizon mobile
manipulation task with zero demonstrations, and verified skills accumulated across sessions let
later sessions build on earlier ones.
We summarize our contributions below:
1.
We introduce  RAX  and establish  scaling online exploration  as a foundational principle for agentic robotics. In RAX, the agent operates directly through perception and robot control interfaces without policy training, compiling successful decision sequences into executable code programs that run autonomous execution loops.
2.
Using RAX, we conduct the first systematic, multi-embodiment study of scaling online exploration across simulation and real robot environments. RAX acquires diverse manipulation capabilities solely through autonomous exploration, outperforming state-of-the-art baselines by     +  37.4   +37.4    points on average across five simulation benchmarks, while solving high-precision, deformable, articulated, and long-horizon manipulation tasks on real robots without human demonstrations.
3.
We demonstrate rapid adaptation and continual learning on real robots, showing that generated programs can be selectively updated in response to environmental and task shifts while retaining verified skills in a persistent repository for composition and reuse in complex tasks.
We release the full architecture of RAX, together with its agent instructions, skills,
benchmark integrations, and evaluation protocols, as a generalist robot-agent platform, on
which a new robot can be brought up through an interface alone, without data collection or
policy training.
2  Related Work
Language Models for Robot Control.
A substantial body of work uses pretrained language models as high-level planners or program
generators for robots. SayCan grounds language-model plans in learned
affordances  ( Ahn et al., 2022 ) , Inner Monologue folds environment feedback into iterative
replanning  ( Huang et al., 2022 ) , and Code as Policies, ProgPrompt, and VoxPoser synthesize
executable programs, situated task plans, or 3D value maps directly from
instructions  ( Liang et al., 2023 ;  Singh et al., 2022 ;  Huang et al., 2023 ) . These methods
typically invoke the model zero-shot or with a few in-context examples, producing a plan or a
program that is executed with little opportunity to improve from experience.  RAX
instead treats the language model as a  learner : it interacts with the robot over many
episodes and revises its perception and control programs according to what it observes.
Agentic Robot Learning.
More recently, several works let coding agents improve robot behavior through interaction.
ENPIRE runs agents in a closed loop of automatic reset, rollout, and policy training on a
fleet of bimanual arms, and accelerates discovery by scaling the fleet  ( Xiao et al., 2026 ) ;
FAEA and Encore refine policy programs from execution feedback, the latter starting from a few
teleoperated demonstrations  ( Tsui et al., 2026 ;  Kang et al., 2026 ) ; Baton explores long-horizon
tasks subtask by subtask with transition-aware memory  ( Xu et al., 2026 ) ; SimEX develops robot
skills in a simulator reconstructed from the physical workspace before a few trials on the
real robot  ( Hu et al., 2026 ) ; RPG practices in simulation on tasks derived from an offline
trajectory dataset and refines a library of reusable skills  ( Wang et al., 2026d ) ; EmbodiedSWE
turns coding-agent solutions into training data for vision-language-action
models  ( You et al., 2026 ) ; and CaP-X benchmarks coding agents on
manipulation  ( Fu et al., 2026 ) . These works establish that agents can improve robot behavior
through interaction, and have so far demonstrated it mainly in tabletop manipulation with
parallel-jaw
grippers  ( Xiao et al., 2026 ;  Tsui et al., 2026 ;  Kang et al., 2026 ;  Xu et al., 2026 ;  Hu et al., 2026 ;  Wang et al., 2026d ) ,
often on a single platform  ( Xiao et al., 2026 ;  Hu et al., 2026 ;  Wang et al., 2026d ) , with humanoid and
mobile settings explored through pretrained locomotion  ( You et al., 2026 )  or short
pick-up tasks  ( Fu et al., 2026 ) . Several also draw on demonstrations  ( Kang et al., 2026 ) ,
offline datasets  ( Wang et al., 2026d ) , reconstructed simulators  ( Hu et al., 2026 ) , or neural
policy training  ( Xiao et al., 2026 ) .  RAX  complements these efforts: it learns each
task on the robot itself, from its own exploration, and does so across single-arm and bimanual
manipulators, dexterous hands, mobile manipulators performing long-horizon household
activities, and legged humanoids whose locomotion the agent constructs itself, on established
benchmarks and on real robots. On this basis, it studies systematically how performance scales
with exploration, with 3D perception, and with accumulated memory.
Scaling Robot Learning.
Vision-language-action models  ( Brohan et al., 2023 ;  Kim et al., 2024 ;  Black et al., 2024 )  and imitation
learning methods  ( Zhao et al., 2023 ;  Chi et al., 2025 )  improve robot capability by scaling
demonstration data and model size, and world action models extend this recipe by learning to
predict how the scene evolves together with the actions that produce
it  ( Wang et al., 2026e ;  Yuan et al., 2026 ;  Kim et al., 2026 ;  Bi et al., 2026 ) . To cover multiple embodiments, generalist
policies pool demonstrations across robots into a single training
mixture  ( O’Neill et al., 2024 ;  Team et al., 2024 ;  Doshi et al., 2024 ;  Intelligence et al., 2025 ;  Bjorck et al., 2025 ) ,
and a robot outside this mixture requires data of its own and further fine-tuning. In language
modeling, computation spent at inference has emerged as a further scaling
axis  ( Guo et al., 2025 ;  OpenAI, 2024 ) .  RAX  instead studies how robot
capability grows with online experience acquired and organized by the agent itself, without
additional demonstrations or parameter updates. Because this experience is gathered on the
robot at hand, RAX extends to a new embodiment without pooled data, and adapts to it within a
few episodes of exploration.
Memory and Cognitive Architectures.
Language agents can retain experience as explicit memory: Voyager grows a library of code
skills through open-ended exploration in a game  ( Wang et al., 2023 ) , and Reflexion and
ExpeL distill feedback into textual lessons that improve later
attempts  ( Shinn et al., 2023 ;  Zhao et al., 2024 ) . At a broader level, classical cognitive
architectures such as Soar and ACT-R structure intelligent behavior around perception,
memory, and deliberation  ( Laird et al., 1987 ;  Anderson et al., 2004 ) , CoALA revisits this structure
for language agents  ( Sumers et al., 2023 ) , and Sutton’s common model of the intelligent
agent  ( Sutton, 2022 )  and OaK architecture  ( Sutton et al., 2022 )  hold that all
task-specific knowledge should be acquired at runtime from the agent’s own experience, a view
developed further as the era of experience  ( Silver and Sutton,  ) .  RAX  brings this
view to physical robots, where every skill is executable control code that enters memory only
after it succeeds without supervision.
3  The RAX Cognitive Architecture
Inspired by Sutton’s OaK architecture  ( Sutton et al., 2022 ) , RAX acquires all task-specific knowledge
at runtime from the agent’s own experience. Building on task-agnostic robot control interfaces and low-level controllers, the agent autonomously develops task-specific perception, manipulation strategies, and executable skills through exploration. The following modules surround the language-model core:  perception and control ,
autonomous robot program , and  memory for continual learning  (  Figure   2  ).
Figure 2 :   System architecture and self-improving loop of RAX.  The coding agent, powered by a frozen LLM, interacts with physical hardware across an isolation boundary using multimodal perception and control SDK interfaces. By reflecting on execution outcomes, the agent continually updates a persistent memory system containing working context, task notes, and a versioned repository of verified skills. During exploration, the agent compiles its perception and planning logic into standalone Python control programs that execute high-frequency loops directly on the robot. When encountering perception or planning failures due to environment variations, the program raises an exception ( raise Unsure() ), delegating control back to the agent to make adjustments and refine the codebase.
3.1  Multimodal Perception
To build a physically accurate model of the world, we equip the agent with multimodal sensory inputs, including RGB images, depth maps, camera parameters, and force signals. The agent can thus construct 3D world models using depth data while regulating contact via force feedback. Notably, the 3D perception and object model fitting behaviors completely emerges from the agent exploration process, while we provide no skills, instructions or examples regarding specific usage of these multimodal sensing signals.
A real-robot task illustrates this process: opening an air fryer’s drawer, placing a banana in its basket, and closing the drawer (  Figure   3  ). The agent lifts RGB-D observations into a point cloud in the robot’s base frame and constructs a geometric model of the fryer from its own measurements, localizing it in each new scene layout by fitting the fryer’s axis and handle direction with robust estimators. Because the drawer moves, the model is articulated, consisting of a fixed body and a drawer that slides along a prismatic joint. The agent plans every action, including grasping, pulling, and releasing, on this model and checks each motion for collisions.   Section   14.2.1   details the model, the estimators, and how the program uses them. On a humanoid, the same process yields a gravity-aligned frame from the floor plane, landmarks for self-localization, and tracking updates after every gait cycle.

3.2  Planning and Control
Given the accurate world model, the agent then directly plans the robot actions in 3D world using robot control SDK and kinematic solvers. As the interface between the agent and the physical robot,
we expose the robot’s control SDK as MCP tools, together with helpers such as an inverse
kinematics (IK) solver and the robot’s URDF model. With these tools, the agent plans each motion
and searches for feasible trajectories, accounting for the robot’s posture, collisions, and
joint limits. In the air fryer task (  Section   14.2  ), the drawer’s handle has a short horizontal arm on top and
a grip hanging down from its end. Grasping the grip from the front, as a person would, leaves
the arm almost no joint margin near its base for the pull, so the agent grasps the short arm from
above and pulls the drawer open in 3 cm steps (actions 1 and 2 in   Figure   3  (b)).
The 18 cm banana barely fits the 19 cm basket: released from a level hand, it touched the top
of the fryer, and the opening fingers would hit the fryer’s body. The agent therefore tilts the
hand by     60  ∘   60^{\circ}    about the banana’s axis, with the banana’s concave side toward the fryer, and
releases it with its middle just beyond the basket’s center (action 3). The agent found these
motions itself, by searching through the control tools during exploration, without human advice
or demonstrations;   Figure   27   shows them on the real robot.
3.3  From Exploration to Autonomous Robot Program
Generating each action with LLM-reasoning is expensive and slow. To enable high-frequency close-loop planning, the agent automates the decision process into a autonomous robot program with code that can directly execute to complete the task. Unlike prior work on coding agents for robotics  ( Lu et al., 2026 ;  Xiao et al., 2026 ) , we do not rely on hand-designed primitive skills or train policies by imitating human demonstrations, which inherently restricts scaling beyond human capability  ( Sutton, 2019 ) . Instead, RAX agents directly control the robot without pre-trained policies or hand-coded primitives, progressively transferring control from high-level deliberation to autonomous code programs, resulting in  autonomous decision-making through agent-native coding . Initially, the agent controls the robot through tool calls while perceiving the scene via the core LLM. Upon achieving task success, it compiles these decisions into code programs that run independently of main-agent deliberation. For example, after identifying object shapes and geometries, the agent generates a 3D object model and automatically estimates its position and pose using depth-derived point clouds when encountering new layouts. This eliminates the need for the main agent to repeatedly perceive and process raw images, which is slow and costly.
The agent decomposes tasks into stages and implements modular skills with programs that check preconditions, execute motions, and verify outcomes, operating much like a software development process through testing, debugging, and code versioning. Empirical measurements from exploration, such as gait-cycle distance or reliable grasp orientation, become program parameters. The agent tests successive code versions during exploration and uses stage-level failures to identify which specific skill requires revision. The hammer-delivery program on the HumanoidArena DoubleDesk task (  Section   11.3  ), for instance, decouples approach, grasp, transit, obstacle crossing, and placement so that every failure traces directly to a specific stage (  Figure   20  ).
Once reliable, the program is tested unattended in a new scene with exception handling and agent monitoring the generated logs in case of emergency situations. If perception or planning fails due to significant open-world variations, the program throws an exception, enabling the agent to step in, perceive the environment, and make necessary adjustments. Through scaled program testing and debugging during exploration, the result is a  fully automated program  that perceives, decides, and acts in unseen scenes with minimal or no agent intervention. Automated perception and planning allow it to adapt to new layouts in ways that replayed trajectories cannot. Deployment thus spans a continuum from the agent acting alone to a fully automated program, along which the agent advances as it accumulates experience.
3.4  Continual Learning with Memory
As online experience scales and decision-making becomes automated, RAX continually expands its capabilities by constructing persistent memory systems for reuse across episodes and tasks. Persistent memory carries experience at multiple timescales (  Figure   2  , top).  Within a session , notes
retain the current strategy, confirmed results, failed approaches, and useful parameters
through context compression, which lives in the agent scratch pad in workspace.  Across sessions and tasks , a skill  repository  stores each skill with its code, the conditions under which it
applies, and evidence of its execution. It is continually contributed and merged by agents across different sessions and tasks, evolving with more experience.
A skill enters the repository only after it executes successfully without supervision, together
with the evidence of that execution. Later sessions retrieve and compose skills that are
known to work instead of rediscovering the same behavior. The benefit is largest on real
robots, where every episode costs operator time: a grasp or a drawer-opening skill becomes a
building block for longer tasks, and each session leaves the library more capable than it
found it.
Learning via Practice
Much like humans, who repeatedly practice individual skills to gain proficiency before rehearsing complex, long-horizon tasks end-to-end, robot agents follow a similar cognitive progression. Here we depart from the conventional per-task training and evaluation protocol in robotics and frame robot learning as a continual process, where it generates and refines skills through practice and gradually moves on to more complex tasks by reusing the skills in the repository. Taking household tasks as an example, we let the agent practice individual subtasks, such as picking and placing (PnP) boxes and buckets or sorting tabletop items; each practice session is an exploration session on a single sub-task. During this process, the agent develops autonomous programs, rehearses them end-to-end to improve robustness, and eventually commits them to a multi-task skill library. During deployment on long-horizon compositional tasks, the agent reuses these subtask skills directly while verifying execution evidence and preconditions to handle environmental variations beyond those encountered during practice. Such skill acquisition and practice can also occur in parallel across multiple robots and tasks, enabling collective learning across multi-robot systems.
3.5  Parallel Multi-Agent and Multi-Environment Exploration
Online exploration can be time-consuming due to the latency of agent reasoning and environment execution. To accelerate this process, we parallelize exploration across multiple agents and environments, enabling agents to evaluate distinct strategies concurrently rather than sequentially within a single environment. In our simulation experiments, leveraging parallel environments and agents reduces the wall-clock time required to reach target performance by more than     2  ×   2\times   , highlighting the scalability of parallelized exploration for robotic systems.

4  The RAX System
RAX supports a wide range of embodiments in simulation and in the real world, including
single-arm and bimanual manipulators, dexterous hands, mobile manipulators, and humanoids, with
one agent architecture. To do so, it adopts a separation familiar from software engineering, in
which a frontend is kept apart from the backend that serves it. In RAX, the backend is the robot’s physical stack: the
hardware drivers or the simulator, the low-level controllers, the sensor pipelines, and the
safeguards around them. The frontend is the agent’s workspace, where the agent observes,
decides, and acts, and where it writes the programs that encode its decision logic. The two meet
only at a tool interface (  Figure   4  ), and the same frontend connects to the backend of every platform, from
the real Franka and Rainbow RB-Y1 robots to each simulated benchmark. The agent never touches the
backend: it cannot modify controllers, drivers, or robot infrastructure. Because the agent acts only through these tools, its programs contain the
decision logic of a task, namely perception, planning, and the checks between stages, while
low-level control, from joint-level PD control to whole-body motion tracking on humanoids, and
the enforcement of safety limits remain in the backend. The remainder of this
section describes the separation and what each side provides (  Section   4.1  ), and the
control interface through which one frontend drives arms, dexterous hands, mobile manipulators,
and humanoids (  Section   4.2  ).
4.1  Frontend–Backend Separation
Figure 4 :   Frontend–backend separation.  The agent and its programs act only through the
tool interface; the backend owns control, sensing, and safeguards on every platform.
On a real robot, the backend owns everything that keeps the hardware calibrated and safe. It runs
the vendor’s drivers and real-time controllers, serves calibrated RGB-D images together with the
intrinsics and poses of their cameras, and records the robot’s sensors and state continuously,
so that the agent can review the outcome of an action after the fact. It also enforces the
safeguards. Motion is enabled only while an operator has armed the robot, and disarming halts it
immediately; every motion command is validated before execution against workspace bounds, joint
limits, and self-collision, and on the RB-Y1 mobile manipulator also against joint load. A command that violates
a limit is refused before the robot moves, together with the limit it violated, so that the agent
can change its approach.
The frontend receives exactly two things from the system, tools and skills. The  tools  expose as much of the backend as
possible: observation, raw control, and model-based helpers in the form of forward and inverse
kinematics, motion planning where the platform offers it, and a preview that executes a candidate
motion on the robot model alone, without the scene. They also provide the geometric primitives on
which perception is built, namely the back-projection of pixels to metric 3D points, the poses of
the cameras in the robot’s frame, and the kinematic chain from each camera to the end-effectors.
The  skills  are documents that describe how to work with these tools: the robot’s frames,
action spaces, rates, limits, and failure modes, the conventions of perception, and the workflow
of exploration and memory. They are organized along four axes, namely task strategy,
coordination, perception, and robot-specific control, and are composed into a single workspace
for each session according to its embodiment and observation mode. Everything that solves a task,
from object models and perception pipelines to grasps and control code, is written by the agent,
which works in an isolated container with a persistent workspace and standard programming tools.
Figure 5 :   A long-horizon task on the real RB-Y1.  The agent composes six sub-tasks from skills
learned in earlier sessions. It finds the cups from Gemini’s rim points and depth, measures the desk
edge by picking points in the head image, and plans the base routes on a model of the scene.
This division has three consequences. First, programs written by the agent call exactly
the tools that the agent itself calls, so code developed interactively runs unchanged as
a fully automated program. Second, the interface returns compact results, consisting of
structured state and the final image of each motion, while the complete images and actions of
every motion are stored as episodic evidence that the agent retrieves on demand, which keeps the
agent’s context small over sessions that last many hours. Third, on real robots, the skills that
agents verify are kept in a versioned repository for each robot, in which every session works on
its own branch, and a contribution is merged only after its structure, its entry point, and the
evidence of its unattended success have been validated.
Most importantly, the separation makes RAX multi-embodiment by construction. Bringing up a new
robot requires only a backend that exposes it through the tool interface, together with documentation of its control and
sensing interfaces, while the frontend, the organization of
memory, and the evaluation protocol are
shared across all platforms. No expert teleoperation data is collected and no policy is trained to bring a robot into
RAX. The single-arm, bimanual, dexterous, mobile, and humanoid embodiments of our experiments,
in simulation and in the real world, differ only in their backends and in the
documentation of their interfaces, and the agent learns to control each of them through exploration.
4.2  Multi-Embodiment Control Interface
RAX adopts a layered control design. Low-level controllers, from joint position and impedance controllers to whole-body motion
trackers, run in the backend and are responsible for high-rate tracking and
stability, while the agent makes decisions at the level of short action chunks and motion goals.
Each platform exposes raw control for full expressiveness, together with model-based helpers in
the form of forward and inverse kinematics, collision-aware motion
planning  ( Sundaralingam et al., 2023 ) , and a robot-only preview that executes a candidate
motion on the robot model without the scene. The agent thus chooses its own level of
abstraction, from individual joint targets to planned free-space motions.

On the real robots, the backend wraps each vendor’s own control stack. The Franka FR3 arm runs joint impedance control, and the agent commands straight-line Cartesian
moves of the tool center point, joint-space moves whose paths are checked against the workspace
and the table before the arm moves, and force-controlled grasps that close the gripper to a
target width with a set force. The Rainbow RB-Y1, a wheeled mobile manipulator with a torso, two arms, and
a two-joint head that carries an RGB-D camera, runs joint position control on its robot controller,
which also accepts Cartesian IK commands for the torso and arms. The agent commands end-effector
poses, joint-space postures of the torso, arms, and head, coordinated motions of the torso and arms, motions
of the differential-drive base, and the gaze of the head camera. It can query the vendor’s
kinematic model for the collisions, joint load, and center of mass of any posture, and dry-run any
motion command to learn whether it would be accepted. Neither robot offers a motion planner, so
the agent composes long motions from short checked moves through clear intermediate postures.
On the HumanoidArena
benchmark  ( Wang et al., 2026b ) , the agent commands the Unitree G1 through whole-body
kinematic references rather than joint torques: each reference specifies a desired heading, a
full joint configuration, and hand commands, and a whole-body motion tracker converts these references into balanced whole-body motion. Because the robot moves through space only by
stepping, locomotion is not provided as a primitive but must be constructed by the agent from leg
references, and agents do so by measuring their own gait, calibrating step length, and composing
walking, turning, and stepping over obstacles from these measurements.
On DexJoCo  ( Wang et al., 2026a ) , the official
operational-space controller tracks the flange pose of each arm while position actuators drive
the sixteen joints of each Allegro hand, and no motion planner is
provided, so the agent plans the motion of each arm and the configuration of each hand itself. The remaining simulated
platforms span the same range of abstraction. The single arm of LIBERO and
LIBERO-Pro  ( Liu et al., 2023 ;  Zhou et al., 2025 )  is driven through the benchmark’s own
operational-space controller by relative end-effector commands alone, whereas on
RoboDojo  ( Chen et al., 2026a )  and BEHAVIOR-1K  ( Li et al., 2023 )  the native controllers
execute joint targets under each benchmark’s own dynamics, and inverse kinematics and motion
planning are offered as helpers alongside raw control rather than as replacements for it. Motion
planning accounts for the robot and static structures but never for task objects, which the agent
must perceive itself.
5  Experiments
In this section we report our simulation benchmark results as well as case studies on both simulation and real robot experiments.
5.1  Setup
We comprehensively evaluate RAX in both simulated environments and on real-world robotic hardware. In simulation, the evaluation spans six benchmarks covering single-arm, bimanual, dexterous, mobile, and humanoid embodiments: RoboDojo, BEHAVIOR-1K, HumanoidArena, DexJoCo, LIBERO, and LIBERO-Pro. In each session, a coding agent starts in a localized workspace containing only the platform’s baseline skills. Guided by a task description and RGB-D observations, the agent explores training scenes within a strictly defined episode budget. The submitted code is then executed as a fully automated program under each benchmark’s official evaluation protocol (  Section   10  ).
On physical robots, RAX is deployed on a Franka FR3 manipulator to master five distinct tabletop tasks: (1)  memory , tracking and finding a hidden cube randomly shuffled under four cups (  Section   14.1  ); (2)  articulated objects , opening an air fryer drawer, inserting a banana, and closing it (  Section   14.2  ); (3)  deformable objects , wiping a stain off a table using a wet towel (  Section   14.3  ); (4)  precision , inserting pegs into a ManipulationNet board with a stringent 0.1,mm clearance (  Section   14.4  ); and (5)  precision and long horizon , dismantling and rebuilding a Bandu tower of irregular pieces (  Section   14.5  ).
Additionally, we evaluate RAX on a Rainbow RB-Y1 mobile manipulator to solve a long-horizon logistical task. This involves pulling out a chair, stacking cups, picking up a banana, loading the items into a basket, carrying the basket to a cabinet, tucking the chair back, and subsequently transferring a box to the cabinet (  Section   14.6  ). Crucially, the agent receives only natural-language instructions and zero teleoperated demonstrations. It is designed to autonomously evaluate its own success criteria, only prompting a human operator to reset the physical scene between trials.

Setup.

Setup.

5.3  Ablations
In this section we ablate the key design choices of our system, including parallel exploration with multi-agent and multiple environments, the effect of depth sensing over RGB-only observations, and the evolve of inference tokens and inference time over exploration.
5.3.1  Parallelization
Exploration can also be parallelized
(  Section   3.5  ): the same budget of
exploration episodes is distributed across    K  K    parallel environments, explored by a team of
cooperating agents that share a common workspace. In the same way that multiple agents
scale test-time compute in parallel rather than purely serially, trading some efficiency for
wall-clock time, parallel environments let a team of agents consume an exploration budget
concurrently. We parallelize exploration on  make
toast . All sessions use RGB-D observations, an image sequence of one successful completion,
and instructions that summarize the official task code, including its numeric success
thresholds; the fully automated program is evaluated on the same 32 unseen scenes. Parallelization
reduces the time needed to consume the exploration budget for both agents
(  Table   7  ). With four agents in four environments, Claude Code reaches a score of
92.2 in 4.9 hours, against 63.3 in 13.7 hours for a single agent with a larger budget; with
two agents in two environments, Codex matches its single-agent score in 9.2 hours instead of
14.2.

Case study: perception with and without depth.
To understand where this gap comes from, we inspect the fully automated programs submitted
by the RGB-D and RGB-only agents on make toast random with a budget of 32 episodes. Both agents use the
vision-language model in the same role, to point at semantic image locations such as the
toaster slots, the top crust of a bread slice, and the lever. They differ in how they turn
these image points into motion.
With depth.  The RGB-D agent lifts every image point into a metric 3D point and
builds the task’s geometry from these points. It first refines each slot opening by
fitting a line to its visible contour, then measures both rim endpoints of each slot in 3D,
from which it derives the slot centers and their common heading. On the bread, it measures
two points along the top crust and one on the near side, and recovers the slice’s full 3D
orientation from the plane through these points. After the grasp, it measures the slice
again in the wrist camera to obtain its pose in the hand, and repeats this measurement above
the slot to correct any slip before release. The agent also uses metric geometry to verify
its perception: a measurement is rejected when a rim point does not lie within a narrow band
at the toaster’s roof height, when the two rim endpoints are not 9 to 20 cm apart, or when
the two slots are not 2.6 to 7.5 cm apart, and a press of the lever counts only when the
lever is measured to have travelled 2.5 to 13 cm downward.
Without depth.  The RGB-only agent does not give up on 3D reasoning; it
reconstructs a coarse camera model of its own. It maps overhead-camera pixels to table
coordinates through a linear calibration at an assumed height, about 1.8 mm per pixel
across the image and 1.4 mm per pixel along it, and then refines every target by visual
servoing in the wrist camera: it moves the gripper until the target is centered, with
hand-tuned gains of 0.4 to 0.8 mm per pixel, and rotates it until the slot or the bread is
aligned in the image. The quantities that depth would provide are replaced by constants,
including the grasp and release heights, the 3.8 cm spacing between the slots, and the
height to which the lever is pressed, and success is judged by asking the vision-language
model whether a slice is held or seated. These approximations hold only where the scene
matches the agent’s assumptions. In evaluation, 36 of its 45 episodes ended in the lever
stage without success, the step at which a fixed press height replaces a measured one,
against 8 successes for the RGB-D agent.
5.3.3  Inference Time and Tokens
Here we demonstrate the decrease of inference wall time and output tokens with exploration as more and more decisions are being automated with programs.
Simulation
As the agent compiles its experience into autonomous code programs, the computational overhead of action generation decreases substantially. We evaluate this efficiency gain across two benchmark tasks:  loading the car  in BEHAVIOR-1K (128 exploration episodes across two parallel environments) and  make toast random  in RoboDojo (64 exploration episodes). We define episode  inference time  as the cumulative wall-clock latency dedicated to action generation—excluding simulator and hardware step times—regardless of whether actions stem from direct LLM deliberation, code program execution, or a hybrid mode.   Figure   7   tracks inference latency and output token consumption across all successful exploration episodes. On  loading the car , the initial successful episode required 123 minutes of inference time and 254k output tokens. By the final exploration episode, inference overhead dropped to 4 minutes and 4k tokens, while environment execution time remained over 1 hour per episode. Similarly, on  make toast random , initial task completion required 17 minutes of inference latency. Once execution transitioned to the compiled program, inference latency for the final agent-monitored successes fell to 6 seconds per episode—matching the 3–7 seconds observed during standalone program rehearsals (which accounted for 7 of the 15 total successes).

Real robots
Similar efficiency trends hold on real robots using the Franka manipulator (  Table   9  ). We evaluate air fryer manipulation (  Section   14.2  ) and Bandu tower assembly (  Section   14.5  ), comparing an initial trial in which the agent generates each action via active deliberation against a subsequent execution of the compiled autonomous program. In both paradigms, the system actuates the robot through identical tool interfaces, with robot time defined as the duration spent executing arm, gripper, and visual perception calls. For the air fryer task, initial task completion (including online exploration) required 72 minutes of inference latency and 262k output tokens, against 3 minutes of robot time. Upon compilation, the initial autonomous run required only 18 seconds of inference latency (attributable entirely to local programmatic execution), with four subsequent unattended trials consistently yielding latencies between 18 and 23 seconds. Similarly, on the Bandu tower, step-by-step LLM deliberation to assemble six blocks required 17 minutes of inference latency; once compiled, autonomous assembly of seven blocks completed with 10 seconds of program overhead alongside 11 minutes of continuous robot execution. During these autonomous runs, control proceeded without human intervention or online LLM action synthesis, while background monitoring generated at most 2.2k tokens per run in parallel without imposing latency on robot execution.

5.4  Intriguing Emerging Agentic Behaviors with Scaling Exploration

outcome of each action with a new measurement.

Simulation.
On the bimanual Tower of Hanoi of DexJoCo (  Section   11.2  ), the agent
received no model of its Allegro hands. It spent its first episode on its own hand: it moved single
joints, lifted the wrist cameras’ depth into points to see what each joint moves, segmented the
white fingertip caps, and fitted the fingertip offsets on which every grasp of its program is built;
its thumb offset lies within 1.1 mm of the official model it never saw. On the LIBERO-Long task of putting two cans into a basket
(  Section   11.1  ), the program perceives the scene anew in every round; before each
grasp, it hovers 7 cm above the can, refits the lid from the wrist camera, and rejects a top that
is not can-shaped. Because the agent-view camera cannot see the floor of the basket, the program
maps the basket from the wrist camera while it holds the first can, and maps it again after the
first release. On the bimanual Tower of Hanoi of DexJoCo (  Section   11.2  ), the program verifies
every lift by measuring the held disk from three cameras and pinches again when the disk rose less
than half of the lift; after placing the red disk, it measures the disk’s top again and finds it on
average 0.66 mm below the height it predicted. On the humanoid that carries a hammer over a bar
(  Section   11.3  ), the program perceives anew at every stage and before every step at the
bar, and it confirms a grasp by measuring the height of the handle again. Without depth, the
RGB-only agent recovers metric relations by moving the robot by known amounts and servoing on the
wrist camera (  Section   5.3.2  ).
Real robot.

5.4.2  Error Recovery and Safety
On real robots, the agent’s mistakes have physical consequences, and it turns each one into a rule
that its later programs follow (  Figure   9  ). On the RB-Y1, an in-place turn that the agent
planned by hand swung the rear of the base into a cabinet; from then on, the agent checked every
base move against the area the base sweeps. Lifting a bucket while squatting overloaded a wrist and
stopped the robot; standing up before the lift, a correction from the operator, resolved it, and
the agent kept it as a rule in its skill. On the Franka, an unusual arm posture drove the elbow
into a camera; the agent then restricted itself to natural arm postures, kept the arm away from
the cameras, and recalibrated the bumped camera itself (  Section   14.2.1  ). In simulation, the
humanoid crosses a bar only from foot placements that its own falls showed to be safe
(  Section   11.3  ).

5.4.3  Human–Robot Interaction
The agent reaches the operator through a request tool and uses it with purpose (  Figure   10  ). On
the ManipulationNet board, after the board shifted during its attempts at tight fits, it asked the
operator to tape the board to the table. On the air fryer (  Section   14.2  ), it refused to pick a banana placed in front
of the camera it had hit earlier, because its forearm would pass within about 1 cm of the camera, and
asked for the banana to be moved. After unattended successes, it asked the operator to move and rotate
the fryer, in effect designing its own tests of generalization: across runs 6 to 10, the fryer moved
by up to 7 cm and its handle turned by up to 18 ∘ , and the program succeeded unattended in every
new placement but one, where it needed help and which exposed two errors in its program that the
agent then fixed.
5.5  Continual Learning
In this section, we demonstrate how RAX achieves continual learning with robot programs: by reusing skills learned in earlier exploration sessions, and by rapidly adapting its programs when the environment or the task changes.
5.5.1  Reusing Skills
On the RB-Y1 mobile manipulator, RAX acquires skills through isolated exploration sessions and reuses them to solve long-horizon compositional tasks (  Figure   11  ). In initial sessions, the agent independently learned to park and tuck an office chair, stack nested cups, transport a bucket by its rim onto a cabinet, and pick and place a box. Each skill was committed to the repository only after achieving successful end-to-end execution, stored as a versioned program bound to explicit precondition checks. The multi-stage tidy-up task (  Figure   5  ) evaluates the composition of these skills under a single high-level goal: park the chair, stack the cups, place the cups and a banana inside the bucket, transport the bucket onto the cabinet, tuck the chair back under the desk, and finally pick the box onto the other empty cabinet.
Skills are called, not relearned
In the final execution of the tidy-up task, every stage is resolved by composing stored skills from the repository (  Figure   11  ). The agent executes the chair skill sequentially: it estimates the chair geometry, plans a collision-free motion path, grasps the backrest, navigates along the path, and releases the target. It invokes the cup-stacking skill using semantic visual grounding from the current scene, applying fine-grained closed-loop offsets prior to insertion. For the bucket and box skills, the agent parameterizes execution using real-time perception data, such as the estimated cabinet boundary derived from depth sensing. To bridge gaps between stored skills, the agent dynamically synthesizes ad-hoc code—such as extending the grasp planner to handle a banana, commanding torso elevation prior to transit, and re-estimating desk pose before final chair insertion.
Skills are refined in use
Across three iterations of the tidy-up task, the agent iteratively updated program versions rather than rewriting entire control loops. The bucket and box skills required minor programmatic adjustments (   ∼  \sim   25 out of more than 1200 lines) to integrate dynamic cabinet-edge measurements from onboard depth perception. Skills encountering greater environmental domain shift underwent larger revisions: following two failed grasp attempts, the agent updated the chair skill to grasp 4 cm deeper, while extending the cup-stacking skill to support picking additional object classes.

Repository expansion
Intermediary control code synthesized by the agent to bridge task stages is modularized and saved as new skills. For instance, a synthesized  hand-reach  primitive was automatically abstracted, committed to the repository, and subsequently reused across both the chair-manipulation and cup-stacking routines.
5.5.2  Rapid Adaptation of Programs
When task conditions vary post-deployment, RAX preserves valid program subroutines and selectively updates only the modules invalidated by environmental shifts (  Figure   12  ). On the Franka manipulator, two end-to-end autonomous programs were adapted to novel task variants within the same session.
Find the cube
In a hidden-object task, the physical occlusion sequence was modified: rather than directly inverting a cup over the target cube, the cube was placed inside an upright cup prior to inversion. The original program detected no covering cup and safely halted execution via exception handling without initiating ungrounded motion. The agent extended its perception pipeline with a detector for cubes contained within upright cups, validated the new logic against current and historical sensor logs, and resumed execution to complete the task (  Figure   22  ). Crucially, the cup-tracking, execution-monitoring, and removal routines were reused without modification. When substituting the cube with a red wedge, the agent generalized its geometric object representation from a fixed cube primitive to an object parameterized by estimated dimensions, color, and height, adjusting grasp synthesis accordingly while preserving 20 of the original 41 program functions (including the tracking pipeline;   Figure   23  ).
Wiping with paper towels
Following the acquisition of a reliable surface-wiping skill using a wet cloth, the task was extended to require pulling disposable paper towels from a dispenser box, executing the wiping motion, and discarding used towels into a receptacle. The agent synthesized a composite program that imported the original wiping module as a dependency. The new program reused existing subroutines for stain segmentation against the table background, reachable workspace estimation, pressing by position control (    12  ​  mm   12\,\text{mm}    below the measured surface contact, along a serpentine trajectory), and post-wipe residue verification. Only paper-handling subroutines were added: locating the dispenser box and disposal bin, extracting individual sheets onto the stain, discarding the crumpled towel, and clearing loose paper from the workspace. The stain was removed in both wet runs, although leftover sheets still had to be cleared with supervised scripts (  Section   14.3  ,   Figure   29  ).
6  Discussion
Progress in robot learning has largely been driven by collecting more demonstrations and
training larger models. Our results show that a capable agent, when allowed to explore, continues to
improve with the experience it accumulates, without teleoperation and without updates to its
parameters. Because this form of learning relies on general-purpose agents whose capabilities are
advancing rapidly in other domains, every improvement in those agents translates directly into
improved robot learning.
The knowledge acquired by RAX agents takes the form of perception and control programs,
skills, and notes. In this form, knowledge executes at the rate of the robot, can be inspected
and verified, composes into longer behaviors, and transfers across tasks, and we
expect code to play the same role for learning from experience that network parameters play
for learning from data. Since the instructions, skills, and memory structures of RAX are
themselves code and text, a natural next step is to let agents improve the architecture itself
from experience, and to share verified skills across fleets of robots, so that a skill learned
by one robot becomes available to all.

9  Agent Instructions and Skills
Every session starts from the same workspace template: one instruction file and a folder of skills,
written once and shared by all platforms ( auto_research_agent/  and  agent_skills/
in our code). Robot-specific facts, such as tool names, cameras, and control rates, are filled in when
the workspace is built, so the agent reads the same instructions on every robot.
Instructions.
The instruction file fixes the order of work rather than how to solve any
task. The agent first reads the task text and its own notes from earlier sessions, then (1) solves the
task by controlling the robot directly through tools until it confirms success, (2) turns what it did
into a program whose steps check their preconditions, verify their results, and report states they
were not built for, (3) runs that program on every further exploration episode, stepping in where it falls
short and fixing the code, and (4) keeps its notes, code, and a hand-off note current, since only
those carry over to later sessions. In benchmark sessions it then freezes the program, rehearses it
once end to end without help, and submits it. The file also states the budget rules: new layouts
in every episode, so scene geometry is measured again rather than assumed, and a blocker is
reported rather than bypassed.
Skills.
Skills are short documents that the agent opens when it reaches the step they
cover. They are grouped by axis, task strategy, coordination, perception, and robot control, and a
session receives only the layers that match its robot and observation mode. The task and
coordination skills are robot-agnostic (  Table   12  ); the perception and control layers give
each robot’s interface under the same names, so a task skill can point to, for example, the
robot’s interface or its free-space motion without knowing which robot it runs on.

10  Benchmarks and Tasks
This section gives the protocol that all simulation experiments share and then the setting of
each benchmark and its tasks. The real-robot tasks are described in   Section   14  .
10.1  Sessions
Agents.
Every experiment is a session of one coding agent in its own command-line
harness: Claude Code with Claude Opus 5.5 or, on four RoboDojo tasks and one BEHAVIOR-1K task,
Codex with a GPT-6 model, at the xhigh reasoning effort unless stated otherwise. A session
provides one or more simulated environments; with more than one, the agent may start subagents
of the same model, which share its workspace and its budget. The weights of the model are never
updated.
Workspace.
The agent starts from an empty workspace. Its folders for code, notes, and
outputs are empty, and it holds only the instructions of the harness, the task description, the
contract of the tool interface, and the skills of the platform, composed for the embodiment and
the observation mode of the session (  Section   9  ); the agent keeps no memory from earlier
sessions. It runs in a container without network access, with 16 GB of memory and four CPUs,
and reaches the simulator only through its tools. Every program it registers runs in a fresh
container with 8 GB of memory, four CPUs, and no network access.
Task information.
The task description is generated from the public definition of the
task; its content differs between benchmarks and is given below. Images of the completed task
are frames of successful official demonstrations, either the final frame of each or a sequence of
keyframes along each. They contain no actions and no states, and only the exploring agent sees
them, never its programs. During an interactive episode, the agent may ask the benchmark’s
evaluator whether the task is complete.
Budget and scenes.
The exploration budget counts exploration episodes. A single ledger
charges every episode start and every rehearsal, across all environments and subagents, and the
agent sees how many episodes remain. The budget is an upper bound, since submission ends
exploration. Exploration scenes come in a fixed order, which the agent cannot choose, from the
training distribution of the benchmark, and evaluation scenes from its official evaluation set,
which exploration never uses.
Limits.
Each episode has the native step limit of the benchmark and a wall-clock limit,
which during an interactive episode also bounds the agent’s own deliberation. The agent and its
programs may call a vision-language model, Gemini 3.8 Flash, with a budget of $10 per session
that exploration and evaluation share.
10.2  Rehearsal and Evaluation
Rehearsal.
When the agent considers its program ready, it freezes a copy of its
code with a registered entry point into a bundle and requests a rehearsal. The bundle is executed
alone in a fresh isolated environment on a new exploration scene while the agent is paused, and the
rehearsal consumes one exploration episode, like an episode in which the agent acts itself.
Afterwards, the agent reads the outcome and the logs of the rehearsal and may revise the bundle
and rehearse again. Only a bundle that has completed a rehearsal without error can be submitted,
and submission ends exploration.
Fully automated program.
Evaluation executes the submitted bundle on each unseen
scene in a fresh isolated environment, without the agent and without edits or retries. The
results are never revealed to the agent. Because the bundle calls the same tools that the agent
called during exploration, the program that is evaluated is the program that was rehearsed.
Agent-in-the-loop program.
At the end of exploration, the workspace is frozen,
including the code, the notes, the handoff, and a compressed version of the conversation. For
each evaluation scene, a fresh copy of the agent starts from this frozen workspace and attempts
the scene, running its code, observing, and acting through the same tools as during exploration.
Scoring.
Both forms are scored by the benchmark’s native evaluator, with partial
credit wherever the benchmark defines it. An error, a timeout, or an early exit of the program
counts as a failure, and scores are averaged over all scheduled evaluation episodes.

11  Simulation Case Studies
This section follows single sessions on the simulation benchmarks in detail: what the agent
explored, the program it wrote, and how that program behaves on unseen scenes.
11.1  Re-Perception Under Perturbation: Two Cans into a Basket
The first task of the LIBERO-Long suite asks the robot to put both the alphabet soup and the
tomato sauce in the basket, on a table that also holds a ketchup bottle, a carton of orange
juice, milk, butter, and cream cheese. The agent explored the task for 15 episodes in about an
hour, ten of them interactive and five rehearsals of its program, and wrote a program of 1,362
lines that succeeds in all 50 official initial states and in 44 of the 50 perturbed states of
LIBERO-Pro. The perturbation exchanges the soup with the ketchup and the tomato sauce with the
orange juice, which moves the two cans by 15 and 32 cm (  Figure   14  a). This
section shows what the program perceives, how it plans, and why its behavior transfers.
Perception.
The program perceives the scene anew in every round, and it divides the
work between a vision-language model and depth (  Figure   13  ). Gemini only names
the objects: it returns a pixel on each can and in the basket, together with a short description
of each can’s state. Every geometric quantity comes from depth. The program lifts the agent-view
depth into the world frame, takes the table as the mode of the point heights, and, starting from
each Gemini pixel, segments the object by a flood fill over 3D-connected points; the top height
is a high percentile of the segment, and the axis is the centroid of its top 1.2 cm. A segment
counts as a can only if its top is 4.5 to 8 cm wide and 5 to 30 cm above the table, bounds
that the agent set after measuring every object on the table and that reject the taller and
narrower ketchup bottle. A second detector, which uses depth alone, finds flat, round plateaus
of the size of a lid and adds any can that Gemini missed. Before grasping, the program hovers
7 cm above the lid and refits the lid disk from the wrist camera; a top that is not can-shaped
is blacklisted, and the grasp yaw is the first of four candidates whose finger zones are clear
of other objects.
Placing by footprint reach.
The agent-view camera cannot see the floor of the basket,
which its near wall hides, and the agent found during exploration that this flat floor is only about
7 by 10 cm: drop spots chosen by clearance put the second can’s footprint over the sloped walls,
where the can stalled. The program therefore maps the interior from the wrist camera while it
holds the first can, as a height map with 4 mm cells, and computes for every cell the highest
point under the footprint of a can, its  footprint reach  (  Figure   13  c,d).
It chooses the pair of spots, at least 6.8 cm apart, that minimizes the larger of their two
reaches, releases each can just above its reach, and remaps the basket after the first release.
During exploration, the agent also arranged perturbed layouts of its own,
stacking the tomato sauce on the soup, standing the soup on the cream-cheese box, placing the cans
side by side, and pushing the basket by 8 cm and rotating it by 20 ∘ , and it ran its program
on each of them.

Why the program transfers.
Nothing in the program refers to where the objects stood
during exploration, so the perturbation changes its inputs but not its procedure. Under
perturbation, its first estimate of each can’s axis lies within a median of 3.1 mm of the ground
truth, against 2.9 mm on the official layouts, and the wrist refit within a median of 1.0 mm,
while the cans themselves moved by 15 and 32 cm (  Figure   14  b); a policy that
reproduced its official motions would miss each can by that displacement. The checks also absorb
labelling errors. When Gemini placed the soup’s label on the ketchup bottle, which now stands
where the soup stood in the official layouts, the wrist refit measured a top 3.7 cm across, and
the program rejected it as not can-shaped, blacklisted its position, and found the soup in the
next round. All six failures share one cause: the soup is not visible from the agent-view camera
at the start, and the program, which re-perceives only from its home pose, stops with about 300
steps left. The listings below condense the program’s main loop and give the agent’s code for
the footprint reach and the choice of drop spots, without docstrings and one log line.

H = np.where(np.isfinite(b["H"]), b["H"], b["rim_z"]) # unobserved cells count as rim
res = b["grid"][2]
k = int(np.ceil(r / res))
yy, xx = np.mgrid[-k:k + 1, -k:k + 1]
fp = (xx ** 2 + yy ** 2) * res ** 2 <= r * r # disk of the can’s footprint
return ndimage.maximum_filter(H, footprint=fp, mode="constant", cval=b["rim_z"])
def plan_spots(b, r=0.036, min_sep=0.068):
F = footprint_max(b, r)
ii, jj = np.nonzero(b["interior"])
if len(ii) < 2:
return None
f = F[ii, jj]
keep = np.argsort(f)[:400]
ii, jj, f = ii[keep], jj[keep], f[keep]
res = b["grid"][2]
D = np.hypot(ii[:, None] - ii[None], jj[:, None] - jj[None]) * res
cost = np.maximum(f[:, None], f[None]) + 0.5 * np.maximum(0.0, 0.08 - D)
cost[D < min_sep] = np.inf
a, c = np.unravel_index(np.argmin(cost), cost.shape)
if not np.isfinite(cost[a, c]):
return None
s1, s2 = cell_xy(b["grid"], ii[a], jj[a]), cell_xy(b["grid"], ii[c], jj[c])
return [(s1, float(f[a])), (s2, float(f[c]))]
11.2  Self-Calibration and Grasp Design: Tower of Hanoi with Two Dexterous Hands
The bimanual Tower of Hanoi task of DexJoCo asks for the final two moves of a three-level tower:
the medium red disk goes from the middle peg onto the large blue disk on the right peg, and the
small yellow disk from the left peg on top of it. Two Franka arms carry 16-degree-of-freedom
Allegro hands, and the disks slide over pegs that stand 13 cm above them, so a grasp has to hold
a disk level as it travels along its peg without touching the peg. The agent received no grasp
and no model of the hand, only the joint semantics and a few generic postures in its skills. It
wrote a program that completed all 150 formal episodes
on unseen layouts, in which the board shifts by up to 4.9 cm and the table height varies by as
much.
Measuring its own fingertips.
The agent spent its first episode on its own hand,
without touching a disk. It moved single joints of the right hand and lifted the wrist cameras’
depth into world points to see what each joint moves, finding that the first thumb joint turns
the thumb from pointing sideways to pointing straight down and that the last two flex its tip
forward. It then held the posture it meant to grasp with, the index finger and the thumb both
pointing down, segmented the white fingertip caps in the right wrist camera, lifted them to 3D,
and split them into two clusters (  Figure   15  ). Relative to the measured flange,

11.3  From Exploration to Code: Carrying a Hammer over a Bar on a Humanoid
In the DoubleDesk task of HumanoidArena, a Unitree G1 humanoid has to take a hammer from one desk,
carry it over a bar on the floor, and drop it into a basket on a second desk. The agent commands
the robot through whole-body kinematic references that a learned tracker, SONIC, executes; it
was given the tracker, three teleoperated demonstrations, a forward-kinematic model of the robot,
and a tool that returns the level frame of the pelvis. Over 125 exploration episodes and 10.7 hours,
it wrote a program of 3,639 lines in eleven files, of which the 637-line kinematic model is the
one it was given. The program completed 34 of the 60 formal episodes; before submitting it, the
agent predicted “roughly half to two-thirds”.
Perception.
Every quantity the program uses comes from the depth image of the head
camera, lifted into a point cloud in the level frame of the pelvis (  Figure   18  ).
The rotation into that frame comes from the provided tool, and the agent’s own fit of the floor
plane by random sample consensus agrees with it to within 0.07 ∘ . On this cloud, the agent’s
code finds the floor as the mode of the point heights, the bar as the dominant line among points 5
to 11 cm above the floor, the desk tops and their near edges among upward-facing points, and the
back wall, and it localizes the robot from the bar, the desks, and the wall against a map whose
constants it measured itself. It finds the hammer by its orange handle, takes the handle’s
principal axis, decides which end carries the head from the dark points beyond the handle, and
measures its length, using the 0.302 to 0.310 m it found during exploration to place the centre when
part of the hammer is hidden; on the unseen scene of   Figure   18  , the length is
0.305 m. It finds the basket as the largest cluster of
points above a desk and fits a rectangle of 0.60 by 0.40 m with its rim 0.90 m above the floor,
and it measures the distance of each sole from the bar by combining the fitted bar with the
kinematic model. The program perceives anew at every stage and before every step at the bar, and
after a grasp it confirms that the hammer is held by measuring the height of the handle again.

Locomotion and the bar.
The agent’s skills recommended walking by replaying a cycle cut
from a teleoperated recording. The agent cut a symmetric 66-step cycle from one demonstration,
looped it with a ramp in heading, and measured that its amplitude does not control the length of
a single step, which varied by    ±  \pm   10 cm; it therefore calibrated multi-step walks against its
own localization and used them as a table of distances. Sidestepping moved the robot by 1 to 2 cm
per cycle, so lateral placement turns and then walks. The crossing replays the step over the bar
from one demonstration: with the recorded pitch, the pelvis did not travel and the lead foot
landed on the bar, so the agent scaled the pitch to zero; perpendicular approaches landed the lead
foot on the edge of the bar, so it approaches at 64 ∘ , where the swinging foot also reaches
sideways; and it adds a trailing step when the robot ends astride the bar, after learning never
to turn in that position. Whether a crossing succeeds depends on the stance from which it starts,
and the agent built a model of how each step moves the two soles relative to the bar, from its
own measurements of 102 transitions (  Figure   19  a). The model predicts that a left step
places the left sole 14.5 cm ahead of the right one up to an amplitude of 0.35, and up to 25 cm
at 0.6; a planner searches three actions ahead to bring the left sole into the window from which
the program crosses. The bounds of that window are measured too: crossings started with the left
sole within 21 cm of the bar succeeded in 17 of 17 trials, which set the far edge of the window
at 21.5 cm, and the trailing sole is kept within
37 cm of it, since the agent found that crossings with the trailing sole closer than 35.5 cm had
succeeded 27 times out of 27, and those with it between 35.5 and 42 cm had fallen 4 times out of
13. The agent then wrote its own Monte Carlo simulators of the approach, which replay the stance
model with its measured errors, and used them to choose that margin, which lowered the simulated
risk of a fall from 9.3 to about 6% at a cost of 0.3 actions. Over all 137 crossings in its logs,
every crossing started with the trailing sole within 35.5 cm of the bar succeeded, and in the formal
evaluation the robot crossed the bar in all 59 logged episodes without a fall
(  Figure   19  b). In the episode of   Figure   18  c, the model predicted that the
left step would bring the left sole to 16.7 cm before the bar, and the point cloud measured it at
17.3 cm.

11.4  Adaptation Under Perturbation on LIBERO-Pro
After its exploration on unperturbed layouts, RAX may adapt its program to the perturbed
distribution of LIBERO-Pro. A subagent reads the program, the description of the perturbed
task, and the first frame of a perturbed layout, and judges whether the program will transfer.

and code of its exploration, and continues for at most 5 episodes on perturbed layouts before the
program is evaluated again on its own. In this mode, RAX runs as an agent-in-the-loop program
across the change of distribution: the program acts alone, and the agent steps in only to
revise it, so that adaptation exercises the continual learning of   Section   3.4  . The
agent adapted its program on five of the 40 tasks, tasks 3, 8, and 9 of the Long suite and
tasks 1 and 5 of the Goal suite (  Table   19  ).

12  Exploration Budget of ASPIRE on LIBERO-Pro
ASPIRE  ( Lu et al., 2026 )  writes robot programs in CaP-X  ( Fu et al., 2026 )  with Claude Code
and Claude Opus 4.6. Its programs call the CaP-X interfaces for perception, including
text-prompted segmentation and vision-language pointing, for grasp planning, including a
top-down grasp selector, for inverse kinematics, and for joint-space motion, and they may not
read the simulator’s ground-truth state. On LIBERO-Pro, the unit of development is a task under
one perturbation: each of the 30 tasks of the Spatial, Object, and Goal suites is developed
separately for the position and the task perturbation, giving 60 programs, each written for
its own perturbed suite.
For each task and perturbation, ASPIRE executes an initial program on a debugging split of 15
environment seeds (51–65), where a seed fixes one instance of the task, including object
poses, distractors, and the initial state of the robot. After each execution, the coding agent
reads a trace of every primitive call, with its inputs, outputs, and return status, the camera
frames before and after the call, grasp candidates, object poses, and motion-planning results.
It diagnoses the failure, patches the program, and replays the debugging seeds, with at most
three replays per seed. On some tasks, an evolutionary search additionally proposes    K  K
candidate programs per iteration, conditioned on the three best programs and their failure
traces, and executes each candidate on the debugging split; the reported searches run for up
to four iterations, and    K  K    is not reported. The final program is executed once on a
validation split of 15 further seeds (66–80) and then evaluated on seeds 1–50. A coordinator
promotes validated repairs into a shared library of skills, each stored with its failure
signature, its condition of use, its repair strategy, and a code sketch, which later sessions
read as in-context guidance. With the same loop on Claude Opus 5,   Kang et al. (2026)   report
a median of 0.99 hours and 91 thousand output tokens per task and perturbation.
The debugging and validation seeds index instances of the same perturbed suite as the
evaluation seeds, so every rollout before the final evaluation is drawn from the distribution
on which the program is evaluated. This is also required by the task perturbation, which
changes the goal of the task: a program developed on the original task would pursue the
original goal. ASPIRE’s result on the Long suite comes from a separate setting, in which a
skill library built on the 90 tasks of LIBERO-90 is applied to the Long tasks without any
debugging on them. ASPIRE does not report the total number of rollouts per task;

14  Real-Robot Tasks
This section describes the setup of every real-robot experiment: the task, the robot and its
sensors, what the agent was given, what the operator did, how many trials the agent ran, how
success was judged, and the final outcome. Five tasks use a Franka FR3 arm with a parallel
gripper, two exterior RGB-D cameras (left and right of the table), and an RGB-D camera on the
wrist; the sixth uses a Rainbow RB-Y1 mobile manipulator with an RGB-D camera on its head. The
control interfaces are those of   Section   4.2  . In every task the agent received only the task
text quoted below, typed by the operator, and the robot’s tools; it received no demonstrations,
no object models, and no trained policy. Each session ran Claude Code with maximum reasoning
effort. The agent could send requests to the operator through its tools, and the operator could
reply in a chat; we report every reset and intervention recorded in the agent’s notes. Times are
local wall-clock times taken from the agent’s notes and the camera recordings, which are timestamped
frame by frame. The key-frame figures show raw camera frames without overlays.
14.1  Find the Cube
Task.
The operator hides a white cube of about 3 cm under one of four inverted green
cups (about 9.3 cm tall) and shuffles the cups by hand; the robot must then lift the cup that
holds the cube away and grasp and lift the cube. The task text was:  “First wait for the
operator to place a cube under a green cup and watch it permute the positions of the cups. after it
finishes, you should identify the cup with the cube insides and lift the cup away, then grasp the
cube and lift it in the gripper, as success.”  The agent had to watch the shuffle while it
happened: it held the arm still at a watch pose above the cups and recorded the wrist camera’s
stream, then identified the cup from that recording.
Operator.
The operator hid the cube, shuffled the cups, and reset the scene between
trials when the agent asked. During the session the operator made the game harder in three steps.
At first the cube was covered by a cup and the cups were slid around. In later trials the operator
also lifted the cube and moved it, or set a decoy cup on its old spot. From 21:35 the operator
dropped the cube into an upright cup, not necessarily the nearest, turned that cup over, and then
shuffled. From 21:50 the cube was replaced by a red wedge of about 4 cm.
Trials and outcome.
The agent ran 12 trials between 20:08 and 22:35, and recorded each
in its notes; trials that stopped partway were resumed from the step that failed. In the first
trial the shuffle started before the arm reached the watch pose. In the next two the agent
finished parts by hand-issued commands, and in the third its tracker assumed a static cube and
chose the decoy. Trials 4, 5, and 6 were three consecutive end-to-end successes of the agent’s
program without intervention, in 166, 231, and 194 s. Trial 7 missed the moment the cup
covered the cube; trial 8 identified the cup correctly but pinched the cube through the cup wall
and carried both, after which the agent grasped cups higher and with less force. Trial 9 introduced a
new way of hiding the cube: dropped into an upright cup that was then turned over. The program
recognized no hiding event it knew and stopped without moving the robot. The agent adapted on the
spot: it added a detector for a cube lying inside an upright cup, checked it on the recorded stream
and on all seven recordings so far, and resumed the same scene one minute later, when the robot
lifted the predicted cup and grasped the cube in 98 s (  Figure   22  ).   Figure   24   shows how its program tracks the cups. With the red wedge, the cup was identified correctly in trials 10 and 11;
the wedge was grasped after several fixes and manual help in trial 10, and on the first attempt in
the resumed trial 11 (  Figure   23  ). For the wedge the agent kept the cup tracker and
20 of the program’s 41 functions unchanged, generalized its model of the hidden object to a
measured size, color, and height, and changed the grasp to close on the wedge along two axes. Success was judged from the gripper width after the grasp and from the
wrist camera’s view of the object in the gripper.

14.2  Air Fryer
Task.
The robot must open the drawer of an air fryer by its handle, put a banana into
the basket, and close the drawer. The task text was:  “You should open the air fry pan, put
the banana inside, and close it. Reminder: the plate is really heavy and you should figure out
where to grasp and the force applied. Also if the position of the air fry pan is out of range you
may ask for operator reset. Be careful about the forces and maybe not pull out the plate entirely so
we do not have to lift it in everytime.”  The agent’s perception, its articulated model of the
fryer, and its verification are described in   Section   14.2.1  .
Operator.
The operator reset the scene between runs; after the first run, for example, the operator took the
banana out of the basket, which the robot cannot reach into. Between runs the fryer was moved (by
about 6 cm and 4 cm in the two table directions before run 7) and rotated it (so that the handle
faced the robot’s base, before run 8). Before the final run the operator moved the banana away
from the left camera at the agent’s request and added an orange ball as a second object.
Runs and outcome.
The session lasted from 09:18 to 12:05. The agent first completed the
task once by direct tool calls (run 1, about 75 minutes including exploration), then wrote a
program and ran it nine times (runs 2–10). Run 2 ended with a safety stop when the elbow hit the
left camera; the collision moved the right camera, which the agent stopped using. Runs 4, 5, and 8
needed resumes after a false-negative check, a descent timeout, and refused long moves, and run 8
also needed recovery commands issued by the agent. Runs 6, 7, 9, and 10 were clean unattended
successes, including run 7 on the moved fryer and run 9 on the rotated one. In the final run the
program opened the drawer by 13.1 cm, placed the banana and then the ball in the basket, and
closed the drawer, in 210 s, leaving the handle 3.5 mm from its initial position;
Figure   27   shows it.   Figure   25   shows how its program handles the fryer’s layout, the camera bump, and the release. Success was judged by the agent’s own measurements: the drawer
opening, the objects’ points inside the basket rim, and the handle’s final position.

14.2.1  Agent-Written 3D Perception
This section details the perception code behind   Figure   3  . The task is to open the
drawer of an air fryer by its handle, put a banana into the basket, and close the drawer, on a
real Franka FR3 with a left exterior and a wrist RGB-D camera. The agent wrote the perception
and the program itself, in about 1,500 lines of Python; they use no learned detector and no
vision-language model. All numbers below are from the agent’s final run.
Lifting to a metric frame.
Every depth pixel is back-projected with the camera
intrinsics and the camera-to-base pose into the robot’s base frame, and the views of the
exterior and wrist cameras are fused in that frame. All later computations operate on these
points; estimates are projected back into the images only to check them.
Segmentation and geometric primitives.
Each part of the scene is selected by a
colour threshold combined with a height band and a workspace region: the dark lid on top of the
fryer, its white body, the dark handle outside the body, the yellow banana, and an orange ball
just above the table. Geometric primitives are then fitted to the selected points, each with a
plausibility check on its size:
•
the fryer body, by a robust circle fit to its side (radius 8 to 16 cm accepted), and
the lid, seen from the wrist camera above, by a second circle (4.5 to 8 cm), whose centre
gives the fryer’s vertical axis    c  c   ;
•
the handle, by the direction from the axis to its horizontal arm, which gives the pull
direction    d  d   , the outer face of its grip in 1.5 cm height slices, the height of its arm,
and its lateral offset;
•
the banana, by its principal axis and a quadratic centre line, which give its arc
middle, the normal on its convex side, its chord (13 to 21 cm accepted; 18.0 cm here), and
its height;
•
the basket, once the drawer is open, by a circle fitted to its rim.
The pull direction from the top view must agree with the one from the side view within
12 ∘ ; the side view alone was biased by about     4  ∘   4^{\circ}   , which is why the agent added the
top view.
Task frame and articulated model.
All targets are expressed in a frame anchored on
the fryer: the axis    c  c   , the pull direction    d  d   , and     t  =   z  ×  d    t=z\times d   . The agent also wrote an
articulated model of the fryer: a fixed upper cylinder and the back of the lower body, and a
drawer cylinder with box models of the handle’s grip and arm, which translate together by the
drawer’s opening along    d  d   . The model provides a signed distance from any point, and the
program instantiates it at the drawer’s current opening to check every planned motion for
clearance between the arm, hand, fingers, wrist camera, and held object, and the fryer, the
table, and keep-out regions around the exterior cameras.
How the agent built the model.
No model of the fryer was provided. The agent first
completed the task once by hand, controlling the robot step by step, and recorded what it measured
in its notes: the fryer’s top at a height of 0.415 m and the seam between body and drawer at
0.245 m, a handle with a horizontal arm and a hanging grip, and the basket centre relative to the
handle once the drawer was out. It also noted that the drawer slides freely along the pull
direction and tips slightly when released. About 90 minutes into the session it turned these
observations into the model above, in the first version of its program, and revised it in later
versions.   Table   21   separates what the agent estimates in each new scene from what
it fixed from these measurements.

Verification.
Each step is checked by a new measurement. The opening is the shift
of the handle face (13.1 cm here), and the step fails if it falls more than 3 cm short of the
command. The rim is searched for around the model’s prediction and found 6.5 mm from it, and the
release poses use the measured rim. The banana counts as placed when its points lie inside the
rim and below its height: 99.99% of them, with its top at 17.9 cm against a rim at 23.5 cm.

shifts sideways by about 1.5 cm; after closing, its face lies 3.5 mm from its initial position.
Sensor limits and calibration.
The agent recorded two limits of its sensors and
coded around them: the wrist camera’s depth is unreliable closer than about 30 cm, so metric
targets come from the exterior camera; and side-view pixels on the edge of the banana take the
depth of the rim behind it, so heights are measured from the top-down wrist view. When the arm
bumped the left camera, whose reported pose stayed unchanged, the agent re-estimated that pose
by matching image features against frames captured before the bump, lifting the matches to 3D
with both depth maps, and fitting a rigid transform, with a residual of 3.5 mm and fixed
landmarks within 2 to 9 mm of their references. It applies the correction only to frames
captured after the bump, and it stopped using the right camera, which had moved too far to
correct.

Operator.
The operator poured soy sauce when the agent asked, washed the towel and

The session lasted from 09:21 to 12:46. The agent first wiped a
stain by direct tool calls (two passes; the first left a smeared film, and the second, after the
operator added soap, cleaned it), then wrote a program that locates the towel heap, grasps a wad
of it, locates the stain against a clean reference image, scrubs it in a back-and-forth pattern,
parks the towel, and checks for residue. It ran the program in 13 recorded trials and resumes (trials 1 to 7b). Failures
were a refused far reach, an operator reply the program did not expect, one false “clean”
verdict on thin streaks (the operator asked for a second wipe; the agent then added a check with

wiping region to the reachable area, and a refused approach move. The last two trials, 6 and 7b,
cleaned the stain in one pass without intervention; trial 7b reused the scene of trial 7 after the
agent fixed the approach move (  Figure   28  ).   Figure   30   shows how its program finds, wipes, and checks the stain. Success was judged by the agent’s residue

trials 6 and 7b) and by eye in the three camera views.

Afterwards the operator asked for a variant:  “pull
paper towels out of the box, wipe table, and then throw them into the waste bin.”  The agent wrote
a new program that imports the towel program unchanged and calls its parts: locating the stain
against the clean reference, fitting the wiping region to the reachable area, the press-then-grasp
of a wad, the zig-zag wipe 12 mm below the measured contact, and the residue check. The new code
handles the paper: it finds the box and the bin, pinches the top of a protruding sheet and pulls it
out, piles six sheets on the stain, releases the wad over the bin and scrapes paper stuck to the
fingers, and sweeps up sheets left on the table. After three dry runs, the stain was removed in both
wet runs (  Figure   29  ), but leftover sheets, and in the second run a flat wet scrap
that the sweep missed, were cleaned up with supervised scripts.

21.8 mm. The full run took about 55 minutes including the operator’s extraction of the pegs from
the earlier L3 attempts. Success was judged by the insertion depth the agent measured with the arm
and by images of the upright pegs.

(a) The pieces after disassembly; (b)–(c) pieces are placed on the base; (d) the knob is held
over the urn for visual alignment; (e) the completed tower. Time is from the first frame.
Figure 34 :   The Bandu assembly program,  running fully automatically. It finds the pieces with both
exterior cameras and Gemini, keeps a slot model of the demonstrated tower, and places each piece by a
guarded place, a tactile search for the seat (with a tilt check for the urn), or a camera alignment of the
knob over the urn’s opening.
Task.
Bandu is a stacking game with irregular wooden pieces. The task text was a single
sentence:  “Stack the bandu blocks as the demonstrated tower.”  The “demonstration” was a
tower standing on the table when the session began; the agent was not shown how it was built. The tower stands on a base of four rectangular blocks laid in a     2  ×  2   2\times 2
pattern and consists of seven pieces: a ring with a dowel standing in it, a barrel, a goblet with an
urn seated in its cup and a knob seated in the urn, and an oblique cylinder that the user added
at 13:42, asking for it on top of the barrel. Several of these placements leave little play, and
the knob’s opening clearance was about 1 mm by the agent’s estimate. The user told the agent to
take the tower apart and rebuild it, and to repair its own disturbances rather than rely on
human resets.
Operator.
The operator reset the pieces once after the robot’s hand swept the tower
(at 15:06, during a sideways pick the user had asked for), restarted or re-homed the gripper twice, and moved
one piece the arm could not reach. The user asked for visual alignment instead of a contact search
for the knob (“align with at most 1 mm opening error”).
Exploration and outcome.
The session lasted from 11:13 to 17:20. The agent first took the
tower apart and rebuilt it by direct tool calls, then wrote a program with a disassembly and an
assembly mode and alternated them over runs 1 to 15, fixing a failure after each stop. In the
final exploration cycle the program disassembled the tower (7/7 pieces, 459 s) and then rebuilt
it fully automatically, without intervention: 7/7 pieces in 663 s, the knob placed by visual
alignment from both exterior cameras to an offset of 0.19 mm before insertion (  Figure   33  ).   Figure   34   shows how its program perceives, places, and checks each piece. Each
placement was checked by the measured seat height and, for the urn, an uprightness check in both
cameras; the final tower was compared with the demonstrated one in both exterior views.
14.6  Long-Horizon Tidying on the RB-Y1
Task.
The RB-Y1 must tidy a lab corner in six chained subtasks given in one
instruction:  “I want you to complete a series of tasks and you should reuse the skills while
still monitor and control the process. First, you should move the chair in front of you out and
park it to the left of the yellow table in front of you to clear it out of the way. then you should
stack the two silver cups together and carry the stacked cups and banana over to the orange basket
to your right and place them in, and pick up the orange basket on to the cabinet with dark top.
Then you should move the chair back and tuck it to the table again. Finally you should pick up the
box on your right and put it also on the cabinet. Be agile and reactive.”  The robot perceives
the scene only through its head camera and must move between the table, the basket, and the cabinet
with its base.
Skills from earlier sessions.
The agent started from a shared skill library written in
five earlier RB-Y1 sessions: carrying a box between the floor and a table ( bimanual-box-pnp ,
from three sessions), lifting the basket onto the cabinet by its rim with both grippers
( bimanual-bucket-rim-pnp ), and moving and tucking an office chair ( office-chair-tuck )
and nesting two cups ( stack-cups ), both from one chair session. Carrying the cups and the
banana into the basket had no skill. During the session the agent added a skill for reaching hand
moves ( oc-hand-reach ) and a composition skill for the whole task, and updated the
library after each trial.
Operator.
The operator reset the scene before each trial, stayed in the loop
throughout, and gave advice in the chat, such as “straighten the arms”, “lift first”, and
“check the torso and height against previous skills”. In trial 1 the robot’s base hit the
cabinet during a hand-planned turn, after which the agent checked the base’s swept footprint
before every base move. In trial 3 the operator re-armed the robot after controller faults while the cups
were being nested.
Trials and outcome.
The agent ran the whole sequence three times; all six subtasks
were completed in each trial (trials 1 and 2 overnight on the first day, trial 3 on the
next evening). Trial 3, shown in   Figure   5  , ran from 19:31 to 21:09 (98 minutes), with the agent at
every checkpoint of the skills. Success of each subtask was judged by the agent from head-camera
images (for example, two rims visible for nested cups, both objects inside the basket, the basket
and the box on the cabinet).
