Abstract.
High Bandwidth Flash (HBF) has recently emerged as a promising technology that provides terabyte-scale accelerator-local capacity at bandwidths approaching HBM, with a potential cost-per-bit advantage over HBM.
However, its NAND foundation brings long latency, out-of-place updates, and finite write endurance directly into the accelerator memory hierarchy, making its effects on performance and lifetime difficult to predict.
To study this emerging design space, we present HBFSim, an LLM-aware event-driven simulator for heterogeneous HBM+HBF memory systems that preserves application-level memory semantics while modeling flash-internal behavior. HBFSim models HBM, HBF with host-managed flash translation, and conventional capacity tiers in one simulation driven by a calibrated serving frontend.
Using HBFSim, we study decoding of Llama-3.1-70B and Qwen3-235B-A22B under three workloads that differ in their input and output lengths.
HBF serves data that does not fit in HBM 11.0–19.0   ×  \times    faster than host DRAM; HBM is better used to hold the running sequences’ KV cache than as a cache for HBF; and at a published peak load of Llama-3.1-70B, HBF lasts 2.0 to 6.9 years, in proportion to the stacks that share the KV writes. The artifact is available at  https://github.com/FlashLabAE/HBFSim
and will track public HBF device data as it becomes available.

1.  Introduction
Memory capacity has emerged as a primary bottleneck in serving large language models (LLMs). Model weights occupy tens to hundreds of gigabytes, while key–value (KV) state grows linearly with context length and request concurrency, quickly exceeding accelerator memory capacity. For example, an 8B model serving eight concurrent 128K-context sessions can exhaust the HBM of a modern GPU (e.g., the 131 GiB of HBM3e on an NVIDIA H200), while long-context serving for 70B-class models may exceed the memory capacity of an entire eight-GPU node  ( Kwon et al., 2023 ;  Qin et al., 2025 ;  Dubey et al., 2024 ;  NVIDIA, 2023 ) . High Bandwidth Flash (HBF) has recently emerged as a promising approach for extending accelerator-local memory capacity. SanDisk’s disclosed HBF design targets a 16-die, 512 GB flash stack that delivers up to 1.6 TB/s  ( SanDisk, 2025a ;  SanDisk, 2025b ) , enabling multi-terabyte accelerator-local memory systems without host-memory accesses. The same disclosure targets 8–16   ×  \times    HBM capacity at similar cost and bandwidth, making capacity per dollar, rather than higher speed, the main motivation for HBF  ( SanDisk, 2025a ) .
Unlike conventional DRAM expansion, HBF brings asymmetric read and write performance, page programming, flash translation layer (FTL) management, write amplification, and finite program/erase endurance into the accelerator memory hierarchy. Its effect on LLM serving is difficult to predict because no public HBF hardware is available for validation  ( SK hynix, 2026b ) . Nevertheless, system architects must decide on memory organization, placement policies, and provisioning before production devices become available.
For example, moving read-only weights to HBF mainly exercises its read path and frees HBM for the growing KV cache, whereas placing mutable KV state in HBF creates program traffic and consumes write endurance.
Therefore, it is necessary to study the performance of HBM+HBF memory hierarchies under realistic LLM serving workloads before committing to a design. Because such hardware is unavailable, a simulator is required to evaluate these trade-offs.
Existing simulators each cover one level of this hierarchy: DRAM simulators  ( Luo et al., 2024 ;  Li et al., 2020 )  stop at the memory controller, SSD simulators  ( Tavakkol et al., 2018 ;  Li et al., 2018 )  put flash behind a storage interface, and LLM serving simulators  ( Zhang et al., 2024 ;  Ding et al., 2026 ;  Khairy et al., 2020 )  represent memory by capacity and bandwidth. None connects the placement of LLM data to both completion time and physical flash traffic.
HBFSim addresses this limitation. It models HBM, HBF with a host-managed FTL, and conventional capacity tiers in one event system, coupled in a closed loop with a serving frontend whose scheduler and GPU compute are calibrated against measurements, and it accepts address-level traces as well as production request traces.
Using HBFSim, we study decoding of Llama-3.1-70B and Qwen3-235B-A22B under three workloads that differ in their input and output lengths. We find that HBF serves the data that does not fit in HBM 11.0–19.0   ×  \times    faster than host DRAM; that HBM should hold the running sequences’ KV, because caching HBF with LRU or FIFO rereads nearly the whole working set once it exceeds HBM, and that KV should be written to HBF only when it must leave HBM; and that the FTL costs little on the read path as long as its layout keeps reads parallel, while HBF’s lifetime depends on the amount of KV that reaches flash. These findings connect HBF’s potential cost-per-bit advantage to measurable latency and wear rather than to a single capacity or bandwidth number.

This paper makes the following contributions:
•
Workloads at two granularities.  HBFSim takes fine-grained address-level traces, with one record per memory access, and coarse-grained request traces, which its frontend expands into the series of weight and KV accesses that each request causes.
•
A coupled and fast memory-system model.  HBM, HBF with a host-managed FTL, and external tiers (host DRAM, CXL SSDs, and NVMe SSDs) share one timeline and interact as in a real system, for example through the FTL’s tables in HBM.
•
Preliminary takeaways for HBF.  Decoding Llama-3.1-70B and Qwen3-235B-A22B under three workloads yields five simple rules: HBF pays off only under capacity pressure; HBM should hold the running KV and HBF the weights, with KV written to flash only when it must leave HBM; generic cache replacement loses to this placement unless a step fits in HBM with room to spare; the FTL should preserve the flash array’s parallelism; and endurance, set by how much KV reaches flash, is a first-order constraint.
2.  Background
2.1.  Memory Demand of LLM Serving
A serving system’s memory holds the model weights, which every request reuses; the KV cache, the per-layer keys and values of every processed token, which decoding reads instead of recomputing; and activations, which are small by comparison.
For Llama-3.1-70B a BF16 KV cache takes 320 KiB per token  ( Dubey et al., 2024 ) , 320 GiB for 1M tokens. Serving systems allocate KV in fixed-size blocks  ( Kwon et al., 2023 )  and retain the blocks of finished requests so that later requests with the same prefix skip its prefill  ( Zheng et al., 2024 ;  Qin et al., 2025 ) , so the KV footprint grows beyond the active requests. Figure   1   shows the weights and the KV cache of 1M tokens, in one request or retained across many: for small models the KV cache dominates, every model from 70B up exceeds eight HBM4 stacks, and the newest open models, with 1.6T to 2.8T parameters, exceed even an eight-H200 node with their weights alone, while hybrid or compressed attention keeps their KV small.
The two phases of a request access this data differently. Prefill processes the prompt, produces its KV, and is usually compute-bound; chunked prefill lets it share a batch with decoding work  ( Agrawal et al., 2024b ) . Each decoding step generates one token per request: it reuses the weights across the batch, reads every running request’s KV, and appends one token’s KV per layer, so it is usually bound by memory bandwidth, and its traffic grows with model size, batch, and context. When weights and KV exceed HBM, systems offload to host DRAM or SSDs  ( Sheng et al., 2023 ;  Liu et al., 2024 ;  Qin et al., 2025 ) , at access costs set by the slower tier and its interconnect.
2.2.  High Bandwidth Flash
HBF stacks NAND flash dies on a logic base die and connects them to the
accelerator through an HBM-like interface in the same
package  ( SanDisk, 2025a ;  SanDisk, 2025b ) .
The OCP HBF specification  ( Open Compute Project, 2026 )  defines stacks with up to 16 channels and three speed grades.
For example, at speed grade 2 each channel carries 96 GB/s of payload, or about 1.5 TB/s per
stack, and SanDisk targets 512 GB per stack. An HBF stack therefore offers
8-16 times the capacity of an HBM stack at a similar interface
bandwidth.
However, HBF still behaves like NAND. A page read takes microseconds, compared to tens of nanoseconds of DRAM, so HBF reaches its bandwidth only with many
reads in flight. Data is programmed, not overwritten: a page program takes
tens of microseconds and occupies its bank, and a block must be erased before
its pages are programmed again. The specification assigns address mapping,
garbage collection (GC), and wear leveling to host software; the device
itself performs neither GC nor copyback  ( Open Compute Project, 2026 ) . Each block tolerates
a limited number of program/erase (P/E) cycles, and no P/E rating for HBF has
been published. Host decisions thus shape both performance and lifetime:
what the host places in HBF determines the traffic HBF sees, and the host’s
flash translation layer (FTL) determines how many erases each write costs.
2.3.  Questions for HBM+HBF Systems
Before HBF hardware is available, system designers need to answer five
questions. Is HBF a better capacity tier than host DRAM or SSDs? How much HBM
should accompany it? Which data should stay in HBM, and should HBM act as a
cache for HBF or as separately addressed memory? How should the FTL handle
KV writes? How long will HBF last under serving traffic? The answers
depend on each other through the serving loop: slower memory stretches
decoding steps, which changes how requests are batched and therefore the
memory traffic itself. Answering them requires running a real serving
scheduler against memory models that include flash management, with the
two coupled in a closed loop.

HBFSim is a closed-loop simulator of LLM serving on accelerator memory
built from HBM, HBF, and other capacity tiers. Figure   2
shows its three layers. A serving frontend turns request traces into batches
and the requests in each batch into memory accesses.
A policy layer decides in which memory each
object is stored and how data moves between tiers. A device engine executes the memory transactions on models of HBM, HBF, or external capacity
tiers, and feeds the outcome of that work back to the frontend, which schedules the next batch based on the feedback.
Slower memory therefore reshapes batching as it would on a real system: longer iterations let more requests queue before the next one starts, and when KV no longer fits, the scheduler moves some KV to a slower tier or preempts requests, which shrinks the batch.
Three challenges shape this design.
Workloads and device accesses differ in granularity and semantics.  A
serving system works with requests, weights, and KV blocks; HBM serves data bursts
of tens of bytes; and HBF is accessed like memory but programs flash pages (e.g., 4 KiB) in
order, erases whole flash blocks, and leaves its FTL to the host. Address-level
traces preserve individual accesses but can only cover short runs, whereas production
request traces cover long periods of serving but record no memory accesses.
The levels of the memory hierarchy are coupled.  Existing simulators model one level in isolation, but in an HBM+HBF system the two levels jointly determine performance. What HBF must serve depends on what HBM can hold, and the traffic HBF generates in turn consumes HBM capacity and bandwidth. Placement decisions therefore shift load between the tiers rather than simply adding a slower level beneath HBM, so neither tier can be simulated independently.
The number of events is huge.  One decoding step of a 70B model reads
tens of millions of flash pages, each passing through about a dozen shared resources, from the plane and flash channel to the TSVs and ECC engine.
Because slower memory changes batching, these accesses must be simulated in a
closed loop rather than replayed.
As shown in Figure   2  , layers in HBFSim communicate through narrow interfaces. The frontend describes work
in terms of model objects such as weight tensors and KV blocks. Policies map objects to devices and emit transaction
graphs with explicit dependencies. The engine contains no LLM-specific logic. This
separation lets users change one layer, for example, add a caching policy or
an FTL, without touching the others.
3.1.  Serving Frontend
HBFSim accepts workloads at two granularities.
In an  address-level trace , a record is
one memory access with optional data class, arrival time, and layer
annotations; such traces are replayed directly.
Detailed instruction-and-address tracing and cycle-level simulation incur substantial costs even for a small inference workload. For Qwen2.5-1.5B-Instruct (bfloat16, batch size 1), a 32-token prefill followed by two fixed-token decode steps required 43.4 minutes for trace collection on an RTX 4000 Ada with NVBit  ( Villa et al., 2019 ) . The resulting 1,030-kernel traces occupy 98.3 GiB uncompressed, or 7.46 GiB in the compressed format consumed by Accel-Sim2.0  ( Pan et al., 2026 ) . Full trace-driven simulation already takes 19.9 wall-clock hours even for a small model. For larger models, both the trace size and simulation time would become prohibitively large, rendering this approach unrealistic.
In a  request-level trace , a record is one inference request: its arrival time,
prompt and output lengths, and prefix hashes  ( Qin et al., 2025 ;  Wang et al., 2025 ) .
It contains no detailed memory accesses.
Which bytes an
inference step touches does not depend on the values it computes, only on
the model architecture and on which requests the scheduler runs with how
many tokens (for MoE models, also on the routed experts, which depend on
the values and are therefore an input, recorded or synthetic). The frontend, ServeLoop, therefore regenerates the accesses of every
step. Its scheduler replays the trace with vLLM’s continuous batching and
chunked prefill  ( Yu et al., 2022 ;  Kwon et al., 2023 ;  Agrawal et al., 2024b ) ,
including paged KV, prefix sharing, and preemption. A compiler turns each
iteration into the byte ranges that every operator reads or writes in weight
tensors, KV blocks, and embedding rows, leaving addresses and memories to
the policies. A decoding step of Llama-3.1-70B under the workload with 32 sequences and 6K tokens of context becomes     1.8  ×   10  5    1.8\times 10^{5}    such transactions.
The generated accesses are verified at three levels. Batching: given the
same service times, the scheduler forms the same batches as vLLM
(Section   3.5  ). Addresses: the byte ranges and their order
match 6,568 held-out warp streams captured with NVBit on an A100; the H200
we model has no capture, so its KV is read block by block, which changes the
time per output token (TPOT) by at most 0.55% against the A100 order.
Volume: the frontend counts each byte once, whereas prefill kernels refetch
the same KV for other query heads or tiles, which GPU caches partly absorb,
so prefill traffic is a lower bound.
HBFSim times every batch, prefill and decode alike, using an operator-level GPU model. It decomposes each batch into operators and computes each operator’s time from three components: a fixed overhead, a compute time, and a memory-access time. The compute time is derived from the operator’s FLOPs and a compute-throughput coefficient fitted to measured kernels. We obtain the memory-access time from HBFSim’s detailed simulation of HBM and HBF accesses, rather than an ideal-bandwidth assumption. To stay anchored to real GPU behavior, we fit each operator’s fixed overhead, compute throughput, and memory bandwidth from measured kernels to establish a baseline time. During simulation, we replace the baseline’s ideal memory time with the simulated access time, while retaining the measured kernel’s additional memory overhead beyond the GPU’s peak bandwidth. The batch time is then the sum of all operator times. This design ensures that HBF latency and bandwidth directly affect each operator’s memory time, and thus the batch time, while the compute portion stays tied to measured GPU performance.
3.2.  Memory Policies
HBFSim provides two ways to organize HBM and HBF. In  peer mode , HBM and HBF form one address space, and each object is stored in one of them. HBM is filled in a priority order and the rest overflows to HBF:  weights first  places the weights, then KV blocks in address order, retained prefixes included;  KV first  places the running sequences’ KV, then the weights, then the retained prefixes. In  tiered mode , HBM caches objects stored in the HBF or other capacity
tier in 4 MiB lines with LRU, FIFO, or decayed-LFU  ( Robinson and Devarakonda, 1990 )  replacement; decayed
LFU evicts the line with the fewest recent accesses and halves all access
counts periodically, as in frequency-based replacement  ( Robinson and Devarakonda, 1990 ) .
Dirty data is tracked at 4 KiB granularity, and dirty KV is written back
either eagerly, while compute leaves the link idle  ( Lee et al., 2000 ) ,
or only when its line is evicted.
KV released before eviction is discarded without being
written.
3.3.  Device Engine
HBM.  An HBM stack follows the JEDEC organization of its
generation, set by the number of channels and pseudo-channels and the pin
rate. The following study uses HBM4 for analysis  ( JEDEC, 2025 ) , with 32 channels of two
pseudo-channels at 8 Gb/s per pin, or 2 TB/s per stack. Because our studies concern capacity tiers, HBFSim models HBM at the
pseudo-channel level rather than at the command level of DRAM simulators such
as Ramulator 2.0  ( Luo et al., 2024 ) . Requests are split into pseudo-channel
transfers, groups of four pseudo-channels share an arbitration queue and a
service timeline, and an average access latency and a bandwidth efficiency
account for row activation and refresh.
HBF.  As in the OCP specification, the model separates the device
from its host-side management. The device has independent transmit and
receive timelines for each channel, ordered page sensing within each bank,
page buffers, ECC, and TSV transfers. It programs the pages of a block in
order and, as the specification requires, erases a block when its first
page is written. The organization of flash into channels, dies, planes, and
blocks and the timing of reads, programs, and erases follow
MQSim  ( Tavakkol et al., 2018 ) . We reimplemented them because MQSim’s FTL runs inside
an SSD, whereas HBF’s runs on the host, and HBF operations must share one
timeline with HBM and the serving frontend. Like an SSD, and beyond the
specification, each stack has a device-managed DRAM that buffers writes
until a page is full and caches recently read pages.
The host runs the FTL. It maps logical pages to physical ones and runs
garbage collection, which picks victim blocks by their number of valid pages
with a small weight for wear; static wear leveling is implemented but
switched off in our studies. Since the specification forbids the device
from moving valid data, garbage collection reads live pages into a copy
buffer in HBM and writes them back. We implemented three mappings and
keep each one’s index in HBM. Page-level mapping has an 8-byte entry per
4 KiB page; the whole table lives in flash as translation pages, and HBM
caches part of it. Extent mapping keeps a sorted list of runs of
consecutive pages, 48 B per run. Both write by appending and spread
consecutive pages over all planes. Block-level mapping has one entry per
1 MiB logical block and keeps the block in one physical block on one plane,
each page at a fixed offset. We model two consequences: NAND programs a
block’s pages in order, so a page whose predecessors have not been written
yet waits in the device DRAM; and any write that is not an in-order append
copies the whole block to a fresh one. We do not stripe blocks over planes,
because a copy would then move a 1.5 GiB stripe. Every mapping gets 0.1%
of the HBF capacity in HBM, 3.1 GiB of the 96 GiB of two HBM4 stacks, and
its lookups compete with the application’s traffic: with page-level
mapping, one Llama-3.1-70B decoding step at 2 HBM + 6 HBF issues
1.0–1.7      ×   10  7    \times 10^{7}    lookups, one per flash page read.
Other tiers.  Host DRAM, CXL SSDs, and NVMe SSDs share one
model consisting of a link, a controller, and media queues. A CXL SSD adds
a device-side DRAM cache with FIFO replacement.

To make full-iteration simulation tractable, we combine coarse-grained HBM
approximation with exact HBF acceleration. Only HBM is approximated:
scheduling transfers per 4 KiB chunk and pseudo-channel rather than per
32-byte burst runs an all-HBM forward pass 24.8   ×  \times    faster
(134.7   ×  \times    for sequential reads), while keeping batch completion times
within 0.04%.
For HBF, the bottleneck is reserving roughly a dozen shared resources per
page, as in SimpleSSD  ( Jung et al., 2018 ) ; here we reduce per-reservation
overhead without sacrificing accuracy. A first-fit calendar organizes each
resource’s idle intervals into 64-interval leaves labeled with their maximum
duration, so searches immediately bypass leaves with insufficient space.
Multi-page reads are batched into groups of one page per plane to share
stage-time calculations, reuse calendar lookup states across groups, and
compute stride addresses from the first page, while the FTL updates free
space only for planes whose state changes. Page grouping speeds up a
Llama-3.1-70B batch (7.3M page reads) by 1.48   ×  \times   , and lazy FTL
recounting accelerates ten write batches (3.2M page programs) by
1.55   ×  \times   . Every page still reserves all resources in strict order
without pruning or rounding idle intervals, yielding bit-identical
completion times across all 82,449 transactions in the batch.
Wall-clock time then tracks flash page reads at roughly     2.7  ×   10  5    2.7\times 10^{5}
reads/s per core (Figure   3  b); all 405 configurations in
Section   4   took 80.0 core-hours on an Apple M2 Ultra and an M5 Pro.
3.5.  Calibration and Validation
Three components are calibrated against hardware
(Figure   3  a). The scheduler is checked against vLLM 0.26’s:
both receive the same requests and the same measured batch times, and over
282 batches in ten test cases with staggered arrivals, shared prefixes,
prefix eviction, and preemption, they form the same batches with the same
token ranges, prefix hits, and completion times. The operator model is
fitted to kernel measurements: on an A100 and an H200 NVL we timed the Marlin
GEMMs and FlashAttention-2 paged attention that vLLM uses with 8-bit
weights, inside whole layers under CUDA graphs, over 525 shapes per GPU
spanning batch, query, and context sizes, and fitted each operator’s fixed
overhead, compute rate, and memory rate by least squares.
We then predict 64 whole-layer shapes that never entered the fit: the mean
absolute error is 5.8% on the A100 and 5.0% on the H200, and the largest,
41.8% on the A100, occurs in Llama-3.1-70B layers whose batch mixes long
and short contexts. Finally we run complete requests on each GPU, from the
embedding to the output head, and compare each batch’s time: predicted and
measured batch times differ by
10.2% on average on the A100 (Llama-3.1-8B, 46 batches) and by 5.8% on
the H200 (Llama-3.1-8B and Llama-3.1-70B, 86 batches); for Llama-3.1-70B on
the H200, the time to first token differs by 9.3–13.6% and TPOT by
4.6–7.0%. The host DRAM path is fitted to measured pinned-memory copies
between an H200 NVL and its host (issue time, bandwidth per direction,
fixed latency).
HBM4 and HBF cannot be calibrated yet. Their interfaces follow the
specifications; HBM’s access latency and bandwidth efficiency and HBF’s
internal timing (4    μ  \mu   s page read, 75    μ  \mu   s program) and parallelism
are assumptions users can replace. Every default parameter
records its source, published, from the literature, or assumed; 18 of the
30 parameter groups are assumptions. The engine checks its own accounting on every run (programs
by cause must sum to the physical programs; valid, invalid, and free pages
to the capacity), the test suite compares HBM scheduling, HBF reads and
writes, and GC against reference models, and every result records the
hashes of its inputs, configuration, and binary.
4.  Case Studies
We use HBFSim to answer the questions of Section   2.3   with two models and three workloads.
4.1.  Setup
System.  We model one accelerator package with eight memory stacks,
each an HBM4 stack or an HBF stack (Table   1  ); we write
2 HBM + 6 HBF for a package of two HBM and six HBF stacks (2:6 in the
figures, 2H6F in Table   3  ). We compare 1 HBM + 7 HBF,
2 HBM + 6 HBF, 4 HBM + 4 HBF, and 6 HBM + 2 HBF, whose HBM holds 43.4,
91.9, 188.9, and 285.9 GiB of data. The HBF stacks follow OCP speed grade 2, with 16
channels, one die per channel, 16 planes per die, and blocks of 256 pages of
4 KiB. Like an SSD, each HBF stack has a device DRAM of 0.1% of its flash
that serves as write buffer and read cache. Unless noted otherwise, the host
FTL uses page-level mapping and caches translation pages in 0.1% of the HBF
capacity, reserved in HBM. We serve Llama-3.1-70B  ( Dubey et al., 2024 )  with
8-bit weights (67.7 GiB) and a BF16 KV cache (320 KiB per token), and
Qwen3-235B-A22B with FP8 weights (223.0 GiB for the 128 experts of each of
its 94 MoE layers) and a BF16 KV cache (188 KiB per token); the figures
label them 70B and 235B. Public traces carry no expert routes, so the 235B
model routes every token to a uniformly random top-8 of its 128 experts,
seeded by the token’s prefix; at 32 sequences a decode step reads
197.9 GiB of the 223 GiB of weights. GPU compute follows the H200 NVL
operator profile (Section   3.5  ), which covers batches of up
to 16; for larger batches we keep the per-FLOP and per-byte costs measured
at 16.

Workloads.  A decode step reads the KV of every running sequence,
so what distinguishes workloads is how much context the sequences hold and
how that context was produced. We characterize a workload by its
input:output length ratio and compare three (Table   2  ):
long OUTPUT (2K prompt tokens, 6K output tokens), balanced (4K and 4K), and
long INPUT (6K and 2K), 8K tokens per request in each. The public traces of
Mooncake  ( Qin et al., 2025 )  and Qwen  ( Wang et al., 2025 )  are
input-heavy (at most 29% of their requests have more than 62.5% of their
tokens in the output), so no output-heavy workload can be drawn from them;
their median request holds 5.5K–7.3K tokens. Prompts
are private, so no KV is shared. We replay each workload through the
scheduler with 32 sequences per batch and a prefix cache that retains 1M
tokens (320 GiB of KV for Llama-3.1-70B, 188 GiB for Qwen3-235B-A22B).
The first batch’s requests arrive spread over one request’s lifetime, so in
the steady state the running sequences are at every stage of their
lifetimes. Among the steps in which every
batch slot is busy while requests wait and the prefix cache is full, we take
the one whose running sequences hold the median context and install its
state as replayed, each KV block at its replayed address. We then measure a
short window instead of a full replay: each sequence prefills a private
16-token suffix, which resumes it as a running request and yields its first
token, and decodes seven more; TPOT is the mean time of these seven decode
steps. The three
workloads hold 5.2K, 6.3K, and 7.3K tokens of context on average, so a step
reads 51–71 GiB of KV for Llama-3.1-70B and 30–42 GiB for
Qwen3-235B-A22B, 40% more under long INPUT than under long OUTPUT, and
writes one token of KV per sequence.

Takeaway 1: HBF is most valuable under memory-capacity pressure.  It offers little benefit when the working set fits in HBM, but substantially outperforms offloading to CPU memory, CXL SSDs, and NVMe SSDs once spilling occurs, for example when Qwen3-235B-A22B serves 32 sequences whose 253–265 GiB working set exceeds the 188.9 GiB of HBM at 4 HBM + 4 HBF. Under a fixed stack budget, however, adding more HBM can hurt performance if the resulting loss of HBF bandwidth outweighs the reduction in spill traffic.

Capacity and placement.  We vary the split between HBM and HBF
(Figure   5  ). In peer mode, HBM
should give priority to the running sequences’ KV. The working set of Llama-3.1-70B
(119–139 GiB) fits at 4 HBM + 4 HBF, where KV first and tiered
mode reach the compute-bound 49–54 ms. At 2 HBM + 6 HBF, KV first takes
69–83 ms and weights first 75–95 ms, 4–14% more: it fills the HBM
left after the weights with KV blocks in address order, retained prefixes
included, and leaves 38–65 GiB of running KV in HBF per step, whereas KV
first reads only weights from HBF (29–49 GiB). At 1 HBM + 7 HBF even KV first reads 8–28 GiB
of running KV per step from HBF (89–98 ms). Under long OUTPUT, weights
first still takes 75 ms at 4 HBM + 4 HBF, where the working set fits,
because the added HBM fills with retained prefixes while 31 GiB of
running KV per step still come from HBF. The working set of
Qwen3-235B-A22B (253–265 GiB) exceeds HBM at all three splits. Its
decode step is dominated by the 198 GiB of expert weights it reads, so KV
first falls only gradually, from 163–170 ms at 1 HBM + 7 HBF and
152–160 ms at 2 HBM + 6 HBF to 115–128 ms at 4 HBM + 4 HBF, and
weights first is 4–7% behind. At 1 HBM + 7 HBF the step takes only 7% longer than
at 2 HBM + 6 HBF: seven HBF stacks serve the experts. The three workloads differ little: their contexts differ by 1K
tokens, and TPOT follows (69, 76, and 83 ms with KV first at
2 HBM + 6 HBF): a step’s cost depends on how much context it reads, not
on how it was produced.
Tiered mode.  Tiered mode matches peer mode with KV first when the
working set fits in HBM and, with LRU or FIFO, is 1.7–2.2   ×  \times    slower
for Llama-3.1-70B and 1.3–2.4   ×  \times    for Qwen3-235B-A22B when it does
not. Each step reads the working set in the same order, a cyclic pattern larger
than HBM, so LRU evicts almost every 4 MiB line before it is reused and the
step rereads the whole working set from HBF, 117–137 GiB for Llama-3.1-70B
and 231–243 GiB for Qwen3-235B-A22B, instead of only the spill. This is
why 4 HBM + 4 HBF is slower than 2 HBM + 6 HBF for Qwen3-235B-A22B in tiered
mode (275–291 against 201–211 ms): four HBF stacks serve the same
reread instead of six. At 1 HBM + 7 HBF the single HBM stack, which also
absorbs every refill as a write, becomes the limit at 1.4–1.6 TB/s of
its 2.0.
Replacement.  No policy wins everywhere. FIFO rereads the same bytes
as LRU in another order: within 1% of LRU for Qwen3-235B-A22B and
1–20% faster for Llama-3.1-70B. Decayed LFU keeps the lines read most often: for
Llama-3.1-70B at 2 HBM + 6 HBF it keeps the running KV in HBM and refills
the weights every step, the division of KV first, and takes 84–90 ms,
37–48% less than LRU. At 1 HBM + 7 HBF, where the running KV
(51–71 GiB) no longer fits, the same policy is the slowest, 261–308 ms,
1.4   ×  \times    LRU: it evicts its newest lines first. For Qwen3-235B-A22B it
cuts LRU’s time by 7–10% at 1 HBM + 7 HBF and 22–31% at the next two
splits but stays 1.0–1.8   ×  \times    above KV first: a newly filled line
starts with a count of one, so the expert weights, which every step reads
once, keep being evicted and refilled.

When each mode wins.  One quantity separates the two modes in
Figures   5   and   6  : the set a step reads against the
HBM capacity. Peer mode with KV first wins whenever that set exceeds HBM, and the
margin must be real: at    α  \alpha    = 1 and 4 HBM + 4 HBF the 180 GiB set,

Takeaway 2: Under the evaluated workloads and 4 MiB cache-line configuration, the tested replacement policies incur substantial refill traffic when the active working set exceeds HBM capacity.  None of the evaluated policies matches peer mode with KV first once the set a step reads exceeds HBM, and they beat it only when that set fits with room to spare, because none captures the distinct access patterns, mutability, and lifetimes of inference data. Effective HBF management therefore requires inference-aware placement and migration rather than generic cache replacement.

Write path.  A decode step writes too little KV to compare ways of
writing it, so we also serve 112, 56, and 38 requests of the three
workloads from an empty KV state at 2 HBM + 6 HBF (outputs capped at
8 tokens), which writes 46–47 GiB of KV per workload. Writing the KV that does not fit in HBM straight to HBF, writing
all KV into HBM and to HBF when its line is evicted, and draining it to HBF
in the background give the same mean request time within 1.5%, because
prefill is compute-bound and each HBF stack buffers writes in its device
DRAM. The background drain, however, writes 70–71 GiB to flash,
1.2–1.6   ×  \times    as much as write-back on eviction (45–60 GiB). In decode,
KV first never programs an HBF page, while tiered mode with LRU programs
61,000–65,000 pages per step for Qwen3-235B-A22B as it evicts dirty KV.
Takeaway 3: KV data should be prioritized in HBM and moved to HBF only under capacity pressure.  KV is continuously appended during decoding, making its placement a primary determinant of HBF write traffic. Allocating KV to HBF only when it must leave HBM incurs no performance loss in our experiments, whereas proactive migration creates avoidable writes for KV entries that may be freed shortly.

In decode, HBF mostly serves reads, so we ask what the FTL costs on the
read path and how fast writes wear HBF.
Address translation.  We compare the three mappings of
Section   3.3   at 2 HBM + 6 HBF with weights first, so that the
running KV is read from HBF (Figure   8  ). A decode step writes
almost nothing, so we also run the prefill windows of Section   4.3
(46–47 GiB of new KV each). All three receive the same 3.1 GiB of HBM, but
only page-level mapping uses a sizable part of it: 97–152 MiB of
translation pages for the pages a decode step touches, against 0.9 MiB for
the extent index and 10 MiB for the block index. Extent mapping stays within
0.5% of page-level mapping in decode and in prefill: KV is written and read
in long runs, so one index entry serves many pages. Block-level mapping is
4.2–4.3   ×  \times    slower in decode (324–399 against 75–95 ms), because a
block lies on one plane, which reads its 256 pages one after another in about
1.0 ms, whereas the other two mappings spread the same pages over all planes;
prefill, which spends more of its time in compute, hides part of this and is
1.5   ×  \times    slower.
Takeaway 4: HBF mapping should preserve internal parallelism rather than maximize address granularity.  Decode reads weights and KV in long sequential runs, so one translation serves many pages. An extent mapping that stripes each run across all planes matches a page-level table at a fraction of its memory, whereas a block-level mapping that keeps each block on a single plane serializes its page reads and slows decoding considerably.

Lifetime.  A decode step writes one token of KV per sequence, so
wear comes from new KV written into flash, and we estimate lifetime at a
published peak load. TensorRT-LLM reaches 489 output tokens/s per H200 for
Llama-3.3-70B, which has the architecture of Llama-3.1-70B, with 5,000-token
prompts and 500-token outputs  ( NVIDIA, 2026 ) , 1.64 GiB/s of new
KV per GPU. The published table has no Qwen3-235B-A22B, so we apply the same
token rate to it; with 188 KiB of KV per token against 320 KiB, it writes
41% less.
HBFSim measures the share of this KV that reaches HBF with weights first
(87.5–100%) and replays each workload’s KV writes and releases (about
1 TiB, twice the stack’s capacity) through one HBF stack with garbage
collection, which gives the flash bytes erased per written byte in steady
state, the quantity that consumes P/E cycles. With either mapping this is 1.0 within 0.1%: KV
is appended and freed in bulk, so one block with no valid page left is
erased per MiB written. Block-level mapping programs 1.5–3.5% fewer
pages, because pages that wait in the device DRAM for their block’s
unwritten prefix are dropped when a sequence ends, but their block is still
erased. Assuming 100,000 P/E cycles, as for the SLC NAND used in HBF
designs  ( Wang et al., 2026 ) , Table   3   gives the
resulting lifetime: 24–83 months for Llama-3.1-70B and 40–141 months for
Qwen3-235B-A22B, in proportion to the HBF stacks that share the writes and
the same with either mapping: how long HBF lasts is set by how much KV
reaches flash.
Takeaway 5: HBF endurance is a first-order system constraint.  Under baseline inference workloads, KV spill generates enough writes to make projected HBF lifetime a major challenge even when performance is acceptable. Practical HBF systems therefore require write reduction and endurance-aware management.

The HBF specification is still a draft, so we ask which device parameters
the results depend on, taking Llama-3.1-70B on the three workloads at
2 HBM + 6 HBF with KV first, where a step reads 29–49 GiB of weights
from HBF (69–83 ms per token), and changing one parameter at a time
(Figure   9  ).
Only the rate at which the flash array senses pages matters. Doubling the
page read time to 8    μ  \mu   s raises TPOT by 30–42%, 16    μ  \mu   s by
91–126%, and the 40    μ  \mu   s of conventional NAND by 3.7–4.8   ×  \times   ;
halving the planes per die at equal capacity has the same effect as
doubling the read time (29–40% for 8 planes, 87–121% for 4). The
interface does not matter: speed grade 3 doubles grade 2’s 1.5 TB/s and
changes TPOT by 0.1%, and grades 1 and 2 on 8 channels are equally
29–40% slower, only because their stacks have half the planes. A plane
senses one 4 KiB page per read time, so a stack’s 256 planes deliver
0.26 TB/s at 4    μ  \mu   s, a sixth of the interface. The write side is
invisible in decode, even without the device DRAM: with KV first a step
appends its KV in HBM and programs no HBF page, so program times from 37.5
to 600    μ  \mu   s, write credits, and write timeout leave TPOT unchanged, and
the thermal throttling ceiling adds at most 0.2%. For read-heavy decode, an
HBF design should therefore spend on planes and read time before interface
speed.
5.  Discussion
Limitations.
Our case studies reproduce one decoding step per workload, seven tokens per
running sequence, and one prefill window per
workload for the write path and the mapping comparison, without garbage
collection, so TPOT omits its interference with reads. We model
one accelerator; tensor or pipeline parallelism would give each a share of
the weights and KV. The
studies combine an H200 compute profile, extended beyond its measured
batch of 16, with HBM4 and HBF, a pairing that does not exist today, so
HBF timing and endurance remain assumptions. The lifetime estimates apply a published serving load
around the clock to the HBF write share and write amplification that
HBFSim measures, and assume perfect wear leveling.
Extending HBFSim.
New memory policies use the policy interface, new FTL schemes the host
mapping interface, new HBF generations the device configuration, and new
models, traces, and GPUs their descriptors, importers, or operator profiles.
6.  Related Work
HBF and hybrid HBM–flash memory.
H3  ( Ha et al., 2026 )  and SK hynix  ( SK hynix, 2026a )  evaluate hybrid HBM+HBF
organizations with projected device parameters. FlashAccel co-designs data
layout and storage management for HBF  ( Wang et al., 2026 ) . Petrucci
et al. compare HBF with LPDDR analytically and identify writes as the
limit for offloading KV to flash  ( Petrucci et al., 2026 ) .
HBFSim lets such designs be compared on the same workloads; our endurance
results quantify the write problem they point out.
Memory and storage simulators.
Ramulator 2.0  ( Luo et al., 2024 )  and DRAMsim3  ( Li et al., 2020 )  model
DRAM at the command level. MQSim  ( Tavakkol et al., 2018 )  and FEMU  ( Li et al., 2018 )  model
SSDs behind an NVMe interface, with mapping, GC, and wear leveling inside the
device, and Cylon  ( Yoon et al., 2026 )  emulates CXL SSDs with a DRAM cache in the
device. HBFSim follows MQSim’s approach to the flash organization and
Cylon’s device class for the CXL SSD, but treats HBF as memory with a host-side FTL whose metadata
competes with the application in HBM.
LLM serving simulators.
Vidur  ( Agrawal et al., 2024a ) , LLMServingSim  ( Cho et al., 2024 ) ,
Frontier  ( Feng et al., 2026 ) , and
ASTRA-sim  ( Won et al., 2026 )  simulate scheduling, computation, and
communication for LLM inference, LLMCompass  ( Zhang et al., 2024 )  adds
operator-level modeling with mapping search, and GTSim  ( Ding et al., 2026 )  and
Accel-Sim  ( Khairy et al., 2020 ;  Pan et al., 2026 )  model GPU microarchitecture. They represent memory by its capacity and
bandwidth; HBFSim models the devices at the transaction level, flash
management included, under a validated scheduler.
7.  Conclusion
HBF could give accelerators an order of magnitude more memory, but only if
systems use it in ways that suit flash. HBFSim lets researchers test these
choices before hardware exists. Our case studies support five
takeaways. HBF is most valuable
under capacity pressure, where it keeps TPOT 11.0–19.0   ×  \times    lower than
host DRAM and 86.6–154.1   ×  \times    lower than an NVMe SSD. Conventional
cache replacement is a poor fit for HBM–HBF tiering: no policy matches
peer mode with KV first once the set a step reads exceeds HBM, and a cache
wins only when that set fits with room to spare. HBM should hold the
running sequences’ KV and HBF the read-only weights; KV should move to HBF
only when it must leave HBM. The mapping should preserve the flash array’s parallelism,
which an extent index does at a fraction of a page table’s memory.
Endurance is a first-order constraint: at a published peak load of
Llama-3.1-70B, HBF lasts 2.0 to 6.9 years, in proportion to the stacks
that share the KV writes. We
release HBFSim so that others can replace our assumptions with
measurements.
