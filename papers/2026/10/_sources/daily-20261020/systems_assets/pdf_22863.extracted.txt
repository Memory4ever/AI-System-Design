Abstract
Agentic large language model (LLM) applications turn a single user request into a se-
quence of model and tool calls over a growing context. Retaining the key-value (KV) state
computed for this context in GPU memory allows subsequent calls to reuse it rather than re-
compute it. However, retaining KV state across a serving fleet can require substantial GPU
memory. We characterize four productionMicrosoft M365 workload traces, namely Deep
Research, Enterprise Assistant, Coding Agent, and Enterprise Chat, spanning more than
121 million model calls. Agentic applications issue most calls within a session, and each call
re-reads the growing context. In Deep Research, the application issues 89% of model calls.
Sessions have a median of 13 model calls, while Enterprise Chat, our lower-agency reference,
has 333. The median context grows from approximately 10K tokens to 68K tokens by the
30th call. About 80% of context tokens are served from the prefix cache, and a predictable
class of models accounts for 67% of call-context KV.
This reusable KV state is large and remains idle for most of its lifetime. Since the produc-
tion models are confidential, we use the public Llama-2-70B KV layout, with grouped-query
attention and 16-bit values, to estimate the memory demand consistently across models. Un-
der this assumption, the KV state of a single 99th-percentile Deep Research session exceeds
the 80 GB high-bandwidth memory (HBM) capacity of an NVIDIA H100 GPU. Retaining
the KV state of all live sessions at their peak, which we term the hold-all-live ceiling, requires
an estimated 501.8TB of GPU HBM. However, model inference occupies only 5.6% of the
time for which this state is retained. Enterprise Chat has smaller sessions but approximately
349K concurrent live sessions, resulting in a similar capacity challenge.
Trace-driven replay shows that an idle cap of one hour reduces the hold-all-live ceiling by
3.6×, whileincreasingthefractionofcallsthatrecomputetheircontextfrom4.07%to4.53%.
However, eviction alone is insufficient under tighter memory budgets. With a pooled budget
equal to one tenth of the busiest hour’s no-eviction demand, least recently used (LRU)
eviction causes 63% of Deep Research calls to recompute their context. Furthest-next-use
(FNU), a clairvoyant policy based on Belady’s rule, reduces this to 31%. Multi-resolution
retention (MRR) instead demotes the LRU session’s KV state to an int4 representation
within the same memory budget. MRR reduces the recomputation rate to 13.6%,2.3×
lower than FNU, despite selecting sessions using recency alone.

1 Introduction
Production LLM serving is shifting from individual requests to persistent, tool-interleaved ses-
sions. In conventionalchat, a user request opens aturn: the serving system performs a short
sequence of model and optional tool calls, and control returns to the user. In anagenticwork-
load, the request that opens a turn initiates a longer internal loop in which an orchestrator (e.g.,
one following the ReAct or Magentic pattern [58, 11]) repeatedly invokes models and tools, ap-
pends their results, and decides when the task is complete [66, 60, 28]. Asessionis a user’s
ongoing interaction with one application: a sequence of one or more turns that share a ses-
sion identifier, together with the context they accumulate (Section 2.2 defines calls, turns, and
sessions precisely).
This distinction changes thestatethat an LLM serving system must manage. Within a turn,
a chat application typically returns control to the user after a short orchestration path, whereas
an agentic application may re-enter the model many times without human input (Figure 1); a
session repeats this loop once per turn. Each model call firstprefillsits input context, computing
the attention keys and values of every context token in aKey-Value (KV) cache[20], and then
decodesoutput tokens one at a time. Keeping reusable KV resident in GPU memory lets a
later call skip prefill over a context prefix that an earlier call already processed, so the retained
state remains valuable across otherwise idle intervals. Serving must therefore manage the size,
lifetime, and placement of a session’s evolving KV working set, in addition to scheduling the
prefill and decode phases of individual model calls.
Agentic applications are emerging as a substantial component of datacenter LLM work-
loads, but their long-running control loops create KV residency and placement demands that
request-level measurements do not capture. Recent studies (TraceLab [66], the GitHub Copilot
study [28], and the ReAct study [60]) show that agents repeatedly invoke models and tools,
carry growing contexts, and produce comparatively short outputs. None exposes theserving
deploymentselected for each call, and only the Copilot study operates atproduction scale, for a
single coding workload and at the granularity of logical model endpoints. At hyperscaler scale,
even modest errors in estimating prefix reuse, KV residency lifetime, or placement locality can
translate intoterabytes of excess GPU memory or extensive context reconstruction.

2 Agentic Workloads and How We Measure Them
Before examining KV behavior, we establish what prior characterizations leave unmeasured,
describe the four production workloads and how we measure them, and show how agentic each

workload is.
2.1 What Prior Characterizations Miss
Existing LLM serving systems primarily optimize request-level prefill, decode, and latency [20, 3,
65]. Agentic applications instead compose repeated model and tool calls into persistent sessions
whoseKV cacheremains valuable between model calls [26]. The closest agentic workload char-
acterizations cover coding-agent traces and benchmark-driven agents [66, 28, 60]. They establish
that agentic workloads contain repeated model and tool calls, growing contexts, short outputs,
and substantial prefix reuse. None jointly examines diverse production enterprise workloads, the
serving deployment of each call, byte-valued KV residency, and capacity-constrained residency
replay at fleet scale (Table 1).
These studies record the logical model of each call but not the servingdeploymentselected
for it. Consequently, they cannot measure how KV reuse changes when consecutive calls to
the same model are served by different deployments. Our telemetry includes the serving region
and deployment for three traces, allowing us to compare same-deployment continuations with
same-model calls routed to another deployment (Section 4.4.2). Prior characterizations also
report demand primarily in tokens. We convert peak session context toKV bytesusing an
explicit, linearly rescalable model assumption and aggregate these estimates across concurrently
live sessions (Sections 2.3 and 4.2). This enables comparisons withGPU memory capacityand
exposes the sensitivity of fleet estimates to how long a session counts as live and to temporal
resolution. TraceLab evaluates cache timeouts against hit rate and relative storage, but prior
studies do not compare destructive eviction policies, which discard an evicted session’s KV, using
byte-valued session state. We therefore develop atrace-driven residency replaythat consumes
the observed production calls under fixed memory budgets (Sections 5.2–5.5). It separates
recomputation caused by limited memory from that caused by deployment-local placement, and
evaluates retaining displaced KV at lower precision.

3 The Agentic Loop Makes KV Retention Valuable
This section measures how persistent orchestration shapes session depth, context growth, token
volume, model-class structure, and KV reuse. Within each turn, agentic sessions re-enter the
model repeatedly without human input and accumulate context across these calls, which creates
sustained demand for reusable KV state.

3.2 Context Accumulates Across the Loop
Deeper sessions tend to require more KV memorybecause context continues growing across
model calls. Figure 3(c) shows that the medianResearchcontext grows from9,764tokens
on the first call to41,045by call 11 and68,118by call 30, and first reaches95%of its call-30
value at call 27. Thus, estimating session demand from its first few calls would systematically
understate the KV required by deep sessions.
Individual sessions, however, do not grow monotonically. InResearch,90.9%of multi-call
sessions contain at least onecontext reduction, a call with less context than its predecessor,
and the median reduction leaves23.7%of the preceding call’s context. The rising median
in Figure 3(c) therefore reflects net growth across repeated growth-and-reduction cycles. A
reduction may reflectcompaction, summarization, truncation, or a transition between model
roles; the telemetry does not record its cause. Compaction near the model’s context-window
limit is a plausible cause, but we do not equate every reduction with an explicit compaction
event.

4 Why Not Keep Every Session’s KV Resident?
The simplest residency policy retains each session’s KV state from its first to its last call. We
now show four hurdles to this policy: a single session can fill a GPU’s memory, live sessions
add up across the fleet, the retained state sits idle across heavy-tailed gaps, and its reuse is
associated with staying on the deployment that built it.
4.1 A Single Session Can Fill a GPU
Under the reference KV representation (Section 2.3), the estimatedper-session KV working set
is the peak KV state of sessions,Ws =β·max i∈s(xi), Eq. (5). This is a byte estimate, not a
measurement of observed physical HBM allocation.
AResearchsession requires an estimated25.7GiB at P50,59.2GiB at P90, and81.6GiB
at P99 (Figure 7). These estimates include KV state alone: model weights, activations, and
runtime state require additional GPU memory. For scale, the P90 working set is comparable
to most of the 80 GB HBM of one H100, while the P99 estimate exceeds this capacity. In
practice, a model with the reference attention configuration may be served by a tensor-parallel
group of GPUs, each holding the KV of a subset of the attention heads [20]; the tensor-parallel
model replica, rather than one GPU, must collectively hold the session’s KV. The working-
set distributions also differ across workloads (Figure 7): a medianResearchsession carries
approximately2.5×the KV state of a medianChatsession.

Because holding every session’s KV state is costly, we replay residency policies on the observed
call streams. We first sweep an idle cap over the completeResearchtrace, then compare
destructive eviction with multi-resolution retention (MRR), which keeps displaced KV as a
recoverable int4 copy, under fixed budgets with one KV object per session, and finally measure
the miss rate that remains with unlimited memory when KV objects are deployment-local.

5.1 Reclaiming Idle State: Nominally Live State Is Not Always Residency-
worthy
Thehold-all-liveceiling is deliberately pessimistic: a session whose consecutive calls are days

residency-worthy, likely to resume soon enough that keeping their KV resident pays off, and

5.5 Routing: Deployment-local KV Creates an Independent Floor
The replay so far models one KV object per session. To represent deployment-local state, we
repeat the busiest-hourResearchreplay with KV objects keyed by both session and deploy-
ment. Over the same176,007calls, this increases the number of modeled cache objects from
9,486to35,588, because a session routed among deployments may establish separate state at
each one.
With unlimited residency capacity, reconstruction occurs only on the first access to each
modeled cache object. Session-only keying gives the5.4%first-touch floor of Section 5.2, while
session-and-deployment keying raises it to20.2%. Deployment-local state thus imposes a routing
floor that neither more memory nor better eviction within a deployment can remove; lowering
it requires deployment affinity, KV replication, or migration. This replay assumes that KV
remains local to the deployment identifier reported by the telemetry and is not automatically
shared across deployments.
Together, the capacity and placement results identify two distinct sources of reconstruction.
Limited GPU memory displaces reusable KV even under clairvoyant FNU eviction, while deploy-
ment changes make state unavailable under deployment-local caching. Recoverable retention,
such as MRR, mitigates the first; affinity-aware routing, replication, or migration mitigates the
second.
5.6 Lessons learned
Relative to prior serving work, our production measurements offer four lessons. First, request-
levelKVmanagement[20,50]doesnotconsiderreuseacrosscallswithinasession. InResearch,
89.3% of calls are internal and 80.3% of context tokens hit the prefix cache, motivating session-
18
=== PAGE 19 ===
level residency decisions. Second, retaining KV throughout a session’s lifetime can overestimate
demand: a one-hour idle cap reduces theResearchceiling from 501.8 to 140.8TB, while
reconstruction increases from 4.07% to 4.53%. Third, eviction policy has limited impact under
tight memory: clairvoyant FNU reconstructs 31.1% of calls, while retaining an int4 copy within
the same budget reduces this to 13.6%. Finally, locality-aware routing [29, 38, 45] is relevant in
production, since mean reuse falls from 88.9% to 29.0% after a same-model deployment change.
5.7 Open Problems and Limitations
OurmeasurementsexposetwocomplementaryopportunitiesforagenticLLMserving: preserving
reusableKVunderlimited GPUmemoryandcoordinatingitsplacementwithapplicationcontrol
flow. We frame these as research directions rather than evaluated system designs.
Reversible, multi-resolution KV residency.MRR isolates one effect, keeping displaced
KV recoverable instead of destroying it; it does not show that int4 retention is the best mecha-
nism. Residency mechanisms leave the context unchanged and decide only whether, where, and
at what precision its KV is kept: discard and recompute, exact offload to host or remote storage
with a fetch on resumption [41, 29, 1], or quantized retention as in MRR [32, 17, 30]. Context
reduction, such as compaction, rolling summaries, or agent memories that keep a pointer and
retrieve content on demand [19, 37, 9], changes the context itself: it can change the response,
and because prefix caching reuses only an unchanged prefix, each edit invalidates the cached KV
after it. Context reduction and KV residency can be combined: reduction shrinksWs, residency
retains the remaining state, and our replay already sizes sessions after the application’s own
reductions (Section 3.2). Exact offload avoids MRR’s precision loss but moves four times the
bytes of an int4 copy; it beats reconstruction only if fetch bandwidth exceedsβRprefill, at least
about1GB/s for fp16, and its latency adds to the resumed call unless the fetch is issued during
the preceding idle gap. Hybrids such as VeriCache decode from a compressed copy and verify
against a full-precision copy fetched from a lower tier [57]. The open problem is to decide, for
each session, whether its state should be retained exactly, quantized, offloaded, summarized, or
discarded and reconstructed, given the workload’s idle gaps, reuse and quality tolerance, while
meeting latency and output-quality objectives.
Application-awareplacementandlifecyclecontrol.Model-classpredictability, excursion-
conditioned reuse (Section 3.4), and deployment continuity (Sections 4.4 and 5.5) motivate
coordinating application control flow with KV placement and retention; a context reduction
(Section 3.2) likewise lowers the session’s current KV requirement and provides a natural point
for releasing or demoting superseded state. Current serving interfaces reveal little about an
agent’s expected next model, tool interval, context reduction, or likelihood of resumption. Prior
systems expose parts of this structure through semantic variables, program-level scheduling,
cache-aware routing, and application hints [26, 33, 16, 38, 2]. A broader interface could allow

Scope and limitations.Our results describe four Microsoft M365 workloads observed over

universal properties of agentic or chat serving.Cached tokensreported by the LLM endpoint

the corresponding result.

7 Related Work
Agentic workload characterization.TraceLab characterizes Claude Code and Codex ses-
sions, the GitHub Copilot study measures production coding-agent traffic at scale, and the
ReAct study instruments ReAct-style agents on five benchmarks [66, 28, 60]; Section 2.1 and
Table 1 compare them with this work. KVCache in the Wild characterizes production KV-cache
reuse in single- and multi-turn requests at a large cloud provider [52]; we focus on multi-call
agentic sessions and their deployment placement.
State retention, migration and caching bounds.CachedAttention and Pensieve retain
multi-turn KV state across memory tiers [12, 59], while HCache reconstructs KV state from
stored intermediate activations [13]. Llumnix supports cross-instance request and KV-cache
migration [46]. These systems provide candidate mechanisms for the capacity and locality re-
quirements characterized here; we do not compare their implementation-level latency or transfer
costs. Moreover, because FNU is not optimal for variable-size objects, we treat it only as
a clairvoyant reference policy; flow-based offline bounds provide a more principled optimality
benchmark but are outside our present replay [6].
21
=== PAGE 22 ===
LLM serving and KV management.PagedAttention and vLLM established paged KV
management for high-throughput inference [20]; Sarathi-Serve co-schedules prefill and decode
with chunked prefills [3], whereas Splitwise, DistServe, and Mooncake run the two phases on
separate resources and transfer KV between them [40, 65, 41]. Prefix-caching systems improve
reuse via structured caching, cache-aware scheduling, and distributed KV transport [64, 15,
45, 30, 29]. These systems provide KV-management mechanisms; we measure the session- and
fleet-level demand they must serve in production agentic workloads.
Agent-aware serving and orchestration.Parrot, Teola, ALTO, Autellix, and Pie optimize
serving for whole LLM applications rather than individual requests [26, 48, 43, 33, 16]. More
recent systems use agent semantics for KV prefetching, pruning, and cache management, and
for admission control, program-aware scheduling, and GPU allocation [38, 23, 7, 8, 18, 53].
InferCept and Continuum decide whether to keep, discard, or swap a request’s KV while it waits
on a tool call [1, 22], a per-request counterpart of the idle cap in Section 5.1. Model-routing
systems choose among models, reasoning modes, or quantized model variants to balance quality,
cost, and latency [35, 51, 10, 47]. Our measurements inform these directions by quantifying
model-class predictability, idle-gap structure, deployment-conditioned reuse, and the separate
reconstruction costs of limited memory and routing.
Context reduction and external memory.Prompt and context compression reduce the
state that must be materialized into KV [55, 39, 34, 19], while agent-memory systems externalize
information beyond the active context window [37, 9, 42, 56, 25]. These approaches determine
what enters the model context; we characterize how the resulting KV state is reused, retained,
and placed across a production serving fleet; Section 5.7 discusses how the two compose.
KV compression and tiering.When KV capacity is insufficient, prior work evicts selected
tokens [62, 31, 54, 24, 14], quantizes retained state [32, 17, 61], or moves state across memory
tiers [44, 21, 30, 57]. These techniques define representations and storage tiers for displaced KV;
our trace-driven replay asks a complementary workload-level question: how much reconstruction
remains under destructive eviction, and how much of it a retained lower-precision copy removes.
8 Conclusion
We characterized the KV working set of four production Microsoft M365 workloads span-
ning three agentic applications and enterprise chat. Agentic sessions repeatedly re-enter LLMs
through internal model-tool loops, accumulate context, and reuse much of it across idle intervals;
inResearch, a P99 session’s estimated KV exceeds one H100’s HBM, and a predictableSpine
class holds most call-context KV bytes. Retaining all of this state is costly, and the result-
ing memory pressure is not determined by per-session size alone: deep agentic sessions create
large individual working sets, while enterprise chat creates substantial fleet demand through
concurrency.
Reclaiming state after one idle hour lowers theResearchhold-all-live ceiling by3.6×while
raising the replayed reconstruction rate from4.07%to4.53%. Beyond idle reclamation, the
busiest-hour residency replay identifies two distinct sources of reconstruction. Under a pooled

memory budget equal to10%of the busiest-hour current-context peak, even clairvoyant de-
structive eviction by Belady’s furthest-next-use rule (FNU) reconstructs context for31.1%of
Researchcalls, while int4 MRR, which keeps evicted KV as a recoverable copy, reduces this
rate to13.6%. Separately, even with unlimited memory, modeling KV as deployment-local raises
thefirst-touchfloorfrom5.4%to20.2%. Efficientagenticservingthereforerequiresbothmemory
mechanisms that preserve recoverable KV under capacity pressure and placement mechanisms
that maintain or move reusable state across deployments.
Because the production traces contain sensitive enterprise telemetry, we plan to release Agen-
ticTraceSim and a residency replay for synthetic or user-supplied call streams, for reproducible
counterfactual studies. The generator preserves the workload dependencies needed to reproduce
the reconstruction-rate ordering of LRU, FNU, and unbounded-tier MRR without exposing pro-
duction events. Together, the measurements and the planned artifacts support the study of
fleet-scale KV residency and routing policies that account for session working-set size, expected
reuse, idle duration and deployment placement.
