Abstract
CXL Memory Module – Memory Pooling (CMM-MP) introduces a novel memory pooling architecture to meet the unique requirements of emerging memory-intensive workloads. This industry-first, purpose-built memory-pooling device combines the benefits of Compute Express Link (CXL) with the scalability and cost advantages of Ethernet. Multiple CMM-MP devices together provide a flexible, composable, and disaggregated memory expansion solution. The CMM-MP enables 100s of TB capacity for GPU/CPU applications without modifications. The memory pool is exposed as a large-capacity logical aggregate memory, with all pool discovery, composition, and backend network datapath tasks fully offloaded to the device. CMM-MP supports both memory pooling and sharing usage modes. It provides an application latency of 2.7 us and up to 23 GB/s of memory throughput. Our evaluations demonstrate that CMM-MP significantly outperforms RDMA-based solutions in latency and throughput. We also evaluated real-world use cases of Valkey+YCSB and DiskANN using CMM-MP.

I   Introduction
The rapid growth of memory-intensive applications in modern datacenters, including machine learning, graph processing, cloud-native services, and large language models, has intensified the demand for large, adaptable memory capacity [ 1 ] . Conventional server architectures limit the amount of memory available to the running applications. The current system architectures lead to underutilization and memory scarcity, depending on the application workload [ 2 ] . As workloads evolve, it is difficult to predict the proper memory capacity requirements in advance. Power, space, and thermal constraints limit the ability to scale memory independently [ 3 ,  4 ] . As a result, applications whose peak memory requirements exceed the limits of a single node are poorly served by the traditional tightly integrated memory model. Another challenge for data center operators is efficiently sharing idle or lightly loaded server memory with other hosts without compromising performance, thereby impacting the overall TCO of data centers [ 5 ] . The core challenge is to devise a scalable memory‑expansion architecture that meets datacenter constraints of TCO, performance, power, and cooling [ 6 ] . This leads to a more fundamental realization that the current ecosystem is heavily compute-centric, whereas emerging workloads require in-depth memory architectures and data-loading considerations.
Memory disaggregation [ 7 ,  8 ,  9 ]  alleviates these constraints by decoupling memory from individual compute nodes and exposing it as a shared accessible resource over high‑bandwidth, low‑latency interconnect [ 10 ,  6 ] . This separation enables dynamic allocation, reduces over‑provisioning, improves utilization, and allows data center operators to scale compute and memory independently. By breaking the rigid linkage between compute and memory, disaggregation provides the necessary elasticity to support data‑intensive workloads [ 11 ] .
Building on the flexibility of memory disaggregation, memory pooling consolidates multiple memory devices into a unified, addressable resource shared across many compute nodes. By leveraging a common memory pool, the system minimizes under-utilization and dynamically adapts to workload variations. This pooled‑memory approach improves scalability by avoiding over‑provisioning of host system memory, thereby reducing Total Cost of Ownership (TCO) and power consumption [ 5 ] . Memory pooling can also improve performance and reduce power consumption by reducing data movement. Use cases for in-place memory sharing could include virtual machine (VM) migrations and multiple hosts sharing data [ 12 ,  13 ] .

II   Background and related work
Memory disaggregation has been pursued through a variety of technologies, including RDMA, CXL, and proprietary technologies.
A common technique for memory pooling is Remote Direct Memory Access (RDMA) [ 14 ] . RDMA can provide scale and capacity for memory resources. However, it incurs the overhead of explicit remote‑memory calls and intrusive software changes [ 15 ,  16 ] .
The RDMA approach has improved latency and throughput in key-value systems  [ 17 ] . Aggregating DRAM from multiple servers into a shared pool accessible via RDMA is shown to improve the performance of remote memory [ 18 ] .
As for the CXL solutions [ 6 ] , they can overcome the software complexity of RDMA by offering native load/store semantics [ 13 ]  seamlessly to unmodified applications [ 19 ] , remaining confined to rack‑level deployments. Memory pooling through a dedicated CXL switch is another solution [ 20 ,  21 ]  that enables memory expansion and improves coherence, but it has limited scalability, higher cost, and deployment constraints. Efforts have been made to extend the CXL switch architecture with an external memory controller [ 5 ]  to meet cloud performance requirements and reduce memory costs.
Another solution introduced for CXL2.0 uses the Multi-Logical Device (MLD) [ 22 ]  feature with the CXL switch. It provides transparent, cache-line-granular memory sharing across hosts. However, this approach is limited by physical reach (rack-scale only), switching latency, higher costs, and scalability challenges. The CXL MLD concept later evolved into a Multi-Headed Device in CXL 3.0 [ 12 ] , effectively eliminating the physical CXL switch. It enables a single memory device to expose multiple memory channels to the shared pool, but the physical reach limitation remains.
Hybrid designs that combine CXL and RDMA [ 23 ]  aim to capture the best of both worlds, yet they still inherit RDMA’s overheads and the complexity of an additional software layer on the host, preventing a seamless, transparent memory‑pooling solution.
Another CXL memory approach is CXL Memory Module - Hybrid (CMM-H). It combines DRAM and NAND memory to provide a low-cost, large capacity memory expansion solution [ 24 ]  ,  [ 25 ]
. This approach provides a large memory capacity, but it does not support the memory sharing feature.
CXL‑over‑Ethernet  [ 26 ]  is yet another approach that preserves the low‑latency benefits of CXL for individual remote accesses but does not provide a genuine pooled memory accessible by multiple servers.
Other approaches have attempted to reuse existing interconnects. For example, connecting two CPUs via the Ultra Path Interconnect (UPI) [ 27 ]  and Ethernet  [ 28 ]  enables memory sharing within a single server but is limited in scalability, short-range, and consumes high power.
III   Device Architecture
CMM-MP is a purpose-built device to implement a high-performance memory pooling solution. It is a CXL Type 3 memory device that integrates CXL and Ethernet in a novel architecture to provide large-capacity memory expansion. It contains four dedicated logic subsystems, as shown in Figure   5  .
Fig. 5:  Memory pooling device micro architecture
The CXL Subsystem (SS) implements Gen5x8 CXL .mem protocol to process host memory read/write requests. This subsystem determines whether each host request targets local/remote memory and forwards them to the corresponding subsystems (DDR or Ethernet) for data access.
The Ethernet Subsystem includes two 200 Gbps Ethernet ports (total 400 Gbps of raw bandwidth) for backend connectivity between CMM-MP devices. This subsystem is responsible for packet processing, routing, and network reliability functions, including detection and mitigation of packet loss, duplication, reordering, and incorrect addressing.
The DDR subsystem implements the physical memory capacity with DRAM packages and associated memory controllers. This subsystem arbitrates local requests from the CXL subsystem and remote requests from the Ethernet subsystem.
The ARM subsystem contains an ARM Cortex A53 CPU to handle control-plane functions such as pool device discovery, pool memory-mapping composition, and programming the internal mapping table. The ARM subsystem concurrently injects and receives control packets into and out of the data path alongside host traffic.
Fig. 6:  Address mapping and resolution in CMM-MP device
The remainder of this section provides the host request processing flow and details of each subsystem.
III-A    Memory Pool Address Resolution
The CMM-MP device performs a critical function: mapping and translating host addresses to appropriate internal pool memory addresses. This allows participating hosts to share a common, consistent view of the pool memory address range, which enables seamless access. This process is shown in Figure   6  .
Each CMM-MP device on a server node advertises the entire pool capacity to the host. During server boot, BIOS/UEFI maps the advertised pool capacity to the system memory map. The physical base address of the mapped pool memory is programmed to the Host Managed Device Memory (HDM) Base Address register of the device. During runtime, when applications access the allocated pool memory, those memory requests are fulfilled via the CMM-MP device. The Host address (HA) range of these memory requests is from HDM Base to HDM Base + Pool Capacity. The Normalized Host address (NHA), that spans from zero to the pool capacity (logical address), is determined as follows:

III-B    CXL Subsystem
The CXL subsystem, as shown in Figure   7  , serves as an interface between the host and the device. It implements the CXL specifications    1.1  1.1   /   2.0  2.0    (partially) over a PCIe Gen5 x8 link. It interprets incoming CXL read (MemRd) and write (MemWr, MemWrPtl) transactions. It also supports memory invalidation (MemInv) and speculative memory access (MemSpecRd). This subsystem maps the received host addresses to pool memory addresses.
Fig. 7:  CXL subsystem architecture
The CXL Endpoint (EP) module implements the PCIe Link Training and Status State Machine (LTSSM). It implements PCIe/CXL Transaction, Data Link, and Physical Layer functions as specified in the PCIe/CXL standards. This module extracts CXL requests in the CXL clock domain and provides them via Coherent Processing Interface (CPI) for further processing.
The CXL Application (CAPP) module performs clock-domain crossing (CDC) between the CXL clock and the internal core clocks. It implements CXL flow‑control by managing credit allocation and back-pressure signaling to the CXL-EP module. This module initializes CXL credits during boot and replenishes them at runtime. Incoming host CXL requests are distributed across four channels for concurrent processing. This module receives fully formed host responses, No Data Response (NDR), and Data Response (DRS) from the Response Manager. The NDR and DRS messages are returned to the host via the CXL EP module. It performs a similar CDC function on the outgoing response path.
The CXL Request Manager parses the received CXL requests to extract header and payload fields. This module maps the host address in the CXL request to the logical, aggregate pool memory address (called Normalized Host Address, NHA) using equation 1. This address normalization step is critical for multiple hosts to have a consistent view of the pooled memory, since each participating host maps the pooled memory at different locations in its own system memory map.
The Tag Table module manages metadata for in-flight requests throughout their lifecycle. For each CXL request, the Tag Table allocates a free slot and stores the header fields needed to create CXL responses later. The stored header fields include the memory operation code (MemOpcode), MetaField, MetaValue, Logical Device Identifier (LD‑ID), and the CXL request tag. The index of the allocated Tag Table is used as an internal tag to identify each request. It is carried through the datapath pipeline along with necessary request fields such as address and MemOpcode.
The Pool Address Map Table (PAMT) stores the composition of pooled memory, as shown in   6  . Each CMM-MP device in the pool is assigned a unique device identifier (Device ID). The PAMT Lookup Table (LUT) module translates an NHA into the corresponding target CMM-MP Device ID. This operation also provides the offset within the target CMM-MP device’s memory, thereby resolving the requested data location.
The PAMT entry contains a valid bit, a device ID, and the Device Pool Offset. The device ID field is used to route the request to the proper target device in the pool. The Device Pool Offset field specifies the memory offset within the target device, as shown in figure   6  . The PAMT LUT module forwards the computed memory offset and device ID to the Request Router module for further processing.
The Request Router module first compares the PAMT Device ID with the self Device ID. If the PAMT device ID matches the self device ID, the data request is fulfilled locally. Otherwise, it forwards the PAMT device ID, memory offset, internal Tag index, and other associated request information to the Ethernet subsystem for remote data access.
On the data response side, the Response Receiver module collects completed responses from either the DDR or the Ethernet subsystems. Every response includes the internal Tag, along with any applicable data. The Tag Lookup module uses the internal Tag to get the original CXL Request header fields. Once the relevant header fields are read, the Tag table entry is freed and can be allocated to new host requests. The Response Manager module uses the retrieved header fields and, if applicable, the received payload data to generate an appropriate host CXL response. Response Manager generates two types of CXL responses: NDR and DRS. For read requests, it assembles a DRS that includes the requested data payload. For write and memory-invalidation requests, it creates an NDR that contains status and completion codes. It then formats the responses according to the CXL transaction layer packet specification and forwards them to the CXL application layer for transmission to the host via the CXL EP.

III-C    Ethernet Subsystem
The Ethernet subsystem provides a data transport service for memory pool operation. It implements three logical layers: the Transport Layer, the Data Link Layer, and the Physical Layer. It enables a host to access data on remote devices in the memory pool. Additionally, ARM firmware uses this subsystem to exchange control packets among the pool memory devices. It implements essential network reliability functions to provide lossless, high-throughput, low-latency data transport. The Ethernet subsystem ensures end‑to‑end reliability through automatic retransmission, duplicate-packet handling, and packet-loss detection and recovery. This provides robust and predictable data movement across the memory pool fabric. Figure   8   shows the micro-architecture of the Ethernet subsystem.
The Trans-TX module creates transport-layer packets for: 1) the egress remote memory requests, 2) the responses for the ingress requests. The constructed transport packets are forwarded to the Ether TX module for further processing. The composition of transport packets is shown in Figure   9  . The Egress remote memory request consists of the remote device ID, memory offset, and operation type (read/write). For every outstanding host remote memory request, the Trans-TX module creates and maintains a context data structure in the Request‑In‑Flight Table (RIFT).
Fig. 9:  Transport packet format
The format of a RIFT entry is shown in Figure   10  . The valid flag indicates an outstanding request; once the request is completed, the valid flag is reset, and the RIFT entry is freed for new requests. The Trans-TX module assigns a unique, monotonically increasing 16-bit transmit Sequence Number (SN) to each request. These sequence numbers are separate and independent for each remote device. The sequence number is used to detect lost and duplicate packets on the remote device. If the timestamp exceeds a threshold without a response, Trans-TX retransmits the request to ensure reliable operation of the data fabric. For ingress requests, this module constructs response packets using remote request context information from the Trans-Rx module and the associated data received from the DDR subsystem.
Fig. 10:  RIFT table entry data structure
The Trans-RX module processes two types of packets: 1) ingress requests, 2) data responses for egress requests. The opcode field, as shown in Figure   9  , in the received transport packet, is used to determine the packet type: request or response. To process ingress requests, the Trans-RX module maintains a receive sequence number table for all devices in the pool. This table serves as the foundation for handling out-of-order, duplicate, and lost packets. For each source device ID, the table stores a base sequence number. The base sequence number represents the highest in-order packet that has been successfully received. The table also contains a 64‑bit packet bitmap and an overflow counter for each source-Device ID. Regarding responses to egress requests, the Trans-RX module first extracts the RIFT index from the packet header. The sequence number from the corresponding RIFT entry is used for validating the received response packet. The Ethernet layer is composed of ETH-TX and ETH-RX modules, as shown in Figure   8  . The ETH-TX module receives transport packets from the Trans-TX module and constructs IEEE 802.3 Ether II frames. Similarly, this module accepts control packets from ARM firmware and encapsulates them into Ethernet frames for transmission. The Ethernet frame format is shown in Figure   12  . The destination MAC address is obtained from the target device ID via a lookup in the MAC table. The firmware programs the source MAC address during the discovery phase. The Ethernet subsystem uses special Ethertype values for differentiating datapath and control packets. The fully formed Ethernet frames are then forwarded to the MAC for transmission via the MAC Interface Controller (MIC) module.

The MIC module implements the logic necessary to exchange Ethernet frames with MAC IP. It also performs clock-domain crossing (CDC) to isolate the MAC clock and the core clock domains. Ethernet MAC, PHY, and SERDES are hard macros used to implement the 802.3 Ethernet standard [ 29 ] .
III-D    DDR Subsystem
The DDR subsystem is a high-performance interconnect module that provides the access interface to actual DDR memory media. It supports three DDR4 channels, each with 16 GB of DRAM, delivering high-bandwidth, low-latency data access. As shown in Figure   14  , the DDR subsystem consists of a DDR4 memory controller, Clock Domain Crossing (CDC) logic using an asynchronous FIFO, and requester interfaces. The subsystem arbitrates concurrent read and write requests from multiple requesters from the CXL (local host accesses) and Ethernet (remote host accesses) subsystems. The DDR Subsystem stripes the memory addresses across its channels to maximize throughput while maintaining a strict request-response association. This mechanism ensures the data read from DDR memory is delivered to the correct requester.
Fig. 14:  DDR Subsystem controller
III-E    ARM Subsystem
The ARM subsystem functions as the control plane of the disaggregated memory pool. CMM-MP firmware performs autonomous pool device discovery, pool memory map composition, and datapath configuration without host intervention. This subsystem comprises an ARM CPU core, a CXL General-Purpose Control and Status Register (GP-CSR) interface, and an Ethernet Packet interface module, as shown in Figure   15  . The Host software utility communicates with the ARM firmware via GP-CSR (Receive RX, Transmit TX). The host software sends commands and hints to the device by writing them into the RX GP-CSRs using the CXL.io protocol. To receive communication from the Host software, ARM firmware polls the RX GP-CSRs. The ARM firmware sends back responses and event information to the Host software via TX GP-CSRs. ARM firmware sends and receives Ethernet frames via the Transmit and Receive packet FIFOs, which interface with the datapath. The ARM subsystem uses a special Ethertype value in IEEE 802.3 Ethernet frames to distinguish control packets from data packets. After the successful discovery phase, ARM firmware configures the datapath by programming PAMT entries, device IDs, and MAC addresses.
Fig. 15:  ARM subsystem micro architecture
III-F    CMM-MP Pool Device Discovery
One of the critical functions of ARM firmware is pool discovery. Discovery is the process of identifying and enumerating all available devices in the memory pool. During pool initialization, discovery is performed autonomously by device firmware running in the ARM subsystem. ARM firmware uses a discovery packet as shown in Figure   16  . After power-on, each device broadcasts a discovery message and listens for incoming messages. It compiles a sorted list of all unique responses, ordered by chip identifier. The rank of the chip identifiers in the sorted list is used to assign device IDs to the devices. These device IDs and the associated capacities are used to program the global pool map in PAMT. Upon successful completion of the discovery process, which runs concurrently across all devices, the memory pool transitions to the runtime state.
Fig. 16:  Discovery frame format
IV   Host Interface
This section describes the software interface and the memory allocation process for CMM-MP. CMM-MP advertises the pool memory as CXL Type 3, NUMA memory to the Host. Hosts can use CMM-MP as a memory resource in pooling, sharing, or both modes simultaneously. In pooling mode, all or part of the pool memory can be allocated to one or more hosts for exclusive access. Multiple hosts can access their allocated memory concurrently from the pool. In the sharing mode, an allocated pool memory address range can be accessed concurrently by multiple Hosts.
When pool memory is used as shared memory, CMM-MP devices guarantee atomicity of host accesses, but not the order of execution of host requests. For this reason, data coherency must be handled by the upper-layer software in the relevant hosts, if necessary. Such shared memory can be used in common usage modes such as producer-consumer and writer-reader, with explicit out-of-band synchronization and communication between participating hosts.
We developed a host management utility called Memory Pool Control (mpctl). It runs on each host and facilitates online or offline allocation of the memory pool segments. Each host reserves an address space equal to the entire memory pool using the Linux GRUB command. The memory pool region is divided into fixed, predefined memory segments using the memmap kernel parameter. All Memory Pool Segments (MPS) are offline by default. The Grub settings define the number and size of MPS that can be offlined/onlined.
As shown in Figure   17  , the mpctl online MPS 0, 3 for Host 1 and MPS 1, 2 for Host 2.

V   Aggregated memory pool
As shown in Figure   18  , CMM-MP devices can be used to create a scale-up memory pool solution that multiple hosts can share. The memory pool chassis contains the desired number of CMM-MP devices, which are connected through one or more dedicated Ethernet switches in the rack. Each host uses a local CMM-MP device to access the pool memory. The allocated memory segments ( small color boxes ) can reside on different CMM-MP devices. In this scale-up system architecture, compute and memory can scale independently. Such system architecture enables potential use of different cooling methods (e.g., liquid or air cooling) for compute and memory. VI   Distributed memory pool
As an alternative to the aggregated memory pool solution described earlier, CMM-MP devices can also be used to create a distributed memory pool, as shown in Figure   20  . A set of hosts can pool together their CMM-MP device memories to create a large-capacity memory pool. The CMM-MP devices are connected using one or more dedicated Ethernet switches in the rack. Servers can be added or removed from the pool as needed. This system architecture provides the data center operator with the flexibility to use existing server resources more efficiently. Compared to the aggregated memory pool architecture, this solution tightly couples compute and memory for scaling while retaining the scalability advantage, as additional hosts can be added to the pool.

VII-C    Real World Application Use Cases
To evaluate the performance of memory pooling on real-world database workloads, Valkey [ 32 ]  database, an in-memory key–value store, is employed. We performed Valkey native micro-benchmark (Valkey-benchmark) as well as a more application-oriented benchmark, YCSB [ 33 ] .
Figure   22   shows the Valkey benchmark throughput for SET and GET operations while varying the value size from 64 up to 4096 bytes. As the value size increases, throughput decreases across all configurations due to the larger data transfer volume. MP-L remains close to the system memory baseline across all value sizes. MP-R shows lower throughput compared with MP-L because larger values require more data to be transferred over the backend Ethernet network.
As seen in the figure   22  , even though CMM-MP has 10x less raw bandwidth compared to the system memory (32 GB/s vs 304 GB/s), the Valkey throughput performance degradation is below 50% for these tests. Note that system memory bandwidth is calculated using 38 GB/s DDR5 4800 MT/s single-channel bandwidth and 8 channels per socket in the test server.
Fig. 22:  Valkey benchmark throughput
Figure   23   reports the corresponding average latency for Valkey. For both SET and GET operations, MP-L latency remains close to system memory across different value sizes, demonstrating that local pooled memory behaves similarly to local System memory. MP-R shows higher latency due to the additional network transport required for remote memory accesses. When the dataset size is small, the latency performance degradation remains moderate around 20%.
Fig. 23:  Valkey benchmark latency
In addition to the Valkey benchmark, Valkey is used alongside the Yahoo Cloud Serving Benchmark (YCSB). YCSB provides multiple workload patterns representing different read/write ratios.
Figure   24   shows the throughput for YCSB workloads A-F across three memory configurations: System memory, local pooled memory (MP-L), and remote pooled memory (WS). Across all workloads, MP-L achieves performance comparable to system memory, indicating that the CXL-attached memory pool incurs minimal overhead for local accesses. Remote pooled memory exhibits lower throughput due to the additional network hop, but still maintains substantial performance.
As seen in the figure   24  , even though CMM-MP has 10x less raw bandwidth compared to the system memory (32 GB/s vs 304 GB/s), the Valkey + YCSB throughput performance degradation is well below 30% for these tests, indicating CMM-MP’s potential for TCO optimization.
Fig. 24:  Valkey+YCSB throughput
Figure   25   shows the corresponding Valkey YCSB latency results. MP-L exhibits latency comparable to system memory across all workloads, whereas MP-R incurs higher latency due to backend Ethernet communication, but the increase remains moderate and consistent across all workloads. The latency degradation remains about 30% for all workloads, except D. Workload D has a 5% insert rate, which causes greater network write overhead.
Fig. 25:  Valkey+YCSB Latency
Another use case is DiskANN [ 34 ] , a high-performance approximate nearest-neighbor (ANN) search system designed for very large graph vector datasets. In this evaluation, we use the SIFT dataset with 1 million records, and one single CPU core to run the Search_disk_index algorithm. For all the experiments, memory is exposed as a ramdisk to ensure a fair comparison. Figure   26   shows the query throughput (QPS) of DiskANN under different search list sizes for five configurations: system memory, CMM-H, MP-L, MP-R, and SSD. System memory achieves the highest throughput, while MP-L closely follows the System memory baseline across all search sizes (L), indicating that the CMM-MP architecture can effectively support memory-intensive vector search workloads. MP-R exhibits lower throughput due to the cost of remote memory access over the backend network, yet it still significantly outperforms disk-based storage by a factor of about 3x. These results demonstrate that pooled memory can offer substantially higher performance than disk for large-scale vector search workloads.

VIII   Conclusion
In this paper, we propose CMM-MP, a highly cost-effective yet scalable memory pooling architecture. To the best of our knowledge, we have developed an industry-first, purpose-built memory pooling device that enables flexible and scalable compute and memory disaggregation. CMM-MP requires no application changes to utilize the memory pool and preserves traditional software interfaces such as load/store, devdax, and fsdax. This architecture offloads and abstracts all the memory pool composition and management functions from the Host OS to the device. The CMM-MP device effectively uses Ethernet to connect multiple memory devices on the backend while presenting a standard CXL Type 3 memory interface to the host. Our experiments demonstrate that CMM-MP can provide an easy-to-use solution compared to traditional RDMA-based solutions, while delivering significantly lower latency and higher throughput. CMM-MP provides a practical, cost-effective foundation for future memory-centric data centers.
Our future work will focus on developing more advanced features. We plan to support emerging scale-up and scale-out backend protocols, such as Ethernet Scale Up Network (ESUN), Scale Up Ethernet - Transport (SUE-T), Ultra Accelerator Link (UALink), and Ultra Ethernet (UE), for efficient, high-bandwidth data transfers to xPUs. We also plan to explore device-side caching to fully capture and utilize application workload spatial and temporal localities. Another focus area is to extend current static memory management to a dynamic approach for more robust pool usage. We also plan to explore and investigate fine granular, dynamic allocation and management of pool memory.
