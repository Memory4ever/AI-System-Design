Abstract.
Modern GPU compilers expose rich layout abstractions for mapping tensors to
threads and on-chip resources, but compute-unit-local (CU-local) 3D DRAM architectures
lack a corresponding abstraction for specifying how operand-tile data are arranged
within the DRAM address space.
Without such an abstraction, conventional placement under the existing DRAM
address mapping can subject structured tile accesses to severe
row-buffer conflicts.
We present  TileDRAM , a compiler–runtime toolchain that introduces
tile-to-DRAM layouts  as a compiler-visible abstraction for DRAM placement.
TileDRAM extends the GPU Linear Layout abstraction from compute-side mapping
targets to DRAM placement coordinates and selects layouts per tile access
signature, using recurring tile-local access behavior as the specialization unit.
Since row-buffer locality depends on ordered request
history, TileDRAM evaluates candidate layouts through their row-buffer behavior under
fixed DRAM address mappings. Accesses under the selected layouts are realized through ordinary
address arithmetic, without new address-remapping hardware or ISA support.
In full-trace replay on Accel-Sim/Ramulator2 across 108 MoE FFN cases,
TileDRAM reduces the request-weighted row-conflict rate from 75.7% to 15.2%
and achieves a 1.77   ×  \times    geomean speedup. Retargeting six traces
to six 3D DRAM organizations yields a 2.20   ×  \times    geomean
speedup under the same compiler abstraction. On an RTX 3090, address transformation adds 0.17%
geomean overhead over identity.
1.  Introduction
Memory bandwidth is a first-order system constraint in LLM inference. The
pressure is most acute in feed-forward network (FFN) layers, where dense
matrix projections dominate data movement at small batch sizes. In mixture-of-experts (MoE)
models, routing activates only a few experts per token, yet each activated
expert still performs dense projections over activation and weight tensors
( Shazeer et al., 2017 ;  Fedus et al., 2022 ) . On GPUs, these projections
execute as grouped or batched tiled general matrix multiplications (GEMMs),
whose thread blocks repeatedly fetch operand tiles as they advance along the
reduction (K) dimension. These structured tile streams make high-bandwidth 3D
DRAM an attractive substrate.

Prior 3D DRAM systems motivate two representative chip-wide abstractions for GPGPUs:
using 3D DRAM as the GPU’s global memory  ( Li et al., 2025 ;  Pan et al., 2025 )
or as a GPU-wide last-level cache (LLC)  ( Loh and Hill, 2012 ;  Zhao et al., 2019 ) .
Using the stack as GPU global memory routes its bandwidth through the
package-level endpoint instead of delivering the stack’s high local bandwidth
directly, while the LLC abstraction
pays network-on-chip (NoC) area and power to distribute that local bandwidth
GPU-wide  ( Kahng et al., 2009 ) .
We instead focus on the compute-unit-local
(CU-local) organization motivated in Section   2.1  ,
where each CU accesses its nearby 3D DRAM stack through a software-managed
address-space aperture served by a local memory controller.
However, this high-bandwidth local path also subjects operand
request streams directly to the DRAM controller.
Without warp-level request coalescing and traffic attenuation through the on-chip caches,
numerous fine-grained and potentially redundant memory requests can propagate
to the DRAM subsystem, substantially amplifying contention among concurrent memory requests,
and ultimately reducing the effective memory bandwidth available to the application.
DRAM service efficiency therefore depends on the row-buffer locality of
the resulting row-access sequence.
This dependence on DRAM placement reveals a missing abstraction between compiler-visible
tile semantics and DRAM placement: a  tile-to-DRAM layout  that defines
how operand-tile data are arranged within the DRAM address space.
Under a fixed DRAM address mapping, the tile-to-DRAM layout determines the
physical address stream presented to the memory controller and thereby governs
the row-buffer locality of DRAM accesses (Figure   1  ).
Across our 108 full-trace MoE FFN cases, conventional placement under the
fixed DRAM address mapping yields a 75.7% request-weighted
row-conflict rate: successive accesses to the same row buffer target different
rows, each paying a precharge and an activation.
Modern GPU software stacks offer rich tile-level abstractions for compute-side
layout and data movement, but provide no corresponding abstraction for DRAM
placement. Triton, CUTLASS, and CuTe provide tiled programming and layout
abstractions
( Tillet et al., 2019 ;  , 2026 ;  Cecka, 2026 ) , while cuTile, CuTe DSL,
TileLang, and Gluon expose tiles directly in their programming abstractions
( , 2026 ;  , 2026 ;  Wang et al., 2026 ;  , 2026 ;  Hagedorn et al., 2023 ) . Linear Layouts
provide a formal representation of distributed tensor layouts as linear maps between labeled
vector spaces over     𝔽  2   \mathbb{F}_{2}     ( Zhou et al., 2026 ) . Across these systems, the
operand tile is already an established compiler-visible unit for specifying
layout and data movement. However, these abstractions stop at the compute side:
they determine how tile data map to threads, registers, and shared memory, but
not how operand-tile data are arranged within the DRAM address space. DRAM
placement therefore remains outside the compiler’s tile-level layout
abstraction.
Prior work improves row-buffer locality by modifying the DRAM address mapping
in the memory controller
( Liu et al., 2018 ;  Rotaru et al., 2025 ;  Zhang et al., 2022 ) . Application-specific
synthesis can optimize one global mapping for a representative workload trace
( Rotaru et al., 2025 ) , but that mapping must therefore accommodate
the heterogeneous access
patterns within the trace (Section   2.3  ). Independently
specializing these patterns at the controller side would require maintaining
multiple mapping contexts and selecting the appropriate context for each
request  ( Zhang et al., 2022 ) .
Taken together, these observations yield two key insights.
First, CU-local integration provides high local bandwidth, but compiler-awareness
of DRAM placement is necessary to fully utilize the bandwidth. Placement should
therefore become an explicit compiler-controlled decision.
Second, we identify recurring tile-local access behavior as a stable unit
for specializing placement.
This granularity also aligns naturally with existing GPU
software abstractions, where operand tiles are already compiler-visible units for
layout and data movement.
Guided by these insights, we propose  TileDRAM , a compiler–runtime
toolchain that introduces tile-to-DRAM layouts as a compiler-visible
abstraction for compiler-controlled DRAM placement. TileDRAM represents this
abstraction as  tile-to-DRAM Linear Layouts : reusable     𝔽  2   \mathbb{F}_{2}   -linear maps
that extend the Linear Layout abstraction from compute-side resources to DRAM
placement coordinates. Each layout maps logical operand-tile coordinates to
DRAM placement coordinates.
Although access behavior varies with operand properties and tile
configurations, the same ordered tile-local access behavior recurs across many
tile instances. TileDRAM captures this with a  tile access signature
that combines tile configuration, operand properties, and the ordered
tile-local access sequence.
The tile-to-DRAM mapping itself is stateless,
with each tile coordinate mapped without reference to access history.
However, the induced row-buffer behavior is stateful, because whether a request
hits an open row depends on preceding requests in the ordered tile-local access sequence.
TileDRAM therefore evaluates candidate layouts by simulating row-buffer state
transitions under each signature’s ordered access, selecting the layout with
the fewest row conflicts.
An offline solver selects reusable layouts for each tile access signature;
the compiler applies them during address generation, and the runtime supplies each
tile’s placement without new address-remapping hardware or ISA support.
Retargeting to
different 3D DRAM organizations reselects layouts while reusing the same
abstraction and compilation path.
Using NVBit traces of Triton/Gluon kernels  ( Tillet et al., 2019 ;  , 2026 ;  Villa et al., 2019 )  replayed with
Accel-Sim/Ramulator2  ( Khairy et al., 2020 ;  Luo et al., 2024 ) , TileDRAM
reduces the request-weighted row-conflict rate from 75.7% to 15.2%
and achieves a 1.77   ×  \times    geomean kernel
speedup across 108 MoE FFN cases. Across six full-trace streams
retargeted to six 3D DRAM organizations, TileDRAM reduces row
conflicts by 79.2% and achieves a 2.20   ×  \times    geomean speedup.
On an NVIDIA GeForce RTX 3090, address transformation adds 0.17% geomean
overhead over identity across the 108 measured kernel configurations.
Together, these results establish compiler-controlled DRAM placement as a new
optimization dimension: with the DRAM address mapping left unchanged, the
compiler-selected layout alone accounts for the gain.
Our main contributions can be summarized as follows:
•
We introduce  tile-to-DRAM layouts  as a compiler-visible

2.  Background and Motivation
2.1.  3D DRAM and the CU-local Architecture
Recent 3D DRAM architectures place multi-tier DRAM structures close to
logic through dense vertical integration. In the CU-local organization modeled
here, the vertically integrated DRAM structure is connected to a separate logic
die through face-to-face Cu–Cu hybrid bonding
( Li et al., 2025 ;  Niu et al., 2022 ;  Pan et al., 2025 ) . The logic die can host memory
controllers and near-memory compute in recent designs
( Li et al., 2025 ;  Nair et al., 2026 ;  Pan et al., 2025 ) . This stacked integration
provides a high-bandwidth local DRAM–logic path, while a distinct
package-level endpoint connects the GPU or xPU to the stack
( Li et al., 2025 ;  Nair et al., 2026 ;  Pan et al., 2025 ) .
This separation makes the package-level endpoint the bandwidth boundary for
chip-wide access. Stratum reports 19.01–30.34 TB/s of internal bandwidth
across its memory tiers  ( Pan et al., 2025 ) . Exporting a stack through an
HBM-style package interface instead offers roughly 0.8–1.2 TB/s per stack in
HBM3/HBM3E  ( , 2025 ;  , 2024 ) , making the package-level endpoint
16–38   ×  \times    narrower than the modeled internal path. This gap motivates
placing compute near the stack rather than exporting its bandwidth
( Li et al., 2025 ;  Pan et al., 2025 ) . Recent industrial inference hardware
provides a concrete instance of this CU-local principle. OpenAI’s Jalapeño
adopts a memory-sliced architecture in which each compute core slice has a
local view of its own HBM4 slice and the chip omits a global last-level cache,
avoiding contention on a unified global memory subsystem
( Ho et al., 2026 ) . Remote and global memory accesses use a separate
general-purpose interconnect.
A transparent GPU-wide LLC offers a contrasting global abstraction: it makes
the stack a shared last-level cache reachable from every CU. Requests and
responses therefore traverse a chip-wide NoC and arbitration path. The
associated routers, buffers, and links consume area and power even when the
target cache line resides in that stack
( Kahng et al., 2009 ;  Zhao et al., 2019 ) . More generally, GPU-global-memory
and GPU-wide-LLC organizations place package-level or chip-wide interconnects
on the common path to stack-resident data. A CU-local organization instead
keeps common accesses within a local compute–memory domain, while retaining a
separate path for remote or global communication.
Motivated by this locality-oriented organization, we model the CU-local design
shown in Figure   1  (b), where each CU accesses its nearby 3D
DRAM stack through a local memory controller, and analyze one CU–stack pair at
a time. TileDRAM’s architectural boundary is a software-managed CU-local
aperture in a dedicated device-physical address space. Requests to this
aperture reach the local controller without virtual-address translation,
warp-level request coalescing, or caching; all other addresses traverse the
conventional memory hierarchy. The local stack remains a conventional banked,
row-buffered DRAM system  ( Mutlu and Moscibroda, 2007 ;  Rixner et al., 2000 ) .

2.3.  Stable Specialization Granularity in MoE FFNs
Application-specific synthesis constructs a workload-tuned controller mapping
from representative address differences  ( Rotaru et al., 2025 ) , shared
by all tensor and kernel requests reaching
the controller. Two properties of MoE FFN traffic, together with the cost of
exhaustive trace-wide controller-map synthesis, make the complete trace an
impractical specialization unit.
Heterogeneity appears within a single GEMM. The    A  A    (lhs) operand advances over
row and reduction coordinates, the    B  B    (rhs) operand over reduction and
output-feature coordinates, and both are loaded in the same reduction loop. One
global mapping must therefore serve two distinct address-difference
distributions  ( , 2026 ;  , 2026 ) .
The complete trace also depends on runtime composition: routing sets expert-local
workloads, while grouped GEMM uses runtime     (  M  ,  N  ,  K  )   (M,N,K)    values to form and schedule
tiles across problems  ( Hwang et al., 2023 ;  , 2026 ;  , 2026 ) . Expert-local    M  M    changes the number of tile instances,
their source-interval bases, and the interleaving of requests from different
tiles  ( , 2026 ;  , 2026 ;  , 2026 ) .
Trace-wide synthesis is also expensive: because each outer mapping candidate
induces a separate trace-dependent fixed-domain problem, exhaustively searching
the evaluated mapping families against the Llama 4 full trace requires on the
order of     10  14   10^{14}    evaluations of candidate copy events before any fixed-domain
solve, and every new phase, problem shape, or autotuned tile configuration
presents a fresh workload-wide target
(Appendix   B  ).
By contrast, the tile-local view is invariant. Once addresses are expressed as
source-interval offsets, tile configuration and operand properties fix one
ordered tile-local access sequence across instance origins and evaluated    M  M
values (Figure   3  ). The tile access signature records
these fields together with the resulting sequence, so TileDRAM selects one
tile-to-DRAM layout per signature
(Section   4.1  ).
3.  Overview
TileDRAM realizes compiler-controlled DRAM placement as a target-scoped
PLAN–BIND–APPLY lifecycle (Figure   4  ).
1         The DRAM configuration fixes the DRAM organization and the
controller-owned DRAM address mapping.
2         A tile access signature combines tile configuration, operand
properties,
and the ordered tile-local access sequence.
3         Layout selection evaluates layout candidates over the ordered requests for row reuse and
ranks legal candidates by fewer row conflicts, greater parallelism, and lower
address-generation complexity.
4         The selected layout is combined with the DRAM configuration
and packaged as a reusable tile-to-DRAM Linear Layout template.
5          BIND  looks up the  PLAN -produced
template for each tile access signature.
6          BIND  then combines the referenced
template with the tile ID, source interval,
and the DRAM region to construct a tile descriptor.
7         During execution,  APPLY  transforms each source
address using a GF(2)-based address transform, then uses the descriptor’s
region base to form the backend address.
8         A new DRAM configuration reruns  PLAN ;
BIND  and  APPLY  remain unchanged.

4.  Tile-to-DRAM Linear Layouts
This section develops tile-to-DRAM Linear Layouts as an     𝔽  2   \mathbb{F}_{2}   -linear
representation of compiler-controlled DRAM placement. For each tile access
signature, we formalize how a
candidate layout and the signature’s ordered tile-local access sequence jointly determine
row-buffer behavior. TileDRAM formulates layout selection as a row-locality
optimization subject to the target DRAM address mapping and placement constraints.
Each admitted signature yields a reusable tile-to-DRAM layout template for the target

5.  Compiler and Runtime Realization
The target-specific tile-to-DRAM layout template developed in
Section   4   is realized through the three-stage
PLAN–BIND–APPLY lifecycle.  PLAN  selects and realizes the template.
BIND  spans compilation and runtime: compiler-side

metadata to construct a tile descriptor for a resident tile (a concrete tile
instance placed in a DRAM region). During execution,  APPLY  consumes that descriptor to
transform each active lane’s source address; GPU execution and replay use the
same address transformation.

5.1.  Semantic Extraction and Offline Template Construction
Programming interface.
TileDRAM does not require programmers to name DRAM banks, rows, or
address-map bits. The programmer-facing annotation supplies problem, tile,
execution, and operand properties, while the kernel body remains ordinary
Triton/Gluon code (Appendix   C  ); DRAM placement remains
TileDRAM-managed rather than part of the kernel’s logical tile specification.
Semantic extraction.
From the tiled-kernel representation, the compiler derives the tile
configuration and operand properties. A recorded representative active-lane
sequence supplies the ordered tile-local access sequence; together, these
fields form the tile access signature. Normalization relative to the source
interval (Section   4  ) yields the representative
normalized source sequence used by  PLAN . For each admitted signature and
target contract,  PLAN  synthesizes the layout and its target-specific layout
realization, publishing one reusable template keyed by the signature.
5.2.  Template Binding and Address Lowering
Tile binding ( BIND )
On the compiler side,  BIND  performs template lookup for each admitted
tile access signature and records a reference to the corresponding
target-specific layout template produced by  PLAN , together with the
rule for deriving the tile ID from the execution context. A tile ID identifies
an operand tile within the current GEMM instance. For GEMM, the lhs and rhs tile
IDs are represented by the operand-tile coordinates     (   i  m   ,   i  k   )   (i_{m},i_{k})    and
(   i  k   ,   i  n   )   (i_{k},i_{n})   , respectively. When the tile is placed in a DRAM region, the compiler-defined tile-ID rule yields
the concrete tile ID from the current execution context, and runtime
BIND  obtains the referenced template from this binding metadata and
combines it with the tile ID, source interval     [  A  ,  A  +  E  )   [A,A+E)   , and concrete
DRAM region to construct a tile descriptor for the resident tile. Each
admitted resident tile uses one tile access signature and one corresponding
target-specific layout template throughout its residency, so its descriptor
remains fixed and is reused by accesses to the same resident tile.
Thus, lhs accesses from CTAs
that differ only in     i  n   i_{n}   , and rhs accesses from CTAs that differ only in     i  m   i_{m}   ,
resolve to the same tile descriptor.
At execution, runtime  BIND  provides the descriptor for the
current resident tile as input to  APPLY .
Address lowering ( APPLY )
At compilation, the compiler places  APPLY  after the source pointer
tensor is formed by address arithmetic for each admitted tile access. At execution, the path
uses the tile descriptor for the current resident tile to
transform each active lane’s source address for its
16-byte LDGSTS.128 transfer. The transformation follows three ordered stages:
Extract  each source address relative to the source interval, yielding the
layout-unit index and within-unit byte offset;  Transform  the layout
unit through the descriptor’s target-specific layout realization; and
Reconstruct  the backend address from the transformed unit,
unchanged byte offset, and region base before the copy. Per-lane integer
and pointer operations realize this software-selected placement through ordinary
address generation, requiring no new address-remapping hardware or ISA support.
The formal address contract is given in Appendix   A.1  , and
the binding metadata and address-lowering sequence appear in
Appendix   C  . Only operand accesses with a tile descriptor
are redirected to their assigned DRAM regions, while ordinary
loads and stores retain the conventional memory path.
5.3.  Runtime Replay and Simulator Execution
Simulator replay represents each dynamic tile access as an ordered tile-local access sequence of
active-lane asynchronous-copy events (LDGSTS.128) carrying source address     s  i   s_{i}    and event
metadata     η  i   \eta_{i}   . Here,     η  i   \eta_{i}    denotes the event’s identity, destination,
dependency, and request attributes. Runtime scheduling may interleave ordered tile-local access sequences
from resident tiles while preserving the event order within each sequence.
Each sequence carries the descriptor for its resident tile as
input to the  APPLY  path.
For each asynchronous-copy event, the simulator evaluates the same address
transformation specified by  APPLY  using the descriptor for the
sequence’s resident tile. It carries the resulting backend address
together with the event metadata into replay. Replay uses the descriptor’s
template and placement while preserving event metadata and dependency. The
production compiler lowering and simulator-side transformer implement one
common address function, checked against an independent reference evaluator.
Appendix   D   reports the covered configurations,
address-function families, and byte addresses. Each transformed
asynchronous-copy event forms one CU-local DRAM request in the Ramulator2
replay. Ramulator2’s fixed address mapper and controller advance row-buffer
state and return service latency to GPGPU-Sim, which applies it to the
originating asynchronous-copy dependency.

7.  Related Work
3D DRAM Architectures and Accelerators.
Vertical integration and hybrid bonding place high-bandwidth memory close to
compute, motivating architectures that exploit local memory–logic bandwidth
for LLM and MoE inference. H 2 -LLM co-designs heterogeneous hardware and
dataflow around hybrid-bonded memory  ( Li et al., 2025 ) , HybridSpec combines
such memory with heterogeneous execution and speculative decoding
( Huang et al., 2026 ) , Stratum uses tiered monolithic 3D DRAM and expert
placement for MoE serving  ( Pan et al., 2025 ) , and Raptor demonstrates an
early-silicon 3D-DRAM accelerator  ( Nair et al., 2026 ) . At industrial scale,
OpenAI’s Jalapeño pairs compute core slices with local HBM4 slices in a
memory-sliced organization  ( Ho et al., 2026 ) .
Other designs explore hybrid NVM–DRAM, processing-in-memory, and near-memory
parallelism  ( He et al., 2026 ;  Huang et al., 2025 ;  Li et al., 2026 ) . These systems
establish the architectural substrate for TileDRAM; TileDRAM instead exposes
how operand tiles are placed within local DRAM as a compiler-visible layout
decision.
Compute-Side Tile Layouts and Algebraic Layout Abstractions.
Modern GPU programming systems make tiled tensor organization and layout
first-class abstractions: CUTLASS and Triton support tiled computation, while
CuTe provides composable tensor layouts and layout algebra
( Cecka, 2026 ;  , 2026 ;  Tillet et al., 2019 ) . Graphene represents
multidimensional data and threads as hierarchically tiled first-class tensors,
expressing optimized GPU computations as mappings between data and thread tiles
( Hagedorn et al., 2023 ) . Gluon exposes explicit tensor layouts for
low-level control, and Jalapeño uses Gluon to program its spatial
architecture  ( Ho et al., 2026 ;  , 2026 ) . Linear Layouts provide an
algebraic representation for such compute-side layouts, mapping
hardware-resource coordinates to logical tensor coordinates over     𝔽  2   \mathbb{F}_{2}     ( Zhou et al., 2026 ) . TileDRAM extends this abstraction to DRAM placement coordinates, making tile-to-DRAM placement a
compiler-visible layout decision.
Controller Mapping and Software-Directed DRAM Placement.
Permutation-based interleaving distributes pages across DRAM structures
( Zhang et al., 2000 ) ; Liu et al.  ( Liu et al., 2018 )  propose PAE, an
XOR-based mapping that improves bank/channel parallelism while preserving
row-buffer locality; SDAM exposes software-configurable mappings for a 3D
memory controller  ( Zhang et al., 2022 ) ; Rotaru et al. synthesize an
application-specific mapping over     𝔽  2   \mathbb{F}_{2}    from a representative application
trace  ( Rotaru et al., 2025 ) ; and FACIL selects a mapping for each
huge page  ( Seo et al., 2025 ) . These approaches treat the controller mapping as
the decision variable. A single workload-specific mapping must serve
heterogeneous accesses, while specializing different access patterns requires
multiple mapping contexts and controller-side selection support.
Software-directed placement instead chooses where data reside, at page
( Agarwal et al., 2015 ) , DNN-layer  ( Pandey and Panda, 2024 ) , region
( Khadirsharbiyani et al., 2022 ) , or stream
( Li et al., 2024 )  granularity; the stream-based design also
controls element order and cache placement in a distributed DRAM cache.
TileDRAM keeps the controller mapping fixed and instead specializes data
placement using recurring ordered tile-local access behavior. Many tile access
signatures can therefore coexist under one mapping, with each
placement realized through ordinary address arithmetic and without
controller or ISA changes.
8.  Conclusion and Future Work
TileDRAM shows that DRAM placement can be an explicit compiler-controlled tile
layout decision while the memory-controller address mapping remains fixed.
Building on recurring tile-local access behavior as a stable specialization
unit, it extends GPU Linear Layouts to represent reusable tile-to-DRAM
placements selected per tile access signature. The resulting
compiler–runtime toolchain realizes these layouts through ordinary address
arithmetic, without new ISA support or remapping hardware.
Across 108 full-trace MoE FFN cases, TileDRAM reduces the request-weighted
row-conflict rate from 75.7% to 15.2% and achieves a 1.77   ×  \times    geomean
speedup; retargeting across six 3D DRAM organizations yields a 2.20   ×  \times
geomean speedup, while address transformation adds 0.17% overhead on
an RTX 3090.
Our evaluation focuses on tiled GEMM within one CU–stack pair, with the 3D DRAM
memory system evaluated through trace-driven Accel-Sim/Ramulator2 replay.
Future work includes extending TileDRAM to other kernels, such as attention
and convolution, coordinating layouts
across multiple CU–stack pairs, and validating compiler-controlled placement on
physical 3D DRAM systems.

B.2.  Cost of Rotaru-Style Exhaustive Full-Trace Synthesis
The multi-bank mapping synthesis of Rotaru et al.  ( Rotaru et al., 2025 )
uses a complete workload trace as its specialization unit and treats the domain
mapping as an outer search variable. After fixing an outer mapping, the trace is
compressed into weighted same-domain predecessor differences for the
fixed-domain Problem 3 solver. Changing the outer mapping changes
request-domain membership, same-domain predecessors, and therefore the resulting
difference histogram. Trace construction is thus candidate-dependent: a separate
fixed-domain Problem 3 instance must be reconstructed for every outer candidate
before its inner subspace solve.
For the evaluated organization, the source coordinate spans     n  =  23   n=23    bits and the
target requires     b  =  7   b=7    tier-and-bank dimensions, corresponding to 128
row-buffer domains for a full-rank     W  D   W_{D}   . The bit-selecting family
then contains 245,157 candidates for     W  D   W_{D}   , while the structured-XOR family
contributes 105,417,617 raw candidates. Together they yield
105,662,774 outer candidates before rank filtering and row-space deduplication.
Applying this search directly to the Llama 4 full trace with 7,864,320
active-lane copy events would perform approximately     8.31  ×   10  14    8.31\times 10^{14}
evaluations of candidate copy events before any
fixed-domain Problem 3 solve, full-map completion, or physical address-mapping
evaluation.
At a sustained aggregate rate of 10 billion evaluations of candidate copy events
per second on a large multicore CPU, this construction requires approximately
23.1 hours; at 1 billion evaluations per second, it requires approximately 9.6
days. These throughput-based estimates quantify raw outer construction before
Problem 3 solves, map completion, or physical address-mapping evaluation. The
outer construction alone therefore makes Rotaru-style exhaustive full-trace
controller-map synthesis computationally prohibitive as a routine
per-configuration path at the MoE FFN scale. Each new phase, problem shape, or
autotuned tile configuration supplies a new workload-wide specialization target.
These experiments separate synthesis tractability from mapping effectiveness.
Fixed global hashes are inexpensive but produce negligible changes in the
evaluated replay. Rotaru-style exhaustive full-trace synthesis explores a much
larger mapping space, but its candidate-dependent outer construction is
computationally prohibitive at this scale. TileDRAM instead changes the
specialization granularity: it keeps the controller mapping fixed and reuses
placement selected per recurring tile access signature.
