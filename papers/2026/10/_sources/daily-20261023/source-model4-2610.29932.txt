Abstract
Can LLM agents make contributions to frontier computer science R&D? We introduce FrontierCS 2, a benchmark of 48 open-ended tasks. We take a paper and the code its authors released and delete the paper’s contribution. The deleted code becomes the human reference that sets the bar.
Earlier open-ended benchmarks give each agent a problem statement and grade one program after the run. FrontierCS 2 places the agent inside a research environment. The agent inherits a working repository and may submit a patch at any point. For each patch, a judge returns a development-suite score but keeps the evaluator, the held-out final suite and the reference private, and grades the final submission on that suite against the reference.
The tasks span 13 domains, from machine-learning systems and high-performance computing to databases, security and robotics. Beyond these 48 tasks, FrontierCS 2 keeps a private set of more than 100 tasks, to be announced in the future.
We evaluate 12 agents. The best one is Claude Opus 5.5, passing 58% of its runs. No run passes on 16 tasks. A higher score is not the same as a pass: most runs that beat the reference on the combined final score still fall short on some metric or workload. On a shared capability scale for agents and tasks, the median task is roughly as difficult as what the strongest agent can handle.

1 Introduction
Figure 1: Pass rate. Share of each agent’s runs whose final submission beats the human reference on every metric and held-out workload; the harness is in gray.
Consider a researcher who picks up a published system to make it better. They inherit a working codebase, change one component, test the change on the workloads the paper reported, and are judged against the paper’s own implementation. Much of research and development in computer science looks like this. We ask whether an LLM agent can do the same.
Existing open-ended benchmarks answer a narrower question. On FrontierCS ( 1 ) , ALE-Bench ( 2 ) and AtCoder heuristic contests ( 3 ) , agents stay below the top human experts. These benchmarks share one design: the agent receives a problem statement and writes one program, and an evaluator scores it once, after the run ends.
Benchmarks that do place the agent in a real environment are narrow in another way. SWE-bench ( 4 ) and MLE-bench ( 5 ) grade against tests or a leaderboard. ResearchGym ( 6 ) , MLS-Bench ( 7 ) and PaperBench ( 8 ) stay within machine learning, and those that span other fields grade against a rubric or a reimplementation rather than the authors’ own code.

In this paper, we evaluate agents against the published code itself, inside the repository it came from, across computer science. FrontierCS 2 is the second version of FrontierCS ( \Cref tab:fcs-versions). We take the code a paper’s authors released, delete the paper’s contribution, and ask the agent to rebuild it so that it beats the original ( \Cref fig:overview). We call the deleted code the human reference and measure it on the paper’s own workloads ( \Cref sec:method). The agent works as a researcher would. It edits the code, submits a patch whenever it likes, and gets back a score on a development suite from a judge. The evaluator, the held-out final suite and the human reference stay with the judge ( \Cref sec:scoring). At the end, the agent names one patch as final, and the judge grades that patch on the held-out suite. A run passes only when the patch beats the human reference on every metric and every held-out workload.
We evaluate 12 models, each paired with one agent harness, with one run per task. The best agent, Claude Opus 5.5 in Claude Code, passes 58% of its runs, and every other agent passes fewer than half of its runs ( \Cref fig:pass-rate). No agent passes any of 16 tasks. To compare agents and tasks on one scale, we fit the FrontierCS Capabilities Index (FCI) together with a matching difficulty index. The median task sits at about the strongest agent’s FCI ( \Cref sec:exp-eci). The leading agent also changes with the cost budget per run ( \Cref sec:scaling).
In summary, our contributions are:
[topsep=2pt,itemsep=1pt]
•
Tasks built by subtraction: we delete a paper’s contribution from its repository and keep the deleted code as the bar ( \Cref sec:method).
•
A judge that scores patches during a run and keeps the evaluator, the held-out suite and the reference private ( \Cref sec:scoring).
•
48 tasks in 13 domains, with 12 agents evaluated ( \Cref sec:experiments) and three case studies ( \Cref sec:cases), and a private set of more than 100 tasks, to be announced in the future.

2 Related work
Open-ended coding benchmarks.
Unlike competition benchmarks with known solutions, such as LiveCodeBench Pro ( 9 ) , benchmarks that score a program on an objective with no known optimum now span heuristic contests ( 2 ) , combinatorial optimization ( 10 , 11 ) , GPU kernels ( 12 ) , and algorithmic and research problems ( 1 ) . Speed-up benchmarks start from a codebase and measure against a fixed baseline: the human nanoGPT speedrun record ( 13 , 14 ) or a naive PyTorch inference server ( 15 ) . FrontierCS 2 instead grades most of its tasks against the human reference, code the paper’s authors released, and scores each patch during the run.
Agent benchmarks for research and engineering.
A second family scores what an agent produces inside an environment. SWE-bench ( 4 ) and Terminal-Bench ( 16 ) grade with held-out tests, MLE-bench ( 5 ) with Kaggle leaderboards, and RE-Bench ( 17 ) against human experts given the same time budget. PostTrainBench ( 18 ) measures the downstream score of a post-trained model, and DeployBench ( 19 ) checks whether a research artifact runs its designated experiment. EdgeBench ( 20 ) also gives the agent feedback during a run. PaperBench ( 8 ) grades replication from scratch with a rubric, while AIRS-Bench ( 21 ) and ResearchGym ( 6 ) compare against published machine-learning results. RSI-Forge ( 22 ) turns papers from many fields into tasks whose baseline is an agent’s reimplementation of each paper’s method. Into the Unknown ( 23 ) grades follow-up papers on unpublished directions against expert criteria, and ReuF2F ( 24 ) poses formalized undergraduate research problems. None of these benchmarks sets its bar by measuring the original authors’ code. MLS-Bench ( 7 ) is the closest in design: each of its 140 machine-learning tasks across 12 areas asks the agent to improve one named component. We extend that design beyond machine learning to 13 computer-science domains, from databases to cryptography.
Building tasks from existing artifacts.
Methods that build tasks at scale start from an artifact that already works and break it in a controlled way. SWE-bench pairs a pull request with the tests it fixed, and SWE-smith ( 25 ) injects bugs into a repository so that existing tests fail. FrontierSmith ( 26 ) mutates closed competitive-programming problems into open-ended ones, and BenchEvolver ( 27 ) evolves solved problems into harder variants. DiscoGen ( 28 ) instead generates algorithm-discovery tasks procedurally. Like ResearchGym, we remove a paper’s method from its repository. Unlike it, our oracle is the removed code itself, and our tasks span 13 domains.
3 Task building
Figure 2: FrontierCS 2 task building. We delete the paper’s contribution from its own repository and give the agent what remains. The judge keeps the deleted code as the human reference, the pass thresholds measured from it on the paper’s workloads, and a final suite with held-out workloads.
We build the tasks by subtraction from the code the paper’s authors released ( \Cref fig:construction,tab:sources). 1 1
1
Except Structured LWE, an original cryptanalysis challenge ( \Cref app:sources). We locate the code that implements the paper’s contribution, delete it, and leave everything it depends on unchanged. Take SVG-EAR ( 29 ) , which we build from the Sparse VideoGen repository 2 2
2
\url https://github.com/svg-project/Sparse-VideoGen . We delete the error-aware attention class and three of its routines. These routines average each cluster, choose the cluster pairs to compute, and compute those pairs while estimating the rest. The agent receives this repository with the deleted functions still declared and called, and it must write them. It may edit only the files that held the contribution. The human reference is a private patch that restores the deleted code. Subtraction gives each task built this way an oracle that already runs in its repository on the paper’s own workloads.
We set each metric’s pass threshold from the reference’s own measurements on the workloads the paper reported. For SVG-EAR, latency must be at most 0.96 times the reference’s latency, PSNR must stay within 0.25 dB of the reference value, SSIM within 0.01 and LPIPS within 0.005. The judge scores every submission on a development suite of these workloads. Only the final submission is scored on a final suite, which adds held-out instances the agent never sees (different seeds, queries or input graphs).
4 Judge
Figure 3: FrontierCS 2 judge. Each colored box is a sandbox. The agent’s sandbox reaches only the driver. The agent sees only a development-suite score and a sanitized message per patch; all that decides its result stays with the judge.
The agent and the judge hold separate information ( \Cref fig:evaluation). The agent holds the repository; the judge holds the evaluator, the held-out final suite and the human reference. The agent has five hours and may submit a patch to the allowed files at any time. The judge returns the patch’s score on the development suite and a message that counts the development workloads meeting each metric’s threshold, without the reference score or the evaluator’s raw output.
They also run apart, each in its own sandbox, linked only by a driver started for the run. The agent’s sandbox reaches no network but the driver, which forwards its model calls and patches, so it cannot download the authors’ code. On GPU tasks, the agent may start a development GPU through the driver, while only the judge uses the GPU that measures the patch against the human reference. Some tasks also give the judge test sandboxes: on Continuum ( 30 ) , a vLLM serving task, they run SWE-bench episodes against the patched vLLM.
Development-suite scores guide the agent and do not count toward its result. At the end of the run, the agent names one submission as final, and the judge evaluates that patch alone on the held-out suite. We do not pick its best development-suite submission for it, since choosing the patch is part of a researcher’s work. We say a submission beats the reference on a metric when it meets that metric’s threshold. A run passes when its final submission beats the reference on every metric across every held-out workload. The judge also assigns a final score from 0 to 100 on a scale each task defines. 3 3

5 Evaluation results
5.1 Experimental setup
Figure 4: Pass rate and cost. Each point is one agent: pass rate on the y-axis against mean cost per run in US$ on a log-scale x-axis. GPT-6.1 Sol passes less often than GPT-6 Astra and sits far to its left on the cost axis.
Agents.
An agent pairs a model with a harness, the program that runs the model’s tool calls and submits its patches to the judge. We evaluate 12 models, each in one harness. We name each agent by its model, but the harness is part of what we measure. \Cref tab:agents lists each agent’s harness, version, reasoning effort and output limit.
Tasks and runs.
A run is one agent on one task, from the starting repository to its final submission. Each of the 12 reported agents runs each task once. The provider refused two Gemini 4 Argon runs before a final submission. Like every run without a passing final submission, they count as failures, in the pass rate and in FCI alike.
Metrics.
Our main metric is the pass rate, the share of an agent’s runs that pass. We also report an agent’s mean score, its mean margin over the human reference. This is the average over its runs of the final score minus the reference’s score on the same task (0 is a tie). \Cref fig:pass-cost sets each agent’s pass rate against its mean cost per run. A higher final score does not mean a pass, and a pass does not need a higher score ( \Cref fig:score-ref). Most runs whose final score exceeds the human reference’s miss a threshold on at least one metric or workload. Conversely, some passing runs score at or below the reference’s final score, since the final score is one number on each task’s own scale, while a pass needs every metric to hold at once.
Figure 5: Final score against the human reference. Each faint point is one run’s final score minus the human reference’s on the same task, one row per agent; the line spans each agent’s range and the dot marks its mean. The vertical line at 0 marks a tie.
5.2 FrontierCS Capabilities Index (FCI)
The FrontierCS Capabilities Index (FCI) puts the agents on one capability scale, and the FrontierCS Difficulty Index (FDI) puts the tasks on the same scale. FCI adapts Epoch AI’s Epoch Capabilities Index ( 31 ) , an item response model. We fit it to per-metric outcomes and to score margins over the human reference, rather than to raw scores.
One joint fit takes two observations from every run: which of the task’s metrics the run beats the human reference on, and the margin of its final score over the reference’s. The metric outcomes tell the fit how hard each part of a task is, and the margin tells it how close a failed run came. Both share one fitted run effect, which says how far that run lands above or below its agent’s strength.
Each agent has one strength, which we report as its FCI: ten points per logit, with Kimi K2.7 at 0. Kimi K2.7, run in Kimi Code, is a thirteenth agent that serves only as this 0 point: its runs enter the fit, but we do not report it. A task’s FDI is the FCI at which an agent passes it half the time. The human reference has no FCI, since its code cannot beat itself. Intervals are 90% bootstrap intervals over the tasks, and \Cref app:fci gives each step of the fit.
Figure 6: FrontierCS Capabilities Index. Each bar shows an agent’s FCI from 0 with its 90% bootstrap interval as a whisker. The intervals separate only agents that sit far apart on the capability scale.
Claude Opus 5.5 leads FCI, followed by GPT-6 Astra and GPT-6.1 Sol, and Step 5 Preview is last ( \Cref fig:fci); FCI and the pass rate order the agents almost alike. The tasks span a wider range of difficulty than the agents do: the median task sits at about the strongest agent’s FCI. Each task’s FDI is uncertain, however, so we do not order individual tasks by it. FDI measures how hard a task is to pass, and across tasks it follows the pass rate closely.
5.3 Test-time scaling
Test-time scaling asks what FCI an agent would reach under a cost cap per run. At budget B B , a run that finished within B B keeps its held-out result, and a run still going at B B counts as one without a final submission, which scores 0. With the task parameters fixed at their FCI fit ( \Cref sec:exp-eci), the FCI at B B is the strength that best fits these outcomes ( \Cref app:fci). A run’s outcome can only improve as B B grows, so no curve falls, and each ends at the agent’s FCI.
Figure 7: Test-time scaling. FCI of each agent against the cost budget per run, in US$ on a log scale; a run still going at a budget counts as one without a final submission. Each curve starts at the first budget at which its FCI is at least 0 and ends at the agent’s FCI. Two slanted strokes mark an empty budget range skipped on the axis. The leader changes with the budget.
Which agent leads depends on the budget ( \Cref fig:scaling). At the smallest budgets, DeepSeek V4.1 Flash leads. Its costs are lower bounds, so this lead depends on how we price its tokens. Claude Opus 5.5 leads at the largest budgets.
6 Case studies
6.1 Two checksums shrink private lookups
Figure 8: QuarterPIR bytes per lookup. Bytes per private lookup on the 67-million-entry database; the x-axis starts at 1,200. Muse Wonder 1.0’s checksums remove far more of the reference’s bytes than any other passing run does. Kimi K3, far below the rest and not passing, is left out. Step 5 Preview’s run timed out.
Private information retrieval lets a client read one entry of a database held by a server, without the server learning which entry it read. QuarterPIR ( 32 ) makes this cheap. The client first builds a compact summary of the database; afterwards, each lookup costs one short request and one short reply. In our task the agent rewrites how the server answers requests, and it may also change the messages and the client. A run passes if every lookup returns the right entry and the run beats the human reference on the bytes each lookup sends, on every timing, and on the memory the client keeps.
In the human reference, every reply carries values the client rarely needs. Along with the answer, the server returns one parity value for each group of the database. The client needs only one of them, to correct the hint it refreshed after its previous lookup. Asking for that one alone, however, would tell the server where its previous lookup went. Muse Wonder 1.0 replaces these values with two checksums, the construction that lets a RAID-6 disk array rebuild two failed disks. Since the client already knows the only two groups in which its own values can differ from the server’s, two checksums are enough to recover the one it needs. This shrinks every reply, and therefore every lookup. Privacy is unchanged, because the task lets the server see only a public function of the request the authors’ client would send.
Muse Wonder 1.0’s run passes with a final score above the human reference’s. Most agents pass this task, but no other passing run shrinks the lookup by nearly as much ( \Cref fig:case-quarterpir). We found this idea only by reading the patches, since neither of our measures picks it out. A pass counts the same whether a run saves a few bytes or the most. GPT-6.1 Sol even scores slightly higher than Muse Wonder 1.0 with a far smaller saving.
6.2 Two faster clocks for a packet scheduler
Figure 9: BBQ clock period and circuit size. Each point is one agent’s circuit on the largest tree, 4,096 priorities. The x-axis gives its size in lookup tables and the y-axis its clock period, with shorter, faster clocks at the top; the grey dot marks the human reference. Claude Opus 5.5’s circuit has the shortest clock period and is among the largest. Agents without a correct circuit at this size are left out.
A network switch or network card has to decide, for every packet it sends, which waiting packet goes next. Programmable schedulers express this decision as a priority queue: each packet carries a priority, and the queue must hand out the most urgent one millions of times per second. BBQ ( 33 ) builds such a queue as an FPGA circuit. It marks the occupied priorities in a tree of bitmaps. Each bit keeps a count of the packets below it, so that the bit can be cleared when its last packet leaves. In our task the agent rewrites the logic of the tree’s levels. A run passes if the circuit is correct and beats the human reference on throughput and on worst-case latency at every tree size, including a larger one that the agent never sees during development.
On the smaller trees, the slowest step of each clock cycle in the human reference begins with a counter read from on-chip memory. The operation just ahead may have changed the same counter a moment earlier. The circuit therefore has to check the value it read against recent updates before it can use it. Gemini 4 Argon keeps the memories but settles that check while the read is still in flight, leaving little work for when the value arrives. Claude Opus 5.5 takes the other route. It moves every counter from memory into registers and updates a whole level of the tree in a single cycle, so that on the development trees no operation waits for a read.
Only these two and GPT-6.1 Sol pass, and the two designs trade speed for size ( \Cref fig:case-bbq). Both handle more operations per second than the human reference on every tree. On the largest tree, however, the circuit of Claude Opus 5.5 uses the most lookup tables of the passing circuits. Its design also does not serve trees as large as those BBQ was designed for. Gemini 4 Argon keeps roughly the human reference’s circuit size and memory layout. Registers alone do not explain Claude Opus 5.5’s clock. Other agents also move the counters into registers, and on the largest tree they end up slower than the human reference. The final score ranks Claude Opus 5.5 first, because it rewards speed and ignores circuit size.
6.3 A measured budget for sparse video attention
Figure 10: SVG-EAR time and PSNR. Each run’s mean time per clip and mean PSNR against full attention on the held-out clips, with the human reference’s in grey; the x-axes start at 600 s and 16 dB. Only GPT-6 Astra is both faster and closer to full attention than the human reference on average, and it still fails. Step 5 Preview, far slower, is off the chart.
Video diffusion models spend most of their time in attention. SVG-EAR ( 29 ) , our running example in \Cref sec:method, computes some blocks of attention exactly and estimates the rest from cluster centroids. Within a fixed budget, it computes the blocks whose estimates would err the most. A run passes only if every held-out clip is faster than with the human reference and stays within narrow bands of its PSNR, SSIM and LPIPS.
No run passes, and GPT-6 Astra comes closest. It keeps the authors’ design but measures the error instead of predicting it. Every few denoising steps, it computes the exact attention of a few real queries and rebuilds their output under several budgets. Each attention head then runs with the smallest budget whose error stays under a bound. Astra also corrects a bias of the centroid estimate that the paper leaves in. Its videos come out faster than the human reference’s on every clip and, on average, closer to full attention ( \Cref fig:case-svgear). It still fails on image quality in two clips. Speed was not the obstacle on this task. Most runs beat the reference’s time on every clip, and no run stays within every image band.
7 Conclusion
We built FrontierCS 2 to ask whether LLM agents can make contributions to frontier computer science R&D. Each task measures an agent against the code that researchers released with their paper, in that code’s own repository. Beyond these 48 tasks, FrontierCS 2 keeps a private set of more than 100 tasks, to be announced in the future.
The case studies show what the pass and the final score capture and what they miss. On SVG-EAR, a run faster than the human reference on every clip and closer to full attention on average still fails on image quality in two clips ( \Cref sec:case-svgear). On QuarterPIR, neither measure separates the run that removes far more bytes per lookup from the other passing runs ( \Cref sec:case). On BBQ, the final score ranks the largest passing circuit first, because it ignores circuit size ( \Cref sec:case-bbq). We think benchmarks like this one will need to report such side costs next to the pass.
FCI and FDI are the measures we recommend for benchmarks like this one. They place agents and tasks on one scale, use every metric outcome and score margin of a run rather than one number, and come with intervals that show which differences the data support ( \Cref sec:exp-eci).

Appendix D Computing FCI and FDI
FCI and FDI come from one statistical model, fitted to all runs at once. Our fitting code carries out the twelve steps below, and every value in this appendix comes from the fit behind \Cref sec:exp-eci. \Cref tab:fci-params lists the constants and fitted values.
Step 1: collect the runs.
The fit uses every run with a final score on the evaluated tasks. Besides the 12 reported agents, it includes Kimi K2.7, which anchors the zero of the scale but is not reported. A run that ends without a saved final submission scores 0, and so do the two runs that Gemini 4 Argon’s provider refused ( \Cref sec:exp-setup). This gives 624 runs.
Step 2: score each metric.
Each task’s judge measures a fixed set of metrics, such as latency, throughput or accuracy, on every held-out workload. A run beats a metric when its final submission beats the human reference on that metric in every held-out workload. A run that fails before the held-out evaluation beats no metric. A run therefore passes exactly when it beats every metric of its task.
Step 3: merge metrics into groups.
Two metrics that every run of a task beats or misses together cannot be told apart by the data, and fitting each with its own difficulty would make the task look harder than it is. Such metrics form one group. A run beats a group when it beats every member. Let K t K_{t} be the number of groups of task t t , and let x a ​ t ​ g ∈ { 0 , 1 } x_{atg}\in\{0,1\} record whether agent a a beats group g g of task t t . The tasks yield 115 groups.
Step 4: measure the score margin.
Final scores use each task’s own scale, so the fit converts a run’s distance from the human reference into a common unit. The reference score s t ref s^{\mathrm{ref}}_{t} is the median, over the task’s runs, of the human reference’s final score measured within each run. If the runs of a task record no positive reference score, a value set in advance takes its place. The spread d t d_{t} is the standard deviation of the task’s final scores that lie strictly between 0 and 100, or of all its final scores when fewer than three do. The unit is c t = max ⁡ ( d t , c ) c_{t}=\max(d_{t},c) , whose floor c c is the median of d t d_{t} over the tasks. The margin of agent a a on task t t is
y a ​ t = s a ​ t − s t ref c t , y_{at}=\frac{s_{at}-s^{\mathrm{ref}}_{t}}{c_{t}},
(1)
where s a ​ t s_{at} is the run’s final score. A run enters the fit with its margin in one of three ways. A run that passes, or fails and scores below the reference, contributes y a ​ t y_{at} as measured. A run that fails but scores above the reference contributes only y a ​ t ≥ 0 y_{at}\geq 0 : it is at least level with the reference, since at least one of its metric groups misses. A run that ties the reference exactly contributes no margin.
Step 5: write the likelihood of one run.
Each agent has a strength θ a \theta_{a} , each metric group a difficulty β t ​ g \beta_{tg} , and each task a tie level h t h_{t} , all in logits. The tie level is the strength at which a run’s expected margin is zero. A run also has a run effect u a ​ t ∼ 𝒩 ⁡ ( 0 , σ u 2 ) u_{at}\sim\mathcal{N}(0,\sigma_{u}^{2}) , which says how far this run lands above or below its agent’s strength. The groups and the margin come from the same measurements, so both share the run effect. Given u a ​ t = u u_{at}=u , the run beats group g g with probability
P ⁡ ( x a ​ t ​ g = 1 ∣ u ) = σ ⁡ ( θ a + u − β t ​ g ) , σ ⁡ ( z ) = 1 1 + e − z , P(x_{atg}=1\mid u)=\sigma(\theta_{a}+u-\beta_{tg}),\qquad\sigma(z)=\frac{1}{1+e^{-z}},
(2)
and its margin is normal with slope α \alpha and noise σ e \sigma_{e} ,
y a ​ t | u ∼ 𝒩 ⁡ ( α ⁡ ( θ a + u − h t ) , σ e 2 ) . y_{at}\mid u\sim\mathcal{N}\big(\alpha\,(\theta_{a}+u-h_{t}),\ \sigma_{e}^{2}\big).
(3)
A measured margin enters through this density, and a margin known only to be at least 0 through the probability Φ ⁡ ( α ⁡ ( θ a + u − h t ) / σ e ) \Phi\big(\alpha\,(\theta_{a}+u-h_{t})/\sigma_{e}\big) , where Φ \Phi is the standard normal distribution function. Write f a ​ t ​ ( u ) f_{at}(u) for this density, this probability, or 1 for a run that ties. The likelihood of the run integrates the run effect out,
L a ​ t = ∫ ∏ g = 1 K t σ ​ ( θ a + u − β t ​ g ) x a ​ t ​ g ​ ( 1 − σ ⁡ ( θ a + u − β t ​ g ) ) 1 − x a ​ t ​ g ​ f a ​ t ​ ( u ) ​ ϕ σ u ​ ( u ) ​ 𝑑 u , L_{at}=\int\prod_{g=1}^{K_{t}}\sigma(\theta_{a}+u-\beta_{tg})^{x_{atg}}\big(1-\sigma(\theta_{a}+u-\beta_{tg})\big)^{1-x_{atg}}\,f_{at}(u)\,\phi_{\sigma_{u}}(u)\,du,
(4)
where ϕ σ u \phi_{\sigma_{u}} is the density of 𝒩 ⁡ ( 0 , σ u 2 ) \mathcal{N}(0,\sigma_{u}^{2}) . Gauss–Hermite quadrature with 64 nodes evaluates the integral.
Step 6: set the priors.
Each strength has the prior θ a ∼ 𝒩 ⁡ ( 0 , 1 / λ ) \theta_{a}\sim\mathcal{N}(0,1/\lambda) with λ = 0.35 \lambda=0.35 . Each task’s tie level has h t ∼ 𝒩 ⁡ ( 0 , 6 2 ) h_{t}\sim\mathcal{N}(0,6^{2}) , and its group difficulties have β t ​ g ∼ 𝒩 ⁡ ( h t + δ , τ 2 ) \beta_{tg}\sim\mathcal{N}(h_{t}+\delta,\tau^{2}) . The offset δ \delta is how far a typical group sits above the tie level, and τ \tau is how widely the groups scatter around that point. This prior keeps a group that no run beats at a finite difficulty, pulled toward the task’s other evidence.
Step 7: find the joint mode.
For fixed hyperparameters ( σ u , α , δ , τ , σ e ) (\sigma_{u},\alpha,\delta,\tau,\sigma_{e}) , the fit maximizes the log posterior
∑ a , t log ⁡ L a ​ t + ∑ a log ⁡ p ⁡ ( θ a ) + ∑ t log ⁡ p ⁡ ( h t , β t ​ 1 , … , β t ​ K t ) \sum_{a,t}\log L_{at}+\sum_{a}\log p(\theta_{a})+\sum_{t}\log p(h_{t},\beta_{t1},\ldots,\beta_{tK_{t}})
(5)
jointly over the 13 strengths and the 163 task parameters, namely 115 group difficulties and 48 tie levels. It uses Newton’s method. Each run touches one strength and one task, so the Hessian is sparse: the step for the strengths is solved through their Schur complement, and a step that lowers the objective is halved until it does not.
Step 8: fit the hyperparameters.
The five hyperparameters maximize an approximate marginal likelihood. At the joint mode of Step 7, a Laplace approximation integrates each task’s parameters out; the sum of these terms over tasks, plus the strengths’ log prior at the mode, is the objective. Nelder–Mead searches it from two starting points, with σ u \sigma_{u} capped at 7 logits. \Cref tab:fci-params lists the values at its maximum, and Step 7 is then repeated at these values.
Step 9: place the agents on the FCI scale.
An agent’s FCI is its strength relative to Kimi K2.7’s,
FCI a = 10 ​ ( θ a − θ K2 ​ .7 ) , \mathrm{FCI}_{a}=10\,(\theta_{a}-\theta_{\mathrm{K2.7}}),
(6)
where θ K2 ​ .7 \theta_{\mathrm{K2.7}} is the strength of Kimi K2.7. Kimi K2.7 thus sits at 0, and ten points equal one logit: an agent ten points higher has e ≈ 2.72 e\approx 2.72 times the odds of beating any metric group, for the same run effect.
Step 10: bootstrap the FCI intervals.
Each of 500 bootstrap draws resamples the tasks with replacement, so a task may appear several times or not at all. The draw refits the strengths and task parameters from the full fit’s mode, with the hyperparameters held at their Step 8 values, and maps its strengths to FCI through its own θ K2 ​ .7 \theta_{\mathrm{K2.7}} . An agent’s 90% interval spans the 5th to 95th percentile of its FCI across the draws. All 500 draws converge.
Step 11: compute each task’s FDI.
With the group difficulties at the mode, an agent of strength θ \theta passes task t t with probability
P t ​ ( θ ) = ∫ ∏ g = 1 K t σ ⁡ ( θ + u − β t ​ g ) ​ ϕ σ u ​ ( u ) ​ 𝑑 u , P_{t}(\theta)=\int\prod_{g=1}^{K_{t}}\sigma(\theta+u-\beta_{tg})\,\phi_{\sigma_{u}}(u)\,du,
(7)
since a pass needs every group beaten in the same run. P t P_{t} rises with θ \theta , and the task’s difficulty D t D_{t} solves P t ​ ( D t ) = 1 / 2 P_{t}(D_{t})=1/2 , found by bisection. Its FDI is 10 ​ ( D t − θ K2 ​ .7 ) 10\,(D_{t}-\theta_{\mathrm{K2.7}}) , on the scale of \Cref eq:fci-scale. For the 90% interval of the FDI, 2,000 draws of the task’s parameters come from the Laplace Gaussian at the mode, with the strengths held. Each draw is weighted by the ratio of the exact posterior to the Gaussian density, which corrects the one-sided posterior of a group that no run beats. The interval spans the weighted 5th to 95th percentiles of D t D_{t} across the draws.
Step 12: refit FCI under a cost budget.
Test-time scaling, defined in \Cref sec:exp-rules, holds every task’s parameters and the hyperparameters at the full fit. At a budget of B B US$ per run, a run that finished within B B contributes its outcomes from Steps 2 to 4. A run still going at B B counts as a run with no final submission: it beats no group, and its margin is that of a final score of 0. The agent’s FCI at B B is the strength that maximizes its runs’ log likelihood plus its log prior, found by Newton’s method and mapped by \Cref eq:fci-scale. Its 90% interval comes from 100 bootstrap draws over the agent’s tasks. The rule uses no development score, because development scores swing: the judge assigns 0 whenever a submission fails a correctness or quality check, yet most runs that drop to 0 after a positive score recover above 0 later. A rule based on development scores would also have to pick a patch at each budget (the newest, the best so far or the last valid one) without held-out verification.
