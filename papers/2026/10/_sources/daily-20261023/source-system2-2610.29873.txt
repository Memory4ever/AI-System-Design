Abstract.
Large language model (LLM) inference exhibits distinct computational characteristics across its two phases: prefill is compute-intensive, whereas decode is more memory-bound.
As a result, AI accelerators achieve varying levels of efficiency across the two phases.
GPUs are well suited to prefill, but are often underutilized during decode. By contrast, NPUs can utilize their compute resources more effectively during decode.
Motivated by this observation, we explore a heterogeneous architecture that integrates GPUs and NPUs, mapping prefill to GPUs and decode to NPUs to achieve high performance and efficiency.
However, realizing such heterogeneous integration is challenging because LLM phase disaggregation requires KV cache transfer from prefill to decode—that is, from GPUs to NPUs—which is complicated by differences in inter-device communication mechanisms and KV cache tensor layouts.
To address this, we propose HAWK , a transfer mechanism that enables rapid KV cache transfer across heterogeneous devices. HAWK establishes a remote direct memory access (RDMA) path for direct cross-device transfers while handling inter-device tensor layout discrepancies as part of the transfer process.
In particular, HAWK allocates tensor-layout-aware RDMA buffers on the NPU side to match the target tensor layout. Leveraging these buffers, HAWK orchestrates data transfer from a conventional contiguous GPU RDMA buffer to the corresponding NPU buffers, allowing transferred tensors to be consumed directly without additional data rearrangement while maintaining transfer efficiency.
We implement and evaluate HAWK on a system built with commercially available GPUs and NPUs, demonstrating performance within 7.88% of a GPU-only system under the same SLO constraints while achieving up to 1.26 × \times higher power efficiency and 1.72 × \times higher cost efficiency.
Keywords: Large language models (LLMs), Graphic processing units (GPUs), Neural processing units (NPUs), Heterogeneous Architecture
1. Introduction
LLMs have become a dominant foundation for modern artificial intelligence systems and are widely used across a broad range of applications, including conversation agents and assistants for coding and research ( Singh et al., 2025 ; Grattafiori et al., 2024 ; Anthropic, 2025 ; Team et al., 2024 ) .
To improve model capabilities, LLMs have grown substantially in scale and complexity, driving a corresponding increase in AI infrastructure requirements ( Kaplan et al., 2020 ; Narayanan et al., 2021 ; OpenAI, 2026 ; Microsoft, 2025 ; Stanford Institute for Human-Centered Artificial Intelligence, 2026 ) .
In particular, GPUs have emerged as a primary platform for LLM inference due to their programmability, versatility, and high performance ( NVIDIA, 2026a ; NVIDIA, 2026i ; AMD, 2026 ; NVIDIA, 2023 ; AMD, 2025 ) .

GPU Underutilization in LLM Inference: However, GPU efficiency varies across different phases of LLM inference: prefill and decode.
During prefill, the model processes input tokens in parallel, resulting in general matrix-matrix multiplication (GEMM) operations that efficiently map onto GPU tensor cores ( AMD, 2022 ; NVIDIA, 2019 ; NVIDIA, 2023 ) and enable high computing utilization.
In contrast, during decode, the model generates one token at a time and the computation is dominated by general matrix-vector multiplication (GEMV). Since GEMV provides limited tile-level parallelism and data reuse, it results in lower compute utilization. In particular, modern LLM inference systems increasingly adopt disaggregated prefill-decode architectures ( Hu et al., 2024b ; Zhong et al., 2024 ; Jiang et al., 2025b ; Jin et al., 2024 ; Qin et al., 2025 ; Bai et al., 2026 ; Patel et al., 2025 ; Liang et al., 2025 ; Hu et al., 2024a ; Ruan et al., 2025 ; Hong et al., 2025 ; Wu et al., 2025 ; Shi et al., 2025 ; Wang et al., 2025a ; Singh et al., 2024 ; Chen et al., 2025b ) , which decouple the two phases to reduce interference between them and improve system scalability.
In this setting, a heterogeneous system that uses GPUs for prefill and NPUs for decode can achieve both high performance and efficiency.
Challenges: Despite its potential advantages, this heterogeneous system faces several challenges to practical adoption.
The first challenge is transferring KV caches generated during GPU prefill to NPUs for decode.
In homogeneous GPU systems, optimized communication software stacks such as NVIDIA NIXL ( NVIDIA, 2026g ; NVIDIA, 2026c ) enable direct GPU-to-GPU data transfer via RDMA over InfiniBand or RoCE.
In contrast, heterogeneous data transfer remains relatively underexplored. Moreover, NPUs often rely on diverse, vendor-specific communication mechanisms ( Intel, 2025 ; Amazon Web Services, 2026b ; The JAX Authors, 2024 ; Tenstorrent, 2026c ) , further complicating interoperability with other devices.
The second challenge is handling heterogeneous tensor memory layouts. In LLMs, many data structures, including weights, activations, and KV cache, are represented as tensors ( Kwon et al., 2023 ) .
Accelerators across device types and vendors often employ device-specific tensor memory layouts to reduce memory traffic and optimize computation ( Chen et al., 2025b ; Tenstorrent, 2026f ; Google, 2025 ; Huawei Cloud, 2026 ; Qualcomm, 2026 ) .
Resolving such tensor layout discrepancies requires additional data rearrangement, complicating data transfer and increasing latency.
Enabling Heterogeneous LLM Inference:
This paper presents HAWK ( H eterogeneity- AW are K ey-Value Transfer), a mechanism that enables high-performance LLM inference across heterogeneous devices.
HAWK establishes a direct data transfer path between GPU and NPU memory by connecting both to a common RDMA stack.
To handle tensor layout discrepancies, HAWK applies a transfer-aware transformation to the GPU KV cache to produce a tensor layout that matches the target NPU layout while facilitating efficient RDMA transfer.
On the NPU side, HAWK allocates RDMA buffers to match the tensor layout expected by the target NPU, with separate buffers distributed across its DRAM channels. This organization allows the transferred tensor to be consumed directly for decode without post-transfer conversion.
In our evaluation, HAWK achieves up to 27.69 × \times faster heterogeneous KV cache transfers than naive host-staged transfers, with a latency difference of only 0.65% relative to a GPU-to-GPU RDMA path.
Compared with a GPU-only system, our heterogeneous system with HAWK achieves up to 1.26 × \times higher power efficiency and 1.72 × \times higher cost efficiency, with a performance difference of at most 7.88% under the same SLO constraints.
To the best of our knowledge, this work is the first to design and evaluate a high-performance data transfer mechanism across heterogeneous devices on a real system. While this work focuses on KV cache transfer, HAWK can also support other tensor objects, such as weights and activations, required by other forms of disaggregated LLM serving.
Overall, this paper makes the following contributions.
•
We characterize the phase-dependent execution behavior of GPUs and NPUs for LLM inference. GPUs achieve high compute utilization during prefill but are substantially underutilized during decode.
In contrast, NPUs exhibit higher compute utilization while achieving decode performance comparable to GPUs, providing a more efficient design point consistent with their dataflow-oriented architectures.
•
We propose a heterogeneous GPU–NPU serving system that assigns prefill to GPUs and decode to NPUs to achieve high performance and efficiency. We identify cross-device data transfer as a critical bottleneck in this design, motivating the need for a high-performance heterogeneous transfer mechanism.
•
We present HAWK , a heterogeneity-aware KV cache transfer mechanism. HAWK leverages an RDMA-based transfer path that bypasses host intervention and handles cross-device tensor-layout mismatches through transfer-aware tensor transformation and tensor-layout-aware RDMA buffer allocation.
2. Background
2.1. LLM Inference
Figure 1 illustrates the inference process of a conventional decoder-only Transformer, which consists of two phases: prefill and decode. Both phases follow the same sequence of a token embedding layer, multiple decoder layers, and a language modeling (LM) head, but differ in the number of tokens processed.
During the prefill phase, all input tokens are first converted into embedding vectors by the token embedding layer (❶). The resulting embeddings are then processed by multiple decoder layers, each consisting of layer normalization, multi-head attention, residual connections, and a feedforward network (FFN) (❷), to capture inter-token relationships, incorporate contextual information, and refine token representations. The output of the decoder layers is then passed through the LM head to produce token scores, from which the next token is selected (❸). The selected token is subsequently fed back into the token embedding layer as input, initiating the autoregressive decode phase (❹), which continues until an end-of-sequence (EOS) token is generated or the maximum generation length is reached.
In particular, multi-head attention within each decoder layer computes Query, Key, and Value (QKV) activations from the input, which serve as the core intermediate representations for attention computation and inter-token interaction ( Vaswani et al., 2017 ) . The Key and Value activations generated for each token remain unchanged during subsequent decoding steps and can therefore be reused. To exploit this property, LLM inference stores these activations in memory as a key-value (KV) cache and retrieves them in later decoding steps, avoiding redundant computation. The KV cache grows incrementally as new tokens are generated, with the Key and Value activations of each new token appended to the existing cache.

2.2. Characteristics of Prefill and Decode
The dominant computations in the decoder layer, including QKV projections, attention computation, output projection, and FFN projections, depend on the input shape ( Agrawal et al., 2023 ; Park et al., 2024 ) , as shown Table 2 . During prefill, all input tokens are processed in parallel ( L L equals the initial input length), producing a matrix of embedding vectors; consequently, these computations are dominated by GEMM.
During decode, in contrast, the model processes one newly generated token at a time ( L L equals 1), producing a vector; accordingly, the dominant computations are mapped to GEMV, which exhibits lower arithmetic intensity and reduced data reuse relative to GEMM.
Moreover, decode requires fetching KV caches from previously processed tokens, which introduces more memory traffic than prefill.

3. Motivation
3.1. Phase-Dependent GPU Efficiency
GPUs are a primary platform for LLM inference due to their high performance and mature software ecosystem ( Kwon et al., 2023 ; Zheng et al., 2024 ; NVIDIA, 2026i ; Lee et al., 2024 ) . However, GPU computational efficiency varies across inference phases due to the distinct characteristics of prefill and decode.
We profile GPU kernels in a decoder layer during prefill and decode on A100 GPUs using Nsight Compute ( NVIDIA, 2026e ) .
Figure 2a shows tensor core and DRAM utilization for the QKV projection kernel as a representative example.
During prefill, the kernel achieves high tensor core utilization ( ∼ 92.92 % \sim 92.92\% ) with relatively low DRAM utilization ( ∼ 19.26 % \sim 19.26\% ) because the computation is dominated by GEMM operations that maps efficiently onto GPU tensor cores.
During decode, in contrast, the kernel exhibits lower tensor core utilization ( ∼ 35.90 % \sim 35.90\% ) and higher DRAM utilization ( ∼ 64.09 % \sim 64.09\% ), reflecting GEMV-dominated computation and additional memory accesses for KV cache retrieval.
Table 3 shows that other kernels in a decoder layer also exhibit low computational efficiency during decode for similar reasons.
Although request batching can make GEMV execution more GEMM-like by increasing B B in Table 2 , these benefits emerge only at sufficiently large batch sizes ( Park et al., 2024 ) , as the performance gains from small-batch execution are limited, as shown in Figure 2a .
In practice, however, such large batch sizes are often infeasible due to memory capacity constraints: the KV cache size in elements, 2 × L × N l × N h × N h ​ d × B 2\times L\times N_{l}\times N_{h}\times N_{hd}\times B , grows linearly with batch size, where N l N_{l} , N h N_{h} , and N h ​ d N_{hd} denote the number of decoder layers, the number of KV heads, and the head dimension, respectively.
Furthermore, GPU power consumption remains relatively stable across the two phases, as shown in Figure 2b .
Because tensor cores represent a significant component of GPU power consumption when active ( Kandiah et al., 2021 ) , the lower tensor core utilization during decode might be expected to reduce power consumption. However, the power consumption does not show a corresponding decrease when transitioning from prefill to decode.
Consequently, decode on GPUs exhibits not only lower computational efficiency but also lower power efficiency than prefill.

3.2. Potential of NPUs for Efficient Decode
NPUs are specialized accelerators designed for AI workloads. While their detailed designs vary, most broadly adopt dataflow-oriented architectures that explicitly manage computation and data movement to maximize data reuse and reduce the impact of off-chip memory accesses ( Sze et al., 2017 ; Chen et al., 2016 ; Jouppi et al., 2017 ; Liao et al., 2021 ; Kaplan, 2024 ; Amazon Web Services, 2026a ) . These characteristics can be particularly beneficial for GEMV-like computation during decode.
Table 4 compares the compute utilization and power efficiency of GPUs (A100) and NPUs (p150a) for representative kernels in a decoder layer during decode.
Compute utilization is calculated by dividing the achieved throughput (TFLOPS) by the peak throughput of the compute cores used by each kernel and multiplying by 100.
During decode, the evaluated NPUs use fewer compute cores than during prefill (e.g., 8 versus 64 for FFN operations ( Tenstorrent, 2026e ) ) and select cores closer to DRAM to better accommodate the limited parallelism and memory-intensive nature of GEMV-like computation.
By concentrating computation on fewer cores, they maintain high utilization of the assigned cores, exceeding GPU utilization across all evaluated kernels.
While using fewer cores may limit kernel throughput, it can also improve power efficiency by reducing the number of active compute cores.
In our evaluation, the NPU achieves higher power efficiency for attention and FFN kernels, which account for a substantial fraction of LLM decoding time ( Wang et al., 2025b ) .
Although we evaluate one NPU platform, other NPU architectures may achieve similar efficiency gains through different mechanisms.
When these efficiency gains are achieved while maintaining comparable performance, as shown in Table 1 , NPUs can be considered an attractive option for efficient decode serving.

3.3. LLM Disaggregation with GPUs and NPUs
Figure 3 illustrates a phase-disaggregated LLM serving system that separates the prefill and decode phases on different computing resources ( Hu et al., 2024b ; Zhong et al., 2024 ; Jiang et al., 2025b ; Jin et al., 2024 ; Qin et al., 2025 ; Bai et al., 2026 ; Patel et al., 2025 ; Liang et al., 2025 ; Hu et al., 2024a ; Ruan et al., 2025 ; Hong et al., 2025 ; Wu et al., 2025 ; Shi et al., 2025 ; Wang et al., 2025a ; Singh et al., 2024 ; Chen et al., 2025b ) .
An LLM replica is loaded onto each computing resource, typically on separate server nodes, and the request router forwards incoming requests to the prefill instance (①). The prefill instance generates the first token and KV cache for the input tokens (②), which are then transferred to the decode instance for subsequent token generation (③).
By isolating the two phases, this system reduces inter-phase interference, thereby stabilizing tail latency and improving request goodput ( Zhong et al., 2024 ; Chen, Michelle and Flansburg, Kevin and Krasnov, Vlad, 2026 ; Qin et al., 2025 ) . It also enables flexible scaling of prefill and decode instances and phase-specific resource allocation, making it attractive for production LLM serving ( Patel et al., 2025 ; Qin et al., 2025 ) .
As a result, many LLM serving software stacks actively support phase disaggregation ( Kwon et al., 2023 ; Zheng et al., 2024 ; NVIDIA, 2026c ; NVIDIA, 2026i ; llm-d, 2026 ; AWS, 2026 ) , which has also been widely adopted in real-world LLM serving platforms ( Qin et al., 2025 ; Chen, Michelle and Flansburg, Kevin and Krasnov, Vlad, 2026 ; Together AI, 2026 ; llm-d, 2026 ) .
Leveraging this approach, we explore a heterogeneous LLM serving system that maps prefill to GPUs and decode to NPUs according to their computational characteristics. GPUs provide high performance and efficiency during prefill, while NPUs offer comparable decode performance with higher efficiency, enabling the system to achieve both high performance and efficiency.
3.4. Challenges: Handling Heterogeneity
Despite the potential benefits of a heterogeneous GPU–NPU system, several challenges hinder its practical deployment.
The first challenge is cross-device data transfer, particularly for KV caches. In a GPU-only system, GPUs support RDMA-based transfers ( NVIDIA, 2026d ) through optimized communication software ( NVIDIA, 2026g ; Qin et al., 2025 ) , allowing the network interface card (NIC) to directly access GPU memory, as shown in Figure 3 (④).
However, in a heterogeneous system, GPUs and NPUs rely on distinct software stacks and communication mechanisms ( Intel, 2025 ; Amazon Web Services, 2026b ; The JAX Authors, 2024 ; Tenstorrent, 2026c ) , which may not directly interoperate.
A straightforward solution is to use the host as a staging point, which avoids the need for direct interoperability (⑤). However, this approach incurs substantial latency from additional copies between the host and each device, as well as host intervention.
We observed that, even between GPUs, host-staged transfer incurs 1.83 × \times to 5.25 × \times the latency of direct transfer as the transfer size increases from 10 MB to 1.2 GB, adding substantial overhead to LLM serving.

The second challenge is handling differences in KV cache tensor layouts across devices. A tensor layout defines the ordering and shape of tensor dimensions, as well as how tensor elements are mapped to the virtual address space and distributed across physical memory channels. Different accelerators employ device-specific tensor layouts to optimize data movement and computation, and these differences can be particularly pronounced between GPUs and NPUs ( Tenstorrent, 2026f ; Google, 2025 ; Huawei Cloud, 2026 ; Qualcomm, 2026 ) (e.g., row- or column-major layouts on GPUs versus tiled layouts on NPUs), as illustrated in Figure 4 .
Consequently, GPU-to-NPU tensor transfers require additional layout transformation to match the target NPU layout, introducing extra latency.
One way to avoid this overhead is to force one device to adopt the tensor layout of the other. However, because each tensor layout is optimized for its device, enforcing a unified layout can reduce memory access efficiency and requires modifications to existing compute kernels, potentially degrading their performance ( Prabhu et al., 2025 ; Li, 2026 ) .

4. Heterogeneity-Aware KV Cache Transfer
Our goal is to enable an efficient GPU–NPU heterogeneous LLM inference system. To this end, we present HAWK , a heterogeneity-aware KV cache transfer mechanism that enables direct, high-performance tensor transfer between GPUs and NPUs.
Figure 5 illustrates an overview of a heterogeneous system with HAWK.
HAWK builds on the Linux RDMA stack and establishes a common RDMA path for GPU and NPU memory by integrating device-specific RDMA memory support (❶), enabling the NIC on each node to directly access device memory without host intervention.
Once the GPU prefill instance generates the KV cache, HAWK transforms the GPU KV tensors into transfer-friendly aligned tensors (❷). The transformation partially aligns tensor elements with the target NPU layout while maximizing the size of each RDMA transfer.
HAWK then transfers the transformed tensors from a conventional GPU RDMA buffer into multiple layout-aware RDMA buffers on the NPU, which are organized according to the target tensor layout (❸).
This organization allows the partially aligned tensors to naturally conform to the target NPU layout during transfer, enabling the received tensors to be consumed directly during decode without additional layout transformation (❹).
4.1. Building a Direct Data Path Across Devices
The essential step toward efficient data transfer is to establish a high-performance transfer path between computing devices.
To this end, HAWK connects GPU and NPU device memory through a common Linux RDMA stack spanning kernel space (e.g., ib_core ( kernel development community, ) ) and user space (e.g., libibverbs ( IBM, 2025 ) ), as shown in Figure 6 .
On the GPU side, HAWK leverages the GPU peer memory client ( NVIDIA, 2026d ; NVIDIA, 2022 ) (①), whereas on the NPU side, it extends the NPU driver with a corresponding peer memory client (②).
Table 5 summarizes the implementation of the NPU-side RDMA stack.
These clients expose device memory to the RDMA subsystem by providing the memory-mapping information required for memory registration, enabling the NIC to directly access the registered memory.
Building on this kernel-level support and a common RDMA stack, various transfer engines ( Qin et al., 2025 ; Mao et al., 2025 ; Zhou et al., 2026 ) abstract low-level RDMA primitives and orchestrate runtime data movement (③). Together, these components establish a high-performance, flexible data transfer path across heterogeneous devices.

4.2. Tensor-Layout-Aware Buffer Allocation
RDMA buffers are memory regions used to store data for RDMA operations.
In conventional RDMA use cases, allocating a single large virtually contiguous buffer is practical because it simplifies buffer metadata management and RDMA request construction compared with using multiple scattered buffers.
However, this design can be less efficient for NPUs, especially when transferring tensors.
For GPUs, tensors are distributed across multiple DRAM channels at a fixed granularity (e.g., 256 B) to increase memory-level parallelism ( Park et al., 2025 ; Liu et al., 2018 ) while remaining mapped to virtually contiguous address ranges, making a single RDMA buffer well suited to the GPU memory organization.
NPUs also distribute tensors across multiple DRAM channels, but explicitly control which tensor chunks are placed in each partition rather than relying on a fixed-size mapping, improving memory locality and reducing traffic between off-chip memory and on-chip SRAM.
Therefore, an NPU tensor has a distinct memory layout and address mapping compared with a conventional virtually contiguous buffer.

These discrepancies in address mapping and memory organization between GPUs and NPUs introduce two major issues.
The first issue is that, even if a GPU tensor is transformed to match the target NPU tensor layout in dimensions and element ordering, transferring it through a conventional RDMA buffer may still require additional post-transfer adjustment before it can be used as an NPU tensor object (\raisebox{-0.0pt}{\small{c}}⃝).
The second issue is that using a conventional virtually contiguous RDMA buffer on an NPU can cause severe memory fragmentation. Because the buffer layout does not follow the NPU tensor layout, memory usage can become imbalanced across DRAM channels, leaving some channels exhausted while capacity remains available in others. This imbalance can prevent subsequent tensor allocations (\raisebox{-0.0pt}{\small{d}}⃝). Even if new tensors are allocated only from partitions with sufficient remaining capacity, such selective allocation can disrupt the intended data placement and reduce data-movement efficiency, ultimately degrading performance.
To address this issue, HAWK allocates NPU RDMA buffers according to the target NPU tensor layout, using one virtually contiguous buffer per DRAM channel with corresponding software support, as shown in Table 6 . This layout-aware allocation allows transferred data to be consumed directly from the RDMA buffers or converted into the target tensor with only limited intra-channel data movement, avoiding costly data rearrangement across multiple DRAM channels.
Although using multiple virtually non-contiguous buffers can increase buffer-management overhead and the number of RDMA requests required to transfer a tensor, the number of buffers is bounded by the number of DRAM channels in the NPU. This count is typically around ten or fewer, and each per-channel buffer remains contiguous. As a result, the additional buffer-management and RDMA-request overhead remains modest relative to a conventional single-buffer design.

4.4. Putting It All Together
Algorithm 1 summarizes the end-to-end flow of KV cache transfer between GPU prefill and NPU decode instances, omitting the first-token transfer (a single integer) for simplicity.
First, the decode instance requests the KV cache associated with a request ID from the prefill instance (line D1). The prefill instance then retrieves the corresponding KV cache, applies the transfer-aware transformation, reserves the required space in the GPU RDMA buffer, copy the tensor to the reserved region, and sends the associated metadata, including the total size and buffer offset, to the decode instance (lines P1–P7). Using this metadata, the decode instance constructs RDMA requests by pairing regions of the GPU RDMA buffer with the corresponding per-channel NPU RDMA buffers (lines D2–D5). These requests are submitted as a batch to avoid sequential RDMA request submission. After the transfer completes, the decode instance reconstructs the NPU KV cache tensor from the received RDMA buffers (lines D6–D7). Finally, both instances release the reserved regions in their RDMA buffers (lines D8–D9 and P8–P9).
4.5. Discussion
4.5.1. Extensibility Across NPU Architectures
Diverse NPUs employ device-specific tensor layouts to optimize memory placement, data movement, and compute efficiency, and these layouts often differ from GPU tensor layouts ( Tenstorrent, 2026f ; Google, 2025 ; Huawei Cloud, 2026 ; Qualcomm, 2026 ) . Such layout differences can arise even when the same framework-level tensor is placed on different devices.
For example, TensorFlow tensors placed on Google TPUs ( Abadi et al., 2016 ; Jouppi et al., 2017 ; Jouppi et al., 2023 ) use layouts that differ from those used on GPUs ( Google, 2025 ; Google, 2026 ) , including differences in tiling, padding, and element ordering. These differences highlight the need for heterogeneity-aware data transfer across devices. In this context, HAWK provides a generalizable design for such transfers.
Our prototype implementation is configured for an optimized tiled tensor layout ( Tenstorrent, 2026f ) , many other NPUs similarly employ tiled or blocked tensor layouts ( Google, 2025 ; Huawei Cloud, 2026 ) , allowing HAWK’s core mechanisms to be adapted to these architectures. Even when tensor-layout details differ, HAWK can be adapted through device-specific changes to tensor-aware RDMA buffer allocation to accommodate the target NPU layout.
4.5.2. Adaptability to Other Forms of Disaggregation
Most data objects in LLM inference, including model weights, KV caches, and intermediate activations, are represented as tensors.
Since HAWK fundamentally targets efficient tensor transfer across heterogeneous devices, it can be adapted to other heterogeneous disaggregation schemes that require transferring tensor objects between devices.
For example, in operator-level disaggregation ( Heo et al., 2024 ; Zhu et al., 2025 ) , attention computation can be performed on GPUs while subsequent operators are executed on NPUs.
In such a configuration, intermediate activation tensors must be transferred between the two devices.
Compared with KV caches, intermediate activations are typically smaller, making fixed transformation and layout-adjustment overheads more significant relative to the transfer time. Moreover, their transfer lies between dependent operators, limiting opportunities for latency hiding through overlap.
In this context, HAWK can provide substantial benefits for such tensor transfers.
4.5.3. Reverse Transfer
While HAWK targets data transfer from GPUs to NPUs, the same approach can be extended to NPU-to-GPU transfers, which can be useful when an NPU offers higher prefill efficiency than a GPU.
In such cases, the transfer-aware transformation can be performed on the NPU, partially aligning the tensor with the target GPU layout while arranging portions destined for contiguous regions of the GPU buffer contiguously within each per-channel NPU buffer.
Each contiguous portion in the per-channel NPU RDMA buffers can then be mapped to the corresponding region of a virtually contiguous GPU RDMA buffer, completing the remaining layout alignment during transfer.
This preserves the benefit of fewer, larger RDMA transfers while allowing the transferred tensor to be used directly for GPU decoding without additional post-transfer layout transformations.
5. Evaluation
5.1. Methodology
5.1.1. Hardware Configuration
The system consists of a single prefill instance and a single decode instance: the prefill instance runs on NVIDIA A100 PCIe GPUs ( NVIDIA, 2020a ) , interconnected within each node via NVLink Gen 3 and PCIe Gen 4, while the decode instance runs on Tenstorrent p150a boards ( Tenstorrent, 2025 ) , interconnected via Ethernet-based links.
We use Tenstorrent NPUs because, to the best of our knowledge, they are the only NPU platform that provides an open-source software stack permitting the low-level modifications required by HAWK.
The prefill and decode instances run on separate nodes connected via 200 Gbps HDR InfiniBand, with each node equipped with a ConnectX-6 NIC ( NVIDIA, 2020b ) .
5.1.2. Software Configuration
We use vLLM v0.10.0 ( Kwon et al., 2023 ) as the serving framework to demonstrate that our system and HAWK can operate within a widely used LLM serving environment. To support NPU execution, we integrate the Tenstorrent LLM stack with vLLM through a plugin.
For GPU-side RDMA support, we use nvidia-peermem ( NVIDIA, 2026b ; NVIDIA, 2026h ) . On the NPU side, we extend the Tenstorrent software stack (user-mode driver v0.68.0 ( Tenstorrent, 2026e ; Tenstorrent, 2026b ) and kernel-mode driver v2.5.0 ( Tenstorrent, 2026a ) ) to implement the RDMA-related functionality required by HAWK, including a peer memory client and tensor-layout-aware RDMA buffer allocation.
Building on this support, we implement a user-space transfer mechanism on top of Mooncake Transfer Engine v0.3.6 ( Qin et al., 2025 ; kvcache.ai, 2026 ) , a high-performance data transfer engine for disaggregated LLM serving. Our mechanism integrates transfer-aware tensor transformation with RDMA buffer pairing.
For the model, we use Llama 3.1 70B ( Grattafiori et al., 2024 ) , whose scale requires multiple accelerators and is therefore suitable for evaluating phase-disaggregated serving. We distribute the model across four devices per instance using tensor parallelism (TP). In practice, the current Tenstorrent LLM stack tightly couples each supported model to a specific device type and device count, which limits our evaluation to this model ( Tenstorrent, 2026d ) .

5.1.3. Comparison Configurations
We compare our system against three baseline configurations.
1. GPU-GPU + Host Staging (GG-Host) uses GPUs for both prefill and decode and transfers the KV cache through host staging.
2. GPU-NPU + Host-Staging (GN-Host) uses GPUs for prefill and NPUs for decode and transfers the KV cache through host staging, followed by tensor-layout adjustment on the NPU side.
3. GPU-GPU + Direct RDMA (GG-Direct) uses GPUs for both prefill and decode and transfers the KV cache directly between GPU memories via RDMA using the Mooncake Transfer Engine. We verify that its RDMA transfer performance is comparable to that of other GPU RDMA transfer engines, such as NIXL ( NVIDIA, 2026g ) .
4. GPU-NPU + HAWK (GN-HAWK) uses GPUs for prefill and NPUs for decode and transfers the KV cache using HAWK.
One additional configuration uses GPUs for prefill and NPUs for decode, transferring the KV cache directly between device memories via RDMA while using a conventional single contiguous RDMA buffer on the NPU side. This setup incurs post-transfer adjustment overhead because the buffer does not conform to the NPU tensor layout.
We implement a prototype of this configuration, but it fails with an out-of-memory error during serving due to NPU memory fragmentation: the buffer creates imbalanced memory usage across DRAM channels, leaving insufficient capacity for subsequent tensor allocations. This failure further highlights the importance of HAWK’s tensor-layout-aware RDMA buffer allocation. We therefore exclude this configuration from the quantitative comparison.
5.1.4. Workloads
We evaluate our system using two types of workloads. First, we use a synthetic workload to evaluate KV cache transfer overhead. Second, we evaluate end-to-end LLM serving performance using workloads derived from prior work on phase-disaggregated LLM serving ( Zhong et al., 2024 ) , excluding the smallest workload due to its limited KV cache transfer volume. Each serving workload is derived from a different dataset ( anon8231489123, 2023 ; Bai et al., 2024 ) and exhibits different input/output token lengths and request sizes, resulting in different KV cache transfer characteristics.
For each workload, we vary the average request arrival rate and assume a Poisson arrival process.

5.4. Serving Efficiency
The main benefit of GPU-NPU heterogeneous integration with HAWK lies in power and cost efficiency.
We compare these efficiencies at 90% SLO attainment using output token throughput, focusing on GG-Direct and GN-HAWK as the best-performing homogeneous and heterogeneous configurations, respectively.
5.4.1. Power Efficiency
We calculate power efficiency by dividing output token throughput by the aggregate ASIC power of all prefill and decode devices, averaged over the same measurement interval.
Specifically, we use device ASIC power, including compute cores and on-chip SRAM, because the available Tenstorrent monitoring interface reports only NPU core power ( Tenstorrent, 2026g ) .
To estimate GPU ASIC power, we first collect board-level power measurements using NVIDIA DCGM ( NVIDIA, 2026f ) .
We then collect binary traces of GPU kernels executed during prefill and decoding using NVBit ( Villa et al., 2019 ) and feed them into a detailed GPU power simulator to estimate the fraction of total power attributable to the GPU ASIC for each phase ( Kandiah et al., 2021 ) .
Finally, we apply these phase-specific fractions to the corresponding board-level power measurements.
Regarding excluded power components, both configurations use the same interconnect hardware and exhibit similar transfer times, suggesting that differences in interconnect energy consumption may be limited.
We also consider memory power. Although HBM2e in the evaluated GPU offers higher bandwidth per watt than GDDR6 in the evaluated NPU, estimates accounting for their respective memory bandwidths indicate higher memory power consumption for the GPU ( Micron, 2020 ) .
As shown in Table 8 , GN-HAWK achieves 1.26 × \times and 1.15 × \times higher power efficiency than GG-Direct for Chatbot and Summarization, respectively.
These gains come from combining GPU prefill with NPU decode to improve efficiency while maintaining comparable serving performance.
HAWK makes this combination effective by reducing transfer overhead between the heterogeneous devices.
Although the magnitude of the gains may vary across NPU platforms, the results demonstrate the potential of GPU-NPU heterogeneous serving to improve power efficiency.

6. Related Work
6.1. Phase-Disaggregation
Prior work has proposed diverse optimizations for prefill-decode disaggregated serving systems, including phase-aware resource provisioning and placement ( Patel et al., 2025 ; Zhong et al., 2024 ; Hu et al., 2024b ) , heterogeneous GPU deployment ( Jiang et al., 2025b ; Chen et al., 2025b ) , cluster-level scheduling and dynamic prefill-decode ratio adaptation ( Jin et al., 2024 ; Qin et al., 2025 ; Ruan et al., 2025 ; Wu et al., 2025 ; Wang et al., 2025a ) , and KV cache management and transfer optimization ( Qin et al., 2025 ; Hu et al., 2024a ; Hong et al., 2025 ) .
These efforts primarily optimize disaggregated serving within GPU-based systems. We extend this scope to GPU-NPU phase disaggregation and demonstrate its potential for LLM serving.
6.2. Other Forms of Heterogeneous Integration
Prior work has explored LLM inference systems that combine GPUs with CPUs ( Lin et al., 2026 ; He and Zhai, 2024 ; Jiang et al., 2025a ; Kamahori et al., 2025 ) , NPUs ( Moon et al., 2025 ; Chen et al., 2025a ; Wei et al., 2025 ) , or PIM/PNM accelerators ( Park et al., 2024 ; Kim et al., 2025a ; Lee et al., 2025 ; Kim et al., 2025b ) , as well as integrated NPU-PIM systems ( Seo et al., 2024 ; Chen et al., 2025c ; Heo et al., 2024 ) .
These studies exploit hardware heterogeneity through workload partitioning, offloading, scheduling, and disaggregation to improve inference performance and efficiency. Against this backdrop, we investigate the practical challenges of coordinating GPUs and NPUs across multiple servers and develop system-level solutions to address them.
7. Conclusion
We propose a GPU–NPU phase-disaggregated LLM inference system that leverages GPUs for prefill and NPUs for decode to achieve both high performance and efficiency. Realizing such a system, however, requires an efficient data-transfer path that addresses heterogeneity between GPUs and NPUs. To this end, we present HAWK, which enables direct data transfer over a common RDMA stack while addressing tensor-layout discrepancies through tensor-layout-aware RDMA buffer allocation and transfer-aware tensor transformation.
Our evaluation shows that HAWK enables the heterogeneous system to maintain performance within 7.88% of a GPU-only system under the same SLO constraints, while achieving up to 1.26 × \times higher power efficiency and 1.72 × \times higher cost efficiency.
