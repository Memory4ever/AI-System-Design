Abstract
Customized agent deployments define policies over tools, resources, and execution conditions. Providing these policies in the task agent’s prompt does not reliably prevent violations. Training a guard requires examples of tool calls that comply with or violate those policies. We introduce AgentPolicyForge, a framework that uses executable environments to construct policy benchmarks and iteratively train policy guards. With this framework, we construct PolicyGym, a dataset across ten policy families using 698 scenarios for training data generation and 254 separate held-out scenarios for human-reviewed test sets. Tool calls are executed and their outcomes recorded to help determine whether they comply with the policy. Every violating case uses a permitted tool, requiring checks of arguments, resources, and context rather than tool identity alone. The case construction process supports iterative guard training: an attacker generates requests using retrieved strategies, and the guard is fine-tuned on balanced, environment-verified examples. Training improves policy enforcement even with a fixed archive. Updating the archive further reduces in-domain attack success compared with keeping it fixed. We compare policy-aware task agent self-regulation with a trained policy guard. On PolicyGym, the final guard-based configuration achieves a 40–44\% relative reduction in attack success rate and fewer benign rejections than policy prompting alone.
1 Introduction
Language-model agents increasingly call tools, query databases, and modify
external systems (Schick et al., 2023; Yao et al., 2023; Xi et al., 2025).
Deployments govern these actions through policies specifying which tools
and resources agents may use and under what conditions
(Wen et al., 2026a; VIOLA, 2026).
For example, a transfer tool may be permitted only for amounts below a
limit, and record access may be restricted to the record’s owner.
An allowed tool can therefore still be used in violation of policy:
compliance depends on its arguments, the resources it accesses, and
the state in which it executes.
Providing the policy directly to the task agent reduces violations,
but leaves substantial enforcement errors. In our evaluation, a
policy-prompted frontier agent still allows violating calls to execute
in 13–15\% of threat episodes and rejects around 9\% of benign requests
(§4.2).
A separate guard allows policy enforcement to be trained
and evaluated independently of the task agent, without changing the task agent’s weights.
To train and evaluate this guard, we need tool calls paired with policies,
relevant context, and compliance labels.
These examples must cover both compliant and violating calls, with labels
grounded in what the agent actually proposes. A request alone is insufficient:
the agent may propose a different action, and successful execution does not
establish policy compliance. Executable environments let us reset state,
execute concrete calls, and inspect their outcomes, linking policy judgments
to observable evidence. Training data can then be refreshed to target
remaining misses and false alarms, while held-out tests stay fixed to
measure progress.
Existing policy benchmarks and monitors provide resources for evaluating
deployment-specific compliance, including PolicyGuard (Wen et al., 2026a) and VIOLA (VIOLA, 2026).
Our focus is constructing new policy cases from executable environments:
binding rules to concrete tools and state, collecting calls and execution
evidence, and reusing this process for both fixed tests and fresh guard
training data.
We introduce AgentPolicyForge, a framework that uses executable
environments to construct policy benchmarks and iteratively train policy
guards through a shared case-construction process. A shared construction process generates requests targeting compliance
or violation, collects calls from a policy-blind task agent, and executes them to collect
evidence for determining whether the calls comply with the policy.
Environment adapters provide access to tools, state, and execution.
The framework then binds policy rules and executable checks to each scenario’s tools and state.
With this framework, we construct PolicyGym, a dataset for training and evaluating
policy guards across ten policy families. Training data generation uses 698 Agent World Model
(AWM) scenarios (Wang et al., 2026). Human-reviewed tests use 254 separate held-out
scenarios: 187 in-domain (ID) and 67 out-of-domain (OOD) within AWM.
OOD scenarios come from groups not used for training data generation, but remain within AWM.
Each example pairs a proposed tool call with policy rules, relevant context,
execution evidence, and a compliance label.
Every violating test case uses a permitted tool but breaches an argument, resource, or context
condition, which shows that identifying forbidden tools alone is insufficient.
We use PolicyGym’s training seeds and the construction process to generate
fresh examples for iterative guard training. Each round,
an attacker retrieves archived strategies to generate fresh requests.
We fine-tune the policy guard using supervised fine-tuning (SFT) on a
balanced set of verifier-confirmed violations and compliant calls,
including violations it missed and compliant calls it incorrectly blocked.
Training with a fixed archive already reduces ASR on both evaluation splits.
We also update the archive with candidate strategies derived from
attack outcomes. Candidates are validated on training scenarios
before entering the archive.
This archive-mediated coevolution links guard updates through SFT
to strategy updates that guide subsequent requests.
After ten rounds of coevolutionary training, the guard achieves attack success
rates (ASR) of 8.22\% in-domain and 7.89\% out-of-domain when filtering fixed
task-agent proposals. Compared with policy-aware task-agent self-regulation,
this configuration achieves a 40–44\% relative reduction in ASR and rejects
fewer benign requests. We compare fixed and evolving archives after ten matched training rounds. Updating the archive lowers in-domain ASR by 24.1\% but increases benign over-block by 0.75 percentage points.

2.1 Problem Setting
We study a policy guard that checks a task agent’s proposed tool call using only
information available before execution. Given a user request q, the task agent proposes
c=(\text{tool},\text{args}). The guard decides whether to allow it using the request,
proposed call, policy \Pi, visible pre-action state s, and relevant tool schema
\Sigma. We denote these inputs by z=(q,c,\Pi,s,\Sigma).
The attacker controls the request and seeks to induce a violating call that the guard
allows, but cannot modify the policy, tool schema, or visible state supplied to the guard.
Execution outcomes support labeling during data construction but are not included
in the guard’s inputs.
A policy \Pi specifies permitted tools \mathcal{T}^{\mathrm{ok}}, permitted resources
\mathcal{R}^{\mathrm{ok}}, and conditions \mathcal{C} over call arguments and environment
state. A condition is violated only when it applies to the call and is not satisfied;
we therefore define each \phi\in\mathcal{C} to return true outside its applicability scope.
Let \text{res}(c) denote the resources accessed by the call. A proposal violates the
policy if any of the following holds:
\displaystyle V_{0}
\displaystyle:\;\text{tool}\notin\mathcal{T}^{\text{ok}},
\displaystyle V_{1}
\displaystyle:\;\exists\,\phi\in\mathcal{C}:\neg\phi(\text{args},s),
\displaystyle V_{2}
\displaystyle:\;\text{res}(c)\not\subseteq\mathcal{R}^{\mathrm{ok}}.
(1)
Here, V_{0} denotes a forbidden tool, V_{1} an unsatisfied applicable condition, and V_{2}
an unauthorized resource. Although the general formulation includes V_{0}, PolicyGym
focuses on V_{1} and V_{2} through a permitted-tool invariant: every violating
test case uses a permitted tool. This prevents tool identity alone from revealing violations
and requires checking policy conditions on arguments, resources, or state.
For example, a transfer tool may be allowed even though the proposed amount exceeds the policy limit.
The guard outputs an intervention level: 0 (Pass), 1 (Monitor), 2 (Verify), 3 (Modify), or
4 (Block).
These levels provide more detailed feedback than a simple allow/block decision, distinguishing flagging a potential problem from blocking an action. In our evaluation,
only Level 4 prevents execution. Levels 2 - 4 count toward intervention recall and FPR, measuring how often the guard flags violating and compliant calls, respectively.
2.2 From Executable Environments to Policy Cases
Figure 1 (left) shows how executable environments support
policy binding, seed generation, and the construction of labeled calls.
Environment and policy binding.
To construct a policy from a template, we select a tool, identify the relevant
arguments or resources, and fill in the rule’s conditions. For example,
“Each [operation] must not exceed [limit]” becomes “Each transfer must not
exceed $500” by selecting a transfer tool, its amount argument, and a $500
limit. The template includes an executable check that compares the proposed
amount with this limit.
Deployment policies can also be supplied directly by users. For PolicyGym,
we use reusable templates covering ten policy families (§3).
An environment adapter connects the construction process to each environment.
It provides tool definitions and argument types, identifies resources, and
supports inspecting state, restoring the initial state, and executing calls.
A template can be applied only when the environment provides the fields and
state needed to check its rule.
Seed and request generation.
Each seed is a structured input for request generation. It contains
the scenario’s policy clauses, a target operation, and key argument values.
A violating seed specifies an intended call that breaks one selected policy rule.
A compliant seed specifies an intended call that satisfies all policy rules
that apply to it.
The attacker converts each seed into a natural-language request. The seed describes the intended action, but we label the call the agent actually proposes. The attacker converts each seed into a natural-language request. Training seeds generate requests for training data, and held-out seeds generate requests for test cases.
Task-agent proposals and execution.
The task agent receives the attacker’s request and tool schemas, then proposes a call. The task agent does not receive the policy. We execute each call from the environment’s initial state after checking that its arguments are valid and it matches the request, then record the result. We keep successfully executed calls and label them as compliant or violating. Execution success does not mean the call follows the policy.
Labeling and human review.
We consider two sources of compliance labels: (1) An LLM judge interprets the policy
and execution evidence to provide a judgment, the applicable clause, and supporting
evidence. (2) An executable rule checker, called the verifier, evaluates the
encoded policy conditions. These checks are possible because the policy
templates specify the rules, and the environment provides tool schemas,
actual call arguments, and recorded state.
We train the guard using LLM labels and compare this with training
using verifier labels (§4.3). In both experiments, we keep only cases that the verifier can label as compliant or violating.
Test cases receive both an LLM label and a verifier judgment. We retain only cases with a definite verifier judgment and a human-approved LLM label.
Why train a guard when executable checks are available?
During data construction, we use policy checks and execution records
to help label calls. At deployment, policies may be written in natural
language without matching check code. A verifier can enforce these
rules only after they are encoded and the required information is
available before execution. We train a guard to judge proposed calls from policy text and pre-action context, without verifier judgments or execution results. Complete executable checks can still be used directly when available.
2.3 Iterative Guard Training and Archive Updates
In Figure 1 (right), each round generates training examples, updates the guard’s parameters through SFT, and validates new attack strategies. Strategies that pass validation are saved in the attacker archive for later rounds.
To collect examples, the attacker generates requests using archived strategies.
The task agent proposes calls, and the current guard judges them. We execute
valid calls in the sandbox even if the guard would block them, so we can
check their outcomes. We discard calls that fail, do not match the request,
or cannot be judged by the verifier.

violation. Here the LLM judge uses the policies, calls, and execution evidence to provide SFT labels, but the guard receives only pre-execution information. Algorithm 1 summarizes the training procedure.

3 PolicyGym: Benchmark Construction
3.1 AWM Environments and Policy Instantiation
We build PolicyGym on Agent World Model (AWM) (Wang et al., 2026), which provides
1{,}000 resettable scenarios with SQLite data and typed FastAPI/MCP tools.
We define rule templates for ten policy families: time windows, backdating,
amount limits, own-record access, restricted tables, protected identifiers,
data residency, field masking, protected flags, and dual approval.
We fill these templates using each scenario’s tools, arguments, resources,
and state to create concrete policies (§2.2).
Appendix Table 5 explains each family and its required evidence.
Every violating test case uses a permitted tool. Its violation can be determined
from one call’s arguments, resources, or state (V_{1} or V_{2}), although the
same episode may contain other calls.
3.2 Training Seeds and Labeled Examples
The source pool contains 6,603 seed–policy pairs from 698 AWM scenarios.
We check whether each seed supports a valid call that satisfies or violates
the specified policy. This leaves 5,655 seeds: 2,863 targeting violations and
2,792 targeting compliance. These seeds guide request generation. They are
not labeled tool-call examples.
3.3 Held-Out Test Construction and Evaluation
We construct the test sets from scenarios excluded from the source pool using the same steps in §2.2.
ID scenarios belong to naming groups represented in that pool, and OOD
scenarios belong to groups absent from it. Both splits remain within AWM
and use the same policy families and construction process.
Using held-out seeds, we generate requests and collect task-agent calls
through the process in §2.2. Test cases must have a
definite verifier judgment and a human-approved LLM label. Cases that fail
review are discarded. After filtering and class balancing, the ID test
contains 1,070 episodes from 187 scenarios, and the OOD test contains
304 episodes from 67 scenarios (Table 1). Each split
has equal numbers of compliant and violating episodes, and the two splits
share no scenarios. A blind review of 100 test episodes finds 98% agreement
with reference labels (\kappa=0.96). This measures agreement on the reviewed
sample, not full-test accuracy (Appendix A.8).

4 Experiments
We first evaluate policy enforcement, then test whether generated cases
improve the guard through iterative training, and finally assess the
additional benefit of updating the strategy archive.
4.1 Experimental Setup
Models and baselines.
Qwen3-14B (Yang et al., 2025) is the guard’s base model. Claude Sonnet 4.6 and Claude Sonnet 5 serve as the
frozen attacker and task agent, respectively. Baselines include policy-aware
task-agent self-regulation, PolicyGuard-4B (Wen et al., 2026a), GPT-6-luna, Claude Haiku 4.5, the Clef-Flash
decision model (Cloudflare, 2026), Phi-4 (Abdin et al., 2024), and three
prompting variants of untrained Qwen3-14B (Table 2).
All external guards judge the same frozen, human-reviewed proposals. The policy-aware
task agent can revise its actions. The trained guard uses the fused prompt
(Appendix E).
Training conditions.
R0 is the guard before any SFT in our framework, and R10 follows ten rounds
of generation and SFT. The fixed-archive and evolving-archive runs start
from the same guard and archive. They use the same seed-sampling schedule,
generation budget, labeler, and optimizer. Both use new examples, guard
feedback, and saved examples. Only the evolving run adds new strategies.
Appendix A.9 details data collection and optimization.
Metrics.
ASR (\downarrow) is the percentage of threat episodes in which
at least one violating call executes before any block. A later block does
not undo a successful attack. Over-block (\downarrow) is the
percentage of benign episodes with at least one blocked call. Both metrics
score whole episodes. In the main evaluation, only Level 4 blocks execution.
Intervention recall is the percentage of violating calls flagged
by the guard. Intervention FPR is the percentage of compliant calls
incorrectly flagged. These metrics score individual calls and count
Levels 2–4 as flags, even when execution is not blocked. For binary guards,
a Block decision counts as both a flag and a block. Appendix B
also reports results when every Level 2–4 response blocks execution.
We also report accuracy, violation-class F1 (the harmonic mean of precision
and recall), and Youden’s J, which is violation recall minus FPR.

4.2 Is Policy Prompting Sufficient?
Providing the policy sharply reduces violations, but leaves substantial enforcement errors.
Without the policy, the task agent executes violating calls in over 98\% of threat episodes.
With the policy, its ID/OOD ASR remains 14.77\%/13.16\%, and it rejects
8.79\%/9.21\% of benign requests (Table 2).
Frozen external guards still leave enforcement errors.
We evaluate GPT-6-luna, Haiku 4.5, and the Clef-Flash decision model
as frozen external policy guards on the same tool proposals.
Their ASR ranges from 10.47\% to 16.64\% across the two splits,
showing that neither general-purpose models nor the decision model
fully enforce the policies. Other baselines show different
safety–utility trade-offs: PolicyGuard-4B blocks few benign requests
but misses more violations, whereas Phi-4 blocks many compliant
requests without achieving the lowest ASR.
Prompt design helps but does not eliminate enforcement errors.
We compare single-shot, decomposed, and fused prompts for untrained Qwen3-14B.
Both decomposed and fused prompts reduce ASR and benign rejection relative to
single-shot prompting. We select fused for training because it has the lowest
benign rejection and highest intervention recall among these prompts.
However, it still misses violations and has higher in-domain ASR than decomposed
prompting: flagging a call for verification does not ensure it is blocked.
The trained guard improves enforcement.
Compared with policy-aware task-agent self-regulation, R10 reduces ID/OOD ASR
by 44.3\%/40.0\% to 8.22\%/7.89\%. It also rejects fewer benign
requests, with rates of 7.48\%/5.92\%. This compares two enforcement
configurations: the guard filters fixed proposals, whereas the policy-aware
agent can revise its actions. Passing a benign call does not necessarily
mean that the task is completed.
Among the guards in Table 2, R10 has the lowest ASR at
the reported decision rules. It improves both ASR and benign rejection over
single-shot and decomposed Qwen3-14B. Compared with Haiku 4.5, R10 improves
both rates out-of-domain. In-domain, it lowers ASR by 2.25 percentage
points but increases over-block by the same amount.

4.3 Does Training on Generated Cases Improve Enforcement?
Figure 2 shows that training lowers ASR
for both Qwen3-8B and Qwen3-14B, but increases benign over-block.
All checkpoints judge the same tool calls.
After ten rounds, Qwen3-14B reaches 8.22\% ASR in-domain and
7.89\% out-of-domain. Over-block rises to 7.48\% and 5.92\%,
increases of 3.93 and 3.95 percentage points from the untrained guard.
For both models on both splits, the ASR reduction exceeds the increase
in over-block. The figure’s net gain is therefore positive at Round 10
when these two changes receive equal weight.
Can a stricter blocking rule replace training?
R0 often flags violations with Verify rather than Block.
We therefore also score both checkpoints with Level \geq 2 treated
as Block. R10 still achieves lower ASR and over-block than R0 on both
splits, showing that lowering the blocking threshold alone does not
recover the trained guard’s performance
(Appendix B).
Training also works with verifier-derived labels.
We test whether generated cases can improve the guard when training labels come
from the executable verifier instead of the LLM judge. After ten rounds,
verifier supervision reaches 11.40\%/11.18\% ID/OOD ASR and
6.54\%/2.63\% over-block. Both supervision sources reduce ASR relative to R0.
Compared with LLM supervision, verifier supervision misses more violations but
blocks fewer compliant calls. The runs share initialization, source schedule,
and optimization settings, but each generates its own training examples.
The comparison therefore measures the resulting training procedures, rather than
isolating label quality on identical data (Appendix D).

5 Related Work
Policy-compliance benchmarks.
PolicyGuardBench pairs web trajectories and their prefixes with policies to train
and evaluate the PolicyGuard detector (Wen et al., 2026a). VIOLA
(VIOLA, 2026) evaluates policy compliance in multi-agent execution traces.
PolicyGym complements these trajectory benchmarks with concrete tool calls
constructed in executable environments, accompanied by deployment policies,
execution evidence, and human-reviewed test labels. Every violating test case
uses a permitted tool, requiring checks of arguments, resources, and context
rather than tool identity alone.
Execution-based guard training.
BraveGuard (Feng et al., 2026a) and HazardAuditor
(Feng et al., 2026b) turn safety threats into executable
computer-use tasks and collect agent trajectories to train guards.
AgentPolicyForge constructs compliant and violating tool calls from
deployment policies, using execution evidence and rule checks to support
labeling for evaluation and iterative guard training.
Adversarial and coevolutionary training.
Related methods use self-play (Liu et al., 2026),
train attack and defense agents (Zheng et al., 2024; Wen et al., 2026b),
update attack and detection prompts (Liu et al., 2025),
or jointly train conversation and feedback agents
(Zhang et al., 2025).
SafeCoEvo co-evolves a safety harness and guard through runtime experience
(Cheng et al., 2026). Rainbow Teaming maintains a MAP-Elites archive
of adversarial prompts (Samvelyan et al., 2024; Mouret and Clune, 2015).
These methods study safety and alignment through adversarial feedback.
AgentPolicyForge focuses on compliance with explicit deployment policies,
including restrictions on otherwise permitted tool calls. It keeps
attacker weights frozen, validates strategy updates on training scenarios,
and trains the guard through SFT on execution-grounded cases.
6 Conclusion
AgentPolicyForge builds policy benchmarks and trains guards using executable
environments. PolicyGym provides training data and human-reviewed tests.
Generated data improve enforcement, with archive updates adding an in-domain
gain at Level 4 in the matched run.
Future work will evaluate guard adaptation to new policy types and deployment changes.
Limitations
PolicyGym studies synthetic policies whose violations can be determined from one
tool call. Both test splits share AWM and policy templates, so they do not establish
generalization to new policy types or deployments. The Qwen-AgentWorld pilot
reuses interfaces with simulated responses, but high benign rejection limits
direct guard transfer. We do not compare learned guards with complete executable
rule checks.
Results use one generation seed and two Qwen3 backbones, without measuring
variation across training runs. The attacker, task agent, and judge use proprietary
Claude models and may share biases in generated calls and labels. The follow-up
human review covers 100 test episodes, not independent double annotation of the
full test sets. Training-label accuracy remains unmeasured.
Evaluation uses fixed attacks and does not compare systems at equal benign
rejection. Baselines also differ in model size. These comparisons therefore do
not isolate all effects of training, model size, and blocking rules. External
adapters used evaluation feedback, and VIOLA has few benign trajectories.
We measure blocking decisions, not task completion, the outcomes of verification
or modification, or deployment cost.
Ethical considerations
This work studies defensive policy guards in synthetic, resettable environments. It uses no real
user data or production systems; all generated policy violations are simulated and confined to
these environments.

A.2 Source Records and Fixed Environment Context
We start with 6,603 seed–policy pairs from 698 resettable AWM scenarios.
Each adapter provides the tool operations, argument types, affected tables, and
initial database state. We fix the reference time, initial state, verifier, and
environment version for data collection and evaluation.
A.3 Validating Attacker Seeds
We first check that each policy can be applied to the scenario’s tools and that
the required arguments and resources are available. A threat seed must support at
least one permitted tool call that violates the policy. A benign seed must support
a compliant call with valid arguments. Of the 6,603 source rows, 5,655 pass these
checks: 2,863 threat seeds and 2,792 benign seeds. These seeds are used to generate
requests and are not yet labeled tool-call examples.
A.4 From a Seed to an Executed Trajectory
For each seed, we restore the database to its initial state and load the policy,
tool schemas, and fixed reference time. Sonnet 4.6 generates a request. The task
agent receives the request without the policy and proposes a call. We retain calls
that use a permitted tool, have valid arguments, match the request, execute
successfully, and have an applicable policy clause. Each record stores the
pre-action inputs, execution results, verifier judgment, and LLM target.
The released supervision pool can include cases with an Unknown verifier
judgment. Test cases require a determinate judgment and human review.
The attacker receives the policy, tool schemas, task context, target operation,
and argument values. When enabled, it also receives retrieved strategies and
instructions on how to phrase the request. It must preserve the target action
without inventing tools or state, and return only a request inside
<query> tags. Only this request goes to the task agent.
During adaptive collection, benign requests are used unchanged.
The supplementary material includes the condensed prompt template.
The guard receives the fixed reference time and information from the adapter
about tool permissions and operation types. Additional state signals summarize
earlier calls, rather than the full database. This field is empty in query-only
adaptive collection. Execution results are used for offline labeling and are
not given to the guard.

A.7 Held-Out Test Set Construction
We group scenarios by removing the final numeric suffix from their names.
The 698 source scenarios form 298 groups. The ID test contains 187 other scenarios

from 62 groups absent from both the source pool and the final training split.
The two test sets share no scenarios. Of the 81 ID groups, 80 appear in the final
training split and one appears only in calibration. Grouping by name does not
guarantee that groups represent semantically different application domains.
We begin with 1,620 ID and 540 OOD candidate episodes. Strict verifier checks

and class balancing, the test sets contain 1,070 ID episodes (535 per label) and

context, tool calls, and call order. The sets contain 3,521 ID calls and 955 OOD calls.

A.9 Round-Specific Training Data
R0 is the guard before any SFT in our framework. Each round samples 100 threat
and 100 benign seeds. Each threat seed generates four request versions: direct,
longer semantic context, schema-dense, and natural operational. Each benign seed
supplies one request. This gives 500 attempted trajectories, collected in four
shards that share no scenarios. The same schema, execution, and verifier checks
apply throughout.
The previous guard scores each valid proposal. The violating examples include
current attacks that bypassed the guard, attacks it blocked, historical attacks,
and simple training attacks. Compliant examples include current controls,
historical examples, and calls the current guard incorrectly blocked.
Historical replay reuses saved SFT examples, including cases collected before
Round 1. It does not execute tools again or retrieve attack strategies.
Each round targets 320 records, split equally by verifier label. When available,
24–32 incorrectly blocked compliant calls make up 15–20% of the target compliant
half. We do not fill a shortfall in these hard benign cases with ordinary benign
examples, invalid executions, or cases with unknown labels. When at least four
policy families are available, each family contributes at most 25% of its class.
After label-specific filtering, the evolving run retains 164, 170, 154, 138, 150,
130, 148, 154, 148, and 148 records in successive rounds.
Optimization.
Each round runs ten optimizer steps with learning rate 5\times 10^{-7} and global
batch size 32. We repeat the accepted examples as needed to complete these steps,
for 100 steps overall. Across rounds, the evolving archive uses 1,504 accepted
records and the fixed archive uses 1,590. These totals count records before
optimizer reuse. They are not unique-example counts, because replay can include
the same example in multiple rounds.
The two conditions use the same generation budgets, source schedules, and number
of optimizer steps. Filtering can leave different numbers of accepted examples.
We use one stochastic generation schedule. Evaluation uses fixed proposals and
temperature zero, although separate inference runs can still produce different outputs.
A.10 Attack-Strategy Promotion
The frozen attacker builds the initial archive S_{0} by summarizing earlier
verifier-confirmed violations into 18 strategies. Each strategy describes how the
attack works, when to use it, and which assumptions to avoid. We keep these
summaries concise and remove unsupported assumptions. Later rounds produce new
candidate strategies from successful and failed attacks.
We test candidates in additional rollouts on training scenarios. These scenarios
may also be used for request generation, but never come from the test sets.
We reject candidates that rely on nonexistent tools, invented state or authorization,
the wrong policy family, or actions that do not violate the target rule.
To evaluate the remaining candidates, we compare the prior archive with an archive
that includes them, using the same validation inputs.
All candidates must be retrieved in at least two training scenarios. Adding them
must not reduce the number of executed calls confirmed as violations by the verifier.
The validation runs must also have no disqualifying flags for unsupported authority,
fabricated context, or mismatched targets. Candidates then face one of two checks:
•
Production strategies must produce at least one new bypass: a case
that bypasses the guard with the candidate but not with the prior archive.
The number of new bypasses must exceed the number of prior bypasses lost.
•
Exploration strategies must produce at least one bypass and keep the
total bypass count at or above the prior archive’s count. They do not need to
produce a new bypass.
The exploration check therefore requires the bypass count to stay the same or
increase, rather than requiring every metric to improve. Strategies with the same
meaning are merged. The fixed-S_{0} control uses the same data collection and guard
training procedure but does not update the archive.
The archive grows from 18 to 25 strategies across nine policy families.
Four production additions produce six new bypasses in the paired validation runs,
and three exploration additions pass their admission check
(Table 9).

Appendix E Additional Baselines and a Smaller-Backbone Replication
E.1 Frozen Guards and Task-Agent Baselines
Prompts and parsing.
The single-shot prompt asks Qwen3-14B for a verdict. The decomposed prompt first
asks for the policy clause and evidence, then uses a second model call for the
decision. The fused prompt returns the clause, evidence, intervention level, and
reason in one response. We use the fused prompt because it has low over-block
and high intervention recall, although the decomposed prompt has lower ID ASR.
The prompts do not guarantee valid output syntax. If a response cannot be parsed,
the evaluator allows the call. Haiku produces one malformed response on each split.
For GPT-6-luna, empty responses are retried with a larger token budget, after which
all responses can be parsed.
Comparison scope.
The models in Table 2 differ in size and decision rules.
The policy-aware task agent can change its proposed actions, whereas external
guards judge fixed calls. Allowing a benign call does not establish that the task
is completed. R10 has the lowest ASR, but other methods have lower benign rejection
or intervention FPR. The test violations are fixed and were not adapted to each
checkpoint.

Scenario concentration and uncertainty.
We draw 20,000 bootstrap samples of scenarios with replacement, separately for
threat and benign episodes. Each sampled scenario contributes all its episodes.
If a scenario is drawn more than once, its episodes are counted that many times.
We use the same draws for both checkpoints, compute differences in episode-level
error rates, and obtain percentile intervals from those differences.
The threat groups contain 171 ID and 50 OOD scenarios, and the benign groups
contain 178 and 59, respectively.
ID threat errors decrease in 14 scenarios and increase in one. No scenario accounts
for more than two net corrections. Removing any one scenario leaves the ID ASR
difference between -2.82 and -2.26 points. The OOD interval reaches zero.
These intervals describe the two checkpoints from one paired training run and do
not measure variation across training seeds.
Decision transitions.
All 17 corrected threat episodes are stopped at a verifier-confirmed violating
call. Of the 15 ID corrections, 13 change from Level 2 to Level 4 and two change
from Level 0 to Level 4. Both OOD corrections change from Level 2 to Level 4.
Most corrections therefore block violations that the fixed-archive guard had
already flagged. The OOD benign-error totals are equal, but the decisions differ:
evolving training corrects two false alarms and introduces two others
(Table 15).
Exploratory policy-family breakdown.
The net reduction in ID misses is eight for protected identifiers, three for time
windows, two for own-record access, and one for data residency. Other families are
unchanged. Both corrected OOD misses involve protected identifiers.
A case can have several applicable clauses, so its assigned primary family does
not show which clause caused the decision to change.
The promoted production strategies concern time windows and own-record access.
We therefore cannot link each corrected test error to a particular new strategy
from these results alone. Doing so would require training comparisons that change
individual strategies.

Appendix H External Benchmark Protocols and Diagnostics
H.1 VIOLA Data Processing and Evaluation
VIOLA assigns labels to complete multi-agent trajectories. We extract
1,709 calls and their inputs and outputs from 57 Test trajectories
(848 calls) and 57 Dev trajectories (861 calls), keeping each call’s
agent identity and applicable policies.
We develop the evaluation adapter on Test and use it unchanged on Dev.
The combined results therefore do not represent evaluation on entirely
unseen data. The guard reviews recorded calls and outputs rather than
blocking calls before execution. Here, over-block is the percentage of
benign trajectories incorrectly flagged as violating.
Detection and confirmation.
The guard first checks each recorded call for possible violations. It returns a
verdict, check type, quoted policy clause, evidence, and comparison. Deterministic
checks verify that the quoted text appears in the input.
The same checkpoint then reviews each candidate violation. It rejects findings
based on optional instructions, rules that do not apply to the agent or situation,
unsupported state, or evidence that satisfies the rule. It can confirm visible
violations and missing required fields or steps. A trajectory is labeled violating
if any candidate is confirmed. Reference labels are never included in the prompts.
We compute overall metrics by pooling the Test and Dev confusion matrices.
A trajectory contains about 15 calls on average, so even one false alarm can flag
an otherwise compliant trajectory. If each of n calls independently has a
false-positive probability p, the trajectory-level probability is 1-(1-p)^{n}.
This expression illustrates the effect of repeated checks. It does not assume
that the actual decisions are independent.
Inference settings and error handling.
We rerun R0 and R10 with the same initial inputs, evaluation scripts, and serving
settings, keeping all 114 trajectories. The first scan uses temperature zero and
an output limit of 384 tokens. The confirmation pass uses 128 tokens.
There are no request errors or parsing failures on Test. On Dev, R0 has four scan
parsing failures and R10 has three. Each has one confirmation parsing failure.
An unparseable response does not count as a confirmed violation, and no trajectory
is removed. Table 3 uses this R10 rerun together with
the earlier fixed-archive predictions. The supplementary reproduction notes give
the serving settings.
