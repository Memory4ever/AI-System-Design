 DynaWeave: Learning to Adapt through
 Dynamic Scenario Synthesis
 Xuan Yang
 Chunxiao Liu
 Hongsheng Xin
 Hao Xu
 Ning Miao
  Abstract
 Large language model (LLM) agents increasingly use tools to complete tasks in stateful environments. However, many training environments remain largely static apart from changes caused by the agent’s own actions, whereas external events introduced by other users, services, or sudden contingencies in real environments can invalidate ongoing plans. To address this gap, we introduce DynaWeave, an automated synthesis framework that transforms existing static tasks into verifiable dynamic scenarios. The framework generates exogenous events relevant to each task, covering changes in task requirements, environment state, and external information. It uses directed acyclic graphs (DAGs) to represent dependencies between events and an execution engine to activate them during agent interaction. A dynamic verifier revises only the evaluation checks affected by events that actually occur and retains all other checks. Using DynaWeave, we collect 2,095 verified interaction trajectories across 36 environments and use them for supervised fine-tuning of Qwen3.5 models. Experiments on Gaia2, CostBench, and ToolMaze show that DynaWeave achieves consistent improvements in overall performance across all three evaluated model sizes, increasing the task completion rate on CostBench by 67.34 percentage points and even exceeding the performance of Gemini-3.1-Pro-Preview on ToolMaze. These results support dynamic scenario synthesis as a practical approach to training agents to adapt to changing environments. Our code is available at
 https://github.com/Miaow-Lab/DynaWeave .

  1  Introduction
 Large language models (LLM) are increasingly capable of using tools to complete tasks in external environments beyond the conversation. For example, an agent may search a database, compare available options, and then book a room or issue a refund through a tool. Existing benchmarks provide executable environments such as websites, applications, and tool sandboxes in which agents perform tasks, and automatically assess whether the results satisfy the user’s request.   ( Zhou et al., 2024 ;  Xie et al., 2024 ;  Trivedi et al., 2024 ;  Lu et al., 2025 ;  Yao et al., 2024 ;  Barres et al., 2025 ) . Recent advances in environment synthesis further automate the construction of applications, tasks, and verifiers, expanding the supply of verifiable interactions for agent training and evaluation   ( Dong et al., 2026 ;  Song et al., 2026 ;  Wang et al., 2026 ;  Froger et al., 2025 ) .
 Despite this recent progress, most existing environments rely on an implicit assumption: once a task begins, the environment remains largely unchanged except through the actions of the evaluated agent. In practice, however, real-world environments offer no such guarantee of stability: another user may claim a resource that the agent had previously found available; a service may suddenly become unavailable; or an unexpected contingency may disrupt the original plan. We refer to such changes that affect a task during its execution but are not caused by the evaluated agent as  exogenous events . These changes can easily invalidate an otherwise correct plan, making success contingent on the agent’s ability to dynamically revise its decisions rather than merely execute them.
 Recent benchmarks have demonstrated the importance of evaluating agents under dynamic scenarios. Unlike previous static benchmarks, a dynamic scenario is characterized by the possibility of exogenous events during task execution. Gaia2  ( Froger et al., 2026 )  provides asynchronous environments that evolve independently of the agent; CostBench  ( Liu et al., 2026 )  changes tool costs and availability during execution, requiring agents to revise their plans; ToolMaze  ( Zhu et al., 2026 )  introduces explicit or implicit tool failures that require recovery and replanning; and ClawMark  ( Meng et al., 2026 )  incorporates external updates into multi-turn, multi-day workflows. TThese benchmarks highlight the value of evaluating adaptation, but constructing dynamic scenarios and their corresponding verifiers can require substantial manual effort. Producing such scenarios at the scale needed for agent training therefore remains a challenge.
 In this work, we propose DynaWeave, a framework that automatically transforms existing static tasks into verifiable dynamic scenarios. Given an executable environment, a task, and its original verifier, DynaWeave identifies possible changes relevant to the task and generates corresponding exogenous events. It filters out events that are invalid, implausible, or have no meaningful effect on the task. The resulting scenarios are configured before evaluation, and events are activated during agent interaction when their conditions are met. The original verifier is adapted to account for events that actually occur while preserving unaffected task requirements. This design combines automatic event generation, reproducible execution, and verification, allowing existing task collections such as EnvScaler  ( Song et al., 2026 )  and Agent-World  ( Dong et al., 2026 )  to be extended without manually designing dynamic scenarios for each domain.
 To evaluate the value of these scenarios for agent training, we use DynaWeave to collect 2,095 verified interaction trajectories and subsequently perform supervised fine-tuning on Qwen3.5 models with 2B, 4B, and 9B parameters. Across all three model sizes, this training consistently improves the overall scores on Gaia2 and ToolMaze, as well as the task completion rate on CostBench. In particular, the Qwen3.5-2B model improves its task completion rate on CostBench from 3.00% to 70.34%, representing a substantial gain of 67.34 percentage points. Furthermore, on ToolMaze, the 9B model achieves a composite score of 32.28 after training, even exceeding the baseline performance of Gemini-3.1-Pro-Preview (32.19). These results strongly indicate that the benefits of training on the generated trajectories generalize well and extend beyond the training environments, effectively improving the models’ adaptability to unexpected changes during task execution.
 The main contributions of our work are as follows: (1) We propose DynaWeave, a general framework for automatically transforming existing static, executable tool-use tasks into verifiable dynamic variants with exogenous changes occurring during task execution.(2) We construct 2,095 dynamic scenarios across 36 environments from EnvScaler,     τ  2   \tau^{2}   -bench, ToolSandbox, and AgentDojo, and collect verified interaction trajectories for supervised fine-tuning. (3) Experiments on three dynamic benchmarks show consistent improvements across three model sizes, demonstrating the value of DynaWeave for training agents to adapt to changes in dynamic environments.
  2  Related Work
  2.1  Executable benchmarks and environment synthesis
 Executable benchmarks evaluate agents through continuous interactions with working applications and rigorous checks of task completion. WebArena  ( Zhou et al., 2024 )  and OSWorld  ( Xie et al., 2024 )  support reproducible interaction with complex web and computer systems; AppWorld  ( Trivedi et al., 2024 )  and ToolSandbox  ( Lu et al., 2025 )  evaluate intermediate environment states or complete interaction trajectories; and    τ  \tau   -bench  ( Yao et al., 2024 )  incorporates simulated users and specific domain policies. AndroidWorld  ( Rawles et al., 2025 )  expands overall task coverage through parameterized initialization, which effectively varies task instances rather than necessarily introducing unpredictable external changes during execution.     τ  2   \tau^{2}   -bench  ( Barres et al., 2025 )  permits both the user and the agent to modify a shared environment, emphasizing real-time coordination between participants. Ultimately, these existing settings provide valuable, reusable tools and evaluation procedures on which more dynamic extensions can readily build.
 Environment synthesis addresses the cost of constructing such resources. AgentScaler  ( Fang et al., 2025 )  and AutoForge  ( Cai et al., 2025 )  automate environment construction for agent training. EnvScaler  ( Song et al., 2026 )  separates executable environment skeletons from task scenarios and rule-based validators, while Agent World Model (AWM)  ( Wang et al., 2026 )  constructs database-backed environments with accessible state for reward computation. Agent-World  ( Dong et al., 2026 )  further connects environment and task synthesis to capability gaps identified during training. Their primary focus is expanding the supply and diversity of executable tasks. DynaWeave addresses a complementary dimension: generating changes within an existing task, determining when and how they become observable, and adapting evaluation to their effects. It reuses the source environment and tool interface, preserving unaffected requirements rather than constructing every dynamic scenario from scratch. This executable foundation also allows event application to be checked separately from agent behavior, so errors in the generated scenario need not be treated as failures of adaptation.
  2.2  Dynamic and asynchronous agent benchmarks
 Dynamic benchmarks examine how agents respond when earlier information or plans become invalid. Gaia2  ( Froger et al., 2026 )  introduces independently evolving, asynchronous environments, supported by ARE’s  ( Froger et al., 2025 )  for applications, event execution, and verification. ClawMark  ( Meng et al., 2026 )  incorporates external updates into workflows spanning multiple turns and days. CostBench  ( Liu et al., 2026 )  studies economical replanning under changes such as tool failures and revised costs, whereas ToolMaze  ( Zhu et al., 2026 )  combines tool dependency structures with explicit or implicit failures that may be transient or permanent. ClawArena  ( Ji et al., 2026 )  focuses on revising beliefs as evidence changes, and SimuHome  ( Seo et al., 2026 )  models temporal changes in a smart-home simulator. Together, these benchmarks expose distinct challenges in adaptation, from recognizing unreliable information to recovering from disrupted execution.
 Our focus is complementary to constructing these evaluation settings: automatically deriving plausible events and corresponding verification rules from existing static tasks across domains. An execution engine enables scheduled changes, but event selection and evaluation must still account for the source task’s requirements. ProEvolve  ( Li et al., 2026 )  and EvoArena  ( Xu et al., 2026 )  address change across environment versions and successive tasks, including evolving tools, schemas, data, and agent memory. In contrast, DynaWeave retains the tool interface and environment rules while introducing changes during task execution. This scope supports paired evaluation of static and dynamic variants and the collection of demonstrations of adaptation within the same underlying environments.
  3  DynaWeave
  Figure 1:  Overview of DynaWeave. (a) The framework generates task-grounded exogenous events from an existing static task, validates their specifications, and organizes compatible events into a dependency graph. (b) An execution engine activates events during agent interaction through action completion, virtual time, or random activation. (c) The dynamic verifier adapts checks affected by realized events while retaining unaffected requirements. (d) Agents interact through the original tools, receiving tool results and permitted event notifications; verified teacher trajectories provide demonstrations for supervised fine-tuning. 
 DynaWeave transforms existing static tasks into verifiable dynamic scenarios by reusing their executable environments and adapting the original success criteria. Given an environment, its initial state, a task instruction, and the original verifier, it constructs a dynamic scenario    Π  \Pi    and a corresponding dynamic verifier     V  Π   V_{\Pi}   . As illustrated in Figure   1  , the framework consists of three components. First,  exogenous event construction  identifies plausible event themes relevant to the task, specifies each event’s effects, activation conditions, and observability, and organizes compatible events into a directed acyclic graph (DAG). Second,  controlled dynamic execution  activates events based on action completion, virtual time, or random triggers, while respecting event dependencies and environment conditions. Third,  dynamic verifier adaptation  revises checks affected by events that actually occur and preserves requirements that remain applicable. When correctness depends on the timing or order of actions, the verifier also checks the execution trace.
  3.1  Exogenous Event Construction
 To construct plausible exogenous events for static tasks, we design a three-stage pipeline that first identifies event themes, then generates their specific content, and finally organizes the resulting events into a directed acyclic graph.
  Identifying Sources of Change. 
The first stage identifies where relevant dynamics may arise during task execution. To guide the automatic generation of plausible event themes, we distinguish three sources of dynamics: (i) task requirements, where the user revises the original goal; (ii) environment state, where resource availability or tool functionality changes; and (iii) external information, where a contingency affect the goal or path of the task. For example, a typhoon warning at the intended destination may require the agent to reconsider a flight booking. Given the environment information, initial state, and task description, DynaWeave determines which sources can plausibly affect the task and proposes corresponding event themes. Each theme provides a concise description of a potential change, such as the user cancelling a trip, fewer rooms being available, or a typhoon warning being issued. These themes guide the generation of concrete events in the next stage.
  Specifying Executable Events. 
Building on the selected themes, DynaWeave expands each concise description into a concrete event with three components. First, it specifies the source of the change, the environment entities or resources affected, and the resulting effects. Second, it defines the conditions under which the event is triggered, such as after a particular agent action or when a virtual clock reaches a scheduled time. Detailed trigger mechanisms and their implementation are discussed in Section   3.2  . Third, it specifies how the event becomes observable to the agent. We distinguish three modes:  loud  events explicitly notify the agent of the change;  silent  events provide no notification and must be discovered through available tools; and  partial  observations reveal only part of the change, requiring further investigation to establish its implications. Generated event candidates undergo programmatic checks and independent review to assess whether their effects are executable, their causes are plausible, and their consequences are relevant to the task. Accepted events are then passed to the composition stage.
  Constructing Dependency Graphs. 
In the final stage, DynaWeave combines multiple events into a coherent dynamic scenario. Some events depend on earlier changes; for example, a service can recover only after it has failed. An LLM selects compatible events and proposes dependencies based on their causes, effects, and activation conditions. The resulting scenario is represented as a directed acyclic graph (DAG),     Π  =   (  𝒩  ,  𝒜  )    \Pi=(\mathcal{N},\mathcal{A})   , where each node in    𝒩  \mathcal{N}    represents an event. An edge      (   e  i   ,   e  j   )   ∈  𝒜   (e_{i},e_{j})\in\mathcal{A}    means that event     e  i   e_{i}    must occur before event     e  j   e_{j}    can be triggered. The graph does not impose a fixed order on independent events. Its acyclic structure prevents circular dependencies in which events wait for one another. Each proposed graph is validated for structural correctness and consistency among event dependencies, activation conditions, and effects.
  3.2  Controlled Dynamic Execution
 Once the event DAG is constructed, DynaWeave uses a programmatic execution engine to monitor agent interactions and apply events when their trigger conditions are satisfied. We consider three trigger mechanisms: completion of a specified agent operation, passage of virtual time, and random activation to model the complex mechanisms of changes in real environment.
  Action Completion.  An event can be triggered after the agent completes a specified tool operation. The execution engine matches the completed call against the operation recorded in the event specification, including relevant arguments or occurrence counts when needed. This places changes at meaningful points in the task, such as immediately after the agent checks a resource’s availability. The event is applied after the tool call finishes, so the operation itself remains intact while its result may become outdated before the agent’s next decision. For example, after the agent confirms that a hotel room is available, an external booking may reserve that room, requiring the agent to reconsider its choice before completing the reservation.
  Virtual Time.  A virtual clock provides a strictly reproducible measure of elapsed time within the simulated environment. Starting from an initial state of      c  0   =  0   c_{0}=0   , the clock advances after each executed tool operation according to      c   k  +  1    =    c  k   +   d  ⁡   (   a  k   )      c_{k+1}=c_{k}+d(a_{k})   , where     d  ⁡   (   a  k   )    d(a_{k})    is the simulated duration of action     a  k   a_{k}   . We use the durations pre-defined by the source environment when available; otherwise, we assign fixed durations to tool operations and keep them strictly consistent across all agent evaluations. To precisely determine an event’s scheduled time     c  e   c_{e}   , we accumulate these simulated action durations along the task’s reference static trajectory and select a strategic time when the event’s prerequisite conditions hold and its effects can still influence subsequent decisions. During dynamic execution, the event is automatically activated at the first interaction boundary where      c  k   ≥   c  e    c_{k}\geq c_{e}    and its eligibility conditions are satisfied.
  Random Activation.  At each interaction interval, an event that satisfies its eligibility conditions can be activated with a specified probability     p  e   p_{e}   . We fix the random seed before execution to make the random activation process reproducible. An event may remain inactive when the interaction ends, and the verifier accounts only for changes that actually occurred.
 Under all three mechanisms, each event is applied at most once. When an event occurs, the engine applies its specified effects, provides only the observations allowed by its observability mode, and records the changes separately from those caused by the agent’s tool calls. These records support the dynamic verifier described in Section   3.3  .
  3.3  Dynamic Verifier Adaptation
 Given the original verifier     V  0   V_{0}    and the generated event specifications, DynaWeave uses an LLM to identify checks whose validity depends on the information, state, or task requirements affected by each event. Unaffected checks are retained, while those whose expected outcomes have changed are revised accordingly. A task requirement is removed only when the user explicitly cancels it. Changes that affect how a task can be completed do not, by themselves, alter the requested outcome. For example, consider a meeting for which the user changes only the requested start time from 15:30 to 16:00. The original verifier would reject a booking at the updated time, whereas removing the time check could accept bookings at an incorrect time. The dynamic verifier instead revises the expected time while retaining other requirements. By contrast, a room becoming unavailable does not, by itself, authorize a change in meeting time. This distinction separates changes in the task from changes in the plan used to complete it.
 The proposed modifications are expressed as structured rules and validated before execution for consistency with the task requirements and event specifications. Incompatible modifications are rejected at this stage. During execution, each modification takes effect only when its associated event occurs; inactive events leave the applicable checks unchanged. When multiple events occur, their modifications are applied in the realized execution order, consistent with the DAG. The verifier therefore evaluates the requirements applicable to the observed execution rather than assuming that all potential changes have occurred. When a requirement depends on the timing or order of actions, DynaWeave supplements outcome checks with checks over the execution trace. These checks assess whether the agent’s actions satisfy the requirements in effect at the relevant point in execution, while allowing different valid action sequences rather than prescribing a fixed solution.
 Before accepting a generated verifier, DynaWeave checks that it agrees with the original verifier when events are disabled. Strict validation additionally tests two solutions: a solution to the original static task that the event is expected to invalidate, and an adapted solution that satisfies the revised requirements. The verifier should reject the first and accept the second. This comparison provides evidence that the event meaningfully affects the task and that the adapted verifier distinguishes an invalid response from a valid adaptation.
  3.4  Interaction with Dynamic Scenarios
 DynaWeave retains the tools, argument schemas, and interaction protocol of the source benchmark. Dynamic scenarios change how the environment evolves and what the agent observes, without requiring a new interaction interface.

At the end of the interaction,     V  Π   V_{\Pi}    evaluates whether the agent has satisfied the task requirements, taking into account the events that actually occurred.
 For supervised fine-tuning, we collect trajectories from a teacher model. These trajectories record the observations available to the teacher, including event notifications, user messages, or changes in tool results, together with its subsequent actions. They provide demonstrations of how the teacher responds to changes and adjusts its actions during task execution.

  4.1  Experiment Setup
  Training Details. 
We apply DynaWeave to EnvScaler  ( Song et al., 2026 )  ToolSandbox  ( Lu et al., 2025 ) , AgentDojo  ( Debenedetti et al., 2024 ) , and     τ  2   \tau^{2}   -bench  ( Barres et al., 2025 ) , extending their executable environments with dynamic scenarios. The resulting corpus contains 2,095 dynamic scenarios and 3,414 events across 36 environments, covering healthcare, scheduling, mobile assistance, workplace applications, travel, retail, banking, and telecommunications. Figure   2   summarizes the corpus statistics. Using Qwen3.5-35B-A3B as the teacher model, we collect 2,095 verified interaction trajectories for supervised fine-tuning (SFT) of Qwen3.5 models. We fine-tune the models in non-thinking mode using LLaMA-Factory and LoRA with a rank of 16. All models are trained for two epochs with a learning rate of     1  ×   10   −  4     1\times 10^{-4}   , an effective batch size of 64, and a maximum sequence length of 16,384 tokens.
  Evaluation Benchmarks. 
We evaluate DynaWeave on three dynamic benchmarks to assess generalization beyond the training environments. Gaia2  ( Froger et al., 2026 )  provides asynchronous application environments that evolve independently of the agent. It evaluates execution, search, ambiguity resolution, adaptation, and reasoning under time constraints. CostBench  ( Liu et al., 2026 )  evaluates planning in a travel environment where tools have different costs. Its dynamic conditions change tool costs, user preferences, execution lengths, or tool availability, requiring agents to revise their plans while controlling cost. ToolMaze  ( Zhu et al., 2026 )  evaluates recovery from explicit tool errors and from corrupted outputs without explicit error messages. Both types of failure can be transient or permanent.
  4.2  Main Results
 Table   1   presents the performance of DynaWeave on three dynamic benchmarks. Across all three model sizes, DynaWeave improves overall scores on Gaia2 and ToolMaze, as well as task completion on CostBench. These gains encompass more reliable tool use, more efficient task completion, and better aggregate recovery from tool failures, demonstrating that DynaWeave enhances agents’ ability to adapt to dynamic scenarios and generalize beyond the training environments.
  DynaWeave transfers across distinct forms of environmental change. 
The three benchmarks test different dynamic scenarios, from asynchronous application updates to changing planning constraints and tool failures. DynaWeave yields gains across these settings: for 4B, Gaia2 overall improves from 3.3 to 5.0, CostBench completion rises from 72.41% to 90.81%, and ToolMaze success under perturbations increases from 21.25% to 25.38%. Both the 2B and 9B models likewise improve across all three benchmarks. DynaWeave-9B even surpasses GPT-4o and Gemini-3.1-Pro-Preview on ToolMaze. These consistent improvements across out-of-domain environments show that DynaWeave learn to adjust the actions and plans in response to dynamic changes, rather than merely reproduce tool-use patterns from the training environments.
  The gains extend to both execution reliability and efficiency. 
DynaWeave improves task completion without sacrificing execution efficiency. On CostBench, the 9B model raises completion to 92.39% while reducing its cost gap from 0.755 to 0.140 and invalid tool use from 7.08% to zero. ToolMaze likewise shows higher mean recovery rates and lower normalized recovery costs at every model size (The detailed results of ToolMaze are deferred to Appendix   A  ), alongside improvements in Gaia2 Search and Execution. These joint gains are consistent with agents obtaining updated information when needed and revising their actions, rather than continuing a plan based on outdated assumptions. A targeted query after a change can incur an immediate cost but prevent repeated failed calls or actions that no longer advance the task. Responding appropriately to the new information can therefore improve both the likelihood of completion and the efficiency of reaching it.
  DynaWeave improves models across different sizes. 
DynaWeave consistently improves models of all evaluated sizes. Larger models retain stronger overall performance after training across the three benchmarks, suggesting that their underlying reasoning and tool-use capabilities may help them interpret changes and select appropriate responses. Targeted training also narrows the gap between model sizes: the trained 4B model outperforms the original 9B model on both Gaia2 overall and CostBench task completion. These results show that DynaWeave can strengthen smaller models while providing further gains for larger ones.
 Despite these gains, models trained with DynaWeave still struggle when tool results are incorrect but contain no explicit error message, or when success requires responding to changes at the right time, as reflected in ToolMaze’s corrupted-output conditions and Gaia2’s Adaptability and Time categories. These cases require agents to recognize when information is unreliable or outdated and decide when to check it again. The limitations may stem from the absence of these types of changes in the dynamic scenarios used for training.

  4.3  Data Efficiency and Performance Saturation
 We examine how the number of training trajectories affects Qwen3.5-4B performance, keeping the source tasks, environments, and number of training epochs fixed. Figure 3 shows that adding trajectories improves task completion on CostBench and both task success under perturbations and the composite score on ToolMaze. A substantial share of these gains is achieved with 1,048 trajectories, approximately half of the full corpus. At this size, CostBench task completion reaches 87.08% and the ToolMaze composite score reaches 28.91, compared with 90.81% and 29.99, respectively, when all 2,095 trajectories are used. The gains become smaller as the training set grows.
 The effects on other metrics are less uniform. ToolMaze’s normalized recovery cost decreases across all evaluated training set sizes. However, CostBench’s invalid tool use ratio and cost gap reach their lowest values before the full corpus is used, while ToolMaze’s PRR peaks at 1,571 trajectories and then declines slightly. These results show that higher task completion does not necessarily coincide with improvements in every measure of reliability and efficiency. One possible explanation is that SFT trains the model to imitate demonstrated actions without directly optimizing execution cost. Overall, training on more trajectories generated with DynaWeave improves task performance within the evaluated range, but the gains diminish and additional data does not improve all metrics consistently.

  4.4  Contributions of Different Event Sources
 To examine the contributions of different sources of change, we compare training on a mixture of all three sources with training on subsets that each exclude one source:  Task Requirement ,  Environment State , or  External Information . For this comparison, we use Qwen3.5-4B and 1,048 trajectories for each setting. As shown in Table 2, the mixed subset achieves the highest task completion rate on CostBench and the highest composite score on ToolMaze. It also yields the highest ToolMaze task success under perturbations and the lowest recovery cost. CostBench task completion drops most when Task Requirement events are excluded, whereas ToolMaze success under perturbations and recovery efficiency decline most when Environment State events are excluded. These patterns suggest complementary benefits from learning to revise task goals and adjust execution to changes in the environment. In particular, demonstrations involving changes in task progress may help agents identify which actions remain necessary and avoid redundant execution during recovery.
 Compared with the mixed subset, excluding External Information events improves ToolMaze task success without injected failures, but lowers average success and increases recovery cost under tool failures or corrupted outputs. This pattern suggests that learning to respond to new information may help agents adjust their actions when execution is disrupted. On CostBench, some subsets that omit an event source achieve a lower cost gap or a lower invalid tool use ratio than the mixed subset, but all have lower task completion rates. These results highlight the need to assess efficiency alongside task completion.
 We further compare these subsets with a smaller mixed subset containing 524 trajectories, approximately 25% of the full training corpus. On ToolMaze, this smaller subset achieves a composite score of 27.64, exceeding all three subsets that contain 1,048 trajectories but omit one source. It also achieves higher average task success under perturbations and lower recovery cost than these larger subsets, despite lower success without injected failures. This comparison highlights the importance of data composition as well as quantity. However, differences in task and environment coverage, together with the different numbers of optimization steps across dataset sizes, prevent us from attributing this advantage solely to the inclusion of all three event sources. Overall, the results support retaining all three sources to improve task completion and recovery, rather than increasing data quantity without considering the diversity of changes it covers.

  5  Conclusion
 We presented DynaWeave, an automated framework for transforming existing static tasks into verifiable dynamic scenarios. The framework generates exogenous events involving task requirements, environment state, and external information, controls their execution, and adapts the original verifier to the changes that actually occur. It preserves the original tools and unaffected task requirements, allowing existing environments to support training under changing conditions. Supervised fine-tuning on 2,095 verified trajectories collected across 36 environments improves the overall performance of Qwen3.5 models of all three evaluated sizes on Gaia2, CostBench, and ToolMaze, supporting generalization beyond the training environments. Our analyses further show diminishing gains from increasing data quantity and highlight the value of including all three event sources for task completion and recovery. However, higher task completion does not always coincide with better execution efficiency, and responding to changes at the appropriate time remains challenging. Future work should investigate how scenario construction and training can better address these limitations. Overall, DynaWeave provides a practical way to use existing task collections to train agents not only to execute plans, but also to revise their actions as conditions change.
