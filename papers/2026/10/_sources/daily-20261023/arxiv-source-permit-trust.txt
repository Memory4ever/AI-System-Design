D.1 Interface and trust assumptions
The Protected LLM P P is an arbitrary agent strategy over its observations, interaction history, and random coins. It chooses operations and can re-plan on endorsed feedback. The harness mediates the memory interface and tool boundary; it does not inspect or taint-track the agent’s internal reasoning. The Quarantined Reader Q Q may behave adversarially and holds no tool capability. Appendix B.1 gives the operation-level view; Supplement S2 gives the normative semantics.
Stored values and authority.
Each immutable block has bytes, a source-based label, provenance, and a tool scope. The labels are 𝖳 \mathsf{T} (user-typed), 𝖴 \mathsf{U} (untrusted), 𝖢 \mathsf{C} (personally confirmed), 𝖯𝖢 \mathsf{PC} (agent-composed), and, in the federated extension, 𝖢𝖢 \mathsf{CC} (community-confirmed). The readable store ℳ 𝔼 \mathcal{M}_{\mathbb{E}} consists of non- 𝖴 \mathsf{U} blocks. Readability alone does not authorize a sensitive call: a literal must byte-match a 𝖳 \mathsf{T} block or a confirmed block scoped to that tool. A 𝖯𝖢 \mathsf{PC} block has no independent endorsement authority. A confirmation for the reasoning target makes its bytes readable but grants no sensitive-tool scope.
The trusted command channel creates 𝖳 \mathsf{T} blocks. Pasted content and all tool outputs, including errors and status text, enter 𝖴 \mathsf{U} . Reader-generated summaries also enter 𝖴 \mathsf{U} . The agent receives an opaque handle, not those bytes. Accepting confirmation creates a fresh 𝖢 \mathsf{C} copy; it never relabels the untrusted source in place. Endorsed and untrusted identifiers use separate allocation streams, so an attacker cannot influence a later endorsed identifier by adding untrusted blocks.
Mediation rules.
The harness enforces the following properties (complete rules: Supplement S2.3 ).
•
Every handle-expressed tool argument gates, even if its hidden bytes equal an already trusted value. The gate resolves the handle, displays the exact bytes and target, and binds an acceptance to those same bytes. Rejection or failed resolution prevents the flow.
•
Sensitive-tool literals use only the typed or exact-tool-confirmed fast paths. The baseline permits agent-composed literals at data tools. Consequently, endorsement for one purpose does not imply a confidentiality guarantee for all later data-tool uses; Option O2 adds exact-tool checks there.
•
Reader failure, empty retrieval, and unoccupied identifiers have the same opaque reply. Handle structure follows operations rather than hidden content, size, or success. The reply alphabet contains only fixed acknowledgements, handles, fixed failures, decisions, and verbatim readable-store bytes. Trusted retrieval sees ℳ 𝔼 \mathcal{M}_{\mathbb{E}} alone.
•
All attacker-influenceable user-facing content is recorded in the display transcript. Authenticated facts and untrusted source claims occupy separate zones. Selection previews carry no authority; authorization uses the resolved value in the decision pane.
•
A batch displays every value that would flow, records its pages and decisions, and executes only after all required approvals. Accepted values remain endorsed even if a later review aborts the invocation. Full batch semantics and the corresponding determinacy argument are in Supplement S2 – S3 .
Assumptions and boundaries.
Both integrity results assume source-based labels, immutable stored blocks, and faithful displays ( A1 – A3 in Supplement S2.4 ), together with the enforced interface above. Action Integrity additionally assumes sound atomic endorsement : acceptance means that the user intends the exact displayed value at the named tool, separately for each reviewed value, including accepted positions of a transaction that later aborts ( A4 ). An LLM verifier can violate this assumption; the theorem does not establish its accuracy. Reasoning Integrity instead assumes a common exogenous typed-input stream and matched scheduling and coins ( A6 and conventions C1 , C9 ); it does not require endorsements to be semantically correct. Timing, termination, and compromised harness components are outside these guarantees.
Lemma D.1 (Protected-agent isolation) .
In every interface-conformant execution, each bytes-carrying reply delivered to P P is the verbatim content of a readable-store block at delivery. Untrusted sources reach P P only through opaque handles until endorsement. This is a statement about the source of a delivered value, not disjointness of byte strings across stores.
Proof sketch.
Inspect the reply constructors. Tool capture, untrusted recall, reader search, and crystallization return handles or fixed tokens. Only trusted recall and retrieval return bytes, and both read ℳ 𝔼 \mathcal{M}_{\mathbb{E}} . Input ingestion and each operation preserve this property, so induction extends it to arbitrary run length. Full proof: Supplement, Lemma S3.12 .
∎
D.2 Integrity Proofs
D.2.1 Action Integrity
Definition D.2 (Personal Action Integrity) .
A sensitive sink event at tool t t is personally authorized when each argument value v v byte-matches user-typed content, or this user has accepted the exact bytes v v for t t , either at that call or in a retained in-scope confirmation. For a batch, acceptance covers each displayed element separately. Action Integrity requires this property for every sensitive sink event of every execution.
Theorem D.3 (Action Integrity) .
Under the interface and A1 – A4 above, every execution starting from a well-formed configuration has personal Action Integrity, for arbitrary agent strategies, attacks, and reader behavior. The empty configuration is well formed; a seeded configuration must carry a valid endorsement record. The invariant requires immutable source-correct blocks, valid endorsement ancestry and history, interface-conformant state, and authorization of the accumulated sink log (complete definition: Supplement, Definition S3.3 ).
Proof sketch.
The empty state satisfies the invariant. For each transition, new untrusted blocks confer no authority; agent writes confer readability but no new authorization; and an accepted confirmation creates a fresh copy justified by the exact display and sound endorsement. A sensitive call therefore has only three admissible cases: a typed literal, an in-scope confirmed literal, or fresh accepting confirmation. Every handle takes the third case, and a batch applies it to every flowed element. Failed reviews prevent the call, while already accepted values remain individually authorized. These cases preserve the invariant and establish sink safety by induction. The single-user interpreter has no 𝖢𝖢 \mathsf{CC} creation path. Full statement and proof: Supplement, Theorem S3.21 .
∎
Corollary D.4 (No silent resolution) .
Under the same conditions, never-endorsed untrusted bytes cross a tool boundary, including a data-tool boundary, only through acceptance of those exact bytes for that tool in that call. After endorsement at any target, their readable copy may be used as a literal at baseline data tools. Sensitive-tool scope checks and the rule that handles always gate still apply.
Proof sketch.
Isolation leaves never-endorsed bytes available only through handles, and every handle resolution gates. Endorsement subsequently creates a readable copy, enabling the stated literal path. This distinguishes exact-byte authorization from control influence carried by a logged decision. Full proof and Option O2 ’s closure of the later data-tool path: Supplement, Corollary S3.23 .
∎
Reuse and contextual authorization.
The policy authorizes exact values for tools, not complete transactions. Separately approved values may be combined without joint review, and a changed task context may make their reuse inappropriate. Shared disputes suspend community reuse but preserve prior personal confirmations. Candidate expiry retires dormant or inactive shared entries (Supplement, Rule R14 ); it is not a universal authorization lifetime. Local scope leases are a future extension outside the proved model (Option O3 ). Context-bound or transaction-level approval would require extended semantics and revised confirmation-cost accounting.
Future direction: combined-memory review.
Human or agent memory managers could assemble related memories with their provenance and intended use, then review their joint meaning. The combined item remains untrusted until confirmation; its components’ approvals do not automatically endorse it. If subsequently published, it must gather fresh endorsements of its exact content under the community-promotion rules. Revisions require their own review. This proposed workflow builds on crystallization and endorsement but has not been evaluated and does not authorize every later transaction using the combined memory. Future experiments should compare it with per-item review under matched attack-search and review budgets, measuring harmful endorsement, delayed-combination success, benign utility, and review burden.
D.2.2 Reasoning Integrity modulo the display transcript
The protected view is 𝗈𝖻𝗌 P ​ ( c ) = ( ℳ 𝔼 , H , x , h ) \mathsf{obs}_{P}(c)=(\mathcal{M}_{\mathbb{E}},H,x,h) : the readable store, observable handle structure, typed input, and decision history. Matched configurations c 1 ≈ c 2 c_{1}\approx c_{2} agree on this view, the agent’s interaction history and consumed coins, endorsed allocation state, and initial ghost display and sink logs. Their untrusted stores and private handle resolutions may differ arbitrarily. A common endorsed seed with empty histories is a canonical matched start.
The complete display transcript 𝖣𝖳 ⁡ ( ρ ) \mathsf{DT}(\rho) records selection surfaces and previews, exact decision-pane values and provenance zones, targets, selections, accepts and rejects, and batch pages and aggregated decisions, including reviews in aborted transactions. Its event kinds are interpreter-assigned. The observable behavior ℬ ⁡ ( ρ ) \mathcal{B}(\rho) comprises protected-agent operations, tool invocations, the reply stream, final protected view, and the ungated sink projection. The latter omits arguments flowed by fresh confirmations, which are already recorded in the transcript.
Theorem D.5 (Reasoning Integrity modulo the display transcript) .
Under A1 – A3 and the input and scheduling conditions above, fix matched starts, any two attacks, and a coupled coin sequence. For runs ρ 1 , ρ 2 \rho_{1},\rho_{2} of a common horizon,
𝖣𝖳 ⁡ ( ρ 1 ) = 𝖣𝖳 ⁡ ( ρ 2 ) ⟹ ℬ ⁡ ( ρ 1 ) = ℬ ⁡ ( ρ 2 ) . \mathsf{DT}(\rho_{1})=\mathsf{DT}(\rho_{2})\quad\Longrightarrow\quad\mathcal{B}(\rho_{1})=\mathcal{B}(\rho_{2}).
Paste presence and content, reader outputs, and tool outputs need not agree across the attacks. The statement is trace-wise for every coupled coin sequence. In plain terms, the two runs may differ in whether pasted input arrives, its contents, and reader and tool outputs. The guarantee holds for every fixed sequence of random choices used identically in both runs.
Proof sketch.
Maintain matched protected views, histories, coin positions, and transcript prefixes. The strategy then chooses the same next operation. A display-free step returns only a constant token, an operation-determined handle, or matched readable bytes, preserving the invariant. At a display step, the append-only transcripts and equality of the complete transcripts make the newly appended segments prefix-comparable. The interface’s display-segment determinacy lemma forces those segments to be equal, including page structure, decisions, and released bytes. The two steps therefore create the same endorsed copies and replies. Induction gives the claimed equality; sink annotations follow the same mediation cases as Action Integrity. Full proof, including the segment lemma and batch cases: Supplement, Lemma S3.20 and Theorem S3.25 .
∎
Corollary D.6 (Attack-surface confinement) .
Under the same comparison conditions, a difference in protected-agent operations, tool invocations, or ungated sink events entails a difference in the complete display transcript.

This is a conditional noninterference guarantee. An attacker can affect a preview or an endorsement decision, and thereby the transcript and later behavior. The theorem excludes additional influence that bypasses that recorded release surface; it does not establish reasoning correctness or make displayed attacks harmless.
Appendix E Scope of the Lean 4 Verification
The Lean artifact is available upon request and will be released with the code when the paper is published. The artifact contains the executable single-user interpreter, proofs, build assertions, dependency manifest, and axiom report. It pins Lean 4 and Mathlib to v4.31.0 (Mathlib revision fabf563a ); lake exe cache get && lake build reproduces the check. Supplement S9 gives the complete correspondence table, ten modeling deltas, and the specification corrections discovered during mechanization.
What is checked.
action_integrity and action_integrity_from establish the single-user action guarantee from the empty endorsed store and from any state satisfying the mechanized invariant. reasoning_integrity and reasoning_integrity_from prove the transcript-conditioned comparison from empty or shared endorsed seeds, for arbitrary agent strategies and independently chosen attacks. Their conclusions include equal sink logs, operations, replies, and final protected views. Paste presence and content can differ. Supporting results check reply isolation, mandatory handle gating, and attack-surface confinement. A standalone batch layer checks displayed-element flow, rejection behavior, and transcript determinacy; executable assertions cover the baseline counterexample and eight scenarios.
What remains a paper proof.
The run-level integration of batched iteration, durable endorsements from accepted positions of an aborted invocation, arbitrary mid-run matched starting states, and the reduction from reactive actors to event-indexed oracles are proved in the supplement, outside the checked interpreter. Options O1 – O2 are checked at the gate level only; their wider integration, Option O3 , the federated protocol, probability bounds, and confirmation-budget results are not mechanized. The checked interpreter returns one selected element at a direct collection-handle call and records additional transcript-determined selection information. These representation differences and their correspondence arguments are explicit in S9 .
Trusted base and artifact.
The artifact’s clean-build axiom report lists only propext and Quot.sound for the top-level theorems, with no sorryAx ; the executable assertions additionally trust Lean’s evaluator. Kernel checking certifies the mechanized statements, not the correspondence between that model and a deployed harness or the reliability of a verifier. The artifact includes the full source, CORRESPONDENCE.md , pinned build instructions, the build log, and source checksums. Thus the concise statements here remain auditable against both the complete paper proofs and the precise mechanized scope.
