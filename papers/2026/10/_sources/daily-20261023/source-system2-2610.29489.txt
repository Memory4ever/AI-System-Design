Abstract
A Transformer is built around attention, and because every token attends to every other, the cost of that one operation grows with the square of the sequence length and comes to dominate the layer on long sequences. FlashAttention made that cost manageable by working through the attention matrix in tiles and updating the softmax as it goes. Almost all the work since has targeted GPUs.
Vector processors efficiently run High-Performance Computing (HPC) workloads. Modern commercial vector architectures feature large physical vector register files with hundreds of kilobytes of storage capacity. Because a single register holds up to 512 single-precision numbers, one instruction can execute 512 element operations, significantly reducing loop bookkeeping per result. These savings are proportional to how much of the register an instruction actually utilizes, making the choice of which loop to vectorize a first-order decision rather than a tuning detail. We port PyTorch’s CPU FlashAttention kernel to a RISC-V CPU with 2KB vector registers and find that it achieves 5.17 of the 32 peak floating-point operations per cycle the core can issue (16.2% of peak). The kernel walks each tile one query row at a time, leaving suboptimal dimensions to dictate vector instruction lengths. The product against 𝐕 \mathbf{V} is vectorized along the head dimension—64 elements here, compared to the 512 elements a register holds. In the softmax, each query row requires a maximum and a sum: two reductions that collapse a full register to a single scalar once per tile. Additionally, because the hardware lacks a native exponential instruction, the softmax computes exponents via a polynomial whose coefficients compete with tile data for vector registers and cause spilling.
We propose two techniques. The first transposes the two matrices the kernel builds, the tile of scores and the running output, so that queries lie along the contiguous axis. This leaves the algorithm and its values unchanged but puts the vector length of every part of the kernel under one controllable parameter, the number of queries in a tile, so it can be chosen to match the machine’s vector length. It also makes the maximum and the sum run along the query axis, which removes both reductions. The second moves the polynomial’s coefficients into scalar registers, which stops the spilling and cuts the softmax region’s vector memory instructions by 78.7%.
On silicon the two together cut whole-kernel cycles by 1.84 1.84 to 2.08 × 2.08\times at a head dimension of 64, raising floating-point utilisation from 16.2% to 29.7% of peak. An FPGA of the same design ranks the changes identically and scores them higher, at 2.71 × 2.71\times , so the silicon figure is the conservative one.
I Introduction
Vector processors utilizing Single Instruction Multiple Data (SIMD) paradigms offer superior throughput for High-Performance Computing (HPC) tasks. By executing a single instruction across multiple data streams simultaneously, SIMD reduces instruction-fetch overhead in the processor front-end while conveying extensive semantic context directly to the underlying hardware. These inherent efficiencies drove the dominance of early vector designs from the 1970s through the 1990s, highlighted by systems such as the CDC STAR-100 [ 1 ] and Cray-1 [ 2 ] . Even as the 1990s saw the rise of massively parallel supercomputers containing thousands of nodes, vector-based execution retained its utility [ 3 , 4 ] , prompting chip manufacturers to integrate SIMD extensions into mainstream general-purpose microprocessors [ 5 , 6 ] . Today, as conventional performance scaling hits diminishing returns alongside skyrocketing demand for floating-point acceleration in modern workloads, vector processing is undergoing a major revival across both industry [ 7 ] and academia [ 8 , 9 , 10 ] .
This resurgence has propelled out-of-order (OoO) vector machines into mainstream commercial production, with NEC’s SX-Aurora TSUBASA standing as a prime real-world implementation [ 11 , 12 ] . To maximize SIMD data-parallelism, vector registers now span a wide range, from the 512 bits of Arm’s SVE in Fugaku [ 13 , 14 ] to the 16 384 16\,384 bits of NEC’s SX-Aurora [ 15 ] and of RISC-V designs [ 16 , 17 ] .
Despite the relevance of vector architectures, FlashAttention [ 18 , 19 ] , the standard implementation of attention, and almost all of the engineering that followed it, target GPUs [ 20 , 21 ] . This paper proposes several novel techniques to efficiently run FlashAttention on vector architectures featuring long register widths. What changes at this width is which architectural decisions matter. On a 128-bit unit, any loop with a handful of iterations fills the datapath, making the choice of which loop to vectorize a mere tuning detail. On a register holding 512 elements, however, a loop over a head dimension of 64 utilizes only an eighth of its capacity, and no instruction scheduler can recover the remaining throughput. PyTorch’s CPU FlashAttention walks each score tile one query row at a time—a traversal that forces the key block to dictate the vector length of the score product and softmax, while leaving the head dimension to set the vector length for the value product. Recent RISC-V kernels retain one of these axes [ 22 ] or pack multiple heads into a single register once capacity exceeds the head dimension [ 23 ] ; neither approach alters the underlying traversal.
This paper reorients the recurrence. We transpose the score tile and the running output, an outer-loop vectorisation [ 24 ] of the query loop, so that the query axis becomes the contiguous axis of both. One tile parameter then sets the vector length of every region and can be set to the register width, and the per-query maximum and sum become vectors instead of reductions. The paper contributes:
•
a region-level characterisation, on silicon, of FlashAttention-2 on a 16 384 16\,384 -bit RISC-V processor that separates each region’s vector-length limit from its access-pattern limit (Section III );
•
a software exponential whose polynomial coefficients are held in scalar rather than vector registers, which removes spill traffic that a 32-register file otherwise makes unavoidable (Section IV );
•
reorientation of the recurrence, with an instruction-count model of when it wins (Section V );
•
an evaluation on the EPAC chip and an FPGA that separates orientation
from the softmax work: reorientation alone is worth 1.43 × 1.43\times in
cycles (Section VII ).
None of this is a comparison against a GPU or a short-vector CPU, and none is needed for the claim, which is conditional: given a long-vector machine and a query block longer than the head dimension, the orientation in which the recurrence is evaluated decides the vector length of every region, and with a query block as long as the register it removes about 30% of the kernel’s cycles at no change in the arithmetic performed.

The softmax normalises each query against every key, so it runs along the second axis of 𝐒 \mathbf{S} , after subtracting each row’s maximum to keep the argument in range. The scale α \alpha is a constant of the model, 1 / d 1/\sqrt{d} here. It is applied as one multiply per score in every arm, so its numerical value affects no measurement below. Heads are independent, and FlashAttention runs them in parallel [ 19 ] , which makes a single head the unit of work. What follows measures one head on one core, the level at which vector behaviour is visible. Of the two matrix products one writes an N × N N\times N result and the other an N × d N\times d result, and Section III shows that the difference is what decides their vector length.
Forming 𝐒 \mathbf{S} explicitly costs Θ ⁡ ( N 2 ) \Theta(N^{2}) memory. FlashAttention [ 18 ] avoids it by tiling both operands, processing queries in blocks of B q B_{q} rows and keys in blocks of B k ​ v B_{kv} , and carrying the normalisation of each query block as a running maximum and sum that are rescaled whenever a new tile moves the maximum [ 26 ] . The tile shape ( B q , B k ​ v ) (B_{q},B_{kv}) is a parameter of the implementation, not of the mathematics.
II-B Long-vector processors
A vector instruction applies one operation to many elements. Short-vector SIMD units fix that number in the encoding, at four or eight elements, so a loop of a handful of iterations already fills the datapath. Vector processors instead carry the number in a register, set at run time, and recent designs have made it large: one register now holds several hundred values. The gain is that a single instruction stands for all of that arithmetic, so the instruction stream is short relative to the work it represents. The cost is that the gain is proportional to how much of the register an instruction actually uses.
The RISC-V vector extension is length-agnostic [ 27 ] . Throughout, vlmax is the largest number of elements a register holds, 512 in FP32 here, and v ​ l vl the active length of an issued instruction. With registers this long the scalar core must supply addresses, loop bookkeeping and configuration changes fast enough to keep a very wide back end busy. Decoupled vector architectures [ 28 , 29 ] let it run ahead, but the supply problem returns whenever v ​ l vl is low, because each instruction then buys less work.
The processor studied here, EPAC [ 17 ] , has registers of 16 384 16\,384 bits. That is 32 × 32\times the register of current commercial RVV silicon [ 30 ] and of A64FX [ 14 ] , at the long end of open RVV designs [ 31 , 32 , 33 ] , and equal to the 256 × 64 256\times 64 -bit registers of NEC’s SX-Aurora [ 15 ] . Section VI-A describes it.
III Characterising the Stock Kernel
This section measures where the stock kernel’s cycles go on the chip, region by region, and separates two limits that a whole-kernel number does not distinguish. The score product runs at the full register width and is held back by its access pattern. The value product has no access-pattern problem and is held back by its vector length. Each calls for a different remedy, and the two that follow are the subjects of Sections IV and V .
Our starting point, the stock kernel , is the FlashAttention-2 [ 19 ] forward pass of PyTorch’s CPU backend [ 34 ] : its blocking, loop order, data layout and online-softmax recurrence, unchanged. We start from FlashAttention-2 because the versions after it are specific to GPUs: FlashAttention-3 [ 20 ] is built on warp specialisation and asynchronous copy engines, and FlashAttention-4 [ 21 ] on tensor cores whose throughput has outgrown their exponential units. Neither mechanism exists on a vector unit. PyTorch has no vector backend for RVV, so we ported the kernel by implementing the vector primitives it calls with RISC-V vector intrinsics, keeping their structure: FP32 inner kernels, a polynomial approximation of the exponential because the hardware has none, and the row maximum and row sum as vector reductions. III-B Wide vectors, strided operands: the score product
gemm_qk sweeps the key axis, so B k ​ v B_{kv} and not d d sets its vector length. At B q = 128 B_{q}=128 , B k ​ v = 512 B_{kv}=512 the measured average v ​ l vl is 512, the full architectural width, so vector length is not what limits this region. The access pattern is. Computing 𝐐 i ​ 𝐊 j ⊤ \mathbf{Q}_{i}\mathbf{K}_{j}^{\!\top} needs 𝐊 j \mathbf{K}_{j} transposed, and 𝐊 \mathbf{K} is stored with d d contiguous, so walking the contraction axis steps by the row pitch, 256 bytes at d = 64 d=64 , a separate cache line per element. Read in place, without packing, 88.9% of the region’s vector memory instructions are strided. A strided access costs 128–512 cycles at full length where a unit-stride one costs 32–128 (Table IV ), so the region pays for the class of its instructions, not their count.
Packing solves the strided case. Copying the key block into a contiguous buffer before the product leaves the arithmetic and the vector length untouched and replaces almost every strided load with a unit-stride one. It makes gemm_qk 2.38 × 2.38\times faster. Packing is performed by the matrix-multiplication routine the kernel calls, in every arm, so every result below includes it; it is long-established [ 35 , 36 ] and not the subject of this paper.
III-C Contiguous operands, short vectors: the value product
gemm_pv has no access-pattern problem. Its first operand was written by the kernel moments earlier and is unit-stride by construction; its second, 𝐕 j \mathbf{V}_{j} , is read along the contiguous head dimension. Both operands are already contiguous along the axis the product sweeps, so packing has nothing to offer here. What limits the region is that the product is untransposed, which makes d d its vector axis: its instructions request 64 elements from registers that hold 512, so the region runs at an eighth of the architectural width whatever the block size, and no block size changes d d . Against gemm_qk at the same tile this is the cleanest contrast available: two dense products over the same tile, differing in which axis each sweeps. The width is fixed by the loop shape, so the remedy is a different axis, which Section V supplies.
IV A Long-Vector Softmax
This section leaves the traversal of Section III alone and works on the softmax. The region evaluates an exponential in software, and its cost on this machine turns out to be the polynomial’s coefficients rather than its instructions. Two changes follow: the coefficients move into scalar registers, and the three passes over a score row fold into one. Section IV-D gives what they are worth together and the limit they run into.

IV-B The constants were vectors
The softmax region reads each score row to find its maximum, again to exponentiate and again to sum, then writes it back. The trace nevertheless counted 62 416 62\,416 vector memory instructions for the region and 126.1 MB moved, against 13 264 13\,264 and 25.4 MB once the coefficients were moved into scalar registers and nothing else changed. The difference is 24 memory instructions on every one of the 2,048 calls, and it was spill traffic.

Here it is not: the seven coefficients held that way are seven registers live across the whole polynomial, competing with the tile data and the running state for the 32 the compiler allocates, and the allocator spills [ 40 ] . The spilled constants are reloaded on every call, which is the excess the trace had found. No single instruction can take the coefficient from a scalar register instead, because the scalar operand of every .vf multiply–add ( vfmacc , vfmadd and their negated forms) is a multiplicand, while Horner’s rule needs c j c_{j} as the addend. A shorter polynomial could relieve the pressure. Degree 4 holds five coefficients rather than seven and may fit, but it pays in accuracy and leaves the mechanism in place, since each remaining c j c_{j} is still a live vector register. Equation ( 5 ) leaves the accuracy alone and holds none of them, at one extra instruction per step.

IV-C A fused traversal removes what remains
With the spills gone, the region’s remaining traffic is its own structure: it reads each row of the score tile to find its maximum, again to exponentiate, and again to sum. Holding the row in a vector register across all three passes is possible only because a row of B k ​ v ≤ vlmax B_{kv}\leq\textup{{vlmax}} elements fits in a single register, so the maximum, the exponential and the sum all see it without a reload. Memory instructions fall by a further 30.9%, the two loads per call the algorithm predicts, and moved bytes by a third. Arithmetic falls by 9 instructions per call and the other classes by 10, almost all of them moves and configuration changes (Table I ). The region’s cycles fall by 1.62 × 1.62\times .
IV-D The ceiling
Together the two changes reduce the softmax region’s cycles by 2.49 × 2.49\times and the whole kernel’s by 1.27 × 1.27\times . The softmax is then a fifth of the budget, so removing it entirely would buy at most 1.24 × 1.24\times . Further work inside the softmax is not where the remaining time is.
The fused traversal also carries a precondition. Folding three passes into one keeps a row of the score tile in a register between them, so it requires B k ​ v ≤ vlmax B_{kv}\leq\textup{{vlmax}} and the saving disappears above that. The natural layout’s best key block is 512, exactly vlmax on this machine, so the optimisation applies at the measured optimum and not beyond it. The transposed form of Section V has no such precondition: its vector length is B q B_{q} , it accumulates down the key rows, and no row of the tile is ever held resident.

V Reorienting the Vector Axis
This section transposes every term of the recurrence. Section V-A gives the transposed form and what changes in each region. Section V-B treats the softmax, where the change is structural rather than a matter of width: two classes of instruction leave the region. Section V-C gives an instruction-count model of when the transpose wins.
V-A The transposed formulation
At the natural layout’s own best tile, B k ​ v = 512 B_{kv}=512 , gemm_qk and the softmax already run at the register width (Table II ). gemm_pv cannot: it takes its length from d d (Section III-C ), and its average v ​ l vl stays near 64 at every tile in Table II .
What decides which axis each region sweeps is the order in which the kernel walks the tile, and Algorithm 1 never says what that order must be. So we transpose the two matrices the kernel builds:
𝐒 i ​ j ⊤ = α ​ 𝐊 j ​ 𝐐 i ⊤ , 𝐎 ~ i ⊤ = 𝐕 j ⊤ ​ 𝐏 ~ i ​ j ⊤ . \mathbf{S}^{\!\top}_{ij}=\alpha\,\mathbf{K}_{j}\mathbf{Q}_{i}^{\!\top},\qquad\tilde{\mathbf{O}}^{\!\top}_{i}=\mathbf{V}_{j}^{\!\top}\tilde{\mathbf{P}}^{\!\top}_{ij}.
(6)
The algorithm is unchanged: every product accumulates in the same order, and the softmax computes the same maximum and sum, now vertically, down the key rows of the tile (Section V-B ). Figure 2 shows one tile in each orientation. The new shapes change four things.
The score tile is now B k ​ v × B q B_{kv}\times B_{q} , so a row of it holds queries instead of keys. That is where the vector length now comes from.
𝐊 j \mathbf{K}_{j} is now read in the orientation it is stored in, and 𝐐 i \mathbf{Q}_{i} is the block read across the stride. So 𝐐 i \mathbf{Q}_{i} is what the matrix-multiplication routine packs, on every call as it packed 𝐊 j \mathbf{K}_{j} before, and the strided loads of packing now scale with B q B_{q} instead of B k ​ v B_{kv} .
We never build 𝐕 j ⊤ \mathbf{V}_{j}^{\!\top} . Transposing a product swaps which operand supplies the vector axis, and neither operand has to move for that, so the value product reads 𝐕 j \mathbf{V}_{j} where it already sits and sweeps B q B_{q} .
The output comes out transposed, and putting it back is almost free. The kernel already walks the output once to divide by ℓ i \boldsymbol{\ell}_{i} , so that pass now reads unit-stride and writes strided instead. It adds 9 to 13% to the normalisation region, which is under half a percent of the kernel.
This change is outer-loop vectorisation [ 24 ] : the query loop carries the softmax state, and making it the vector loop turns that state into a vector. With 512 elements in a register, carrying it as a vector is exactly what removes the reductions. Algorithms 1 and 3 are the same kernel in the two orientations. One parameter, B q B_{q} , now sets the vector length of every region, replacing B k ​ v B_{kv} and d d . The two reduction lines of the first become the two elementwise lines of the second. Table II shows this and measures it.
The bottom half of Table II matters as much as the top. At B q = 128 B_{q}=128 the reoriented kernel runs every region at 128, which is worse than the 512 the natural layout reaches in two of its three regions. Reorientation does not make the kernel faster at every tile. It puts the vector length of every region under one parameter, B q B_{q} , and everything then depends on setting that parameter to the register width. At B q = 128 B_{q}=128 the reoriented kernel is slower than the fused one; at B q = 512 B_{q}=512 , the register width, it is 1.43 × 1.43\times faster.

V-B Softmax becomes vertical
The softmax is where the change is structural rather than merely wider: two classes of instruction leave the region altogether. In the natural orientation a query row occupies B k ​ v B_{kv} contiguous elements, so rowmax \mathrm{rowmax} and rowsum \mathrm{rowsum} are reductions along a vector register and the running state 𝐦 i , ℓ i \mathbf{m}_{i},\boldsymbol{\ell}_{i} is a pair of scalars per row. Transposed, a key row occupies B q B_{q} contiguous elements and the same two quantities are indexed by the query axis, so they become vector registers and the reductions become elementwise accumulations down the key rows. The reoriented softmax makes two passes over the tile,

Figure 2 shows the two directions.
Two costs disappear and a third shrinks. The two reductions per query row per key block are gone and so is the move that pulled each reduction’s result into a scalar register. The third is 𝝆 i \boldsymbol{\rho}_{i} . Both forms compute it once per query row per key block, but the natural orientation holds the running maximum as one scalar per row and evaluates each 𝝆 i \boldsymbol{\rho}_{i} as a separate scalar exponential, while the transposed form holds it as a vector and covers a whole query block with one vector exponential.
One cost is added. The two passes read each score twice where the fused traversal read it once, which at each arm’s own best tile is 10% more memory instructions in the region.
V-C When the transpose wins
The transpose changes no arithmetic. It changes how many vector instructions carry it. For a block no longer than vlmax a row is one vector, so a region’s instruction count is the number of rows it walks times what it issues per row. Each region then compares in its own way, natural over reoriented.
Value product. Both forms issue the same instructions per row, but the natural form’s rows are d d long and the reoriented form’s B q B_{q} , so the ratio is
B q d . \frac{B_{q}}{d}.
(8)
This is the only place the head dimension enters. The transpose wins here whenever B q > d B_{q}>d , and the gain falls as d d grows.
Score product. Again the instructions per row are the same; the rows are B k ​ v B_{kv} long in one form and B q B_{q} in the other, so the ratio is B q / B k ​ v B_{q}/B_{kv} . It is a trade of one block length for the other and is even when the two are equal.
Softmax. The natural form walks N 2 / B k ​ v N^{2}/B_{kv} query rows of B k ​ v B_{kv} elements, the reoriented form N 2 / B q N^{2}/B_{q} key rows of B q B_{q} . Per row both do the same elementwise work E E : scale, maximum, subtract, exponential, accumulate and store. Both rescale the accumulator, which is the value product ratio again and is counted there. Both compute 𝝆 i \boldsymbol{\rho}_{i} once per row, in scalar code in one form and as one vector exponential per tile in the other, and neither is counted here.
What differs is the price of the maximum and the sum. In the natural orientation a row is one vector, so both are reductions, one vfredmax and one vfredusum , each followed by a move to a scalar register. Transposed, a row holds different queries, so the maximum is a vfmax and the sum a vfadd down the key rows, and nothing leaves the vector registers. The transpose pays two extra memory instructions per row instead, because it reads the score tile a second time and writes the scaled scores back before it:

VI Methodology
VI-A Target platform
EPAC [ 17 ] was developed within the European Processor Initiative: an in-order RISC-V scalar core driving a decoupled vector unit whose registers hold 16 384 16\,384 bits. Table III lists the parameters the kernel design depends on, and four of them shape everything below.
Addressing is at cache-line granularity . A unit-stride access uses every element of each 64-byte line it brings in. An access whose stride is larger than a line uses one element per line, so it brings in sixteen times more data than it consumes. There is no operand chaining , so a dependent instruction waits until its producer has retired every element and the cost of a sequence tracks its dependence depth, at the latencies of Table IV . The register file is small in registers and large in bytes : the compiler allocates 32 architectural registers and 40 physical registers, so a kernel holding too many live values spills [ 40 ] , and one spilled register at full length is 2 KB of traffic. There is no hardware exponential , so the softmax evaluates a software polynomial whose cost is its instruction count and dependence structure, both under the kernel’s control.
The vector unit implements RVV 0.7.1 [ 41 ] , the draft current when it was designed; a successor implements the ratified 1.0 [ 17 ] . Nothing below depends on the difference: every instruction the kernels use has a 1.0 counterpart, and the limits Section III identifies come from loop lengths, which no 1.0 feature changes.

VI-B Measurement targets and instrumentation
Cycle counts come from two targets of the same design, the EPAC chip at 1 GHz and an FPGA implementation of the same design at 50 MHz (Table III ). Both implement the same processor revision, so a change that helps on one is expected to help on the other; they differ in clock and in sustained memory bandwidth per cycle. The 64 B/cycle ceiling is fixed by the cache-line interconnect; the FPGA sustains about half of it, while on the chip the SerDes link to the DDR4 bank limits at 1 GHz and sustains roughly a tenth. The chip therefore charges far more for memory traffic relative to arithmetic than the FPGA does, which Section VII-B measures directly. No result below is averaged across the targets and no table mixes them; results lead with the chip. Every arm is vectorised, so no figure below is a speed-up over scalar code. The absolute reference is the machine’s peak of 32 FP32 FLOP/cycle, against which the stock kernel reaches 16.2%. All measurements are FP32, on one core and one attention head, at d = 64 d=64 and N = 1024 N=1024 unless stated.
Instruction-level data comes from the RAVE QEMU plugin [ 42 ] , which reports per-region instruction mixes, effective vector lengths and moved bytes. It models register width only: no caches, no pipeline, no latencies. Its role is to establish which instruction stream the compiler and the intrinsics emit, which the hardware counters cannot show. Cycles and retired instructions are read per region through a tracing interface [ 43 ] , each reported against total cycles for the same region, because an absolute instruction count can move opposite to performance when a kernel does less work in a denser issue stream.

VII-B The two targets rank the changes identically
Table V puts the FPGA beside the chip, each arm at its own fastest tile on each. Every step is larger on the FPGA, uniformly and by a growing margin, while the ordering and the winner are the same on both.
The cause is in the measurement rather than inferred. Table VI divides chip cycles by FPGA cycles for the same arm, tile and region, which says how much more each kind of work costs on silicon. Two regions bracket the rest. gemm_qk is almost all arithmetic and costs about 1.6 × 1.6\times more on the chip, for all four arms. The normalisation pass is almost all memory traffic and costs about 3.7 × 3.7\times more, likewise for all four.
The softmax walks across that bracket as it is optimised, from 1.17 × 1.17\times for the stock kernel to 2.98 × 2.98\times reoriented. Each change removes vector instructions and spill traffic that both machines charge for, and what is left behind is a read and a write of the score tile, which the chip charges three times as much for. The better the kernel, the more of its remaining cost is memory and the more the two targets diverge. That is why the FPGA scores every step higher and why the chip figure is the one to quote.

VIII Discussion
What the result is conditional on. Equations ( 8 ) and ( 9 ) state the condition: the reoriented form wins in the value product whenever the query block is longer than the head dimension, in the score product once it is also longer than the key block. The width is what makes the orientation a first-order choice. On a short register every block spans many vector instructions, so the length ratios tend to one and the reductions are a small share of the instruction stream. The result therefore scales with register width: it is largest on the longest machines, and those are the machines on which attention is now expected to run. The result also assumes a long query block. It concerns prefill and training, where B q B_{q} can be set to vlmax , and not autoregressive decode, where a query block holds one row or one query group and the natural orientation is the right one.
Where the remaining headroom is. The reoriented kernel reaches 29.7% of peak, so a factor of three is unclaimed, and the regions do not share it evenly. gemm_pv is at 46.4% of peak and gemm_qk is now the largest single region at 35% of the budget, while the softmax is a quarter of it and removing it entirely would buy at most 1.33 × 1.33\times . The score product is the next target. It is a dense product whose operands are already packed, so what it leaves on the table is in the matrix-multiplication routine itself: register blocking and an inner kernel tuned for a decoupled unit without chaining. That work applies to both orientations alike and so cannot flatter either.
IX Related Work
Attention kernels. FlashAttention [ 18 ] removes the quadratic memory cost by tiling both operands and carrying the normalisation as an online recurrence [ 26 ] ; later versions improve parallelism on GPUs [ 19 ] and exploit asynchrony and low precision [ 20 ] . FlashAttention-4 [ 21 ] meets the problem of Section IV on GPUs whose matrix units have outgrown their exponential units, computing part of the exponentials as a polynomial on the FMA pipes and skipping most rescalings of the running maximum. That line of work treats the traversal as fixed. CPU implementations target short-vector SIMD [ 44 , 45 ] and vectorise along the head dimension, where any axis fills a register.
Attention on RISC-V vector processors. Titopoulos et al. [ 22 ] vectorise FlashAttention for RVV along the key axis, with the maximum and sum as vector reductions and a bit-level approximation of the exponential, and evaluate registers of 32 to 128 elements in simulation. FlashAttention-V [ 23 ] meets the mismatch this paper addresses from the other side: once the register outgrows the head dimension it packs several heads into one register, keeping the reductions, and so extends to decode, where a query block is a single row, at the cost of needing vlmax / d \textup{{vlmax}}/d heads; it is evaluated in simulation up to 8192 bits and on a 256-bit board. Reorienting along queries needs no extra heads and removes the reductions but needs a long query block, so the two apply to different cases. VEXP [ 46 ] adds an exponential instruction to a RISC-V core rather than computing it in software.
Long-vector architectures. RISC-V vector implementations span a wide range of register widths [ 47 , 31 , 32 , 33 , 16 , 30 ] . SX-Aurora [ 15 ] and the processor studied here [ 17 ] sit at the long end of that range.
Restructuring kernels for long vectors. Sparse matrix products on long-vector machines needed a different blocking and accumulation structure rather than a better-tuned loop [ 48 ] ; there the vector length was too short because the data was sparse, here because the implementation chose the wrong axis of a tile that is large in both.
X Conclusion
The FlashAttention recurrence fixes which values a kernel computes. It does not fix the orientation in which they are computed, and on a processor whose registers hold 512 single-precision elements that freedom is worth 1.43 × 1.43\times over a fused natural-orientation kernel sharing the same exponential and the same matrix-multiplication routine. Transposing the score tile and the running output puts every region under one parameter, the number of queries in a tile, and turns the softmax’s per-row reductions into elementwise accumulations. With the exponential’s coefficients moved out of the vector registers where they spilled, the kernel is 1.84 × 1.84\times - 2.08 × 2.08\times faster on EPAC silicon; an FPGA of the same design ranks every change identically.
