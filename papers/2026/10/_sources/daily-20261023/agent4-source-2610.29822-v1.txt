Abstract
As coding agents become more capable, developers increasingly use them to fix bugs
through multi-turn interactions. Existing benchmarks do not adequately cover this
scenario. Most present a complete issue report in a single turn without interaction.
Their evaluation can produce both false positives and false negatives, accepting
incorrect patches or rejecting correct ones. We introduce UserSWE for evaluating
coding agents’ ability to fix repository-level bugs through multi-turn interactions
with dynamic users and execution-grounded verdicts at every turn. Its construction
pipeline turns repository history and existing single-turn benchmarks into multi-turn
tasks. At each turn, information pools constrain what the simulated user can reveal, while a persona chain sampled from a transition model calibrated on 20,859 development sessions governs how it speaks. Tests run after every turn, and a pair
of agents from different model families writes and gates each verdict, using test
results as primary evidence and model judgment only for aspects the tests cannot
resolve. We evaluate eleven agents on 72 tasks from 42 repositories and find that
agent rankings change with the interaction budget. Claude Fable 5.1 resolves the
most tasks in one turn, GPT-6-Astra resolves the most by the eighth turn, and Claude
Opus 5 leads at most intermediate budgets. These results indicate that single-turn
performance is insufficient to characterize interactive coding ability.

 1 Introduction
 Figure 1: Existing multi-turn benchmarks keep the simulated user in one persona, while in the real development sessions we measure a developer’s style shifts from turn to turn.
On the same date-off-by-one bug, the static simulator phrases every turn as precise guidance, while the UserSWE simulator opens on a vague complaint, guesses a wrong cause, and reaches guidance only at the third turn.
AI programming assistants are deployed at scale and used daily by developers ( Liang et al., 2024 ) .
Their form has evolved from autocompletion to context-grounded conversation, and then to agents that navigate repositories, edit files, and run tests on their own — a practice popularly called vibe coding ( Ross et al., 2023 ; Yang et al., 2024 ; Sarkar and Drosos, 2025 ) .
Developers pose follow-up questions and refine their requests in response to intermediate model outputs ( Barke et al., 2023 ; Ross et al., 2023 ) , where initial requests are often incomplete and gradually clarified across turns. Studies of agents in real-world settings further confirm this same iterative pattern holds across entire tasks ( Siddeeq et al., 2026 ; Baumann et al., 2026 ) .
As a representative scenario, debugging with an agent has now become a standard conversational workflow for developers.
However, prevailing benchmarks do not measure how well an agent works in this scenario for two main reasons.
One is that most use a single-turn setup, handing the agent everything at once and asking for a correct patch in return, so the agent is never put in the conversation where the work actually happens.
The few that do run several turns stay static, releasing the information in a written order or phrasing every turn in one fixed conversational style, which leaves the agent talking to an unresponsive mechanism and not to a simulation of a developer.
Figure  1 sets a static user beside a dynamic one on the same task.
The other concerns multi-turn judging, where every intermediate turn calls for independent assessment, but standard tests can only provide factual execution evidence, and unrestricted LLM judges are prone to making inferences beyond what results actually demonstrate.
For both reasons, a benchmark that measures coding agents’ abilities in conversation is still missing.
To address this, we propose UserSWE, which settles where the tasks come from, where the turns come from, and how each turn is judged.
The first is a construction pipeline that produces multi-turn tasks along two routes.
One route mines a repository’s own history for paired issues that a maintainer publicly recorded as linked.
The other takes an instance of an existing single-turn benchmark and stages it as a conversation.
As we continue running the pipeline along these two routes, it consistently generates new and up-to-date tasks.
The second is a method for simulating the user across the turns of a conversation.
We calculate a persona transition matrix on 20,859 real development sessions from an internally deployed commercial coding assistant, and we write each turn’s utterance from that matrix together with the information pools of the task, so the persona an agent meets becomes dynamic as the session goes on.
For each task we draw the whole chain in advance, which ensures any agent on the same task meets the same user.
The third is an evaluation framework , which enables the coding agent to operate under constraints, with dual agents judging its generated outputs based on evidence.
The framework sets rules that prevent coding agents from receiving credit beyond their demonstrated ability.
Based on tests run after every turn, a Judge from one family writes the verdict, and a Reviewer from another family clears it before it counts.
We select 72 tasks from the pipeline as UserSWE and evaluate agents on it.
The evaluation on UserSWE reveals behavior that a single-turn evaluation cannot show.
Claude Fable 5.1 resolves the most tasks within a single turn, 31.9%, and still finishes second on the length-discounted pass rate, behind Claude Opus 5, which reaches a similar place in fewer turns, 2.99 against 3.14.
GPT-6-Astra resolves the most tasks of any agent by the eighth turn, 81.9%, and places fourth once the turns it spends getting there are discounted.
In this paper, we make the following contributions.
 (1) A construction pipeline. 
It builds multi-turn tasks from repository evidence and existing single-turn benchmarks.
 (2) A multi-turn user simulation. 
We introduce a user simulator with dynamic personas grounded in real development conversations.
 (3) An evaluation framework. 
We propose a dual-agent judging evaluation framework complemented by a suite of supporting mechanisms, such as equivalent pass testing.
UserSWE will be released along with the evaluation framework.
 2 Related work
Table  1 compares UserSWE with existing coding-agent benchmarks. Below, we discuss two complementary lines of related work.
Multi-turn benchmarks and simulated users.
Multi-turn evaluations must specify both what the user reveals and how the user speaks. SWE-Interact releases a task’s requirements one at a time and uses a fixed, terse senior-developer persona derived from SWE-chat ( Raghavendra et al., 2026 ; Baumann et al., 2026 ) , while SWE-Together reconstructs a task-specific simulator from a recorded session and triggers utterances according to the live trajectory ( Wu et al., 2026 ) . These approaches condition information release on the trajectory but do not vary the user’s voice according to a measured distribution of developer personas. More broadly, simulated users can diverge from real developers, and persona choice can substantially change measured performance ( Seshadri et al., 2026 ; Zhou et al., 2026 ; Truong et al., 2025 ) . UserSWE samples a persona chain from real development sessions and generates an information pool for each task, which helps simulate users naturally.
SWE benchmarks and evaluation reliability.
SWE-bench established issue-level, execution-based evaluation for coding agents ( Jimenez et al., 2024 ) . Later work addresses task contamination and freshness through larger, private, or continuously refreshed task collections ( Xue et al., 2026 ; Liang et al., 2025 ; Deng et al., 2026 ; Zhang et al., 2025 ) ; SWE Context Bench is closest to our mining route but poses related instances independently ( Zhu et al., 2026 ) . A parallel line shows that verdicts can fail because tests are too loose or tight, LLM judges exhibit bias, or the evaluation harness can be gamed ( Xue et al., 2026 ; Zheng et al., 2023 ; Wataoka et al., 2024 ; Wang et al., 2026 ) . Panel-based judges and rule-based checkers improve reliability but remain imperfect ( Verga et al., 2024 ; Lù et al., 2025 ) . In the multi-turn setting, SWE-Interact still verifies only the final solution and rubric-scores intermediate turns ( Raghavendra et al., 2026 ) . UserSWE executes tests after every turn and uses a cross-family writer/reviewer gate, grounding each verdict in execution and reserving model judgment for evidence the tests cannot cover.

 3 Preliminaries
The dominant executable format for software-engineering evaluation poses one issue as one task and grades the returned patch by executing tests ( Jimenez et al., 2024 ; Deng et al., 2026 ) .
Given an issue and the repository state b at the commit preceding its fix, the agent answers once with a patch \hat{g} .
Write t(s)\in\{0,1\} for the outcome of test t in workspace state s , and let s\oplus p apply patch p to s .
The task also carries the maintainer’s own fix, the gold patch g , and two sets of tests from b and b\oplus g ,
 t(b)=0\ \ \text{and}\ \ t(b\oplus g)=1\quad\forall\,t\in F,\qquad\qquad t(b)=t(b\oplus g)=1\quad\forall\,t\in P, 
 (1) 
the fail-to-pass set F , which the fix has to turn green, and the pass-to-pass set P , which it must not break.
A patch \hat{g} resolves the task when t(b\oplus\hat{g})=1 for every t\in F\cup P , and the reported score is the fraction of tasks resolved ( Yang et al., 2024 ) .
 4 UserSWE
We introduce UserSWE, which evaluates agents on issue fixing inside a multi-turn conversation and so measures coding ability more completely than a one-shot format can.
Where Section  3 is settled in a single exchange, an agent here works on the issue over several turns, each turn answering what the user has just asked for, and we check the fail-to-pass and the pass-to-pass set after every one of those turns.
Turning both sets green in as few turns as possible is what UserSWE credits as strength at resolving code issues interactively.

 4.1 Data Construction
We mine issue cascades and single issues from two sources and select the suitable ones as tasks.
The first route searches repository histories for two issues explicitly linked by a maintainer.
Each side has a merged fix with tests, giving the task two related acceptance points.
The second route takes tasks from published single-turn benchmarks, preserving their repository state, gold patch, tests and original acceptance point while changing how their information is released across a multi-turn conversation.
Both routes then turn each task into an information pool.
The pipeline extracts symptoms from the issue report and uses the gold patch to construct correct or wrong directions about the cause, with the wrong direction later shared by the off-target and wrong personas.
A cascade also carries follow-up information for its second issue.
The pool is frozen before evaluation and checked for identifiers introduced by the gold patch, with an additional cross-phase scope check for cascades.
Agents evaluated on the same task therefore draw from the same frozen candidate information pool, preventing differences in pool construction from confounding the comparison.
Before admission, each task passes both mechanical and human checks.
The framework reruns the fail-to-pass and pass-to-pass tests in the evaluation container, verifying that the fail-to-pass tests fail at the base state and pass after the gold patch is applied, while the pass-to-pass tests pass in both states.
Appendix  A details how tasks from both sources are converted into information pools and admitted as executable tasks.
 4.2 Multi-turn Interaction
Section  4.1 fixes what the simulated user may say, but not which item should be selected at each turn or the voice in which it should be expressed.
We handle these questions separately, first selecting the content through a release policy and then rendering it through a conversational persona model calibrated on real development sessions.
After each turn, the simulated user selects guidance from the information pool according to the agent’s response and the canonical test results.
The information selection process follows a fixed priority hierarchy designed to mirror the logic of natural developer interactions. If the agent poses a direct question, the simulated user responds with a direct answer. Otherwise, it selects content in descending order of priority: the most severe user-observable blocking failure, an unaddressed core business boundary, or a secondary edge case. This hierarchy governs what information the user simulator releases at the current turn.
Once the content is selected, the framework must decide how to express it.
The expression of the developer varies between people and between turns of the same session.
Its two common components align with the two kinds of content in the information pool, namely how a developer describes what was observed and whether they offer a view of the cause .
We therefore factor the simulated user along two axes.
Clarity records whether the symptom is stated precisely or vaguely, and veracity records whether the user offers no view, a correct one, an off-target one, or a wrong one.
Crossing these axes yields eight conversational personas, and Table  2 presents the same request phrased in each of them.

We do not assume the eight cells occur uniformly.
From 20,859 real development sessions from an internally deployed commercial coding assistant, we measure the opening persona and its turn-to-turn transitions.
Of these sessions, 13,530 change code, and the eight cells account for 98.65% of them, with 52.98% opening on a clear symptom and no view of the cause.
The transitions form a family of matrices conditioned on the opening persona rather than one global matrix.
We pseudorandomly draw a complete persona chain for each task in advance so that different agents on the same task face the same changes in the user.
The selected content is rendered in the persona assigned to that turn.
Appendix  B gives all eight opening-conditioned transition matrices and the persona design.
The information pool fixes what may be said, the release policy selects what this turn says and the frozen persona chain fixes how it is said, which completes the multi-turn interaction.
What remains is how each turn is judged, which is the next subsection.
 4.3 Evaluation
A multi-turn evaluation framework entails two dimensions of freedom, each causing evaluation misjudgments when improperly calibrated.
The degree of freedom allowed by the framework, when set too loose or too tight, renders the evaluation scores unreliable.
The degree of freedom granted to the agent, when set too loose or too tight, prevents it from demonstrating its true capabilities.
Our evaluation framework for UserSWE addresses these two dimensions separately.

Freedom for the agent.
Deciding whether a solution is correct can fail in either direction.
Tests are written around the maintainer’s own fix, so they may reject a patch that implements the behavior without converging on the interface of the gold patch, producing a false negative.
In a neighboring setting this is measurable, where rule-based evaluation of agent trajectories recovers only 55.9% of the runs an expert calls successful, because the check demands an exact match and turns away trajectories that differ in ways that do not matter ( Lù et al., 2025 ) .
At the other end, tests weak enough to pass a patch that fixed nothing give a false positive ( Xue et al., 2026 ) .
Moving the primary signal off test execution and onto a model’s reading of whether the semantics are satisfied ( Wu et al., 2026 ) widens the false positives.
Admitting only the verbatim passing of the shipped tests ( Jimenez et al., 2024 ; Deng et al., 2026 ) widens the false negatives.
In UserSWE the framework may, on the basis of what the agent actually implemented, propose a change to a test and count a pass on the genuinely modified test as an equivalent pass , which is EqualPass in Algorithm  1 .
How much capability it brings to bear is likewise not capped, since a setting that gives no tools and asks for a patch from the issue body alone cannot measure the difference between scaffolds ( Jimenez et al., 2024 ; Yang et al., 2024 ) .
We block its access to the assets that would settle the task for it, and restrict outside lookup where that is necessary.
Freedom for the instrument.
The freedom given to the simulated user and the Judge does not decide what is correct.
It decides whether the instrument has itself become a variable.
A simulated user left to improvise drifts with whichever model it runs on, so one task stops being the same task across two evaluations ( Raghavendra et al., 2026 ) .
A simulated user whose every line is written in advance is not a user.
We freeze the agenda and not the wording.
Which persona holds at which turn and which facts may be said are fixed by the persona chain and the information pools, and the opening request is fixed outright so that every agent starts from the same point.
Which fact to raise at a later turn and how to phrase it is left to the simulated user.
The Judge side is the same problem seen from the other end.
A language model scores its own family’s output too highly ( Zheng et al., 2023 ; Wataoka et al., 2024 ) , and a panel drawn from disjoint families brings that bias down ( Verga et al., 2024 ) , so we chain two families.
The Judge writes a verdict and a Reviewer from a different family may rewrite it before it takes effect, with the two swapped between tasks.
This is an inline gate rather than a post-hoc audit, and every judgment the framework issues has passed through both.
Both halves rest on the same thing.
A verdict counts only where the tests have been run and have said so, since the outcome the loop returns is the outcome of executing them, and a model’s reading enters where the tests are silent rather than where they disagree with it.
Metrics.
A multi-turn setting admits a quantity the one-shot format has no room for, namely how much of the turn budget an agent had left when it succeeded.
Beyond the plain resolve rate we therefore report the L ength- D iscounted P ass R ate (LDPR), which is counted as
 \mathrm{LDPR}\;=\;\begin{cases}(K+1-k)/K&\text{tests all pass,}\\[2.0pt]
0&\text{otherwise,}\end{cases} 
 (2) 
where k is the weighted number of turns used; a turn without a code edit counts as half a turn.
Agents that resolve a task in fewer conversational turns receive higher scores, while those that fail to complete the task within the predefined maximum turn limit are assigned a score of zero.

 5.1 Main results
We select 72 tasks from the continuously running pipeline.
Appendix  A details task construction and admission.
We evaluate 11 agents on UserSWE, each a model on a scaffold as listed in Table  13 . Of these tasks, 22 are mined from open-source repository history and contain two issues, while the other 50 are converted from published single-turn benchmarks.
The evaluation framework uses two different model families for user simulation and result adjudication.
The judging and review sides are rotated between gpt-5.6-sol on the Codex scaffold and opus-5 on the Claude Code scaffold.
We selected them because they represent the most capable cross-family model combination that can be deployed stably at present. The framework is not bound to these two specific models, and either can be replaced with suitable alternatives.
Information pools and persona trajectories are drawn per task in advance, so every agent is evaluated fairly on the same task.
The two subsets run under different turn budgets, K=5 for a single-issue task and K=8 for a two-issue one, since a second acceptance point needs the extra turns to be reached at all.
Table  3 reports results on UserSWE, the share of tasks resolved within the first k turns for k from 1 to 8, together with LDPR (Equation  2 ) and the mean number of turns used.
More detailed results, such as costs, are in Appendix  D , and Appendix  E follows individual sessions case by case.

 5.2 Analysis of the multi-turn design
 5.2.1 Multi-turn against single-turn
As the main table shows, the agent that is best at the opening is not the agent that is best at the end.
Claude Fable 5.1 resolves more tasks within the first turn than any other agent and still finishes behind Claude Opus 5 on LDPR.
GPT-6-Astra resolves more tasks by the eighth turn than any other agent and places fourth on LDPR.
A single-turn evaluation cannot show either of these, because it observes one point of the curve and reports it as the whole of an agent’s ability.
 Figure 3: The order of the four leading agents on published single-turn tasks, and how that order changes as the turn budget grows on UserSWE.
We look more closely at the four agents that lead on LDPR.
Figure  3 tracks the order they stand in as the turn budget grows.
Over eight budgets the four take six different orderings between them, and three of the four lead at some budget.
GPT-6-Astra is last of the four through the third turn and catches up to lead by the eighth.
They end within six points of each other, between 76.4% and 81.9% resolved by the eighth turn, so these are reorderings among agents of comparable final ability.
We also compare these four agents on a separate collection of 42 single-turn tasks drawn from SWE-bench Pro and SWE-bench-Live.
Claude Fable 5.1 ranks first at 78.6%, well ahead of Claude Opus 5 at 64.3%, GPT-6-Astra at 61.9% and Grok-4.6 at 59.5%.
Fable’s large single-turn margin explains its early lead, but the ordering changes as the turn budget grows.
 5.2.2 Dynamic conversational persona
Most existing benchmarks model the simulated user as a static persona with both clear expression and correct causal views ( Raghavendra et al., 2026 ; Baumann et al., 2026 ) .
That profile opens only 19.03% of the 13,530 observed sessions, and holding it for a whole session is rarer still: 0.72% of sessions stay clear and correct for five consecutive turns on the same issue and 0.24% do so for eight.
Even among the sessions that actually run that long, the shares are 2.81% and 1.86%.
We compare a reference arm that remains clear and correct at every turn with the persona chain. Both arms run the 50 single-issue tasks, which fit a five-turn budget and so isolate the persona from the cascade’s issue-to-issue carryover, and each comparison uses the same task and agent and changes only the user trajectory. Table  4 reports LDPR and mean weighted turns k .
Three of the four agents move the same way, scoring higher and finishing sooner under the clear-and-correct user, and the size of the shift varies widely between them, from 0.020 to 0.076 in LDPR.
The largest is GPT-6-Astra, whose LDPR increases from 0.580 to 0.656 while k decreases from 2.92 to 2.54, and Kimi-K3 moves the other way.
How much an agent depends on precise phrasing is itself a property of the agent, and it shows across all 72 tasks and all eleven agents. Splitting the full set by whether the opening states the symptom precisely or as an impression, the gap between the two halves runs from 0.268 for Claude Fable 5.1 down to - 0.088 for DeepSeek-v4.1-Flash (Appendix  F ).
An idealized user therefore reports a benchmark easier than the one most users present, and it flatters some agents more than others.

Evidence marks a state unsupported by per-item test results or an executed command, guidance a next-turn utterance that breaks the interaction rules, equivalence a mishandled equivalence request, and persona a turn that does not execute the trajectory drawn for it.
Both configurations catch problems that would otherwise take effect under a single Judge.
The two configurations object to different things: evidence accounts for 70.3% of what the Codex Reviewer files, whereas the Claude Code Reviewer splits its objections almost evenly between evidence and guidance, 42.1% and 41.5%.
Overall, 87.4% are rated major or critical, meaning that under the rubric they may change the follow-up, completion state or score rather than wording alone.

 5.3.2 Equivalent passes
Our equivalent-pass mechanism is strictly execution-based. Tests tied to the gold patch’s interface or structure may reject functionally equivalent implementations. We allow targeted rewrites for the tested implementation, but award credit only when the rewritten test passes and still fails at baseline; descriptive claims do not count.

 6 Limitations
UserSWE has three limitations.
 (1) Scale. Multi-turn evaluation runs a full session and reruns tests after every turn, making it more expensive than scoring one patch per task and limiting the released set to 72 tasks. Table  15 reports detailed per-task costs.
 (2) Horizon. UserSWE covers one maintenance episode over one or two issues, from a base commit to a fixed set of acceptance points. It does not cover longer-term work such as building a repository from scratch, which remains a direction for future extensions.
 (3) Session logs. The user model uses opening distributions and turn-to-turn transitions measured from 20,859 sessions collected from an internally deployed commercial coding assistant. Future versions could incorporate additional signals about task types and request phrasing.
 7 Conclusion
We present UserSWE, a benchmark for evaluating coding agents in multi-turn
conversations with dynamic users. We contribute a construction pipeline that builds
multi-turn tasks from repository history and existing benchmarks, a user
simulator with dynamic personas grounded in real development sessions, and an
evaluation framework that anchors cross-family judging and review to executed
tests. Together, these components produce UserSWE, which we use to evaluate
eleven agents on 72 tasks and uncover behaviors that single-turn
evaluation cannot reveal.

Ethics statement
The benchmark tasks are constructed from publicly available issues, pull requests and repository histories, together with previously published benchmarks. Repository-derived materials remain subject to their upstream licenses.

This limits the released behavioral information to what is needed to instantiate the simulator while reducing privacy and security risks associated with development logs.

NECESSARY C1-C3

 Appendix C Evaluation framework


 

The framework separates environment controls, the Judge, the Reviewer and a post-run audit.

 



 C.1 Environment controls





Internal assets.


 

The agent sees the agent-facing task statement and its workspace,
but not the source issue or pull-request records, gold patch, fail-to-pass
tests, acceptance list, phase map, scorecard, Judge–Reviewer records or other
evaluation metadata. These assets are mounted outside the workspace, and tool
controls block direct and indirect access to them.

 





External retrieval.


 

General technical documentation is allowed. The agent may not retrieve this
task’s issues, pull requests, commits, releases, other source versions or
ready-made fixes from code hosts, package registries, mirrors or caches.
External lookups are recorded. A violation is terminal only when
task-specific protected material is returned and used.

next user message. Table  10 gives the action associated

 D.2 Confidence intervals and paired comparisons


 

The sampling unit is the task.
All eleven agents run the same 72 tasks, so every comparison between two agents is paired within the task and the spread of task difficulty drops out of it.
That spread is the larger of the two sources of variation, since the standard deviation of mean LDPR is 0.283 across tasks and 0.073 across agents.
Pairing removes it, which is why every agent is given the same tasks and the same persona trajectories.
