Abstract
Enterprise agents act on documents. Before an agent can follow a policy, answer a compliance
question or file a ticket, some ingestion layer must turn a Word file or PDF into tokens—and
that layer is where an agent deployed in the wild silently loses information. Mature converters
recover text, tables and structure faithfully, so the pipeline looks healthy. We show that one
layer is lost by all of them—the meaning an author encodes in how text looks —and that
the loss makes agents confidently wrong rather than visibly incomplete, which is the
harder failure to detect in deployment.
We build a task from 76 real policy documents: recover the requirements the author singled out
for attention, scored against the file’s own OOXML properties by a deterministic matcher with no
LLM judge. Formatting-blind ingestion collapses from micro F1 0.690 0.690 to 0.150 0.150 (docling) and
0.075 0.075 (plain text), a gap that replicates across six answering models from two vendors—five Claude
models spanning the Opus, Sonnet and Haiku tiers, and OpenAI’s GPT-5.6. The failure is silent in a way that matters for autonomy: an
agent that cannot see the cue guesses, and docling’s false-positive rate on requirements the
author did not flag is four times ours.
A span-level leave-one-out localises the loss to two cues—highlight ( + 0.302 +0.302 ) and colour
( + 0.262 +0.262 ), both p Holm < 10 − 4 p_{\text{Holm}}<10^{-4} —while bold, italic, monospace and strikethrough each
sit within ± 0.003 \pm 0.003 of zero. The same asymmetry appears in PDF. Colour is also the cue no
mainstream converter preserves and no parsing benchmark scores, and it is common: 32.8 % 32.8\% of
6,460 6{,}460 documents carry a deliberate colour or highlight, 10.3 % 10.3\% on an obligation. A
pre-registered test shows that typing a cue for the agent adds + 0.085 +0.085 beyond merely
preserving it ( p Holm = 0.049 p_{\text{Holm}}=0.049 ). We validate the labels against rendered page images
through an independent modality ( κ = 0.72 \kappa=0.72 ) and bound what wording alone can achieve

where this reliability is won or lost, and that the fix is cheap and measurable.
1 Introduction
An enterprise agent deployed in the wild does not read documents; it reads whatever an ingestion
layer hands it. Before it can answer a compliance question, follow an operating procedure, or decide
whether an action is permitted, some converter has turned a .docx or PDF into tokens. That
layer is rarely the object of study, and it is where a large amount of an agent’s practical
reliability is decided.
The failure we report is a property of that layer, and it has the shape that makes agent deployments
hard to trust. It is not an outage and not an empty field. The pipeline reports success, the text
looks complete, and the agent answers fluently and wrongly. Enterprise authors mark obligations
visually—a red requirement, a highlighted exception, a struck-through value that no longer
applies—and every mainstream converter we tested discards that layer while preserving the words
around it. An agent reading the result sees a list of requirements with no indication which ones the
author flagged, and, as we show, it guesses.
Three properties make this a safety-relevant ingestion problem rather than a formatting
inconvenience. First, it is silent : nothing in the pipeline signals that information was
dropped, so no monitor fires. Second, it inverts the usual failure mode: the agent does not
abstain or return less, it asserts more, and its false-positive rate on requirements the author did
not flag rises fourfold. Third, it is common , present in about a third of real
documents, so it is not an adversarial edge case but the ordinary state of enterprise corpora.
The setting is demanding in ways that compound this. Enterprise procedural documents span 50–300
pages and mix formal definitions, step-by-step procedures, compliance rules, exception clauses,
organisational charts, decision flowcharts, timelines and regulatory references—content whose
semantics a human reader partly reconstructs from presentation rather than from wording. Documents
are long enough that fixed-chunk ingestion fragments cross-references a reader resolves globally;
content is heterogeneous, and several kinds of it (headers, footnotes, tracked revisions) are
unreachable from a naive document walk; and authoring conventions are inconsistent, so the same
visual device means different things across departments and must be interpreted rather than mapped
one-to-one. Stated concretely, the problem is to produce a representation of such a document that a
model can read without losing what the author encoded visually , and that is faithful, complete
and economical enough to fit a context window.
This paper aims to contribute on three fronts. We quantify what formatting-blind ingestion
costs an agent downstream, on real documents and against ground truth taken from the file’s own
markup rather than from our judgement, and we show the effect holds across six answering models from two vendors. We localise it: a span-level leave-one-out over six cue classes
attributes essentially the whole effect to colour and highlighting, with bold, italic, monospace and
strikethrough contributing nothing measurable—which turns “formatting matters” into a specific,
actionable claim about the two cues no mainstream converter preserves and no parsing benchmark
scores. And we ask whether recovering a cue is enough, or whether an agent also needs to be told what
the cue means ; a pre-registered test says the latter, though the margin is modest and we
report it as such. Alongside these we release a validated evaluation instrument: labels derived from
OOXML run properties, scored deterministically with no LLM judge, checked against rendered page
images through an independent modality, and bounded above by a supervised text-only classifier so
that the task’s cue-dependence is measured rather than asserted. We also report what did not work,
since both bear on how such systems should be built: progressive disclosure did not reduce token
cost, and the typed layer shows no benefit on the two models that attempt the task only sparsely.
2 Related Work
Document conversion and benchmarks. A mature toolchain converts documents for agent
consumption: python-docx and docx2python read OOXML directly, mammoth maps
it to HTML, and Docling [ 4 ] , Unstructured [ 16 ] and pymupdf4llm
target LLM-ready Markdown. These are evaluated on text accuracy, reading order, tables and
formulas—the axes of OmniDocBench [ 11 ] and ParseBench [ 12 ] —so
character-level presentation sits largely outside that frame. Microsoft’s Office Comprehension
Benchmark [ 10 ] is the first public suite evaluating LLM systems jointly on native Word,
Excel and PowerPoint files, and we evaluate on its Word File-Fidelity track directly
(§ 4.5 ); even there, formatting-dependent items are a minority and none turns on what a
surviving cue means .
Formatting recognition. The closest refereed work is TexTAR [ 15 ] , an ICDAR
2025 oral recognising textual attributes in document images. It covers precisely four—bold,
italic, underline, strikeout—and neither colour nor highlighting, the two our ablation finds
load-bearing. It also works from images and stops at attribute detection, where we recover cues
from OOXML and PDF geometry, assign semantic roles, and measure the effect on answer correctness.
Layout analysis [ 7 , 18 ] models page geometry, which is
complementary: our documents are text-heavy and their semantics sit in character properties.
Rendered versus ingested document. Liu et al. [ 9 ] mine the OOXML
specification for 21 “evidence forks” under which a file presents one view in Office and another
after extraction— plural ground truth . Every fork runs in the direction extraction
reveals what the canvas hides , and their six dimensions contain no run-level character formatting;
ours runs the other way. Yang et al. [ 5 ] establish the premise adversarially at
USENIX Security: moderation systems “operate primarily on tokenized text and often overlook visual
cues that humans naturally use”, a gap they exploit to reach over 86 % 86\% human recognition at under
1 % 1\% detection across 13 deployed systems. We differ from both in studying ordinary documents, where
nobody crafted anything.
Is emphasis already a machine signal? Two findings bracket the question our ablation
answers. PASTA [ 13 ] steers attention post hoc, motivated by exactly our premise—that
writers “leverage the subtleties of text style, such as bold and italics, to guide the attention of
readers”—reporting a 22 % 22\% average gain for LLAMA-7B. Against it, Dillitzer et
al. [ 2 ] report an attention–performance divergence : emphasis redirects
attention, yet “increased concentration does not inherently improve task accuracy”. Whether gains
come from cue salience or cue typing is exactly what § 4.4
pre-registers. Relatedly, Braun et al. [ 6 ] show prompt-side structure matters,
but manipulate formatting the prompt author controls, not what the document author chose.
Typed extraction. Xu et al. [ 19 ] discover entity attributes without a
predefined schema; we adopt their few-shot finding but replace mutual-dependency validation with
source-quote verification, since a guided schema makes hallucination the risk that matters. Generic
LLM extraction is competitive given suitable prompting [ 17 ] ;
REBEL [ 3 ] and ERNIE [ 20 ] extract triples for knowledge graphs,
and work on legal contracts [ 8 ] shares the need for typed extraction but
treats semantics as linguistically encoded. To our knowledge no prior system treats character-level
formatting as a first-class extraction cue, and no benchmark scores whether a cue’s meaning reached
the model.
3 Formatting-Aware Parsing
The parser reads the .docx file using python-docx and produces a flat list of RawBlock objects, each carrying structured formatting annotations. This stage is entirely code-based, with zero LLM calls.
3.1 Formatting as First-Class Signal
Parsing is the subject of this paper; the typed extraction and package rendering that consume its
output are summarised in Appendix S5 . The parser reads the .docx file with
python-docx and emits a flat sequence of blocks carrying structured formatting annotations,
entirely in code with zero LLM calls. Every contiguous run of text with identical formatting becomes
a FormattingSpan , an immutable record of 12 attributes; eleven high-confidence
formatting-to-semantics mappings then attach SemanticRole hints—red text or red highlight
to critical_warning , any other visible highlight to warning , strikethrough to
deprecated , and so on (Table 4 , Appendix S4 ). These are hints , not ground
truth: we deliberately exclude medium-confidence mappings such as green text to status marker,
because a wrong hint biases an agent worse than no hint.
Blocks are serialized in a hybrid form. Markdown carries what a model has seen extensively in
pretraining ( **bold** , ˜˜ struck ˜˜); custom tags carry what Markdown
cannot express ( [COLOR:#FF0000] , [HIGHLIGHT:YELLOW] ); and structural tags carry
document-level metadata a model cannot infer from text alone, such as which paragraphs belong to one
ordered list. Appendix S4 enumerates the tag set.
3.2 Cue Disambiguation and Recovery
Cues are ambiguous and must be resolved before the text reaches an agent, and two of our rules were
corrected during this study after corpus measurement contradicted the initial design. Bold means
key_term when only some spans of a block carry it and implicit_heading when the
block is a standalone line under 200 characters and entirely bold. Colour is matched by channel
threshold rather than hex literal, which admits dark reds while excluding orange—though we note
that 99.7 % 99.7\% of red spans in the corpus are exactly #FF0000 , so the tolerance buys less
than expected. Highlight is typed by presence , not hue: our initial rule typed only yellow,
and measurement showed cyan and light-grey highlighting of obligations is common, so any highlight
except WHITE / NONE —which render identically to unhighlighted text—now types as
warning . That single correction raised the share of author-marked paragraphs receiving a
salience role from 79.1 % 79.1\% to 97.6 % 97.6\% . Roles attach at block level while spans carry raw
inline markers, and that separation is what makes the salience-versus-typing ablation possible.
Several kinds of content are unreachable from a w:body walk and were silently absent from
our own representation until an external benchmark exposed it: headers and footers, footnotes,
document properties, OMML equations, and—most consequentially—tracked changes, where a deletion
is a w:r nested inside w:del carrying w:delText , so the accepted
revision , the text actually in force, is discarded. Appendix S4 gives the full rule
set and the OOXML paths.
4 Evaluation
Our claim is that a formatting cue carries meaning that survives or is destroyed during
parsing, and that whether it survives changes whether a downstream model answers
correctly. Testing this requires a task whose ground truth is the cue itself rather
than our interpretation of it. We therefore evaluate on three levels: a real-document
task at scale built from OOXML run properties (§ 4.1 – 4.4 ),
an external benchmark whose questions we did not write (§ 4.5 ), and
and a controlled test that the advantage survives an identical downstream pipeline (§ S9 ).
All experiments use Claude Opus 4.6 unless stated, temperature 0. Question
generation and second-opinion judging use different model families, so no model both
writes and answers a question. Scripts, item sets, per-document content hashes and
raw result JSON accompany the paper.
4.1 Corpus, prevalence, and task
We scanned 6,462 real .docx policy documents from a public corpus, named by content SHA-256, detecting cues at OOXML run level so nothing is inferred from wording. Walking the whole package, 32.8 % 32.8\% carry deliberate red text or a non-white highlight and 10.3 % 10.3\% carry one on a sentence expressing a modal obligation—the risk-bearing case; a further 2.6 % 2.6\% carry cues only outside the body, where no baseline we test can see them (Appendix S1 ).
This supports a real-document task at scale. A policy document contains several
requirement-like sentences; the author marked some (red text or highlight) and left
others unmarked. We ask:
List every requirement in this document that the author has singled out for
special attention or elevated priority.
Ground truth is the marked set, taken directly from OOXML run properties—never from
judgement. Scoring is set retrieval (precision, recall, F1) with a false-positive rate
measured against real unmarked requirements from the same document, so a system
that lists everything is penalised. Matching is lexical and deterministic: no
LLM judge is involved . A gold requirement counts as retrieved when a run of four
consecutive opening content words appears in the answer. That rule is deliberately
conservative, and we verified it does not depress the numbers: only one of the 332
gold requirements has fewer than four content words and is therefore unmatchable by
construction, giving every arm a recall ceiling of 0.997 0.997 , and no unmarked distractor is
unmatchable at all. Relaxing the rule to a three-word run or 60% content-word overlap
would accept a further 4.8 % 4.8\% of unmatched pairs, but inspection shows most of those are
the looser rule wrongly matching a different requirement that shares boilerplate
wording, so we keep the strict form. Construction requires at least one marked and at least three
unmarked requirements per document, and rejects any document whose marked sentences
are the only ones carrying urgency words. This yields 84 documents
(332 marked, 4,192 unmarked distractors); 76–79 are scored in a given run, as a
document is used only when every arm produces a representation under the size cap, so
comparisons stay paired.
Is the task solvable without formatting? We measure this rather than assert
it. Fitting a supervised text-only classifier (TF-IDF word 1–2 grams plus character
3–5 grams, logistic regression, grouped by document so no fold shares a
document with its training split) to the marked/unmarked labels gives
ROC AUC = 0.664 =0.664 . The two interpretable heuristics a zero-shot reader could actually
use sit at chance: an urgency-keyword rule scores 0.508 0.508 and sentence length
0.492 0.492 . So the wording carries a weak signal recoverable only with supervision on the
labels, and this 0.664 0.664 is a ceiling on any formatting-blind method.

4.4 Does typing add anything beyond preserving?
The novel component of this system is not preserving cues—docx2python does that—but
attaching typed roles to them. Isolating that contribution requires comparing our
representation against the same representation with the role tokens removed and
every inline cue marker retained .
This effect proved unstable across exploratory runs, for a reason we can name.

4.8 Implications for agents deployed in the wild
Three consequences follow for anyone running document-consuming agents in production.
The failure is invisible to standard monitoring. Every arm we tested returns
well-formed output on every document; none raises, none reports missing content. A pipeline
health check, a schema validator, and a token-count sanity check all pass. The only signal is
answer quality on questions whose ground truth lives in the source markup—which is precisely
what an operator does not have. This argues for ingestion-level assertions rather than
output-level monitoring: our own parser now asserts that a recovered cue implies a located span,
and that assertion caught a defect we had already published in a table.
It degrades precision, not just recall, which is the wrong direction for autonomy. An
agent that returns less is inconvenient; an agent that confidently returns more is
dangerous, because a downstream action may be taken on a requirement the author never flagged.
docling’s false-positive rate on unmarked requirements is 0.043 0.043 against our 0.011 0.011 . Under two
of the six answering models the effect appears as extreme conservatism instead—recall 0.09 0.09 at
precision 0.96 0.96 —so the same missing signal produces opposite pathologies depending on the
model, and neither is detectable without ground truth.
The fix is cheap, and it belongs before the agent. Recovering these cues is
deterministic, code-only, and costs no LLM calls; the entire effect reported here comes from
parsing alone. It does cost tokens—roughly twice plain text—so it is a deliberate trade of context
budget for factuality rather than a free win. Notably, the cue must be typed and not merely
passed through: showing an agent [COLOR:#FF0000] is worth less than telling it the span
is a critical warning ( + 0.085 +0.085 , p Holm = 0.049 p_{\text{Holm}}=0.049 ), which is consistent with evidence that
emphasis redirects model attention without accuracy reliably following [ 2 ] .
5 Conclusion
An enterprise agent reads whatever its ingestion layer produces, and that layer silently discards
the meaning authors encode visually. On 76 real policy documents, recovering the requirements an
author singled out falls from micro F1 0.690 0.690 to 0.150 0.150 (docling) and 0.075 0.075 (plain text), a gap that replicates across six answering models from two vendors. The failure is the
difficult kind for
autonomy: not an error the pipeline reports, but an agent that answers fluently and wrongly, with
four times the false-positive rate on requirements the author never flagged.
The loss is localised. A per-cue leave-one-out attributes essentially all of it to
highlight ( + 0.302 +0.302 ) and colour ( + 0.262 +0.262 ), both p Holm < 10 − 4 p_{\text{Holm}}<10^{-4} , with
bold, italic, monospace and strikethrough each within ± 0.003 \pm 0.003 of zero—and the same asymmetry
reappears in PDF. Colour is simultaneously the cue that matters most and the one no mainstream
converter preserves and no parsing benchmark scores. A pre-registered test further shows that
typing a cue for the agent adds + 0.085 +0.085 beyond preserving it
( p Holm = 0.049 p_{\text{Holm}}=0.049 ), consistent with evidence that emphasis redirects attention without
accuracy reliably following [ 2 ] .
Limitations. Exposure is common but not universal: a third of documents carry a deliberate
colour or highlight and 10.3 % 10.3\% carry one on an obligation. PDF support requires a usable text layer,
since we do not OCR. The typed layer is robust on three of the six models but shows no benefit on two that attempt the task only sparsely, so it is conditional on the model engaging with the hint. Ground
truth is derived automatically from run properties and validated against rendered pages by an
independent modality ( κ = 0.72 \kappa=0.72 ) but not yet by human annotators, which is the most valuable
addition remaining. The task is unsaturated at recall 0.60 0.60 , and this is genuine difficulty rather
than measurement: the scorer’s structural ceiling is 0.997 0.997 . Our representation costs roughly twice
plain text in tokens, a deliberate trade of context budget for factuality. Absolute micro F1 is stable
only to about ± 0.08 \pm 0.08 across configurations, so every claim rests on paired per-document tests.
Future work. Human validation of the labels; OCR-backed cue recovery for scanned pages;
non-English documents, where these cues carry culturally inflected semantics; and diff-based
re-ingestion across revisions, for which tracked changes already supply reviewer-signed ground truth.

Appendix S5 System Architecture and Tiering
The system processes documents in three stages (diagrammed in Figure 3 , Appendix S12 ). Stage 1
(Parse & Serialize) is entirely code-based with zero LLM calls, and is the subject of
this paper: it recovers character-level presentation and emits annotated text. Stage 2
(Extract) and Stage 3 (Render) consume that text and are described in
§ S7 . The separation concentrates LLM reasoning where it adds value—
entity classification, relationship identification, editorial summarization—and keeps
deterministic work in code. Five design principles guide the architecture
(Appendix S12 ), the most consequential being formatting is signal,
not decoration and source-quote provenance .
Appendix S6 Adaptive Tiering by Document Size
Because Stage 2’s cost is what makes a formatting-faithful representation practical at
enterprise document sizes, we note the tiering here and specify it in
Appendix S22 . A tier is selected from the annotated document’s estimated token
count: a single extraction call below 25K tokens (most enterprise SOPs), the same plus
faithfulness validation on a 20% sample to 50K, and above that segmentation into up to 16
overlapping ∼ \sim 8K-token chunks merged pairwise, costing 2 ​ N − 1 2N{-}1 calls for N N segments
— 3 at N = 2 N{=}2 , rising to 31 at the maximum. Segments are kept small deliberately so each
call completes inside the service’s ∼ \sim 330 s streaming limit; wall-clock time is 30 seconds
to 8 minutes depending on tier.
A uniform 4K-token chunking alternative would need an estimated 40–80 calls for a
100-page document and would fragment extractions across chunk boundaries; that figure is
analytical, from the chunk count, and not a measured baseline. The tiered design instead
exploits the fact that one long-context call yields globally coherent output, able to
deduplicate and resolve cross-references in a single pass.

Appendix S12 Architectural Design Principles
Five principles guide the system’s architecture:
1.
LLM for reasoning, code for assembly. LLM calls handle tasks requiring judgment (entity classification, relationship inference, editorial summarization). Deterministic tasks (parsing, serialization, rendering, file I/O) remain in code. This minimizes cost, maximizes reproducibility, and reduces non-determinism.
2.
Formatting is signal, not decoration. Every formatting attribute (bold, italic, color, highlight, font) is preserved through the pipeline and presented to the LLM as a semantic hint. The pipeline never strips formatting.
3.
Source-quote provenance. Every extracted entity must cite a verbatim quote from the source document. This is the primary anti-hallucination mechanism, more effective than any post-hoc validation.
4.
Type specificity over generality. Seventeen entity types with distinct schemas produce richer extractions than a generic “extract all entities” approach. A Procedure has steps with actors and deadlines; a Rule has conditions and consequences. These distinctions matter for downstream use.
5.
Progressive disclosure over monolithic output. The output is not a single flat document but a tiered package: a lean entry point containing critical guardrails, a quick-reference sheet for common lookups, and typed sub-files loaded on demand. This matches how AI assistants actually consume skill content.

Appendix S14 Serialization Tag Set and Attribute Encoding
Structural metadata tags. Every block is wrapped in a structural tag carrying document-level metadata:
•
[HEADING level=2 style="Heading 2"] — heading level and Word style name
•
[TABLE has_header=True cols=4] — table structure hints
•
[IMAGE type="flowchart" size=45K] — image classification placeholder
•
[PARAGRAPH roles="CRITICAL_WARNING"] — block-level roles
These structural tags encode information the LLM cannot infer from text alone: which numbered paragraphs are part of an ordered list, which table has a header row, which paragraph sits under a given heading level. Without these, the extraction model would need to re-derive heading hierarchy from font size heuristics, a fragile and error-prone operation.
Attribute encoding for fine-grained context. Tag attributes also carry indentation depth (for nested lists), font size (to distinguish normal body text from large callout headings), and style name (which encodes the Word template’s intended semantic, e.g., “Caption”, “List Number 2”). Style names are particularly valuable because they reflect the document author’s own semantic intent, which often aligns with entity type triggers.

Appendix S16 Handling python-docx Limitations
Several content types common in enterprise documents are not natively exposed by python-docx and require XML-level access:
•
Text boxes : Content in w:txbxContent elements must be extracted by walking the XML tree directly.
•
Tracked changes : python-docx silently skips deleted text. Insertions ( w:ins ) and deletions ( w:del ) require XML parsing.
•
Comments : Stored in word/comments.xml , accessible only through the OPC package interface.
•
Merged cells : Vertical merge continuations ( tc.vMerge ) report as empty cells.
•
OLE objects : Embedded objects appear as empty paragraphs; detected via w:object elements and logged as warnings.
These workarounds add approximately 80 lines of XML-handling code but are essential for complete extraction from real-world enterprise documents.
Appendix S17 Why 17 Entity Types?
Fewer types (e.g., the 6-type schema common in generic IE) force-fit distinct content into overly broad categories: a Rule with conditions and consequences is fundamentally different from a Procedure with ordered steps, even though both describe “what to do.” The 17-type taxonomy was validated against real enterprise SOPs to ensure each type has clear, non-overlapping trigger signals.
Appendix S18 The 12-Point Extraction Mandate
Beyond the obvious “extract all entities” instruction, several rules address specific failure modes observed in early testing:
•
Read-before-extract : The model must read the entire document before beginning extraction, preventing the common failure mode where entities in later sections are missed because the model starts outputting before fully reading.
•
Checklist-as-procedure : Checkbox lists are Procedure entities, not Warning entities, even if they contain prohibitions. Without this rule, models frequently misclassify “checklist items to verify” as warnings.
•
WRONG/CORRECT pattern : When a document presents “Incorrect: X / Correct: Y” examples, these become worked_examples in the type_specific_fields of a Rule entity. Without this rule, the WRONG examples are sometimes extracted as independent factual claims.
•
Procedural completeness : Sub-steps within a step must be preserved in full. The model must never “summarize” a 12-step sub-procedure into a one-line description. This rule prevents the single most common form of information loss in SOP extraction.
•
Warnings and prohibitions are highest priority : Even if the surrounding content is low-confidence, a Warning entity with red text and explicit consequences must always be extracted at HIGH confidence.
The remaining 7 points of the 12-point mandate cover standard but necessary rules: ALL-CAPS lines as implicit headings, proper Enumeration item extraction (preserve all items verbatim), Scope entity completeness, Metric unit and threshold preservation, cross-reference tracking for relationship extraction, confidence calibration for diagram-derived entities, and deduplication precedence (explicit stated entity wins over diagram-inferred).

Appendix S21 Structured Output via Tool Use
Free-form type_specific_fields. The tool use schema intentionally leaves type_specific_fields as a free-form JSON object rather than defining a per-type nested schema. This avoids an excessively deep and brittle tool definition ( > > 200 lines of JSON Schema) while still guiding the model through the system prompt’s per-type field descriptions. The Pydantic model that receives the output validates only the required fields, tolerating per-type variation.
The system uses the Strands Agents SDK with a @strands.tool -decorated function as the extraction target. The model is forced to call extract_entities with the full ExtractionResult payload, which Pydantic validates before returning to the pipeline. This guarantees valid structured output without JSON parsing heuristics. The agent’s message history is inspected post-call to extract the tool input dict, which is then deserialized into typed Python models.
Appendix S22 Tier 3 Merge: Additional Details
Segmentation walk. The algorithm walks blocks sequentially, accumulating a running token count and starting a new segment when the 8,000-token threshold is exceeded.
Oversized block handling during segmentation. A subtle complication arises with oversized blocks—single paragraphs exceeding 2 × 2\times the overlap budget (i.e., > > 8,000 characters). Including these in the overlap would cause them to dominate the next segment’s context, crowding out the actual boundary content. Such blocks are explicitly excluded from overlap computation via a skip_next_overlap flag, ensuring the overlap consists of the intended preceding context rather than one large anomalous block.
Restore from originals. After merging, the compact summaries are replaced with full original data by matching merged entity names to original segment entities via case-insensitive string matching. For entities that appeared in multiple segments (cross-segment duplicates), the merge call identifies them as a single entity; the restore step takes the union of all source_quotes arrays and merges type_specific_fields (e.g., unioning steps arrays from both segments ensures no sub-steps are lost during deduplication).
Appendix S23 Why Source-Quote Verification Instead of Mutual Dependency?
The ZOES Mutual Dependency (MD) principle validates (entity, attribute, value) triplets by checking if masking one component allows recovery of the others. MD addresses attribute granularity —ensuring discovered attributes are neither too coarse nor too fine. In our guided-schema extraction, attributes are predefined, so the granularity problem MD solves does not exist. The actual risk is hallucination : the LLM fabricating content not in the source. Source-quote verification targets this risk directly with a simpler prompt and lower cost.

Appendix S26 Anthropic-Spec Description Generation
The SKILL.md YAML frontmatter requires a description field that the Anthropic skill specification calls “pushy”—it must use imperative trigger language to combat undertriggering (the failure mode where the AI assistant possesses the skill but fails to load it because the user’s query doesn’t explicitly mention the skill name).
The description generation algorithm uses a three-tier fallback:
1.
Audience + entity trigger keywords (primary) : Extract applies_to from the Scope entity as audience context. Collect up to 5 Procedure , Rule , and Warning entity names as trigger keywords. Format: ‘‘For {audience}. Use this skill whenever users ask about {entity_names}.’’ 1 1
1
Entity names from the document are preferred over applies_to as triggers because they match the vocabulary users employ when asking questions (“How do I reset a password?”) rather than the document’s audience description (“IT Support team handling end-user requests”).
2.
SCOPE entity summary (fallback) : If no Scope entity has applies_to , use the scope entity’s LLM-generated summary as the description.
3.
Domain + high-confidence entity names (last resort) : Use the document title plus names of HIGH-confidence Definition , Rule , and Procedure entities.

Appendix S28 Open-Schema Discovery
The 17-type taxonomy covers approximately 95% of enterprise SOP content. For novel document types containing structures outside the taxonomy (e.g., escalation matrices, audit checklists), the system supports an optional open-schema discovery mode inspired by ZOES’s Root Attribute Induction [ 19 ] .
The approach uses a two-pass prompt strategy: Pass 1 adds the instruction “if you encounter structured information that does not fit any of the 17 types, create a new type with a descriptive name and define its schema” to the standard extraction prompt. If novel types are discovered, Pass 2 re-extracts with the expanded taxonomy to ensure consistent application across the entire document.
Appendix S29 Conflict Resolution
When the source document contains contradictory information (e.g., “probationary period is 90 days” in Section 1 vs. “60 days for part-time employees” in Section 7), the system: (1) flags the entity with a conflict marker, (2) preserves both values with source citations, (3) adds an entry to a dedicated “Conflicts & Ambiguities” section in the output, and (4) lowers the entity’s confidence. The system never silently resolves contradictions—that decision belongs to a human reviewer.
Appendix S30 Implementation Details
Architecture and dependencies. The system is implemented as a Python 3.12+ package comprising ∼ \sim 1,800 lines of production code across 10 modules. The largest modules are: llm/prompts.py ( ∼ \sim 763 lines, extraction + merge + validation prompts), rendering/skill_renderer.py ( ∼ \sim 1,100 lines, entity routing and multi-file rendering), and llm/extraction.py ( ∼ \sim 630 lines, tier orchestration, segmentation, and binary merge).
The five runtime dependencies are: python-docx ( ≥ \geq 0.8.11) for document parsing, an agent SDK ( ≥ \geq 0.1.0) for LLM calls against a managed cloud LLM service, pydantic ( ≥ \geq 2.0) for structured output validation, click ( ≥ \geq 8.0) for CLI, and rich ( ≥ \geq 13.0) for progress display. Notably absent: NumPy, sentence-transformers, FAISS, scikit-learn—the embedding-based deduplication machinery common in document processing pipelines is entirely replaced by inline LLM deduplication.
Bedrock integration. LLM calls use the Strands Agents SDK’s BedrockModel with cross-region inference profiles ( us.anthropic.claude-opus-4-6-v1 for all calls: extraction, merge, faithfulness verification, and vision). The SDK handles streaming, retry with exponential backoff ( delay = 2 attempt + jitter \text{delay}=2^{\text{attempt}}+\text{jitter} ), and structured output via tool use.
Errors are classified as retryable (throttling, rate limits, transient server errors, connection timeouts) or non-retryable (authentication failures, expired tokens, malformed requests, maximum token exceeded). On retry exhaustion after 3 attempts, a PipelineError is raised with context about the failed tier and call index, enabling targeted debugging.
