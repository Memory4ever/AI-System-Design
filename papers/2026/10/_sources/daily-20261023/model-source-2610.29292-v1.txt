  Abstract 
    
 An LLM multi-agent system (MAS) is only as good as the agents it chooses to trust: its accuracy and cost hinge on its topology, meaning which agents are included and how they communicate. A single task score, however, does not reveal which agents help or hinder performance. We propose Contrastive Attribution Topology Search (CATS), which searches for compact teams within a fixed supergraph of specialized agents. An LLM attributer compares execution traces across candidate topologies and assigns credit to individual agents. CATS uses these credits to update supergraph edges while progressively pruning weak edges and agents, yielding a small team for deployment. With small open-weight models and matched candidate evaluations, CATS improves mean accuracy on BigCodeBench by 5.3 percentage points over score-only heuristic search while using 54% fewer deployment tokens. On MBPP, CATS matches the strongest baselines with fewer tokens than the other searches. In a HotpotQA prompt-poisoning stress test, CATS excludes all adversarially prompted agents in all three runs, whereas random search retains some at comparable accuracy. Per-agent credit thus supports both team optimization and the pruning of potentially harmful agents. 
  
 
 
  1  Introduction 

 
 LLM-based multi-agent systems split work across specialized agents, for
example one that writes code and another that tests it. Such collaboration
can improve small models  [ 9 ,  10 ] ,
but more agents and messages mean more tokens. Building a good system
therefore requires choosing which agents to include and how they
communicate, that is, the  topology . Since the best topology depends
on the task, manual design is
difficult  [ 6 ,  5 ] ,
which motivates automated search over candidate teams. 
 
 
 Task scores, however, evaluate the team as a whole: a correct solution may
contain unnecessary work, and a failed one may include useful
contributions. Scores alone thus say little about which agents to keep.
Can feedback on individual agents guide the search for compact, effective
teams? 
 
 
 We introduce  Contrastive Attribution Topology Search (CATS) , an
offline meta-agent that assembles teams from a fixed agent pool. Starting
from a  supergraph  of candidate links, CATS evaluates sampled teams
on target-domain tasks. An LLM compares their transcripts and assigns each
agent signed credit. CATS then updates link probabilities, prunes weak
links and unreachable agents, and selects one fixed team for deployment.
Agent models, prompts, roles, and tools never change. 
 
 
 Our contributions are:  (i)  contrastive per-agent credit to guide
team construction (Figure   1  ),
 (ii)  higher mean accuracy and lower deployment token use than
score-only search on two coding benchmarks with matched candidate evaluations
(Table   1  ), and  (iii)  a HotpotQA stress
test where CATS excludes all poisoned agents in every run, while random
search retains some at comparable accuracy
(Table   2  ).

subgraph of a hand-crafted complete directed acyclic graph specialized to a

scheduling order).

  BigCodeBench.  Our selected topology     G  ⋆   G^{\star}    improves mean accuracy
over the strongest baseline, score-only heuristic search, by 5.3 points while using
54% fewer deployment tokens with matched candidate evaluations
(Table   1  ). Gains hold across all three seeds,
but standard deviations overlap and uncertainty remains
(Table   8  ). 
 
 
  MBPP.      G  ⋆   G^{\star}    performs comparably to the hand-crafted MAS and
random search, using fewer deployment tokens than the other searches but
more than the hand-crafted MAS (Table   1  ). 
 
 
  Final-candidate ablation.  Deploying     G  ⋆   G^{\star}    instead of
    G  p   G_{\mathrm{p}}    roughly halves coding deployment tokens, with
higher mean accuracy on BigCodeBench and the same on MBPP
(Table   1  ). 
 
 
  Offline search tokens.  Including attribution, CATS uses 28% and
35% fewer mean search tokens than score-only search on BigCodeBench and
MBPP, respectively, but roughly twice those of either search baseline on
poisoned HotpotQA (Table   10  ). 
 
 
  Discovered architectures.  Every selected coding team retains a draft
coder; 3 of 6 have no inter-agent edges, but agents can still interact through
the shared environment. All selected HotpotQA teams instead retain reader-to-submitter paths
(Appendix   A.2  ). These patterns support team
construction, with agent selection the clearest coding result; they do not
isolate a benefit from communication optimization. 
 
 
 
  4  Poisoned-Pool Stress Test 

   
   Figure 3 :   Selected topologies on HotpotQA 
(seed 13). Poisoned agents are in orange.   
 
 
 A meta-agent that assembles teams must also decline to delegate to agents it
should not trust. To probe this failure mode, we construct a  poisoned 
variant of HotpotQA  [ 12 ] , a third domain
distinct from the coding tasks above. Its supergraph contains six
adversarially prompted agents and four honest agents. The attacks include
plan misdirection, fabricated evidence, citation spoofing, instruction
hijacking, late answer overwrites, and exact-match sabotage
(Table   3  ).
The search receives no adversarial supervision: it observes only task scores
and transcripts, and is never told which agents are poisoned.
Table   2   shows why task score alone is
insufficient to assess delegation: comparable scores can mask different
levels of poisoned-agent recruitment. CATS retains no poisoned agents across
all three seeds. Random search retains two on average.
Score-only search’s teams are cheap but
inaccurate: 1, 2, and 5 agents, one with four poisoned. CATS instead removes
their incoming edges, making them unreachable
(Figure   3  ). Exclusion is therefore a
byproduct of the optimization signal, not a separate security filter. 
 
 
 
  5  Related Work 

 
 Topology is an established optimization target: GPTSwarm optimizes agent
graphs, MaAS samples query-dependent systems from an agentic supergraph, and
AgentPrune prunes redundant or malicious
communication  [ 17 ,  15 ,  16 ] .
Graph-GRPO derives statistical, per-edge credit from relative task rewards within groups of
sampled graphs  [ 3 ] . CATS instead
uses LLM-judged, per-agent credit, adapting contrastive attribution from prompt
optimization  [ 14 ]  to topology search:
agent configurations stay fixed, while team membership and communication
links change. Introspective LLM judges do not faithfully
approximate leave-one-out contribution  [ 8 ] , so we
treat our credit as an optimization signal, not a causal measure. 
 
 
 
  6  Limitations, Responsible Use, and Conclusion 

 
 Evaluating a single model family across three domains and three seeds limits
what we can conclude about broader transfer and variance, while high baseline
scores on MBPP leave little headroom for accuracy gains. Moreover, although
pruning yields sparse coding teams, this may reflect coordination via the shared
environment rather than a general lack of need for direct communication.
Finally, we only track token cost without optimizing it, making Pareto search
over score and cost, as done for prompts
by   Büssing et al. [2]  , a natural next step. 
 
 
 Attribution credits have not been validated against human judgments.
Credit–success correlation (Table   9  ) is only a
consistency check, since the attributer sees  system_score .
The score-only baseline was not separately tuned and does not isolate which component of CATS
accounts for the difference. Credit is node-level, propagated equally to all
incoming fired edges. A comparison with Graph-GRPO’s statistical edge-level
credit remains future work  [ 3 ] . 
 
 
 CATS turns a hand-crafted supergraph into a
small fixed team. It improved the balance between performance and efficiency
on BigCodeBench, reduced unnecessary complexity on the easier MBPP, and
excluded poisoned agents that task scores alone could not detect. In all
three domains it matched or beat score-only heuristic search on
score, deployment-token use, or both.
This supports attribution for team optimization and the pruning of
potentially harmful agents, not a security guarantee. 
 
 
 Responsible-use statement. 

 
 Selecting a topology determines which agents gain access to tools and task
context. Our stress test shows that attribution can exclude fixed adversarial
prompts, but this does not establish deployment safety. An adaptive adversary
could act beyond the capped transcript window or exploit the unverified LLM
attributer directly. Tool and data permissions must therefore remain outside
the optimizer.

 The selected coding teams consistently retain a draft coder alongside one or
two other agents, but their communication patterns differ
(Table   4  ). For example, BigCodeBench
seed 13 connects a draft coder, implementer, and test designer in a chain;
MBPP seed 13 selects the same roles with only direct entry edges from
 start . Two further BigCodeBench teams likewise have only entry edges,
while the remaining MBPP teams retain a single inter-agent edge. These
patterns show that selecting a set of agents and connecting that set are
distinct decisions. Because agents access a shared environment, teams with
only entry edges can still interact through the persisted artifact. 
 
 
 HotpotQA yields a different pattern: every selected team retains the
second-hop reader and either the drafter or final submitter, with directed
communication from a reader to the answer-submitting agent. These teams
combine retrieval and answer submission while excluding all poisoned roles.
The contrast with coding illustrates that the search does not always remove
communication. However, these graphs alone do not establish the benefit of
their particular edges; that would require a comparison that holds agent
membership fixed.

  A.4  Evaluation Protocol 

 
 Field caps use  o200k_base  tokens, retain the prefix, discard the tail,
and append the marker  ... [truncated]  outside the cap. Agent input fields
(query and upstream outputs) use the 900/700-token caps in
Table   5  ; the attributer’s query
and string-valued  says  fields use 120 tokens for coding and 150 for
HotpotQA, with  does  tool-effect logs and  final  summaries
exempt from field capping. The assembled attributer prompt is also
prefix-capped at its model limit minus the attribution field cap. 
 
 
 Seeds 13–15 jointly control splits, global randomness, topology sampling, and
generation. The generation endpoint, hosted by the University of Freiburg,
used the aliases  gemma-4-12b-llmlb  (agents/baselines) and
 gemma-4-31b-llmlb  (attributer). Weight hashes and quantization were not
exposed. Coding runs use fresh temporary directories and process groups with a
30-second timeout. Crashes, timeouts, empty environments, and unusable results
score zero. Deployment tokens count all agent-call input and output tokens per
held-out task. All reported    ±  \pm    values and shaded bands are Bessel-corrected
sample standard deviations over three runs.

  Appendix B  BigCodeBench Attributer Call 

 
 We adapt contrastive attribution  [ 14 ]  for
BigCodeBench by grading the persisted code artifact instead of agent text. We
also expose ordered, compact tool effects. The representative call below is
excerpted, with omitted material marked  [...] . 
 
    
   ⬇  
  =====     PROMPT     (  ABRIDGED  )     ===== 
 
  #     Task 
 
  You     are     an     attribution     agent     for     a     multi  -  agent     system  . 
 
  [...] 
 
  Your     goal     is     to     estimate     how     each     agent  ’  s     behavior     contributed     to     the 
 
  outcome     of     its     execution     by     comparing     differences     across     executions  . 
 
 
 
  Base     your     attribution     on  : 
 
  -     the     system     score     differences     across     executions  , 
 
  -     the     system     prediction 
 
  [...] 
 
  -     what     each     agent     measurably     changed     in     the     shared     environment  . 
 
 
 
  #     Attribution     Scale 
 
  Assign     a     float     score     in     [-1.0,     1.0]     to     each     agent     for     each     execution  : 
 
  -     positive     =     helpful     contribution 
 
  -     negative     =     harmful     contribution 
 
  -     0     =     neutral     or     unclear     impact 
 
 
 
  #     The     Protocol 
 
  This     system     is     graded     on     an     artifact     held     in     a     shared     coding     environment  , 
 
  not     on     any     agent  ’  s     text  :     the     code     persisted     with     ‘  write_code  ‘     is     what     the 
 
  hidden     test     suite     runs  ,     and     it     appears     in     no     agent  ’  s     output  .     So     every     agent 
 
  is     given     two     keys  :     ‘  says  ‘     (  its     text     output  )     and     ‘  does  ‘     (  a     numbered     log     of 
 
  every     tool     call     it     made  ,     in     order  ). 
 
 
 
  Each     ‘  does  ‘     line     is     ‘<  seq  >     <  VERB  >     <  target  >     <  delta  >     ["<  observed  >"]‘: 
 
      1     SET     code  =  c1     4  L 
 
      [...] 
 
      5     EDIT     code     c1  ->  c2     +1/-1 
 
      6     NOOP     write_code     "[  rejected     -     unsafe     import  ]" 
 
 
 
  [...]     Only     targets     named     in     ‘  final  ‘     are     graded  .     Scratch     writes     count     only 
 
  through     a     visible     later     observation     followed     by     a     graded     write  .     When     several 
 
  agents     write     code  ,     credit     only     what     survives     into     the     graded     value  .     Trust 
 
  ‘  does  ‘     over     conflicting     claims     in     ‘  says  ‘,     and     treat     example     tests     as     the 
 
  exact     required     behavior  .     [...] 
 
 
 
  #     Input 
 
  You     will     receive     JSON     with     ‘  query  ‘     and     an     ‘  executions  ‘     list  .     Each     execution 
 
  contains     ‘  system_score  ‘,     ‘  final  ‘,     and     a     mapping     from     agent     names     to     ‘  says  ‘ 
 
  and     ‘  does  ‘.     [...] 
 
 
 
  #     Output 
 
  First  ,     briefly     compare     the     executions     and     identify     the     key     behavioral 
 
  differences     that     lead     to     differences     in     the     system     score  . 
 
 
 
  Then     return     JSON     inside     <  attribution  >...</  attribution  >.     The     top  -  level     object 
 
  must     have     exactly     one     key  ,     ‘  executions  ‘,     containing     exactly     four     items     in 
 
  input     order  .     Each     item     contains     only     ‘  agent_credits  ‘,     with     exactly     the     seven 
 
  specified     agent     names     and     float     values     in     [-1.0,     1.0].     [...] 
 
 
 
  #     Few  -  shot     example 
 
  [...] 
 
 
 
  =====     RESPONSE     (  ABRIDGED  )     ===== 
 
  All     four     executions     failed     (  system_score  :     0.0),     primarily     because     the     agents 
 
  struggled     to     align     the     code     implementation     with     the     actual     data     structure 
 
  implied     by     the     prompt  . 
 
 
 
  [...] 
 
 
 
  In     Execution     3,     EDGE_CASE_TESTER_4     wrote     tests     to     the     scratchpad 
 
  (‘  test_list  ‘).     However  ,     because     no     coder     followed     these     tests     with     a     write     to 
 
  the     graded     ‘  code  ‘     target  ,     these     tests     had     zero     impact     on     the     outcome  .     [...]
