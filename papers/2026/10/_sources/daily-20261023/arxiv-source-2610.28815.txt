Abstract
Agentic harness evolution optimizes an agent’s instructions, tools, and control flow by using its task execution experiences as evolving evidence.
While more evolution tasks should intuitively improve performance, our preliminary study reveals a paradoxical failure mode: the performance of existing methods degrades as the task pool expands. Our further analysis demonstrates that this degradation stems from suboptimal evidence selection during optimization, as different evidence combinations lead to substantially different evolution outcomes. To address this issue, we propose Successive Scale Racing (SSR) , a framework that adaptively searches for optimal evidence combinations in each evolution round. SSR constructs diverse evidence combinations based on the corresponding task quality and coverage, and efficiently races the resulting candidate harnesses under a small compute budget. Empirically, across three distinct benchmarks, SSR achieves state-of-the-art results in all six configurations. Notably, as the task pool grows from 40 to 200, SSR steadily improves the pass rate from 64.3% to 68.3%, while the baselines’ performances all drop. Furthermore, its racing mechanism identifies near-optimal candidates while reducing validation executions by 60%.
1 Introduction
An agent harness governs a language model’s interaction with its environment through instructions, tool interfaces, context management, and control flow ( Ning et al., 2026 ; Pan et al., 2026a ) . By determining what the model observes, remembers, and can do ( Packer et al., 2023 ) , it shapes how model capabilities are used on real-world tasks. Harness engineering has relied heavily on human design and implementation, such as manually refined interfaces ( Yang et al., 2024 ) and coordination protocols ( Hong et al., 2023 ; Qian et al., 2023 ) . Recent work automates this process, evolving agent designs and workflows from execution experience while keeping model weights fixed ( Hu et al., 2024 ; Zhang et al., 2024a ; Zhang et al., 2026 ) .
Current frameworks for agentic harness evolution commonly follow an execution–reflection–optimization paradigm ( Lee et al., 2026 ; Lin et al., 2026 ; Wang et al., 2026 ; Liu et al., 2026 ) . The agent first solves assigned tasks, producing execution trajectories. An agent acting as the optimizer then distills lessons, which we refer to as evidence, from these trajectories, and uses them to guide improvements to the harness. This process repeats until a stopping criterion is met or the execution budget is exhausted.
Figure 1: Many existing methods evolve on large, fixed task pools, which can induce noisy or redundant signals. SSR searches over ordered evidence groups.
In machine learning, expanding training task pools generally improves generalization and system capabilities ( Kaplan et al., 2020 ; Hoffmann et al., 2022 ) . However, whether agentic harness evolution similarly benefits from larger task pools remains underexplored.
To address this gap, we first evaluate existing state-of-the-art methods ( Lin et al., 2026 ; Wang et al., 2026 ; Liu et al., 2026 ; Pan et al., 2026b ) by enlarging the set of training tasks used for evolution. Surprisingly, our preliminary study in Section 3 shows that larger task pools do not consistently yield better harnesses with existing methods. AHE ( Lin et al., 2026 ) , for example, initially improves but drops from 63.0% at 80 tasks to 57.7% at 200 tasks. Based on this observation, we pose our core research question:
How can we leverage experience from more tasks to evolve better harnesses?
To provide further insights into this problem, we investigate how different trajectory selections impact harness updates. We find that a set of
tasks selected by a simple LLM judge can generate better harnesses than either an equally sized alternative subset or the much larger full task pool.
This reveals a key insight: more task experiences, while providing more information, might also introduce noise or redundant signals . Feeding all trajectories into the optimizer could blur the focus of individual modifications. Thus, harness performance depends not on the total volume of available evidence, but on selecting the appropriate combinations of evidence for each evolution step.
However, searching for effective evidence combinations presents two key challenges: (1) The space of possible trajectory combinations is combinatorial. Generating every candidate harness and thoroughly evaluating each on validation tasks is computationally prohibitive. (2) The ideal evidence scale is not static; it shifts as the parent harness evolves and handles tasks differently across iterations.
To address these challenges, we propose Successive Scale Racing (SSR) (Figure 1 ), a framework that adaptively searches over evidence combinations under a fixed execution budget. SSR addresses the two challenges in the following ways: (1) Instead of enumerating combinatorial subsets, SSR introduces Representative Evidence Ranking (RER) to order task evidence by quality and coverage. It generates candidates from a selected set of evidence combinations based on the rankings. To minimize validation costs, SSR employs a cumulative performance racing mechanism that evaluates candidates on shared task batches and progressively prunes weaker candidates early. (2) In every evolution round, SSR refreshes execution trajectories based on the incumbent harness and dynamically re-ranks evidence subsets, allowing the winning evidence combination to adaptively shift as the harness evolves.
We evaluate SSR on SWE-Bench Pro Verified, DeepSWE, and GAIA-2 ( Zheng et al., 2026 ; Huang et al., 2026 ; Froger et al., 2026 ) across two execution setups. SSR achieves top performance and exhibits positive scaling, raising accuracy from 64.3% to 68.3% as the task pool expands from 40 to 200 tasks.
Our main contributions are threefold: (1) We identify noisy and redundant evidence signals as a primary cause of performance degradation when scaling task pools in harness evolution. (2) We propose SSR, which effectively searches over evidence scales using quality-coverage ranking and performance racing. (3) Across three benchmarks under two execution setups, SSR leads in all six settings and benefits from larger task pools, achieving higher efficiency and performance.
2 Related Work
2.1 Agent Harness Engineering
Harness design encompasses reasoning–action loops ( Yao et al., 2022 ) , multi-agent conversation ( Wu et al., 2023 ) , sandboxed execution ( Wang et al., 2024 ) , and prescribed repair workflows ( Xia et al., 2024 ) . Automated optimization spans instruction search ( Zhou et al., 2023 ; Yang et al., 2023 ) , feedback-guided prompt revision ( Pryzant et al., 2023 ; Agrawal et al., 2025 ) , pipeline compilation ( Khattab et al., 2023 ) , and textual feedback propagation ( Yuksekgonul et al., 2024 ) . Beyond prompts, GPTSwarm optimizes computational graphs ( Zhuge et al., 2024 ) , AgentSquare evolves and recombines modules ( Shang et al., 2024 ) , and AgentOptimizer updates tool functions ( Zhang et al., 2024b ) .

2.2 Self-Evolving Agents and Harnesses
Experience can improve outputs through self-feedback ( Madaan et al., 2023 ) , later attempts through verbal reflection ( Shinn et al., 2023 ) , and future tasks through reusable skills ( Wang et al., 2023 ) , extracted insights ( Zhao et al., 2023 ) , contextual guidelines ( Fu et al., 2024 ) , instruction manuals ( Chen et al., 2024 ) , reasoning memory ( Ouyang et al., 2025 ) , or evolving playbooks ( Zhang et al., 2025 ) . Code-level evolution includes SICA’s self-edits ( Robeyns et al., 2025 ) , DGM’s archive ( Zhang et al., 2026 ) , HGM’s descendant-based search ( Wang et al., 2026 ) , and MGM’s cross-task and cross-lineage comparisons ( Liu et al., 2026 ) . AHE structures trajectory evidence ( Lin et al., 2026 ) , while Meta-Harness exposes historical code, scores, and traces ( Lee et al., 2026 ) . Retro selects a challenging, diverse coreset and uses self-preference for retrospective optimization ( Pan et al., 2026b ) .
3 Preliminary Study
In this preliminary study, we investigate how task-pool size and evidence use affect harness evolution. To start with, we conduct experiments on SWE-Pro-V with the Codex setting, as in the analyses of Section 6 . We report final Avg Pass@1 (%) averaged over three independent runs. 3.1 Effect of Task-Pool Size
We vary the training task pool from 40 to 200 tasks across Retro, AHE, HGM, and MGM. Contrary to intuition, none of these methods consistently benefits from larger pools (Figure 3 ). For instance, AHE peaks at 63.0% accuracy with 80 tasks, but degrades to 57.7% with 200 tasks.
Observation 1.
Expanding the task pool does not necessarily produce a better harness under existing evolution strategies, and can even degrade performance.
3.2 Effect of Evidence Configuration
To understand this degradation, we analyze how different evidence selections impact optimization starting from the same harness (Figure 3 ). An LLM judge ranks experience records from the 160-task pool into Top 40 and Bottom 40 subsets. Top 40 outperforms All 160 by 3.4% and Bottom 40 by 5.4%, showing that evidence quality and scale matter significantly. Conversely, a randomly sampled 40-record subset from the 80-task pool trails All 80 by 1.3%, confirming that unguided scale reduction is unhelpful.
Observation 2.
Evolution outcomes depend on the evidence combinations (from task trajectories) the optimizer uses; a well-selected subset can outperform full-pool evidence.

4 Successive Scale Racing
In this section, we introduce Successive Scale Racing (SSR) . As illustrated in Figure 4 , our framework operates in four key stages: (1) Representative Evidence Ranking (RER), which orders experience records by quality and coverage; (2) Multiscale Candidate Generation, which independently modifies a shared parent harness using nested evidence prefixes generated from the ranking; (3) Candidate Performance Racing, which progressively prunes weaker candidates using cumulative scores on shared validation batches; and (4) Recursive Evolution, which updates the parent harness and refreshes execution evidence for subsequent rounds.

4.1 Representative Evidence Ranking
An effective evidence set must offer actionable and transferable insights without overwhelming the optimizer with redundant or low-value execution logs. To achieve this balance, Representative Evidence Ranking (RER) establishes a global ordering of experience records that jointly optimizes individual evidence quality and collective pool coverage.

Because the optimal evidence scale is unknown a priori and shifts as evolution proceeds (Appendix E ), SSR treats evidence scale as a per-round search variable. Third, the shared evidence core facilitates effective validation batching during performance racing (Section 4.3 ).

4.3 Candidate Performance Racing
Evaluating every proposed harness on every task would spend substantial execution budget on weak candidates. This is a fixed-budget best-arm identification problem ( Audibert et al., 2010 ; Karnin et al., 2013 ) : each harness is an arm, each task execution is a pull, and the goal is to return the best harness within the budget. SSR follows the successive-halving schedule ( Karnin et al., 2013 ; Jamieson and Talwalkar, 2016 ) with a constant elimination quota, and protects the parent as an incumbent. SSR introduces new tasks over K K stages and directs later evaluations to surviving candidates. The parent remains active throughout as a common reference and is never included in the child-elimination quota. Evaluation continues across stages even when only one child remains.

4.4 Recursive Evolution
After an accepted update, SSR reruns the new parent on all training tasks and rebuilds the experience records, outcome labels, and RER ordering. If the parent is retained, it reuses these records and the ordering while generating fresh candidates. Racing scores are accumulated within each round. Training-trajectory acquisition and all parent and child evaluation executions count toward the execution budget B B . Evolution ends when the execution budget is exhausted or no strict improvement has occurred for P P consecutive rounds, and returns the current incumbent. This maintains a single evolving harness while repeatedly exploring alternative evidence combinations.

6.1 Experimental Setup
Benchmarks and models.
We use SWE-Bench Pro Verified (SWE-Pro-V; Zheng et al., 2026 ), DeepSWE ( Huang et al., 2026 ) , and GAIA-2 ( Froger et al., 2026 ) , with disjoint train/validation/test splits of 80/20/100, 50/13/50, and 80/20/100 tasks. Training trajectories supply evidence for candidate generation, validation tasks support selection, and test tasks assess the resulting harness. For GAIA-2, we adopt Retro’s 200-scenario mini configuration from the official validation split, its four-message-per-turn cap, and no optional judge relaxations ( Pan et al., 2026b ) . Our execution settings are Codex with GPT 5.5 high and Claude Code with Opus 4.8 high. The optimizer matches the executor’s model and reasoning configuration.
Baseline methods.
We compare SSR with the initial harness, Meta-Harness ( Lee et al., 2026 ) , HGM ( Wang et al., 2026 ) , MGM ( Liu et al., 2026 ) , AHE ( Lin et al., 2026 ) , and Retro ( Pan et al., 2026b ) . Within each platform, methods start with the same empty additional harness while retaining the platform’s default tools and runtime. Baselines follow their original evolution procedures. SSR generates one candidate from each RER prefix of 25%, 50%, 75%, and 100%, using a common parent.
Experimental control.
All subsequent analytical experiments are conducted using Codex and Claude Code. When isolating specific components (e.g., fixed-strategy vs. ordering variants), we keep the candidate count, optimizer, racing mechanism, and execution cap identical to ensure fair comparison.
Evaluation protocol.
For our main results (Table 1 ), each end-to-end condition is evolved across three independent runs. We evaluate the resulting final harness on test tasks using Average Pass@1 across three trials, reporting the mean performance over the three runs (with standard deviations detailed in Appendix D ). Ablation studies and controlled analyses use a single evolution run per condition under the same evaluation protocol, whereas the racing audit relies on three selection replays over a fixed trajectory matrix. All reported performance differences represent absolute percentage point changes. Full experimental configurations are provided in Appendix C .
6.2 Overall Performance
As reported in Table 1 , SSR achieves state-of-the-art performance across all six benchmark–execution configurations. Under Codex (GPT 5.5 high), SSR outperforms the strongest baselines by 3.0%, 1.3%, and 1.7% on SWE-Bench Pro Verified (65.7%), DeepSWE (68.0%), and GAIA-2 (38.0%), respectively. Under Claude Code (Opus 4.8 high), SSR maintains consistent superiority, exceeding the top-performing baselines by 1.3% on SWE-Bench Pro Verified (63.3%), 1.3% on DeepSWE (65.3%), and 1.7% on GAIA-2 (36.0%). These results confirm that SSR provides robust performance gains across diverse task domains and models.

6.3 Effects of Task Experience and Search Resources
Scaling task pools.
We first evaluate how harness evolution scales as the available task pool expands from 40 to 200 tasks, with execution budgets scaled proportionally. As shown in Figure 6 a, SSR exhibits monotonic performance gains, steadily raising accuracy from 64.3% to 68.3%. In stark contrast, AHE suffers from severe degradation when task volume grows, peaking at 63.0% at 80 tasks before plummeting to 57.7% at 200 tasks. This confirms that SSR successfully converts larger task pools into continuous harness improvements.
Scaling search resources.
Next, holding the task pool fixed, we scale the total execution budget from 800 to 4,000 while expanding candidate-generation caps (from 15 to 35 for SSR, and from 55 to 145 for MGM). As illustrated in Figure 6 b, increased compute budget consistently benefits both methods, with SSR improving from 66.3% to 71.0% and maintaining a decisive lead over MGM (51.0% to 60.3%) at every checkpoint. These results demonstrate that SSR can effectively leverage additional compute to explore and identify superior harnesses.
6.4 Effects of Evidence Selection Strategies
Comparison with fixed evidence strategies.
To isolate the benefit of multiscale evidence, we compare SSR against fixed-evidence variants across four candidate generators: Top K Fixed (supplying the same top 25% of the evidence), Top K Resampling (independent 25% subsets), and Fixed N (full evidence set). As shown in Figure 6 a, relying on repeated sampling from identical evidence ( Top K Fixed ) or feeding full evidence ( Fixed N ) yields suboptimal performance on both benchmarks. While varying evidence composition ( Top K Resampling ) improves outcomes, SSR’s multiscale strategy provides a further gain of 1.4% on SWE-Pro-V (65.7% vs. 64.3%) and 1.3% on DeepSWE (68.0% vs. 66.7%), demonstrating the distinct necessity of searching across evidence scales.
RER ordering ablation.
We evaluate the necessity of RER by comparing it with Random ordering and a Quality only baseline under the same nested-prefix construction. As illustrated in Figure 6 b, ordering evidence by quality alone improves over random ranking on both benchmarks. Incorporating representative coverage via RER yields an additional performance boost of 1.0% on SWE-Pro-V (65.7% vs. 64.7%) and 0.7% on DeepSWE (68.0% vs. 67.3%), confirming that joint optimization of quality and coverage provides superior evidence guidance.

6.5 Racing Cost–Quality Audit
To evaluate the efficiency of our selection mechanism, we isolate 12 candidate harnesses (three per evidence scale) generated from a single parent. We construct a 160-task audit matrix, disjoint from candidate-generation and test sets, and compare Racing against a Uniform Subset baseline that distributes evaluation budgets equally across all candidates.
As shown in Figure 7 , Racing consistently outperforms uniform allocation across all validation budget levels (20%–60%). Notably, at just 40% of the full validation cost, Racing achieves a 65.3% score—within 0.4% of the full-matrix upper bound (65.7%)—while saving 60% of validation executions. Increasing the budget to 60% yields no further performance gains. These results confirm that SSR’s adaptive racing mechanism achieves near-optimal candidate selection with a substantially reduced evaluation budget.
7 Conclusion
We propose Successive Scale Racing (SSR) to address performance degradation when scaling task pools in harness evolution. SSR ranks task experience by quality and coverage, generates multiscale candidate harnesses, and efficiently races them under a fixed compute budget. Across three benchmarks and two execution setups, SSR achieves top performance in all six settings and enables positive task-pool scaling. Furthermore, its racing mechanism identifies near-optimal candidates while cutting validation executions by 60%, confirming that evidence-driven candidate diversity and execution-based selection provide a robust paradigm for agent self-improvement.
Limitations
While Successive Scale Racing (SSR) demonstrates promising results in scaling agentic harness evolution, several limitations warrant further investigation. First, the performance degradation observed when expanding training task pools is a multifaceted phenomenon. While our study focuses on noisy, conflicting, and redundant evidence as a primary underlying driver, other systemic factors may also contribute to this failure mode. Second, searching over evidence scales via SSR represents an initial step toward mitigating this scaling bottleneck. Alternative paradigms, such as adaptive evidence filtering via dynamic context pruning, fine-grained trajectory credit assignment, or reinforcement learning-based optimizer tuning, remain promising unexplored avenues for addressing noisy feedback during evolution. Third, our empirical evaluation, though conducted across multiple benchmarks and execution setups, is bounded by the specific choice of foundation models used as task agents and optimizers. Further validation is needed to determine how well these findings generalize to a broader spectrum of model architectures, such as open-weight models of varying scales or domain-specialized language models.
Ethical Considerations
Improving agent harnesses can increase both the benefits of automated task completion and the potential harms of erroneous or misused tool actions. Our benchmark evaluations do not establish safety in unrestricted deployment. Practical use should retain execution isolation, restricted tool permissions, and human oversight for consequential actions. Task experience may also contain sensitive information or biases that can propagate into evolved harnesses; trajectories and generated artifacts should therefore be reviewed before sharing or deployment. The use and redistribution of third-party datasets, models, and code should respect their respective licenses and terms.

A.6 Interpretation and Limits
A sufficient gap condition.
Suppose h ⋆ h^{\star} is the unique maximizer in 𝒞 \mathcal{C} and
Δ min = min h ≠ h ⋆ ⁡ [ μ ⁡ ( h ⋆ ) − μ ⁡ ( h ) ] > 0 . \Delta_{\min}=\min_{h\neq h^{\star}}[\mu(h^{\star})-\mu(h)]>0.
On the uniform event, if 2 ​ ε r < Δ min 2\varepsilon_{r}<\Delta_{\min} at every completed stage, then h ⋆ h^{\star} strictly outranks every competing active harness empirically. It cannot be removed if it is a child, and is protected if it is the parent. Final selection returns h ⋆ h^{\star} . Replacing ε r \varepsilon_{r} with deterministic upper bounds turns this into a sufficient 1 − δ 1-\delta exact-selection condition. This is a conservative condition, not a claim of optimal sample complexity.
Why the discrepancy term is necessary.
The training tasks can be directly involved in candidate generation and are selected preferentially. Their ranking need not agree with validation ranking even if rollout noise vanishes. For example, consider two children with validation gap μ ⁡ ( a ) − μ ⁡ ( b ) = d > 0 \mu(a)-\mu(b)=d>0 and training mean difference m ¯ T ​ ( a ) − m ¯ T ​ ( b ) = − 1 \overline{m}_{T}(a)-\overline{m}_{T}(b)=-1 . At validation weight α ∈ ( 0 , 1 ) \alpha\in(0,1) , their expected mixed-score difference is α ​ d − ( 1 − α ) \alpha d-(1-\alpha) . It is negative whenever d < ( 1 − α ) / α d<(1-\alpha)/\alpha . The children can therefore be misranked even with exact expected scores. This is a mathematical illustration, not experimental data. A vanishing validation-target selection bound requires a discrepancy assumption or a change to the selection objective; the proof does not silently make either change.
Relation to the audit and to generalization.
The theorem compares expected rewards on a fixed finite validation pool. The racing audit instead measures a score gap against a realized full evaluation matrix; that is a related empirical diagnostic, not the same estimand. Within-round random task ordering and fresh executions justify the conditional finite-pool result even after conditioning on prior history. They do not make repeatedly reused validation tasks independent of the evolved harness for population generalization. We consequently make no multi-round or test-distribution claim from this theorem. Candidate-generation quality is also outside the selection bound.

This opportunity-set observation therefore does not establish monotonic performance for SSR, an interior optimal scale, or dominance over other evolution methods.
Appendix B SSR Implementation Details
Evaluation-task construction.
At the start of an evolution round, training tasks are partitioned into successful and failed tasks according to the current parent’s collected training trajectories. These labels and the RER ordering remain fixed throughout that round. For prescribed batch sizes b v , b s , b f b_{v},b_{s},b_{f} , sample b v b_{v} previously unused validation tasks uniformly without replacement. For each training class, first select previously unused tasks from the intersection of the surviving candidates’ evidence prefixes, following the RER order. If the intersection cannot supply the class quota, continue through tasks outside the intersection in RER order. Because evidence prefixes are nested, their intersection is the shortest surviving prefix. The parent is not included in this intersection.
Exclude every task already evaluated in the current round. If a training class has fewer remaining tasks than its quota, use all remaining tasks in that class, without repetition or substitution from the other class. Likewise, the validation component is bounded by its remaining tasks. The union is shared by the parent and all active children. Equation 7 weights actual tasks equally, so the effective mixture weights follow the realized task counts. Original training trajectories provide candidate-generation evidence and outcome labels; parent–child racing comparisons use the corresponding executions within the current race. Validation trajectories are not exposed to the optimizer as evidence, and the test set is never used in these decisions.
Integer quotas and ties.
One deterministic integer implementation retains
n r = max ⁡ { 1 , M − ⌊ r ​ M / K ⌋ } , r = 1 , … , K − 1 , \begin{gathered}n_{r}=\max\{1,M-\lfloor rM/K\rfloor\},\\
r=1,\ldots,K-1,\end{gathered}
children after each intermediate stage, with n 0 = M n_{0}=M . Thus stage r r eliminates n r − 1 − n r n_{r-1}-n_{r} children. The quotas are fixed before racing and approximate a constant quota of M / K M/K removals per stage. After the final completed stage, select the best survivor. Rank children first by cumulative score, then by ascending diff size (total added plus deleted lines relative to the parent across editable harness files), and finally by fixed candidate index. Equal RER marginal gains can likewise be resolved by fixed record index. A child tied with the parent never replaces it. These are empirical comparisons without a confidence threshold.
Budget boundaries and stopping.
With active child set 𝒜 \mathcal{A} and proposed new batch B r B_{r} , start the stage only if the remaining execution budget covers R ⁡ ( | 𝒜 | + 1 ) ​ | B r | R(|\mathcal{A}|+1)|B_{r}| executions. Otherwise end the race and select using its last fully completed stage. If no stage was completed, retain the parent. A full evidence refresh requires execution budget for all N N training executions; if that refresh cannot be completed, terminate and return the incumbent. No partial stage enters the cumulative comparison. Stop after P P consecutive rounds without a strict improvement, resetting the counter after an accepted update. If the parent is unchanged, reuse the collected trajectories, judge records, scores, embeddings, and ranking, but generate fresh candidates. Within-race task scores do not automatically carry into a new race.
Judge and optimizer interface.
The judge is prompted to output w i , a i , u i ∈ [ 0 , 1 ] w_{i},a_{i},u_{i}\in[0,1] directly; there is no additional score normalization. It applies the same transferability criteria to successful and failed trajectories. Similarities use embeddings of the judge’s trajectory summaries and extracted experience, with negative cosine values clipped to zero. The optimizer initially receives the selected experience summaries and improvement suggestions plus the parent harness. It can retrieve original trajectories for those selected records on demand, and can modify instructions, tool-related code, context management, and execution flow. Concrete model identifiers, scale choices, task quotas, repetitions, and stopping settings are reported in Appendix C .

Appendix F More Related Work
Racing and successive halving.
Selecting among costly-to-evaluate candidates under a fixed budget is a classical problem. Racing algorithms evaluate all survivors on a shared, growing set of instances and eliminate candidates by statistical tests ( Maron and Moore, 1994 ; Birattari et al., 2002 ; López-Ibáñez et al., 2016 ) . Successive halving and Hyperband instead remove a fixed fraction of candidates at each stage ( Karnin et al., 2013 ; Jamieson and Talwalkar, 2016 ; Li et al., 2018 ) , and best-arm identification analyses bound the resulting selection error ( Even-Dar et al., 2006 ; Audibert et al., 2010 ) . Incumbent-based intensification in algorithm configuration compares challengers with the current best on common instances and replaces it only on strict improvement ( Hutter et al., 2009 ; Hutter et al., 2011 ) . TRIPLE applies successive halving to select among a fixed pool of prompts ( Shi et al., 2024 ) . SSR’s candidate racing combines fixed-quota elimination with a protected parent. It differs in what is raced and on what: the candidates are generated from nested evidence prefixes of one parent, evaluation batches mix held-out validation tasks with training tasks chosen from the survivors’ evidence, and the pool is regenerated as the parent evolves.

Use this for tasks with many requirements , shared interfaces , parsers , CLIs , persistence , async behavior , or UI state .
## 1. Build the Contract Matrix
Before editing , copy ‘ templates / contract - matrix . md ‘ into ‘ $RHO_SCRATCH_DIR ‘ or keep the same information in your notes . For each requirement , record :
- the exact public interface or behavior requested
- the implementation files and call paths that must change
- the edge cases that would prove it
- the command or test that verifies it
Do not treat a compile check or a smoke run as enough when the prompt specifies serialized payloads , exact defaults , filtering , status transitions , boundary UI behavior , or error text .
## 2. Search the Whole Affected Surface
After identifying the main change , search for bypass paths :
- old type / field / function names and direct calls to the old behavior
- alternate constructors and config defaulting paths
- CLI flags , config parsers , web / API entry points , non - interactive flows , proxy / recording paths , and background workers
- interface implementations , mocks , wrappers , generated clients , and tests
- persistence keys , secondary indexes , request payload builders , and response hydration helpers
When semantics change from boolean to enum , sync to async , static address to runtime address , literal parsing to structured parsing , or derived state to persisted state , every old direct path is suspect until searched .

Prefer small tests that pin the public contract over large broad tests that only compile . Good regression targets from prior failures :
- parser / adapter tasks : historical and current input shapes , nil versus empty slices , deterministic ordering , identifier preference , exact output JSON / request body , filtering and exit - code behavior
- CLI / testability tasks : option injection , no process exit on parser or handler errors , error preservation , and dynamic ‘:0‘ listener address propagation
- async / event tasks : non - blocking overflow , backoff / drop counters , close behavior , all emission paths routed through the new abstraction
- state - transition tasks : no resources , one resource , newest resource removed while older remain , final resource removed , monotonic timestamps in UTC
- UI / control tasks : initial zero state , start , middle , exact end , out - of - range / invalid input , state and position observers staying in sync
- import / packaging tasks : end - to - end payload contents , redirects , missing package ‘ __init__ . py ‘, relative imports from package initializers , and precise error messages
- storage lifecycle tasks : create , list order , get single / array / empty , update preserving unrelated fields , delete cleanup from every index , null last - seen values

# DeepSWE solve harness
Use this harness to turn a task prompt into observable acceptance checks before
the implementation starts . A green pre - existing suite is regression evidence ;
it is not evidence that a new feature satisfies its contract .
## Non - negotiable runtime rules
- Multiple workers may share the host ‘/ tmp ‘. Never keep task - specific mutable
state at a fixed global ‘/ tmp /...‘ path .
- Put matrices , notes , logs , patches , reports , and other persistent solve state
under ‘ $RHO_SCRATCH_DIR ‘ ( the runner creates ‘ task /. harness - state /‘ and exports
its absolute path ).
- A truly disposable file or directory may be made with ‘ mktemp ‘; the process
that creates it must remove it .
- Reading shared tools or using concurrency - safe tool - managed caches under
‘/ tmp ‘ is fine .
- In container tasks , repository changes and commits belong in ‘/ app ‘, not in
the host workspace . Treat ‘/ host - ws ‘ and ‘ $RHO_SCRATCH_DIR ‘ as staging and
evidence locations only .
Initialize the acceptance ledger without overwriting an existing one :
‘‘‘ sh
harness / bin / init - acceptance - matrix
‘‘‘
If the harness is mounted elsewhere , invoke that script by its discovered
absolute path . It writes only to ‘ $RHO_SCRATCH_DIR ‘.
For a container repository that cannot be edited directly , keep a candidate
patch in ‘ $RHO_SCRATCH_DIR / change . patch ‘, check it before mutation , then apply
the same bytes :
‘‘‘ sh
docker exec - i " $container " sh - lc ’ cd / app && git apply -- check -’ \
<" $RHO_SCRATCH_DIR / change . patch "
docker exec - i " $container " sh - lc ’ cd / app && git apply -’ \
<" $RHO_SCRATCH_DIR / change . patch "
‘‘‘
Prefer several small checked patches over one large shell - quoted rewrite .
## The solve loop
### 1. Establish the real repository contract
Before editing :
1. Read repository instructions and the prompt completely .
2. Confirm the repository root , current revision , available toolchain , and
test / build conventions . Inspect nearby implementation and tests .
3. If requested , create a branch from ‘ main ‘ before changes . Configure Git
identity repository - locally only if a commit requires it .
4. Record prohibited tooling , offline constraints , exact public names , exact
errors , submission / commit requirements , and supported modes in the ledger .
Do not download a generator or replace checked - in generated artifacts when the
task requires the checkout ’ s existing toolchain . Do not broaden the task with
unrelated cleanup , completion , documentation , or sorting changes .
### 2. Derive acceptance rows from prose
Create one row for every independently observable clause . Pay special attention
to words such as ** all **, ** every **, ** only **, ** never **, ** exactly **, ** same **,
** before **, ** after **, ** until **, ** even on failure **, ** default **, and ** must **.
Classify each row :
- ‘ P ‘ positive behavior
- ‘ N ‘ rejection , error , or prohibited behavior
- ‘ B ‘ boundary or unrestricted input domain
- ‘ X ‘ exact API , schema , representation , ordering , or message
- ‘ C ‘ composition with another feature , mode , or existing API
- ‘ L ‘ lifecycle , state transition , concurrency , or cleanup
- ‘ R ‘ backward compatibility and unchanged behavior
For each row write the public entrypoint , setup , action , exact observable
result , and oracle . A helper - level assertion is insufficient when the contract
is visible through a CLI , transport , renderer , compiler , serializer , or other
public path .
### 3. Build the smallest high - risk interaction matrix
Do not blindly test a full Cartesian product . Use pairwise cases plus cases at
representation and lifecycle boundaries . At minimum cover :
- every explicitly accepted syntax / value / API variant , including alternate
grammar branches and aliases ;
- every execution mode / backend / public access path named by the prompt ;
- every state - changing builder operation followed by every terminal mode it
can affect ;
- empty , zero , nil / null , missing , duplicate , maximum / exact - limit ,
just - over - limit , whitespace , Unicode , special property names , and invalid
values where legal ;
- first use , repeated use , reset / reuse , removal , failure , and use after
serialization or reconstruction ;
- operation - order reversals : configure before / after registration , abort before
start / during pending work / after completion , and callbacks on every exit path ;
- disjoint concurrent inputs , out - of - order completion , one stalled worker ,
cleanup races , and bounded - retention pressure when concurrency is required ;
- a new feature composed with the closest existing API , rather than only used
alone ;
- processing exactly once versus repeated processing , especially pipelines
that coalesce , render , merge , or replay in multiple stages .
Turn a category definition into both qualifying and non - qualifying cases . Turn
an unconditional statement into an empty - input case . Turn an ordering statement
into multiple items whose insertion , lexical , priority , and completion orders
differ .
### 4. Choose semantic , implementation - independent oracles
Test what the caller observes , not the trigger or representation chosen by the
implementation .
- Serialization / output : assert exact keys and types , empty arrays versus null ,
ordering , section counts , comments , whitespace , and final newlines . Then parse
or decode and assert semantics .
- Transformations / optimizers : compare before / after behavior over the supported
domain . Include a preservation case and a locality counterexample proving
unrelated input still changes when allowed .
- Parsers : cover every syntax container , contextual fallback , exact diagnostic ,
malformed delimiter / quote case , and compatibility when the feature is off .
- Stateful systems : assert the transition , current snapshot , side effects ,
cleanup , and subsequent operation --- not merely stored fields .
- Caches / concurrency : vary worker inputs . Assert preserved union and actual reuse
or work counts , not merely valid files / checksums .
- Resource bounds : instrument every queue , collector , formatter , and replay
stage . Compare default - concurrency output byte - for - byte with the baseline .
- Async / UI : drive real event paths and passive state changes . Do not inject an
implementation - specific event merely to make the test pass .
- Binary formats : decode and assert every requested field with known nonzero
values ; structural validity alone is too weak .
- Type - level APIs : add compile - pass and compile - fail checks as well as runtime
tests .
Keep focused acceptance tests in the repository when its conventions allow .
Never weaken , narrow , or delete a regression just because it exposes an
architectural problem .
### 5. Trace the complete data and state flow
Before settling on an architecture , trace the feature from public input to the
final consumer . List every parsing , normalization , caching , persistence ,
rendering , reconstruction , and cleanup stage . This catches repeated processing
and metadata lost at boundaries .
Check these questions explicitly :
- What is the true identity key ? If behavior depends on variables , candidate ,
target , path , scope , or generation , a name - only cache is probably too coarse .
- Who owns mutable state , and who clears it on removal , reset , close , error , or
global - state replacement ?
- Does the implementation need to distinguish absence from a legal zero / empty
value ? Use an explicit presence bit rather than a value sentinel .
- Does a reused legacy helper implement the prompt ’ s exact category boundary ?
- Is an immutable API ’ s returned value retained ?
- Can callbacks , timing , metrics , or cleanup be skipped by an early return ?
- Does stored metadata survive every persistence / reconstruction route ?
- Can shared source input be mutated and leak into siblings or later passes ?
### 6. Validate in a cost - aware ladder
Run checks in this order and record the command and exit status in the ledger :
1. smallest compile / type / format check for touched code ;
2. focused acceptance tests , including negative and interaction rows ;
3. affected package / module tests ;
4. public CLI / API / transport smoke test using the built artifact ;
5. broader regression suite , lint , vet , race , or build as appropriate ;
6. final diff , exact API / exports / docs / generated - file audit , and commit checks .
When a broad command is blocked by an offline dependency or unrelated fixture ,
run the narrow suites that exercise the changed code and report the blocker
precisely . Do not claim later commands in a shell chain ran if an earlier command
failed . A failure found by a strong lifecycle test must be fixed or explicitly
reported , never replaced with a weaker scenario .
Avoid waste : inspect before patching , use small verified patches , stop repeating
unchanged failing commands , and do not install unavailable tools merely to make
one optional check green .
### 7. Submission gate
Before the final answer :
- Re - read every prompt clause and mark each ledger row ‘ pass ‘, ‘ blocked ‘, or
‘ unresolved ‘, with evidence .
- Run ‘ git diff -- check ‘ and inspect the final diff for accidental or generated
changes .
- Confirm focused tests are included when appropriate .
- Commit every intended repository change if the task grades committed work .
- Confirm the branch / base requirement and inspect ‘ git status -- short ‘ and the
final commit . Do not call a dirty or partially committed tree clean .
- State exactly what passed , what was blocked , and any remaining contract risk .
