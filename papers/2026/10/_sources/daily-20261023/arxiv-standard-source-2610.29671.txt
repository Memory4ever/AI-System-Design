Abstract
Long-term agent memory is shifting from predefined workflows toward learnable policies for memory construction and retrieval. Existing learning-based methods either optimize construction alone or combine retrieval-side online reinforcement learning (RL) with offline construction supervision, limiting co-adaptation between the two stages. In this paper, we explore end-to-end online RL for a unified memory manager ( Uni-Mem ) that learns both capabilities under a shared policy. However, joint optimization with existing RL algorithms such as GRPO faces confounded group comparisons and sparse feedback over long memory-management trajectories. To this end, we propose Stage-Decoupled GRPO, which alternates construction and retrieval optimization while controlling variation from the other stage within each rollout group, yielding stage-specific learning signals. We further introduce Event-Wise Credit Assignment (ECA), which localizes feedback to responsible events and propagates event-level advantages to their constituent operations.
Experiments on LoCoMo and LongMemEval show that Uni-Mem outperforms the strongest RL-based memory, demonstrating the effectiveness of jointly learning memory construction and retrieval via Stage-Decoupled GRPO and ECA.
1 Introduction
Figure 1: Comparison of training paradigms in different methods. Construction-only RL keeps retrieval fixed, while asymmetric joint learning combines offline construction imitation with online retrieval RL. Uni-Mem jointly optimizes both stages under a shared policy through alternating online RL and event-wise credit.
Long-term memory enables Large Language Model (LLM) agents to reuse information across interactions that exceed their context windows ( Wang et al., 2023 ; Yu et al., 2026b ) . Early memory systems, such as MemGPT ( Packer et al., 2023 ) , Mem0 ( Chhikara et al., 2025 ) , and A-Mem ( Xu et al., 2025 ) , rely on manually specified prompts and predefined workflows to organize and access past information. Despite their effectiveness, these systems remain constrained by frozen LLMs and rigid human priors, limiting the generalization of memory construction and retrieval to dynamic agent environments ( Xiong et al., 2026 ) .
To bridge this gap, recent works formulate memory management 1 1
1
In this paper, memory management encompasses construction (creation, update, and deletion) and retrieval. as a learnable policy optimized via reinforcement learning (RL).
Methods such as Memory-R2 ( Yan et al., 2026a ) and Mem- α \alpha ( Wang et al., 2025 ) keep retrieval fixed and train construction with RL.
Such construction-only RL learns how to build memory without jointly learning how to retrieve it adaptively, limiting memory utility in downstream tasks. To jointly learn both capabilities within a shared-parameter memory manager, approaches such as Mem-T ( Yue et al., 2026 ) combine online agentic RL of retrieval with offline imitation of hindsight-selected construction actions. Yet this asymmetric joint learning can introduce a training lag: online retrieval RL continually updates the shared policy, whereas offline construction supervision remains anchored to earlier policy and memory states, hindering coordinated adaptation across the two stages.
This motivates a central research question:
How can a shared-parameter agentic memory manager, which operates through multi-turn tool interaction, jointly learn long-horizon construction and retrieval via end-to-end online RL?
Achieving this goal poses two main challenges. (1) Confounded group comparisons.
Existing group-relative RL (e.g. GRPO Shao et al. (2024) ) derives advantages from reward differences among sampled rollouts. For a unified memory manager, each rollout couples construction trajectories with a retrieval continuation, so its final reward reflects decisions from both stages. When both stages vary across rollouts, trajectory-level group-relative advantages can conflate their contributions, obscuring the learning signal for each stage.
(2) Long-horizon credit attribution.
The manager policy performs hundreds of memory operations (tool calls) per rollout, yet receives the outcome reward only at answer time. Such sparse feedback neither localizes the query-relevant portions of a rollout nor reveals whether the required information was stored or successfully retrieved. Moreover, memory updates further complicate attribution by overwriting memory items produced by earlier decisions. Thus, feedback must be attributed to the relevant stage and operations within them.
In this work, we propose Uni-Mem , a unified memory manager that jointly learns agentic construction and retrieval through end-to-end online RL. Fig. 1 compares the training paradigms of existing methods with ours. To address confounded group comparisons, we introduce Stage-Decoupled GRPO , which decouples the two stages contributions in group-relative advantages. Specifically, we alternate construction and retrieval optimization while controlling variation from the other stage within each rollout group. For construction, we bypass learned retrieval: since each memory record retains the identifier of its source chunk, we directly gather the records linked to a query’s annotated supporting evidence (used only during training) and score them with a frozen answer model. This evidence-indexed score reflects what was stored rather than how it was retrieved. For retrieval, all rollouts in a group share an identical memory state resampled from the current policy, so reward differences reflect retrieval alone. Alternating the two phases yields stage-specific signals, enabling both capabilities to co-evolve.
To address long-horizon credit attribution, we introduce Event-Wise Credit Assignment (ECA) , which organizes multiple memory operations into events 2 2
2
In this paper, we distinguish two types of events: construction event and retrieval event, denoted in Sec. 3.1 , triggered by an incoming dialogue chunk ( construction event ) or a query ( retrieval event ).
ECA uses a query’s supporting evidence to localize the responsible construction events, and reuses evidence-indexed scoring to penalize an unsuccessful retrieval event only when sufficient evidence has been stored. For update-robust evidence attribution, ECA tracks events along the same memory update chain and assigns them the corresponding credit. Since the event stream is fixed by the input data, rollouts share aligned event positions. ECA thus normalizes each event’s feedback against same-position events across the rollout group, rather than at the trajectory level, and broadcasts the resulting advantage to all memory tool calls within that event. Our contributions are summarized as follows:
•
We propose Uni-Mem , a unified memory manager that jointly optimizes agentic construction and retrieval via end-to-end online RL, with Stage-Decoupled GRPO separating the two stages’ contributions to group-relative signals.
•
We introduce Event-Wise Credit Assignment , which localizes outcome feedback to responsible events and computes advantages over position-aligned events across rollouts.
•
Extensive experiments on LoCoMo and LongMemEval demonstrate that Uni-Mem outperforms the strongest RL-based memory manager, supporting the effectiveness of jointly learning memory construction and retrieval.
2 Related Work
Long-term Memory Agents.
Long-term memory enables LLM agents to retain and reuse information beyond their active context.
Retrieval-augmented generation (RAG) provides a basic mechanism for accessing external information ( Lewis et al., 2020 ) , while early agent-memory systems consolidate interactions into persistent records and reflections ( Park et al., 2023 ; Zhong et al., 2024 ) .
Subsequent work emphasizes hierarchical storage and consolidation ( Packer et al., 2023 ; Kang et al., 2025 ; Fang et al., 2026 ) , or structured and associative organization ( Chhikara et al., 2025 ; Xu et al., 2025 ; Rasmussen et al., 2025 ; Gutiérrez et al., 2025 ; Yuan et al., 2026 ) .
Agentic retrieval further enables iterative evidence gathering from retained histories ( Yan et al., 2025 ) .
Complementing these architectural advances, Uni-Mem learns a shared policy for multi-turn memory construction and retrieval via adaptively tool calling, allowing both capabilities to adapt jointly to downstream tasks.
Reinforcement Learning for Memory Agents.
RL-based memory methods optimize compressed working states, as in MEM1 ( Zhou et al., 2026 ) and MemAgent ( Yu et al., 2026a ) , external-memory construction ( Wang et al., 2025 ) , or retrieval decisions ( Tan et al., 2025 ; Hsu et al., 2026 ) . AgeMem ( Yu et al., 2026b ) coordinates long-term memory and short-term context.
Memory-R1 ( Yan et al., 2026b ) trains memory construction and a separate answer agent, whereas Memory-R2 ( Yan et al., 2026a ) extends this training to long horizons with local and global group-relative credit.
Denser construction supervision is also explored through intermediate rewards and evidence-based attribution ( Ma et al., 2026 ; Shen et al., 2026 ) .
Beyond individual components, Mem-T ( Yue et al., 2026 ) combines online retrieval RL with offline imitation of construction actions selected using hindsight feedback. Different from existing approaches, Uni-Mem explores an end-to-end online RL of a shared-parameter manager policy while addressing the resulting challenges of confounded group comparisons and credit assignment with Decoupled GRPO and event-wise attribution. Appendix A further positions our work with representative methods’ interaction patterns and training paradigm, including a detailed technical comparison with Mem-T.

5 Experiments
5.1 Experiment Setup
Datasets and Evaluation Metrics.
We evaluate our framework on LoCoMo Maharana et al. (2024) and LongMemEval Wu et al. (2025) .
For a fair comparison, we follow the training data configuration of Memory-R2 Yan et al. (2026a) , partitioning LoCoMo into RL training, validation, and test sets with a 2:1:7 split. We use LongMemEval for out-of-distribution evaluation. We report LLM-as-a-Judge scores ( J J ) using the official Mem0 ( Chhikara et al., 2025 ) judge prompt.
Baselines. We compare Uni-Mem against two groups of baselines.
(I) Training-free methods include RAG for conversation retrieval, as well as A-Mem ( Xu et al., 2025 ) , Mem0 ( Chhikara et al., 2025 ) , and MemoryOS ( Kang et al., 2025 ) .
(II) Training-based methods include MEM1 ( Zhou et al., 2026 ) , MemAgent ( Yu et al., 2026a ) , Memory-R1 ( Yan et al., 2026b ) , and Memory-R2 ( Yan et al., 2026a ) , and Mem-T ( Yue et al., 2026 ) . These methods typically use RL to optimize memory phase. For a fair comparison, we re-evaluate the Memory-R2 (OSS) variant, which uses GPT-OSS-120B OpenAI (2025) as its answer model. Details of baselines are in Appendix D
Implementation Details.
We use Qwen3-4B-Instruct Yang et al. (2025) as the backbone of our memory manager. GPT-OSS-120B serves as the external answer model, and GPT-4o-mini OpenAI (2024) serves as the judge model. Additional training details are provided in Appendix C .

5.3 Ablation Study
Ablation setting. To validate the effectiveness of Uni-Mem ’s module
designs, we conduct an incremental ablation study. Specifically, M 0 M_{0} serves as the starting point, using either the original or SFT-initialized base manager. M 1 M_{1} jointly optimizes memory construction and retrieval using standard GRPO. M 2 M_{2} adds Event-Wise Credit Assignment to M 1 M_{1} . M 3 M_{3} replaces standard GRPO in M 2 M_{2} with Stage-Decoupled GRPO. Finally, M 4 M_{4} incorporates update-robust evidence attribution into M 3 M_{3} , yielding the full Uni-Mem framework. Table 2 presents the ablation results using either the original or SFT-initialized Qwen3-4B-Instruct model. The single-stage rollout and reward-assignment procedures for
M 1 M_{1} and M 2 M_{2} are detailed in Appendix E.2 .
Event-wise Credit Assignment.
Sparse outcome rewards offer limited guidance for credit assignment across hundreds of memory operations. Adding ECA ( M 1 → M 2 M_{1}\rightarrow M_{2} ) improves overall J J by 1.29 and 3.03 percentage points without and with SFT, respectively. These gains support the effectiveness of ECA, which localizes feedback to relevant events and their operations. Update-robust attribution ( M 3 → M 4 M_{3}\rightarrow M_{4} ) continually improves the performance, supporting the additional benefit of credit tracing along memory update lineages.
Stage-Decoupled GRPO.
M 0 → M 1 M_{0}\rightarrow M_{1} brings very limited gain (only 0.37%), which indicates that group-relative advantages can conflate construction and retrieval effects.
Stage-Decoupled GRPO ( M 2 → M 3 M_{2}\rightarrow M_{3} ) improves overall J J by 2.48 percentage points without SFT. In particular, temporal accuracy rises by 10.55 points in this setting, and multi-hop accuracy increases by 4.48 points after SFT.
These gains support the effectiveness of alternating optimization and controlling cross-stage variation in Stage-Decoupled GRPO.

Conclusion
We presented Uni-Mem , a unified memory manager
that jointly learns agentic memory construction and
retrieval through end-to-end online reinforcement learning
under a shared policy.
By combining Stage-Decoupled GRPO with Event-Wise Credit
Assignment, Uni-Mem obtains stage-specific learning
signals and assigns credit to relevant memory operations,
enabling coordinated online learning of construction and
retrieval over long horizons.
Experiments demonstrate that Uni-Mem outperforms
strong RL-based memory baselines on LoCoMo and generalizes
to LongMemEval.
Limitations
Uni-Mem unifies memory construction and retrieval through online RL, enabling coordinated policy learning with stage-specific optimization and event-wise credit assignment. However, training remains resource-intensive because rewards require completing downstream QA and obtaining judge-model evaluations. These evaluations typically rely on external APIs or stronger deployed models, introducing more costs and latency. Running judge evaluations concurrently or adopting asynchronous RL could alleviate the latency bottleneck. Future work will explore more robust process-level supervision to reduce reliance on outcome-based evaluations.

Memory manager as an agent.
Although several prior works describe their memory modules as agents,
the memory manager in most of them acts as a one-step policy: given an
input and a context prepared by a fixed procedure, it produces its
operations in a single generation, and their results are never fed
back to it. We refer to such events as single-turn. In Uni-Mem ,
the manager is instead an agent that interacts with the memory bank
over multiple turns, as in ReAct ( Yao et al., 2023 ) . At each step, it
chooses a tool call, observes the returned result, and decides what to
do next, including when to stop.
Among prior methods, MEM1 ( Zhou et al., 2026 ) interacts with an
external environment over multiple turns, but its memory is an
internal state rewritten in one generation at every turn, with no tool
access to the memory itself. MemAgent ( Yu et al., 2026a ) overwrites
a fixed-length memory once per chunk and answers from the final memory.
Memory-R1 ( Yan et al., 2026b ) , Memory-R2 ( Yan et al., 2026a ) ,
and Mem- α \alpha ( Wang et al., 2025 ) generate the memory operations for
each input in one pass, and answer questions with fixed similarity
retrieval (embedding or BM25).
Mem-T ( Yue et al., 2026 ) performs multi-turn search at query time,
but its construction is a fixed two-step pipeline: a formation step
proposes memory candidates, and an evolution step decides one
operation for each candidate. Neither step issues its own searches or
sees the execution results of earlier operations.
Why an agentic manager helps.
The key difference is who decides what the manager sees. In
single-turn methods, the context for each decision is prepared by a
fixed similarity search against the incoming fact or the raw query;
if it misses a relevant record, the policy cannot recover, and RL
cannot improve this step. An agentic manager gathers its own context,
making this step part of the learned policy. During construction, it
can search for records that a new chunk duplicates or contradicts
before writing. During retrieval, it can reformulate the query and
follow intermediate results for multi-hop questions, as found useful
in multi-step QA ( Trivedi et al., 2023 ; Jin et al., 2025 ) . In line
with this, the trained retrieval policy improves the overall J J score
by 4.50 and 4.04 points on the same memory banks
(Table 3 ).
A.1 Differences from Mem-T
Mem-T is the closest work to ours. Beyond the construction pipeline
discussed above, the main difference lies in how construction is
trained. Mem-T trains retrieval online with MoT-GRPO but learns
construction offline, imitating actions that are scored in hindsight
from retrieval rollouts. These scores come from an earlier policy and
memory state and can become outdated as the shared parameters change.
Moreover, they depend on whether the sampled retrieval surfaces the
stored memory, so a correctly stored fact can receive little credit
when retrieval fails. Uni-Mem trains both stages with
on-policy RL and scores construction with evidence-indexed memory
scoring (Eq. ( 5 )), which does not depend on the
learned retriever. Consistent with this, longer alternation blocks,
which let one stage lag behind the other, lower the overall J J score
from 88.80% to 83.75% (Figure 4 (c)).
Appendix B Implementation Details
B.1 Memory Representation and Provenance Tracking
We use the storage and retrieval layer of Mem0 Chhikara et al. (2025)
(with Qdrant as the vector store) as the memory bank, rather than a
naive record list, since a capable manager should be able to operate
such a well-engineered store.
Crucially, we bypass Mem0’s native interface, in which a fixed LLM
pipeline extracts facts and chooses among ADD ,
UPDATE , DELETE , and NOOP , and the question
is issued as a single search.
Instead, the learned policy decides what to store, when and how to
revise records, and when and how to search ; Mem0 only executes these
decisions.
CREATE inserts agent-written content verbatim without Mem0’s
fact extraction, UPDATE replaces a record’s text and
embedding under the same ID, DELETE removes it, and
SEARCH returns the most similar records with their IDs and text.
The single source-chunk index c i c_{i} in the main text is a
simplified notation for record provenance. In implementation,
each record maintains a cumulative list of chunk IDs:
CREATE initializes this list with the current chunk ID,
and UPDATE appends the current chunk ID while retaining
previous associations.
Index ⁡ ( E k , ℬ ) \operatorname{Index}(E_{k},\mathcal{B}) selects the current
versions of all surviving records whose provenance lists
intersect E k E_{k} , including records updated rather than
originally created in an evidence chunk.
This metadata is hidden from the manager and used only for
evidence-indexed scoring (Eq. ( 5 ))
and credit assignment during training.

Construction events.
Each event starts with a chunk of up to two new dialogue messages
and up to ten preceding turns from the same session as read-only
context.
The manager may interleave searches with memory writes.
A write requires a successful search response observed in an
earlier assistant turn of the same event; an empty result is valid.
A write bundled with the first search is therefore rejected.
FINISH closes the event and advances to the next input,
including when no memory changes are needed.
Retrieval events.
Each event starts with a question and a reference date, when available.
Only SEARCH and FINISH are permitted.
The manager may refine its queries over multiple rounds;
retrieved records are accumulated and deduplicated by ID.
A voluntary FINISH requires a successful search response
and hands the accumulated evidence to the frozen answer model.
The environment then clears the retrieval cache and advances
to the next question, or terminates after the final question.
Execution rules.
Each call is a JSON object containing name and
arguments , enclosed in <tool_call> tags.
Calls within a response execute sequentially, and their results
or errors become observations for the next decision.
For updates and deletions, displayed memory aliases are resolved
to backend record IDs.
FINISH must be issued alone: when bundled with other
calls, it is ignored while the remaining calls undergo
their usual checks.
In our RL configuration, each event permits at most eight
searches and 24 manager responses; exhausting the response
budget forces event closure.

20 for retrieval. Smaller requested limits are raised to
these values, and all limits are capped at 200.

Appendix D Details of Baselines.
We describe the baseline methods below. Training-free methods manage memory without task-specific parameter updates, whereas training-based methods learn memory-related policies from task feedback.
RAG.
RAG indexes conversation history and retrieves relevant text segments through embedding similarity. The retrieved segments are provided to an answer model as supporting context. It provides a basic conversation-retrieval baseline without explicit fact extraction or memory editing.
A-Mem.
A-Mem ( Xu et al., 2025 ) organizes interactions into structured notes containing the original content, timestamps, keywords, tags, and contextual descriptions. It links semantically related notes and revises existing notes when new information arrives. At query time, relevant notes are retrieved through embedding similarity to support answer generation.
Mem0.
Mem0 ( Chhikara et al., 2025 ) maintains an external memory bank through an extraction-and-update pipeline. An LLM extracts salient facts from incoming interactions, retrieves related memories, and selects among ADD , UPDATE , DELETE , and NOOP to maintain the bank. Relevant memories are subsequently retrieved to answer questions.
MemoryOS.
MemoryOS ( Kang et al., 2025 ) organizes information into short-term, mid-term, and long-term personal memory. Dialogue records are grouped into topic-based segments, with dialogue-chain FIFO updates and heat-based consolidation transferring information across levels. Retrieval combines relevant dialogue segments and pages with recent context and persistent user and agent information for response generation.
MEM1.
MEM1 ( Zhou et al., 2026 ) integrates memory consolidation into an agent’s reasoning process. At each interaction step, it combines the previous internal state with new observations to generate an updated state and the next action. Earlier interaction content is removed from the active context, and RL trains the agent to preserve task-relevant information within this bounded context.
MemAgent.
MemAgent ( Yu et al., 2026a ) processes long inputs sequentially while maintaining a bounded textual memory. Each new chunk triggers a rewrite of the memory, and the final answer is generated from the question and the resulting memory. Its multi-conversation RL algorithm uses final-answer rewards to optimize the sequence of memory updates and answer generation.
Memory-R1.
Memory-R1 ( Yan et al., 2026b ) contains a memory manager and a separate answer agent. The manager learns to select ADD , UPDATE , DELETE , or NOOP for extracted information. Fixed similarity-based retrieval supplies candidate memories to the answer agent, which learns to filter and reason over them through memory distillation. Both components are optimized using downstream answer correctness.
Memory-R2.
Memory-R2 ( Yan et al., 2026a ) trains a shared-parameter fact extractor and memory manager over chunked, multi-session conversations. Its LoGo-GRPO algorithm combines global trajectory supervision with local session rerollouts from shared intermediate memory states to improve credit assignment. A curriculum progressively increases the session horizon, while similarity-based retrieval remains fixed. The standard variant uses a separately trained Qwen2.5-7B-Instruct answer agent. We additionally evaluate a variant that pairs the Memory-R2 memory policy with GPT-OSS-120B ( OpenAI, 2025 ) as the answer model. This variant matches the answer model used by Uni-Mem , enabling a comparison of the memory systems with the same downstream answer model.
Mem-T.
Mem-T ( Yue et al., 2026 ) maintains working, factual, experiential, and raw memories. Memory construction follows a formation-and-evolution pipeline, while retrieval uses multiple search steps to gather evidence. Its MoT-GRPO algorithm trains retrieval through branching rollout trees and propagates answer feedback to intermediate operations. Construction is trained through offline imitation of actions selected by hindsight scores derived from retrieval outcomes and evidence alignment.

Appendix G Prompt Templates
G.1 Memory Manager Prompt
The same system prompt governs memory construction and query-time retrieval
(Prompt ). The manager maintains long-term memory
and retrieves evidence for an external answer model through a shared tool
interface.
⬇
# Role
You are an autonomous memory manager controlling a long - term memory store for
an external assistant . You see one external event at a time . The event is either
new conversation content to ingest or a user query to answer . You cannot know
how many future events remain , and you must never try to end the whole episode .
# Operating Principles
Maintain an accurate , useful memory store .
- Store durable user - specific facts , preferences , relationships , plans ,
commitments , recurring projects , explicit instructions , and dated events .
- Update a memory only when the current messages explicitly correct or
supersede the same stored event , preference , or relationship , making its
claim wrong or stale – never just to add more detail . A different event , a
different date , a compatible preference or relationship , or an unrelated
topic is a new memory ; create it .
- Delete memories only when they are wrong and no replacement is needed .
- Use the shortest useful action sequence that satisfies the current event .
# Memory Writing Standard
The memories you store are later semantically searched and handed to a separate
answerer that uses them to answer future questions . Write each memory so that
the right one is easy to retrieve by a natural - language question and complete
enough to answer from on its own .
- One focused unit per memory : a single event , preference , decision , or
relationship . Capture that one unit with its own essential specifics
( names , date ).
- One occasion or topic per memory . Different events , different dates , or
unrelated topics each get their own memory ; never merge them into one . A memory
that spans several dates or several unrelated events is too broad : it is hard to
retrieve , and its single timestamp is wrong for most of what it contains .
- Concise but complete : a focused memory is usually 1-2 sentences ( about 15-80
words ; up to 3 sentences / 100 words only when it is dense with proper nouns ,
dates , or quantities ). The range is a guide , not a hard cap , and completeness
always wins over word count – never drop a proper noun , date , or number to stay
short . When a topic carries many details , split it into several focused
memories rather than packing one wide memory ; when unsure , prefer two memories
over one merged .
- Self - contained : understandable without other memories . Start with the
speaker ’ s actual name and replace pronouns with names .
- Preserve specifics verbatim : proper nouns and titles ( people , places , books ,
films , brands , dishes ), exact quantities , and qualifiers . Never generalize a
concrete detail (" Ferrari 488 GTB ", not " a sports car ") – the exact wording is
what a future question is scored against .
- Anchor time to the Observation Date as absolute dates ; never store
" last week "/" recently ", and never blur an explicit number or duration .
- Resolve a relative day - of - week reference to its absolute date before storing .
If on 11 May , 2022 the conversation mentions something that happened " on
Monday ", infer the actual date (9 May , 2022) and write the memory as " On 9
May , 2022, < what happened >" – never store the bare weekday .
# Memory Write Gate
create_memory , update_memory , and delete_memory require previously observed
retrieval evidence for the related person , entity , date , or topic .
- Before any write tool call , you must have already observed relevant results
from memory_search in an earlier assistant response during the
current event .
- A retrieval result from the same assistant response is not yet observed . Do
not call memory_search and then write in that same response .
- If you have not observed relevant retrieval evidence , do not write . Either
retrieve first or finish the event if there is no durable memory work to do .
- Search queries should use the relevant names , entities , dates , and topic
keywords needed to check for duplicates , stale memories , or contradictions .
- Create a new memory for each new fact , event , preference , feeling ,
reflection , question asked , or decision .
- Call update_memory only when the current messages explicitly correct or
supersede the same retrieved event , preference , or relationship , making its
stored claim wrong or stale and requiring in - place correction .
- Capture every fact the conversation states ; do not skip one because it seems
minor .
# Query Handling
For query events , answer from long - term memory evidence when the question
depends on remembered user - specific information .
- Retrieve and observe enough relevant memories before answering a memory - based
query .
- If the available memories do not support an answer , do not invent one .
- You do not answer the question yourself . Retrieve useful evidence , then
finish the event so a separate external answerer can respond from it .
# Tool Contract
You may use memory_search , create_memory , update_memory ,
delete_memory , and finish_event when they are
available in the tool schema .
finish_event must be the only tool call in its assistant response . Do not bundle
finish_event with memory_search , create_memory , update_memory , or
delete_memory .
# Output Format
Wrap every tool call in :
< tool_call >
{" name ": "< tool >", " arguments ": {< json >}}
</ tool_call >
G.2 LLM-as-a-Judge ( J J ) Prompt
Prompt gives the mem0_base evaluation
template, supplied as a user message. Given a question, a reference answer,
and a generated answer, the judge returns CORRECT or WRONG .
We report J J as the percentage of evaluated answers labeled
CORRECT . Braced fields denote runtime inputs.
⬇
Your task is to label an answer to a question as " CORRECT " or " WRONG ". You will be given the following data : (1) a question ( posed by one user to another user ), (2) a ’ gold ’ ( ground truth ) answer , (3) a generated answer which you will score as CORRECT / WRONG .
The point of the question is to ask about something one user should know about the other user based on their prior conversations . The gold answer will usually be a concise and short answer that includes the referenced topic , for example :
Question : Do you remember what I got the last time I went to Hawaii ?
Gold answer : A shell necklace
The generated answer might be much longer , but you should be generous with your grading - as long as it touches on the same topic as the gold answer , it should be counted as CORRECT .
For time related questions , the gold answer will be a specific date , month , year , etc . The generated answer might be much longer or use relative time references ( like ’ last Tuesday ’ or ’ next month ’), but you should be generous with your grading - as long as it refers to the same date or time period as the gold answer , it should be counted as CORRECT . Even if the format differs ( e . g ., ’ May 7 th ’ vs ’7 May ’), consider it CORRECT if it ’ s the same date .
Now it ’ s time for the real question :
Question : { question }
Gold answer : { answer }
Generated answer : { response }
First , provide a short ( one sentence ) explanation of your reasoning , then finish with CORRECT or WRONG . Do NOT include both CORRECT and WRONG in your response , or it will break the evaluation script .
Just return the label CORRECT or WRONG in a json format with the key as " label ".
