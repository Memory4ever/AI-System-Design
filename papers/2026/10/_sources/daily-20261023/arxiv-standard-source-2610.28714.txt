Big Claims, Small Margins:
Do Reported GraphLLM Gains Survive Simple Baselines?
Michal Podstawski
Affiliation: NASK National Research Institute, Warsaw, Poland
Correspondence to: michal.podstawski@nask.pl
Abstract
LLM-based methods for node classification on text-attributed graphs (TAGs) routinely report state-of-the-art accuracy.
We ask how these results compare with inexpensive baselines run on the same splits.
On the splits of three recent studies, we tune four baseline representatives with validation-only selection and compare them with the highest mean that each paper reports for an LLM-based method in the matched setting.
Correct & Smooth on TF-IDF features trails this reference by a median of 2.3 percentage points, and an MLP on frozen e5-large-v2 embeddings by 2.8 points.
Correct & Smooth is within 3 points of the reference or better on 15 of 24 tasks, but the reference is significantly higher on 12 of 22 testable tasks, so several reported gains remain substantial.
Reading released code next to the papers, we also document evaluation risks: selection of hyperparameters or checkpoints on the test set, labels of test-pool nodes used in training, baseline numbers reused without disclosure, and a text–label misalignment in a released Cora loader.
Reports of the same method on the same split also differ by up to 12.5 points across papers whose configurations are not documented to match.
Keywords: text-attributed graphs, graph neural networks, large language models, evaluation, reproducibility, benchmarks
1 Introduction
Text-attributed graphs (TAGs), such as citation networks, co-purchase graphs and hyperlinked web pages, attach natural-language text to every node.
A fast-growing line of work combines large language models (LLMs) with graph learning on TAGs: recent methods use LLMs to encode node text, predict from graph inputs, or supply supervision ( Section 2 ).
New methods typically report state-of-the-art node-classification accuracy.
Graph learning has seen this pattern before.
Careful re-evaluations showed that reported GNN gains often shrink under fair comparison ( Shchur et al., 2019 ; Errica et al., 2020 ; Platonov et al., 2023 ) .
They also showed that propagated features with a linear head ( Wu et al., 2019 ) , label propagation with a base predictor ( Huang et al., 2021 ) , and tuned MLPs ( Zhang et al., 2022 ; Katsman et al., 2024 ) are competitive on popular benchmarks.
Comparable reality checks exist in recommendation ( Dacrema et al., 2019 ) , metric learning ( Musgrave et al., 2020 ) and tabular learning ( Grinsztajn et al., 2022 ) .
LLM-based methods add two complications: a much higher training and inference cost, and papers that inherit splits, features and sometimes baseline numbers from one another.
Question and scope.
We ask a narrow question: when inexpensive baselines are run on the splits a paper used, with a fixed tuning budget and validation-only selection, how do they compare with the best LLM-based result that paper reports in the same setting?
We cover three recent studies whose splits we could recover: LLM4HeG ( Wu et al., 2025b ) and KCoT on the LLaGA split ( Xie et al., 2026 ; Chen et al., 2024a ) ship masks, and for LLMNodeBed ( Wu et al., 2025a ) we reconstruct the seeded splits from the released code.
Together they give 24 dataset–protocol pairs.
We also report problems in released code that we verified directly.
Findings.
Several reported gains remain substantial and significant, but on many tasks the margin over a cheap baseline representative fixed by name is a few points ( Section 4 ).
The released code of several papers selects on the test set, trains on labels of test-pool nodes, or misaligns node texts and labels, and one paper reuses another paper’s baseline numbers without disclosure; we cannot always establish whether the published tables came from this code ( Section 5 ).
Finally, papers whose configurations are not documented to match report the same method on the same split up to 12.5 points apart, and KCoT reports no variance, so its margins cannot be tested.
2 Related Work
LLMs on text-attributed graphs.
The LLM can enhance or encode node text ( He et al., 2024 ) , or predict from graph tokens or serialized neighborhoods ( Chen et al., 2024a ; Tang et al., 2024 ; Zhang et al., 2026 ; Xie et al., 2026 ; Wang et al., 2026 ) .
It can also annotate, teach or judge in co-training loops ( Xu and Ding, 2026 ; Peng et al., 2026 ; Wei et al., 2025 ; Wu et al., 2025b ; Duan et al., 2025 ) , or provide the text side of graph foundation models ( He et al., 2025 ; Wang et al., 2025b ; Zhu et al., 2025 ; Liu et al., 2025 ; Wang et al., 2025a ) .
Benchmarks.
CS-TAG ( Yan et al., 2023 ) , GLBench ( Li et al., 2024 ) , TSGFM ( Chen et al., 2024b ) and LLMNodeBed ( Wu et al., 2025a ) re-run many methods under one protocol each.
LLMNodeBed finds that LLMs help most when labels are scarce.
These benchmarks do not systematically report the cheap baseline families we use: bag-of-words with a linear model, and label propagation or Correct & Smooth.
Unlike them, we evaluate on each paper’s own splits and compare against the numbers that paper reports.
Evaluation critiques and simple baselines.
Split choice and unequal tuning distort GNN comparisons ( Shchur et al., 2019 ; Errica et al., 2020 ; Platonov et al., 2023 ) , and many benchmarks barely need structure ( Liu et al., 2022 ; Bechler-Speicher et al., 2024 ; Katsman et al., 2024 ; Bechler-Speicher et al., 2025 ) .
For GraphLLMs, Petkar et al. (2026) and Xu et al. (2025) argue that current benchmarks can be solved largely from one modality, and a review proposes a reporting standard for graph learning ( Kurashkin et al., 2026 ) .
Strong simple baselines include propagated features with simple heads ( Wu et al., 2019 ; Frasca et al., 2020 ; Rubio-Madrigal and Burkholz, 2026 ) , Correct & Smooth ( Huang et al., 2021 ) , and gradient-boosted trees on neighbor aggregates ( Bazhenov et al., 2026 ) .
Concurrent work.
NodeGround ( Lee et al., 2026 ) and Platonov et al. (2026) re-evaluate graph foundation models against tuned GNNs, without LLM-based methods and on their own splits.
A concurrent submission finds that most published gaps on standard node-classification benchmarks fall below the benchmarks’ statistical resolution ( Anonymous, 2026 ) ; it does not cover GraphLLM methods or compare numbers across papers.
3 Evaluation Protocol
We specified the initial protocol before the pilot runs.
Later changes are logged with dates.
Among them are two reporting rules introduced after we inspected interim results: named family representatives, and a reference rule that rescales reported standard deviations.
3.1 Splits, data and metrics
For each paper we use its own train/validation/test split and its own node texts.
LLM4HeG and the LLaGA split used by KCoT ship masks; we use them as-is and check that they are disjoint and agree with the node identifiers in the instruction files.
For LLMNodeBed we re-implement the split function and seed sequence of the released code.
We have not verified that nothing else consumes the NumPy random state before the split in the original pipeline, so these splits are likely, but not proven, to be identical.
LLMNodeBed’s semi-supervised WikiCS split cannot be recovered from the released code (its released masks have 20 columns), so that task is excluded.
We report the paper’s own metric, accuracy, on its own test nodes.
External files are treated as untrusted: released code is read, never executed, and pickled graph objects are loaded with an allow-list of data-container types only.
3.2 Baselines and representatives
Every baseline uses only node texts, the graph and training labels ( Table 1 ).
TF-IDF statistics and SVD projections are fitted on all nodes without labels. This is the same transductive feature access a GNN has.
Each family is reported through one representative fixed by name.
TF-IDF applies logistic regression to TF-IDF features, without the graph.
TF-IDF+Prop propagates TF-IDF as [ X , A ^ ​ X , … , A ^ K ​ X ] [X,\hat{A}X,\dots,\hat{A}^{K}X] before logistic regression, with the input fixed to TF-IDF.
C&S applies Correct & Smooth ( Huang et al., 2021 ) to the TF-IDF predictions, and e5-MLP is an MLP on frozen e5-large-v2 embeddings ( Wang et al., 2024 ) , without the graph.
We do not report the best of our baselines per dataset as a result.

3.3 Tuning and selection
Each representative receives 50 trials of TPE search ( Akiba et al., 2019 ) over a fixed space ( Appendix B ).
The trial with the best validation accuracy is selected, with ties broken by validation log-loss.
Test scores are recorded for every trial for later analysis, but selection uses validation scores only.
Each tuning run uses its own sampler and model seed.
On LLM4HeG’s fixed split we match its 10 runs; on the LLaGA split, where KCoT reports no run count, we also use 10.
LLMNodeBed reports 4 runs: on its stored masks we perform 4 tuning runs, and where it re-draws splits per run we use one tuning run per re-drawn split.
3.4 Reference and statistics
The reference for each task is the highest mean that the paper reports for an LLM-based method in the matched evaluation setting: LLM4HeG Table 2, KCoT Table 2 (Single Focus, node classification) and LLMNodeBed Table 2 (semi-supervised and supervised).
It is a best-of- N N over methods on the paper’s test set, which makes it a demanding comparison for a single fixed baseline; we do not claim that this makes our tests conservative.
LLM4HeG and LLMNodeBed compute their reported standard deviations with np.std , i.e. the population standard deviation.
We rescale these by n / ( n − 1 ) \sqrt{n/(n-1)} to sample standard deviations.
We then apply Welch’s t t -test from summary statistics, Holm-corrected over the table.
Where a paper reports no standard deviation or run count (KCoT), we give the difference only and mark significance as not assessable.
A non-significant difference is not evidence of equivalence.
Our runs and the paper’s runs share a split but are not paired, so the test treats them as independent samples.
On the 12 tasks with fixed masks, the compared spread reflects training randomness only; on the 12 tasks with re-drawn splits, it also reflects variation in the partition of the observed graph.
On fixed masks the test therefore omits test-set sampling variance, which on graphs is inflated by dependence between test nodes ( Anonymous, 2026 ) .
These summary-statistic tests concern the evaluated runs and do not establish generalization to newly sampled graphs.
3.5 Pipeline check
With the same code we reproduced GCN ( Kipf and Welling, 2017 ) and SGC ( Wu et al., 2019 ) on the public Planetoid splits ( Yang et al., 2016 ) ( Appendix C ).
This validates the training and evaluation code, not every data loader.

Do the gains survive?
Several reported gains remain substantial under our comparison.
On many of the evaluated tasks, however, a cheap baseline representative fixed by name comes within a few points of the best LLM-based result.
The code audit in Section 5 identifies separate evaluation risks; it does not establish that published gains arise from them.
5 What the Released Code Shows
We read the released code of several recent GraphLLM papers next to their tables.
Below are problems we verified in the source files, pinned to specific commits in Appendix D .
In some cases we cannot determine whether the published tables were produced with the released code; we say so where it applies.
A text–label misalignment in a released loader.
Petkar et al. (2026) report 28.7–29.7% accuracy on Cora for text-only (soft-prompted LLM) models and conclude that Cora is “structurally sufficient”.
Their released loader takes the text of node i i from the paper ID in row i i of the original cora.content file.
It takes the label of node i i from the PyG Planetoid version of Cora.
The two files order nodes differently: position by position, the two label sequences agree on only 18.4% of nodes.
Matching rows by their bag-of-words vectors yields a consistent mapping between the class labels of the two files.
We re-implemented the loading logic without executing their code, which leaves 2,692 nodes after their de-duplication.
We then trained TF-IDF + logistic regression on 5 of their seeded 60/20/20 splits.
With their alignment it reaches 29.1 ± \pm 1.5%, close to the majority-class rate of 30.4%; with the correct alignment it reaches 80.9 ± \pm 1.2%.
In this reconstruction, text alone is highly informative on Cora, and the misalignment alone brings TF-IDF to near the majority-class rate.
We cannot establish whether this loader produced the published text-only result.
Selection on the test set.
We found test-based selection at three levels.
LLM4HeG ( Wu et al., 2025b ) picks its learning-rate × \times weight-decay grid point by the highest mean test accuracy over ten seeds.
Sweep configurations in GIT’s repository history ( Wang et al., 2025b ) maximize final/test_mean .
The LLM–GNN co-teaching README ( Peng et al., 2026 ) reports the “round-best” accuracy over training rounds that log test accuracy.
In the released baseline script of Wang et al. (2026) , GNN checkpoints are selected by test accuracy; we cannot establish whether the published baseline rows used this script.
We also reconstructed the LLM4HeG grid-selection procedure (same grid, seeds and epoch rule) for FAGCN, GraphSAGE and an MLP on their features.
In this reconstruction, test-based selection raises accuracy by 0.30 pp on average and by at most 0.91 pp over 15 dataset–model pairs.
We do not transfer this size to the full LLM4HeG pipeline.
Labels of test-pool nodes used in training.
GNN-as-Judge ( Xu and Ding, 2026 ) retrains its GNN judge on “agreed” nodes, where the GNN and the LLM predict the same class.
These nodes are drawn from the test-mask pool, and the retraining uses their ground-truth labels.
The retrained GNN’s predictions then become targets for LLM fine-tuning.
The same code evaluates LLM rows on 1,000 randomly sampled test nodes but GNN rows on the full test set.
We cannot tell whether the published tables used this code path.
Reused baseline numbers.
In the node-classification part of the Single Focus block of KCoT’s Table 2 ( Xie et al., 2026 ) , 32 of 32 baseline cells are identical to LLaGA’s Table 1 ( Chen et al., 2024a ) .
The paper states that it adopts LLaGA’s settings; we found no statement that these numbers are taken from LLaGA.
One split, different numbers.
On LLaGA’s PubMed split, LLaGA reports 95.03% for itself, while RGLM ( Zhang et al., 2026 ) reports 90.34% for LLaGA.
KCoT reports 94.23% for GraphGPT, whereas RGLM reports 81.76%.
The split is shared, but the configurations are not documented to match: RGLM’s released evaluation script uses SBERT node features ( Appendix D ), which need not match the features behind the other numbers.
Without the full configuration, differences of 4.7 and 12.5 points show that such numbers are not comparable across papers, not that either method is unstable.
Baselines far below standard results.
UniGraph ( He et al., 2025 ) reports a supervised GCN on DeBERTa features at 48.42% on Cora with 20 labels per class. A standard GCN on bag-of-words features with the same label budget reaches 81.5% ( Kipf and Welling, 2017 ) ; the features differ, and we have not established that the rest of the protocol is identical.
6 Recommendations
1.
Report cheap baselines on your split , with the same tuning budget as your method: TF-IDF with a linear model, label propagation or Correct & Smooth on top of it, and frozen embeddings from the LLM your method uses.
2.
Select on validation only , at every level: epochs, checkpoints, grids and rounds.
3.
Release the split (masks or seeded code) and the exact text version.
4.
Report effect sizes with uncertainty : mean, standard deviation and number of runs. A non-significant difference is not evidence of equivalence.
5.
Mark copied numbers , and copy only when splits, features and tuning match.
6.
Evaluate all rows on the same test nodes.
7 Limitations
We do not re-run the proposed methods; we compare against reported numbers, so our conclusions concern the published claims.
Results are conditional on the specified search spaces, the 50-trial budget and the chosen representatives.
We cover three studies whose splits we could recover. LLMNodeBed’s splits are reconstructed from its released code and are likely, but not proven, to be identical, and studies without recoverable splits are not compared.
Finally, the code findings describe the released code at the pinned commits, which need not be the code that produced the published tables.

Appendix A Data, Splits and Node Order
LLM4HeG.
•
Source: the authors’ dataset/*.npz files (Git LFS) at commit 99c97e3 .
•
Each file has a single train/val/test mask (48/32/20; Amazon 50/25/25). The “10 splits” in the training script are ten seeds on this split.
•
Texts: node_texts .
LLaGA split (KCoT).
•
Source: LLaGA’s processed_data.pt for Cora and PubMed, from the data release linked in the authors’ README, with stored random 6:2:2 masks.
•
We assert that the stored masks equal the node ids in sampled_2_10_{train,val,test}.jsonl .
•
Cora node order equals cora.content (all 2,708 feature rows and labels coincide).
LLMNodeBed.
•
Source: the authors’ Hugging Face dataset xxwu/LLMNodeBed , revision bba716f (recorded in the download metadata).
•
Files: cora , citeseer , pubmed , wikics , instagram , reddit , history (Books), photo and computer , each as .pt .
•
Semi-supervised: stored masks, except Books/Photo/Computer, whose 10/10/60 splits are regenerated per run seed as in the released code.
•
Supervised: np.random.seed ( s ) (s) followed by a shuffle and 60/20/20 cut points, for s = 0..3 s=0..3 . ogbn-arxiv uses the stored OGB split.
•
Semi-supervised WikiCS is excluded because its 20-column masks cannot be indexed by the released code.
•
The Cora/PubMed node order in this release differs from the LLaGA/TAPE order, so node ids are never mixed across releases.
Seeds: 0–9 for LLM4HeG and the LLaGA split; 0–3 for LLMNodeBed.
