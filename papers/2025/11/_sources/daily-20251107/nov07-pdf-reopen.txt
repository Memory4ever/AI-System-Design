L6@P0: ABSTRACT
L7@P0: The proliferation of 100B+ parameter Large Language Models (LLMs) with 100k+ context length support
L8@P0: have resulted in increasing demands for on-chip memory to support large KV caches. Techniques such as
L9@P0: StreamingLLM (Xiao et al., 2024b) and SnapKV (Li et al., 2024) demonstrate how to control KV cache size
L10@P0: while maintaining model accuracy. Yet, these techniques are not commonly used within industrial deployments
L11@P0: using frameworks like vLLM or SGLang. The reason is twofold: on one hand, the static graphs and continuous
L12@P0: batching methodology employed by these frameworks (Kwon et al., 2023; Zheng et al., 2024) make it difficult to
L13@P0: admit modifications to the standard multi-head attention algorithm (Chen et al., 2023), while on the other hand,
L14@P0: the accuracy implications of such techniques on modern instruction-following and reasoning models are not well
L15@P0: understood, obfuscating the need for implementing these techniques. In this paper, we explore these accuracy
L16@P0: implications on Llama-3.1-8B-Instruct and DeepSeek-R1, and develop SnapStream, a KV cache compression
L17@P0: method that can be deployed at scale. We demonstrate the efficacy of SnapStream in a 16-way tensor-parallel
L18@P0: deployment of DeepSeek-671B on SambaNova SN40L accelerators running at 128k context length and up to
L19@P0: 1832 tokens per second in a real production setting. SnapStream enables 4× improved on-chip memory usage and
L20@P0: introduces minimal accuracy degradation on LongBench-v2, AIME24 and LiveCodeBench. To the best of our
L21@P0: knowledge, this is the first implementation of sparse KV attention techniques deployed in a production inference
L22@P0: system with static graphs and continuous batching.

L248@P2: 2.2 Reconfigurable Dataflow Units (RDUs)
L249@P2: Built on a dataflow architecture, the SN40L AI accelerator
L250@P2: optimizes AI training and inference tasks. Prior works (Prabhakar et al., 2024; Prabhakar, 2024) describe the architecture
L251@P2: in more detail. This section provides a brief overview of key
L252@P2: architectural components. Each socket features four RDU
L253@P2: cores, I/O blocks for connecting to DDR, HBM, Peer-toPeer (P2P) links, and a host system (see Figure 2). A socket
L254@P2: can perform 638 TFLOPs of BF16 operations and has 520
L255@P2: MB of on-chip SRAM. Each socket also interfaces with 64
L256@P2: GB of HBM memory providing 1.6 TB/s of peak bandwidth,
L257@P2: and 1.5 TB of DDR memory providing over 100 GB/s of
L258@P2: peak bandwidth. A Top-Level Network (TLN) connects tile
L259@P2: components to the IO blocks. Each socket consists of 1040
L260@P2: Pattern Compute Units (PCUs), which provide systolic and
L261@P2: streaming compute capabilities, and 1040 Pattern Memory
L262@P2: Units (PMUs) which provide program-managed on-chip
L263@P2: memory for storing tensors. Collectively, a PCU and PMU
L264@P2: block is known as a Fused Compute Memory Unit (FCMU).
L265@P2: Additionally, the Address Generation and Coalescing Units
L266@P2: (AGCUs) serve as the interface to external memory and
L267@P2: other sockets.

L333@P3: 2.5 StreamingLLM
L334@P3: StreamingLLM (Xiao et al., 2024b) is a technique that enables LLMs to process sequences beyond their fixed context
L335@P3: windows, effectively supporting unbounded streaming inputs. Conventional LLMs are limited by a fixed attention
L336@P3: window, which constrains their ability to maintain coherence over long sequences. StreamingLLM addresses this
L337@P3: by retaining a small set of attention sink tokens (the initial
L338@P3: prompt tokens that consistently receive high attention across
L339@P3: decoding steps) together with the most recent tokens. These
L340@P3: tokens act as stable anchors that preserve long-term context,
L341@P3: allowing the model to maintain continuity without storing
L342@P3: the entire KV cache.
L343@P3: The core mechanism of StreamingLLM is a compact KV
L344@P3: cache strategy that combines these sink and recent tokens
L345@P3: to form a reduced attention context. During decoding, the
L346@P3: model attends primarily to this subset, substantially lowering memory usage while preserving model accuracy.

L399@P3: 3.1 KV Cache Structure
L400@P3: In SnapStream, the KV cache has three distinct components,
L401@P3: indexed by their sequence position relative to the prefill
L402@P3: length L:
L403@P3: • Sink tensors k1, ..., kLsink
L404@P3: • Recent tensors kL−Lrecent , ..., kL
L405@P3: • Top-K tensors ktopk:1, ..., ktopk:K
L406@P3: See Figure 3(b) for a depiction of the three components in
L407@P3: yellow, green, and purple, respectively. Each component is
L408@P3: initialized during prefill, with top-K tensors appended to
L409@P3: the sink and recent tensors after any padding. Let Lsr =
L410@P3: Lsink + Lrecent; then, the exact structure of the KV cache has
L411@P3: two cases:
L412@P3: 3.1.1 Case 1: L < Lsr
L413@P3: In this case, the key tensor cache is constructed during
L414@P3: prefill as k1, ..., kL, kpad:L+1, .., kpad:Lsr, ktopk:1, .., ktopk:K.
L415@P3: This structure is no different than that described in Section 2.3, as the Top-K tokens xtopk:· are themselves padding
L416@P3: tensors in this case. Accordingly, during decoding, the KV
L417@P3: cache is updated in-place in the same manner as previously
L418@P3: described.
L419@P3: 3.1.2 Case 2: L ≥ Lsr
L420@P3: In this case, the key cache is constructed as
