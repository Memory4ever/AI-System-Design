L169: 
L170: Work submitted to arXiv undergoes a series of quality assurance checks as part of cite83†moderation . This helps authors by ensuring their work will be discoverable and archivable and helps readers find relevant research that is in a consistent, readable format.
L171: Quality assurance checks can take between one to four days to resolve, sometimes longer. Authors will be notified by email if any issues are found in the submission. Authors will also receive an email when the submission is posted publicly.
L172: Submissions to arXiv are typically posted publicly Sunday through Thursday, with no announcements Friday or Saturday. You can check the cite88†current arXiv time†arxiv.org , which also shows the next deadline. Submissions are made public as part of the cite27†scheduled announcement process . This includes new submissions as well as cite35†replacements , cite44†withdrawal notices , cite30†cross listings and cite32†journal reference .
L173: ## A note about arXiv-id assignments
L174: 
L175: The final cite49†arXiv identifier is assigned as part of the automated process when the work is announced. It is not possible to generate or to be provided with the arXiv identifier or DOI in advance. Submitting authors will receive an email when the work is announced and it will appear on their account dashboard.
L176: Note: The arXiv identifier cannot be back-dated, so identifiers will be assigned in the month of first announcement. It may be the case that a submission appears in a different identifier month than its original submission date due to various factors.

L7@P0: Abstract
L8@P0: AI models excel at creating content, but typically render it with static, predefined
L9@P0: interfaces. Specifically, the output of LLMs is often a markdown “wall of text”.
L10@P0: Generative UI is a long standing promise, where the model generates not just the
L11@P0: content, but the interface itself. Until now, Generative UI was not possible in a
L12@P0: robust fashion. We demonstrate that when properly prompted and equipped with
L13@P0: the right set of tools, a modern LLM can robustly produce high quality custom UIs
L14@P0: for virtually any prompt. When ignoring generation speed, results generated by
L15@P0: our implementation are overwhelmingly preferred by humans over the standard
L16@P0: LLM markdown output. In fact, while the results generated by our implementation
L17@P0: are worse than those crafted by human experts, they are at least comparable in
L18@P0: 44% of cases. We show that this ability for robust Generative UI is emergent,
L19@P0: with substantial improvements from previous models. We also create and release
L20@P0: PAGEN, a novel dataset of expert-crafted results to aid in evaluating Generative
L21@P0: UI implementations, as well as the results of our system for future comparisons.
L22@P0: Interactive examples can be seen at generativeui.github.io.
L23@P0: 1 Introduction
L24@P0: AI models today generate content: text, code, images, videos, etc. However, the results of these
L25@P0: powerful tools are often presented using hard-coded and pre-designed user interfaces. Generative UI
L26@P0: is a new modality where the AI model generates not only content, but the entire user experience. This
L27@P0: results in custom interactive experiences, including rich formatting, images, maps, audio and even
L28@P0: simulations and games, in response to any prompt (instead of the widely adopted “walls-of-text”).
L29@P0: An instant AI team for each prompt. Today, rich visual interfaces exist for common user journeys.
L30@P0: Specifically, teams composed of product managers, UX designers, and engineers work for extended
L31@P0: periods of time to build amazing rich experiences for broad prompt categories, shared by many users.
L32@P0: Generative UI enables us to spin up an instant (AI-based) product management, UX design, and
L33@P0: engineering teams, to build an interactive experience, over the course of a minute, for a specific
L34@P0: prompt. While not as competent as human experts, Generative UI enables custom experiences for
L35@P0: any prompt.
L36@P0: At present, the prevalent UI for interacting with LLMs is a markdown-based chat interface. Specifically, the model outputs markdown (that can include heading, emojis, tables, code-blocks, etc.).
L37@P0: These are significantly easier for humans to consume than raw text, yet results created by our Generative UI implementation are overwhelmingly preferred over both (see Table 2). To evaluate our
L38@P0: implementation of Generative UI we use human rater preference compared to a set of baselines. We

L45@P2: 2 Method
L46@P2: Our Generative UI implementation outputs a single fully-generated web page and a set of accompanying assets, such as images. The page is rendered as-is on the user’s browser. See Figure 2 for a
L47@P2: high level overview of the system.

L49@P2: As depicted in Figure 2, we employ 3 main components:
L50@P2: 1. A server exposes several endpoints enabling access to key tools, such as image generation
L51@P2: and search. The results can be made accessible to the model (increasing quality) or sent
L52@P2: directly to the user’s browser (increasing efficiency).
L53@P2: 2. Carefully crafted system instructions. These in turn include: (1) the goal (2) planning and
L54@P2: thinking guidelines, (3) examples, and (4) a large set of technical instructions including
L55@P2: formatting guidelines, tool endpoints manual, and tips for avoiding common errors. These
L56@P2: contribute to the quality of the generated results (see Appendix A.5 for an illustrative prompt
L57@P2: from an early research prototype).
L58@P2: 3. A set of post-processors. These lightweight components address a set of remaining common issues. Additional post processors deal with error reporting and page analysis. See
L59@P2: Appendix A.6.

L132@P5: 4 The PAGEN Dataset
L133@P5: To facilitate a clear and consistent evaluation of our Generative UI implementation, we compare its
L134@P5: results to expert-human-made websites. To that end, we constructed a human-expert-made dataset
L135@P5: of websites for a sample of prompts (using the LMArena and Info-Seeking prompt sets used for
L136@P5: evaluation in this paper) . We call this dataset PAGEN and make it available publicly, in hopes of
L137@P5: encouraging consistent comparisons with future work.
L138@P5: We considered several methodologies for collecting these human made websites, including utilizing
L139@P5: existing public websites, using a pre-existing dataset, and engaging a specific provider to develop all
L140@P5: of the necessary websites. Ultimately, we opted to construct our own dataset by contracting highly
L141@P5: rated independent web developers sourced online. This decision was driven by a desire to create a
L142@P5: clear pairing of a specific user prompt and the resulting website, maintain uniformity in time and
L143@P5: investment across websites, ensure clear and consistent guidelines for all use cases (e.g. encourage
L144@P5: interactivity and high quality visuals), ensure that the user experience is prioritized without any
L145@P5: foreign considerations (such as SEO optimizations), ensuring no copyrighted content was used, and
L146@P5: ensuring the consistency of the tools used (e.g. we encouraged using AI tools), and the diversity and
L147@P5: quality of the contractors. See more details in Appendix A.4.
L148@P5: 5 Related Work
L149@P5: The concept of automatically generating user interfaces from high-level descriptions has been a
L150@P5: long-standing ambition in Human-Computer Interaction (HCI) and software engineering. Our work
L151@P5: builds upon several key areas of research, including natural language interfaces, code generation by
L152@P5: large language models (LLMs), and evaluation methodologies for generative systems.
L153@P5: UI Generation from Natural Language Early efforts in this domain often relied on structured
L154@P5: inputs or constrained languages to generate interfaces for specific platforms [Puerta et al., 1994,
L155@P5: Landay and Myers, 1995]. With the rise of deep learning, approaches evolved to translate visual
L156@P5: inputs, such as hand-drawn mockups or screenshots, directly into code [Beltramelli, 2017, Gui et al.,
L157@P5: 2025]. The recent proliferation of powerful LLMs has enabled the generation of UI code directly
L158@P5: from unstructured natural language prompts. Our approach differs by tasking the LLM to generate
L159@P5: entire, interactive, and data-driven web applications from a single prompt, effectively acting as an
L160@P5: autonomous web developer.
L161@P5: Large Language Models for Code Generation The capabilities of our system are fundamentally
L162@P5: enabled by the advancements in code generation by LLMs. This field gained prominence with models
L163@P5: like OpenAI’s Codex [Chen et al., 2021], which demonstrated a strong ability to translate natural
L164@P5: language into functional code across various languages. Subsequent research has produced a host
L165@P5: of powerful code-generating models, such as AlphaCode [Li et al., 2022] and Code Llama [Rozière
L166@P5: et al., 2024], that are trained on vast datasets of public code. While these models are often used as
L167@P5-6: 6assistants for developers (e.g., GitHub Copilot), our work leverages this underlying capability for a
L168@P6: different purpose: the autonomous end-to-end generation of a complete user-facing product, not just
L169@P6: a code snippet. As we demonstrate, this ability to architect and implement a full application appears
L170@P6: to be an emergent property of the most recent state-of-the-art models.
L171@P6: Interaction Paradigms for AI The standard user interface for interacting with LLMs is a chatbased format where the model’s output is rendered as markdown. While an improvement over plain
L172@P6: text, this modality is inherently static. Some systems have explored a middle ground, which we
L173@P6: term "Templated UI," where an LLM can invoke and populate predefined, interactive widgets from a
L174@P6: fixed library to enrich its responses [Pinsky, 2023]. Our work represents a paradigm shift away from
L175@P6: both static markdown and constrained templates. By allowing the model to generate the UI itself,
L176@P6: we unlock the potential for bespoke, dynamic, and highly contextual experiences, such as games,
L177@P6: simulators, and custom data visualizations, that are tailored to the specific needs of each prompt.
L178@P6: 6 Discussion
L179@P6: We presented a novel implementation of Generative UI, where the model can produce a custom
L180@P6: visual interactive interface for any prompt. We show that when ignoring generation speed, our results
L181@P6: are overwhelmingly preferred by users over the standard markdown UI (in 83% of evaluated cases,
L182@P6: see Table 2). We further show that Generative UI is an emergent capability of the newest and most
L183@P6: capable models. As shown in Tables 3 and 4, the use of our newest models results in a significant
L184@P6: increase in user preference and a significant reduction in generation errors, vs. previous models. Our
L185@P6: implementation relies on a combination of exposing a set of tools in an easy-to-use fashion, detailed
L186@P6: system instructions (see Appendix A.5), and a series of post-processors to correct common issues.
L187@P6: PAGEN We created the PAGEN dataset - a curated dataset of expert built web sites for LLM
L188@P6: prompts (see Section 4). While the pages created by the expert humans are better than those created
L189@P6: by our system, we show that our Generative UI implementation can at least match its quality in 44%
L190@P6: of cases. We are making PAGEN available publicly to enable easier evaluation by future research.
L191@P6: Limitations and Future Directions One primary limitation and an important area for future
L192@P6: research is the slow generation speed, which can often take a minute or two. Streaming the generated
L193@P6: results allows the users to start interacting with a partially rendered page, reducing this number by
L194@P6: about a half. Optimizing the use of techniques such as speculative decoding [Leviathan et al., 2022]
L195@P6: could result in further improvements. A second important limitation of Generative UI is that errors
L196@P6: (Javascript errors, CSS errors, HTML errors, etc.) can occasionally occur.
L197@P6: A First Step Towards a New Paradigm LLMs transformed the world’s finite collections of texts
L198@P6: to an infinite collection, where an ephemeral text is created on the spot for any need. This turned
L199@P6: out to be very useful. It is early days for Generative UI, and important limitations exist. Yet, we are
L200@P6: excited about a future where users don’t have to pick from a finite library of applications or visual
L201@P6: pages, but instead, they have access to an infinite catalog, where the right ephemeral interface is
L202@P6: generated on the spot tailored for their need.
