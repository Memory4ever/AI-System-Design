L118: ## III Proposed 3D Flash PIM Architecture
L119: ### III-A Challenges in Developing 3D Flash PIM
L120: Directly using the same flash architecture for PIM has a major challenge in terms of latency. Typically, a 3D NAND flash plane has 4 rows per block, 700-2,800 blocks per plane, and 64-128 stacks with 20-50$\mu$s read latency [cite47†9 , cite48†10 ]. This substantial read latency introduces a significant delay in token generation when making a 3D flash PIM with the conventional plane size, as shown in Fig. cite49†5 .
L121: It takes 1.4s to generate an output token with 8-bit quantized OPT-30B using the naïve implementation of 3D flash PIM. By selecting the proper plane size (Section cite12†III-B ) and bus architecture within the die (Section cite13†III-C ), we can significantly improve the time required to generate an output token by 210$\times$ (i.e., 2.5$\times$ faster than four RTX4090 with vLLM).
L122: To meet the low latency requirements of emerging applications, a new type of NAND flash, e.g., Z-NAND [cite50†11 ], has been introduced that provides the read latency of 3$\mu$s with a reduced page size. Reducing the page size shrinks the WL region, effectively reducing the load capacitance of WL, equivalently $t_{\text{decWL}}$ in Eq. (cite51†3 ). Other components that determine the plane size, i.e., the number of blocks and stacks, also affect the latency.
L123: For instance, with more rows (= BLSs), the BL gets longer, which increases the $t_{\text{pre}}$ in Eq. (cite51†3 ).

L147: ### III-B 3D NAND Plane Configuration
L148: A 3D NAND flash plane can be configured by ‘$N_{\text{row}}\times N_{\text{col}}\times N_{\text{stack}}$’. These size parameters affect the lengths of BL, BLS, WL, and string, which change the resistance $R_{x}$ and the capacitance $C_{x}$ of them. For instance, $R_{\text{WL}}$ and $C_{\text{WL}}$ are proportional to $L_{\text{WL}}=L_{\text{cell}}+L_{\text{staircase}}$. Thus, with $R_{x}$ and $C_{x}$ calculated, we can estimate the latency of a 3D flash PIM for a given size configuration by

L150:  | $\displaystyle t_{\text{decBLS}}$  | $\displaystyle\approx h\bigl(\!R_{\text{BLS}}\!\times\!C_{\text{BLS}}/2\!\bigr)\!,$  |  | (5b)
L151:  | $\displaystyle t_{\text{decWL}}$  | $\displaystyle\approx h\bigl(\!R_{\text{s}}\!\times\!(C_{\text{cell}}\!+\!C_{\text{stair}})\!\bigr),$  |  | (5c)
L152: where $h(\tau)\propto\tau^{\tiny 1.5}$ is the Horowitz delay equation [cite56†12 ], where $\tau$ is the RC time constant (only dominant terms are shown). The precharge latency ($t_{\text{pre}}$) is mainly determined by the latency of turning on the $N_{\text{col}}$ precharge transistors through a switch transistor (1^{st} term) and the latency of precharging each BL (2^{nd} term).
L153: The BLS decoding latency ($t_{\text{decBLS}}$) is dominated by $R_{\text{BLS}}\times C_{\text{BLS}}$ when $N_{\text{col}}$ is less than 16K. L156: Obviously, as $N_{\text{row}}$, $N_{\text{col}}$, or $N_{\text{stack}}$ becomes larger, the PIM latency increases due to increased RC values in Eq. (cite58†5 ). L158: The $t_{\text{decWL}}$ has the sub-linear dependence on $N_{\text{col}}$ or $N_{\text{stack}}$ since each sizing parameter affects either $C_{\text{cell}}$ or $C_{\text{stack}}$.
L159: As shown in Fig. cite57†6 b, the energy consumption of 3D flash PIM also increases as $N_{\text{row}}$, $N_{\text{col}}$, and $N_{\text{stack}}$ become larger. The energy consumptions for some operations are defined as

L307: ##### Expert Role Specialization
L308: 
L309: To further enhance the adaptability of MoE and address the limitation of homogeneous expert types, we explicitly categorize experts into three distinct roles:
L310: 
L311:   * •
L312: 
L313: Routed Experts: These are task-specific experts responsible for modeling domain-specific knowledge. They are dynamically activated according to the proposed dynamic capacity routing strategy.
L314: 
L315:   * •
L316: Shared Experts: These experts capture general, domain-independent knowledge. Unlike routed experts, shared experts are persistently activated for all tokens, ensuring that common knowledge is always available during inference.
L317: 
L318:   * •
L319: Null Experts: These are “empty” experts whose output is identically zero. They serve as a mechanism for selective forgetting, effectively removing outdated or irrelevant knowledge from the model’s output. Null experts are also dynamically activated via the dynamic capacity routing strategy.
L320: This role specialization enables the model to (i) allocate computational resources according to token-specific knowledge demands, (ii) maintain a persistent general-knowledge backbone via shared experts, and (iii) selectively forget outdated or irrelevant knowledge through null experts, thereby improving both adaptability and controllability of MoE-based architectures.
L321: ##### Dynamic Capacity Routing
L322: 
L323: Vanilla MoE applies a fixed number of experts to every token, ignoring variations in token complexity and knowledge demand. We address this limitation by introducing a dynamic capacity routing strategy, which determines the number of routed experts for each token based on a Top-P sampling. Formally, let the router produce a probability vector over routed experts for token $i$:
L324:  | $$\mathbf{p}^{(i)}=[p^{(i)}_{1},p^{(i)}_{2},\dots,p^{(i)}_{N_{r}}],\quad\sum_{j=1}^{N_{r}}p^{(i)}_{j}=1,$$  |
L325: 
L326: where $N_{r}$ is the number of routed experts. We sort experts in descending order of $p^{(i)}_{j}$, obtaining a permutation $\pi^{(i)}$ such that:
L327: 
L328:  | $$p^{(i)}_{\pi^{(i)}(1)}\geq p^{(i)}_{\pi^{(i)}(2)}\geq\dots\geq p^{(i)}_{\pi^{(i)}(N_{r})}.$$  |
L329: 
L330: The set of activated routed experts for token $i$ is then:
L331:  | $$\mathcal{R}_{i}=\left\{\pi^{(i)}(1),\dots,\pi^{(i)}(k_{i})\right\},\quad k_{i}=\min\left\{k\,\middle|\,\sum_{j=1}^{k}p^{(i)}_{\pi^{(i)}(j)}\geq P\right\},$$  |
