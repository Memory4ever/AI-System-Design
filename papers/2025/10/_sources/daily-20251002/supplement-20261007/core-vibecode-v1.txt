Abstract
We propose VibeCodeHPC, an automatic tuning system for HPC programs based on multi-agent LLMs for code generation. VibeCodeHPC tunes programs through multi-agent role allocation and iterative prompt refinement. We describe the system configuration with four roles: Project Manager (PM), System Engineer (SE), Programmer (PG), and Continuous Delivery (CD). We introduce dynamic agent deployment and activity monitoring functions to facilitate effective multi-agent collaboration. In our case study, we convert and optimize CPU-based matrix–matrix multiplication code written in C to GPU code using CUDA. The multi-agent configuration of VibeCodeHPC achieved higher-quality code generation per unit time compared to a solo-agent configuration. Additionally, the dynamic agent deployment and activity monitoring capabilities facilitated more effective identification of requirement violations and other issues.
Index Terms: Code Generative AI, Auto-tuning, Vibe Coding, Multi AI Agents, Software Productivity
I Introduction
I-A Background
In recent years, large language models (LLMs) have demonstrated remarkable capabilities in code generation, automatically transforming natural language specifications into executable programs. Trained on massive corpora of source code and natural language text, these models have found applications in rapid prototyping, in code refactoring, and in automated testing. However, while LLM-based systems have achieved promising results in generating functionally correct code, their application to performance-critical domains such as High-Performance Computing (HPC) remains limited.
HPC programming imposes strict requirements beyond functional correctness. Applications in this domain must achieve optimal execution time, minimize power consumption, and balance numerical accuracy with computational speed. Moreover, HPC software typically relies on parallel programming models – MPI, OpenMP, CUDA, and OpenACC – which requires appropriate strategy selection based on application characteristics and target execution environments. Meeting these demands requires not only correct code generation but also architecture-aware performance tuning and parallelization.
Despite the rapid progress of LLMs, several challenges hinder their effective use for HPC code generation:
1.
Limited integration with auto-tuning: Auto-tuning systematically explores parameter spaces to find optimal configurations—a proven approach for performance optimization. However, current LLM-based systems lack full integration with auto-tuning workflows, often generating code without performance optimization. The autonomous application of domain-specific knowledge, such as memory access optimization and communication design, remains limited.
2.
Lack of HPC-specific considerations: Current code generation systems rarely address HPC-specific requirements including parallelization strategy selection, numerical accuracy trade-offs, and power efficiency. Notably, these systems cannot automatically select optimal parallelization methods for given workloads and environments.
3.
Immature iterative improvement cycles: Performance evaluation, feedback integration, and iterative refinement – essential for self-optimizing code generation – are not well established in existing systems.
I-B Vibe Coding and VibeCodeHPC
To address these challenges, we apply the Vibe Coding paradigm [1][2] to performance tuning. Vibe Coding enables rapid prototyping through code generation and performance evaluation, even when specifications remain uncertain or incomplete.
Building on this paradigm, we propose VibeCodeHPC, a novel code generation framework for HPC applications that tightly integrates auto-tuning into the generation and refinement process. This framework bridges the gap between LLM capabilities and HPC requirements through systematic performance optimization.
I-C Aims and Contributions
Current LLM-based code generation systems have successfully interpreted natural language specifications and produced executable code. However, in performance-critical domains such as HPC, several challenges remain:
1.
Auto-tuning integration: We propose an iterative prompting mechanism incorporating performance feedback via auto-tuning, enabling performance-guided code refinement. Architecture-aware optimization is achieved through embedded auto-tuning parameter selection.
2.
Parallelization and accuracy control: Our system standardizes code generation for MPI, OpenMP, CUDA, and OpenACC while incorporating user-defined trade-offs between numerical accuracy and computational speed.
3.
Multi-agent iterative refinement: We design a multi-agent architecture where specialized AI agents handle distinct auto-tuning tasks, enabling continuous improvement of generated HPC code quality.
4.
Dynamic agent management: Multi-agent systems require runtime agent deployment and activity monitoring for flexible processing and appropriate instruction dispatch. We propose implementation and prompt-engineering approaches to realize these capabilities.
By combining LLM-based code generation with auto-tuning, HPC-specific optimization, and multi-agent collaboration, VibeCodeHPC bridges the gap between functional correctness and peak performance in autonomous HPC code development.

The remainder of this paper is organized as follows. Section II presents VibeCodeHPC in detail. Section III evaluates the performance of the proposed methods. II VibeCodeHPC
II-A System Overview
We propose VibeCodeHPC, a code generation framework for HPC applications that integrates LLM-driven code synthesis with auto-tuning and AI-agent iterative refinement.
VibeCodeHPC adopts the Vibe Coding paradigm, which supports rapid prototyping and performance optimization even under uncertain or evolving specifications. In this approach, users provide requirements through prompts without formulating detailed specifications or engaging in manual code development. Detailed experiments are presented in Section III.
VibeCodeHPC comprises three primary components:
1.
LLM-based Code Generator: Generates initial HPC code from natural language specifications, incorporating domain constraints such as numerical accuracy requirements, target parallel programming models (MPI, OpenMP, CUDA, OpenACC), and architecture-specific considerations.
2.
Auto-Tuning Engine: Explores parameter spaces (thread counts, block sizes, tiling factors, communication strategies) using search algorithms including Bayesian optimization and genetic algorithms, collecting performance metrics for each configuration.
3.
Iterative Refinement through Prompting with AI Agents: This approach establishes a feedback loop in which performance evaluation results are fed back to the LLM, thereby guiding the iterative refinement of the generated code. Multiple specialized AI agents are responsible for sub-tasks such as performance data analysis, selection of parallelization strategies, and the evaluation of numerical accuracy trade-offs.
Fig. 1 illustrates the VibeCodeHPC architecture, showing interactions between the LLM and AI agents with the auto-tuning engine and multi-agent feedback. User-provided requirements are processed starting from the Experimental Planning AG (3) in Fig. 1.
Fig. 1: A conceptual design of VibeCodeHPC.
In Fig. 1, we assign the following five AI agents (AGs), each controlled by an LLM with user-specified execution scripts:
1.
Candidate Generation AG: Generates code variants through mutation and manages the candidate pool. Uses benchmark results (execution time, numerical accuracy) to guide subsequent generation.
2.
Candidate Selection AG: Selects promising candidates from the generated code pool. Defines benchmarking criteria and uses performance evaluation results for selection decisions.
3.
Experimental Planning AG: Creates code generation plans based on user requirements and produces necessary execution scripts. Incorporates selected candidates to enhance generation capabilities and triggers fine-tuning when sufficient code samples accumulate.
4.
Code Generation AG: Generates code following experimental plans using strategies including one-shot, multi-shot, and chain-of-thought approaches. Employs retrieval-augmented generation (RAG) to switch between commercial and local LLMs. Maintains generation history for the Benchmark/Code Verification AG.
5.
Benchmark/Code Verification AG: Verifies and benchmarks generated code through compilation and execution. Collects metrics including execution time, numerical accuracy, and script-specified benchmarks. Returns aggregated results to the Candidate Generation AG.
II-B Iterative Prompting Workflow
The VibeCodeHPC workflow consists of five iterative steps:
1.
Specification Input: Users provide natural language specifications including functional requirements, target hardware, performance goals, and optional constraints (acceptable accuracy loss, energy budget) through the Experimental Planning AG (AG3).
2.
Initial Code Generation: The Code Generation AG (AG4) produces an initial implementation using specified parallelization models. When no model is specified, the system proposes candidates based on historical data and hardware characteristics.
3.
Performance Evaluation: The Benchmark/Code Verification AG (AG5) executes generated code on the target system, systematically exploring parameter spaces and collecting metrics including execution time, energy consumption, and accuracy.
4.
Feedback Integration: The Candidate Generation AG (AG1) analyzes performance data through specialized agents, identifies bottlenecks (memory-bound kernels, load imbalance), and constructs refined prompts with recommendations for alternative strategies, loop transformations, or numerical approximations.
5.
Iterative Refinement: The entire loop in Fig. 1 updates code based on feedback, repeating until performance meets user thresholds or improvement rates fall below specified limits.
II-C AI Agent Collaboration
II-C1 Overview
VibeCodeHPC employs a multi-agent architecture with specialized agents for distinct optimization tasks:
•
Code Generation Agent: Produces performant HPC code from natural language prompts.
•
Performance Analysis Agent: Identifies bottlenecks and estimates optimization impact.
•
Parallelization Strategy Agent: Selects and configures parallel programming models (MPI, OpenMP, CUDA, OpenACC) based on workload and hardware characteristics.
•
Accuracy-Performance Trade-off Agent: Balances numerical precision with execution speed according to user constraints.
•
Auto-Tuning Orchestration Agent: Manages search algorithms and schedules parameter tuning experiments.
This agent-based design enables concurrent processing of auto-tuning tasks and facilitates integration of domain-specific optimization modules without system-wide modifications.
II-D Dynamic Inter-Agent Monitoring
Effective multi-agent collaboration requires dynamic information sharing regarding agent activity status (e.g., token usage), including token usage. Additionally, agent deployment must support runtime reallocation, enabling dynamic scaling of agents with identical objectives based on situational demands.
Existing multi-agent implementations (e.g., Tmux Multi-agent Communication Demo11
1
https://github.com/nishimoto265/Claude-Code-Communication/blob/main/README-en.md) support only fixed allocation at startup, lacking deployment flexibility. To address this limitation, VibeCodeHPC implements dynamic agent deployment, as illustrated in Fig. 2.
In Fig. 2, the PM agent launches via the launch script. Within the Common Processing Flow, hook functions control agent behaviors, preventing polling-type agents from entering idle states.
The Data Management component obtains agent IDs and session information, creating a database to store per-agent information including token consumption status. From this activity database, a Context Usage Report is generated periodically. This report enables users to monitor system status and allows the management agent to assess subordinate agent activity and issue appropriate instructions. Specifically, it provides data for evaluating memory compaction performed by the code generation agents’ auto-compact feature (Section III).
These mechanisms enable dynamic agent allocation, allowing the management agent to launch subordinate agents as needed, forming the core of VibeCodeHPC’s distinctive multi-agent functionality.
Fig. 2: Dynamic agent allocation and status monitoring in VibeCodeHPC.
II-E Advantages over Conventional Approaches
Compared to traditional code generation systems and standalone auto-tuning frameworks, VibeCodeHPC offers several key advantages:
•
Integrated generation and tuning: Performance optimization is embedded from the initial code generation stage through tight coupling.
•
Multiple parallelization model support: Multiple parallelization models are supported within a unified refinement loop.
•
Flexible performance trade-offs: User-defined constraints explicitly control the balance between numerical accuracy and computational speed.
III Performance Evaluation
III-A Experimental Environments
We conducted experiments using the Supercomputer “Flow” Type II Subsystem [3] at the Information Technology Center, Nagoya University.
The system specifications include: two Intel Xeon Gold 6230 CPUs (20 cores, 2.10-3.90 GHz); four NVIDIA Tesla V100 GPUs (2560 FP64 cores, up to 1530 MHz); 384 GiB DDR4 main memory (2933 MHz); and 32 GiB HBM2 device memory per GPU. The theoretical peak performance reaches 33.888 TFLOPS in double precision (1.344 TFLOPS per CPU socket, 7.8 TFLOPS per GPU). Memory bandwidth comprises 281.5 GB/s for main memory and 900 GB/s per GPU for device memory. GPU interconnection uses NVLINK2 (50 GB/s bidirectional), while CPU-GPU connection employs PCI-Express 3.0 (x16).
The underlying Claude Code is installed on a local PC, which also serves as the launch point for the multi-agent system. Code generation is performed on this PC, and the resulting code is transferred to the supercomputer via SSH. Job submission to the supercomputer is likewise initiated from the local PC. Notably, most of this workflow is implemented through script engineering within Claude Code. For efficient management of SSH and SFTP sessions, we employed Desktop Commander MCP22

https://github.com/wonderwhy-er/DesktopCommanderMCP, which is particularly recommended for supercomputers that require two-factor authentication.

III-E Discussion
III-E1 Achieved Performance and Multi-agent Behavior
In the solo-agent case shown in Fig. 3, only 24.1% of the theoretical peak performance was achieved. As a result, the project was gracefully terminated after 35 minutes, although the target execution time was set to 2–3 hours. In addition, the solo-agent failed to push the code to GitHub and improperly employed cuBLAS-based coding, which was explicitly prohibited in the requirements. We believe this behavior resulted from memory loss when the agent process was suspended (auto-compacted in Claude Code).
In contrast, the multi-agent version can mutually monitor whether the specifications are being satisfied. Therefore, it not only reduces violations of the requirement definitions but also enables the use of active memory for improved code generation. In other words, these can be considered decisive advantages of the multi-agent approach over the solo-agent approach.
Interestingly, although the PG achieved high performance, the CD issued a warning regarding the implementation that violated the requirements by using cuBLAS, and the PM ordered an emergency stop. This is a noteworthy interaction in the multi-agent system. Listing 2 shows these interactions.

III-E2 Generated Codes
Regarding the v1.4.0 CUDA optimization code (43.14% of theoretical performance) generated by the multi-agents, the following techniques were automatically incorporated:
1.
double buffering combined with read-only cache optimization to hide the access latency to the L2 cache;
2.
utilization of the read-only texture cache through the __ldg (read-only data cache) instruction;
3.
blocking scheme: BLOCK_M/N = 64, BLOCK_K = 16.
This implementation can be regarded as a valid one in CUDA. The fact that such code can be automatically generated is an interesting case, despite being the optimization of a simple matrix–matrix multiplication code, which is assumed to have abundant training data.
III-E3 Summary
In summary, the success of the multi-agent approach can be attributed to several factors. These include stepwise optimization, in which the implementation gradually progressed from a basic version to advanced optimizations; parallel development, where multiple programmers simultaneously explored different approaches; rapid feedback, enabling early detection of failures and timely course correction; and budget management, which allowed efficient job execution at low cost.
However, there remains considerable room for improvement. The achieved performance was only 43.14%, compared to the target of 60%. Time constraints also limited the opportunity to explore additional optimization methods. Furthermore, aggressive optimization attempts, such as those implemented in version 1.5.0, resulted in accuracy issues.
IV Related Work
IV-A LLM-Based Code Generation
Large language models (LLMs) including GPT-4, LLaMA 3, and Code LLaMA have significantly advanced automatic code generation. These models have demonstrated capabilities in producing syntactically correct and semantically meaningful code from natural language descriptions, with applications in software prototyping, automated bug fixing, and code refactoring. Chen et al. [4] showed that models trained on large-scale code corpora can generate effective solutions for programming contest problems. Austin et al. [5] and Li et al. [6] introduced prompt engineering and in-context learning strategies to improve code correctness and robustness. However, these studies primarily focus on general-purpose programming tasks without addressing HPC-specific performance constraints.
IV-B HPC Code Generation and Optimization
HPC code generation traditionally relies on domain experts to manually implement performance-critical kernels using parallel programming models such as MPI, OpenMP, CUDA, and OpenACC. Compiler-assisted approaches [7][8] have aimed to automate parts of this process by applying loop transformations, memory layout optimizations, and vectorization. More recent studies have investigated domain-specific languages (DSLs) [9][10] to generate optimized HPC kernels from high-level specifications. While these methods can yield high performance, they typically require explicit user annotations or DSL expertise, limiting their accessibility. The integration of LLMs into HPC code generation remains largely unexplored, especially in conjunction with automated performance tuning.
IV-C AT and Iterative Refinement
AT has been widely adopted in HPC to search parameter spaces and identify optimal configurations for target architectures. Frameworks such as ATLAS [11], OpenTuner [12], and GPTune [13] automate this process, often leveraging search algorithms like Bayesian optimization, genetic algorithms, or multi-armed bandits. Additionally, iterative refinement strategies—where code is repeatedly modified based on performance feedback—have been explored in machine learning-guided compilation [14] [15] . While these approaches are effective in optimizing existing code, their integration with LLM-driven code synthesis is still in its infancy.
IV-D Iterative Prompt in LLM-based Code Generation
Recent studies have explored iterative prompting in code generation AI. DiCuffa et al. [16] used the DevGPT dataset to demonstrate that structural prompt patterns enable high-quality outputs with fewer iterations. Sorokin et al. [17] introduced an iterative self-learning loop with re-ranking models and approximate policy optimization, achieving performance surpassing GPT-4. Ye et al. [18] proposed Prochemy, which automatically refines initial prompts based on execution results, enhancing performance in code translation and HumanEval tasks.
However, iteration can introduce vulnerabilities. Shukla et al. [19] reported a 37.6% increase in critical vulnerabilities after five iterations, highlighting the need for human oversight. From a structural perspective, Ren et al. [20] proposed Knowledge-driven Prompt Chaining (KPC) for exception handling, while Li et al. [21] introduced Structured CoT, improving Pass@1 accuracy by up to 13.79% on HumanEval. Ridnik et al. [22] demonstrated that test-driven, multi-stage iterative flows improved Pass@5 accuracy from 19% to 44%.
Wei et al. [23] investigated CUDA code optimization using multi-agent systems without additional training. However, the role-sharing approach proposed in our study has not been evaluated for cross-language optimization.
These studies constitute methodological investigations into iterative prompting. Research on AI-agent collaboration paradigms, as exemplified by VibeCodeHPC, remains nascent.
IV-E Summary
Existing research in LLM-based code generation has achieved significant progress in producing functionally correct programs, but it rarely addresses HPC-specific performance optimization. On the other hand, the HPC community has developed powerful auto-tuning and compiler-based optimization techniques, yet these methods often lack the flexibility and adaptability of LLM-based code synthesis. Bridging these domains—by integrating LLM-driven generation, HPC performance tuning, and iterative improvement—remains an open challenge, which our proposed VibeCodeHPC framework seeks to address.
V Conclusion
We presented VibeCodeHPC, a novel LLM-driven framework for generating and optimizing HPC code through tight integration of auto-tuning and iterative refinement. Unlike conventional code generation systems focusing primarily on functional correctness, VibeCodeHPC explicitly incorporates HPC-specific concerns including parallelization strategy selection, numerical accuracy–performance trade-offs, and architecture-aware optimization.
Our multi-agent architecture coordinates specialized AI agents to analyze performance metrics, explore parameter spaces, and refine generated code in a closed feedback loop. Experimental results demonstrate substantial performance improvements while preserving the flexibility of natural language–driven code synthesis. The framework features dynamic multi-agent deployment and activity monitoring, where aggregated reports enable management agents to issue appropriate instructions to subordinate agents.
Beyond addressing current limitations in LLM-based HPC code generation, VibeCodeHPC enables rapid performance prototyping under uncertain or evolving specifications, allowing both domain experts and non-experts to efficiently explore high-performance solutions.
Future work will extend the framework to:
•
Integrate dynamic workload adaptation for runtime performance optimization
•
Incorporate reinforcement learning for efficient auto-tuning parameter exploration
•
Support emerging heterogeneous computing platforms including exascale and quantum-accelerated systems
VibeCodeHPC represents a significant advancement toward bridging AI-assisted programming and expert-level HPC performance tuning, fostering a new generation of performance-aware, AI-driven development tools.
The iterative prompting approach of VibeCodeHPC can be implemented within existing auto-tuning frameworks, languages, and tools [24][25][26]. Integrating the proposed approach into auto-tuning systems represents progress toward broader generalization. #define BLOCK_M 64
#define BLOCK_N 64
#define BLOCK_K 16    // Reduced to fit in 48KB shared memory
#define THREAD_M 4
#define THREAD_N 4
__device__ __forceinline__ double ldg_double(const double* ptr) {
#if __CUDA_ARCH__ >= 350
return __ldg(ptr);
#else
return *ptr;
#endif
}
__global__ void gemm_kernel_optimized(
int M, int N, int K,
double alpha, const double* __restrict__ A, int lda,
const double* __restrict__ B, int ldb,
double beta, double* __restrict__ C, int ldc) {
// Double buffering for overlapping computation with memory access
__shared__ double As[2][BLOCK_M][BLOCK_K];
__shared__ double Bs[2][BLOCK_K][BLOCK_N];
// Block indices
const int bx = blockIdx.x;
const int by = blockIdx.y;
// Thread indices within block
const int tx = threadIdx.x;
const int ty = threadIdx.y;
const int tid = ty * blockDim.x + tx;
// Calculate thread’s output tile position
const int thread_row = (tid / (BLOCK_N / THREAD_N)) * THREAD_M;
const int thread_col = (tid % (BLOCK_N / THREAD_N)) * THREAD_N;
// Bounds check for thread mapping
if (thread_row >= BLOCK_M || thread_col >= BLOCK_N) return;
// Global position for this thread’s output
const int global_row = by * BLOCK_M + thread_row;
const int global_col = bx * BLOCK_N + thread_col;
// Register file for accumulation
double acc[THREAD_M][THREAD_N];
// Initialize accumulators
#pragma unroll
for (int i = 0; i < THREAD_M; i++) {
#pragma unroll
for (int j = 0; j < THREAD_N; j++) {
acc[i][j] = 0.0;
}
}
// Calculate loading responsibilities for this thread
const int A_loads = (BLOCK_M * BLOCK_K + blockDim.x * blockDim.y - 1) / (blockDim.x * blockDim.y);
const int B_loads = (BLOCK_K * BLOCK_N + blockDim.x * blockDim.y - 1) / (blockDim.x * blockDim.y);
// Pointers to current tiles in global memory
const double* A_global = A + by * BLOCK_M * lda;
const double* B_global = B + bx * BLOCK_N;
// Buffer index for double buffering
int write_buf = 0;
int read_buf = 1;
// Prefetch first tile into shared memory using read-only cache
#pragma unroll
for (int load = 0; load < A_loads; load++) {
int idx = tid + load * blockDim.x * blockDim.y;
if (idx < BLOCK_M * BLOCK_K) {
int row = idx / BLOCK_K;
int col = idx % BLOCK_K;
if (by * BLOCK_M + row < M && col < K) {
As[write_buf][row][col] = ldg_double(&A_global[row * lda + col]);
} else {
As[write_buf][row][col] = 0.0;
}
}
}
#pragma unroll
for (int load = 0; load < B_loads; load++) {
int idx = tid + load * blockDim.x * blockDim.y;
if (idx < BLOCK_K * BLOCK_N) {
int row = idx / BLOCK_N;
int col = idx % BLOCK_N;
if (row < K && bx * BLOCK_N + col < N) {
Bs[write_buf][row][col] = ldg_double(&B_global[row * ldb + col]);
} else {
Bs[write_buf][row][col] = 0.0;
}
}
}
__syncthreads();
// Main K-loop with double buffering
for (int k_tile = 0; k_tile < K; k_tile += BLOCK_K) {
// Swap read/write buffers
read_buf = write_buf;
write_buf = 1 - write_buf;
// Prefetch next tile (if not last iteration)
if (k_tile + BLOCK_K < K) {
#pragma unroll
for (int load = 0; load < A_loads; load++) {
int idx = tid + load * blockDim.x * blockDim.y;
if (idx < BLOCK_M * BLOCK_K) {
int row = idx / BLOCK_K;
int col = idx % BLOCK_K;
int global_k = k_tile + BLOCK_K + col;
if (by * BLOCK_M + row < M && global_k < K) {
As[write_buf][row][col] = ldg_double(&A_global[row * lda + global_k]);
} else {
As[write_buf][row][col] = 0.0;
}
}
}
#pragma unroll
for (int load = 0; load < B_loads; load++) {
int idx = tid + load * blockDim.x * blockDim.y;
if (idx < BLOCK_K * BLOCK_N) {
int row = idx / BLOCK_N;
int col = idx % BLOCK_N;
int global_k = k_tile + BLOCK_K + row;
if (global_k < K && bx * BLOCK_N + col < N) {
Bs[write_buf][row][col] = ldg_double(&B_global[global_k * ldb + col]);
} else {
Bs[write_buf][row][col] = 0.0;
}
}
}
}
// Compute with current tile in read buffer
#pragma unroll
for (int k = 0; k < BLOCK_K; k++) {
// Prefetch into registers
double a_reg[THREAD_M];
double b_reg[THREAD_N];
#pragma unroll
for (int i = 0; i < THREAD_M; i++) {
if (thread_row + i < BLOCK_M) {
a_reg[i] = As[read_buf][thread_row + i][k];
} else {
a_reg[i] = 0.0;
}
}
#pragma unroll
for (int j = 0; j < THREAD_N; j++) {
if (thread_col + j < BLOCK_N) {
b_reg[j] = Bs[read_buf][k][thread_col + j];
} else {
b_reg[j] = 0.0;
}
}
// Outer product accumulation
#pragma unroll
for (int i = 0; i < THREAD_M; i++) {
#pragma unroll
for (int j = 0; j < THREAD_N; j++) {
acc[i][j] += a_reg[i] * b_reg[j];
}
}
}
__syncthreads();
}
// Write results to global memory with coalesced access pattern
#pragma unroll
for (int i = 0; i < THREAD_M; i++) {
#pragma unroll
for (int j = 0; j < THREAD_N; j++) {
int row = global_row + i;
int col = global_col + j;
if (row < M && col < N) {
int idx = row * ldc + col;
// Use atomic operation for correctness in edge cases
if (beta == 0.0) {
C[idx] = alpha * acc[i][j];
} else {
C[idx] = alpha * acc[i][j] + beta * C[idx];
}
}
}
}
