# 学习理念

理解一种设计，是能解释它为什么成立、何时不再合适，以及替代方案付出了什么代价，而不是记住名称与公式。

## 从问题推导机制

先明确问题和约束，再从简单方案推导所需机制，最后引入术语、数学与工程实现。
让读者看见每一步设计的必要性，而不是直接接受标准答案；也不要为引出新技术，刻意把旧方案写成错误。

## 用约束变化串起技术

重要技术路线应讲清：

- 旧方案解决了什么，在什么条件下合理；
- workload、规模、硬件或 SLO 的哪项变化使它触及边界；
- 新机制如何改善问题，又增加什么成本、状态、耦合或 failure mode；
- 新旧方案分别适用在哪里，尚未解决的压力是什么。

这些是推理线索，不是逐章照填的模板。数学、实现与取舍应服务于同一问题，不按论文、框架或发布日期罗列。

## 分清技术关系

画演进箭头前，先判断关系：

- **直接演进（Direct Evolution）**：继承、扩展或替代已有设计。
- **分层 / 依赖（Layering / Dependency）**：解决不同层的问题，组合工作。
- **原理复用（Principle Reuse）**：采用相同原理，但不代表存在直接技术谱系。
- **解释性类比（Explanatory Analogy）**：帮助理解，不作为历史或实现证据。
- **替代分支（Alternative Branch）**：在不同约束下解决同一问题，并非先后替代。

例如，KV Cache 可以复用缓存原理，但不能因此称为 CPU Cache 的直接后代。
