# 同一次训练更新，三个框架如何组织

本节服务于主讲第 14～15 页。2026-09-23 重新核验官方架构、GRPO 和异步流程文档，2026-09-24 补核生成引擎、权重交接及 verl V1 异步流程；来源见 [S10～S16、S22～S27](./SOURCES.md)。下面的八条回答及奖励是教学设定，不是运行三个框架得到的结果；流程映射不等于默认配置，更不是统一硬件上的实测排名。

## 先固定共同问题

沿用迷宫任务：Q1、Q2 是两个不同起点的问题，每题独立生成四次路线，共八条回答。这里仅为算清分组，采用到达得 1、失败得 0 的结果奖励，不沿用动画的步数扣分。先固定同步 GRPO、同一个策略 v7、八条回答合成一个训练 batch、只执行一次 optimizer step。八条回答可以分多次前向和反向计算，但中途不更新参数；也不按两个问题训练出两个模型。Reference/KL 是否开启及其系数须另行对齐，不影响这里的分组说明。

| 问题 / Group | 四条回答 | 奖励 | 组内均值 | 本例的组内优势 |
| --- | --- | --- | ---: | --- |
| Q1 / G1 | a1、a2、a3、a4 | 1、1、0、0 | 0.5 | +1、+1、−1、−1 |
| Q2 / G2 | b1、b2、b3、b4 | 1、0、0、0 | 0.25 | +1.732、−0.577、−0.577、−0.577 |

优势计算采用 `(奖励 − 本组均值) / 本组标准差`，本例标准差按四条样本的总体公式计算，分别为 0.5 与约 0.433；忽略防止除零的微小量。实际 recipe 的标准差自由度、是否除标准差和 loss 归一化必须明确，不能拿这组数冒充三框架默认输出。

八条回答不合成一个八人比较组；G2 的成功回答相对本组更突出，但不能仅凭优势大小断言它产生更大的最终参数更新。Token 概率、长度权重、裁剪及其他损失项也会参与。全部回答参与同一套共享参数的更新，不是只保留最高分答案。

```text
2 prompts × 4 responses
        ↓
G1: a1 a2 a3 a4    G2: b1 b2 b3 b4
        ↓
分别算组内优势 → 8 条回答的训练 batch
        ↓
按显存切 microbatch → backward / 梯度累积 → 一次 optimizer step
        ↓
共享参数 v7 → v8 → 同步给生成端 → 下一轮重新生成
```

Group 是比较单位，训练 batch 是一次更新使用的数据，microbatch 是显存允许的一次计算量。三者不必相同。比如每次只能计算两条回答，可以分四次 backward，并按全 batch 的目标权重累积梯度，再执行一次更新；不是每两条重新计算一个组的优势。实际分布式实现还须核对跨 worker 的归约与样本/token 计数，不能把各小批均值不加权地随意相加。[verl GRPO 的 batch 与归一化说明](https://verl.readthedocs.io/en/latest/algo/grpo.html)

每条回答要带着题目及组身份、准确 token IDs、行为概率、奖励、结束原因与 action mask 进入训练。v7 是教学中的生成快照标记，不声称各框架都使用同名版本字段；异步模式还要更精细地追踪生成期间的策略变化。生成逐 token 执行，训练可并行处理已知序列，外部评分又可能等待程序返回。这才是框架要组织的不同工作。

## vLLM 加速的是哪一段

在线 RL 需要不停生产新尝试。八条回答长短不同，简单地等整个生成 batch 全部结束，会让先结束的槽位空着；预留每条最大长度的 KV 又可能浪费容量。连续批处理按迭代接入、移出请求，PagedAttention 用非连续 blocks 管理增长中的 KV，改善生成阶段的调度和内存使用。这些机制让同样资源可能产出更多回答，不会替我们选择奖励、计算优势或执行策略梯度，也不保证消除所有空等与碎片。推理机制入口见 [PagedAttention](https://arxiv.org/abs/2309.06180)。

先分别观察生成、评分、概率/价值重算、参数更新、权重交接的耗时与等待，再判断瓶颈。长输出、多次采样常给生成侧很大压力；慢工具、外部验证器或复杂训练也可能先成为限制。不能用一个固定的“rollout 占比”推导所有训练都该先换推理引擎。vLLM 是框架可接入的执行组件，不是与 verl、miles、SkyRL 同层的算法替代品；具体框架可能选择 SGLang 或其他生成后端。

## 把八条回答放进三个框架

下面固定同样的数据与优化目标，只改变执行组织。表里的先后是同步教学顺序，不代表内部每项操作必须串行，也不是可直接运行的 API。

| 这一轮发生什么 | verl 的阅读路径 | miles 的阅读路径 | SkyRL 的阅读路径 |
| --- | --- | --- | --- |
| Q1、Q2 各尝试四次 | 控制器把生成任务交给 rollout workers | Rollout 层把生成请求交给 SGLang engines | Generator 组织尝试，InferenceEngine 执行生成 |
| 八条回答得分 | RewardManager / 奖励逻辑把分数与样本对应 | 内置或自定义 reward 函数处理 rollout 结果 | Generator 联合 Environment / 任务逻辑返回轨迹与奖励 |
| G1、G2 分别算优势 | GRPO estimator 按题目分组；数据对象交接角色结果 | 配置 GRPO 目标，训练前保留 rollout group 身份 | Trainer 用配置的 estimator 处理 Generator 交付的数据 |
| 八条回答更新同一模型 | Actor workers 在选定训练后端计算梯度 | Actor 的 Megatron / FSDP 后端执行更新 | Trainer 的训练 workers 执行更新 |
| v8 交给生成端 | 通过选定的训练/rollout 后端完成权重交接 | 权重更新路径把训练参数送到 SGLang | 通过配置的 inference engine 权重同步路径交接 |
| 下一轮继续 | 控制器推进下一轮算法流程 | Rollout 继续生产，训练继续消费 | Generator 再采轨迹，Trainer 再优化 |

这些环节三个框架都需要。差别在于它们把哪些复杂性封装为主要接口，以及扩展、诊断时应该先看哪里。具体调用名会随版本变化；来源为 [verl 架构](https://verl.readthedocs.io/en/latest/hybrid_flow.html)、[Miles Core Concepts](https://miles.radixark.com/docs/user-guide/concepts) 与 [SkyRL System Overview](https://docs.skyrl.ai/docs/getting-started/overview)。

## 设计重心

| 维度 | verl | miles | SkyRL |
| --- | --- | --- | --- |
| 理解入口 | 算法控制流与分布式计算流分离 | rollout、trainer 与权重交接的一致性和效率 | 训练、生成、环境与 Agent 的可替换接口 |
| 主要证据 | HybridFlow 与官方架构指南 | Miles v0.1 报告、radixark 仓库 | 当前统一库、Generator/环境接口与 Agent 文档 |
| 同题四回答如何进入更新 | 控制器组织角色调用和 batch 数据，worker 执行后端计算 | rollout groups 交给 trainer，按运行模式处理缓冲与版本 | generator 产生轨迹，环境反馈接入 trainer 的数据流 |
| 值得优先评估的需求 | 研究不同目标、角色和训练/推理后端组合 | 已依赖 SGLang，重视大模型 rollout/训练交接 | 自定义多轮环境、任务生成与 Agent 轨迹 |
| 需要付出的工程成本 | 组合空间大，数据布局和配置须一致 | 需验证模型适配、路由/数值一致性与滞后策略 | 模块接口、环境终止与 token mask 必须准确实现 |

“值得评估”是根据设计重点作出的判断，不是排他能力声明。三个框架都有重叠能力，不能把 verl 写成只能做单轮、miles 写成只能使用一个训练后端，或 SkyRL 写成只做 Agent。

## verl：把“做什么”与“怎样算”分开

对于这个 GRPO 例子，控制器表达生成、评分、优势计算和更新的顺序；计算角色负责把调用落到模型执行。好处是换一个奖励函数不必重新实现全部分布式计算。新的约束是：当角色、后端和布局被自由组合时，传递的数据仍必须代表同一个数学目标。

具体追踪 Q2 的 b1：它属于 G2，得分为 1，优势约为 +1.732。即使调度为了平衡长度把 b1 放到另一个 worker，它仍属于 G2，不能改与旁边的 a3 比较。Actor worker 收到的不只是 b1 的文字，还包括参与 loss 的位置和对应的概率、优势。研究者主要在算法流程、estimator 与角色接口上表达“怎么利用这八条数据”，训练后端负责“怎么把计算铺到设备上”。改成 PPO 时会增加价值预测和 Critic 更新，不是只把配置名字换一下。

阅读时先看 [HybridFlow 指南](https://verl.readthedocs.io/en/latest/hybrid_flow.html) 的控制/计算分层，再回官方仓库定位训练循环、数据对象和 worker。指南中的 `RayPPOTrainer`、`WorkerGroup`、`DataProto` 可以作为阅读线索，不应被当作任何新模式都不变的公共 API。

教学追问：如果两个 worker 对同一批序列采用不同长度归一化，即使各自都能 backward，是否仍在执行同一个更新？答案是不一定。接口能传 tensor，不等于接口已经表达清楚统计含义。

### 概率不一致时，先诊断，再选择校正

假设 b1 某个 token 的生成概率为 0.20，训练端重算为 0.12。若参数已经更新，差异可能是预期变化；如果相同权重、token 与上下文仍有显著差异，则需检查精度、计算路径及生成设置。不能只看两个数字就认定训练坏了，更不能把生成/训练策略差异与保留 SFT 行为的 reference KL 混为一谈。

verl 的 [Rollout Correction](https://verl.readthedocs.io/en/latest/algo/rollout_corr.html) 提供相应策略的 logprob 比较、重要性加权与拒绝采样等选项：用概率关系调整样本贡献，或让异常样本不进入指定目标。截断有偏差/方差取舍，过滤会丢失数据。文档中的差异指标、有效样本量与拒绝比例可帮助判断更新是否依赖少数异常样本；具体比较哪两个策略取决于模式。校正不能补救 token 错位、奖励定义错误，也不能创造没采到的成功经验。此处数值为教学设定，不是框架实测。

## miles：让生成与训练处理同一个行为

根据 [v0.1 报告](https://arxiv.org/html/2609.08368v1)，SGLang 负责 rollout，训练可选择 Megatron-LM 或 FSDP；中间还必须完成权重同步和轨迹交接。报告关注 token 级交接、MoE 路由一致性及异步执行。其出发点是生成端与训练端即使加载同一份参数，也可能因为数值、路由或 token 处理差异而产生不一致。

把本例映射到官方 Core Concepts 的采样/训练计数：`rollout_batch_size=2`、`n_samples_per_prompt=4`，在该文档描述的无过滤计数关系下，可以配成 `global_batch_size=8`、`num_steps_per_rollout=1`。这解释了“两题”不等于“训练 batch 只有两条”。这是文档字段的数值映射，不是完整可运行配置；异步、样本过滤和具体 recipe 需要重新核对。

例如 b1 的回答经过文本解析、模板重建再分词后，训练端可能得到与生成时不同的 token 序列。Token-In-Token-Out（TITO）保留实际 token 路径；报告中的 session server 记录并复用历史 token，避免任意重建。对支持的 MoE 路径，Rollout Routing Replay（R3）进一步记录并重放生成时的 expert 选择，减少训练端走到另一组 expert 的不一致。前者保护行动序列，后者保护部分计算路径，不能互相替代，也不保证全部数值一致。额外元数据与模型适配都是成本；报告 §2.4～2.5 有适用边界，不由机制名称推出所有配置精确 on-policy。

教学追问：异步生成的回答来自 v7，而 trainer 已更新到 v10，这条数据是否过期？没有仅由“差三版”决定的通用答案；至少需要真实行为概率、变化幅度、接受规则及效果验证。

## SkyRL：把任务交互变成可训练轨迹

[当前仓库](https://github.com/NovaSky-AI/SkyRL) 已把此前训练库与 Tinker 后端工作整合进统一 `skyrl`，并保留 Agent 与 Gym 组件。解释设计时应聚焦生成、训练和环境交接，不应继续用旧目录名称替代整个框架。

从算术扩展到查询数据库：模型产生查询，环境返回结果，模型继续回答。自定义 generator/环境接口负责把这段交互组织成轨迹。训练端不仅需要字符串，还需要明确哪些 token 来自策略、哪些来自环境，以及停止是因为成功、失败还是时间预算耗尽。接口设计降低了表达新任务的成本，但不会自动解决信用分配与奖励漏洞。

放回本例，Generator 返回 a1～b4 八条轨迹，Environment / 任务逻辑给出是否到达的分数，Trainer 仍按 G1、G2 的比较结果更新共享参数。若把 Q2 改成“每走一步都返回新视野”的多轮迷宫，每个 b 回答会包含多次行动和环境观察，而不是把四次尝试变成同一条轨迹的四个步骤。需要扩展的是交互与轨迹组织，GRPO 同题比较的含义不因此改变。官方 `GeneratorOutput` 的 token、reward、loss mask、stop reason 等字段提供接口线索；Agent Integration 页面标注 WIP，不能把字段列表当作永久兼容契约。

教学追问：把数据库返回文本也算进 policy loss，会发生什么？模型被要求提高并非自己生成的 token 的概率，训练目标已经改变；这不是普通 padding mask 能自动解决的问题。

## 训练完成后，怎样让新策略真正生效

Actor trainer 已经得到 v8，不代表 rollout engine 自动变成 v8。要交付的是可用于前向生成的策略参数，不是 Critic 的价值参数，也不必把训练所需的全部 optimizer state 交给推理端。训练和推理采用不同分片或权重格式时，还要完成必要转换。这里以全参数策略更新为例，adapter 更新有自己的加载与身份管理要求。

```text
策略 trainer 得到 v8
→ 建立生成交接窗口，按约定处理在途请求
→ 按需转换、传输并加载策略权重
→ 确认相关 workers 完成，处理旧 KV / prefix cache
→ 记录新版已可用，恢复生成
```

[vLLM v0.21.0 Weight Transfer](https://docs.vllm.ai/en/v0.21.0/training/weight_transfer/) 区分初始化、开始、传输、结束阶段，提供 NCCL 和 CUDA IPC 后端。前者可用于分离 GPU 的训练/推理，后者用于同卡进程间交接；不能据此把共置描述成 Actor/Critic 参数相同或同步零开销。上图是正确交接需要满足的概念顺序，不承诺单个 API 自动完成所有版本与故障管理。

在途请求的选择也有代价：等待其结束会受长尾拖延，中止后重采浪费已有工作，保留 token 并用新权重续写则使一条轨迹可能跨版本。[vLLM v0.19.0 Async RL](https://docs.vllm.ai/en/v0.19.0/training/async_rl/) 说明了相应暂停模式与 cache 清理选项；[verl V1 Async Trainer](https://verl.readthedocs.io/en/latest/advance/v1_async_trainer.html) 描述保留 token/logprob、用新版本恢复、重建前缀 KV 的路径。已有 token 是历史行动，可以保留；KV 是旧参数计算出的中间状态，不能无条件冒充新参数的计算结果。具体实现和允许的近似须按配置核对。

最后区分两份交接：权重送到生成端，决定以后的尝试；轨迹从生成端送到训练端，说明此前真正做过什么。v8 同步完成，不会把已完成的 v7 回答自动变成 v8 的样本。

## 同步与异步：优化等待，也改变数据新鲜度

```text
第1批：Q1、Q2 各四答；第2批：Q3、Q4 各四答。
先启动：第1批八条完成，评分与组信息准备好。

同步：生成端   [等待训练]       [接收 v8]  [开始第2批，v8]
      训练端   [训练第1批→v8]   [交接 v8]  [等待第2批]

异步：生成端   [生成第2批，v7]  [接收 v8]  [继续后续尝试]
      训练端   [训练第1批→v8]   [交接 v8]  [检查第2批 → 接受后更新到v9]
```

同一列表示同时发生的工作，不表示各阶段等长。异步第 2 批假设在权重交接前生成并评分完；第 1 批尚未准备好时，训练端依然要等，不能训练尚未生成的回答。重叠要求独立资源或可调度的资源余量，不能认为两个满载任务在同一张 GPU 上会免费并行。提前采样时 v8 尚未完成，v7 是当时可用的参数，而不是明明有新策略却故意不用。

第 2 批是 Q3、Q4 上真实发生的新经历，不是正确答案库；训练第 1 批得到 v8，不意味着已经学会这些任务。因此，旧版本生成的数据仍可能有价值，但不能冒充当前策略的采样。保存其 token、奖励、行为概率与版本，用 v8 重算目标所需概率，再按算法校正、截断或过滤。若这八条完整数据符合接受规则，就可以用于下一次更新 v8→v9；这是当前参数上的新梯度，不是给 v8 直接加上 v7 的旧梯度。校正有偏差/方差和数据覆盖边界，不保证与新鲜采样等价，也不保证 v9 更好。机制入口见 [Rollout Correction](https://verl.readthedocs.io/en/latest/algo/rollout_corr.html)。

动画另一种结局假设两组旧回答都不符合接受规则：丢弃这些回答，用 v8 重采 Q3、Q4，等完整、评分并检查后再更新。在新数据到达前，训练端仍要等待。这说明提前做的采样可能白做，异步不是无损加速。两个结局只是受控情景，不以版本差 1 自动判定质量；真实实现也可以按组接受、过滤及补齐，而不必整批同命运。

同步更容易建立清楚的版本边界，但慢轨迹会拖延整个 batch。异步可重叠阶段，却引入策略滞后和分布偏移。过滤超时样本也有代价：它可能系统性删除困难、长轨迹任务。两种方式都需要以任务有效进展而非单纯 GPU 忙碌率衡量价值。上图是概念对照，不宣称三个框架采用完全相同的异步算法。

### 如果只有 b4 一直没完成

在前面固定的同步八条 batch 中，七条先完成不意味着可以把 G2 改成三条比较后照常更新。要等待 b4，或按预先约定的超时、重试及过滤规则处理，并明确统计样本是否已经变化。这是三框架共同面对的算法条件，不是某一家框架特有的缺点。

| 改用其他执行方式时 | 官方材料提供的机制线索 | 不能误解成什么 |
| --- | --- | --- |
| verl V1 Async Trainer | 共置/分离模式、partial rollout、版本滞后及整组处理；具体调度不同 | 单控制器不等于只能同步；保留部分 token 不等于可以无条件沿用旧 KV |
| miles Fully Async | 生成端持续生产，buffer 管理完成的组，trainer 按规则消费 | G1 完成不代表在 global batch 仍要求八条时可以直接用四条更新；也不能把未完成 G2 静默改组 |
| SkyRL one-step off-policy 示例 | 用生成/训练两个循环和队列，让下一批生成与当前批训练重叠 | 这是批次流水线，不等于自动取消 b4 的等待；与 fully async、partial rollout 不是同一种机制 |

因此，异步不是消灭依赖，而是在更多批次之间重叠工作。只有这八条数据且不改变 batch 条件时，可重叠空间本来就有限。若允许消费其他已完成组，需要承认训练样本组合和策略新鲜度也变了。Miles 的 buffer 接受/过滤策略见 [Fully Async](https://miles.radixark.com/docs/user-guide/fully-async)；SkyRL 的批次流水线见 [One-Step Off-Policy](https://docs.skyrl.ai/docs/tutorials/one_step_off_async)。两者都不是无代价的吞吐开关。

### 从“效果不好”缩小到可以验证的原因

miles 的异步文档提供队列长度、已消费及队列中数据的策略滞后、超时和过旧组过滤数等指标。队列持续为空提示生成供给不足；持续堆满且滞后增加提示训练消费跟不上。版本覆盖指标也很重要：没有版本记录不等于数据新鲜。版本差只是一种可操作的接受依据，不直接证明样本有害，过滤阈值仍需验证。

这使工程排查有了入口，却不是自动根因诊断。奖励全零可能因为题太难，也可能是解析器或评分程序坏了；训练奖励上涨而验证下降，可能是奖励漏洞，也可能是数据分布不同。应抽查八条轨迹的输入、实际 token、评分依据、结束原因、组身份与生成记录，再以固定样本重算、同步对照等方式验证假设。这里是排查建议，不宣称框架能自动完成这些判断。

减少等待与错误数据可能提高同样时间预算中的有效尝试数量，但不能把 throughput 增加等同于学习收益。探索不到成功样本、奖励与真实目标错位、未见任务不泛化，仍要靠任务设计和评估处理。框架机制能减少系统造成的失败，不能证明受约束的全局最优，也不能保证每次运行取得同样结果。

## 用这个案例做选择，而不是给框架排名

只跑两个单轮问题，三个框架的核心结果应由对齐后的算法和数据解释，案例本身不足以选出胜者。选择的依据是下一步最可能变化的东西：频繁换优势、loss 或计算角色时，优先检查 verl 的流程与后端组合；已有 SGLang、主要压力是大模型生成/训练交接时，优先检查 miles 的一致性与权重同步路径；任务正从一问一答变成多轮环境交互时，优先检查 SkyRL 的 Generator/Environment 契约。这是评估起点，不是排他推荐。

讲者可追问：“b1 被移动到另一个 GPU，属于哪个组？只有七条完成能否更新？v8 训练完成但生成端仍是 v7，下一轮是什么数据？”能回答这三个问题，才算理解了框架在保护什么，而不只是记住三个名字。

## 对照实验应固定什么

一次有效的框架比较应固定模型与 tokenizer revision、数据划分、奖励程序、temperature、输出上限、组大小、loss normalization、KL/clip 设置、精度、硬件与评估预算。分别测量采样、评分、更新、权重同步时间，同时报告有效轨迹数、截断率、测试成功率和资源成本。

同样叫“GRPO”的默认配置可能并不相同。先核对目标，再比较性能；先做小规模正确性检查，再扩大模型。框架能减少重复工程，但不能替代任务定义、奖励审计和独立评估。
